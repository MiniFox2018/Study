# 第 15 章：智能体间通信（A2A）

> 来源：<https://adp.xindoo.xyz/chapters/>  
> 整理语言：中文

## 本章定位

建立智能体之间的消息、任务、状态和能力交换机制，支持跨智能体协作。

## A2A 管的是跨 Agent 的任务交接

本章的 A2A 指 Agent2Agent 协议；一般的多 Agent 消息传递不必都实现该协议。A2A 把远端 Agent 当作内部实现不透明的服务，让调用方发现能力、传递任务、接收状态和结果，而不要求共享其提示词、工具或内部记忆。

官方核心概念包括 Agent Card（身份、能力、入口及认证要求）、Message（一次通信）、Task（有 ID 与生命周期的工作）、Part（文本/文件/结构化内容单元）、Artifact（可交付成果）。短请求可以直接返回消息，长任务可返回可跟踪任务；不要把所有响应都当成最终完成。

## 具体例子：委托一个文档抽取 Agent

调用方先检查 Agent Card 是否支持 PDF 表格抽取，并确认访问权限；提交文件引用和输出字段约定后取得任务 ID。对方可能要求补充页码，或返回处理中状态；完成时交付表格 Artifact，调用方仍要核对页数、字段和原始数据。状态更新与成果内容是两回事。

轮询、流式或推送用于获得进展，具体支持方式取决于双方能力和协议版本。取消、超时、重复消息、身份验证和文件 URL 的访问控制都需实现。

## 自检与核对

**问题**：已有 MCP，为什么有时还需要 A2A？

**核对**：MCP 常用于应用访问外部工具/上下文；A2A 强调与另一个不透明 Agent 协作及任务生命周期。边界可以组合，并非互相替代；简单本地工作流也不必同时引入两种协议。

核验日期：2026-10-02。依据：[A2A 官方核心概念](https://a2a-protocol.org/latest/topics/key-concepts/)。这是持续更新的 latest 文档；本章只保留概念，实施时固定规范/SDK 版本再查方法名和传输绑定。

## 来自《深入理解 AI Agent》的增量吸收

- A2A 适合放在“不共享上下文的多 Agent 协作”中理解：不同 Agent 通过显式消息、任务、状态和能力描述协作。
- 跨组织协作尤其需要标准协议，因为参与方通常不共享内部上下文、文件系统和实现细节。
- 协议之外仍需解决身份、权限、任务交接、结果验证、超时与失败恢复，否则“能通信”不等于“能协作”。

## 固定协议后再交接任务

跨组织文档抽取的难点是：调用方不能直接读对方的文件系统，也不能假定双方使用同一框架。先约定可观察的输入、状态、结果与失败，才能让一个 Agent 把工作交给另一个 Agent。需要的先修是 JSON、HTTP/JSON-RPC、身份认证与任务状态机；一般多 Agent 的角色设计见[多智能体协作](07-多智能体协作.md)，权限判断见[安全模式](18-安全模式.md)。

下面固定 **A2A v1.0.0**，核验日期 2026-10-08，协议源码 tag 对应 commit `173695755607e884aa9acf8ce4feed90e32727a1`。协议接口的 `protocolVersion: "1.0"` 与 Agent 自己的应用 `version` 是两个版本。Python/TypeScript 对象能在同一进程传递，不证明其 JSON 符合协议，更不证明 TLS、身份认证、流式传输或远端恢复已经工作。[固定版规范](https://a2a-protocol.org/v1.0.0/specification/)、[固定版 a2a.proto](https://github.com/a2aproject/A2A/blob/173695755607e884aa9acf8ce4feed90e32727a1/specification/a2a.proto)。

本轮第一来源`1a8c4fd`的v1.0.1课程/手册增量在章末集中维护。先理解下面的对象和状态，再读新增的绑定、扩展、事件与验收合同，避免把维护历史当先修。

### Agent Card：发现的输出是候选能力与接口

客户端可以读取 `https://{domain}/.well-known/agent-card.json`，也可以从受信目录或显式配置取得 Card。Card 说明 Agent 的入口、媒体类型、技能和安全要求；它本身不证明当前用户有权调用。客户端选择 `supportedInterfaces` 中第一个自身支持的接口；若接口含 `tenant`，后续请求按该值传递。这个 tenant 是路由标识，其业务授权含义由服务定义，不能把任意正文里的 tenant 当作认证结果。

以下为固定版 **JSON 数据示例，未发送网络请求**。示例声明只接受文本和 JSON，因此上传 PDF 前必须重新核查该 Agent 的媒体类型支持，不能因为 A2A 有 raw/url 字段就假定任何服务都会解析 PDF。

```json
{
  "name": "文档抽取 Agent",
  "description": "从已经获准访问的文本中抽取指定字段。",
  "supportedInterfaces": [
    {"url": "https://extract.example/a2a", "protocolBinding": "JSONRPC", "protocolVersion": "1.0", "tenant": "research"}
  ],
  "version": "2.1.0",
  "capabilities": {"streaming": false, "pushNotifications": false},
  "defaultInputModes": ["text/plain", "application/json"],
  "defaultOutputModes": ["application/json"],
  "skills": [
    {"id": "extract_fields", "name": "抽取字段", "description": "按给定字段与证据边界抽取；缺字段时请求补充。", "tags": ["extraction", "evidence"]}
  ]
}
```

技能的 `inputModes` / `outputModes` 可覆盖 Agent 默认媒体类型；`skills[].tags` 是当前必需字段。`skills` 主要描述能力，不是调用方法表。实际 `SendMessageRequest` 没有通用的顶层 `skill_id` 参数，如何选择业务技能由请求内容或约定扩展决定。原课的 `schemaVersion`、顶层 `url`、`"text"/"file"/"artifact"` 模式与 `/.well-known/agent.json` 不能直接拼成当前 Card。

### Message、Task 与 Artifact 各承担什么

一次 Message 有调用方创建的 `messageId`，角色使用 ProtoJSON 的 `ROLE_USER` / `ROLE_AGENT`。Part 必须恰好包含 `text`、`raw`、`url`、`data` 中一个内容字段；`raw` 在 JSON 中是 base64，`data` 可以是任意 JSON 值，文件名与媒体类型使用 `filename` / `mediaType`。base64 可解码只证明字节表示正确，不证明它是真 PDF、无恶意内容或有访问授权；url 也需有效期、出站访问策略和身份绑定。

Task 的服务端生成 `id` 与可选 `contextId` 用来关联工作；状态放在 `status.state`，并非 Task 顶层 `state`。Artifact 是任务的输出，必须有任务内唯一的 `artifactId` 与至少一个 Part。调用方应核对其字段、证据和版本，不以“completed”替代业务验收。

JSON-RPC 绑定发到 Card 指定的 URL，使用 `A2A-Version: 1.0`；认证凭据走该绑定规定的头或元数据。以下请求有两个不同层的标识：JSON-RPC `id` 匹配本次 RPC 回应，`messageId` 匹配业务消息。给 JSON-RPC 换一个 id，不会自动让业务请求幂等。

```json
{
  "jsonrpc": "2.0", "id": "rpc-1", "method": "SendMessage",
  "params": {
    "tenant": "research",
    "message": {"messageId": "msg-1", "role": "ROLE_USER", "parts": [
      {"text": "从材料中抽取字段，并保留来源。", "mediaType": "text/plain"},
      {"data": {"sourceId": "policy:7", "text": "申请需要申请表与证明。"}, "mediaType": "application/json"}
    ]}
  }
}
```

缺少字段列表时，服务可以返回任务并请求补充，而非猜出一个 schema：

```json
{
  "jsonrpc": "2.0", "id": "rpc-1",
  "result": {"task": {
    "id": "task-1", "contextId": "ctx-1",
    "status": {"state": "TASK_STATE_INPUT_REQUIRED", "message": {
      "messageId": "agent-msg-1", "contextId": "ctx-1", "taskId": "task-1", "role": "ROLE_AGENT",
      "parts": [{"text": "请给出要抽取的字段列表。"}]
    }}
  }}
}
```

随后仍用 `SendMessage`，新 `messageId`，在 message 内携带 `taskId: "task-1"`；若同时携带 contextId，两者须匹配。`GetTask` / `CancelTask` 的 params 使用 `id`，不能误写成 `taskId`。gRPC 对应同名方法；HTTP+JSON 对应 `POST /message:send`、`GET /tasks/{id}`、`POST /tasks/{id}:cancel`。三种绑定共享逻辑模型，认证、错误与行为需要等价，而实际序列化和传输各自验收。A2A 的 `GetTask` 与 MCP Tasks 的 `tasks/get` 属于不同协议，不能共用未经转换的 Task 对象。

### 状态机、归属与断线恢复

常见顺序是 `SUBMITTED → WORKING → INPUT_REQUIRED → WORKING → COMPLETED`，JSON 中写完整 `TASK_STATE_*` 枚举。`INPUT_REQUIRED` 是缺信息；`AUTH_REQUIRED` 是需要额外授权，它只表达暂停原因，不授予任何操作权限。`COMPLETED`、`FAILED`、`CANCELED`、`REJECTED` 为终态，不能再接受新的任务消息。协议允许在非终态接收后续消息，业务实现仍要明确哪些状态可续接、允许更改哪些输入。

每次读取、续接、取消、订阅、推送配置都检查当前认证主体与任务访问边界；知道 task ID 或 context ID 不是权限。服务可按用户、角色、项目或租户授权。本章 fixture 选择“同 tenant 的 owner 才能操作”作为教学策略，协议本身并未强制单 owner 模型。任务 TTL 与清理策略也由部署定义。[任务授权范围](https://a2a-protocol.org/v1.0.0/specification/#131-data-access-and-authorization-scoping)。

取消是请求，服务会尝试执行，可能与完成竞争。客户端超时表示没有及时观察到结果，不意味着远端取消；先 `GetTask`，必要时 `CancelTask` 后确认返回状态。重复取消应有同等效果，已清理任务可返回未找到。完成先赢时不把 completed 改成 canceled；取消先赢时停止接纳后续工作。涉及付款、写文件等副作用时，取消并不回滚已提交效果，需业务 receipt 与补偿策略。

`SendMessage` 的幂等是 **MAY**，不是协议保证所有服务都会去重。明确需要安全重试时，服务把 `(tenant, actor, messageId)` 与完整消息摘要和原响应持久绑定，同 ID 同内容返回原响应，同 ID 改内容拒绝；当次仍先复核权限。客户端断线后以 task ID 查状态，并验证 artifact 身份；仅换 request ID 重发可能创建第二个任务。

### 一个可运行的任务归属、取消与重放实验

输入是已由外部认证边界确认的 actor/tenant，以及一个包含 `targetLength` 的业务 Message。输出是当前协议形状的 Task 快照；业务产物只是固定教学文本。程序仅用 SQLite 临时目录、虚拟 TTL 和标准库。每条消息在同一事务中更新任务与重放记录，重新打开数据库后仍可取得原响应。它没有网络、真实 Agent、PDF 解析或 OAuth，也未证明分布式远端副作用恰好执行一次。

```python
import copy, hashlib, json, sqlite3, tempfile
from contextlib import contextmanager
from pathlib import Path

TERMINAL = {'TASK_STATE_COMPLETED', 'TASK_STATE_FAILED',
            'TASK_STATE_CANCELED', 'TASK_STATE_REJECTED'}
def canonical(x):
    return json.dumps(x, sort_keys=True, separators=(',', ':'), allow_nan=False)

class TaskStore:
    def __init__(self, path, clock, allowed):
        self.db = sqlite3.connect(path, isolation_level=None)
        self.clock, self.allowed = clock, allowed
        self.db.executescript('''
          CREATE TABLE IF NOT EXISTS tasks (
            id TEXT PRIMARY KEY, owner TEXT, tenant TEXT, context TEXT,
            expires INTEGER, snapshot TEXT);
          CREATE TABLE IF NOT EXISTS inbox (
            tenant TEXT, owner TEXT, message_id TEXT, digest TEXT, reply TEXT,
            PRIMARY KEY(tenant, owner, message_id));''')
    @contextmanager
    def atomic(self):
        self.db.execute('BEGIN IMMEDIATE')
        try:
            yield
            self.db.commit()
        except BaseException:
            self.db.rollback()
            raise
    def auth(self, actor, tenant):
        if (tenant, actor) not in self.allowed:
            raise PermissionError('当前访问权限不足')
    def load(self, actor, tenant, task_id):
        self.auth(actor, tenant)
        row = self.db.execute('SELECT context,expires,snapshot FROM tasks '
                              'WHERE id=? AND owner=? AND tenant=?',
                              (task_id, actor, tenant)).fetchone()
        if row is None or self.clock() >= row[1]:
            raise LookupError('任务不可访问或已过期')
        return json.loads(row[2])
    def send(self, actor, tenant, message):
        self.auth(actor, tenant)
        if (message.get('role') != 'ROLE_USER' or
            not isinstance(message.get('messageId'), str) or not message['messageId'] or
            not isinstance(message.get('parts'), list) or not message['parts']):
            raise ValueError('Message 必需字段')
        for part in message['parts']:
            if not isinstance(part, dict) or len(set(part) & {'text','raw','url','data'}) != 1:
                raise ValueError('Part 恰好一个内容字段')
        digest = hashlib.sha256(canonical(message).encode()).hexdigest()
        key = (tenant, actor, message['messageId'])
        with self.atomic():
            old = self.db.execute('SELECT digest,reply FROM inbox '
                                  'WHERE tenant=? AND owner=? AND message_id=?', key).fetchone()
            if old:
                if old[0] != digest:
                    raise ValueError('同 messageId 改内容')
                replay = json.loads(old[1])
                self.load(actor, tenant, replay['id'])  # 重放也核归属与 TTL
                return replay
            task_id = message.get('taskId')
            if task_id:
                task = self.load(actor, tenant, task_id)
                if task['status']['state'] in TERMINAL:
                    raise ValueError('终态不接受新消息')
                if message.get('contextId', task['contextId']) != task['contextId']:
                    raise ValueError('contextId 与 taskId 不匹配')
            else:
                task_id = 'task-' + str(self.db.execute('SELECT count(*) FROM tasks').fetchone()[0]+1)
                task = {'id': task_id, 'contextId': message.get('contextId', 'ctx-'+task_id),
                        'status': {'state': 'TASK_STATE_SUBMITTED'}, 'history': [], 'artifacts': []}
                self.db.execute('INSERT INTO tasks VALUES (?,?,?,?,?,?)',
                                (task_id, actor, tenant, task['contextId'], self.clock()+10, canonical(task)))
            task['history'].append(copy.deepcopy(message))
            task['status']['state'] = 'TASK_STATE_WORKING'
            data = [p['data'] for p in message['parts'] if isinstance(p.get('data'), dict)]
            length = next((d['targetLength'] for d in data if 'targetLength' in d), None)
            if length is None:
                task['status']['state'] = 'TASK_STATE_INPUT_REQUIRED'
            elif length not in {'short', '3 paragraphs'}:
                raise ValueError('业务 targetLength 枚举')
            else:
                task['artifacts'] = [{'artifactId': 'summary-1', 'name': '教学摘要',
                                     'parts': [{'text': '固定材料摘要：申请需要申请表。',
                                                'mediaType': 'text/plain'}]}]
                task['status']['state'] = 'TASK_STATE_COMPLETED'
            self.db.execute('UPDATE tasks SET snapshot=? WHERE id=?', (canonical(task), task_id))
            self.db.execute('INSERT INTO inbox VALUES (?,?,?,?,?)', (*key, digest, canonical(task)))
            return copy.deepcopy(task)
    def cancel(self, actor, tenant, task_id):
        with self.atomic():
            task = self.load(actor, tenant, task_id)
            if task['status']['state'] == 'TASK_STATE_CANCELED':
                return task
            if task['status']['state'] in TERMINAL:
                raise ValueError('完成或失败已赢得竞争')
            task['status']['state'] = 'TASK_STATE_CANCELED'
            self.db.execute('UPDATE tasks SET snapshot=? WHERE id=?', (canonical(task), task_id))
            return task

def fails(exc, call):
    try: call()
    except exc: return
    raise AssertionError('应拒绝')
now = [0]; allowed = {('research','alice'), ('research','bob')}
with tempfile.TemporaryDirectory() as folder:
    dbpath = str(Path(folder)/'tasks.sqlite')
    store = TaskStore(dbpath, lambda: now[0], allowed)
    msg = {'messageId':'m1', 'role':'ROLE_USER', 'parts':[{'text':'抽取材料'}]}
    first = store.send('alice','research',msg)
    assert first['status']['state'] == 'TASK_STATE_INPUT_REQUIRED'
    fails(LookupError, lambda: store.load('bob','research',first['id']))
    fails(ValueError, lambda: store.send('alice','research',dict(msg, parts=[{'text':'改内容'}])))
    follow = {'messageId':'m2','taskId':first['id'],'role':'ROLE_USER',
              'parts':[{'data':{'targetLength':'short'}}]}
    final = store.send('alice','research',follow)
    store.db.close()
    store = TaskStore(dbpath, lambda: now[0], allowed)
    assert store.send('alice','research',follow) == final  # 持久重放快照
    fails(ValueError, lambda: store.send('alice','research',dict(follow, messageId='m3')))
    fails(ValueError, lambda: store.cancel('alice','research',final['id']))
    waiting = store.send('alice','research',dict(msg, messageId='m4'))
    assert store.cancel('alice','research',waiting['id']) == store.cancel('alice','research',waiting['id'])
    allowed.remove(('research','alice'))
    fails(PermissionError, lambda: store.send('alice','research',follow))
    allowed.add(('research','alice')); now[0] = 10
    fails(LookupError, lambda: store.load('alice','research',final['id']))
    store.db.close()
print('归属隔离、同ID冲突、重启重放、终态、取消幂等、撤权、TTL边界通过')
```

上述校验只覆盖本例字段子集：完整协议客户端还应验证 text/raw/url/data 的类型、支持媒体类型、配置、响应 oneof 与错误映射。代码中的摘要是固定产物；增加真实抽取时，需记录输入资料 identity 与输出 evidence ID 并做独立准确性评测。

### 流式结果与 Card 签名的有效边界

流式任务先给 Task，随后给状态或 Artifact 更新；聚合 Artifact 时按 `(taskId, artifactId)` 处理 `append` 与 `lastChunk`。例如三段 `A`、`B`、`C`：首段替换/初始化，第二段 append，第三段 append 且 lastChunk，得到 `ABC`。lastChunk 只结束该 Artifact，不能据此宣布整个任务 completed。断线重订阅不能盲目追加旧片段；使用协议或部署约定的恢复信息，必要时 `GetTask` 取权威快照；没有片段身份/序号约定时不能自行声称任意重放去重。

Card 的 `signatures` 是 **可选 JWS**，用 JCS 规范化 payload，并按 ProtoJSON 字段存在语义处理默认值，排除 signatures 自身；信任密钥、算法与发布者关联需独立判断。对排序 JSON 做 HMAC 可以练习篡改检测，但 `json.dumps(sort_keys=True)` 不等于完整 JCS，也不是标准 AgentCard JWS 验证器。**AP2 是支付相关协议，不是 Card 签名或通用授权方案**；2026-10-08只核[AP2官方入口的用途与mandate概念](https://ap2-protocol.org/)，未展开支付实现。Card 完整性、TLS 服务身份、请求认证、业务授权是四个不同问题：一张签名正确的 Card 仍可拒绝用户读取别人的任务。[Card 签名](https://a2a-protocol.org/v1.0.0/specification/#84-agent-card-signing)、[认证与授权](https://a2a-protocol.org/v1.0.0/specification/#7-authentication-and-authorization)。

MCP 工具也可包装 Agent，其执行内部未必透明。将每个 MCP tool 一对一暴露为 A2A skill 可能增加协议和状态管理，却仍只做函数调用；只有跨边界委托有独立任务生命周期、持续交互或成果交付价值时，这层适配才合理。

## 原课五项练习的核对与替代验收

1. **走完整生命周期**：原 PY/TS 在内存中经历 working→input_required→working→completed，文件为 fake-pdf、输出为模板；当前 wire 用完整枚举。上面实际运行的是自写 SQLite 教学状态机，不是原脚本或远端 A2A。合格证据包含暂停、续接同 task、artifact identity，以及越权和终态拒绝。
2. **修改 Card 后签名失效**：HMAC 练习的参考判断是“消息字节变化，原 MAC 不能通过”。它只证明已共享密钥下的篡改检测；正式交付应按 JWS/JCS、受信 key、算法与字段存在语义验证，并把签名与调用授权分开。本批未执行加密库或官方 JWS fixture。
3. **三段 Artifact**：按上节 A/B/C 累积得到 ABC，第三段结束 Artifact；另核 task status、重复交付和断线快照恢复。只有真实 SSE 收到对应事件才可称流式集成通过，本批未开服务器。
4. **MCP 包装为 A2A**：答案应说明每个 skill 的媒体类型、任务/错误/权限映射，是否保留工具具体身份，以及付出的任务生命周期复杂度。封装内部工具不要求暴露推理文本；不能把名字映射表当远端协作成功。
5. **“没有任何框架实现某 multi-hop 功能”**：原题是某时点生态断言，不能给永久唯一答案。改为评判协议是否支持授权请求链，接着对所用框架固定版本检查 SendMessage、任务归属、AUTH_REQUIRED、传递凭据边界、取消传播与恢复证据。没有逐框架证据时写“未核”，不能断言全生态未实现；本轮没有测试框架互操作。

## 消息意图、通信合同与身份：从FIPA遗产读现代协议

2026-10-10 吸收第一来源 Phase16 第02、03课。先修是本章已有Message/Task/Artifact、终态与重放边界；本次补充的是意图语言、协议职责的比较与源码中的验证缺口。现行A2A wire继续按上述v1.0.0，不把来源的自定义Python/TypeScript对象拼成另一套“最新协议”。

### 一个消息有意图，不只是内容字符串

同一句“报告生成”可以是命令、已完成通知，或询问当前状态；如果接收方猜错，重试可能重复执行，通知也可能被误当授权。FIPA-ACL把**performative（交际动作）**与content和关联信息分开，长期有效的思路是：明确“请求做什么、提出什么、承诺什么、报告什么”，再定义相应的后续状态。

| 意图族 | 典型动作 | 内容与后续判断 |
| --- | --- | --- |
| 告知 | inform、inform-if、inform-ref、confirm、disconfirm | 告知命题或查询值；接收者仍检查证据，不由动作名证明事实 |
| 请求/查询 | request、request-when、request-whenever、query-if、query-ref | 描述动作、前提或问题；可拒绝、暂停、失败，request不等于已执行 |
| 协商 | cfp、propose、accept-proposal、reject-proposal | 邀请报价、提交提议、选中或拒绝；提议与实际执行分开 |
| 承诺/控制 | agree、refuse、cancel、failure、not-understood | agree承诺尝试，inform可报告完成；cancel与补偿也不同 |
| 中介/订阅 | proxy、propagate、subscribe | 转发/代理/持续告知；关联对象、范围与取消须另约定 |

表列22个动作名，2026-10-10由[JADE官方ACLMessage API](https://jade-project.gitlab.io/API/jade/lang/acl/ACLMessage.html)的动作常量核对；不含UNKNOWN扩展哨兵。原课“20个”及仅16个源码allowlist不能当完整目录。**FIPA00061是Message Structure，FIPA00037是Communicative Act Library**，不是同一文档。本轮原FIPA官网HTTP/HTTPS返回403，原规范详细节号与形式语义没有重新完整取得；不把官方实现词汇核对写成原规范全文审查。

content language与ontology说明如何读载荷及共享词义，conversation-id关联业务会话，reply-with/in-reply-to帮助匹配消息；它们不等同于认证、权限、幂等key或执行回执。来源的“只有七字段”“ontology必填”是过度简化。形式语义中的信念/意图是在模型假设下解释消息，不是只收到inform就能证明发送者诚实或命题真实。指定相同ontology也不能让任何语义错误在parse时自动拒绝。

自然语言可以解释目标，但关键字段应结构化：对象ID、操作、单位、时间、主体/租户、允许参数、输入版本、期限和输出契约。JSON Schema能拒绝shape/type错误，不能保证“customer”指同一业务对象、金额单位一致或调用者有权付款。typed artifact说明模态，不自动证明语义或来源正确。

### 契约网：从邀标到有界执行

Contract Net的基本顺序是manager发cfp，bidders提交propose，manager选中accept-proposal并拒绝其他proposal，获选者执行后报告结果或失败。每份proposal至少关联任务、报价者、有效期、资源条件与版本；取最小分数前先检查可执行性与业务约束，不能用最便宜覆盖权限或安全拒绝。

例：三份教学报价为A价格3/18分钟，B价格2/25分钟，C价格4/10分钟。若本地政策为`price + ETA/10`，分数分别4.8、4.5、5.0，因此选B；这个公式混合两种单位，ETA/10代表显式定义的时间代价权重，不是通用市场机制。最短ETA选C，严格要求20分钟以内则B不可选，说明约束筛选要先于效用排序。

| 当前状态 | 事件 | 安全的后续行为 |
| --- | --- | --- |
| collecting | 新proposal | 核身份、任务/轮次、期限和范围后收录 |
| collecting | 期限到 | 按固定可行集合与规则award或无可接受报价 |
| collecting | manager撤回 | 原子置cancelled，迟到proposal/award拒绝 |
| awarded | 重复award | 同proposal/摘要按约定去重；不同提议拒绝 |
| running | cancel/timeout | 请求停止并确认实际effect，不能假设回滚 |
| completed | 新动作 | 原任务终态保持；必要时开新任务/补偿流程 |

取消防止已经不需要的工作继续；重试只重发请求，不解决撤回。收到cancel消息、接受取消、实际阻止动作、已经执行的效果补偿是不同阶段。跨服务exactly-once效果仍需要目的端回执和幂等契约，不能由manager日志保证。

源02只把字典render成类似ACL的文本，没有decoder、规范parser或无损round-trip；`content!r`也只是Python表示。源A2A `POST /tasks`和自填input/task_id不是本章已核v1.0.0绑定。该例适合做功能类比，不能声称现代消息“除了语法完全等价FIPA”。

## 按职责选择协议，不按营销标签叠层

| 需要解决的问题 | 可以参考的协议/模式 | 仍需实现的边界 |
| --- | --- | --- |
| 从外部server取得工具/资源/提示能力 | MCP能力发现与调用 | host授权、输入校验、工具身份、结果消费与副作用 |
| 委托不透明的远端Agent并持续跟踪 | A2A Card/Message/Task/Artifact | 当前主体的任务访问、取消/重放/断线恢复与成果验收 |
| 保留执行轨迹、出处与session信息 | ACP历史run/metadata设计、受控事件账本 | 从真实一次执行取得轨迹、采集脱敏与访问控制 |
| 跨域声明身份、证明密钥控制并协商合同 | DID与ANP相关设计 | 可信解析/算法/key用途、撤销、重放、业务权限和可执行协议准入 |

这不是强制四层栈。MCP工具可包装不透明Agent，本地角色可以只用显式消息和调度代码；反过来，Agent委派也可继续用MCP访问能力。[MCP通信与状态工程](../06-专题扩展/06-MCP通信与状态工程.md)已有固定2026-07-28合同。来源02的 `server/discover`、`subscriptions/listen` 不是那份规范中已核的能力发现/订阅方法；实施用具体能力与对应方法，不发明名称补齐历史类比。

原03的ACP输出prompt仍声称JSON-LD、正文已改REST/JSON，ANP输出prompt又声称trust graph、正文否认；同来源内部也会矛盾。[2505.02279v1](https://arxiv.org/html/2505.02279v1)实际作者为Ehtesham等，非原02所称Liu。该综述的ACP描述是REST-native多部分消息和stream，ANP讨论DID与JSON-LD；这是2025年的架构说明，不是2026年所有方法的标准合同。

历史ACP设计的轨迹元数据不证明“每个响应有完整真实推理链”，也不保证某行业合规。可审计执行主要依靠可信边界产生的工具调用、输入/输出摘要、授权、效果回执和来源关系；模型自述“我查过”不能替代这些。隐藏思维文本不是默认应采集的审计字段。协议生态、迁移状态与SDK方法继续由[框架概览](../02-附录/C-智能体框架快速概览.md)按版本核验，本章不把“ACP专属合规、A2A只轻量”作为选择规则。

blocking、async和stream三种交付方式也不能混同：blocking等待当前执行结果；async先给可查询ID，再查状态；stream在连接上连续送进展/产物。async的202或stream的最后一帧不能自行证明效果完成，run/session标识也不等于主体权限。轨迹的一条可检验记录可包括`run_id、parent_id、sequence、actor、input_digest、tool_request_digest、effect_receipt、status、version`，citation另绑定结果段和原资料位置；它们来自可信运行边界，而非允许模型自由补写。记录字段存在，只证明格式，仍需检查真实性、范围与保留/读取政策。

### DID、签名、加密与授权是四种不同判断

DID标识与验证方法可帮助确认对某个key的控制；HTTPS取得DID文档，也仍需防受众错配、恶意解析目标、过期cache、撤销与算法替换。认证成功回答“谁以何种证据发请求”，不回答“现在可以执行哪一步”。key的controller、authentication、keyAgreement等用途应核对，不能同一公钥换一个type标签就当另一套密钥。

源03的 `createIdentity` 只生成Ed25519密钥，把同一DER公钥放进标记X25519的记录。它没有独立密钥协商、HPKE或端到端加密；`humanAuthorization`只是一组字段，gateway未检查它，更未取得真实人类批准。`requiresHumanAuth`对unknown DID返回false也不能作为安全默认。是否需要人审应按可信策略拒绝未知情况，不从源字段名推导授权。

更直接的问题是gateway只验证`signature(message.id)`：攻击者保留ID和签名，换成不同载荷、目标Agent或操作仍可通过该检查。签名应绑定双方实际采用的完整合同：具体body、接收者/受众、nonce/时间、协议与策略版本；验证后还要查当前权限。协商自然语言所说“accepted”不能自动执行生成的协议代码，也不能跳过schema、安全与预算准入。

### 完整CPU例：签名ID的缺口与完整请求的重放边界

本例用本地共享key的HMAC演示字节绑定，**不是DID签名、JWS/JCS、ANP或正式网络认证实现**。严格固定字段与规范化JSON的教学子集；使用可信调用者参数与当前allowlist模拟身份/业务授权。相同message_id变更body、换recipient、重放nonce、撤权、过期和NaN均拒绝。时钟与key固定用于复核，真实部署另需安全密钥、时钟政策、原子持久nonce/receipt及可信解析。

```python
import hashlib, hmac, json, math
from copy import deepcopy

KEY = b'fixture-only-not-a-real-credential'
FIELDS = {'message_id', 'actor', 'recipient', 'action', 'body',
          'nonce', 'issued_at', 'expires_at'}
def encode(req):
    if type(req) is not dict or set(req) != FIELDS:
        raise ValueError('固定完整字段')
    for name in FIELDS - {'body', 'issued_at', 'expires_at'}:
        if type(req[name]) is not str or not req[name]:
            raise ValueError('非空字符串字段')
    for name in ('issued_at', 'expires_at'):
        if type(req[name]) not in (int, float) or not math.isfinite(req[name]):
            raise ValueError('有限时钟')
    if type(req['body']) is not dict:
        raise ValueError('固定body对象')
    return json.dumps(req, sort_keys=True, separators=(',', ':'),
                      allow_nan=False).encode()
def mac(req):
    return hmac.new(KEY, encode(req), hashlib.sha256).hexdigest()

class Gateway:
    def __init__(self, recipient, allowed):
        self.recipient, self.allowed = recipient, allowed
        self.nonces, self.inbox = set(), {}
    def accept(self, authenticated_actor, req, tag, now):
        p = deepcopy(req)
        raw = encode(p)
        if type(now) not in (int, float) or not math.isfinite(now):
            raise ValueError('有限当前时间')
        if (type(tag) is not str or len(tag) != 64 or
            any(ch not in '0123456789abcdef' for ch in tag) or
            not hmac.compare_digest(mac(p), tag)):
            raise PermissionError('请求字节被更改')
        if authenticated_actor != p['actor'] or p['recipient'] != self.recipient:
            raise PermissionError('主体或受众不匹配')
        if (p['actor'], p['action']) not in self.allowed:
            raise PermissionError('当前业务权限不足')
        if not p['issued_at'] <= now < p['expires_at']:
            raise ValueError('请求尚未生效或已过期')
        digest = hashlib.sha256(raw).hexdigest()
        key = (p['actor'], p['message_id'])
        if key in self.inbox:
            old_digest, receipt = self.inbox[key]
            if digest != old_digest:
                raise ValueError('同message_id改变合同')
            return deepcopy(receipt)  # 无第二次执行；当前权限/有效期先核
        nonce_key = (p['actor'], p['nonce'])
        if nonce_key in self.nonces:
            raise ValueError('nonce被其他请求使用')
        self.nonces.add(nonce_key)
        receipt = {'message_id': p['message_id'], 'digest': digest,
                   'state': 'accepted'}  # 只接纳，不表示业务已完成
        self.inbox[key] = (digest, deepcopy(receipt))
        return receipt

def fails(exc, call):
    try: call()
    except exc: return
    raise AssertionError('应拒绝')
req = {'message_id':'m1', 'actor':'alice', 'recipient':'researcher',
       'action':'read', 'body':{'document':'doc:7'}, 'nonce':'n1',
       'issued_at':1, 'expires_at':10}
weak_tag = hmac.new(KEY, req['message_id'].encode(), hashlib.sha256).hexdigest()
changed = deepcopy(req); changed['body']['document'] = 'doc:other'
assert hmac.compare_digest(weak_tag,
    hmac.new(KEY, changed['message_id'].encode(), hashlib.sha256).hexdigest())
g = Gateway('researcher', {('alice','read')})
tag = mac(req)
fails(PermissionError, lambda: g.accept('alice', changed, tag, 2))
fails(PermissionError, lambda: g.accept('alice', req, '不是MAC', 2))
fails(PermissionError, lambda: g.accept('bob', req, tag, 2))
other = dict(req, recipient='coder')
fails(PermissionError, lambda: g.accept('alice', other, mac(other), 2))
first = g.accept('alice', req, tag, 2)
assert g.accept('alice', req, tag, 3) == first
fails(ValueError, lambda: g.accept('alice', changed, mac(changed), 3))
replay = dict(req, message_id='m2')
fails(ValueError, lambda: g.accept('alice', replay, mac(replay), 3))
g.allowed.clear()
fails(PermissionError, lambda: g.accept('alice', req, tag, 3))
g.allowed.add(('alice','read'))
fails(ValueError, lambda: g.accept('alice', req, tag, 10))
fails(ValueError, lambda: mac(dict(req, issued_at=True)))
fails(ValueError, lambda: mac(dict(req, body={'score':float('nan')})))
assert len(g.inbox) == 1
print('ID签名可被换body；完整合同、主体/受众、重放、撤权和时间边界通过')
```

同ID同字节返回receipt是本例的业务重试政策；不是协议普遍规定所有重复都成功，也不是只靠nonce实现业务幂等。allowlist只校主体/action，没有完整对象级权限；把document从doc:7换成别人的对象，仍须另核访问边界。此处key、权限、nonce和inbox都在同一进程，无并发事务、持久恢复与实际效果；通过assert只能证明该本地子集，不是正式认证的充分证据。服务应在一个真实执行轨迹里产生审计事件，不能为了“audit”又运行一次业务handler。

## 协议演示源码的终态、结果与轨迹缺口

源03文中先audit后task，独立源码先`await processTask`再audit；两者顺序不同，而且auditable handler与task handler是两个函数。示例共享的researchTrajectory是可变全局列表，多run会混合痕迹；它没有真正的MCP连接、HTTP绑定或跨服务验证。log中的reasoning/工具返回都是canned材料，不能当实际查证结果。

`TaskManager`在正常event前检查终态，却在catch里无条件写failed；取消后handler抛异常，或listener在completed事件中抛异常，都可能覆盖终态。需要在唯一状态提交边界核current state、allowed transition、task/run epoch与owner；观测listener失败不应擅自改变业务成功/取消。错误与取消动作单独留轨迹。

同artifact ID且`append=false`应按协议/合同替换相应artifact，而来源直接push会制造重复；返回的Task、Card与artifact也有可变引用。event.taskId未匹配当前task，未实现input-required续接与auth-required恢复；这些不能凭有八个字符串状态就说“完整状态机”。已有本章SQLite例负责任务归属/重放/终态，本轮旧代码不重复运行。

协议合同还需关心payload版本、缓存与背压。TTL Card缓存减少发现请求，但key应含受众/tenant/endpoint/版本；旧cache不授权新操作，失效或撤销先于命中率。大量并发发现可用single-flight、限速和stagger，不能把100个模拟lookup叫生产herd测量。流式快照必须深拷贝或不可变，sequence/range和最终状态可恢复；“stream结束”与“业务完成”分别验收。

### 本次增量：v1.0.1的发送模式与绑定合同

2026-10-19继续吸收第一来源`1a8c4fd`的Phase13/19、Phase16/03与/12。上面的v1.0.0与既有离线程序保留原核验日期；本节核到 **v1.0.1 tag、commit `3303592588e388e62e0f69f701af531d2f4e3991`** 的[Proto](https://github.com/a2aproject/A2A/blob/3303592588e388e62e0f69f701af531d2f4e3991/specification/a2a.proto)和[规范正文](https://github.com/a2aproject/A2A/blob/3303592588e388e62e0f69f701af531d2f4e3991/docs/specification.md)。源提交时间仍为2026-10-15，协议版本、教材版本、整理日期三个时间对象分开。接口仍报`protocolVersion: "1.0"`，不要把patch号1.0.1机械塞到要求major.minor的协商字段。

**发送Message不等于永远异步创建Task。** `configuration.returnImmediately`省略或为false时，v1.0.1明确要求等待Task到终态或中断态才返回；true才要求创建后尽快返回，调用者再查询或订阅。直接返回Message时这个开关不影响结果；流式方法也有自己的事件协议。例如抽取服务缺字段，默认发送可直接得到`INPUT_REQUIRED`，不是必须先看到`SUBMITTED`再轮询；补充输入仍发新messageId、关联同taskId，不能重新创建一个没有上下文的新任务。阻塞语义也不消除HTTP deadline、客户端超时和未知效果，需要按既有GetTask/CancelTask合同恢复。

| 绑定 | 发送与返回的外壳 | 易混点 |
|---|---|---|
| JSON-RPC | Card入口上的PascalCase `SendMessage`，JSON-RPC id/result/error；普通JSON用`application/json` | RPC id与业务messageId不同；HTTP+JSON的返回体不能原封套在result之外 |
| HTTP+JSON | `POST /message:send`与`GET /tasks/{id}`等映射；协议JSON用`application/a2a+json` | Card仍是普通JSON；流式响应是`text/event-stream`，不能把协议JSON MIME当SSE MIME |
| gRPC | 同一逻辑服务的二进制请求/响应与metadata | 不把ProtoJSON的字段名/枚举字符串直接当二进制wire字节 |

Part按`text/raw/url/data`内容字段区分，且恰有一个。数据可为数组、标量或null，不限对象；TS写成几个可重叠object union并不构成运行时oneof校验。`filename`和`mediaType`不是另一种内容。Task状态用完整枚举；Artifact用`artifactId`，不能仅将旧`kind`删除却继续用`id`冒充协议字段。状态时间是协议Timestamp的JSON字符串表示，`Date.now()`毫秒数只是演示内部时钟，序列化前必须按绑定转换。状态/Artifact事件还需对应的taskId和contextId，不能靠同进程回调的隐式当前任务代替。

**流的结尾、Artifact结尾与Task终态分别判断。** v1.0.1 `StreamResponse`只在task、message、statusUpdate、artifactUpdate四种载荷中选一，没有旧的`final`字段。直接Message响应是一条事件；任务流先Task再更新。`lastChunk=true`只结束对应Artifact；收到INPUT_REQUIRED表示要补信息，AUTH_REQUIRED表示要走获准的认证过程，都不是业务成功，也不能以关闭网络流当完成。断线之后可以重订阅仍在进行的Task，但标准没有由此保证重放全部历史事件或业务副作用恰好一次。

固定v1.0.1内部也有需明示的冲突：Proto的HTTP注解把SubscribeToTask映射为`GET /tasks/{id}:subscribe`，规范方法表/部分HTTP说明写POST；抽象流说明建议AUTH_REQUIRED时保持流，HTTP详细段又写中断态也关闭。这里保留冲突，分别标来源，不能悄悄选一处称所有SDK都如此。实际实现要冻结生成依据/绑定/SDK版本，用请求响应测试确认，先GetTask恢复权威状态；本次没有运行SDK或网络互操作，不以某一页文字补造兼容性。

### 扩展、绑定与路由：怎样增加能力而不混版本

**扩展改变语义，绑定改变接线。** Extension为某领域规定额外数据、流程或方法；custom binding把同一抽象操作接到另一传输。使用WebSocket传数据，不会自动获得A2A的Task、错误、认证与恢复语义；增加地理位置metadata，也不会自动改变HTTP/SSE为另一传输。前者要定义错误、顺序、结束、重连、凭据与服务参数的映射，后者要定义字段schema、单位、必需性、依赖与版本。声称同一Agent支持多个绑定，就要验证其声明能力在各绑定等价，不能一路提供push配置、另一路同操作只报404。

扩展的一条完整链是：

1. 在Card的`capabilities.extensions`中声明URI、描述、是否required以及扩展定义的params。params是服务声明的数据，不应与每次请求metadata混为一谈。
2. 客户端理解该URI对应的固定规范，核所需依赖，再在当前请求的`A2A-Extensions`服务参数中请求激活。HTTP用逗号分隔的URI列表；Message/Artifact自身的`extensions`字段说明该对象涉及哪些扩展，不代替请求激活。
3. 服务识别自己支持的扩展，验证其额外输入并实施对应行为；不支持的可选扩展可被忽略。客户端没激活required扩展时，应按该版返回ExtensionSupportRequiredError，不能把必需的校验降成一句提示。
4. 响应推荐声明实际激活的URI。若业务正确性依赖该行为，客户端仍要核实际结果与可验证回执，不能把请求头发出或HTTP200当已执行扩展。

教学例：假设扩展URI为`https://policy.example/extensions/review/v1`，约定审阅请求metadata携带base/head，并要求报告逐项绑定这两个版本。URI用于命名这份协议，实际值、schema与效果由双方约定；只在Card写required不会检查Git，更不授予读取私有仓库的权限。将来不兼容地改变字段或批准含义应使用新标识，不能沿旧URI悄悄改变语义。扩展可以用metadata细分WORKING的业务阶段，不能任意加一个核心TaskState枚举值或删除必填字段还称基础协议兼容。自定义方法也要经过同样的身份、资源和动作授权。

**路由不是认证。** 多Agent共享入口可按URL子路径分流、由可信网关按认证凭据映射目标，也可使用接口声明的opaque tenant。选择`AgentInterface`含tenant时，客户端按该值在后续请求中传递；没有声明就省略，不能随意从用户正文捏造一个“管理员tenant”。不同绑定如何映射tenant应按固定规范的路径/请求/metadata定义处理，URI组成部分需要正确编码。无论用了哪种路由，服务仍从真实身份判断对该Agent、Task、Artifact和后端资源的权限。一个名为billing的路由字符串不证明用户拥有billing数据。

**给协议说明排证据优先级。** 固定v1.0.1的Proto为跨绑定数据模型依据；规范抽象操作、绑定段与官方topic页互相核对，发生冲突保存双方位置。官方页面的README、博客与“What's New”也可能没同步更新。这里的14页聚合已经与官方固定tag逐页核成相同正文，但“确实是官方文件”仍不等“每个例子都符合该版Proto”。学习迁移时保留正确目标形式：

| 对象 | 固定v1.0.1应核什么 | 官方说明里不能直接照抄的旧草稿 |
|---|---|---|
| Card与安全 | supportedInterfaces逐接口protocolVersion，capabilities.extensions，securitySchemes＋securityRequirements包装 | 顶层url/protocolVersions/extensions/security，或不带schemes/list的简写 |
| 消息与分块事件 | ROLE_*、Part oneof；StreamResponse的statusUpdate/artifactUpdate | taskStatusUpdate/taskArtifactUpdate包装名、额外index或旧final |
| 分页 | pageSize/pageToken/nextPageToken及结束空token | cursor/limit/nextCursor不是该Proto字段；不能把名字相似的SDK便利函数当wire |

表格是防止混版本的校验方法，不要求保存一套旧协议实现。双版本服务应明确按哪一个接口/版本进入哪一个adapter，分别测试输入、输出、错误与权限；不能将两版可接受字段任意合并、悄悄降级或用“SDK兼容”承诺所有操作互通。安装指令、页面上的“一个月内迁移”与产品时间表不作为本库的执行要求。

**主分支澄清另列，不冒充tag要求。** 教材还保存A2A主分支`679ab3a`、2026-10-05快照。本次从官方固定commit重新取得并核为同字节，复用已全文审过的v1.0.1基线，只完整审查其全部差分。该快照修正了push配置对象名、部分contextId/安全包装示例、每接口版本迁移措辞，并增加[任务内授权范围§7.6.4](https://github.com/a2aproject/A2A/blob/679ab3afc6f95ef47bb969d511053d0f63bca2a2/docs/specification.md#764-in-task-authorization-scope)：AUTH_REQUIRED本身不授予某项操作权限，凭据/批准的含义、有效期、撤销及后续消息是否仍可复用由具体实现、issuer或扩展定义。它支持本章已有的动作与产物绑定方法，但不能反过来称这段文字早已存在于v1.0.1，也不把该main快照宣布为最新正式发布。

### 迁移不能只换字段名：默认值、存在性与信任合同

**同一个布尔槽位也可能表达相反意思。** v0.3.0 Proto 的`blocking`为true时等待、false时立即返回；固定v1.0.1改成`returnImmediately`，true立即返回，false等待至终态或中断态。两者都用字段号4，却不能原样复制值。若旧请求明确指定`blocking=false`，适配后的意图应为`returnImmediately=true`；旧true映射为新false。更容易漏掉的是“未提供”：旧非optional布尔值默认false，新布尔值也默认false，但等待行为已经翻转。迁移前先确定旧客户端实际意图，再显式映射；不能仅把字段名替换后沿用所有默认值。对直接Message回复和流式调用，这个开关另有适用边界，见前面的发送模式。

`historyLength`同样要保留存在性。旧v0.3.0非optional整数以0表示不限制；新v1.0.1是optional，省略与明确0不同。新0要求不返回历史，省略表示客户端未施加该上限，服务仍可有默认保留/返回政策。把所有缺失整数填0，会悄悄把原本期望得到历史的请求改成无历史。适配验收至少保留“省略、0、1”的独立样例，再检查返回的具体消息，不只比较请求能否解析。

这也解释了为什么“Proto字段号相同”不能证明二进制兼容。旧服务包名为`a2a.v1`，新为`lf.a2a.v1`，完整gRPC方法路径随之变化；其他请求字段的重新编号、嵌套和oneof也必须核。用旧生成客户端调用新服务，不能靠加一个版本header自动转换。版本适配器应明确放在边界上，把旧业务意图转换成新对象，再验证响应和错误；SDK便利API与线上wire格式分别核验。[旧版Proto的配置定义](https://github.com/a2aproject/A2A/blob/v0.3.0/specification/grpc/a2a.proto)、[固定新版Proto](https://github.com/a2aproject/A2A/blob/3303592588e388e62e0f69f701af531d2f4e3991/specification/a2a.proto)。

**context由谁提出，和谁有权访问，是两件事。** 新建交互时服务可生成contextId，客户端也可以提出contextId；同一Message同时携带taskId和contextId时必须匹配，只有taskId时服务可从任务推知context。不能从topic页的“server-generated”简写推出客户端永远不得提供context，也不能把猜到/沿用contextId当获准访问该组任务。任务的不可重启规则仍有效：后续修改已完成产物，应建立新任务，按需要沿用context并用referenceTaskIds说明来源。

**绑定有不同承载方式。** 固定v1.0.1的11个gRPC方法中，只有SendStreamingMessage与SubscribeToTask是服务端流；它并未定义客户端流或双向流。请求版本和扩展用小写gRPC metadata键`a2a-version`、`a2a-extensions`，tenant则在请求消息字段中。JSON-RPC中tenant位于params；HTTP+JSON的Proto还定义了`/{tenant}/...`路径绑定，不能因topic标题写“Body-Based”就在所有REST正文强塞同一个字段。路径值需正确编码，若部署允许多种来源，还要明确冲突拒绝政策。Task失败属于业务状态，gRPC调用失败属于传输/协议错误；应结合google.rpc.Status及ErrorInfo识别，不能只看一个整数或把两者合并。

**扩展声明不等于执行。** URI首先是标识符，客户端按受信的固定规范理解它；不是看到任意URI就必须联网下载、加载代码或执行安装命令。metadata按URI命名空间组织是一种约定，具体字段仍由扩展定义。AgentExtension的required表示客户端必须理解并遵从该扩展，而不是所有声明字段都因此成为Proto REQUIRED字段。模型类存在、请求激活、服务实际实施、响应声明与结果回执，需要分别验收；响应回显在该版topic中是SHOULD，不能升格成所有绑定都必须有同一种HTTP响应头。

**Card签名须先统一默认值规则。** 固定v1.0.1规范§8.4.1要求按ProtoJSON存在性保留REQUIRED和显式设置的optional字段；§8.4.2/8.4.3又说删除默认值，二者对显式false等输入可能产生不同签名字节。JCS只能规范化已经选定的JSON对象，不能替双方决定字段是否应当存在。实际互通前，应冻结双方采用的版本与字段存在规则，并共享“省略optional／显式false／显式空值及非法输入”的签名测试向量，核对规范化payload、protected header和签名输入。若对端按不同规则签名，应报告不兼容并核验来源，不能反复删除字段直到某次验签成功。受信key、算法和撤销仍要独立检查。[该版签名章节](https://github.com/a2aproject/A2A/blob/3303592588e388e62e0f69f701af531d2f4e3991/docs/specification.md#84-agent-card-signing)。

研究材料中的SDK行为、未合并提案和release计划都是作者当时的快照。它们可解释为什么要做上述合同测试，却不能证明当前每个SDK仍有相同缺陷，也不能把实验SLIMRPC、候选双向流或未来版本当固定v1.0.1核心能力。跨协议选择继续对照本章与[MCP章节](10-模型上下文协议-MCP.md)：A2A侧重任务委派，MCP侧重能力与资源接入；不能从这种用途区分推断MCP永远无状态或没有异步任务。

### 用事件与图示读懂一次交接

手册的四份events JSON和32张静态SVG及其32个构建源码，本轮按固定字节静读；图在白底静态渲染并逐张视读，未执行JS构建器、动画或演示服务。读图先看箭头表示请求、响应、状态提交、存储写入还是外部动作，再看谁控制每一步；颜色和从上往下的顺序不是时序一致性、网络交付或授权已实现的证明。

**传输完成、委托完成和业务通过不是同一判断。** `05-streaming.events.json`共9个事件：初始Task、WORKING、五段test-log、一个summary、COMPLETED。summary明写11 passed、1 failed；服务的工作合同是“运行并报告测试”，可以完成这项委托，同时报告被测软件仍有失败。调用方若要部署，应验证真实候选commit/build对应的结构化summary且failed=0，并核质量门，不能只看Task completed或自然语言“已完成”。这里的日志、4.21秒、250ms时钟步和健康检查文字来自固定演示，不是本轮真的检出Git、执行CI或部署；也不作为性能/覆盖结论。

整个planner故事是三个有依赖的决定：先取得候选版本的测试报告，符合门槛后再取得匹配diff/base的审阅，符合约定后才请求目标环境部署。Card上的技能描述帮助选择服务；请求本身仍用Message内容/业务约定路由，并没有通用顶层skill参数。审阅要求base branch时，用新messageId补“main”、携带原taskId及匹配contextId，等待同任务恢复；不要把缺信息当失败，也不要把“low severity”文本或报告已创建当放行证据。测试、审阅、部署各绑定产物身份、当前权限与停止条件，不能由三栏图误读为三个动作可无条件并行。

**断线后先认清快照，不能把所有到来的Part都追加。** 手册重订阅例中，断线前已收日志01、02，断线期间服务又存了03、04。重订阅首事件是同Task的当前快照，test-log已经包含01～04；随后增量是05～08。因此在这个明确含完整Artifact的快照合同下，应把该Artifact的当前视图设为01～04，再追加05～08，最终8段。如果沿用旧01、02，再追加快照4段和新4段，就得到10段，重复了前两段。

这不表示任意Task对象都能整体清空本地状态。先区分快照覆盖哪些字段、哪些因historyLength/输出裁剪省略；“字段缺失”与“明确空集合”不同。按taskId/artifactId、append/lastChunk处理，必要时以GetTask对账。协议的首快照有助恢复当前结果，但不保证重放每个遗漏的中间事件，也没有自动提供跨连接全局序号。读快照与订阅事件之间还要有一致切点；业务若需要完整事件审计，应另约定序号/游标、保留期和缺口恢复，参照[流式恢复的快照与序号合同](../../LLM%20工程实践/18-模型演示界面与交互合同.md)，不能拿本例预排好的时间表证明并发窗口无遗漏。Task已终态时，SubscribeToTask按该版返回UnsupportedOperationError，改用获准的GetTask读取保留结果。

**AUTH_REQUIRED是等待状态，不是批准凭据。** 图中operator走普通HTTP批准端点，这是A2A之外的业务过程；A2A没有规定一个通用`/approve`接口。真实门至少要核批准者身份、task/run、目标环境与动作、候选build、请求摘要、期限及当前权限，保存可审计的批准事实，再由状态提交处决定是否恢复。单一共享bearer只证明持有同一个凭据，不天然区分操作员、调用Agent与不同任务负责人。

源capture kit的等待路径调用`Event.wait(timeout=10)`却不核返回布尔值，随后behavior仍会产生固定“Approved by an operator”与完成事件；批准端点本身也不构成完整身份/动作绑定。这个结论来自既有源码静读，不是本轮实际触发超时。四份事件中看见批准文字和staging URL，只证明材料记录了这些字段，不能补出真实操作员批准、实际部署或健康检查。教学改进的验收要包含“从未批准且等到超时”仍不执行，以及错误主体、过期、改build和撤权等负例；这里只给判断标准，不在源服务上执行。

**取消的同等效果，不要求每次返回完全相同。** 固定规范将CancelTask描述为幂等停止效果，同时把已完成、失败或取消列为不可取消状态；手册中第二次CancelTask得到TaskNotCancelableError。重复请求不应多产生效果，但可按固定合同返回已终态错误，清理后也可能NotFound；客户端不能因第二次报错就把已经CANCELED写成FAILED，更不能自动重启任务。停止前留下的两段日志仍可存在，取消不自动撤销已发生的外部写入。

其余图的知识统一回到已有对象与信任合同：一个context可关联多个任务，已终态任务不能“重新打开”完成新工作；单独Message答复没有可轮询的Task；状态中的message与历史记录不必相同，historyLength控制的不是所有可见正文。扩展能力在`capabilities.extensions`声明，请求激活和实际使用另核；图中缺required扩展报错或gRPC顺序是规范/蓝图示意，capture kit并无相应完整抓包或gRPC执行。签名图的HS256/JWS输入有助理解字节绑定，但排序JSON、浮点限制、ProtoJSON字段存在、可信key与撤销仍按前文处理；不照抄“真实Card只能ES256/RS256＋jku”，更不能信任Card自己给出的任意取key URL。

图与记录承担说明功能。读取它们后应能回答：消息是谁发的，哪个状态是中断/终态，哪个Artifact是结果，哪些检查发生在服务入口/状态提交处，哪些事实仍需独立证明。无需把32张来源图和作者系统原样镜像进仓库；上述对象、两段快照例、业务结果与批准反例已融进统一主章，原图的版本/hash和逐项含义见39号维护记录。

### 从兼容性报告反推验收合同

协议要求、SDK实现、一次测试观察和业务正确性各自举证。手册的`research/sdk-splits.md`比较的是作者在2026-10-06整理的固定SDK版本，不是所有语言SDK今天的保证；`conformance-tools.md`、`tck-run.md`与129行摘要也属于该次记录。本库2026-10-19完整静读这些材料，另选读官方TCK固定`1.0.0.alpha2`、commit `29063fe`的[聚合器](https://github.com/a2aproject/a2a-tck/blob/29063fe95e903cddac5d8ff811ab94df1ad6ef86/tck/reporting/aggregator.py)和[结果hook](https://github.com/a2aproject/a2a-tck/blob/29063fe95e903cddac5d8ff811ab94df1ad6ef86/tests/compatibility/conftest.py)核计分；未运行SDK、TCK、服务或作者命令。

不要背一张很快过期的“语言SDK谁支持什么”表。先将自己的服务和客户端固定到具体revision，再用下面14种行为定义请求、预期状态和观察范围；一处互通不能代表其余操作也互通。

| 要核的行为 | 怎样构造可观察的验收 | 必须单独说明的边界 |
|---|---|---|
| 1. 订阅HTTP方法 | 对相同活跃Task按选定绑定实际请求；记录method、path、状态码与首事件 | v1.0.1的GET/POST冲突见上节；兼容适配不等规范全部一致 |
| 2. 流何时关闭 | 分别让服务进入INPUT_REQUIRED、AUTH_REQUIRED、终态，记录事件和连接状态 | executor函数返回、流关闭、任务完成不同；恢复不能只等一个EOF |
| 3. Webhook交付 | 用已授权接收端记录实际body、MIME、认证及事件类别，再核业务身份与去重 | “至少尝试一次”不是最终送达；重试和token头的差异要显式配置 |
| 4. 历史长度 | 对同Task分别省略historyLength、设0、设1，核返回数量和内容 | 省略是客户端不施加上限，服务可以有默认量；0不是省略，也不要求所有部署保存全历史 |
| 5. 分页 | 固定人群/过滤条件，分页直到nextPageToken空，收集ID、时间、重复与遗漏 | token不透明，只原样回传；动态任务列表没有自动一致快照保证 |
| 6. 终态续消息 | 对已完成Task发新消息，核确实拒绝且handler未再次产生效果 | 错误类型/传输码按固定绑定验证；任意异常不等正确拒绝 |
| 7. 协议版本 | 发选定的1.0及明确不支持的版本，另测缺失值的约定 | patch/release号不同于wire major.minor；接受某header不证明按其语义处理 |
| 8. MIME与错误外壳 | 分开测普通结果、RPC业务error、HTTP入口错误与SSE | HTTP200也可能有RPC error；不能用一个成功状态或后缀猜内容形状 |
| 9. 只带taskId | 在合法活跃Task续接，核服务上下文、Task与新增历史是否指向原context | “调用没报错”不能证明正确推断；不要从任意旧历史字段反推权威Task身份 |
| 10. 错配contextId | 活跃Task配另一个context，应拒绝；同时保留合法组合对照 | 不能拿终态Task试它，否则可能只命中了终态门 |
| 11. Artifact分块 | 初块append=false，再追加，核同artifactId的累积结果；另测未知ID追加 | 未知ID的处理要约定；lastChunk不替代Task终态，重放不应重复拼接 |
| 12. 跨主体访问 | 主体A创建、主体B逐个试get/list/send/cancel/subscribe和push配置 | owner字段依赖真实认证结果；匿名统一owner会让形式隔离失效 |
| 13. Extended Card | 未认证、已认证但无权、有权三组，分别核能力与配置存在性 | 声明能力不等已配置，读取回调也不自动做认证；缓存绑定身份与受众 |
| 14. 重发messageId | 同主体同内容、同ID改内容、并发重发、重启后重发分别观察 | messageId不是协议自带效果幂等；即使带同taskId，handler也可能再次执行 |

**一个失败原因必须只改一个条件。** 要验context错配，先建仍活跃的Task A及其context C，发送合法`taskId=A,contextId=C`确认前置成立，再只把context改成D，检查拒绝码和没有副作用。终态拒绝用另一个已完成Task、保持正确context单独测。若同时给错context和终态，再断言“报了任意错”，两种门谁失效都可能没被发现。对外响应还应避免泄露无权资源是否存在，可信内部回执才解释具体拒绝原因；测试这种隐匿策略也不能靠外部报错文字猜。

**兼容解析需有范围，不能为了互通接受所有输入。** 历史SDK可能在JSON、A2A JSON和problem JSON、通知token头、错误码及快照事件上不同。适配层应按固定对端/绑定允许明确组合，限制大小并验证载荷、认证与业务身份；不能照抄研究材料中“whatever Content-Type都解析”或“两个token头都接受”就当安全互通。签名所绑定的原字节、字段规范化与解析后的对象关系也要明确。同messageId的历史去重只去掉重复日志，不能保证handler、计费或外部写入没再发生。

### 调试、互操作与符合性：四种工具的证据不同

| 工具类型 | 能提供什么 | 单独不足以证明什么 |
|---|---|---|
| Inspector | 展示Card、请求响应与事件，做它实现的字段检查 | 完整协议符合性、授权隔离或业务正确；界面补出的kind也不代表原wire含kind |
| CLI客户端 | 复现选定绑定的发送、查询、取消、订阅与实际输出 | 客户端退出0不保证Task成功；可能正确地收到了FAILED或INPUT_REQUIRED |
| TCK单服务测试 | 对冻结要求与实际断言报告某服务的符合性证据 | 注册了requirement就都测到、三个绑定都覆盖、安全与Card签名都已测 |
| ITK跨实现测试 | 在给定SDK/传输/拓扑/场景上观察互通和已知失败 | 全操作符合规范；多跳遍历经过一条边不等测试该边每种错误/权限/恢复 |

手册固定TCK alpha2以A2A v1.0.0快照为基线，教材协议却固定v1.0.1。测试器也可能有尾斜线改Card URL、snake_case参数、把`application/a2a+json`错误地要求包含`application/json`、错误码映射或skip记账的问题。保留原测试结果，定位是服务缺陷、测试器缺陷、fixture前置不匹配、明确不支持还是未知；修测试器后的运行是另一版本的证据，不应抹掉原收据。若服务宣告支持某能力而该绑定没有相应操作，也不能用“都是测试器问题”掩盖实现缺口。

**百分比先问分母与覆盖。** 仓内作者摘要的129个requirement可静态数出62 PASS、31 FAIL、11 SKIPPED、25 NOT_TESTED。固定聚合器排除后两类，显示62/(62+31)约66.7%；这不是62/129的完整覆盖，更不是安全保证。同一聚合器对没有任何可计项目还返回100%，空集合的显示值必须另标“无有效测试”，不能验收通过。

作者又将21个被hook误记的失败重分类为跳过，于是同一62个PASS按62/(129−32−25)约86.1%显示。这里没有新增21个成功行为，更没有重新测出系统改善；只是分母和分类变了。官方alpha2 hook确实只排除passed、未单独排除call-phase skip，聚合器也会用同transport最后一条记录覆盖展示摘要，所以表面`transport=PASS`仍可能有更早失败导致requirement=FAIL。保留逐test回执和聚合规则，不能只看最后的绿灯。

NOT_TESTED中包含认证/授权作用域、Card签名与跨绑定等关键族，因此手册“没有剩余MUST缺陷”的表述只能理解为作者所审查范围的分类意见；原始完整pytest/抓包目录并未随该手册一并收录，本轮不能独立重建全部运行，也已在源码静核发现审批等待超时返回值被忽略等另行缺口。已知未测、未覆盖和发现的缺陷必须跟百分比一起展示。一般评测分母与回归门见[评测与实验管理](../../LLM%20工程实践/06-评测与实验管理.md)，这里保留A2A的具体反例，不复制另一套指标代码。
