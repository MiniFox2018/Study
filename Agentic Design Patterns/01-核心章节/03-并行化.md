## 本章定位

将可独立处理的子任务并发执行，以降低整体时延并提高吞吐与覆盖度。

## 先画出依赖关系

只把输入互不依赖的任务并行。例如三份独立文档分别抽取后再合并，可以并行；“先确认文件路径，再修改该文件”必须串行。没有并发控制地让两个执行者改同一文件，会产生覆盖和难以追踪的结果。

设三个独立任务耗时 2、3、5 秒。忽略协调与限流时，串行共 10 秒，并行至少约 5 秒，而不是 10/3 秒；最慢分支决定汇总时刻。实际还需计入排队、网络和合并成本。

## 具体流程：审查三份说明

1. 给各分支分配唯一文档和同一审查模板：问题、证据位置、建议、未确定事项。
2. 只共享任务要求，各自记录读取版本，避免互相复制推测。
3. 汇总器检查重复、冲突和遗漏；无法一致时保留分歧并回看原文。
4. 为每个分支设超时和预算。一个失败时明确标出覆盖缺口，不能把两份结果写成“三份全部完成”。

## 自检与核对

**问题**：三次同模型回答完全一致，是否等于三份独立证据？

**核对**：不是。相同模型、提示和来源可能产生相关错误；并行扩大候选覆盖，事实仍应回到外部证据或可执行验证。写入任务要分文件所有权或使用独立分支后统一合并。

## 来自《深入理解 AI Agent》的增量吸收

- 并行化可用于独立子任务、并行检索、候选方案生成和多 Agent 研究。
- 并行并不等于简单“同时跑”：需要明确上下文共享/隔离方式、汇总策略、冲突处理和终止条件。
- 多 Agent 并行的典型风险包括共享文件并发冲突、错误级联、同质趋同和循环失控。

## 共享队列调度：并行任务怎样分给工作者

独立文档可以同时抽取，但任务数多、耗时差异大时，“每人固定几份”容易让其他人空闲。共享队列让空闲工作者主动取下一个**就绪任务**，即 pull 调度。工作者从自己的本地队列执行、空闲时从其他队列偷取任务，才是更具体的 work stealing；两者不能只因为动态图标题一样就混称。

任务有依赖也可以用队列：先完成依赖、确认输入版本与权限，再把下游放进就绪队列。顺序由依赖合同保证，不由出队顺序代替。汇总器仍要检查最终产物的完整性。并行工作者、流程规划者和结果验收者可以组合，不能把“没有中心调度进程”理解成“没有计划、没有 trace”。

### 下界、负载均衡与一个算得出的例子

设任务耗时为 $p_i$，总工作量 $W=\sum_i p_i$，工作者数量为 $m$。忽略通信且每个任务不可拆分时，总完成时间至少为

$$T\geq\max(W/m,\max_i p_i).$$

其中 $W/m$ 是总负载下界，最大单任务是不可拆分下界；有依赖时还受关键路径限制。队列调度可以接近下界，但不能由“谁先空闲谁取”保证每组任务最优。任务类别、预取、资源容量和优先级会改变实际结果。

源第 09 课有四个 0.4 秒慢任务、四个 0.1 秒快任务，总量 2.0 秒。固定分配并不是只有 worker0 的四个慢任务：它还分到一个快任务，瓶颈共 **1.7 秒**。四个工作者从共享 FIFO 先各拿一个慢任务，之后各拿一个快任务，忽略开销共 0.5 秒，算术速度比为串行的 4.0 倍、固定分配的 3.4 倍。这是手算调度结果，未运行源线程程序，也不是实测速度。

下面的标准库程序使用整数时间片，避免把 `sleep` 和系统线程抖动当调度结论。它检验输入、任务 ID、固定归属与两种分配的时间轴；**不执行实际任务，也没有持久队列、模型或网络**。

```python
from heapq import heappush, heappop

def workload(tasks, workers, fixed=False):
    if type(workers) is not int or workers < 1:
        raise ValueError('工作者数必须为正整数')
    if not tasks:
        return 0, ()
    ids = set()
    for tid, duration, owner in tasks:
        if (type(tid) is not str or not tid or tid in ids or
            type(duration) is not int or duration <= 0 or
            type(owner) is not int or not 0 <= owner < workers):
            raise ValueError('任务 ID、耗时或归属无效')
        ids.add(tid)
    heap = [(0, i) for i in range(workers)]
    ends = [0] * workers
    events = []
    for tid, duration, owner in tasks:
        if fixed:
            start, wid = ends[owner], owner
        else:
            start, wid = heappop(heap)
        end = start + duration
        ends[wid] = end
        events.append((tid, wid, start, end))
        if not fixed:
            heappush(heap, (end, wid))
    return max(ends), tuple(events)

tasks = [(f't{i}', 4 if i < 4 else 1, 0 if i < 4 else (i-3) % 4)
         for i in range(8)]
assert sum(t[1] for t in tasks) == 20
assert workload(tasks, 4, True)[0] == 17
assert workload(tasks, 4)[0] == 5
assert max(20 // 4, max(t[1] for t in tasks)) == 5
assert workload([], 4) == (0, ())
for bad, n in [(tasks, True), (tasks + [tasks[0]], 4),
               ([('x', 0, 0)], 4), ([('x', 1, 4)], 4)]:
    try:
        workload(bad, n)
        raise AssertionError('应拒绝无效任务')
    except ValueError:
        pass
print('总量20、固定17、共享5时间片；非法输入与重复任务拒绝通过')
```

### 队列保证与工程责任

`queue.Queue` 只在单进程内存中同步。持久 broker 也需要查具体投递、确认、保留、重试与复制语义，不能把“消息不丢”写成“外部效果不会重复”。工作者取得任务后，绑定 claim 的租约与版本；完成结果先取得持久回执，再确认消息。崩溃导致重投时用同操作 ID 和内容摘要向目的端去重，旧工作者回报需受 fencing 约束。恢复与副作用边界见[异常处理和恢复](12-异常处理和恢复.md)。

优先队列在持续高优先级输入时可能饿死低优先级任务；FIFO 的源示例不是“每次挑最快”，不能将该饥饿机制套给它。aging 是随等待时间重新计算优先级，入队时只算一次不能让等待中的任务逐渐晋级。还应记录等待年龄、处理时间、资源占用、失败率，给长任务和不支持的任务设明确退路。三个快任务比一个慢任务多，不足以判定工作者热点；按类别与服务总量比较。

容量与背压定义的是生产者何时停止、等待或拒绝，而不是队列无界增长后多加工作者。worker 专门化须防不支持类别被反复取回又塞回。共享 trace ID 可以构成跨工作者的任务图；去中心化不自动意味着不可审计。源输出蓝图中的“低于每秒 10 项必须拒绝”“高审计要求必须用 supervisor”没有通用阈值依据。

[Matrix v2 §3](https://arxiv.org/abs/2511.21686v2) 的长期价值在于：每份数据携带可序列化的 orchestrator 状态，轻量 Agent 传递状态与控制，重计算由独立服务承担，运行层有日志和 Grafana。它可支持 LangGraph 适配与顺序流程，因此既不是没有编排对象，也不是失去追踪的必然设计。论文吞吐数字只对应其固定硬件、数据生成场景，不能作为本队列例子的速度保证。
