## 本章定位

围绕任务分解、搜索、验证、推导与多步推理等方法提升复杂问题处理能力。

## 把推理拆成可验证动作

复杂题可以分解子问题、检索事实、生成候选、执行计算并检查约束。过程文字越长不代表结论越可靠；模型给出的推理说明也不是其内部计算的完整记录。实际应要求清楚的依据、关键计算和可重复验证。

对确定性运算优先使用程序或计算器；对资料问题先找可信证据；对开放设计生成多个候选后按事先定义的标准比较。多次采样投票只有在错误不完全相关、答案可比较时才可能有帮助。

## 具体例子：安排两项任务

任务 A 需 2 小时，任务 B 需 3 小时且必须在 A 后开始；一名执行者从 9 点开始，最早完成为 14 点。无论生成多少候选，不能把 A/B 并行安排来声称 12 点完成。把约束写成结构化表或代码检查，能直接识别这种“听起来合理”的错误。

验证时既核对计算，也核对假设：如果允许另一个人执行 B，依赖仍然存在；如果 B 不再依赖 A，才可能从 9 点并行。

## 自检与核对

**问题**：三个候选给出同一数值，可以免除单位检查吗？

**核对**：不可以。候选可能共同把分钟当小时；明确变量、单位、边界条件，并用独立方法检查关键结论。

## 中间步骤、示范与外部观察分别解决什么

Few-shot 示范输入/输出或关键计算；CoT 提示可让部分模型生成中间计算；self-consistency 对规范化后的候选答案投票；ToT 在候选状态上扩展、评分和剪枝；ReAct 根据工具观察继续决策；提示链检查前一步产物再进入下一步。它们都不能把缺失前提变成事实。例如原课鸡饲料示例缺少鸡数及等分用餐的明确前提，却反复推出相互矛盾的数量，不适合当已核对示范。

可见计算有助复核，不能当作模型内部计算的完整记录。推理模型通常先接收直接任务、限制和成功条件；出现格式或领域误解再补正确示例，不必要求“展示全部思维链”。[OpenAI 推理提示指导](https://developers.openai.com/api/docs/guides/reasoning-best-practices) 需要用户理解时给简洁依据、证据和可重复计算。三条答案相同也可能共同把分钟当小时，检索到的观察还需来源、时间和权限检查。

## 完整离线例：解析覆盖与投票比例

五份候选中只有一份能解析时，它的票数是 1/5；不能除以成功解析数而报 100%。平票必须显式处理。下面固定协议为 `The answer is 数值 单位.`，保留负号、用 Decimal 合并 `18` 与 `18.0`，拒绝自由文本中的末尾数字。单位不匹配算失败；协议没定义的分数或科学计数直接拒绝。这些候选为合成文字，不是模型采样。

```python
import re
from collections import Counter
from decimal import Decimal
from fractions import Fraction

ANSWER = re.compile(r"The answer is ([+-]?\d+(?:\.\d+)?) (元|个)\.")

def parse_answer(text, unit):
    if type(text) is not str or unit not in {"元", "个"}:
        return None
    match = ANSWER.fullmatch(text.strip())
    if not match or match[2] != unit:
        return None
    value = Decimal(match[1])
    return value if value.is_finite() else None

def vote(samples, unit, minimum_coverage=Fraction(3, 5), minimum_share=Fraction(3, 5)):
    if type(samples) is not list or not samples:
        raise ValueError("样本集必须非空")
    for cutoff in (minimum_coverage, minimum_share):
        if not 0 <= cutoff <= 1:
            raise ValueError("阈值应在0至1")
    parsed = [parse_answer(text, unit) for text in samples]
    counts = Counter(value for value in parsed if value is not None)
    total, valid = len(samples), sum(value is not None for value in parsed)
    result = {"attempts": total, "valid": valid,
              "coverage": Fraction(valid, total), "votes": counts}
    if not counts:
        return dict(result, status="no_parsed_answer", answer=None)
    maximum = max(counts.values())
    winners = [value for value, count in counts.items() if count == maximum]
    share = Fraction(maximum, total)  # 总尝试数包含解析失败。
    if len(winners) != 1:
        return dict(result, status="tie", answer=None, vote_share=share)
    if result["coverage"] < minimum_coverage or share < minimum_share:
        return dict(result, status="insufficient_support", answer=None, vote_share=share)
    selected = winners[0]
    # 返回真正支持获胜值的候选索引，不默认拿第1条说明。
    indices = [i for i, value in enumerate(parsed) if value == selected]
    return dict(result, status="candidate", answer=selected,
                vote_share=share, supporting_indices=indices)

good = ["The answer is 18 元.", "The answer is 18.0 元.",
        "The answer is 18 元.", "The answer is 19 元.", "无法解析"]
chosen = vote(good, "元")
assert chosen["answer"] == Decimal(18) and chosen["vote_share"] == Fraction(3, 5)
assert chosen["coverage"] == Fraction(4, 5) and chosen["supporting_indices"] == [0, 1, 2]
assert vote([good[0]] + ["出错"] * 4, "元")["status"] == "insufficient_support"
assert vote([good[0], "The answer is 19 元."], "元")["status"] == "tie"
assert parse_answer("没有答案，最后检查了18个步骤", "元") is None
assert parse_answer("The answer is -2 元.", "元") == Decimal(-2)
assert parse_answer("The answer is 18 个.", "元") is None
assert parse_answer("The answer is 1/2 元.", "元") is None
wrong_majority = vote(["The answer is 19 元."] * 5, "元")
# 固定题：16枚蛋减3枚和4枚，每枚2元，正确答案18元。
expected = Decimal((16 - 3 - 4) * 2)
assert chosen["answer"] == expected
assert wrong_majority["vote_share"] == 1 and wrong_majority["answer"] != expected
print("解析/规范化/单位/覆盖/平票通过；5/5一致仍可错误，独立计算为", expected)
```

这里的 3/5 是教学策略，不是校准后的正确概率。真实任务应保留 N、解析失败数、各值票数、单位、候选来源和独立验证结果。错误高度相关时增加 N 也未必帮助；低温度不是多次调用必然相同的承诺。示例选择还需与留出集隔离，避免“测得更好”只是展示了测试答案。

## 完整离线例：有预算的候选搜索

ToT 的工程对象是状态、候选生成、评价、搜索与终态，不能只有一段“请想出多个方案”。下面从 0 出发，每步只能加 2 或 4，找出总和 6 的计划。距离目标只决定保留哪些候选；最终计划仍由规则验证。它是确定性 beam search，状态计算不是 LLM 思考，节点扩展数也不是 API 调用数。

```python
def bounded_search(target=6, moves=(2, 4), width=2, depth=3, expansions=12):
    if any(type(x) is not int or x <= 0 for x in (target, width, depth, expansions)):
        raise ValueError("目标与预算须为正整数")
    if not moves or any(type(x) is not int or x <= 0 for x in moves):
        raise ValueError("动作须为正整数")
    frontier, visited, used = [(0, ())], {0}, 0
    for level in range(1, depth + 1):
        candidates = []
        for value, path in frontier:
            for move in moves:
                if used >= expansions:
                    return {"status": "expansion_limit", "expanded": used}
                used += 1
                nxt, plan = value + move, path + (move,)
                if nxt > target or nxt in visited:
                    continue
                visited.add(nxt)  # 同值状态保留首次到达；不证明任意问题可这样合并。
                if nxt == target:
                    assert all(action in moves for action in plan) and sum(plan) == target
                    return {"status": "verified", "plan": plan, "expanded": used}
                candidates.append((nxt, plan))
        if not candidates:
            return {"status": "no_candidates", "expanded": used}
        frontier = sorted(candidates, key=lambda state: (target - state[0], state[1]))[:width]
    return {"status": "depth_limit", "expanded": used}

result = bounded_search()
assert result["status"] == "verified" and sum(result["plan"]) == 6
assert bounded_search(expansions=1)["status"] == "expansion_limit"
assert bounded_search(target=7, depth=2)["status"] == "depth_limit"
assert bounded_search(target=1)["status"] == "no_candidates"
print("有限搜索：", result, "；节点/深度/空候选出口通过")
```

把生成器或评价器换成模型时，要新增无效评分、未完成候选、重复状态、费用、超时和结果核验。LLM 评价器出错不能默认记 0.5 当正常分数；部分轨迹中最后一个数字也不能当最终答案。源码的 top-2 保留策略不是完整 b 叉树，评价调用也要计成本；它在默认升级路径中先做一次 CoT 和五次投票，再做 18 次生成/评价调用，合计 24 次，不是“所有问题先一轮便宜处理”。这是按代码控制流的静态计数，未实测 API。

## 选择策略与练习的核对条件

简单抽取先直接任务；格式边界不清加正常/反例；确定运算先计算器；缺外部事实用检索/工具；候选空间可评估才考虑搜索；复杂产物可分提示链，但每步保留证据与未知项。CoT 生成、内部推理、投票和过程验证不能互相替代。跨策略比较应固定题集、示例集、输出协议与计算预算，记录每题而非只看最终平均值。

1. **四策略比较**：zero-shot、few-shot、zero-shot CoT、few-shot CoT 要真的各有分支；原比较程序缺纯 few-shot。固定手算题先验证评价器，再选择真实模型实验。
2. **示例选择**：比较随机、相似、标签覆盖与顺序，核对每条示范。按前三例截取不能称 embedding 检索；与测试重复的题即使默认没选，也须从库中分离。
3. **N 的成本曲线**：同时报告正确率、解析覆盖、票比、总尝试数和实际 usage。N 次串行增加调用时延；并行可能减少墙钟时间，不减少所有 token 费用。
4. **ReAct 计算**：模型表达式不能直接 `eval`，清空 builtins 不是隔离。使用有长度/深度/数值上限的数值语法，结果通过 [工具协议](05-工具使用.md) 回填。
5. **开放题 ToT**：先定义可检验约束和评价标准，记录候选/淘汰理由；模型偏好与独立评价分开。不能迁移数学题成功率来宣称写作质量。
