## 本章定位

通过角色分工、协调、通信与结果汇总，让多个智能体共同完成复杂任务。

## 分工需要一个共享的完成标准

多智能体系统可由协调者分派独立子任务，也可让提议者与审核者轮流工作。角色名字不会自动创造独立专业能力；多个同类模型可能同时犯同一种错误。引入协作前，先确定单 Agent 的瓶颈是什么。

每个任务包应含范围、输入、输出格式、权限、截止/预算、成功标准和明确的文件归属。子任务报告需区分证据、推断、未验证事项；汇总者承担去重、冲突处理和最终验收责任。

## 具体例子：审查知识库

数学审查者负责数学目录，工程审查者负责部署目录，协调者维护导航与全局链接。每人只改独占文件，在报告中列出错误原句、修正理由和来源。若两组都需改同一术语表，由一个所有者统一修改，另一组只提交建议。

协作效益可用同一任务集比较：单 Agent 与多 Agent 的成功率、遗漏率、总 Token、总时延和人工复核成本。不能只看并行看起来热闹或消息更多。

## 自检与核对

**问题**：子 Agent 说“测试已通过”，协调者应怎样验收？

**核对**：至少核对测试命令、环境、结果与对应修改版本；对关键行为独立复验。只有口头结论，没有可追溯结果，应标为尚未核实。

## 从分工、通信到辩论：三个不同的设计问题

2026-10-09 增量吸收固定来源 Phase14 第 25、28 课。先修是任务拆分、工具权限和单 Agent 的可观察执行。先明确单 Agent 为什么做不好：独立资料能否并行取得、上下文是否超预算、是否需要不同权限或独立审查。若没有可测瓶颈，新增角色与消息可能只增加成本。

**分工**规定谁负责哪部分任务；**控制拓扑**规定谁可以分派、转交和汇总；**反馈协议**规定候选是否独立产生、是否互相批评、怎样修订和停止。它们可以组合。例如中心监督者把四份资料分给工作者，工作者只交结果，属于并行分工与汇总；加入交叉检查才具有辩论机制。纯投票只聚合答案，不读取其他人的理由，也不是辩论。Flow/Crew 等名称属于具体框架的编程与调度抽象，不能直接等同于某个拓扑。

| 控制结构 | 任务如何移动 | 可以解决的问题 | 需要补足的合同 |
| --- | --- | --- | --- |
| 监督者—工作者 | 监督者选择工作者、接收结果并决定终态 | 集中范围控制、上下文裁剪、统一验收 | 监督者的预算、失败隔离、子任务结果格式与对象权限 |
| 对等交接（本课称 swarm） | 当前角色把任务交给另一个角色 | 局部决策可减少中央路由步骤 | 交接后谁拥有任务、可见上下文、未知目标、循环与取消 |
| 层级监督 | 上层管理任务组，下层管理专家 | 上层上下文太大、不同权限或故障域需要隔离 | 每层真实职责、压缩损失、跨层证据与汇总责任 |
| 辩论协议 | 独立候选经过其他候选的反证与修订 | 可检验的推理、遗漏与事实冲突 | 独立初始化、同步轮次、外部判据、预算与平票/弃权规则 |

这不是互斥且穷尽的四分类。层级系统可以在某个任务组里辩论，对等交接也可以只有单路径。人数为 2–4 或超过 10 不是普遍边界；应测实际工具描述与资料 Token、权限、协调收益。Anthropic 的 [Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents) 支持从较简单、可评估的方案出发，按任务增加复杂度，没有规定所有系统必须按“监督→swarm→层级”的顺序升级。

## 辩论怎样形成一条可检验的轨迹

令 $N$ 为提议者数量，$R$ 为**独立初始化之后的批评轮数**。初始化时每个提议者仅看原问题与自己的证据，形成候选。第 $r$ 轮从上一轮的不可变快照读取允许的同伴意见，再提出修订；同轮成员不能偷看先完成者的新答案，否则输入顺序变成协议的一部分。保留原候选、所读证据、修订理由与最终聚合，不只保存最后共识。

停止条件可以是轮数/费用耗尽、没有新增可核证据、明确可验证的成功，或预定共识规则。共识本身不证明事实正确：四人全改成错误答案也会高度一致。不要强迫唯一正确答案的问题产生四个互斥假答案；可要求每人给出独立推导、反例、备选假设与不确定点，允许同答不同证据或弃权。

同模型同提示可能降低多样性，也可能因采样产生不同候选；异构模型可能减少共享盲点，却不保证错误独立或更准确。按独立留出题比较初始单答、投票、辩论与工具核验，并报告错误相关性、错误共识率与成本。自报置信度要经留出集校准，高置信错误者可能主导加权投票。

[Du 等 v1 方法与实验](https://arxiv.org/html/2305.14325v1) 的相关核验范围是协议与实验条件：多个实例先独立回答再交叉批评；论文主要设置为 3 个 Agent、2 个批评轮，不提供普遍收敛保证。§3.3 的跨模型示例仅在 20 道 GSM8K 题比较，不能推成所有模型/任务的长期优势。[Sparse Communication v1 §3–4](https://arxiv.org/html/2406.11776v1) 比较的是固定 6 Agent 的规则图，并固定首轮响应以公平比较后续通信；其成本指标是输入 Token。它支持研究通信稀疏性，不证明任意星形对任何任务最优。

## 消息边、调用与延迟要分别计算

把一次“提议者读取一位同伴的上一轮候选”称为一个**有向 peer read**。全连接每轮 $N(N-1)$ 条；双向星形中，中心读取 $N-1$ 个叶子，叶子合计读取中心 $N-1$ 次，共 $2(N-1)$ 条。$R$ 轮分别为 $RN(N-1)$ 与 $2R(N-1)$。因此 $N=5,R=3$ 为 60 与 24，不是 60 与 12；12 只算了星形一个方向。

假设每个 Agent 每批评轮只调用一次模型，更新调用都是 $NR=15$，另有 5 次初始化，共 20 次。一次调用能读取多个 peer，所以边数不等模型调用数。若每份候选都是 $L$ Token，仅 peer 部分输入可近似为“边数×$L$”；完整输入还含原题、系统约束、历史与包装，输出长度也不同。字节不是 Token，输入 Token 不是总费用。需按实际 usage 和对应价格求费用；未调用模型时只能报告代理计数。

同步轮内可并行，单轮临界路径通常取最慢成员加同步/汇总开销；不能直接拿 $NR$ 乘一次调用延迟当总墙钟时间。星形中心可能拥塞，稀疏传播可能需要更多轮，稀疏减少输入不保证端到端更快。

### CPU 实验：精确边计数与错误共识

下面是完整标准库程序。输入是 5 个虚拟成员和 3 轮；先验证公式、初始调用与更新调用，再用外部 gold=4 的合成题演示：独立初始候选 3 人错误答 5、2 人正确答 4，单纯跟随多数会把所有人带到错误共识。每轮读取同一 snapshot，平票返回 `None`，避免依赖列表先见次序。它不调用模型，不测 Token，也不证明真实辩论会改善或恶化。

```python
from collections import Counter

def incoming(n, kind):
    if type(n) is not int or n < 2:
        raise ValueError('n 必须是至少 2 的整数')
    if kind == 'mesh':
        return {i: tuple(j for j in range(n) if j != i) for i in range(n)}
    if kind == 'star':
        return {i: tuple(range(1, n)) if i == 0 else (0,) for i in range(n)}
    raise ValueError('未知拓扑')

def costs(n, rounds, kind):
    if type(rounds) is not int or rounds < 0:
        raise ValueError('rounds 必须是非负整数')
    reads = rounds * sum(len(v) for v in incoming(n, kind).values())
    return {'peer_reads': reads, 'initial_calls': n, 'update_calls': n * rounds}

def majority(values):
    count = Counter(values)
    high = max(count.values())
    winners = [value for value, freq in count.items() if freq == high]
    return winners[0] if len(winners) == 1 else None

def one_round(answers, graph):
    previous = tuple(answers)  # 同步轮读取不可变快照
    return tuple(majority([previous[i], *(previous[j] for j in graph[i])])
                 for i in range(len(previous)))

assert costs(5, 3, 'mesh') == {'peer_reads': 60, 'initial_calls': 5, 'update_calls': 15}
assert costs(5, 3, 'star') == {'peer_reads': 24, 'initial_calls': 5, 'update_calls': 15}
assert majority([4, 5]) is None and majority([5, 4]) is None
for bad in [('mesh', -1), ('unknown', 1)]:
    try:
        costs(5, bad[1], bad[0])
    except ValueError:
        pass
    else:
        raise AssertionError('应拒绝非法轮数或拓扑')
gold = 4
answers = (5, 5, 5, 4, 4)
initial_correct = sum(x == gold for x in answers)
trajectory = [answers]
for _ in range(3):
    answers = one_round(answers, incoming(5, 'mesh'))
    trajectory.append(answers)
assert initial_correct == 2 and len(set(answers)) == 1 and answers[0] != gold
print('mesh', costs(5, 3, 'mesh'), 'star', costs(5, 3, 'star'))
print('trajectory', trajectory, 'final_correct', sum(x == gold for x in answers))
```

## 第 25 课练习：参考判据

1. **第一轮强制分歧能否加速收敛？** 保持初始化独立，用“指出证据与反例”替代“必须给不同答案”。同题比较正确率、错误共识、轮数与成本；只有收敛更快而准确率下降不算改进。
2. **置信度加权聚合是否更好？** 明确置信度来源，预设平票/弃权。构造一位 0.99 置信错误者与两位 0.6 正确者，说明自报加权可能更差；用留出集校准后再比较，无普遍正确的固定权重。
3. **换成异构意见者是否提高准确率？** scripted LLM 只验证传播规则。真实比较固定题、信息与总预算，独立 gold，测共享错误；角色/供应商品牌不同不证明错误独立。
4. **画全连接与稀疏的成本—准确率曲线。** 先核有向边，再核初始化/更新调用；真实输入/输出 Token 与正确率分开测。仅 3 道已正确 toy 可以画带 fixture 标签的代理计数，不能标真实 Token 收益。
5. **改为 N=5、R=3 后什么变化？** 在本章约定下 60/24 peer reads、5 初始+15 更新调用。增加成员可能引入更多证据，也可能增加错误共识与通信；扩展实验需核原论文任务/轮数，不能从 toy 推断准确率收益。

## 第 25 课自检：七题与答案

1. **Society of Minds 协议做什么？** 独立提出答案，再按有界轮数读同伴意见、批评并修订，最终按明确规则聚合；没有必然收敛或必然正确的保证。
2. **跨模型为什么可能有帮助？** 不同错误模式可能提供反证；只有实测错误相关性与结果才支持收益。原题“为什么一定胜过单模型”的前提应撤回。
3. **稀疏通信省在哪里？** 减少同伴意见输入，可能减少输入 Token；质量与所需轮数须测，不能把任意拓扑都说成同准确率。
4. **何时辩论可能不划算？** 简单、可直接查证的事实题常由一次可靠查证更经济；按真实错误代价、延迟与预算选择。
5. **什么是收敛坍缩？** 成员早早跟随同一个错误候选。保独立候选、要求反证与外部验证可缓解，强迫假答案不构成可靠修复。
6. **同提示为何可能削弱辩论？** 候选与理由过于相似会减少交叉纠错信号；相同提示仍可有采样差异，不能断言必然 groupthink。
7. **orchestrator-workers 自带辩论吗？** 不一定。分派、并行工作与 synthesis 足够构成该模式；增加跨候选反馈后才能实现辩论。

## 第 28 课练习：参考判据

1. **去掉监督者改为 swarm，什么变好或变坏？** 同一任务保持初始信息和权限，重新定义 owner、终态、交接、失败与取消；测中央瓶颈和对等协调成本，不由“少 router”直接宣布更快。
2. **3-hop 能抓住 A→B→A 吗？** 构造依当前角色交替的路由，检查 0/1/3 次额度、未知目的地与循环；明确限制是交接次数还是角色访问数。耗尽返回可诊断终态，counter 只阻止无限交接，不解决权限和副作用。
3. **12 专家的两层系统何时需要嵌套？** 计算实际描述/资料 Token 和选择预算，检查组织职责、权限与故障域；比较上层摘要丢信息的风险。12 是练习输入，不是层级启用门槛。
4. **比较四种形态谁胜出？** 固定工作负载、初始 actor、预算与输出判据，测调用/Token、临界路径时延、正确率、错误恢复与可审计性。无真实生产采样时用明确合成题，不报告用户产品性能。
5. **用 Anthropic 原文映射自己的流程。** 可以从假业务流程练习，但同时标分工、控制拓扑与反馈协议三轴；有混合或单 Agent 的流程无需硬塞四类。本批没有部署业务流。

## 第 28 课自检：七题与答案

1. **源列出的四种是什么？** supervisor-worker、swarm、hierarchical、debate；前三多属控制结构，最后是反馈方法，可组合而非互斥全集。
2. **用工具调用监督有什么机制优势？** 宿主可给不同 specialist 裁剪上下文并限制可用工具。具体框架版本的推荐需查所用官方说明，这不意味着某 library 已弃用。
3. **swarm 与监督者区别？** 本课 swarm 允许当前角色对等交接，监督者集中路由；swarm 仍需要 runtime、权限与生命周期管理。
4. **层级何时合理？** 一层上下文/管理预算不足是一种理由，权限、职责或故障隔离也可以是理由；按收益决定。
5. **Anthropic 支持固定升级顺序吗？** 不支持本源固定阶梯；从能满足要求的简单系统出发，有评测收益才增加复杂度。
6. **什么是假层级？** 新层不对应独立职责、权限、数据或控制收益，仅重复路由规则；层数增加不自动提高能力。
7. **如何限制交接弹跳？** 同一任务有有限 hop、预算、明确终态与责任人，必要时回退/人工处理；记录整条轨迹供诊断。

## 多 Agent 是否值得：按任务瓶颈选择协作方式

2026-10-10 将第一来源 Phase16 第01、04–08课融合到已有分工与辩论解释。先修是本章的控制拓扑、任务包和同步轮次；消息意图与跨组织协议见[智能体间通信](15-智能体间通信-A2A.md)。本次增加的是如何选择、分解、保留证据和接受结果，已有消息边计数程序继续使用。

**上下文不足、工作可并行、权限不同、需要独立审核**是四种不同瓶颈。阅读许多文件时，先试确定性搜索、分块提取、外部索引和裁剪结果；这些方法有效时无需增加 Agent。只有子任务范围可以清楚划开，单任务收敛的结果又能被汇总，隔离上下文才可能有收益。角色提示词可以明确职责，却不会让同一模型突然拥有独立领域专长。能直接由脚本完成的格式检查、哈希和统计，优先由脚本完成。

| 工作的实际依赖 | 可选结构 | 验收重点 |
| --- | --- | --- |
| 调研证据是实现的输入，实现是测试的输入 | 顺序 pipeline，可有有界返工 | 上下游消费的是同一版本的规格和产物 |
| 三份不同资料能够分别读取 | fan-out/fan-in | 全部范围有结果，冲突与遗漏没有被摘要隐藏 |
| 执行中才发现要扩展哪个问题 | supervisor-worker | 动态增加工作的理由、预算和最终覆盖 |
| 独立任务组有各自数据/权限/故障域 | 层级监督 | 每层承担真实职责，并能追溯到叶节点证据 |
| 大量近似独立工作等待领取 | 队列工作者 | 归属、租约、背压、重试与副作用去重 |

简单的并行工具调用也能同时读取三份资料，不必每次增加三个模型循环。若子任务都依赖同一个正在修改的文件，分工可能制造竞态和重复工作；优先单一所有者、只读审查或清楚的文件分区。工作者数量、Token 上限和工具调用次数按当前任务测量，不采用来源“100k以下单 Agent、20次调用以下单 Agent”的固定门槛。

比较时固定任务集、起始信息、权限和总资源预算，报告完成率、重要遗漏、错误副作用、总输入/输出 Token、实际墙钟时延和人工复核成本。需要分清**模型调用次数与串行依赖深度**：同轮三个独立模型请求可以并行；顺序研究→实现→审查的三阶段仍须等待。并行时延通常由最长分支、排队、限流和汇总共同决定，不能简单把总调用数乘一次调用时长。

源01的 `fakeLLMCall` 只截断输入并返回固定格式文本，用字符数/4估 Token、随机生成工具调用数；它没有研究、编码或判断正确性。fan-out 的统计计入 reviewer 结果，返回的 messages 却未保存该结果，因此连演示轨迹也不完整。它可以说明输入如何流转，不能证明多 Agent质量更高或一定更贵、更慢。固定工具/API品牌和未经核验的排行榜判断不作为学习结论。

### 四个结构视角，不是“四轴穷尽所有系统”的定理

来源04的 actor、handoff、shared state、orchestrator 很适合读代码，但应视为分析视角：

1. **Actor**：谁消费输入、持有什么工具和权限、产生什么产物？它可以是模型、脚本或人工检查。
2. **控制转移**：当前任务是否交给下一角色，原角色是等待返回还是退出？交接不是普通信息通知，也不是授予对方更多权限。
3. **状态与投影**：原规格、任务所有者、消息、产物、预算与回执存在哪里，各角色看见哪一部分？共享全文简单，但会扩散无关内容与不可信输入；角色投影须保留必要证据与约束。
4. **调度**：固定阶段、条件边、模型选择、当前角色交接，还是队列领取？路由结果也需允许列表、依赖、预算和终态校验。

“只有共享状态有状态”只成立于特定玩具设计。真实 Agent可能有本地会话、训练参数、私有记忆；调度器有计数、租约、运行版本和取消状态；外部工具有已经发生的效果。将所有这些统称 shared state会掩盖其寿命和授权边界。静态图定义也不使节点内的模型或条件路由确定；可回放日志与真实再次执行得到同一输出是不同性质。

源码04把 message list 放锁中，并不使返回值深度隔离：`snapshot()` 只复制外层列表，`last_by()` 返回原字典，调用者仍可改嵌套内容；selector 又直接读 `state.messages` 绕过锁。真实投影应返回不可变结构或深拷贝，并把写入纳入统一提交边界。其三种默认调度都会研究→写作→审查；所谓“handoff少跑节点”需要另外改变 policy 才能出现。源码 Agent没有文中声称的tools字段，queue调度也未实现。

框架比较要固定版本、读取具体示例：AutoGen 0.4与AG2的旧 `ConversableAgent` 不能合并成一套 API；历史Swarm的“工具返回Agent”也不能概括当前Agents SDK。已有[框架概览](../02-附录/C-智能体框架快速概览.md)和[工具使用](05-工具使用.md)负责当前实现核验；这里保留 actor/控制/状态/调度的问题，不复制一张会很快变化的类名表。

## 监督者与层级：结果必须覆盖原需求

监督者可以把任务拆开、选择执行者和合并结果。它不必永远禁止自己读取原材料；尤其两份摘要冲突、引用缺失或核心结论无法核证时，直接检查少量原证据往往必要。结果包不能只有 summary：至少携带目标ID、所用输入版本、产物/证据位置、成功/失败/取消/未验证状态，以及剩余问题。收到子 Agent 的“完成”不意味着最终需求已经覆盖。

Anthropic于2025-06-13发表的[Research工程文章](https://www.anthropic.com/engineering/multi-agent-research-system)支持独立问题分工与预算控制；它报告的90.2%是特定内部研究评测，不是所有任务的固定优势。**15倍Token对比的是普通聊天**，其单 Agent对聊天约4倍；来源把15倍写成多 Agent对单 Agent是错误分母。80%是该分析中Token使用量解释的性能方差，不能证明“鲜上下文造成80%提升”。2026-10-10核对其收益、架构和生产可靠性部分，不将这些历史数值当当前产品承诺。

### 超时、失败和迟到结果要独立处理

任务包设一个单调时钟 deadline与全局资源预算；启动并行工作还要受并发限额约束。等待超时后，“调用方不再等待”与“工作者已停止”不同。Python 的 `Thread.join(timeout)`不会杀死线程；取消应合作执行，或在适当的进程/服务隔离边界中实施。迟到者即使返回漂亮结果，也要比较 task/run generation和当前owner，避免取消后污染新一轮任务。

结果可分为成功、有证据的失败、未完成、未知副作用；缺失分支必须展示。worker异常不能静默留下None，然后让剩余摘要成为“全面完成”。来源05使用三个 `sleep(0.3)` 线程、无限join、手填Token，演示的是等待重叠，不是模型、成本或生产吞吐测量。CPU计算、API限流、可共享工具锁和重试会改变实际收益。

上线前版本迁移要让新任务进入新版本，已有任务按兼容策略排空、续接或受控迁移。文章的rainbow deployment说明同时保留多版本的一种办法，不意味着任何blue-green方案都无效。日志记录目标、路由、父子任务、版本、预算与最终效果；敏感正文按采集政策处理，不为可观察性默认导出全部内容。

### 层级中的目标覆盖与证据压缩

例：原需求包含 `engineering` 与 `legal` 两个目标。上层误委派成 `engineering` 与 `finance`，下层即使认真完成，也没有补回legal。每层摘要都应携带自己实际覆盖的goal IDs、输入版本、leaf evidence与未覆盖项，顶层按**原需求集合**核对，而不是根据收到几份摘要决定成功。

原06脚本手填branch labels并返回canned answer，没有真实生成、随机纠错或覆盖检查；其原task文本也未写legal要求。它只能演示人为错分支，不支持“深度超过2必失效”或随深度的失败概率。树深度、分支数、摘要压缩量与故障隔离按实际任务测量。增加一层若只重复路由，没有独立职责与状态，就可能只增加损失。

canary把原问题再次交给一个检查者，可用于发现覆盖遗漏，但它不是ground truth。不同摘要对同一个实体、属性、单位和时间给出互斥事实时，回溯证据后再决定；不同时间的数值并不必然矛盾。自由文本无法可靠规范化时标待核，不能简单按字符串不同判冲突。对话达到两轮限额时应明确hold/escalate，而不是为了预算强制接受或提交有副作用的结果。

### 完整CPU例：版本、目标覆盖、冲突与迟到结果

下面是标准库程序，以合成结果包演示验收机制。它没有模型、线程、远端执行或业务副作用。版本变更后旧包拒收，状态非成功的包不能满足需求；输出分为缺失、冲突与验收。深拷贝避免提交者在验收后改嵌套证据。本例把精确字符串claim当可比事实，现实自然语言需先规范化或人工核对。

```python
from copy import deepcopy

class Review:
    def __init__(self, goals, version):
        if (type(goals) not in (list, tuple) or not goals or
            any(type(g) is not str or not g for g in goals) or
            len(set(goals)) != len(goals)):
            raise ValueError('需求非空且唯一')
        if type(version) is not int or version < 1:
            raise ValueError('版本必须是正整数')
        self.goals, self.version = frozenset(goals), version
        self.results, self.attempts = [], []
    def submit(self, package):
        p = deepcopy(package)
        self.attempts.append(p)
        if type(p) is not dict or set(p) != {'version', 'state', 'claims'}:
            raise ValueError('固定结果包字段')
        if type(p['version']) is not int or p['version'] != self.version:
            raise ValueError('旧版本或迟到结果')
        if type(p['state']) is not str or p['state'] not in {'success', 'failed', 'unknown'}:
            raise ValueError('未知状态')
        claims = p.get('claims')
        if not isinstance(claims, dict) or not claims:
            raise ValueError('结果需有目标claim')
        if not set(claims) <= self.goals:
            raise ValueError('错分支或额外目标')
        for goal, item in claims.items():
            if (not isinstance(item, dict) or
                not isinstance(item.get('value'), str) or not item['value'] or
                not isinstance(item.get('evidence'), str) or not item['evidence']):
                raise ValueError('结果缺具体主张或证据')
        self.results.append(p)
    def decide(self):
        values = {goal: set() for goal in self.goals}
        for p in self.results:
            if p['state'] == 'success':
                for goal, item in p['claims'].items():
                    values[goal].add(item['value'])
        missing = sorted(g for g, v in values.items() if not v)
        conflicts = sorted(g for g, v in values.items() if len(v) > 1)
        unresolved = any(p['state'] != 'success' for p in self.results)
        return {'missing': missing, 'conflicts': conflicts,
                'accepted': not missing and not conflicts and not unresolved}

def package(goal, value, version=2, state='success'):
    return {'version': version, 'state': state,
            'claims': {goal: {'value': value, 'evidence': 'fixture:'+goal}}}
def reject(call):
    try: call()
    except ValueError: return
    raise AssertionError('应拒绝')

r = Review(['engineering', 'legal'], 2)
reject(lambda: Review('engineering', 2))
reject(lambda: Review(['engineering'], True))
reject(lambda: Review(['engineering'], 2.0))
reject(lambda: r.submit([]))
reject(lambda: r.submit(dict(package('legal', '通过'), version=True)))
reject(lambda: r.submit(dict(package('legal', '通过'), version=2.0)))
reject(lambda: r.submit(package('finance', '成本通过')))
reject(lambda: r.submit(package('legal', '通过', version=1)))
eng = package('engineering', '通过')
r.submit(eng)
eng['claims']['engineering']['value'] = '事后篡改'
assert r.results[0]['claims']['engineering']['value'] == '通过'
assert r.decide()['missing'] == ['legal']
r.submit(package('legal', '待确认', state='unknown'))
assert r.decide()['accepted'] is False
r.submit(package('legal', '通过'))
assert r.decide()['accepted'] is False  # 未解决的旧attempt不能被最后成功隐藏
conflict = Review(['engineering'], 2)
conflict.submit(package('engineering', '通过'))
conflict.submit(package('engineering', '不通过'))
assert conflict.decide()['conflicts'] == ['engineering']
fresh = Review(['engineering', 'legal'], 3)
fresh.submit(package('engineering', '通过', version=3))
fresh.submit(package('legal', '通过', version=3))
assert fresh.decide()['accepted'] is True
print('覆盖缺失、错分支、旧版本、深拷贝、未知状态与冲突检查通过')
```

`fixture:` 引用只是固定测试数据的来源标签，不是原始资料验真。unknown只可在查明实际情况、建立新的受控run与证据关系后解除；这里用新run示范，不把旧unknown直接改成success。该程序证明本地接受规则，不能证明真实多 Agent具备独立知识或生产权限正确。

## 角色分工中的验证：确定执行不等于完备正确

Planner负责需求与步骤，executor产生结果，critic按规范检查设计和遗漏，verifier对可检验的主张给出实际证据。区分职责不意味着每个角色都要创建一次LLM调用；测试、类型检查和schema校验可以直接用代码。critic也可指出逻辑/安全问题，不限于“主观品味”；verifier的决定是否确定，取决于输入、工具与oracle，不能由名字保证。

例如目标是返回两整数之和，executor写成乘积；字面检查“有def、有return、函数名正确”会通过，输入(1,2)却得到2而非3。来源08叫它LLM critic，实际只是三个字符串条件。真实review应检查需求/代码关系，测试应覆盖正、负、零、类型与异常等契约；测试通过仅说明这些测试的行为，不证明所有输入正确。若executor能看见并针对有限测试硬编码，确定验证同样可以被投机；需求与测试自身也可能错。

来源的 `exec(code, {}, {})` **不是安全沙箱**：默认builtins仍可见，不阻止文件、网络、进程调用或无限循环。本批不执行这段来源程序，也不执行任意生成代码。实际执行需另设访问、资源、时间和进程隔离，记录可信输入与副作用边界。隔离降低执行风险，不自动提高程序正确性。

### SOP、订阅与缺信息询问怎样接起来

[MetaGPT v7 §3.1–3.3](https://arxiv.org/html/2308.00352v7)把五种职责串成产物链：PM消费需求产PRD/user stories；architect产文件列表、数据结构、接口与交互图；project manager分配任务；engineer实现；QA构建测试。共享message pool配合角色订阅，在依赖齐备后触发行动；执行反馈可驱动修订。保留的是结构化交付与依赖，**SOP不会把模型输出变成确定程序**。原论文示例的最多3次修订也不是所有系统的最佳上限。

[ChatDev v5 §3.2](https://arxiv.org/html/2307.07924v5)的communicative dehallucination包含assistant/instructor角色反转：执行者需要精确依赖或类名时，先问具体问题，再按建议修改。询问可以阻止未经确认的猜测，但回答仍可能错，循环仍要设预算。完整示例：requirements说明“整数加法”；planner未说明bool是否算整数，executor先问类型契约；verifier发现测试没覆盖此条件时回问需求，而不是替用户发明约定。

原08把所有MAST失败归于缺验证，误把1642条execution traces全叫失败，又附无法追溯的PwC“10%→70%”。[MAST v3](https://arxiv.org/html/2503.13657v3)分类覆盖系统设计、Agent间失配与任务验证，并承认模型本身的局限；本章不把该比例或案例写成普遍因果规律。对于开放研究、创意和罕见现实决策，可能没有便宜且完备的oracle；可验证部分仍检查，其余用来源与人工rubric记录不确定性，不造一个必定pass的验证者。

## 辩论的新边界：数值趋同模拟不能代替论文复现

已有同步轮、共识与错误共识程序适用于来源07。本次补充三处辨别：

- 来源 `single_shot_majority` 实际返回算术均值；`agreement_score` 是落在mean±0.1范围的比例。它们分别不是离散多数投票与多数占比。离散多数须规定平票/弃权；连续估计可用均值或加权平均，但不能沿用投票证明。
- `updates`保存活Agent引用，逐个`revise`时会读到先修改者的当前答案，因此是依顺序的原地更新，不是大家读取上一轮快照。源码seed对固定初始答案没有作用。它未运行LLM、批评理由或事实核验，几轮后spread变小只证明该平均规则的数值动态。
- 各成员看见相同意见可能使错误更相关，辩论并不必然“去相关”。异构模型、不同采样与证据可以提供多样性，但必须实测；“永远反对”也可能制造假反例。要求可核反证，允许支持、反对、撤回和未定，比强制争论更可靠。

[Du v1 §2](https://arxiv.org/html/2305.14325v1)明确一般不保证收敛，主要实验为3Agent、2个批评轮；不能据此规定所有任务N≤5、R≤3。论文中不同答案生成与外部任务结果才是实验，本课程平均脚本不可复现这些性能。[Should we be going MAD v3摘要与策略](https://arxiv.org/html/2311.17371v3)发现其比较条件下MAD不稳定胜过self-consistency/ensemble，调参、agreement策略与成本均影响结果。可选Multi-Persona的不同立场+judge、ChatEval顺序/同步/摘要协议；每种需先固定哪些历史可见、何时停止与怎样接受。

[NLSOM v2](https://arxiv.org/html/2305.17066v2)探索多模态角色组合，报告最多129成员的系统；它不是“129个LLM在同一个VQA题辩论”的统一方案。所读Artist-Critic附录包含艺术风格生成、critic投票与绘图角色，作者文字的组成计数也需谨慎核对；这里保留模块化专家和产物交接，不引用成员数当通用扩展收益。

## Phase16原练习：组织、调度与结果验收参考答案

### 第01课三项练习与五题自检

1. **增加tester**：输入绑定同一code digest、spec与review，输出测试计划、实际命令/结果和未覆盖条件。review反馈不能代替测试运行。
2. **最多两轮返工**：每轮绑定版本，拒收过期review；验证未满足或预算耗尽时给出未解决终态，不能把最后一次code直接当成功。
3. **并行research与requirements**：确认两者无依赖后并行；coder等待二者齐备并看清冲突/缺失。比较质量、总成本和临界路径，而非单看并发数量。

| 自检 | 中文参考判断 |
| --- | --- |
| 单Agent ceiling指什么？ | 单循环的上下文、职责与依赖处理瓶颈，不是固定文件数或Token阈值 |
| 为什么考虑specialists？ | 专用输入、工具和输出可隔离工作；角色名字不保证能力或质量 |
| pipeline何时胜过fan-out？ | 下阶段实际依赖上阶段产物时；独立子任务才并行 |
| supervisor做什么？ | 分解、委派、收回结果并决定下一步与最终验收 |
| 主要代价是什么？ | 协调、调用与故障成本；并行可能降低时延，成本和质量需测 |

### 第04课五项练习

1. **改policy比较三个调度**：固定输入与输出判据，记录谁执行和为什么；默认源码三个模式都走三个节点，改变policy才可能改变路径。
2. **增加queue scheduler**：检查任务依赖、有限等待、owner/lease和完成条件；队列空不等于所有工作成功，持锁等待future或依赖环要明确失败。
3. **映射LangGraph**：node可以实现actor，edge/condition控制流，state/reducer处理合并，checkpointer等管理持久状态。条件值可能来自模型，图不自动确定。
4. **读Swarm cookbook**：历史演示强调routines/handoffs，调用者仍承担上下文；当前SDK不只复制旧tool-return-Agent，复用已有版本说明。
5. **“哪个框架完全隐藏state”**：原前提不能通用成立；先明确状态寿命、owner、上下文和回执责任。未持久化会丢约束、重复执行和无法恢复，不靠框架名字判断。

### 第05课五项练习

1. **增至5workers看时延**：sleep toy仅证明等待重叠；测固定工作负载、启动成本、限流和合并开销。不能从0.3秒等待外推真实模型。
2. **0.5秒超时kill**：join不杀线程。合作取消/进程隔离与generation fence拒迟到结果，记录deadline、取消请求、ack和最后副作用状态。
3. **无LLM检测矛盾**：规范化同对象、属性、单位和时间，检查互斥值；不能解析的文本保待核。不同时间或不同范围的值不自动冲突。
4. **生产需要哪三项**：明确子任务/证据边界、持久恢复与预算、版本/错误追踪和排空。Anthropic历史15×对聊天，原分母要改。
5. **库与直接tool supervisor比较**：官方README推荐多数场景直接tools以控制context，同时保留库兼容及例外；未说弃用。摘要省输入，但冲突时应能回看原证据。

### 第06课五项练习

1. **happy/perturbed几层后偏离**：手填顶层legal→finance立即漏legal；本脚本不产生层数概率，必须先把需求显式列出来。
2. **再加层统计纠正率**：固定脚本无随机纠错，不能声称概率。构造同需求/预算、多扰动和seed的合成或真实实验，分别测覆盖、错误级联与成本。
3. **canary如何处理异议**：它是另一检查信号，不是ground truth；回溯叶证据、修正分解或标未解决，必要时暂停副作用。
4. **CrewAI具体限制**：固定当前版本核manager_llm/manager_agent、max_iter等实现参数；限制循环不证明正确，数字也非层级通用上限。
5. **哪家loop更便宜检测**：parent/run/subgraph/goal事件都可追踪；未对同任务实测不排名框架价格或debug能力。

### 第07课五项练习

1. **增加至5轮哪里停**：按预设epsilon、预算与外部正确性停止；原平均脚本不是LLM，不支持“3轮总最优”。
2. **永远反对的第四人**：可能打破盲从，也可能编造分歧；改为提出可核反例并允许撤回，用独立gold检查真实收益。
3. **agreement达到1是否正确**：多数占比与mean±tol必须分开；全部一致仍可全错，已有错误共识程序给出反例。
4. **复现agents-only/rounds-only/both**：平均toy只能验证更新规则；论文任务要固定题、预算、初始化与gold，分别做真正模型实验。本批未做。
5. **其他debate variants**：Multi-Persona有angel/devil/judge且可早停；ChatEval有顺序、同步和同步摘要。固定历史可见性与停止规则再比较，不能由名字断言优劣。

### 第08课五项练习

1. **数return的静态检查**：字符串/注释/多分支会误判；可核AST、类型与测试，但没有一个条件证明正确。namespace exec不是sandbox，不执行不可信代码。
2. **requirements分析者加什么**：明确单位、异常、类型、功能与权限；缺信息传给适当上游，verifier发现oracle缺口也回问需求，而非自造标准。
3. **MetaGPT五角色I/O**：需求→PRD→系统设计→任务分配→实现→测试；角色的结构化消息与订阅减少无关传播，SOP不保证确定或正确。
4. **ChatDev破循环在哪**：§3.2角色反转询问具体缺信息，再精准修改；实验有不变代码/轮数停止条件。不是图示本身证明无限循环被解决。
5. **哪里没有便宜oracle**：创意质量、开放研究论证、稀有现实决策。可核部分继续检查，剩余来源与人工rubric判断；撤回缺出处的PwC普遍7倍说法。
