## 本章定位

在关键节点引入人工确认、反馈、审批或干预，实现可控的人机共同决策。

## 把人工节点放在真正的决策点

人工协同可以解决缺失信息、偏好选择、超出已授权范围的操作和结果验收。只读且范围明确的常规步骤可按既有授权执行；不要把每个中间动作都变成确认请求，导致用户无法分辨重要决定。

审批应绑定具体对象、动作和参数。用户批准版本 A 的计划后，若收件人、金额或内容变为版本 B，就不能沿用含糊的旧批准。等待输入期间保存状态，并继续可独立完成的工作。

## 具体例子：准备一封邮件

助手先读取用户提供的材料、整理草稿、显示收件人/主题/正文。用户只要求“写草稿”时，完成到草稿即可；用户明确授权发送具体邮件后，执行发送并核对结果。草稿润色权限不等于发送权限，发送授权也不等于可任意增加收件人。

人工看见的应是可判断的成品和重要差异，而不是“是否继续”四个字。最终验收记录用户决定与实际执行结果，避免只保留模型的解释。

## 自检与核对

**问题**：用户已经批准一次同一范围的批处理，每条记录是否都要重新确认？

**核对**：通常不需要，除非范围变化、出现新风险或明确规则要求逐项批准。应复用已有授权，并只把异常项交给用户。

## 来自《深入理解 AI Agent》的增量吸收

- 人工介入应被设计成明确的系统节点，而不是发生问题后临时接管：高风险动作审批、歧义澄清、失败升级和结果验收都可触发人工。
- 交互形态从文本扩展到语音、GUI、异步消息和现实世界操作后，人机协同需要同时管理**控制权、时序和反馈渠道**。
- 人类评估与自动评估应互补：人工用于价值判断、边界案例和高风险样本，自动评估用于规模化回归。

## 状态机中的人工输入、断点与恢复

StateGraph的node读state并返回update，edge决定去向；conditional edge不是一个node，源“agent/tools/条件边/回边共四node”计数错误。Reducer定义同key怎样合并，默认替换、operator.add追加与add_messages按message ID追加/更新不同。TypedDict主要是静态约定，运行时仍需校验；并行写未声明可合并字段可触发InvalidUpdateError，不是默默last writer wins。[官方Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)、[并发更新错误](https://docs.langchain.com/oss/python/langgraph/errors/INVALID_CONCURRENT_GRAPH_UPDATE)于2026-10-07核对。

静态`interrupt_before/after`是node边界的debug断点，按官方以`None`输入继续。动态`interrupt(value)`在node中请求输入，用`Command(resume=...)`在同thread恢复，node从头重新执行，interrupt前代码可能重跑；二者不能混用。[官方interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)支持的typed response_schema与普通JSON Schema dict有不同校验行为，不能只见schema字段就断言运行时已验。

[Checkpointer](https://docs.langchain.com/oss/python/langgraph/checkpointers)在super-step边界保存完整snapshot，并保存完成task的pending writes用于同step失败恢复；不是任意语句后checkpoint。InMemory保存不跨进程，thread_id需区分租户/用户/会话，访问历史也鉴权；checkpointer短期thread状态与Store跨thread记忆不同。保存checkpoint不等所有外部写已精确一次，time-travel恢复计算状态也不撤销已发邮件或数据库写。

### 可独立运行的暂停、持久恢复与冲突小例

以下是SQLite支持的**自写有限状态机**，不是LangGraph替身或SDK实跑。草稿→等待批准→完成，批准绑定run与草稿版本；本地effect receipt与状态同一数据库事务提交，所以本fixture重试不会重复“发送”。真实邮件无法与本地SQLite共享原子事务，需outbox/供应商幂等与查询回执，不能照此宣称网络exactly-once。

```python
import sqlite3,tempfile,json,hashlib
from pathlib import Path

def fingerprint(text):return hashlib.sha256(text.encode()).hexdigest()
class Flow:
    def __init__(self,path):
        self.db=sqlite3.connect(path)
        self.db.executescript('CREATE TABLE IF NOT EXISTS state(run TEXT PRIMARY KEY,body TEXT);CREATE TABLE IF NOT EXISTS effects(key TEXT PRIMARY KEY,body TEXT);')
    def start(self,run,draft):
        state={'status':'awaiting','draft':draft,'sha':fingerprint(draft),'approved':False}
        with self.db:self.db.execute('INSERT INTO state VALUES (?,?)',(run,json.dumps(state)))
        return state
    def load(self,run):
        row=self.db.execute('SELECT body FROM state WHERE run=?',(run,)).fetchone()
        if row is None:raise ValueError('未知run')
        return json.loads(row[0])
    def resume(self,run,sha,decision):
        if type(decision) is not bool:raise ValueError('明确bool决定')
        with self.db:
            s=self.load(run)
            if s['sha']!=sha:raise ValueError('旧稿批准不可复用')
            if s['status']=='done':return s
            if s['status']!='awaiting':raise ValueError('状态不允许恢复')
            if not decision:s['status']='rejected'
            else:
                key=run+':'+sha
                self.db.execute('INSERT OR IGNORE INTO effects VALUES (?,?)',(key,s['draft']))
                s.update(status='done',approved=True)
            self.db.execute('UPDATE state SET body=? WHERE run=?',(json.dumps(s),run))
        return s
    def close(self):self.db.close()
def merge_by_id(old,new):
    result={m['id']:dict(m) for m in old};order=[m['id'] for m in old]
    for m in new:
        if m['id'] not in result:order.append(m['id'])
        result[m['id']]=dict(m)
    return [result[i] for i in order]
def merge_parallel(updates):
    result={}
    for update in updates:
        for key,value in update.items():
            if key in result:raise ValueError('未声明reducer的并行同key写入')
            result[key]=value
    return result
with tempfile.TemporaryDirectory() as d:
    p=Path(d)/'state.sqlite';f=Flow(p);s=f.start('tenant-a/session-1','草稿A');f.close()
    f=Flow(p);assert f.load('tenant-a/session-1')['status']=='awaiting'
    try:f.resume('tenant-a/session-1',fingerprint('草稿B'),True)
    except ValueError:pass
    else:raise AssertionError('版本变化必须重新确认')
    assert f.resume('tenant-a/session-1',s['sha'],True)['status']=='done'
    assert f.resume('tenant-a/session-1',s['sha'],True)['status']=='done'
    assert f.db.execute('SELECT count(*) FROM effects').fetchone()[0]==1
    s2=f.start('tenant-a/session-2','另一草稿');assert f.resume('tenant-a/session-2',s2['sha'],False)['status']=='rejected';f.close()
msgs=merge_by_id([{'id':'m1','text':'旧'}],[{'id':'m1','text':'新'},{'id':'m2','text':'追加'}]);assert [m['text'] for m in msgs]==['新','追加']
try:merge_parallel([{'plan':['A']},{'plan':['B']}])
except ValueError:pass
else:raise AssertionError('并行冲突不能静默覆盖')
print('SQLite重开恢复/批准版本/本地原子receipt/拒绝分支/message ID更新/并行冲突通过；无LangGraph或真实发送')
```

批准变更tool_call时保留其关联ID与对应ToolMessage，拒绝需合法停止/替换流程；不能追加一句“blocked”后仍路由执行pending旧调用。审阅节点前只做可重放纯计算，把外部副作用置后或以持久task/幂等key保护；循环、Send fanout、subgraph自己的state/namespace与reducer另行定义。保留checkpoint code/config/schema版本，恢复前核迁移，不对任意code顺序变化保证可继续。

## 提议、审阅、执行、核验：批准必须指向同一个动作

长期流程的人工协同需要保存**具体 proposal**：稳定 operation ID、租户/任务、动作及参数摘要、当前对象版本、意图、资料来源、所需权限、最坏影响和恢复方法。等待期间人可以拒绝、修改或撤销；同一合法请求的重试返回原记录，不重新制造一次“待批准”。参数或对象版本变化后，重新形成可审阅提议；不要把批准一个标题当批准后续任意正文。

状态可组织成 `waiting → approved/rejected/expired → executing → verified/unknown/failed`。操作者身份、权限、批准时刻/有效期、批准的摘要与撤销记录均由可信控制层保存。展示决定与执行状态分开：“批准已收到”不等副作用已发生。拒绝、过期、撤销或缺失字段不能默默默认 approve；未知效果接[异常处理和恢复](12-异常处理和恢复.md)。

**提议 idempotency 与目的端 idempotency 是两项合同。** 原第 15 课把 key 定为 `hash(thread_id,action,payload)`：重复提交可合并，但若用户合法两次发送完全相同内容，也会错误折叠。先给每次业务意图稳定且持久的 operation ID，再绑定不可变参数 digest；相同 operation ID＋不同参数拒绝，同一意图的所有 retry 沿用原 key。批准记录的幂等不能代替邮件/支付/外部服务真的按此 key 去重。持久等待只让“后来找到提议”成为可能，不使两天前批准在对象改变后仍有效。

结构化审阅应让人容易看到实际差异、对象、收件人/金额、不可逆性与恢复限制。针对具体操作设计问题或 checklist 可降低无意识点击；“我理解/风险可接受/可回滚”三个勾选并不证明理解，不能称所有产品唯一规定。已有同事项批量授权继续有效；只在真实合同要求、信息变化或越出范围时暂停，避免确认疲劳。

2026-10-09 核对：[LangGraph `interrupt`](https://docs.langchain.com/oss/python/langgraph/interrupts)通过同 thread 与 `Command(resume=...)`续接，node 前段会重跑；[Microsoft HITL](https://learn.microsoft.com/en-us/agent-framework/workflows/human-in-the-loop)有 typed request/response、`RequestInfoEvent`、request ID 和响应路由；[Cloudflare HITL](https://developers.cloudflare.com/agents/concepts/human-in-the-loop/)把 MCP elicitation、Workflows `waitForApproval()`、Code Mode approval 分成不同层。这些 primitive 不自动实现统一 proposal 字段、reviewer ACL、参数摘要、目的端幂等或有效审阅，需应用补齐。前文 SQLite 小例已验证同库原子 receipt 与批准版本，不重复生成它。

**源代码的三个缺口。** `checklist_approve` 用 truthy 判断，字符串 `"false"` 也可能过；函数能把 committed 再写为 approved，使后续重发；`execute` 完成后才写 committed，中间 crash 会重复效果，且 `verify=False` 仍返回 True/committed。源 demo 没模拟该崩溃窗口，内存 SIDE_EFFECTS 也不跨进程。因此两次正常 retry 不等网络 exactly-once；真实状态应由目的端 receipt 与重核后置条件推动。

关于法律，按[EUR-Lex 原法 Article 14](https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:32024R1689)的第 1–4 款核对：它针对 high-risk AI 的有效自然人监督、比例原则、理解能力/局限、避免 automation bias、解释/忽略/覆盖/逆转输出和安全停止。原条没有规定必须三项 checklist、PostgreSQL、某种 checkpoint 频率或每个 Agent 外部动作逐一点击；有关日志又有独立条款。工程模式有助落实监督，不能单靠本例宣称达到法定合规，具体系统仍需判适用范围与完整要求。

### Phase15 第 15 课练习参考

1. **重复执行与 key。** 正常重试同 key 可被本地记录阻止；源没有覆盖 effect 后/status 前 crash，重新批准还会反转状态。timestamp 每次新生成会破坏同一业务意图去重；首次持久生成的唯一 ID 可含创建时间信息，并非含时间就绝对无效。
2. **verify fail 自动 rollback？** 先区分确认失败、回读迟到与效果 unknown。无法确认时冻结新写并核receipt；只有已知效果和安全补偿合同才补偿，不能把未知邮件“补偿”为再发一封。练习完整回读/补偿反例在恢复章节新例。
3. **RequestInfoEvent 缺什么？** 它的 request ID 帮正确匹配响应，typed payload 帮消息合同；业务 permissions/digest/expiry/rollback 要自己定义，不把 toy 或框架字段想象成自动包含。
4. **公开发帖审阅。** 显示确切账号、最终正文/媒体/链接、公开对象与敏感资料、发布后可删但可能已传播的限制。问题应核账号/内容/权限，已明确授权具体内容可直接执行后回读，无需为同事项再循环询问。
5. **同步确认何时足够？** 短时、无跨进程等待、作用可控、确认绑定当下实际参数时可用；仍核中断/重试与外部效果。无需把本地可逆编辑一概升级为 durable 审批服务。

## 人工审阅：资格、证据、容量与申诉

已有提议/批准/执行/核验流程继续管理同一动作。增加human review并不自动使系统安全：人必须有相应资格与权限，看到足够证据，能拒绝/纠正/升级，并有时间真正审阅。审批动作、核对内容、业务裁决和运营交接可以由不同角色承担，不能因都叫 reviewer 就混成一个能力。

审核界面以来源和待决问题为中心，显示关键限定词、版本/日期、冲突、候选差异和不可逆后果。模型confidence和固定“同意”按钮只提供线索；提交者自填 `approved:true`不证明真人或合格owner作出决定。缺政策时升政策owner，缺权限时升授权owner，不能要求普通审阅员替所有专业责任签字。

审阅样本至少有三类：高后果、partial/冲突、随机普通任务。前两类集中风险，后一类发现尚未命名的错误；报告抽样概率/范围、分母、审核一致性、裁决与反馈，不能把非随机高风险集的正确率当整体质量。争议需要保留原候选、证据、人工理由、修订与可申诉路径，而不是只保存最后 approved。

**容量手核例**：每日240件，30%要审核，平均4分钟，则期望工作量240×.3×4=288分钟。一个8小时班次只有60%可用于审核，也只有288分钟，均值恰好持平，尚无波动、返工、培训或请假的余量。高峰到达与服务时间变化还会形成队列，应测等待分布、积压、资格覆盖、SLO、溢出和安全降级；不能仅凭“有人审”推出稳定可用。

运营交接也需要人，但验的是接收方能monitor/eval/contain/shutdown/rollback/recover/change及接受责任。让接收者在已授权的演练环境独立处理旧政策、授权中断、注入、评价器漂移与过载，记录动作/版本/receipt/未通过项。课程91分不能抵消待核授权或回滚演练，资料可访问不等交接完成。

**参考练习**：①审核员面对来源冲突如何处理？保partial/conflict、指出需要谁裁决、停止超出其权限的动作。②审核改了退款金额，旧批准还有效吗？摘要和参数变化后需绑定新提议，不能只保同工具名。③把所有检查改成勾选框是否达成治理？不能，必须有实际证据、资格、执行边界和复验。④怎么验证随机普通样本？记录抽样方式与未选中任务分母，比较漏报/裁决/时间，避免只抽模型主动报错案例。

## 日常审阅台：完整候选、决定与实际作用分开验收

把人工放进工作流，不必先做一个新的审批平台。日历提案、未发送邮件、反馈调查草稿和会议动作收件箱，都可以先生成可审阅产物，再按已经授权的目标消费。真正要避免的是：把“字段齐全”“有人选过 approved”和“外部动作已完成”当成同一个状态。前文的 proposal/当前版本/可信批准/效果回执合同继续有效，以下只补充这些日常场景的判断方法。

### 字段状态、人工决定、外部效果是三个维度

| 维度 | 示例状态 | 应回答的问题 |
|---|---|---|
| 候选数据 | missing、invalid、ambiguous、complete；另有 overdue | 有什么证据，字段是否可用，哪些需要补充？ |
| 审核决定 | pending、approved、rejected、expired/revoked | 谁在什么范围/版本下允许采用哪份候选？ |
| 实际作用 | not_started、draft_saved、submitted、verified、unknown、failed | 实际保存、导入或发送了什么，回读证据是什么？ |

会议来源首轮 ready=2，只表示两条 owner/date/task 完整；三条都 pending，approved=[]；按 CLI 导出合同，CSV 应只有表头。逾期也不必然等拒绝：它可以是“字段完整、已过期限、仍待决定”，具体是否允许继续由当前业务规则和授权决定。未知责任人/日期则不能因选了 approved 就跳过字段门。状态计数分别报告，不用一个绿色 ready 让人误以为动作已经获准。

邮件 action 类别只表示规则命中，不能承诺已提供桌椅、付款或完成打印；草稿保留原句与待编辑位置即可。X-Unsent:1 表明产物意图，项目没有 SMTP 代码；它不是跨应用通用权限控制。把 EML 导入另一个客户端后，仍需由那个执行入口核当前收件人、最终正文、用户授权和发送结果。

### 审阅对象应包含会改变后果的字段

同一已授权范围的批次可以复用既有批准和批量规则；只把变更或异常带回人工，不要求每个正常中间步骤再次点头。为了判断是否仍是同一事项，应给人看最终内容和关键差异，而不是一个名称或摘要分数。

| 场景 | 审阅时至少能看见 | 消费前再核 |
|---|---|---|
| 日历提案 | 日历/日期与时区、每块起止/时长、任务身份、buffer/工作窗/排序政策、未排原因；是否带参与人及通知后果 | 当前忙闲版本、任务/提案摘要和已授权目标；旧空闲快照过期后重新计算，不以文件已存在当导入成功。 |
| 邮件草稿 | 准确 To/必要抄送、主题/最终正文、所回复 message ID 与 thread、附件范围、来源及不确定分类 | 当前草稿版本和真实授权；分类/原发件人字段不替代收件人核验，发送后查真实对象/回执。 |
| 会议动作 | owner、完整 due、task、原行与提案语法、缺失/冲突标记、当前决定及改动 | 当前候选/来源/规则、决定值与权限；先验整份决定，再导出获批完整项，导出和外部建任务分开。 |
| 反馈调查 | 原句、跨度与单位、主题配置/匹配政策、重复关系、不同来源标签、未分类内容 | 模型配置仍只是 proposed；采用哪个配置和发布哪个最终调查草稿分别有记录，不能把词命中写成已确认缺陷或真实客户数。 |

来源会议页的每项摘要只显示 owner/task/decision，due 要点 source 看原文；这不利于核对具体截止日。应把后果关键字段直接呈现，而不是要求人从隐藏上下文补齐。静态 HTMLParser 能证明 selected 值被保留，不证明真实浏览器下载、无障碍操作、误点恢复或审阅质量；这些是后续界面验收。

### 局部 ID 能防一部分陈旧决定，不能绑定整个审阅域

会议来源把 owner、due、task、source lines 做摘要并取前16个十六进制字符作 action ID，先建立全部当前 ID，再拒绝决策文件中的 unknown/stale ID。移动原行会改变 ID，因此旧文件不能默默批准新位置；这是有用的局部合同。可是原文的其它语境、proposal 标记、解析规则、目标系统和权限不在该 ID 中。报告虽带 source_sha256，决策文件仍只是 id→choice，没有核该摘要；原行号与字段不变时，语境变化可能沿用旧决定。

因此先定义“本次批准绑定的审阅域”：可能是完整来源版本，也可能是经过明确政策选定的对象与相关上下文。保留稳定业务意图 ID、候选集合/内容摘要、来源与解释规则版本、具体对象/动作/目标、可信审核者和有效条件。只有这个域不变、权限仍有效时才复用批准；若域变了，形成新候选与差异说明。不要把所有无关文字改动都一律升级为额外审批，也不能把内容不变当作新目标自动获得授权。

本地 JSON 中的 approved 是决定数据，不是审核者认证。可编辑 reviewer 字段、自算 hash 或图中的 checkbox 都不会产生可信身份；同样，来源邮件 build_draft 的 message_id 相同也没有冻结正文。沿用前文可信控制层和 SQLite 示例的版本拒绝思路，增加业务对象/上下文合同，不退回“只看 ID/选项字符串”的较弱例。

### 在动作前拒绝坏决定，在动作后核对真实结果

审阅消费按顺序落实：冻结并预检当前候选；检查整份决定的对象、类型、允许值及当前版本；任何非法项使本次接受失败；再根据明确的批量政策形成可消费集合。对缺字段的行，不因 UI disabled 就省掉后端拒绝，因为 JSON 也可手工生成。对 pending/rejected，不擅自补 approved 来让导出数量好看。

来源会议 CLI 的陈旧 ID 测试要求在写 HTML/JSON/CSV 之前整体失败；这个性质应保留。它没有因此得到后续三文件 I/O 的原子性。保存中途失败，或者邮件规则审阅台已生成而可选模型分支随后失败，都可能留下部分结果。回读当前 manifest/generation 与实际文件，分别记录接受、发布和清理状态，不能把异常解释成“什么都没发生”。

当目标只是本地草稿，核指定产物和内容即可完成该目标；当用户授权真实导入/发送/发布，才进入对应执行入口，核目的端幂等、当前权限与实际回执。没有这类授权的读取任务，应停在资料与提案边界。本批的四项目都只作教材静读，没有邮件、日历、issue、任务系统或模型调用。

### 核对练习：让决定和后果能一一对应

1. **complete 但未 approved**：两条会议动作字段完整，决策文件为空。参考：ready 可为2，approved 必须为0，不能自动导出两条。补 unknown/mixed stale ID 应整份拒绝，不仅忽略那一项。
2. **旧日历仍有空闲**：上午批准的块，下午日历新增冲突会议。参考：保原提案和批准记录，核当前忙闲与授权；冲突使原可执行条件不成立，应给差异/备选，不强行导入旧块或凭模型说“已安排”。
3. **相同邮件 ID、正文已改**：旧分类或旧批准不能仅靠同 ID 继承。参考：核正文/候选摘要、收件人和内容；引文存在也不能替代类别与承诺的语义审核。
4. **来源标签从1变2**：反馈复制到另一个自报标签后计数增加。参考：审核变的是记录/标签数，不声称出现第二名独立客户；采用/发布决定保原文和配置。
5. **已选择值重开**：批准一个、拒绝一个，重开页面后直接下载。参考：应保留原 selected 决定；下载文件还需重新验证版本、值域和权限，不能直接触发外部动作。
6. **已批准导出却消费失败**：若 CSV 已写而后续 JSON 写失败，先核实际产物/版本，不补造“全部未写”或重复外部创建。记录 unknown/partial 与恢复范围，原授权仍按具体事项判断。
