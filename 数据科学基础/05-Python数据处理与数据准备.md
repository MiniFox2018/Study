# 05 Python 数据处理与数据准备

## 1. 工具角色

- NumPy：数组与数值计算；

## 2. DataFrame 思维

DataFrame 可以理解为带字段名和索引的二维数据表。

常见操作：

```python
df.head()
df.info()
df.describe()
df["col"]
df[["a", "b"]]
df.loc[...]
df.iloc[...]
df.query(...)
df.groupby(...)

```

不要只会“把代码跑通”，要知道每一步对行数、字段、粒度和语义做了什么。

## 4. 清洗

### 重复
先确定“重复”的业务定义。完全相同行不一定是重复，重复订单号通常更值得关注。

### 类型
常见问题：

- 数字被读成字符串；
- 日期未解析；
- 布尔值有多种表示；
- 类别拼写不一致；
- 单位混用。

### 缺失
先量化缺失模式，再决定删除或插补。

### 异常
先判断是否真实，再决定截断、变换、保留或分组分析。

## 5. 数据变换

常见操作：

- 新字段计算；
- 字符串处理；
- 时间拆分；
- 分桶；
- 标准化；
- 对数变换；
- 类别编码；
- 宽表/长表转换。

变换应写成可重复执行的代码，而不是手工修改表格。

## 6. 聚合与分组

```python
df.groupby("category")["value"].agg(["count", "mean", "median"])
```

分组时始终确认：

- 分组键；
- 每组样本数；
- 是否存在极小组；
- 加权与非加权平均是否不同。

## 7. 合并

合并前检查：

```text
左表粒度
右表粒度
连接键
键唯一性
预期行数变化
```

合并后检查：

- 行数是否符合预期；
- 未匹配比例；
- 是否出现重复扩张。

## 8. 数据准备与建模边界

用于建模时，还要处理：

- 类别编码；

所有从数据“学习”出来的处理参数（均值、标准差、编码映射等），原则上只应在训练数据上拟合。

```text
读取 → 类型 → 唯一键 → 缺失 → 重复 → 异常
```

## 11. 可运行小例子：从原始记录到可信汇总

前提：会运行 Python 并已安装 pandas。以下数据均在代码中，适合直接复制到新的 Notebook；每段输出对应一个质量检查点。

```python
import pandas as pd

raw = pd.DataFrame({
    "order_id": [1, 2, 2, 3, 4],
    "channel": ["A", "A", "A", "B", "B"],
    "amount": [10.0, 20.0, 20.0, None, 1000.0],
})
# 仅因本例明确规定 order_id 唯一，才按它去重。
orders = raw.drop_duplicates("order_id").copy()
assert len(raw) == 5 and len(orders) == 4
assert orders["order_id"].is_unique
print("金额缺失率：", orders["amount"].isna().mean())
summary = orders.groupby("channel")["amount"].agg(["size", "count", "mean"])
print(summary)
assert summary.loc["A", "mean"] == 15.0
assert summary.loc["B", "size"] == 2
assert summary.loc["B", "count"] == 1
```

缺失率为 `0.25`。A 的行数、非空数、均值分别为 `2、2、15`，B 为 `2、1、1000`。B 的 1000 只代表已知金额，报告时要一起展示缺失情况。

修改值时使用单次 `.loc[行条件, 列名] = 值`，不要用 `df[条件][列] = 值` 这种链式赋值；当前 pandas 的 Copy-on-Write 语义下，它不能可靠地修改原表。[^cow]

合并示例用 `orders.merge(channels, on="channel", validate="many_to_one", indicator=True)` 检查右表键唯一性和匹配情况。pandas 会让两侧的空连接键互相匹配，和 SQL 中通常的 `NULL` 比较语义不同；应先定义空键处理方式。[^merge]

**自查**：如果两条相同订单号的金额不同，还能直接保留第一条吗？\
**核对**：不能。它可能是订单版本更新或错误，应检查时间戳和业务规则；本例的简单去重不适用于该情况。

[^cow]: pandas [Copy-on-Write](https://pandas.pydata.org/docs/user_guide/copy_on_write.html)，核验 2026-10-02。
[^merge]: pandas [DataFrame.merge](https://pandas.pydata.org/docs/reference/api/pandas.DataFrame.merge.html)，核验 2026-10-02。

## 13. 两份目录的记录关联：候选、决定和来源分开

两份CSV中的不同ID可能描述同一个对象，相同标题也可能属于不同版本。记录关联先提出候选，再由明确的业务证据或审阅决定身份；它与按一个已经可靠的主键做merge不同，更不能只按相似度阈值删除“重复项”。

### 13.1 导入两源，保住原字段与稳定身份

给每条记录保存来源命名空间、源ID和完整原字段。例如下面是两份教学目录：

| 来源/ID | title | creator | year |
|---|---|---|---|
| left:map-1 | River Atlas | Ada | 2024 |
| left:map-2 | Garden Tools | Mira | 2020 |
| right:r-7 | Atlas River | Ada | 2025 |
| right:r-8 | River Atlas Junior | Ada | 2024 |

导入至少要求id/title存在且非空、同源ID唯一、表头唯一、行宽一致。creator和额外字段保留；CSV中的year在这里仍是字符串，不因看起来像年份便悄悄变类型。引号内逗号由CSV解析器处理，不能直接split(',')；BOM、空行、表头空格、编码和空值政策要显式约定。

source/source_id是系统保留字段，不能让输入列覆盖它们。工程中可用结构化的`(source,id)`作为身份：简单拼冒号、竖线而不转义，会在来源名或ID本身含分隔符时产生歧义。ID验证与标题规范化也应分开，不随意把业务ID的空格/大小写改掉。

### 13.2 用可解释的相似度找候选

保留原文本，另为匹配计算NFKC规范化、casefold后的token集合。NFKC可将全角字符等兼容形式归一，casefold处理大小写；这只是匹配特征，不替代原始值。连续字母数字类的正则也不等于中文分词、同义词理解或版本识别。

对集合A、B，Jaccard相似度为：

$$J(A,B)=\frac{|A\cap B|}{|A\cup B|}.$$

本例将两个空集合的分数约定为0，而不是把“两边都没有作者”当成作者完全一致的强证据。再用教学权重：

$$s=0.8J(标题)+0.2J(作者).$$

| 候选 | 标题J | 作者J | 加权分数 |
|---|---:|---:|---:|
| map-1 ↔ r-7 | 1 | 1 | 1 |
| map-1 ↔ r-8 | 2/3 | 1 | 11/15≈0.733333 |
| map-2 ↔ r-7 | 0 | 0 | 0 |
| map-2 ↔ r-8 | 0 | 0 | 0 |

以0.25为候选阈值，保留前两对。另一个小例River Atlas与Atlas的标题交并为1/2，作者同为Ada，则分数为`0.8×0.5+0.2×1=0.6`。权重和阈值决定召回/审阅负担，不是“同一对象概率60%”；缺作者时即使标题完全相同，按此公式也只有0.8。

标题词序被集合丢掉，所以River Atlas与Atlas River得1；年份又不在评分中，仍可能是不同版本。Junior与原版也不能因得分高就自动合并。报告保留分项分数、命中依据和候选范围，给审阅者解释风险。

直接遍历左右表会比较n×m对；在比较后过滤阈值并没有减少这项成本。大表可先按可信字段做blocking产生候选块，再算相似度，但需评估同实体跨块的漏报。展示可四舍五入，筛选和排序尽量保留明确精度，避免靠舍入后的同分值改变边界判断。

### 13.3 一对一决定和字段冲突是两步

本例使用受限的一对一政策：一条左记录最多接受一个右记录，反向也一样。拒绝某一对不消耗整条记录，它仍可与另一候选匹配；需要多对一或一对多时另定实体粒度，不能关掉唯一性检查凑结果。

接受map-1↔r-7，仅表示审阅者决定它们指向同一实体。原字段仍有两个冲突：title的顺序不同，year为2024/2025。若只选择year=2025，title冲突仍在；不能把“已接受关联”自动变成“字段已解决”。

一份示意审阅文件如下，它不是实际审批收据：

```json
{
  "fingerprint":"<本次两源记录指纹>",
  "pairs":[{
    "left":"left:map-1","right":"right:r-7","match":true,
    "values":{"title":"River Atlas","year":"2025"}
  }]
}
```

每对必须引用已知ID，match严格为布尔，同一对不得重复；选择字段必须属于该实体可合并字段，值类型符合合同。冲突未解决时可保一个展示候选值，但同时显示双方原值与未解决状态，不能悄悄以左值为真。空字符串、缺失和主动清空也要按字段政策区分。

原记录应作不可变快照或深复制。把输入dict直接放进返回sources，虽然输出看起来保存了来源，外部调用者仍可能改写原输入；一次相等断言不证明没有这种别名。审阅理由、拒绝决定和修订历史也应另保，不能只保存最后的合并字段。

### 13.4 交叉表、完整性与ready的含义

输出由实体表和crosswalk连接：每个源ID指向一个entity_id，实体保存完整sources、选定fields与conflicts。本例四条源记录在接受一对后得到三个实体，但crosswalk仍有四行，不能因实体合并而少掉一条源映射。

验收时检查：

1. 每个原source_id恰有一条映射，没有多重映射或漏项。
2. crosswalk引用的实体确实存在，实体ID唯一且不会因拼接歧义碰撞。
3. 每个合并决定满足一对一政策，未匹配项单独保留。
4. fields的选择能回到原记录与审阅决定；所有未解冲突仍在。
5. 候选已生成、候选已审阅、接受关联、字段已解决分别有数量与状态。

示例的ready只计算“已接受实体是否还存在冲突”。完全没有接受任何合并时，四个原实体都无合并冲突，因此ready也可为true，两个候选却一个都没审。这是其合同的局部就绪状态，不能写成“目录全部核验完成”。应另报候选数、已审/待审数及必要覆盖规则。

源记录指纹可防止把另一组输入的审阅直接套过来。先声明它绑定的是解析后记录还是原始CSV字节；前者不一定区分原文件的换行和列顺序。规范化规则、候选权重、阈值、schema及审阅修订也可有独立版本，不能以一个只含原记录的hash代表所有政策相同。摘要不认证审阅者身份，也不证明决定正确。

网页下载时能解析JSON，只说明语法合格；重新导入仍要校验上述业务合同。继续编辑时保留已有decisions，别每次又从空pairs开始覆盖历史。多产物应作为同一版本发布，避免新crosswalk配旧实体文件；没有实际运行的导出和网络查询不写成已经发生。
