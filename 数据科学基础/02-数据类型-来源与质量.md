# 02 数据类型、来源与质量

## 1. 结构化、半结构化与非结构化

### 结构化数据
拥有稳定模式，例如二维表、关系数据库记录、传感器时序表。

优点：约束明确、查询容易、质量规则容易自动化。

### 半结构化数据
具有部分结构，但字段不完全固定，例如 JSON、日志、HTML、事件流。

优点：灵活；代价是解析和模式治理更复杂。

### 非结构化数据
文本、图像、视频、音频、文档等。

通常需要先提取特征、元数据或表示，才能进入传统分析流程。

## 2. 常见数据来源

- 事务系统：订单、支付、库存、CRM；
- 传感器/IoT：温度、位置、设备状态；
- 调查与实验；
- Web/App 行为日志；
- 文本、图像、视频；
- API 与开放数据；
- 社交网络与图数据；
- 科研观测与仪器数据。

关键不是来源数量，而是理解**数据生成过程**。

## 3. 数据生成过程

分析前要知道：

- 谁产生了这条数据；
- 在什么条件下产生；
- 什么数据没有被记录；
- 记录机制是否随时间改变；
- 是否存在选择偏差；
- 指标是否受业务流程影响。

例如“投诉率下降”可能代表服务改善，也可能代表投诉入口变难。数据本身不能告诉你是哪一种。

## 4. 数据类型与测量尺度

常见变量：

- 类别型：无序类别；
- 有序型：有顺序但间距不一定相等；
- 离散数值；
- 连续数值；
- 时间/日期；
- 地理空间；
- 文本；
- 图结构。

测量尺度决定哪些统计运算有意义。不要对无序类别直接计算“平均值”。

## 5. 数据质量维度

至少检查：

- **完整性**：缺失率；
- **唯一性**：重复记录；
- **有效性**：是否满足类型/范围/格式；
- **一致性**：跨字段、跨表、跨系统是否矛盾；
- **准确性**：是否接近真实值；
- **及时性**：是否足够新；
- **代表性**：是否覆盖目标总体。

## 6. 缺失数据

缺失并不只有一种原因：

- **MCAR（完全随机缺失）**：是否缺失与已观测、未观测的数据值都独立；例如独立于测量值的随机文件损坏。
- **MAR（条件随机缺失）**：给定已观测变量后，缺失机制不再依赖缺失值本身。例如记录了年龄后，问卷收入缺失仅与年龄有关。
- **MNAR（非随机缺失）**：给定已观测变量后，缺失机制仍与缺失值有关，例如高收入者更不愿填写收入。

MAR 是关于条件分布的假设，不是“能用现有字段预测缺失”就能证明；通常不能只凭已观测数据区分 MAR 与 MNAR。删除或均值填充也不是无条件无偏的做法，须说明假设和敏感性。

处理方式：

- 删除；
- 常数/均值/中位数/众数填充；
- 分组填充；
- 模型插补；
- 增加“是否缺失”指示变量。

不要在不知道缺失机制时机械填充。

## 7. 异常值

异常值可能是：

- 输入错误；
- 单位错误；
- 系统故障；
- 极端但真实的事件；
- 欺诈或风险信号。

因此“删除异常值”必须有业务或统计依据。真实极端事件有时恰恰是最重要的信息。

## 8. 数据漂移

数据会变化：

- 人群结构变化；
- 产品规则变化；
- 采集逻辑变化；
- 外部环境变化；
- 标签定义变化。

长期系统需要监测分布、缺失率、类别比例和关键统计量的变化。

## 9. 数据字典

至少维护：

| 字段 | 含义 | 类型 | 单位 | 合法范围 | 缺失含义 | 来源 |
|---|---|---|---|---|---|---|

数据字典能显著减少“同名不同义”和“同义不同名”。

## 10. 用五条记录检查质量

下面是**教学用的虚构记录**，金额单位为元：

| 订单号 | 渠道 | 金额 | 准时 |
|---|---|---:|---|
| 1 | A | 10 | 是 |
| 2 | A | 20 | 是 |
| 2 | A | 20 | 是 |
| 3 | B | 缺失 | 否 |
| 4 | B | 1000 | 是 |

若业务确认订单号唯一，第 2、3 行才可判为重复。去重后 4 行，金额缺失率是 1/4。1000 元只是待核实的极端值，不能因为大就删除。准时字段应映射成明确的布尔值，缺失不能自动映射成“否”。

**先写数据字典，再清洗**：`订单号` 为唯一标识；`金额` 是实付金额还是标价必须明确；`准时` 需要送达时刻和承诺时刻的定义。

**自查**：把缺失金额填成 0 后，已知金额的平均值发生什么变化？\
**核对**：忽略缺失时为 `(10+20+1000)/3≈343.33`，填 0 后为 `1030/4=257.5`。后者引入了“未知等于零”的假设，不能当成观测事实。


## 11. 显式数据合同、隔离记录与批次门禁

### 11.1 合同先于清洗：哪些事能够作出确定判断

数据合同把“这个数据集现在允许什么”写成有版本的规则。最小教学格式可以规定字段类型、是否必需、数值上下界、允许枚举、逐列唯一性、原始批次行数和额外字段政策。先验证合同本身，再判断数据；合同有错时不能返回一个看似有效的PASS报告。

这份来源的 `version=1` 是自定义教学格式，不能直接当作 JSON Schema 或 Open Data Contract Standard。它不检查事实真伪、语义准确性、跨表外键、时间有效性或模型训练泄漏。能通过类型和范围，只证明指定检查通过；例如 `tokens=31` 在范围内不证明它等于真实分词器输出。

一个完整合同示例：

```json
{
  "version": 1,
  "fields": {
    "id": {"type": "string", "required": true},
    "tokens": {"type": "integer", "required": true, "min": 0, "max": 8192},
    "split": {"type": "string", "required": true, "enum": ["train", "test"]}
  },
  "unique": ["id"],
  "min_rows": 1,
  "allow_extra": false
}
```

验证合同至少做到：version是整数1而不是布尔true；fields是非空对象；字段类型只能是string/integer/number/boolean；required和allow_extra必须是布尔；min/max仅用于数值字段，界限必须是有限数值且min≤max；enum是非空且每项都符合字段类型的列表；unique只能列已声明的、不重复的字段名；min_rows/max_rows是非负整数且顺序合理。遇到 `minimum`、`regex` 等未知规则应拒绝，不能忽略拼写错误后假装约束已生效。

源实现只检查字段名非空，空格字段名并未统一拒绝；也未验证所有规则之间的可满足性。例如integer字段限定min=0、max=1、enum=[2]，各项局部合法，却没有任何允许值；若业务需要，应增加交叉规则一致性检查。enum重复项也不自动归一化。

### 11.2 逐行验证保持原值，类型错误先处理

不要在质量验证里悄悄把字符串 `"31"` 转成整数31，也不要把缺失补0。这会掩盖上游变化并改变记录。需要修复时，单独建立有理由、可追溯的转换步骤，再对转换后的新数据版本重新检查。

来源的类型规则有明确含义：string接受字符串；integer仅接受Python精确int类型，31.0不算integer；number接受Python int和有限float；boolean仅接受bool。虽然Python的bool与int有继承关系，这里true既不是integer也不是number。number允许大整数，原测试专门覆盖 `10**400`；不能将网页图的JS安全整数限制当成Python实现限制。小数浮点仍受二进制表示约束，需要十进制精度或单位规则时另定合同。

缺失与null必须分开：字段不存在且required=true产生required问题；不存在但可选则通过；字段存在且值为null，对本格式的四种标量类型都产生type问题。“可选”不等于“允许null”，更不等于“缺失可补默认值”。

每行按声明字段顺序检查；遇到错误类型先报type并跳过该字段的范围、枚举运算，防止数组、null或字符串引发无意义比较异常。类型正确后再查min/max和enum，边界值包含在合法范围内。未声明字段默认报extra；extra名称排序以稳定输出。整行不是对象则报 `{field:"",rule:"object"}`。一行可以有多个问题，应保留而不是只报第一个。

重要实现边界：文档说“平面对象”，实际在 `allow_extra=true` 时，额外字段完全不检查其内部值，因此嵌套对象或数组可随额外字段通过。默认allow_extra=false时它们因extra被隔离；声明字段则受标量类型限制。需要真正保证整个记录平面、额外字段也无秘密或复杂值，应增加明确规则，不能把文档口号当成已实现的验证。

### 11.3 唯一性必须检查全部成员，而不是留下第一条

对每个unique字段，建立“类型正确的值→一开始为1的输入行号列表”。缺少该字段或类型错误的值不参与哈希索引，由逐行验证解释；列表长度≥2才形成重复组。最终把组内所有行都标记unique，包括第一条。

例如ID序列 `a,b,a,a` 产生 `{field:"id",rows:[1,3,4]}`。如果只丢后来出现的行，数据是否被接受就取决于输入顺序，还可能把错误内容留为“权威第一条”。全组隔离使问题显式暴露，后续由有业务依据的去重流程决定保留哪一条。

这里是**每列分别唯一**，不是复合唯一。`unique:["user","day"]` 表示user不能重复、day也不能重复；它不表示 `(user,day)` 组合不能重复。用户A在两天分别一条记录，在这种声明下仍会因user重复失败。组合键需要另一个明确的规则和分组逻辑。

同一number列的1与1.0按Python数值键相等而冲突，0与-0.0也同组；string列的 `a` 与 `A` 不同，空格和Unicode形式也不自动标准化。两个缺失的可选唯一字段不冲突；两个null先因类型错误退出分组，不能把它们解释成有效唯一键。

重复索引只过滤“缺失或类型不符”，不会排除因其他规则失败的行。例如ID合法但tokens<0的行，仍会与同ID的正常行构成重复组；正常行也须被标unique，不能因另一行已坏就假装冲突不存在。

逐列索引的时间通常随行数和唯一字段数增长，内存随批次和组成员增长；该API最多接受10万行列表。这不等于读取时的字节、嵌套深度或单行长度上限，也不是跨批次、跨分区的全局唯一保证。流式或数据库实现需要明确跨批状态、窗口、存储一致性和冲突重试。

### 11.4 隔离分区与整批门禁是两个结果

四行完整输入（JSONL每行一条JSON对象）：

```jsonl
{"id":"sample-a","tokens":31,"split":"train"}
{"id":"sample-b","tokens":-2,"split":"test"}
{"id":"sample-c","tokens":42,"split":"test"}
{"id":"sample-c","tokens":53,"split":"train"}
```

第1行合法；第2行的tokens产生min问题；第3、4行同ID，各有unique问题。因此accepted保留第1条，quarantine有第2、3、4条；counts为input=4、accepted=1、quarantined=3，duplicates记id对应[3,4]，passed=false。隔离项保存原输入行号、原record和issues，能回到原文件逐条排查。

先计算每行问题，再把重复问题加入相关行；对原批次总行数检查min_rows/max_rows。只有隔离数为0且没有批次级问题才passed。即使每行都干净，2行输入遇到max_rows=1也失败，但accepted仍含2条；“有accepted.jsonl”不是“允许导入”。空数据集在没有最小行数要求时可以通过；是否允许空批次是政策选择，不能推断为空总是失败。

报告字段为 `schema_version/passed/counts/dataset_issues/duplicates/accepted/quarantine`。最少保持 `input=accepted+quarantined`，每个重复组成员都出现在隔离问题中，行号范围有效。CLI导出accepted.jsonl、quarantine.jsonl、receipt.json和review.html；receipt不含原记录分区，只保留门禁、计数、重复行号等汇总。

可以把accepted分区当作**新数据集**再执行一次合同，可能得到PASS；这不能追溯地把原始批次改成PASS，更不构成自动丢弃隔离记录的批准。若要继续使用部分数据，应记录新版本、原批关联、排除依据及必要批准，评估选择偏差，不能只为通过门禁删掉困难样本。

### 11.5 消费者必须区分质量失败、处理失败和未知

源CLI默认只生成证据，即使passed=false也可返回0；只有加 `--check` 才在质量规则失败时返回1。非法合同、JSON解析和所捕获的I/O或类型错误返回2。这些退出码与另一个工具的约定无关，集成时必须按当前接口解释。

正确消费者同时检查：本次命令是否完成、是不是当前批次完整产物、schema版本是否支持、passed是否true、计数和分区是否一致，以及当前作业是否启用了门禁参数。出现错误、报告缺失、旧产物残留或无法核验，不得把它们归入PASS；应作为处理失败或unknown阻断。不要仅凭exit=0导入，也不要只解析HTML上的绿色字样。

参考实现没有override通道、审批人身份或签名；需要例外时应另设受控流程，绑定具体批次、合同版本、失败规则、允许用途、责任人与期限。例外许可不能改写原报告的失败事实，也不能由模型自由文本一句“可以忽略”替代。

四个文件逐个写入，不构成原子事务：命令中途失败可能留下前面文件，旧输出目录也可能残存上一批receipt。需要可靠消费时使用独立run目录、完整清单与最后发布的完成标记，或适当事务机制，并由消费者核同一批次身份。来源没有实现这些增强。原记录中有NaN时，即使逐行规则已把它隔离，CLI随后使用 `allow_nan=false` 序列化quarantine仍会报错，这会把质量失败转成不完整导出/错误退出；输入边界应明确拒绝非标准数值或约定安全的错误记录表示。

[Python 3.12 JSON官方文档](https://docs.python.org/3.12/library/json.html#standard-compliance-and-interoperability)说明默认解析允许NaN/Infinity和重复对象成员（重复时取最后值）；本来源CLI没有自定义parse_constant或object_pairs_hook。不要把默认json.loads当成严格JSON或防歧义边界。本次仅核官方对应条目，未执行来源解析器。

源CLI先 `read_text().splitlines()` 并解析全部行，之后evaluate才检查10万行限制；大文件在此之前已分配内存。应另在读入口约束总字节、行数、行长和嵌套资源。空白行会被json.loads拒绝，尾随一个正常换行不额外产生记录；“输入行号”只有在整个JSONL解析与分行规则一致时才可用于回溯，不能先静默跳过坏行再沿用旧行号。

### 11.6 数据真实性、时间与泄漏需要另一层合同

这份报告没有输入文件摘要、合同摘要、数据版本、采集时间、对象身份、抽样覆盖或数字签名。字段和行号能解释当前传入列表的规则结论，不能证明这就是某个生产数据集、也不能证明所有来源记录都已采集。accepted和quarantine保留对象内容，并没有自动脱敏；隔离往往集中保存异常原文和敏感信息，不能因名称叫“隔离”就直接公开或交给模型。

重复组汇总只列字段名和行号，减少原值复制，但不意味着完全匿名。HTML对issues和duplicates做文本转义，有助于避免字段名被作为HTML解释；它没有对任意外部报告做完整schema验证，生成器假定自己构造的行号、计数与passed可信。数据内的文字也不能被当成Agent指令。

对长期训练或分析项目，沿用本仓库数据字典与准备流程，补充这些独立规则：

- **时间**：单位/时区、事件时间与采集时间、允许延迟、更新截止、窗口完整性和迟到数据政策。string类型的日期字段不会自动获得这些检查。
- **跨字段与跨表**：例如开始时间≤结束时间、币种与金额单位相符、外键对应有效对象；当前格式未实现。
- **训练泄漏**：同一实体、近重复文本、时间相邻窗口、标签派生信息是否跨训练与测试边界。示例把同ID分到train/test可被unique=id抓住，但“ID不同”不证明没有泄漏，逐列唯一也不能代替按实体/时间切分。
- **真实完整性**：与源系统的预期数量、分区清单、采集失败和权限范围对账。只在收到的列表中数行，无法发现整个缺失分区。

这些检查缺失时应记录未覆盖或unknown，不把没有报错当作正确。来源1本项目没有实现上述扩展；在本仓库中作为与既有学习内容的衔接，而不是其已完成能力。

### 11.7 练习、图示范围和可核对答案

1. 可选integer字段n缺失、n=null、n="31"、n=true分别怎样？答案：缺失通过；其余三个都是type，不自动填充或转换。
2. unique=["user","day"]是否允许user=A的两天两条？答案：不允许，user已重复；这不是复合键。
3. 第1行ID=x且数值越界，第2行同ID且其他字段都合法，第二行是否接受？答案：不接受，两条都参与类型正确的ID分组，各有unique问题。
4. 2条干净记录但max_rows=1，quarantine=0能否导入？答案：不能，批次级max_rows失败，必须核receipt的passed。
5. 把坏行剔除后重验通过，原始批次是否通过？答案：仍失败；新分区是新的输入版本，须保留排除决策和原批关联。
6. 最后一次命令返回2但目录里有旧receipt写着passed=true怎么办？答案：本次失败，旧产物不能充当本次凭证，等待有效完整产物或人工核验。
