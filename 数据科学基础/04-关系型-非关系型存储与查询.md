# 04 关系型、非关系型存储与查询

## 1. 先从访问模式出发

选存储方案前先问：

- 数据结构是否稳定；
- 是否需要事务；
- 是否需要复杂关联；
- 查询模式是否可预测；
- 数据规模与写入速度；
- 一致性要求；
- 是否需要图遍历、全文检索或大规模分析。

“SQL vs NoSQL”不是谁先进，而是谁更符合访问模式。

## 2. 关系型数据库

核心对象：

- 表；
- 行；
- 列；
- 主键；
- 外键；
- 约束；
- 索引；
- 事务。

关系模型的优势是结构明确、完整性约束强、SQL 查询表达能力高。

## 3. SQL 基础

### 选择与过滤

```sql
SELECT col1, col2
FROM table_name
WHERE condition;
```

### 排序与限制

```sql
ORDER BY metric DESC
LIMIT 20;
```

### 聚合

```sql
SELECT category, COUNT(*), AVG(value)
FROM table_name
GROUP BY category;
```

### 连接

常见连接：

- INNER JOIN：只保留匹配；
- LEFT JOIN：保留左表全部；
- RIGHT JOIN；
- FULL OUTER JOIN。

连接前要明确键是否唯一，否则容易出现行数“爆炸”。

## 4. 数据规范化

规范化用于减少重复和更新异常，但分析系统也可能为了查询效率进行反规范化。

原则：

- 事务系统偏向一致性和规范化；
- 分析系统偏向读取效率与清晰的数据模型。

## 5. 非关系型数据库

### Key-Value
适合高速简单访问，如缓存、会话。

### Document
以 JSON 类文档存储，适合结构灵活的数据。

### Wide-Column
适合大规模稀疏数据和高吞吐写入。

### Graph
节点与边为一等对象，适合关系网络、推荐、路径分析。

不同 NoSQL 类型解决不同问题，不应把 NoSQL 当作单一技术。

## 6. Schema-on-Write 与 Schema-on-Read

- **Schema-on-Write**：写入前先约束结构；
- **Schema-on-Read**：读取分析时再解释结构。

前者更利于质量控制，后者更灵活但治理成本更高。

## 7. 数据湖与列式格式

数据湖用于存放大量原始或半处理数据。常见分析型列式格式如 Parquet，优势包括：

- 列裁剪；
- 压缩；
- 批量分析效率；
- 类型和模式信息。

数据湖如果没有目录、血缘、权限和质量管理，很容易退化为“数据沼泽”。

## 8. 查询正确性检查

SQL/查询结果异常时优先检查：

- Join key 是否唯一；
- WHERE 是否在 JOIN 前后改变语义；
- NULL 如何处理；
- 时间边界是否正确；
- 时区；
- 去重逻辑；
- 聚合前是否重复；
- 指标分母是否一致。

数据科学项目中，大量错误来自查询语义而不是模型。
