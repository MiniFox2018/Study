# 13｜机器学习系统与工程原则

## 1. 模型只是系统的一小部分

成熟机器学习系统通常包含：

```text
数据采集
→ 数据校验
→ 特征/样本生成
→ 训练
→ 评估
→ 模型发布
→ 在线服务
→ 监控
→ 反馈数据
→ 再训练
```

真正的长期成本往往不来自模型公式，而来自系统依赖、数据变化和维护复杂度。

## 2. Hidden Technical Debt

机器学习系统同时具有：

- 普通软件技术债；
- 数据依赖债；
- 模型耦合债；
- 反馈环；
- 实验配置债；
- 外部环境变化。

因此“模型今天效果好”不代表系统长期可维护。

## 3. CACE

`Changing Anything Changes Everything`。

改变：

- 一个特征；
- 采样方式；
- loss；
- 超参数；
- 数据分布；
- 上游模型输出；

都可能改变整个模型行为。

工程结论：

> ML 组件之间不能假设像普通纯函数一样独立。

## 4. Correction Cascade

已有模型 A 不完全满足任务，于是在输出后加模型 B 修正；随后再加 C。

短期快，长期形成：

```text
A → B → C → D
```

每一层都依赖上一层的错误分布，最终任何单点升级都可能破坏全链路。

优先考虑：

- 重新定义统一任务；
- 直接加入必要 feature；
- 明确独立模型边界。

## 5. Undeclared Consumers

模型输出可能被其他系统悄悄依赖。

如果没有：

- consumer registry；
- API contract；
- versioning；
- ownership；

模型升级可能破坏未知下游。

因此 prediction interface 也需要治理。

## 6. Unstable Data Dependency

上游 feature 可能来自：

- 另一模型；
- 动态词典；
- 实时规则；
- 外部服务。

上游“改进”可能造成下游突然退化。

重要信号应：

- version；
- freeze；
- validate；
- staged rollout。

## 7. Underutilized Features

有些 feature：

- 曾经有效，后来冗余；
- 与其他 feature 高相关；
- 仅带极小增益；
- 增加维护依赖。

长期应做：

- ablation；
- leave-one-feature-out；
- feature ownership audit。

## 8. Feedback Loop

推荐、广告、搜索等系统会影响未来训练数据：

```text
模型
→ 展示什么
→ 用户看到什么
→ 用户行为
→ 新训练数据
→ 模型
```

这意味着训练数据不再来自独立世界，而受到当前策略影响。

应保留：

- random traffic；
- exploration bucket；
- unbiased holdout；
- counterfactual analysis。

## 9. Glue Code

一个模型包如果需要大量转换、适配和补丁才能接入生产，就会形成高额 glue-code debt。

缓解：

- 稳定接口；
- 统一数据 schema；
- 清晰 adapter；
- 可替换 backend；
- contract tests。

## 10. Pipeline Jungle

数据准备若长期以：

```text
临时脚本
+ 中间 CSV
+ 手工 join
+ 隐式路径
```

不断堆叠，会变成无法测试和恢复的 pipeline jungle。

应建立：

- DAG；
- input/output schema；
- lineage；
- idempotency；
- retries；
- data validation。

## 11. Dead Experiment Paths

实验开关长期残留生产代码，会造成组合爆炸。

实验结束后应明确：

```text
Win → 主路径
Lose → 删除
Need more data → 延期并设清理时间
```

不要无限保留历史 branch / flag。

## 12. Baseline First

新项目首先建立“足够简单且可信”的 baseline。

原因：

- 判断复杂模型是否真正有收益；
- 验证 pipeline；
- 发现数据问题；
- 测量增量成本。

对于表格任务，LR/GBDT 可能比直接上深网更适合作为 baseline。

## 13. Data Before Model

模型效果不足时，应先区分：

- 数据量不足；
- label 错误；
- distribution shift；
- feature 不足；
- metric 不匹配；
- optimization bug；
- model capacity 不足。

不要默认“换更大模型”。

## 14. Debugging

机器学习系统最难调试的地方是：

> 有 Bug 时，模型仍可能通过其他参数补偿，输出看起来“勉强正常”。

推荐调试方法：

1. 极小数据集 overfit；
2. 手算一个 batch；
3. 检查 input/label 对齐；
4. 检查 loss；
5. 检查 gradient；
6. 检查参数是否真的更新；
7. 检查 train/eval mode；
8. 做 deterministic run；
9. 做 ablation；
10. 比较简单 baseline。

## 15. Monitoring

生产至少监控四层：

### System

- QPS；
- latency；
- error；
- resource。

### Data

- missing；
- range；
- category drift；
- schema。

### Model

- score distribution；
- calibration；
- offline/online metric；
- slice。

### Business

- 用户最终结果；
- 长期指标；
- 风险指标。

## 16. Ownership

每个关键资产应有 owner：

- dataset；
- feature；
- model；
- API；
- metric；
- dashboard。

“大家都负责”通常意味着没人负责。

## 17. 变更策略

任何模型变更都应：

```text
offline validation
→ shadow / canary
→ A/B
→ monitor
→ rollback capability
```

大模型系统同样适用。

来源：华校专《系统架构》《工程实践指导原则》；核心系统原则源于长期有效的 ML Systems 研究。
