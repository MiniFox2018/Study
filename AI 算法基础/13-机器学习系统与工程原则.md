# 13｜机器学习系统与工程原则

> 先完成至少一次小模型训练再读本章。重点是能说明数据、模型、服务之间如何追溯与回滚，暂不要求搭建生产级平台。

## 1. 模型只是系统的一小部分

成熟机器学习系统通常包含：

```text
数据采集
→ 数据校验
→ 特征/样本生成
→ 训练
→ 评估
→ 模型发布
→ 在线服务
→ 监控
→ 反馈数据
→ 再训练
```

真正的长期成本往往不来自模型公式，而来自系统依赖、数据变化和维护复杂度。

## 2. Hidden Technical Debt

机器学习系统同时具有：

- 普通软件技术债；
- 数据依赖债；
- 模型耦合债；
- 反馈环；
- 实验配置债；
- 外部环境变化。

因此“模型今天效果好”不代表系统长期可维护。

## 3. CACE

`Changing Anything Changes Everything`。

改变：

- 一个特征；
- 采样方式；
- loss；
- 超参数；
- 数据分布；
- 上游模型输出；

都可能改变整个模型行为。

工程结论：

> ML 组件之间不能假设像普通纯函数一样独立。

## 4. Correction Cascade

已有模型 A 不完全满足任务，于是在输出后加模型 B 修正；随后再加 C。

短期快，长期形成：

```text
A → B → C → D
```

每一层都依赖上一层的错误分布，最终任何单点升级都可能破坏全链路。

优先考虑：

- 重新定义统一任务；
- 直接加入必要 feature；
- 明确独立模型边界。

## 5. Undeclared Consumers

模型输出可能被其他系统悄悄依赖。

如果没有：

- consumer registry；
- API contract；
- versioning；
- ownership；

模型升级可能破坏未知下游。

因此 prediction interface 也需要治理。

## 6. Unstable Data Dependency

上游 feature 可能来自：

- 另一模型；
- 动态词典；
- 实时规则；
- 外部服务。

上游“改进”可能造成下游突然退化。

重要信号应：

- version；
- freeze；
- validate；
- staged rollout。

## 7. Underutilized Features

有些 feature：

- 曾经有效，后来冗余；
- 与其他 feature 高相关；
- 仅带极小增益；
- 增加维护依赖。

长期应做：

- ablation；
- leave-one-feature-out；
- feature ownership audit。

## 8. Feedback Loop

推荐、广告、搜索等系统会影响未来训练数据：

```text
模型
→ 展示什么
→ 用户看到什么
→ 用户行为
→ 新训练数据
→ 模型
```

这意味着训练数据不再来自独立世界，而受到当前策略影响。

应保留：

- random traffic；
- exploration bucket；
- unbiased holdout；
- counterfactual analysis。

## 9. Glue Code

一个模型包如果需要大量转换、适配和补丁才能接入生产，就会形成高额 glue-code debt。

缓解：

- 稳定接口；
- 统一数据 schema；
- 清晰 adapter；
- 可替换 backend；
- contract tests。

## 10. Pipeline Jungle

数据准备若长期以：

```text
临时脚本
+ 中间 CSV
+ 手工 join
+ 隐式路径
```

不断堆叠，会变成无法测试和恢复的 pipeline jungle。

应建立：

- DAG；
- input/output schema；
- lineage；
- idempotency；
- retries；
- data validation。

## 11. Dead Experiment Paths

实验开关长期残留生产代码，会造成组合爆炸。

实验结束后应明确：

```text
Win → 主路径
Lose → 删除
Need more data → 延期并设清理时间
```

不要无限保留历史 branch / flag。

## 12. Baseline First

新项目首先建立“足够简单且可信”的 baseline。

原因：

- 判断复杂模型是否真正有收益；
- 验证 pipeline；
- 发现数据问题；
- 测量增量成本。

对于表格任务，LR/GBDT 可能比直接上深网更适合作为 baseline。

## 13. Data Before Model

模型效果不足时，应先区分：

- 数据量不足；
- label 错误；
- distribution shift；
- feature 不足；
- metric 不匹配；
- optimization bug；
- model capacity 不足。

不要默认“换更大模型”。

## 14. Debugging

机器学习系统最难调试的地方是：

> 有 Bug 时，模型仍可能通过其他参数补偿，输出看起来“勉强正常”。

推荐调试方法：

1. 极小数据集 overfit；
2. 手算一个 batch；
3. 检查 input/label 对齐；
4. 检查 loss；
5. 检查 gradient；
6. 检查参数是否真的更新；
7. 检查 train/eval mode；
8. 做 deterministic run；
9. 做 ablation；
10. 比较简单 baseline。

## 15. Monitoring

生产至少监控四层：

### System

- QPS；
- latency；
- error；
- resource。

### Data

- missing；
- range；
- category drift；
- schema。

### Model

- score distribution；
- calibration；
- offline/online metric；
- slice。

### Business

- 用户最终结果；
- 长期指标；
- 风险指标。

## 16. Ownership

每个关键资产应有 owner：

- dataset；
- feature；
- model；
- API；
- metric；
- dashboard。

“大家都负责”通常意味着没人负责。

## 17. 变更策略

根据风险选择适用的发布步骤，常见链路为：

```text
offline validation
→ shadow / canary
→ A/B
→ monitor
→ rollback capability
```

大模型系统同样适用。

来源：华校专《系统架构》《工程实践指导原则》；核心系统原则源于长期有效的 ML Systems 研究。

## 18. Compendium 补充：System Design 从需求开始

在选择数据库、消息队列、云服务或模型框架之前，先明确：

- functional requirements；
- traffic / data scale；
- latency / availability SLO；
- consistency requirement；
- cost constraint；
- failure mode；
- data retention / privacy boundary。

系统设计不是“列技术栈”，而是让每个组件都能对应一个明确约束。

## 19. 分布式系统的现实：Partial Failure

分布式系统中，一个组件可能失败而其他组件仍正常。

因此必须显式设计：

- timeout；
- retry；
- exponential backoff；
- idempotency；
- replication；
- health check；
- failover。

“重试”如果没有幂等语义，可能把一次失败变成重复写入或重复扣费。

## 20. Consistency 与 Availability

数据副本之间不一定始终同步。

实际设计要明确：

- 哪些读必须看到最新写入；
- 哪些场景允许 eventual consistency；
- 哪些操作必须具备事务/原子边界；
- 网络分区时系统如何降级。

不要把一致性当成数据库的默认“开关”。

## 21. Feature Store 的长期价值

Feature Store 解决的核心不是“集中放特征”，而是：

- feature definition reuse；
- point-in-time correctness；
- online/offline consistency；
- low-latency serving；
- lineage 与 ownership。

尤其要防止 **training-serving skew**：训练时计算的特征与线上实际使用的特征定义不一致。

## 22. Registry 与 Lineage

生产 ML 需要能回答：

> 这个线上模型到底由哪份代码、哪批数据、哪个配置和哪些依赖训练出来？

因此应记录：

- dataset version；
- code commit；
- feature version；
- hyperparameter/config；
- artifact；
- model registry entry；
- deployment version。

可追溯性不是文档工作，而是故障恢复和模型治理的基础。

## 23. Online Experiment

A/B testing 不只是“随机分两组”。

必须明确：

- unit of randomization；
- exposure definition；
- primary metric；
- guardrail metric；
- sample ratio / contamination；
- interference；
- novelty effect。

推荐/社交系统尤其要警惕一个用户的 treatment 影响另一个用户，使样本不再独立。

## 24. 推荐、搜索、广告与风控的共性结构

很多在线 ML 系统可以抽象为：

```text
Candidate Generation
→ Ranking / Scoring
→ Constraints / Policy
→ Serving
→ Feedback
```

不同业务主要差在：

- candidate space；
- label delay；
- exploration；
- bias；
- latency；
- risk constraint。

这比记某个具体系统架构更具有长期迁移价值。

## 25. 与 LLM 推理系统的连接

大模型服务也遵循同一套原则，只是瓶颈进一步集中在模型状态与 GPU 资源：

- KV cache；
- batching；
- model sharding；
- queueing；
- autoscaling；
- cost / latency tradeoff。

## 用一条迟到标签检查系统

任务是预测用户当天是否退订。训练表里出现“下周客服确认的退订原因”，但线上预测当天无法取得它。这是未来信息泄漏；离线分数再高，也不代表可上线。

把一条样本按时间列清：预测发生时间、特征发生时间、特征入库时间、标签产生时间。训练特征只能使用在当时已经可获得的信息；事件发生早不代表入库也早。

自查：一项特征的名称没变，上游把“过去 7 天计数”改成“过去 30 天计数”，是否只是内部实现？**答案：**不是，它改变模型输入分布，需版本化、重评估，并核对训练和在线是否一致。

最小交付可以只是一个目录：数据说明、固定切分、训练配置、模型文件、指标和错误样例、恢复命令。能从这些材料重建结果后，再增加平台组件。

## 26. AI By Doing 增量：AutoML、部署、增量训练与在线学习

> 对应来源第 39～45、77～83 章。原站中的具体旧版云平台 UI、历史 API 和服务命令不固化，只保留今天仍有效的系统方法。

### 26.1 AutoML 的问题定义

AutoML 可以把模型开发的一部分表示为搜索问题：

$$
\lambda^*
=
\arg\min_{\lambda\in\Lambda}
\mathcal L_{val}(Pipeline_\lambda)
$$

其中 $\lambda$ 可以同时描述：

- preprocessing；
- model family；
- hyperparameters；
- feature generation；
- ensemble strategy。

真正的约束还包括：

- 时间预算；
- CPU/GPU；
- 内存；
- 推理延迟；
- 模型大小。

因此 AutoML 不是“自动找到绝对最好模型”，而是在指定搜索空间、数据切分、指标和资源预算下寻找候选方案。

### 26.2 AutoML 最危险的错误仍是数据问题

AutoML 无法自动弥补：

- 标签定义错误；
- train/test 泄漏；
- 时间穿越；
- 重复样本跨集合；
- 指标与业务目标不一致；
- 采样偏差。

如果验证过程错了，自动化只会更高效地优化一个错误目标。

### 26.3 模型 artifact 不只是一个权重文件

可部署模型至少要能追溯：

- preprocessing definition；
- feature schema；
- model weights；
- code version；
- dependency version；
- training data snapshot/version；
- metric；
- model signature。

否则同一个“model.pkl”或权重文件几个月后可能无法解释也无法复现。

### 26.4 序列化的安全边界

通用对象序列化格式可能在加载时执行代码，因此：

> 不要加载来源不可信的模型文件。

生产环境应考虑：

- 可信 artifact registry；
- checksum/signature；
- 权限；
- 安全扫描；
- 可移植格式或受控运行时。

### 26.5 四类常见推理形态

#### Batch inference

一次处理大量数据，适合离线评分。

#### Synchronous online inference

请求到达后立即返回，重点是低延迟和高可用。

#### Asynchronous inference

请求先排队，完成后再取结果，适合耗时任务。

#### Edge inference

模型运行在终端设备，重点是模型大小、功耗、硬件兼容与离线能力。

模型本身相同，系统约束可能完全不同。

### 26.6 训练—推理一致性

线上输入必须与训练保持：

- 同一字段含义；
- 同一单位；
- 同一缺失值处理；
- 同一类别映射；
- 同一 tokenizer / resize / normalization；
- 同一 feature version。

这就是 training-serving skew 的核心。

### 26.7 增量学习不等于“不断 fit”

数据持续进入时有三种策略：

1. 固定周期全量重训；
2. 小批量增量更新；
3. 逐样本在线更新。

选择取决于：

- 数据到达速度；
- 标签延迟；
- 分布变化速度；
- 算法是否支持增量；
- 更新风险；
- 训练成本。

### 26.8 Concept Drift

如果：

$$
P_t(X,Y)\neq P_{t+1}(X,Y)
$$

模型面对的数据机制发生变化。

可拆成：

- covariate shift；
- prior/label shift；
- conditional/concept drift。

监控不能只看输入均值，还要关注切片、输出、延迟标签和最终任务指标。

### 26.9 Prequential Evaluation

流式学习可用：

> predict → observe label → score → update

而不是先用样本训练再评价同一个样本。

这样避免把“刚学过答案”的结果当成在线泛化能力。

### 26.10 在线更新必须有回滚

建议记录：

- model version；
- update batch/time；
- data range；
- before/after metrics；
- drift signal；
- rollback checkpoint。

自动更新不应绕过发布治理。

### 26.11 云端部署中真正长期的知识

不同云平台名称和控制台会改变，但核心组件长期类似：

$$
Artifact
\rightarrow Runtime
\rightarrow Endpoint
\rightarrow Scaling
\rightarrow Logging
\rightarrow Monitoring
\rightarrow Rollback
$$

因此 Study 不保存旧版云控制台点击步骤；需要实际部署时再查目标平台当前文档。
