# 15｜特征存储、历史时点与训练服务一致性

先修：[特征工程](11-特征工程与选择.md)、[预处理管道](09-预处理管道与可复现实验.md)及[时间验证](13-时间序列与异常检测.md)。本章解决同一个特征为何在训练和服务中变成不同输入，以及怎样构造不偷看未来的训练记录。

## 1. 一份定义，两种读取

离线训练常问“这些实体在过去各个决策时刻的值是什么”；在线服务问“这个请求现在可用的值是什么”。离线存储保带时间/版本的历史，在线存储维护可低延迟读取的当前物化值，registry记录定义。materialization把符合规则的历史/计算结果交给在线路径；backfill为过去时点生成历史，两者都不是创建新标签。

定义至少包括实体命名空间、来源与schema、变换代码/版本、窗口边界、单位/dtype、缺失/过期政策、TTL、负责人和依赖版本。模型固定这些契约，而不只固定“特征名”。同一变换代码可以减少偏差，仍须核实际数据、时间、运行配置和舍入；“用了feature store”不自动证明一致。

## 2. 分清四个时间

| 时间 | 含义 | 常见混淆 |
|---|---|---|
| event/valid time | 业务事件或特征值所描述的时刻 | 不是系统当时一定已经知道 |
| available time | 该版本的值实际可被决策路径读取的时刻 | 不一定等于后来回填文件的写入时间 |
| prediction cutoff | 本次决策允许使用信息的截止点 | 不能改成未来结果/标签到达时间 |
| label window/arrival | 预测目标的未来观察窗口及标签何时成熟 | 标签晚到不授予特征读取未来信息 |

例如在day16预测之后30天是否流失，特征截止仍是16；标签可能到46甚至更晚才可确定。用day28的最新特征回连day16，即使标签最终正确，也把未来行为放进输入。随机划分训练/测试不能修复这种逐行泄漏。

## 3. 一个历史join的明确政策

对每个实体、特征版本和预测时刻T：先过滤event≤T且available≤T的记录，再按声明的event/available顺序选择最新；T−event超过TTL则返回缺失/过期状态。TTL相对于这条预测记录的T，而不是今天运行回填的时钟。边界T−event=TTL是否有效必须固定，本章示例采用有效。

假设u的v1特征：day7值4（day7可用）、day14值3（day14可用）、day15修订值99（day20才可用），以及day28值0。预测day16时选择day14的3；只看event会偷用day15的99，只看实体最新会偷用day28的0。day21时前述修订才可参与。缺失、源故障、过期和未授权是不同原因，不宜只填一个数后丢掉原因。

聚合窗口同样精确：30天计数若定义为(T−30,T]，在T=100时day70不计入，day100计入；另一条路径用闭区间[70,100]会多一天。对于真实时间戳，还要统一时区、夏令时、精度、迟到事件和幂等去重。

## 4. 完整自有例：按当时可知信息取单特征

这个标准库小例用整数天和一个数值特征，明确检查实体、版本、时间、TTL与冲突。返回不可变的值/时间tuple；不实现存储、用户权限、并发或真实Feast服务。记录范围是自有小数据，数值限制为有限且绝对值≤1e308。

```python
from dataclasses import dataclass
from math import isfinite


@dataclass(frozen=True)
class FeatureValue:
    entity: str
    version: int
    event_day: int
    available_day: int
    value: float


def as_known_feature(rows, entity, version, prediction_day, ttl_days):
    if type(entity) is not str or not entity:
        raise ValueError("需要entity")
    if type(version) is not int or version < 1:
        raise ValueError("version须为正整数")
    if type(prediction_day) is not int or prediction_day < 0:
        raise ValueError("prediction_day须为非负整数")
    if type(ttl_days) is not int or ttl_days < 0:
        raise ValueError("ttl_days须为非负整数")
    visible = {}
    for row in rows:
        if not isinstance(row, FeatureValue):
            raise ValueError("需要FeatureValue记录")
        if type(row.entity) is not str or not row.entity:
            raise ValueError("记录entity不合法")
        if any(type(x) is not int or x < 0 for x in (row.event_day, row.available_day)):
            raise ValueError("记录时间不合法")
        if type(row.version) is not int or row.version < 1:
            raise ValueError("记录版本不合法")
        if type(row.value) not in (int, float) or abs(row.value) > 1e308 or not isfinite(row.value):
            raise ValueError("value须为有限数值")
        if row.entity != entity or row.version != version:
            continue
        if row.event_day > prediction_day or row.available_day > prediction_day:
            continue
        key = (row.event_day, row.available_day)
        if key in visible and visible[key] != row.value:
            raise ValueError("同时间/版本记录冲突，不能由输入顺序决定")
        visible[key] = row.value
    if not visible:
        return None
    event_day, available_day = max(visible)
    if prediction_day - event_day > ttl_days:
        return None
    return (visible[(event_day, available_day)], event_day, available_day)


rows = [FeatureValue("u", 1, 7, 7, 4.0), FeatureValue("u", 1, 14, 14, 3.0),
        FeatureValue("u", 1, 15, 20, 99.0), FeatureValue("u", 1, 28, 28, 0.0),
        FeatureValue("u", 2, 14, 14, 30.0), FeatureValue("v", 1, 16, 16, -1.0)]
assert as_known_feature(rows, "u", 1, 16, 10) == (3.0, 14, 14)
assert as_known_feature(reversed(rows), "u", 1, 16, 10) == (3.0, 14, 14)
assert as_known_feature(rows, "u", 1, 21, 10) == (99.0, 15, 20)
assert as_known_feature(rows, "u", 2, 16, 10) == (30.0, 14, 14)
assert as_known_feature(rows[:2], "u", 1, 24, 10) == (3.0, 14, 14)
assert as_known_feature(rows[:2], "u", 1, 25, 10) is None
assert as_known_feature(rows, "unknown", 1, 16, 10) is None
try:
    as_known_feature(rows + [FeatureValue("u", 1, 14, 14, 8.0)], "u", 1, 16, 10)
except ValueError:
    pass
else:
    raise AssertionError("冲突记录不得静默覆盖")
for field in (True, -1):
    try:
        as_known_feature(rows, "u", 1, 16, field)
    except ValueError:
        pass
    else:
        raise AssertionError("TTL类型/范围必须检查")
try:
    as_known_feature([FeatureValue("u", 1, 14, 14, 1 << 20000)], "u", 1, 16, 10)
except ValueError:
    pass
else:
    raise AssertionError("数值超示例范围不能通过")
print("事件时间/可用时间/版本/实体/TTL等号与过期/顺序无关/冲突拒绝通过")
```

2026-10-16用Python3.12.13实际验证：晚到修订/未来值不提前可见、版本与实体隔离、TTL等号和过期、逆序输入结果相同、同时间冲突拒绝。这里验证的是指定读取合同，不是生产数据完整性或授权系统。

## 5. 回填与created时间不能混成一句规则

回填今天生成一个历史特征，不一定意味着用了未来信息。先区分两个任务：复现过去真实在线系统“当时已知”的值，需以真实可用时间约束；研究新定义在历史输入上“当时可以算出”的值，则需证实所有原始输入在截止前可得，窗口/变换/拟合参数也没用未来。不能把回填物理写入时间一律当业务可用时间，否则会无差别排除合法历史重算；也不能只把event改旧日期来掩盖晚到修订。

2026-10-16选读[Feast时点join说明](https://docs.feast.dev/getting-started/concepts/point-in-time-joins)：默认created字段可用于同event去重，而非总是按决策时刻过滤；所读文档支持显式filter_by_created_timestamp=True，要求created语义反映在线可用时刻，NULL被排除，未支持的offline store会报错。使用该机制前核具体版本/后端和字段语义，不能只粘一个flag声称完成双时间治理。

## 6. 版本化和在线物化的边界

同名同版本的不同定义应冲突；变更窗口/默认值/来源/单位等语义时创建新版本，并让模型/离线/在线都固定所需版本。比如从30天改7天，应由新版本明确描述，不把旧名仍然叫30天当不影响语义。注册元数据不是访问授权，owner名字也不能认证调用者。

物化记录保定义/来源版本、数据与有效时间、实际写入状态和当前安装代。低延迟在线store的latest不能替历史：若未来记录先覆盖旧值，回读过去时即使拒绝未来，也未必找得回原值。需要防未来写入或保多版本历史。frozen dataclass内含dict仍可被别名修改；来源写入直接存引用、历史join也返回原values引用，不能当不可变证据。

失败时保上一完整代、当前partial、过期与回填范围；TTL不意味着所有模型都必须无条件用默认值。模型若没在这种缺失/过期分布上验证，可能需要拒绝或升级。提升新鲜度也可能改变模型所见输入，应做一致性和效果对照。

## 7. 用同一批请求定位skew

记录实际服务用过的request ID、实体、决策时间、模型/特征/数据版本和完整特征值，在获准范围内比较三组：

1. 在线读取与训练join：检验两条整体路径在同一历史合同下是否一致。
2. 即时重算与训练join：在变换和输入版本一致的前提下定位年龄差。
3. 第二份代码与即时重算：定位窗口、默认值、单位、类别映射或舍入差。

逐特征报比较数量、缺失/未配对请求、绝对/相对差、超过声明容差的比例。request ID不能只用(entity,day)替代，否则同实体同日多个请求会被字典覆盖；不同键集合和空比较保持未完成，而不是取交集后报0差异。先拒NaN/Inf，源 `NaN > tolerance`为False会掩盖错误；1e-6容差和1%门限只是案例政策，按单位、风险和样本量确定。

## 8. 五项实践与六项自检

1. 快照间隔7天改1天：在同样请求/定义/历史输入上比较年龄与skew，不预写“必然更好”。
2. TTL改3天：数清哪些训练/服务请求变缺失、默认值和效果如何变化，保原分母而不是删行提高分数。
3. 给历史记录增加available/created：构造event在前、可用在后的晚到修订，明确哪种复现任务应排除它。
4. 新增7天窗口版本：旧模型仍读固定旧版本，backfill和online按精确ref发布，不能未带版本就静默追latest。
5. 修复第二条服务路径：逐一统一左边界、无历史默认、单位/舍入，再对同request重比；0差异只对比较范围成立。

六题核心判断：只按实体连接latest可能泄漏未来；T20、TTL7时day17合格而day24不可见；365与−1是默认差；版本保护旧模型语义；fresh与snapshot差83%不等前者必正确；晚到修订需以当时可用语义核对，不能只看event旧日期。
