# 06｜计算性能与并行训练

> 先做过一次训练再学，第一遍仅看计时、显存组成、梯度累积；多机并行是进阶选读，不作为开始深度学习的前置条件。

## 1. 深度学习性能的基本视角

训练速度不是单一 FLOPs 问题，而是：

```text
算法
+ 计算图
+ kernel
+ 内存访问
+ host/device 传输
+ 通信
+ 数据管线
```

任何一层都可能成为瓶颈。

## 2. 命令式与符号/编译执行

命令式执行易调试、控制灵活；图编译/符号执行有机会做：

- op fusion；
- constant folding；
- memory planning；
- kernel selection；
- device scheduling。

现代框架已经越来越趋向“动态图开发 + 编译器优化执行”的混合方式。

## 3. 异步计算

GPU kernel 启动通常异步，CPU 发出任务后不一定立即等待完成。

这意味着：

- 计时必须显式同步；
- Python 代码结束不代表 GPU 已完成；
- host-device copy 可能隐式同步。

错误的 benchmark 很容易把排队时间和执行时间混在一起。

## 4. 自动并行

独立操作可以在不同资源上并行，但实际收益取决于：

- 数据依赖；
- kernel 粒度；
- stream；
- memory bandwidth；
- 调度开销。

“可以并行”不等于“实际更快”。

## 5. 硬件层瓶颈

需要建立 Roofline 式直觉：

- compute-bound：算力限制；
- memory-bound：内存带宽限制；
- communication-bound：多卡通信限制。

矩阵乘法通常更容易利用加速器；大量小 kernel、索引、数据搬运往往效率低。

## 6. 数据并行

最常见多 GPU 训练方式：

```text
复制模型
→ 每卡处理不同 mini-batch
→ 计算局部梯度
→ All-Reduce 聚合
→ 同步更新
```

关键约束：

- 每卡 batch；
- 梯度同步通信；
- load balance；
- 通信与计算重叠。

## 7. 模型并行

当单卡放不下模型时，需要把不同参数/层拆到不同设备。

现代扩展包括：

- tensor parallel；
- pipeline parallel；
- sequence/context parallel；
- expert parallel；
- parameter/optimizer sharding。

D2L 的多 GPU 基础应理解为这些方法的前置概念。

## 8. 参数服务器

Parameter Server 把参数聚合放在中心或分片 server 上，是分布式训练的重要历史架构。

现代大规模 GPU 集群更多使用高效 collective communication，但参数服务器思想仍适用于理解：

- 参数所有权；
- 同步/异步更新；
- stale gradient；
- 带宽瓶颈。

## 9. 内存构成

训练显存不只是参数：

```text
parameters
+ gradients
+ optimizer states
+ activations
+ temporary buffers
+ communication buffers
```

大模型训练中 activations 与 optimizer states 往往非常可观。

## 10. 提升性能的顺序

建议：

1. profiler 定位瓶颈；
2. 提高 batch/算子利用率；
3. 修复数据加载；
4. mixed precision；
5. 减少同步和数据搬运；
6. kernel fusion / compile；
7. 再考虑多卡扩展。

在单卡都没有跑好之前直接堆 GPU，通常只会扩大低效率。

## 11. benchmark 原则

性能测试必须明确：

- warmup；
- synchronization；
- batch size；
- dtype；
- sequence/image size；
- hardware；
- software version；
- 是否含数据加载；
- throughput vs latency。

否则数字几乎不可比较。

## 12. Compendium 补充：Mixed Precision

Mixed precision 的目标是：

> 在不明显损害训练稳定性的前提下，降低显存、提高矩阵计算吞吐。

常见 dtype：

- FP32：范围和精度较高；
- FP16：吞吐高，但数值范围较小；
- BF16：指数范围接近 FP32，通常更容易训练稳定。

FP16 训练中可能需要 loss scaling，防止很小的 gradient underflow。优化器状态或关键累加仍可能保留更高精度。

## 13. Gradient Accumulation

当显存放不下目标 global batch 时，可以连续处理多个 micro-batch，仅累积梯度，最后再更新参数：

```text
micro-batch 1 → accumulate grad
micro-batch 2 → accumulate grad
...
→ optimizer step
```

若各 micro-batch 等大，累积 $K$ 次时应将各自平均损失除以 $K$，再更新一次；不等大时应按有效样本数或 token 数加权。BatchNorm、随机性和更新频率会破坏与单次大 batch 的完全等价。累积降低激活显存压力，不会消除模型、梯度和优化器状态内存。

## 14. Activation Checkpointing

普通反向传播会保存大量中间 activation。

Checkpointing 只保留部分节点，反向时重新计算缺失 activation：

```text
memory ↓
compute ↑
```

这是典型的“用额外计算换显存”。

## 15. Tensor / Pipeline Parallel 的通信本质

Tensor parallel 把单个大算子拆到多个设备，通常需要频繁 collective communication。

Pipeline parallel 把不同层放在不同 stage，通过 micro-batch 流水减少空闲，但会产生 pipeline bubble。

优化时真正需要平衡：

- compute granularity；
- communication volume；
- synchronization；
- topology；
- micro-batch count。

## 16. Parameter / Gradient / Optimizer Sharding

大模型训练的显存不只由参数决定。

将：

- parameters；
- gradients；
- optimizer states；

分散到不同 rank，可显著降低单卡内存占用。

ZeRO / FSDP 一类方法都可以从“哪些状态复制、哪些状态分片”这个统一视角理解。

## 17. MoE 与 Expert Parallelism

Mixture of Experts 每个 token 只激活少数 expert，以更低每-token 计算量使用更大的参数容量。

工程难点：

- router balance；
- token dispatch；
- all-to-all communication；
- expert capacity；
- hot expert / load imbalance。

因此 MoE 的瓶颈往往不是矩阵乘法本身，而是跨设备 token 路由。

## 18. Scaling Law 的工程意义

Scaling law 更适合被理解为：

> 在模型规模、数据规模和训练计算之间存在可测量的系统性权衡。

它可以帮助决定：

- 参数继续变大是否仍值得；
- 数据是否已经成为瓶颈；
- 固定 compute budget 如何分配。

具体拟合系数会随模型、数据和训练方法改变，不应作为长期常数写死。

## 19. 先看拓扑，再看并行策略

多机多卡系统中，GPU 之间并非等价：

- 同卡/同节点高速互联；
- 跨 socket；
- 跨节点网络。

并行策略应尽量让通信最频繁的操作发生在带宽最高、延迟最低的链路上。

来源增补：*Maths, CS & AI Compendium* Chapter 06 distributed deep learning，基准提交 `9850ee574a370bc1cde59de98b394e953775b67d`。

## 先估数量级，再比较速度

1 亿参数仅用 FP32 存权重约需 400 MB（十进制）。若梯度和 Adam 两个状态也各用 FP32，这四份合计约 1.6 GB，还没有包含激活、临时工作区和通信缓冲。

4 张卡、每卡 batch 8、累积 2 次，则一次更新有效 batch 为 $4\times8\times2=64$（无重复样本、等权损失时）。卡数翻倍并不保证耗时减半，要记录通信和数据加载。

自查：仅在 Python 发出 GPU 任务前后读时钟，为什么可能得到过小时间？**答案：**GPU 异步，主机计时可能只量到提交任务。需使用设备计时事件或在适当边界同步，并先预热；测单算子时也不要把下载数据时间混入结果。

## 从并行概念进入路由和预算计算

专家路由的可核对小程序、总参数与激活参数的区别、容量/溢出与负载目标，以及缩放经验式的约束优化进入[Transformer推理与规模设计](../../LLM%20工程实践/14-Transformer推理与规模设计.md)。固定训练预算的拟合最优点不等于服务生命周期成本最低；实际通信、分片和并行策略仍以本章的拓扑及状态视角判断。

## 20. 数据并行与梯度累加的值级合同

每个rank复制同一初始模型，处理自己的数据；DDP只同步梯度，不自动把输入切成无重复子集。实际训练用sampler/数据分片、每epoch重设相应seed，并确认重复padding数据是否计入目标。模型登记参数、optimizer更新和scheduler次数须一致，某rank提前结束还会影响collective顺序。[DDP官方说明](https://docs.pytorch.org/docs/stable/generated/torch.nn.parallel.DistributedDataParallel.html)

若本地loss是n_r个有效样本的均值，则全局平均梯度是`Σ n_r*g_r / Σ n_r`。只有各rank权重相等时无权rank平均才相同。文本的有效token数可能因padding/mask不同，即使每卡序列条数相同也不满足等权。可以按全局有效token数缩放本地sum loss；若后端all-reduce再除D，要相应补D倍，避免二次平均。最后不整除的微批同理，不能简单每个micro_loss除固定K后漏尾组。

梯度累加在一组microbatch之后只step一次，按真实样本/元素/token权重归一；在DDP中前面microbatch的forward/backward均放入`no_sync()`，最后一个同步。它减少同步次数，不必等比例减少通信墙钟，因为最后同步/重叠仍在；BN、Dropout、优化器step/clip时机可破坏与一次大batch逐位等价。

Tensor parallel的column-expand将W1输出列切开，各分片独立做逐元素激活，再对W2输入行分片的局部乘积求和。非线性若跨channel归一化或attention head间共享，不能任意切完直接局部算；先判断依赖与需要collective的边界。Bias通常只加一次，不能把每分片完整bias又求和。

```python
import copy,torch
from torch import nn
import torch.nn.functional as F
torch.set_num_threads(1);torch.manual_seed(2)
net=nn.Linear(3,2).double();X=torch.randn(7,3,dtype=torch.float64);Y=torch.randn(7,2,dtype=torch.float64)
full=copy.deepcopy(net);F.mse_loss(full(X),Y).backward();ref=[p.grad.clone() for p in full.parameters()]
local=[];counts=[]
for ids in [slice(0,2),slice(2,7)]:
    model=copy.deepcopy(net);F.mse_loss(model(X[ids]),Y[ids]).backward()
    local.append([p.grad.clone() for p in model.parameters()]);counts.append(len(X[ids]))
weighted=[sum(g[j]*n/7 for g,n in zip(local,counts)) for j in range(2)]
wrong=[sum(g[j] for g in local)/2 for j in range(2)]
assert all(torch.allclose(a,b) for a,b in zip(ref,weighted))
assert any(not torch.allclose(a,b) for a,b in zip(ref,wrong))
# Gradient accumulation over unequal microbatches: divide sums by full element count.
acc=copy.deepcopy(net)
for ids in [slice(0,2),slice(2,5),slice(5,7)]:
    (F.mse_loss(acc(X[ids]),Y[ids],reduction='sum')/Y.numel()).backward()
assert all(torch.allclose(a,p.grad) for a,p in zip(ref,acc.parameters()))
# Column-parallel expand, local nonlinearity, row-parallel contract.
x=torch.randn(2,3,dtype=torch.float64);W1=torch.randn(3,8,dtype=torch.float64);W2=torch.randn(8,3,dtype=torch.float64)
y=F.gelu(x@W1)@W2
parts=[F.gelu(x@W1[:,i:i+4])@W2[i:i+4] for i in [0,4]]
assert torch.allclose(sum(parts),y,atol=1e-12)
print('unequal-rank weighted and microbatch gradients match; naive mean maxerr',float((wrong[0]-ref[0]).abs().max()))
print('FFN column-expand/local-GELU/row-contract matches; no real collective communication')
```

本例是真实PyTorch求梯度，非均匀2/5数据分片按权平均和2/3/2微批sum归一均与7样本完整MSE一致；无权rank平均的weight梯度最大差约.2568。column-expand→local GELU→row-contract与完整FFN在容限内一致。CPU顺序计算**没有执行真实DDP、NCCL或多GPU吞吐**。

Ring all-reduce常分reduce-scatter与all-gather两阶段，各D−1轮，理想每rank传输约`2G*(D−1)/D`字节。collective可求sum或框架进一步求mean，要查具体约定；不能仅把D−1轮叫完整all-reduce。真实网络拓扑、bucket、延迟、小消息与重叠决定时间，不从字节直接乘固定收益。

## 21. 分片不是静态除法：FSDP/ZeRO与设备拓扑

参数、梯度、optimizer/master的静态预算和真实Adam dtype例子见[训练资源与数值量化](../../LLM%20工程实践/15-训练资源与数值量化实现.md)。FSDP2通常在forward之前按module-group all-gather，在选择reshard_after_forward后释放完整参数，backward前再次gather，之后reduce-scatter梯度。若forward之后保留，后向通信/峰值又不同；不是“永远只通信一次/一定三倍参数字节”。root整模型一个大group与逐block grouping的重叠和峰值差别也很大。[FSDP2官方机制](https://docs.pytorch.org/docs/stable/distributed.fsdp.fully_shard.html)

ZeRO1只分片O，ZeRO2加G，ZeRO3加P；省多少取决于实际P/G/O和D。激活、最大临时full-parameter group、通信workspace仍要留空间。将CPUOffloadPolicy参数/梯度/optimizer状态卸载到CPU，与activation offload分开；PCIe、CPU optimizer和NVMe吞吐要各自测量，不能承诺只慢30–50%。activation checkpoint不减少常驻P/G/O，模型状态本身超预算时先分片/卸载或改模型/优化器。

DP/TP/PP/EP以及sequence/context parallel可以组合，world_size的乘积只适用于明确独立的网格轴；每组成员、collective和参数所有权要画清楚。TP常需要高频低延迟通信，通常偏好节点内高速互联，但跨节点TP并非数学上禁止。EP dispatch按实际token路由，最忙expert/节点和all-to-all拓扑要计入；active参数少不意味着只需存这些权重。

总FLOPs粗算6ND只用于特定dense主矩阵近似，MoE总/active参数、长上下文attention、重算及真实硬件效率应另算。训练目标、数据质量与充分训练先用[规模设计](../../LLM%20工程实践/14-Transformer推理与规模设计.md)拟合范围判断；租用价格、固定GPU小时、某一厂商成本不能作长期教材常数。

## 22. GPipe与1F1B：合法事件、bubble与活跃激活

P个stage，M个microbatch；F(s,m)需前一stage相同m前向结果，B(s,m)需本地F及后一stage相同m的梯度，每stage设备资源不得执行两个不可重叠kernel。GPipe是多microbatch填满前向流水后再反向的fill-drain，不是“一个microbatch跑完全部F/B才下一个”。1F1B先按rank位置warmup，再交错一前一后，最后cooldown；所有梯度完成才step，保持本次iteration的参数版本一致。

在等F/B单位耗时、均衡stage、零通信的简单fill-drain模型中，总时间2(M+P−1)，每stage有效工作2M，所以idle fraction为`(P−1)/(M+P−1)`。`(P−1)/M`是相对有效工作额外比例的一种近似，不是总时间idle fraction。1F1B常降低同时活跃的activation，却不保证这个均匀模型的bubble更少。

```python
from collections import defaultdict

def simulate(P,M,schedule):
    assert type(P) is type(M) is int and min(P,M)>0 and schedule in ('gpipe','1f1b')
    plans=[]
    for s in range(P):
        if schedule=='gpipe':plan=[('F',m) for m in range(M)]+[('B',m) for m in reversed(range(M))]
        else:
            warm=min(P-s-1,M);plan=[('F',m) for m in range(warm)]
            for m in range(M-warm):plan.extend([('F',warm+m),('B',m)])
            plan.extend(('B',m) for m in range(M-warm,M))
        plans.append(plan)
    cursor=[0]*P;done={};events=[];live=[0]*P;peak=[0]*P;t=0
    while any(cursor[s]<len(plans[s]) for s in range(P)):
        chosen=[]
        for s in range(P):
            if cursor[s]==len(plans[s]):continue
            kind,m=plans[s][cursor[s]];deps=[]
            if kind=='F' and s:deps.append(('F',s-1,m))
            if kind=='B':
                deps.append(('F',s,m))
                if s<P-1:deps.append(('B',s+1,m))
            if schedule=='gpipe' and kind=='B':deps.extend(('F',P-1,j) for j in range(M))
            if all(d in done and done[d]<=t for d in deps):chosen.append((kind,s,m,deps))
        assert chosen,'deadlock in supplied stage order'
        for kind,s,m,deps in chosen:
            assert all(done[d]<=t for d in deps)
            events.append((kind,s,m,t,t+1));done[(kind,s,m)]=t+1;cursor[s]+=1
            live[s]+=1 if kind=='F' else -1;peak[s]=max(peak[s],live[s]);assert live[s]>=0
        t+=1
    assert live==[0]*P
    assert len(events)==2*P*M
    # One device-resource per stage: no overlapping events; dependency checks above.
    for s in range(P):
        intervals=[(a,b) for _,r,_,a,b in events if r==s]
        assert all(a2>=b1 for (_,b1),(a2,_) in zip(intervals,intervals[1:]))
    bubble=1-(2*P*M)/(P*t)
    return events,t,bubble,peak
for mode in ['gpipe','1f1b']:
    ev,T,bub,peak=simulate(4,8,mode);print(mode,'virtual makespan',T,'idle fraction',round(bub,4),'peak live activations',peak)
    print('rank0',[(k,m,a) for k,s,m,a,b in ev if s==0])
# Balanced fill/drain formula is idle/(total), not (P-1)/M.
assert abs(simulate(4,8,'gpipe')[2]-3/11)<1e-12
assert max(simulate(4,8,'1f1b')[3])<max(simulate(4,8,'gpipe')[3])
```

程序构造两种完整per-stage工作序列，逐时隙检查真实前后依赖与资源互斥，计算在每stage尚待反向的microbatch数量。P4/M8两种makespan均22、idle fraction均3/11≈27.27%；GPipe峰值每stage8组、1F1B为[4,3,2,1]。这直接回答“1F1B如何省activation”，没有将相同总时间包装成加速。没有模拟非均匀kernel、通信、GPU或optimizer step。

## 23. DualPipe：分块重叠与双向流水的实际条件

DualPipe针对MoE计算与跨节点通信，原报告把每个F/B chunk分为attention、all-to-all dispatch、MLP、all-to-all combine，另有PP点对点通信；backward的attention/MLP又区分input-gradient B和weight-gradient W。input-gradient要及时发上游，weight-gradient可推迟到不阻塞上游的空闲窗口，但必须在optimizer/全局grad norm等依赖前完成。[DeepSeek-V3 §3.2.1](https://arxiv.org/abs/2412.19437)

不仅是“两个forward同时占同一GPU”。原Figure4给出一对F/B内计算/通信重排及SM资源分配；Figure5是双端注入、相反方向stream的完整8rank/20microbatch schedule。重叠需要有可并行的计算/通信资源、依赖满足、内核/链路并发能力；两者争带宽/SM时不能把两段时间直接取max。来源手画F/F重叠表没有这些资源证明，不能当真实schedule。

下面保存两条microbatch的attention→dispatch→MLP→combine依赖，分别以单一资源和独立compute/comm资源排程，验证所有事件。它是**重叠机制的CPU离散例，不是DualPipe复现**，不伪造真实pipeline、EP或all-to-all kernel。

```python
# A two-resource operation graph: compute and communication. NOT DualPipe replay.
# The two independent microbatches allow comm(A) to overlap compute(B).
ops={'attnA':('compute',2,[]),'dispatchA':('comm',3,['attnA']),
     'mlpA':('compute',2,['dispatchA']),'combineA':('comm',2,['mlpA']),
     'attnB':('compute',2,[]),'dispatchB':('comm',3,['attnB']),
     'mlpB':('compute',2,['dispatchB']),'combineB':('comm',2,['mlpB'])}
def run(order,share_resource):
    end={};free={'compute':0,'comm':0,'all':0};events=[]
    for name in order:
        res,dur,deps=ops[name];res='all' if share_resource else res
        assert all(d in end for d in deps)
        start=max([free[res]]+[end[d] for d in deps]);finish=start+dur
        events.append((name,res,start,finish));free[res]=finish;end[name]=finish
    # Validate resources and dependencies, not arithmetic-only speedup label.
    for name,res,a,b in events:
        assert all(end[d]<=a for d in ops[name][2])
        assert all(max(a,aa)>=min(b,bb) for n,r,aa,bb in events if r==res and n!=name)
    return events,max(end.values())
order=['attnA','dispatchA','attnB','dispatchB','mlpA','combineA','mlpB','combineB']
serial,T0=run(order,True);overlap,T1=run(order,False)
assert T1<T0
print('virtual single/two independent resource makespans',T0,T1,'events',overlap)
# If communication steals compute bandwidth/SMs, this two-resource bound is optimistic.
P=8;F=2.;B=4.;W=1.;FB=5.
b1=(P-1)*(F+B);bd=(P/2-1)*(FB+B-3*W)
print('declared paper chunk times: bubble time 1F1B/DualPipe',b1,bd)
```

### 23.1 参数副本、DualPipeV与公平比较

[官方DualPipe README](https://github.com/deepseek-ai/DualPipe)以**相同PP stage数量**比较：DualPipe与DualPipeV每device参数均为2×、activation为P+1，使用同bubble表达式；device数量分别P与P/2。DualPipeV的cut-in-half减少总体复制/设备，不等于“每device一个stage而DualPipe两个”。保持相同device数时PP stages也改变，必须重新比较，而不是把不同基准的1×/2×拼在表里。

示例dense N70B、P8，按该比较基准每device `2N/P=17.5B`参数，低精度2byte仅参数35GB。DualPipe用8device，总参数载荷140B；DualPipeV用4device，总70B。若固定8device比较，则V可以对应16stage，每device载荷又不同。MoE专家经EP分散后，重复部分的**每device实际存储**与expert/dense权重构成有关；不能用37B active代替671B total，必须查网格和所有权。

## 25. 累积窗口：尾组、有效Token与成功时钟

§13/20已有不等微批真实梯度例；本节把它接到实际训练循环。global batch=micro batch×累积数K×数据并行组D仅适用于各rank/micro等大、同权且完整窗口。序列条数相同也可能mask后有效Token不同，应把有效目标分母另记。若第i微批有n_i个有效目标、平均loss为L_i，则全窗口平均为Σn_i L_i/Σn_i；以sum loss/全窗口总有效目标数反向最直接。只除预设K会错误加权短文、padding或尾组；空窗口不能继续optimizer.step，否则旧momentum/decay可能仍改参数。

小例：两微批分别2与6个有效目标、平均loss为1与3，全窗口应为(2×1+6×3)/8=2.5，而两个局部均值再平均为2。最后只剩2个micro但仍除预设4，会将本应合并的梯度再减半。多rank时进一步用所有rank有效总数；DDP若默认再除D，应相应缩放本地sum loss，避免重复平均。§20的2/5数据权重和2/3/2累积反例已实际运行，不在这里再生成基础代码。

窗口开始zero一次，所有micro使用同一参数版本；先正确归一loss、再按相同AMP scale累积，末尾统一unscale、核有限值和稳定全范数、clip、optimizer.step；成功更新才推进成功时钟的scheduler。每micro clip通常不等先相加再clip，每micro step改变更新频率和optimizer矩状态。Dropout随机mask、BatchNorm局部统计和浮点加法顺序可使一次大batch与微批逐位不同，等价检查要声明模型/模式、输入、初态、归约和容差。

### 25.1 no_sync与性能记录的真实边界

DDP的非最终micro要把forward及backward共同放进no_sync，最后一个正常同步；仅包backward可能仍触发同步。一个backward可有多个gradient bucket，不能把“同步分支次数”当网络all-reduce调用数。来源no_sync_context实际为空context，sync_counter是本地分支计数，既没调用DDP.no_sync也没执行真实collective。真实判断应看profiler中的bucket/字节/重叠与墙钟。[DDP no_sync官方说明](https://docs.pytorch.org/docs/stable/generated/torch.nn.parallel.DistributedDataParallel.html)，相关正文选读2026-10-11。

增K降低更新频率并增加每次更新样本，但总时长受数据管线、算子利用率、通信、optimizer和预热影响。固定num_steps同时增K会增总样本/Token预算，不是同一训练质量实验；换K时仅重设seed也不保证样本相同，因为来源逐micro穿插生成X/Y消耗随机数。先生成同一批输入再拆分，性能则固定总有效Token并报告actual updates、warmup、数据加载是否计入、吞吐及每窗口时长。偶数样本的median是否取两中值平均也写清，避免把上中位值当常规定义。

**累积五项练习及判据。** ① 扫100步吞吐曲线时同时报告总样本/有效Token、成功更新数、预热和硬件/数据加载配置，确定是否饱和；不同预算的loss不可直接比较。② 等大均值不除K使梯度K倍，但只有特定SGD条件才使更新K倍；Adam的矩/ε/decay会改变结果，比较梯度和逐参数更新两层。③ 换AdamW时核每有效成功更新state.step/m/v/decay仅推进一次，micro不推进，skip/尾组按明确政策处理。④ 真正接DDP.no_sync时围住非末forward/backward，用collective profiler记录而非固定计数器证明变化；减少同步次数不保证墙钟同比下降。⑤ 2×8与4×4拆同一X/Y和模型初态，检查梯度/参数差，另外加入不等尾组与mask；容差依dtype/尺度，不能盲放宽掩盖错误。真实sweep、AdamW/DDP扩展均未本轮运行。

**累积六题自查。** ① 有效batch恒等式何时成立？单设备等micro为micro×K，DP再乘D，有效Token和不完整尾组单独计数。② 为什么除K？仅等权局部mean时还原全均值；一般用sum/总有效分母，Adam更新不必K倍。③ 什么时候step？整个合法窗口完成后统一step，空/异常窗口拒绝或按政策丢弃，不能仍算成功。④ no_sync包什么？非末micro的forward+backward，最终同步；bucket可不止一个。⑤ 来源equivalence_check证明什么？给定等大、无BN/Dropout fixture的梯度/更新容差一致，不能推广所有随机/分布式情况。⑥ 吞吐曲线有什么必然规律？没有必然常数或线性关系，需同负载和真实设备测量；几个未知环境CPU点不能定义硬件上限。

## 27. Collective先核值与消息所有权，再看通信量

多进程训练最容易混淆三个层次：collective的**数学结果**、消息如何传播的**算法**、以及某个backend在设备上使用的**实现**。All-reduce SUM的合同是每个rank最后都持有所有输入的和；all-gather按rank次序收集分片；reduce-scatter先规约相同位置，再让rank r只保留规定的第r片；broadcast让所有rank取得指定源的值。四种操作不是分布式框架全部通信的穷尽清单，流水还常用点对点send/recv。

### 27.1 Ring索引与张量载荷的小例

将T字节等分为D片，ring的reduce-scatter与all-gather各D−1轮，每rank理想**发送载荷**为`2T(D−1)/D`。D4、64个FP32元素，T256字节，每轮16元素64字节，两个阶段共6轮，故每rank384字节、四rank合计1536字节。这不是IPC/TCP实际总字节：消息头、序列化、复制与收发方向的计数口径还需注明。D改变时公式也改变，只是趋近2T，不是严格与D无关。

若65元素补零到68后等分，每片17元素，实际发送是`2×272×3/4=408`字节；拿原260字节直接代入得到390，会漏padding。时间还受每轮延迟、链路与topology、bucket就绪和重叠影响，不能将字节比例当实测加速。

源Queue ring在第s轮由r发送`(r−s) mod D`、接收`(r−s−1) mod D`并累加。以D3/r0为例：第0轮接片2的两rank部分和，第1轮接片1的另外两rank部分和并加自己的片1，因此最后持有片1的完整和。一般停在`(r+1) mod D`，与正文“停在片r”不同。源码独立reduce_scatter先把片i映射到原片`(i−1) mod D`，再返回`(r+1) mod D`，才让输出对应原片r。验收应拿每片不同值对照SUM，不能仅看所有rank总和或图中的方块在转。

Queue程序建立D(D−1)条有向队列，ring只用相邻边；send会detach/clone并计元素载荷，recv已有30秒timeout。它能用于观察消息顺序，不能据此承诺NCCL的内核、网络竞争、吞吐或故障行为相同。源码多个缓冲用CPU zeros，numpy bytes传载荷，不能只将输入搬CUDA就称已实现GPU通信。

### 27.2 任意源广播与后端支持的两个边界

树广播应以源为虚拟rank0，用`v=(physical_rank−src) mod D`组织树，再映回物理rank。源代码直接从`has_value={src}`计算`h+2**round`，当D4/src2时只会增加rank3，永远到不了rank0/1；循环不结束。已有test只覆盖src0，所以“树深度log D”没有证明任意src实现正确。非法rank/world_size、空tensor、非1D拼接、异构shape/dtype、worker失败与退出码同样要独立核查。

“与Gloo逐字节一致”的宣称也要降级：源compare检查max-abs-diff<1e−5，tests使用allclose，属于指定fixture的浮点容差一致。浮点规约顺序可以不同；应先拒绝非有限结果，再核逐元素容差，只有真正检查bytes/torch.equal时才描述相应位级相等条件。

2026-10-13选读的[PyTorch 2.14后端表与collective接口](https://docs.pytorch.org/docs/2.14/distributed)明确支持Gloo reduce-scatter。[v2.14.0 Gloo实现](https://github.com/pytorch/pytorch/blob/v2.14.0/torch/csrc/distributed/c10d/ProcessGroupGloo.cpp)列表路径对每chunk调用allreduce并等待Works，single路径对大buffer allreduce后取rank片。因此**API语义支持不等于原生reduce-scatter的通信效率**；不能沿旧版本记忆写“Gloo永远不支持”，也不能把上述ring载荷式直接当这个backend的实测字节。本次没启动本机process group，安装构建/版本与设备路径仍须实际验证。

### 27.3 梯度同步记录应该比较什么

源码DDP薄wrapper在初始化逐参数broadcast，在backward完成后逐参数阻塞SUM/D；没有backward hook、bucket、通信重叠、no_sync或buffer同步。图中生产bucket先就绪先通信，是设计意图，不是该wrapper已实现能力。等权本地mean才对应全局mean；不等有效目标沿§20/25加权，不能把“梯度mean对卡数不变”解释成加卡后学习率、batch或质量一定不变。

两个rank处理不同数据，局部loss本来可以不同。源main把rank0与rank3局部loss差写成rank_drift，这不证明参数漂移；全局loss须按有效目标归约，模型一致则逐参数/状态另核。最终L2范数同样是弱摘要，例如`[1,3]`与`[3,1]`范数都为√10但权重位置不同。源77的测试比较rank0每步loss和最终norm，没有逐步全参数基线；源81也只返回最终norm。不能把这些测试写成每步参数byte-equal。

初态一致也不只取决于seed。Broadcast是明确的同步方法，相同环境/算法的相同seed可能生成相同值，不能说相同seed必因float epsilon漂移。数据分片是否正确应看样本ID覆盖、sampler与epoch状态；给每rank不同seed既不保证无重复，也不替代数据分片。某rank跳过None梯度而其它rank照常归约，会改变collective顺序；barrier只能等到达，不能传梯度。

## 28. 分片收益必须使用实际dtype、padding和生命周期

§21已有ZeRO1/2/3与FSDP的状态视角，静态预算继续由[训练资源与数值量化](../../LLM%20工程实践/15-训练资源与数值量化实现.md)维护。这里补“教学预算与运行对象怎样对照”：源78/81在每rank保留完整FP32模型/梯度，用ceil(P/D)个FP32元素分别存master、m、v，先拼完整grad再reduce-scatter SUM/D、手写Adam偏差修正，最后all-gather更新的master并回写完整模型。它不是正文宣称的FP16参数/梯度混合精度程序。

源MLP的参数数为`(16×32+32)+(32×32+32)+(32×4+4)=1732`，D4时每shard433元素，三个状态逻辑载荷`433×3×4=5196`字节。完整FP32参数与梯度各6928字节，所以这几类合计19052字节；还没计flat/padded grad、通信接收列表、m_hat/v_hat与其它临时内存。这是按源码手算，未运行分布式或测峰值。若对照具有完整FP32 master副本的同类实现，P/G/master/m/v合计20P；普通FP32 Adam未必另有master，不能给所有baseline强加额外4P。

正文16P与`4P+12P/D`假设P/G各2字节、master/m/v各4字节。D8的5.5P、65.625%节省是该假设的静态模型，不是源程序实测。7B的两个FP32moments是56GB（十进制），再加master28GB为84GB；原Problem写28GB optimizer与自身表格不一致。真实optimizer dtype依实现，混合精度与分片能组合，但不能说所有ZeRO必须混合精度、stage1永远近乎免费或optimizer总比activation大。

Reduce-scatter本身只有理想ring all-reduce一半的载荷。再加updated-param all-gather，与DDP带宽相近需要比较相同长度/dtype与算法；grad和param格式不同、padding或Gloo内部算法不同，都会改变数字。源源码gather的是FP32 master，而理论表可能使用FP16通信，不能混用。

ZeRO2所需的是分片梯度的**存储与生命周期**。把完整grad非本片位置填0，tensor仍分配同样字节，不会释放显存；先生成完整flatgrad再裁零值也没有证明峰值下降。真扩展需在backward/通信边界分片、按需释放，并核逐参数更新与全rank峰值。全局clip则规约各owned shard的平方和得到全模型范数，用共同系数缩放；每rank独立clip会改变全局方向与约束，稳定范数/非有限处理沿§25。

## 29. 从流水表到训练集成的验收合同

§22已提供合法GPipe/1F1B事件与活跃activation的CPU合同，保留原程序和原实测日期。源79的虚拟表也使用均衡、等时F/B、零通信时隙，`FORWARD_UNITS=1/BACKWARD_UNITS=2`却没有参与排程，所以“measured bubble”只指表中的idle slots，不是设备计时。其另一个Gloo程序每micro依次做rank0 F→send→recv→B、rank1 recv→F→loss→B→send，再处理下一个micro；它确有P2P接口，却只有一个micro在途，和fill-drain GPipe表是两个例子。

这个真实wire例每micro的MSE mean反向没有除micro数M，最后一次step得到各micro mean的**和**，不等combined-batch mean。要核等价，应固定完整X/Y与初态，使用sum loss/总有效元素或在等大情况下除M，再比较梯度、完整参数和optimizer状态。测试仅确认两rank返回、loss数量及虚拟表数量，没有全batch对照、1F1B活跃存储或真实bubble/吞吐。

两种轴组合时，PP分层、对应PP位置的DP组归约梯度/分片optimizer；`world_size=P×D`要求明确独立轴，不能把不同stage的参数扔进同一个reduce。同步发送的死锁风险也应按P2P匹配、依赖、缓冲与异步语义分析，“所有send-first必死锁”“偶奇排列万能”都过强。

源81的tiny GPT是两block、dim32、head4、vocab64、S16的pre-LN masked attention模型；按源码维度为29824参数，tok/pos embedding与独立输出head明确分开。LayerNorm有可学习weight/bias，**没有running statistics**，原测验把它与BatchNorm混淆。输入是随机token而非可泛化语言任务，rank0 loss下降不必单调，更不证明通用质量。源码mask在CPU创建，不能只搬model CUDA就套用新backend。

集成loop只在init做broadcast，ZeRO负责reduce-scatter梯度同步与all-gather参数，没有再独立做DDP allreduce，也没有调用Queue原语或流水程序。额外做一次grad归约可能二次平均/增加通信。其state byte计数仅master+m+v，不是包含全部P/G/activation/临时buffer的memory profile。Checkpoint会all-gather每rank的bytes到**所有rank**，再由rank0顺序保存N份full-model replica与optimizer shard，仍有复制与root IO瓶颈。

正确的集成验收要同时看数据/权重归约、每rank逐参数与状态、成功步时钟、所有进程终态、真实内存/时间及恢复后next-step。固定20步只规定预算，main打印norm/memory而不assert，不保证全部不变量；NaN guard、loss-spike回滚也未实现。源verify_resume只比master shard快照，完整继续训练应接[预训练数据与模型交付](../../LLM%20工程实践/16-预训练数据与模型交付实践.md)§4/10–12的恢复合同。

## 30. 通信、分片与流水练习的评价方法

下面承接原76–79各五项扩展，全部是尚未实施的实验判据。已有§20/22与§25的CPU例继续复用；新增真实collective、设备训练、socket、性能sweep均未运行。

### 30.1 通信与同步的十项练习

1. **树与ring切换（76-1）。** 保相同SUM/shape/dtype，逐值校验后在同硬件sweep消息大小与world_size；报告latency/bandwidth项和统计分布，不预设1MB。
2. **接收deadline（76-2）。** 源已有30秒timeout；扩展配置应报告collective/阶段/peer/rank、协调终止并检查worker退出，不能只抛本rank异常让其它进程挂起。
3. **TCP替换（76-3）。** 明确framing、长度、dtype、序号、partial send/recv和断线时序；同输入对照值及deadline，Queue正确不等TCP已正确。
4. **字节JSONL（76-4）。** 分rank/phase记录payload、padding、消息数和耗时；协议/IPC总字节另测，不将张量计数称网络带宽实测。
5. **4rank大小比较（76-5）。** 对1KB/1MB/16MB同归约、dtype、预热、计时与清理比较；CPU IPC结果不能代替NCCL拓扑结论。
6. **DDP bucket（77-1）。** 一致参数映射/就绪协议与bucket顺序，profiler记录调用/载荷/overlap，深模型同总样本预算对照逐参数同步。
7. **累积no_sync（77-2）。** 非末micro的forward+backward都围住；按有效目标归一且保尾组，核逐梯度/参数/状态和真实通信，沿§25完成而非复写空context。
8. **条件unused（77-3）。** 构造一致/不一致分支，显式处理各rank梯度存在性；失败例有限timeout，不能把无限死锁当正常练习交付。
9. **barrier对照（77-4）。** Barrier不聚合梯度；比较独立更新后的逐参数差解释到达同步与值同步，不声称它是替代allreduce的正确实现。
10. **同步开销（77-5）。** B1/16/256比较时注明总样本、实际updates、F/B/comm/optimizer/data以及重叠；改变batch后的质量也需同协议，不只看秒数。

### 30.2 状态分片与流水的十项练习

1. **ZeRO2（78-1）。** 分片/释放真实grad存储并测峰值；填0不减载荷。与同配置ordinary Adam核完整更新和moments。
2. **状态profiler（78-2）。** 按实际dtype/numel、padding、共享storage与临时峰值对照预算；源FP32对象不套16P混合精度表。
3. **DDP与ZeRO1计时（78-3）。** 固定数据/初态/Adam归约，对比F/B/comm/optimizer；源77的SGD不可直接作为源78 Adam的质量基线。
4. **分片global clip（78-4）。** 所有owned shard平方和归约，核稳定范数与共同缩放，对照完整grad；加入tiny/huge/非有限失败，不只核阈值字符串。
5. **naive allreduce（78-5）。** 全grad allreduce→本片step→param gather，与reduce-scatter路径核逐值/消息与时间；相同dtype/padding/backend才能解释差异。
6. **1F1B（79-1）。** 用§22检每stage F/B依赖、设备互斥、同版本step、idle与activationlive；少activation不等所有条件都更快。
7. **stage重平衡（79-2）。** 目标设备profile真实算子/comm/activation，重排层后核F/B等价和最忙stage耗时，参数数不能替代实测。
8. **流水grad等价（79-3）。** 固定完整X/Y与初态，sum/有效总数归一，核梯度、完整更新与状态；源未除M的写法不能过mean-loss合同。
9. **流水checkpoint（79-4）。** 同RNG核output、input/parameter gradients与buffers，再测目标设备峰值/重算时间；源虚拟表不提供显存测量。
10. **PP×DP（79-5）。** 画stage相邻传输与同stage DP组归约/分片，标每group成员、顺序和状态所有权；二维world乘积本身不证明集成正确。

### 30.3 二十四题自查与参考判断

**通信六题（76）。** ① Ring每rank理想载荷是多少？两阶段各D−1轮，2T(D−1)/D，T含padding，收发/协议口径另说明。② Queue为什么有教学价值？它暴露消息模式与顺序，不证明NCCL硬件性能或所有race。③ reduce-scatter后有什么？rank规定的一片规约和；原ring索引停在r+1，需rotation才对应原片r。④ 树广播为何可减latency？holder按轮扩张，深度约log D，但src2缺陷必须纠正，测试src0不够。⑤ Reference比较证明什么？指定输入/后端的值或容差一致；allclose不是byte-equal，也不是所有输入规格的证明。⑥ Tree何时胜ring？小消息/高latency可能有利，实际topology/crossover需测，固定1MB不是定律。

**同步六题（77）。** ① 为何broadcast初态？明确建立参数一致；同seed不必漂移，也不是只有broadcast能相同。② backward后做什么？等权rank mean梯度SUM/D后统一step，权重不等沿有效目标加权。③ 为什么SUM后除D？可实现mean且有backend可用性条件；不能任意把AVG用于不支持的backend。④ Bucket解决什么？摊薄小collective启动开销，但本wrapper没实现bucket。⑤ no_sync为何存在？前K−1micro避免不必要同步，仍需正确归一/最后同步及forward+backward范围。⑥ 顺序reference为何有用？同初态/同数据/同目标可核更新；源只loss/norm，不证明每步全参数位级相同。

**分片六题（78）。** ① 为什么先分optimizer？在指定Adam12P假设下它是大项且step才用，activation可能更大。② 本例wire是什么？grad reduce-scatter与updated-param all-gather，不是所有stage1的唯一内部实现。③ 为何可与DDP带宽相近？两半ring载荷在同长度/dtype下可对照；single reduce-scatter仅半个allreduce，实际Gloo实现另看。④ 7B/D8理论省多少？16P→5.5P，65.625%，静态112GB→38.5GB/rank，不含activation/temp且不对应本FP32demo。⑤ ZeRO2加什么？真实梯度分片存储/生命周期，zero值不会free。⑥ Checkpoint为何有ownership？避免装错master/m/v片；相同world还需shape、计数、配置和完整布局合同。

**流水六题（79）。** ① Bubble是什么？idle/(total)，闭式需均衡等时零通信，不是任意设备实测。② GPipe为何activation随M增长？全forward后才反向，保待backward张量；重算策略可改变峰值。③ 1F1B为何省activation？按stage位置warmup后交错及时释放，简单模型可同bubble，不是所有策略普遍加速。④ 为什么按compute分stage？最忙stage制约吞吐，实际kernel/comm/内存共同profile，embedding成本也看负载。⑤ send-first一定死锁吗？特定阻塞匹配可能，必须核整体依赖与通信语义，偶奇规则不万能。⑥ PP+ZeRO1省什么？层与对应DP组optimizer两轴分片，1/D用该stage DP组大小，不是整个world。
