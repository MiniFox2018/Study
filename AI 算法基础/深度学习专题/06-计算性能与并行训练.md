# 06｜计算性能与并行训练

> 先做过一次训练再学，第一遍仅看计时、显存组成、梯度累积；多机并行是进阶选读，不作为开始深度学习的前置条件。

## 1. 深度学习性能的基本视角

训练速度不是单一 FLOPs 问题，而是：

```text
算法
+ 计算图
+ kernel
+ 内存访问
+ host/device 传输
+ 通信
+ 数据管线
```

任何一层都可能成为瓶颈。

## 2. 命令式与符号/编译执行

命令式执行易调试、控制灵活；图编译/符号执行有机会做：

- op fusion；
- constant folding；
- memory planning；
- kernel selection；
- device scheduling。

现代框架已经越来越趋向“动态图开发 + 编译器优化执行”的混合方式。

## 3. 异步计算

GPU kernel 启动通常异步，CPU 发出任务后不一定立即等待完成。

这意味着：

- 计时必须显式同步；
- Python 代码结束不代表 GPU 已完成；
- host-device copy 可能隐式同步。

错误的 benchmark 很容易把排队时间和执行时间混在一起。

## 4. 自动并行

独立操作可以在不同资源上并行，但实际收益取决于：

- 数据依赖；
- kernel 粒度；
- stream；
- memory bandwidth；
- 调度开销。

“可以并行”不等于“实际更快”。

## 5. 硬件层瓶颈

需要建立 Roofline 式直觉：

- compute-bound：算力限制；
- memory-bound：内存带宽限制；
- communication-bound：多卡通信限制。

矩阵乘法通常更容易利用加速器；大量小 kernel、索引、数据搬运往往效率低。

## 6. 数据并行

最常见多 GPU 训练方式：

```text
复制模型
→ 每卡处理不同 mini-batch
→ 计算局部梯度
→ All-Reduce 聚合
→ 同步更新
```

关键约束：

- 每卡 batch；
- 梯度同步通信；
- load balance；
- 通信与计算重叠。

## 7. 模型并行

当单卡放不下模型时，需要把不同参数/层拆到不同设备。

现代扩展包括：

- tensor parallel；
- pipeline parallel；
- sequence/context parallel；
- expert parallel；
- parameter/optimizer sharding。

D2L 的多 GPU 基础应理解为这些方法的前置概念。

## 8. 参数服务器

Parameter Server 把参数聚合放在中心或分片 server 上，是分布式训练的重要历史架构。

现代大规模 GPU 集群更多使用高效 collective communication，但参数服务器思想仍适用于理解：

- 参数所有权；
- 同步/异步更新；
- stale gradient；
- 带宽瓶颈。

## 9. 内存构成

训练显存不只是参数：

```text
parameters
+ gradients
+ optimizer states
+ activations
+ temporary buffers
+ communication buffers
```

大模型训练中 activations 与 optimizer states 往往非常可观。

## 10. 提升性能的顺序

建议：

1. profiler 定位瓶颈；
2. 提高 batch/算子利用率；
3. 修复数据加载；
4. mixed precision；
5. 减少同步和数据搬运；
6. kernel fusion / compile；
7. 再考虑多卡扩展。

在单卡都没有跑好之前直接堆 GPU，通常只会扩大低效率。

## 11. benchmark 原则

性能测试必须明确：

- warmup；
- synchronization；
- batch size；
- dtype；
- sequence/image size；
- hardware；
- software version；
- 是否含数据加载；
- throughput vs latency。

否则数字几乎不可比较。

## 12. Compendium 补充：Mixed Precision

Mixed precision 的目标是：

> 在不明显损害训练稳定性的前提下，降低显存、提高矩阵计算吞吐。

常见 dtype：

- FP32：范围和精度较高；
- FP16：吞吐高，但数值范围较小；
- BF16：指数范围接近 FP32，通常更容易训练稳定。

FP16 训练中可能需要 loss scaling，防止很小的 gradient underflow。优化器状态或关键累加仍可能保留更高精度。

## 13. Gradient Accumulation

当显存放不下目标 global batch 时，可以连续处理多个 micro-batch，仅累积梯度，最后再更新参数：

```text
micro-batch 1 → accumulate grad
micro-batch 2 → accumulate grad
...
→ optimizer step
```

若各 micro-batch 等大，累积 $K$ 次时应将各自平均损失除以 $K$，再更新一次；不等大时应按有效样本数或 token 数加权。BatchNorm、随机性和更新频率会破坏与单次大 batch 的完全等价。累积降低激活显存压力，不会消除模型、梯度和优化器状态内存。

## 14. Activation Checkpointing

普通反向传播会保存大量中间 activation。

Checkpointing 只保留部分节点，反向时重新计算缺失 activation：

```text
memory ↓
compute ↑
```

这是典型的“用额外计算换显存”。

## 15. Tensor / Pipeline Parallel 的通信本质

Tensor parallel 把单个大算子拆到多个设备，通常需要频繁 collective communication。

Pipeline parallel 把不同层放在不同 stage，通过 micro-batch 流水减少空闲，但会产生 pipeline bubble。

优化时真正需要平衡：

- compute granularity；
- communication volume；
- synchronization；
- topology；
- micro-batch count。

## 16. Parameter / Gradient / Optimizer Sharding

大模型训练的显存不只由参数决定。

将：

- parameters；
- gradients；
- optimizer states；

分散到不同 rank，可显著降低单卡内存占用。

ZeRO / FSDP 一类方法都可以从“哪些状态复制、哪些状态分片”这个统一视角理解。

## 17. MoE 与 Expert Parallelism

Mixture of Experts 每个 token 只激活少数 expert，以更低每-token 计算量使用更大的参数容量。

工程难点：

- router balance；
- token dispatch；
- all-to-all communication；
- expert capacity；
- hot expert / load imbalance。

因此 MoE 的瓶颈往往不是矩阵乘法本身，而是跨设备 token 路由。

## 18. Scaling Law 的工程意义

Scaling law 更适合被理解为：

> 在模型规模、数据规模和训练计算之间存在可测量的系统性权衡。

它可以帮助决定：

- 参数继续变大是否仍值得；
- 数据是否已经成为瓶颈；
- 固定 compute budget 如何分配。

具体拟合系数会随模型、数据和训练方法改变，不应作为长期常数写死。

## 19. 先看拓扑，再看并行策略

多机多卡系统中，GPU 之间并非等价：

- 同卡/同节点高速互联；
- 跨 socket；
- 跨节点网络。

并行策略应尽量让通信最频繁的操作发生在带宽最高、延迟最低的链路上。

来源增补：*Maths, CS & AI Compendium* Chapter 06 distributed deep learning，基准提交 `9850ee574a370bc1cde59de98b394e953775b67d`。

## 先估数量级，再比较速度

1 亿参数仅用 FP32 存权重约需 400 MB（十进制）。若梯度和 Adam 两个状态也各用 FP32，这四份合计约 1.6 GB，还没有包含激活、临时工作区和通信缓冲。

4 张卡、每卡 batch 8、累积 2 次，则一次更新有效 batch 为 $4\times8\times2=64$（无重复样本、等权损失时）。卡数翻倍并不保证耗时减半，要记录通信和数据加载。

自查：仅在 Python 发出 GPU 任务前后读时钟，为什么可能得到过小时间？**答案：**GPU 异步，主机计时可能只量到提交任务。需使用设备计时事件或在适当边界同步，并先预热；测单算子时也不要把下载数据时间混入结果。

## 从并行概念进入路由和预算计算

专家路由的可核对小程序、总参数与激活参数的区别、容量/溢出与负载目标，以及缩放经验式的约束优化进入[Transformer推理与规模设计](../../LLM%20工程实践/14-Transformer推理与规模设计.md)。固定训练预算的拟合最优点不等于服务生命周期成本最低；实际通信、分片和并行策略仍以本章的拓扑及状态视角判断。

## 20. 数据并行与梯度累加的值级合同

每个rank复制同一初始模型，处理自己的数据；DDP只同步梯度，不自动把输入切成无重复子集。实际训练用sampler/数据分片、每epoch重设相应seed，并确认重复padding数据是否计入目标。模型登记参数、optimizer更新和scheduler次数须一致，某rank提前结束还会影响collective顺序。[DDP官方说明](https://docs.pytorch.org/docs/stable/generated/torch.nn.parallel.DistributedDataParallel.html)

若本地loss是n_r个有效样本的均值，则全局平均梯度是`Σ n_r*g_r / Σ n_r`。只有各rank权重相等时无权rank平均才相同。文本的有效token数可能因padding/mask不同，即使每卡序列条数相同也不满足等权。可以按全局有效token数缩放本地sum loss；若后端all-reduce再除D，要相应补D倍，避免二次平均。最后不整除的微批同理，不能简单每个micro_loss除固定K后漏尾组。

梯度累加在一组microbatch之后只step一次，按真实样本/元素/token权重归一；在DDP中前面microbatch的forward/backward均放入`no_sync()`，最后一个同步。它减少同步次数，不必等比例减少通信墙钟，因为最后同步/重叠仍在；BN、Dropout、优化器step/clip时机可破坏与一次大batch逐位等价。

Tensor parallel的column-expand将W1输出列切开，各分片独立做逐元素激活，再对W2输入行分片的局部乘积求和。非线性若跨channel归一化或attention head间共享，不能任意切完直接局部算；先判断依赖与需要collective的边界。Bias通常只加一次，不能把每分片完整bias又求和。

```python
import copy,torch
from torch import nn
import torch.nn.functional as F
torch.set_num_threads(1);torch.manual_seed(2)
net=nn.Linear(3,2).double();X=torch.randn(7,3,dtype=torch.float64);Y=torch.randn(7,2,dtype=torch.float64)
full=copy.deepcopy(net);F.mse_loss(full(X),Y).backward();ref=[p.grad.clone() for p in full.parameters()]
local=[];counts=[]
for ids in [slice(0,2),slice(2,7)]:
    model=copy.deepcopy(net);F.mse_loss(model(X[ids]),Y[ids]).backward()
    local.append([p.grad.clone() for p in model.parameters()]);counts.append(len(X[ids]))
weighted=[sum(g[j]*n/7 for g,n in zip(local,counts)) for j in range(2)]
wrong=[sum(g[j] for g in local)/2 for j in range(2)]
assert all(torch.allclose(a,b) for a,b in zip(ref,weighted))
assert any(not torch.allclose(a,b) for a,b in zip(ref,wrong))
# Gradient accumulation over unequal microbatches: divide sums by full element count.
acc=copy.deepcopy(net)
for ids in [slice(0,2),slice(2,5),slice(5,7)]:
    (F.mse_loss(acc(X[ids]),Y[ids],reduction='sum')/Y.numel()).backward()
assert all(torch.allclose(a,p.grad) for a,p in zip(ref,acc.parameters()))
# Column-parallel expand, local nonlinearity, row-parallel contract.
x=torch.randn(2,3,dtype=torch.float64);W1=torch.randn(3,8,dtype=torch.float64);W2=torch.randn(8,3,dtype=torch.float64)
y=F.gelu(x@W1)@W2
parts=[F.gelu(x@W1[:,i:i+4])@W2[i:i+4] for i in [0,4]]
assert torch.allclose(sum(parts),y,atol=1e-12)
print('unequal-rank weighted and microbatch gradients match; naive mean maxerr',float((wrong[0]-ref[0]).abs().max()))
print('FFN column-expand/local-GELU/row-contract matches; no real collective communication')
```

本例是真实PyTorch求梯度，非均匀2/5数据分片按权平均和2/3/2微批sum归一均与7样本完整MSE一致；无权rank平均的weight梯度最大差约.2568。column-expand→local GELU→row-contract与完整FFN在容限内一致。CPU顺序计算**没有执行真实DDP、NCCL或多GPU吞吐**。

Ring all-reduce常分reduce-scatter与all-gather两阶段，各D−1轮，理想每rank传输约`2G*(D−1)/D`字节。collective可求sum或框架进一步求mean，要查具体约定；不能仅把D−1轮叫完整all-reduce。真实网络拓扑、bucket、延迟、小消息与重叠决定时间，不从字节直接乘固定收益。

## 21. 分片不是静态除法：FSDP/ZeRO与设备拓扑

参数、梯度、optimizer/master的静态预算和真实Adam dtype例子见[训练资源与数值量化](../../LLM%20工程实践/15-训练资源与数值量化实现.md)。FSDP2通常在forward之前按module-group all-gather，在选择reshard_after_forward后释放完整参数，backward前再次gather，之后reduce-scatter梯度。若forward之后保留，后向通信/峰值又不同；不是“永远只通信一次/一定三倍参数字节”。root整模型一个大group与逐block grouping的重叠和峰值差别也很大。[FSDP2官方机制](https://docs.pytorch.org/docs/stable/distributed.fsdp.fully_shard.html)

ZeRO1只分片O，ZeRO2加G，ZeRO3加P；省多少取决于实际P/G/O和D。激活、最大临时full-parameter group、通信workspace仍要留空间。将CPUOffloadPolicy参数/梯度/optimizer状态卸载到CPU，与activation offload分开；PCIe、CPU optimizer和NVMe吞吐要各自测量，不能承诺只慢30–50%。activation checkpoint不减少常驻P/G/O，模型状态本身超预算时先分片/卸载或改模型/优化器。

DP/TP/PP/EP以及sequence/context parallel可以组合，world_size的乘积只适用于明确独立的网格轴；每组成员、collective和参数所有权要画清楚。TP常需要高频低延迟通信，通常偏好节点内高速互联，但跨节点TP并非数学上禁止。EP dispatch按实际token路由，最忙expert/节点和all-to-all拓扑要计入；active参数少不意味着只需存这些权重。

总FLOPs粗算6ND只用于特定dense主矩阵近似，MoE总/active参数、长上下文attention、重算及真实硬件效率应另算。训练目标、数据质量与充分训练先用[规模设计](../../LLM%20工程实践/14-Transformer推理与规模设计.md)拟合范围判断；租用价格、固定GPU小时、某一厂商成本不能作长期教材常数。

## 22. GPipe与1F1B：合法事件、bubble与活跃激活

P个stage，M个microbatch；F(s,m)需前一stage相同m前向结果，B(s,m)需本地F及后一stage相同m的梯度，每stage设备资源不得执行两个不可重叠kernel。GPipe是多microbatch填满前向流水后再反向的fill-drain，不是“一个microbatch跑完全部F/B才下一个”。1F1B先按rank位置warmup，再交错一前一后，最后cooldown；所有梯度完成才step，保持本次iteration的参数版本一致。

在等F/B单位耗时、均衡stage、零通信的简单fill-drain模型中，总时间2(M+P−1)，每stage有效工作2M，所以idle fraction为`(P−1)/(M+P−1)`。`(P−1)/M`是相对有效工作额外比例的一种近似，不是总时间idle fraction。1F1B常降低同时活跃的activation，却不保证这个均匀模型的bubble更少。

```python
from collections import defaultdict

def simulate(P,M,schedule):
    assert type(P) is type(M) is int and min(P,M)>0 and schedule in ('gpipe','1f1b')
    plans=[]
    for s in range(P):
        if schedule=='gpipe':plan=[('F',m) for m in range(M)]+[('B',m) for m in reversed(range(M))]
        else:
            warm=min(P-s-1,M);plan=[('F',m) for m in range(warm)]
            for m in range(M-warm):plan.extend([('F',warm+m),('B',m)])
            plan.extend(('B',m) for m in range(M-warm,M))
        plans.append(plan)
    cursor=[0]*P;done={};events=[];live=[0]*P;peak=[0]*P;t=0
    while any(cursor[s]<len(plans[s]) for s in range(P)):
        chosen=[]
        for s in range(P):
            if cursor[s]==len(plans[s]):continue
            kind,m=plans[s][cursor[s]];deps=[]
            if kind=='F' and s:deps.append(('F',s-1,m))
            if kind=='B':
                deps.append(('F',s,m))
                if s<P-1:deps.append(('B',s+1,m))
            if schedule=='gpipe' and kind=='B':deps.extend(('F',P-1,j) for j in range(M))
            if all(d in done and done[d]<=t for d in deps):chosen.append((kind,s,m,deps))
        assert chosen,'deadlock in supplied stage order'
        for kind,s,m,deps in chosen:
            assert all(done[d]<=t for d in deps)
            events.append((kind,s,m,t,t+1));done[(kind,s,m)]=t+1;cursor[s]+=1
            live[s]+=1 if kind=='F' else -1;peak[s]=max(peak[s],live[s]);assert live[s]>=0
        t+=1
    assert live==[0]*P
    assert len(events)==2*P*M
    # One device-resource per stage: no overlapping events; dependency checks above.
    for s in range(P):
        intervals=[(a,b) for _,r,_,a,b in events if r==s]
        assert all(a2>=b1 for (_,b1),(a2,_) in zip(intervals,intervals[1:]))
    bubble=1-(2*P*M)/(P*t)
    return events,t,bubble,peak
for mode in ['gpipe','1f1b']:
    ev,T,bub,peak=simulate(4,8,mode);print(mode,'virtual makespan',T,'idle fraction',round(bub,4),'peak live activations',peak)
    print('rank0',[(k,m,a) for k,s,m,a,b in ev if s==0])
# Balanced fill/drain formula is idle/(total), not (P-1)/M.
assert abs(simulate(4,8,'gpipe')[2]-3/11)<1e-12
assert max(simulate(4,8,'1f1b')[3])<max(simulate(4,8,'gpipe')[3])
```

程序构造两种完整per-stage工作序列，逐时隙检查真实前后依赖与资源互斥，计算在每stage尚待反向的microbatch数量。P4/M8两种makespan均22、idle fraction均3/11≈27.27%；GPipe峰值每stage8组、1F1B为[4,3,2,1]。这直接回答“1F1B如何省activation”，没有将相同总时间包装成加速。没有模拟非均匀kernel、通信、GPU或optimizer step。

## 23. DualPipe：分块重叠与双向流水的实际条件

DualPipe针对MoE计算与跨节点通信，原报告把每个F/B chunk分为attention、all-to-all dispatch、MLP、all-to-all combine，另有PP点对点通信；backward的attention/MLP又区分input-gradient B和weight-gradient W。input-gradient要及时发上游，weight-gradient可推迟到不阻塞上游的空闲窗口，但必须在optimizer/全局grad norm等依赖前完成。[DeepSeek-V3 §3.2.1](https://arxiv.org/abs/2412.19437)

不仅是“两个forward同时占同一GPU”。原Figure4给出一对F/B内计算/通信重排及SM资源分配；Figure5是双端注入、相反方向stream的完整8rank/20microbatch schedule。重叠需要有可并行的计算/通信资源、依赖满足、内核/链路并发能力；两者争带宽/SM时不能把两段时间直接取max。来源手画F/F重叠表没有这些资源证明，不能当真实schedule。

下面保存两条microbatch的attention→dispatch→MLP→combine依赖，分别以单一资源和独立compute/comm资源排程，验证所有事件。它是**重叠机制的CPU离散例，不是DualPipe复现**，不伪造真实pipeline、EP或all-to-all kernel。

```python
# A two-resource operation graph: compute and communication. NOT DualPipe replay.
# The two independent microbatches allow comm(A) to overlap compute(B).
ops={'attnA':('compute',2,[]),'dispatchA':('comm',3,['attnA']),
     'mlpA':('compute',2,['dispatchA']),'combineA':('comm',2,['mlpA']),
     'attnB':('compute',2,[]),'dispatchB':('comm',3,['attnB']),
     'mlpB':('compute',2,['dispatchB']),'combineB':('comm',2,['mlpB'])}
def run(order,share_resource):
    end={};free={'compute':0,'comm':0,'all':0};events=[]
    for name in order:
        res,dur,deps=ops[name];res='all' if share_resource else res
        assert all(d in end for d in deps)
        start=max([free[res]]+[end[d] for d in deps]);finish=start+dur
        events.append((name,res,start,finish));free[res]=finish;end[name]=finish
    # Validate resources and dependencies, not arithmetic-only speedup label.
    for name,res,a,b in events:
        assert all(end[d]<=a for d in ops[name][2])
        assert all(max(a,aa)>=min(b,bb) for n,r,aa,bb in events if r==res and n!=name)
    return events,max(end.values())
order=['attnA','dispatchA','attnB','dispatchB','mlpA','combineA','mlpB','combineB']
serial,T0=run(order,True);overlap,T1=run(order,False)
assert T1<T0
print('virtual single/two independent resource makespans',T0,T1,'events',overlap)
# If communication steals compute bandwidth/SMs, this two-resource bound is optimistic.
P=8;F=2.;B=4.;W=1.;FB=5.
b1=(P-1)*(F+B);bd=(P/2-1)*(FB+B-3*W)
print('declared paper chunk times: bubble time 1F1B/DualPipe',b1,bd)
```

在已声明durations下，虚拟单资源18、两资源12；真实设备需测同步开销、争用和critical path。纸面bubble time依赖F/B/W/F&B。例如原Table2给1F1B `(P−1)(F+B)`，DualPipe `(P/2−1)(F&B+B−3W)`，还需满足调度及chunk假设。F&B是实际重叠后两chunk时间，不能未经profile就取F或B，更不能把源`bubble_dualpipev=1.2*bubble_dualpipe`当规律。

### 23.1 参数副本、DualPipeV与公平比较

[官方DualPipe README](https://github.com/deepseek-ai/DualPipe)以**相同PP stage数量**比较：DualPipe与DualPipeV每device参数均为2×、activation为P+1，使用同bubble表达式；device数量分别P与P/2。DualPipeV的cut-in-half减少总体复制/设备，不等于“每device一个stage而DualPipe两个”。保持相同device数时PP stages也改变，必须重新比较，而不是把不同基准的1×/2×拼在表里。

示例dense N70B、P8，按该比较基准每device `2N/P=17.5B`参数，低精度2byte仅参数35GB。DualPipe用8device，总参数载荷140B；DualPipeV用4device，总70B。若固定8device比较，则V可以对应16stage，每device载荷又不同。MoE专家经EP分散后，重复部分的**每device实际存储**与expert/dense权重构成有关；不能用37B active代替671B total，必须查网格和所有权。

原报告要求PP stage和microbatch均为偶数，而不要求M整除P或2P；这是其相对Chimera的一项区别。另一项是所述设计下activation和绝对bubble不会随M增长。传统fill/drain的绝对warmup/cooldown bubble也有固定部分，不能笼统说“1F1B bubble必随M增长而DualPipe独有常数”；比例和绝对时间分开。没有固定500/1000GPU或1Btoken的适用门槛。

真实应用还需模型自定义`overlapped_forward_backward`、通信kernel、参数/梯度复制和一致更新；CPU列表不提供这些。该课正文注册动态图其实是固定SHARE与floor容量的MoE overflow图，没有DualPipe排程；容量的floor/ceil及top-k派发约定需明确，机制主入口留在工程14路由章节。源主程序只是启发式bubble公式，SVG列出的利用率/回收GPU-hours是同类假设推算，不是测量。本文不保留95%GPU利用率或“回收能再训70B”的效果保证。

分布式05五题：

1. checkpoint加入budget时只减对应activation，不能减P/G/O；重算次数、梯度及RNG看数值15。完整step3F→4F是特定额外33%，不是实际墙钟承诺。
