# 06｜计算性能与并行训练

> 先做过一次训练再学，第一遍仅看计时、显存组成、梯度累积；多机并行是进阶选读，不作为开始深度学习的前置条件。

## 1. 深度学习性能的基本视角

训练速度不是单一 FLOPs 问题，而是：

```text
算法
+ 计算图
+ kernel
+ 内存访问
+ host/device 传输
+ 通信
+ 数据管线
```

任何一层都可能成为瓶颈。

## 2. 命令式与符号/编译执行

命令式执行易调试、控制灵活；图编译/符号执行有机会做：

- op fusion；
- constant folding；
- memory planning；
- kernel selection；
- device scheduling。

现代框架已经越来越趋向“动态图开发 + 编译器优化执行”的混合方式。

## 3. 异步计算

GPU kernel 启动通常异步，CPU 发出任务后不一定立即等待完成。

这意味着：

- 计时必须显式同步；
- Python 代码结束不代表 GPU 已完成；
- host-device copy 可能隐式同步。

错误的 benchmark 很容易把排队时间和执行时间混在一起。

## 4. 自动并行

独立操作可以在不同资源上并行，但实际收益取决于：

- 数据依赖；
- kernel 粒度；
- stream；
- memory bandwidth；
- 调度开销。

“可以并行”不等于“实际更快”。

## 5. 硬件层瓶颈

需要建立 Roofline 式直觉：

- compute-bound：算力限制；
- memory-bound：内存带宽限制；
- communication-bound：多卡通信限制。

矩阵乘法通常更容易利用加速器；大量小 kernel、索引、数据搬运往往效率低。

## 6. 数据并行

最常见多 GPU 训练方式：

```text
复制模型
→ 每卡处理不同 mini-batch
→ 计算局部梯度
→ All-Reduce 聚合
→ 同步更新
```

关键约束：

- 每卡 batch；
- 梯度同步通信；
- load balance；
- 通信与计算重叠。

## 7. 模型并行

当单卡放不下模型时，需要把不同参数/层拆到不同设备。

现代扩展包括：

- tensor parallel；
- pipeline parallel；
- sequence/context parallel；
- expert parallel；
- parameter/optimizer sharding。

D2L 的多 GPU 基础应理解为这些方法的前置概念。

## 8. 参数服务器

Parameter Server 把参数聚合放在中心或分片 server 上，是分布式训练的重要历史架构。

现代大规模 GPU 集群更多使用高效 collective communication，但参数服务器思想仍适用于理解：

- 参数所有权；
- 同步/异步更新；
- stale gradient；
- 带宽瓶颈。

## 9. 内存构成

训练显存不只是参数：

```text
parameters
+ gradients
+ optimizer states
+ activations
+ temporary buffers
+ communication buffers
```

大模型训练中 activations 与 optimizer states 往往非常可观。

## 10. 提升性能的顺序

建议：

1. profiler 定位瓶颈；
2. 提高 batch/算子利用率；
3. 修复数据加载；
4. mixed precision；
5. 减少同步和数据搬运；
6. kernel fusion / compile；
7. 再考虑多卡扩展。

在单卡都没有跑好之前直接堆 GPU，通常只会扩大低效率。

## 11. benchmark 原则

性能测试必须明确：

- warmup；
- synchronization；
- batch size；
- dtype；
- sequence/image size；
- hardware；
- software version；
- 是否含数据加载；
- throughput vs latency。

否则数字几乎不可比较。

## 12. Compendium 补充：Mixed Precision

Mixed precision 的目标是：

> 在不明显损害训练稳定性的前提下，降低显存、提高矩阵计算吞吐。

常见 dtype：

- FP32：范围和精度较高；
- FP16：吞吐高，但数值范围较小；
- BF16：指数范围接近 FP32，通常更容易训练稳定。

FP16 训练中可能需要 loss scaling，防止很小的 gradient underflow。优化器状态或关键累加仍可能保留更高精度。

## 13. Gradient Accumulation

当显存放不下目标 global batch 时，可以连续处理多个 micro-batch，仅累积梯度，最后再更新参数：

```text
micro-batch 1 → accumulate grad
micro-batch 2 → accumulate grad
...
→ optimizer step
```

若各 micro-batch 等大，累积 $K$ 次时应将各自平均损失除以 $K$，再更新一次；不等大时应按有效样本数或 token 数加权。BatchNorm、随机性和更新频率会破坏与单次大 batch 的完全等价。累积降低激活显存压力，不会消除模型、梯度和优化器状态内存。

## 14. Activation Checkpointing

普通反向传播会保存大量中间 activation。

Checkpointing 只保留部分节点，反向时重新计算缺失 activation：

```text
memory ↓
compute ↑
```

这是典型的“用额外计算换显存”。

## 15. Tensor / Pipeline Parallel 的通信本质

Tensor parallel 把单个大算子拆到多个设备，通常需要频繁 collective communication。

Pipeline parallel 把不同层放在不同 stage，通过 micro-batch 流水减少空闲，但会产生 pipeline bubble。

优化时真正需要平衡：

- compute granularity；
- communication volume；
- synchronization；
- topology；
- micro-batch count。

## 16. Parameter / Gradient / Optimizer Sharding

大模型训练的显存不只由参数决定。

将：

- parameters；
- gradients；
- optimizer states；

分散到不同 rank，可显著降低单卡内存占用。

ZeRO / FSDP 一类方法都可以从“哪些状态复制、哪些状态分片”这个统一视角理解。

## 17. MoE 与 Expert Parallelism

Mixture of Experts 每个 token 只激活少数 expert，以更低每-token 计算量使用更大的参数容量。

工程难点：

- router balance；
- token dispatch；
- all-to-all communication；
- expert capacity；
- hot expert / load imbalance。

因此 MoE 的瓶颈往往不是矩阵乘法本身，而是跨设备 token 路由。

## 18. Scaling Law 的工程意义

Scaling law 更适合被理解为：

> 在模型规模、数据规模和训练计算之间存在可测量的系统性权衡。

它可以帮助决定：

- 参数继续变大是否仍值得；
- 数据是否已经成为瓶颈；
- 固定 compute budget 如何分配。

具体拟合系数会随模型、数据和训练方法改变，不应作为长期常数写死。

## 19. 先看拓扑，再看并行策略

多机多卡系统中，GPU 之间并非等价：

- 同卡/同节点高速互联；
- 跨 socket；
- 跨节点网络。

并行策略应尽量让通信最频繁的操作发生在带宽最高、延迟最低的链路上。

## 先估数量级，再比较速度

1 亿参数仅用 FP32 存权重约需 400 MB（十进制）。若梯度和 Adam 两个状态也各用 FP32，这四份合计约 1.6 GB，还没有包含激活、临时工作区和通信缓冲。

4 张卡、每卡 batch 8、累积 2 次，则一次更新有效 batch 为 $4\times8\times2=64$（无重复样本、等权损失时）。卡数翻倍并不保证耗时减半，要记录通信和数据加载。

自查：仅在 Python 发出 GPU 任务前后读时钟，为什么可能得到过小时间？**答案：**GPU 异步，主机计时可能只量到提交任务。需使用设备计时事件或在适当边界同步，并先预热；测单算子时也不要把下载数据时间混入结果。
