# 开发环境、编辑器与依赖复现

先修：能够在终端运行一个 Python 文件。本章把“安装了软件”变为“知道代码在哪个环境运行、能在干净环境重建”。模块与包本身见[Core 06](../Core/06-Modules-and-Packages.md)，发布和 CI 见[Core 17](../Core/17-DevOps.md)。

## 1. 按故障所在层理解环境

| 层 | 提供什么 | 检查例子 | 常见故障 |
|---|---|---|---|
| 操作系统与设备 | 文件、进程、编译工具、硬件驱动 | `uname -m`、`git --version` | ARM/x86 混用、驱动或文件权限 |
| 语言解释器/运行时 | 执行 Python、Node 等程序 | `python3 --version`、`node --version` | 命令指向另一版本 |
| 包管理与环境 | 把依赖装入指定解释器 | `python -m pip --version` | pip 与 python 不配套 |
| 任务依赖 | NumPy、PyTorch、SDK 等 | `import numpy` | 模块缺失、二进制或版本不兼容 |

这是诊断分层，不表示必须先装完所有层的所有工具。矩阵入门先需 Python/NumPy；写 TypeScript 工具再需要 Node 与相应执行工具；Rust/Julia 等仅在选用该实现时安装。GPU 是可选分支，不是进入课程的门槛。

“命令存在”“模块可导入”“算子能运行”“模型结果正确”是四种证据。`find_spec('torch')` 只能发现模块，导入时仍可能因二进制不兼容失败。

## 2. 一个不用安装新包的环境检查

把下面代码保存为 `check_env.py`，从项目目录运行 `python3 check_env.py`：

```python
import importlib
import json
import platform
import shutil
import sys

result = {
    "解释器": sys.executable,
    "Python": platform.python_version(),
    "系统": platform.system(),
    "架构": platform.machine(),
    "虚拟环境": sys.prefix != sys.base_prefix,
    "Git路径": shutil.which("git"),
}
try:
    np = importlib.import_module("numpy")
    result["NumPy"] = np.__version__
    result["点积检查"] = int(np.dot([1, 2, 3], [1, 2, 3]))
except ImportError as exc:
    result["NumPy状态"] = f"本路线需要时再安装：{type(exc).__name__}"
print(json.dumps(result, ensure_ascii=False, indent=2))
```

装有 NumPy 时点积为 14；版本、路径和架构取决于机器。本例不把可选库缺失当全课程失败。出现其他导入异常时保留堆栈，它可能指向系统库，而不只是没安装包。

## 2.1 其他语言工具链：能运行最小程序再进入对应路线

Node.js执行JavaScript，TypeScript通常还需要编译或适用的类型擦除/运行工具；不能只因node存在就断言任意TypeScript项目可运行。pnpm管理项目包，`package.json`声明依赖与脚本，锁文件记录解析结果，`node_modules`是可重建安装目录。

已有受支持Node与pnpm时，可在新的练习目录准备TypeScript示例：

```bash
mkdir ts-lab
cd ts-lab
pnpm init
pnpm add -D typescript tsx
```

保存 `hello.ts`：

```typescript
const values: number[] = [1, 2, 3];
console.log("求和：", values.reduce((a, b) => a + b, 0));
```

运行 `pnpm exec tsx hello.ts`，预期求和6。提交声明、必要源文件和锁；复建时按锁使用相应安装选项，例如pnpm的 `install --frozen-lockfile`。这些安装步骤未在本次对你的环境执行。运行成功不代表静态类型检查已完成，后者需单独配置/执行。

Rust的 `rustc` 是编译器，Cargo管理工程、依赖、构建和测试。已有Rust时：

```bash
cargo new rust-lab
cd rust-lab
cargo run
```

可以把 `src/main.rs` 改为 `fn main() { println!("求和：{}", 1 + 2 + 3); }`；输出6。应用通常提交Cargo.toml与锁，构建目录不入Git。编译器目标架构、原生链接库和运行平台也影响二进制可用性。

Julia为可选替代实现，已有Julia时 `julia -e 'println(sum([1,2,3]))'` 输出6。项目用Project.toml声明，Manifest.toml记录解析结果；`julia --project=.`选择项目后，由Pkg按声明管理依赖，不能把全局环境与项目环境混用。

没有对应运行时就先记录未准备，不为了完成一课安装所有语言。获取入口为各工具官方站点；源教程的远程安装脚本、固定Node版本和性能倍数不作为所有机器的默认步骤。

macOS Apple Silicon还需检查终端是否经Rosetta运行、包管理器和二进制是否为预期架构。`uname -m`、`arch`和可执行文件信息是证据；ARM主机、x86进程、两套安装前缀混用时，先决定哪条环境路径，再修对应配置，不盲目把别人的shell初始化行追加到个人配置。

## 3. 解释器、pip、Notebook 内核必须指向同一环境

```bash
python3 -m venv .venv
# macOS/Linux 的 bash 或 zsh
source .venv/bin/activate
python -c 'import sys; print(sys.executable)'
python -m pip --version
```

Windows PowerShell 激活为 `.\.venv\Scripts\Activate.ps1`，命令提示符为 `.venv\Scripts\activate.bat`。也可直接运行环境中的解释器，不依赖激活脚本。

激活改变当前 shell 的查找路径；编辑器和 Notebook 内核不会必然同步切换。先在编辑器选择解释器，再在 Notebook 中查看 `sys.executable`。提示符出现 `(.venv)` 不是充分证据。

环境目录不是跨机器可搬运的安装包：路径、平台 wheel、动态库都可能变化。提交项目声明和锁文件，重建环境；`.venv/` 放入 `.gitignore`。

## 4. uv 的两种使用方式不要混淆

已有环境中使用 pip 风格接口：

```bash
uv venv
uv pip install numpy
```

以项目为单位声明与同步依赖：

```bash
uv init study-lab
cd study-lab
uv add numpy
uv lock --check
uv sync --locked
uv run --locked python -c 'import numpy as np; print(np.arange(3))'
```

后者会维护 `pyproject.toml` 和 `uv.lock`。`uv pip install` 本身不等于更新项目依赖声明。`--locked` 要求锁与项目声明一致，否则报错；`--frozen` 跳过锁是否过期的检查，不能当成同义词。安装是获取依赖的动作，不是本文在你的机器上已执行的动作。

`uv sync` 默认移除不在所选依赖集里的包，因此不要往它维护的环境随意手装额外包，再期待它永久保留。实验、测试、模型服务可用依赖组/可选 extras 分开；只有出现真实冲突才拆环境，不必机械“每课一个环境”。

## 5. 项目声明、锁文件与复现的边界

```toml
[project]
name = "study-lab"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = ["numpy"]

[project.optional-dependencies]
notebook = ["jupyterlab", "ipykernel"]
```

这里版本范围是示例，不是部署锁。项目声明表达“接受什么依赖”，锁文件记录解析结果；可安装的库还需合适的构建后端和包目录，不能只写此片段就宣称包已可分发。

`requirements.txt` 仍有部署、导出锁结果等用途；`pyproject.toml` 不自动替代所有格式。锁可以降低依赖漂移，但不能固定操作系统、驱动、硬件、数据、模型 revision 或浮点执行顺序。跨平台可能选用不同 wheel 或环境标记分支。

复现清单至少记录：解释器版本和路径、系统/架构、框架与驱动、依赖声明/锁、代码提交、数据校验值、模型 revision、随机种子及实际运行命令。

## 6. conda 与 pip：明确管理边界

conda 适合同时管理 Python 与一些非 Python 库。需要 pip-only 包时，可先完成 conda 安装，再用这个环境的 `python -m pip` 安装剩余包；它不是一律禁止混用。混用后 conda 的求解器不一定掌握全部 pip 状态，后续大幅改动优先新建并重建环境。

虚拟环境通常不能隔离主机 GPU 驱动。`nvidia-smi` 显示的 CUDA 能力也不等于安装的 toolkit 版本。具体关系见[跨硬件部署](../../LLM%20工程实践/09-跨硬件部署.md)。

## 7. 编辑器的五项验收

编辑器选择看任务能力：语言诊断、格式化、终端、Notebook、远程调试。不同产品不需要各保存一套重复配置。

1. 打开项目目录，明确工作目录；直接打开单个文件可能丢失项目配置。
2. 选择正确 Python 解释器；终端、运行按钮和调试器分别核对。
3. 开启类型诊断；普通静态类型检查通常不能证明任意运行时张量 shape 正确。
4. 只选一个默认 Python 格式化器，避免两个格式化器来回改动；格式化不等于测试通过。
5. 保存文件、运行最小样例，检查终端路径和输出；自动保存不是远端提交。

VS Code 的示意配置：

```json
{
  "python.analysis.typeCheckingMode": "basic",
  "editor.formatOnSave": true,
  "notebook.output.scrolling": true,
  "[python]": {"editor.defaultFormatter": "charliermarsh.ruff"}
}
```

它要求已安装对应扩展；设置本身不会安装解释器或 Ruff。LSP 在编辑器与语言服务器间传递补全/诊断，调试器处理程序运行控制，两者不同。Notebook 格式化、断点和变量显示也是不同能力。

远程编辑时，界面在本机，语言服务、文件和执行环境主要在远端；“本机已装包”不意味着远端已装包。远程作业与 SSH 见[远程实验管理](../../计算机科学基础/08-Linux系统与运维/09-远程实验进程与日志管理.md)。

## 8. 排错与练习

| 症状 | 先获取的证据 | 处理方向 |
|---|---|---|
| 安装成功却不能 import | 安装命令使用的解释器和 `sys.executable` | 在同一解释器重新确认安装 |
| 本机可以、远端不行 | 系统/架构/锁、数据路径、驱动 | 分层定位，不先全局升级所有包 |
| MPS/CUDA 为 False | 当前平台、torch 构建、驱动及库导入错误 | 不能直接认定没有 GPU |
| 全局安装被拒绝 | 是否系统管理 Python | 使用独立环境，避免强制覆盖系统组件 |

练习：新建两个空环境，不安装包，分别输出 `sys.prefix` 和 `sys.base_prefix`；说明为何路径不同不代表系统 Python 被复制成完整独立操作系统。答案：环境改变解释器与依赖查找位置，仍共享操作系统、设备和外部资源。

练习：项目锁未改，模型下载使用 `main`，实验结果变化是否证明锁失效？答案：不一定，模型资产或数据可能漂移，需固定 revision 和输入再比较。

## 9. 实际复盘：同版本不代表同一二进制环境

本任务的临时验证环境曾把PyPI的PyTorch与原基础环境的NumPy动态库混用，导入出现 `OMP: Error #15`，提示OpenMP运行库重复初始化。先分别测试框架、查看实际导入路径与构建来源，再在临时目录使用相互匹配的PyPI NumPy/SciPy轮子；CPU导入、梯度与小数据转换通过，没有改变用户全局环境。

```python
import sys
import numpy as np
print("解释器：", sys.executable)
print("NumPy版本与路径：", np.__version__, np.__file__)
```

这里的可复用经验是：版本号只是复现信息的一部分，还要看架构、wheel/conda等构建渠道、原生依赖和加载路径。遇到实际冲突时用干净且一致的环境重建，不把设置 `KMP_DUPLICATE_LIB_OK`、关闭错误检查当成正确性验证。相同版本在不同平台仍可能选不同二进制，本文的CPU烟测不保证所有库组合永久兼容。
