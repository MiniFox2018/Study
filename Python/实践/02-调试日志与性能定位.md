# 调试、日志与性能定位

先修：函数、异常、简单数组。语言异常基础见[Core 09](../Core/09-Exceptions-and-Debugging.md)，本章侧重长时间实验中的静默错误和资源证据。先确认结果正确，再优化耗时。

## 1. 三层问题使用不同证据

| 层 | 需要确认 | 典型证据 |
|---|---|---|
| Python与输入 | 控制流、字段、资源和异常 | 最小输入、堆栈、断点、日志 |
| 张量与数值 | shape、dtype、device、有限值、梯度 | 张量摘要、不变量、逐层shape、有限差分 |
| 训练过程 | 数据切分、损失/指标、优化行为 | 训练与验证曲线、基线、参数/梯度变化 |

没有错误堆栈不代表正确；高准确率也不能直接判为泄漏，它是需要检查的数据和评价信号。源站“80%在某层”“读取占60%”及动态火焰图比例是示意，不作为你的机器实测。

## 2. 从小输入建立不变量

下面演示“能算完，但算错形状”：

```python
import numpy as np

prediction = np.array([[1.0], [2.0], [3.0]])
target = np.array([1.0, 2.0, 3.0])
bad = prediction - target
assert bad.shape == (3, 3)  # 广播形成了所有交叉差，而不是逐样本残差。
target_column = target.reshape(-1, 1)
good = prediction - target_column
assert good.shape == (3, 1)
assert float((good ** 2).mean()) == 0.0
print("正确残差形状：", good.shape)
```

看损失曲线前先写清输入、目标、输出、损失是否为预期标量。合法广播造成的静默错误，调试器不会自动替你理解任务语义。

## 3. 可运行的日志与阶段计时

```python
import logging
import time
from contextlib import contextmanager

logging.basicConfig(level=logging.INFO, format="%(levelname)s %(message)s")
logger = logging.getLogger("study")

@contextmanager
def stage(name):
    start = time.perf_counter()
    try:
        yield
    except Exception:
        logger.exception("阶段失败：%s", name)
        raise
    finally:
        logger.info("阶段结束：%s，耗时=%.6f秒", name, time.perf_counter() - start)

with stage("求和"):
    result = sum(range(1000))
assert result == 499500
print("结果：", result)
```

耗时没有固定答案；结果499500才是此例的不变量。入口配置handler，模块只取logger，避免导入多个模块重复写日志。日志保留运行ID、阶段、结果、耗时和错误类别，不输出密钥、完整敏感数据或任意全部模型输入。

## 4. 断点如何缩小失败现场

`breakpoint()` 进入配置的Python调试器，常见 pdb 命令：`p 表达式` 查看值、`n` 执行下一行、`s` 进入函数、`where` 查看栈、`c` 继续、`q` 退出。先用两条记录练习，再用于长循环。

条件断点应反映不变量：比如本应有限的损失变成NaN/Inf、维度不符，而不是对所有任务硬编码“loss>10”。在自动任务中不要无条件放断点，它可能一直等待人工输入；调试代码与生产失败策略要分开。

## 5. 调试器配置与实际执行环境

VS Code 的示意配置：

```json
{
  "version": "0.2.0",
  "configurations": [{
    "name": "调试当前练习",
    "type": "debugpy",
    "request": "launch",
    "program": "${file}",
    "console": "integratedTerminal",
    "justMyCode": true
  }]
}
```

需要相应扩展和正确解释器。`justMyCode=false` 可进入依赖代码，堆栈会更复杂。断点查看变量和执行控制，不等于Notebook的旧输出或静态类型提示。

## 6. profiler测量的是资源，不是正确性

对自己准备的小脚本使用：

```bash
python -m cProfile -s cumulative practice.py
```

`cumtime` 含子调用耗时，`tottime` 更侧重函数本身。一个调用树上父/子累计时间不能直接相加，否则重复计数。按结果正确的同一输入比较，避免把读取缓存与冷下载当成同一工作。

逐行定位可用 `line_profiler` 的装饰器/runner组合，或有文档支持的分析接口；`@profile` 不属于普通Python内置名字，需要工具提供。采样火焰图宽度通常表示累计样本/时间权重、纵向表示调用栈，具体看工具；横向位置通常不是严格时间轴。

CPU解释器profiler可能主要看到GPU提交操作，真实GPU工作是异步的；设备事件和同步计时见[跨硬件部署](../../LLM%20工程实践/09-跨硬件部署.md)。

## 7. 三类内存指标不能互换

```python
import tracemalloc

tracemalloc.start()
before = tracemalloc.take_snapshot()
data = [bytearray(1024) for _ in range(100)]
after = tracemalloc.take_snapshot()
for item in after.compare_to(before, "lineno")[:3]:
    print(item)
assert len(data) == 100
tracemalloc.stop()
```

观察主要分配位置，不把显示字节设成跨版本固定答案。`tracemalloc` 追踪它能记录的分配，不是全部进程RSS、所有原生库缓冲或CUDA显存。进程级指标可由操作系统或 `memory_profiler` 的相应后端观察，需说明后端和采样精度。

NumPy `nbytes` 是元素载荷；视图共享底层数据。PyTorch 的 allocated 为实际活张量相关分配，reserved 是分配器保留空间；二者差异不是自动证明内存泄漏。`empty_cache()` 不释放仍被活对象引用的张量，不能让过大的模型神奇装下。

## 8. 转入张量与模型诊断

[张量框架与模型调试](../../AI%20算法基础/深度学习专题/18-张量框架与模型调试.md)集中维护张量图、广播VJP、PyTorch登记/模式/数据/恢复、JAX显式状态/随机key/jit，以及训练排错。不要分别在日志章和框架章维护两份长期训练模板。

排错交接应保留：预期结果、最小输入、shape/dtype/device、异常或首次非有限值、样本与目标定义、实际版本、一步参数更新证据、已尝试改动。若只有“loss不降”而没有这些证据，不能给出唯一根因。

框架章提供可运行CPU反例：detach导致参数没有梯度/没有更新，修复后有更新；float64光滑gradcheck；不等大小微批梯度与整批核对；小批拟合与hook移除。广播基础继续由本章第2节与数学张量章解释，不再重复长推导。

## 9. 诊断工具不能改变要测的问题

`.item()`、回CPU、频繁打印会同步设备，hooks/异常检测/密集直方图有成本；先用它们定位，再关闭后测真实性能。统计None/0/NaN梯度、空张量、复数或多层tuple/dict输出时，应按实际类型处理，而不是默认任何输出都是单张量。

train/eval管理某些层行为，no_grad/inference_mode管理梯度记录，不能混为一条开关。保存loss或激活时有目的地取标量或detach数值；主梯度路径随意detach会产生“运行但不学习”的错误。具体证据、示例与失败条件见框架章第11～14节。

tracemalloc、进程RSS、设备allocated/reserved分别回答不同内存问题；上游固定“80%错误”“60%读取”“死神经元50%”等仅作候选提示，不能当当前机器或任意任务测量。结果正确、实验边界正确和性能好是三个不同验收层。

## 10. 最小实践与答案

先运行广播例子 → 修正shape并核对loss → 加日志/阶段计时 → cProfile查看同输入 → tracemalloc观察Python分配 → 设置基于不变量的条件断点。随后再进入框架章的小模型失败/修复实验。

1. 程序更快但输出由正确变错，算优化成功吗？**答案：**不算，先满足结果契约。
2. 图像训练的读取真的占60%吗？**答案：**先测实际工作负载；源站火焰图比例是教学构造。
3. 梯度为0一定是程序坏了吗？**答案：**不一定；查看当前局部函数、未用分支、冻结与收敛状态，再核对图和更新。
4. loss出现NaN是否先给所有log和分母加epsilon？**答案：**先找首次非法值及定义域，epsilon会改变式子且对负log输入未必有效。
5. 小批记不住就证明代码bug吗？**答案：**还须检查容量、冲突标签、正则、学习率/预算；通过也仅证明此批可拟合。
