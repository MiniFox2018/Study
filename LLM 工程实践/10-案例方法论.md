# 10｜案例方法论

`self-llm` 的几个案例比“照着命令部署模型”更有长期价值，因为它们展示了如何从真实需求反推数据和训练方案。

## 1. 角色风格模型

角色模仿类案例的核心不是 LoRA，而是：

> **怎样把角色特征转化为可学习数据。**

数据需要覆盖：

- 语言习惯；
- 语气；
- 场景；
- 人物关系；
- 拒绝边界；
- 多轮一致性。

### 风险

如果只抽取经典台词，模型容易：

- 复读；
- 模板化；
- 无法泛化到新场景。

需要把原始语料转换成“任务—回答”训练样本。

## 2. 领域问答

例如数学类领域模型。

需要区分：

- 领域知识；
- 解题过程；
- 最终答案；
- 格式。

如果知识需要经常更新，RAG 可能比参数微调更合适。

如果需要形成稳定推理格式，SFT / RL 才更有价值。

## 3. 个人数字分身

个人表达风格建模核心在数据。

需要特别关注：

- 隐私；
- 数据授权；
- 身份冒充；
- 敏感记忆；
- 删除机制。

工程上应把：

```text
稳定表达规则 → 先用 Prompt/示例；确有需要再训练
动态个人事实 → 经授权的 Memory / RAG
```

分开。

## 4. 综合应用系统

复杂案例通常会组合：

- Prompt；
- RAG；
- Agent；
- SFT；
- UI / API。

这说明真实系统不应强行用单一技术解决所有问题。

## 5. 案例设计模板

### 目标

要改变什么？

### 基线

原模型哪里不够？

### 数据

需要什么样本？

### 方法

Prompt / RAG / LoRA / Full FT / DPO / RL？

### 评测

如何证明改进？

### 部署

实际怎么用？

### 迭代

Bad Case 如何回流？

## 6. 最重要结论

学习项目可以以“理解 LoRA”为目标，产物是能解释、运行并修改小实验；应用项目则应从“系统在哪些可重复场景下失败”开始。两种目标应分别验收，教学实验成功不等于解决了真实业务问题。

然后选择最小、最可验证的改动。

## 7. 一个完整但很小的案例设计

**目标**：本地文档问答回答“请假申请需要哪些材料”，并标出证据段。**基线**：直接把现行制度全文放入上下文；如果全文足够短且表现可靠，暂不建向量库。**失败样例**：旧制度混入、同名条款、文档缺答案、用户无访问权限。

若输入过长才引入检索，记录每个问题应召回的证据 ID；若检索正确却回答错误，修改上下文组织或生成约束；若找不到答案，要求明确证据不足。评测时分别核对证据命中、答案正确、引用对应、权限遵守与成本，而不是只保存一段看起来不错的演示。

**自检**：基线已经能答对全部练习题，还要不要加入微调？

**核对**：应用目标下先停止增加复杂度；扩大有代表性的验证，确认实际需求是否满足。若目标是学习微调，可另做隔离实验，并明确它尚无业务增益证据。
