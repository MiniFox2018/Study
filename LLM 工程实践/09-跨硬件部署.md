# 09｜跨硬件部署

## 1. “模型支持”其实有多层含义

一个模型能否在某平台运行取决于：

- 权重格式；
- 算子；
- dtype；
- attention kernel；
- runtime；
- 推理框架；
- 驱动；
- 通信库；
- 模型自定义代码。

因此“硬件有算力”不等于“软件栈已支持”。

## 2. NVIDIA / CUDA

生态成熟，常见：

- PyTorch；
- Triton；
- NCCL；
- vLLM；
- SGLang；
- Flash Attention；
- Tensor Parallel。

适合高吞吐服务和训练。

## 3. AMD / ROCm

核心逻辑与 GPU 推理类似，但需要使用 ROCm 软件栈，并确认：

- PyTorch ROCm；
- 推理框架 ROCm backend；
- kernel 支持；
- GPU 型号支持矩阵。

不要照搬 CUDA 安装命令。

## 4. Ascend / CANN

Ascend NPU 通常涉及：

- CANN；
- torch-npu；
- vLLM-Ascend / SGLang-Ascend / MindIE 等适配。

版本兼容关系较强，因此环境版本必须严格按当前兼容矩阵确认。

## 5. Apple Silicon / MLX

MLX 是 Apple Silicon 原生机器学习框架。

重要特性：

- CPU/GPU 共享统一内存；
- 数据不需要在独立 CPU/GPU 显存间频繁复制；
- 适合个人 Mac 本地推理与实验。

MLX-LM 在此基础上提供 LLM 推理和相关工具。

## 6. 多硬件决策

### 优先看工作负载

单用户本地：

- Apple Silicon / consumer GPU 可很好满足。

高并发：

- 更关注吞吐、KV Cache 和调度。

大模型：

- 更关注显存 / 统一内存、Tensor Parallel。

训练：

- 还需要考虑反向传播和 optimizer state。

## 7. 统一抽象

跨硬件时尽量保持：

```text
上层 OpenAI-compatible API
        ↓
推理服务层
        ↓
硬件 Backend
```

这样业务层不必感知底层 GPU/NPU 类型。

## 8. 版本规则

驱动、runtime、PyTorch、推理框架、硬件插件都属于高时效内容。

仓库只保留架构关系，不固化版本号。
