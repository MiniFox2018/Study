# 09｜跨硬件部署

## 1. “模型支持”其实有多层含义

一个模型能否在某平台运行取决于：

- 权重格式；
- 算子；
- dtype；
- attention kernel；
- runtime；
- 推理框架；
- 驱动；
- 通信库；
- 模型自定义代码。

因此“硬件有算力”不等于“软件栈已支持”。

## 2. NVIDIA / CUDA

生态成熟，常见：

- PyTorch；
- Triton；
- NCCL；
- vLLM；
- SGLang；
- Flash Attention；
- Tensor Parallel。

适合高吞吐服务和训练。

## 3. AMD / ROCm

核心逻辑与 GPU 推理类似，但需要使用 ROCm 软件栈，并确认：

- PyTorch ROCm；
- 推理框架 ROCm backend；
- kernel 支持；
- GPU 型号支持矩阵。

不要照搬 CUDA 安装命令。

## 4. Ascend / CANN

Ascend NPU 通常涉及：

- CANN；
- torch-npu；
- vLLM-Ascend / SGLang-Ascend / MindIE 等适配。

版本兼容关系较强，因此环境版本必须严格按当前兼容矩阵确认。

## 5. Apple Silicon / MLX

MLX 是 Apple Silicon 原生机器学习框架。

重要特性：

- CPU/GPU 共享统一内存；
- 数据不需要在独立 CPU/GPU 显存间频繁复制；
- 适合个人 Mac 本地推理与实验。

MLX-LM 在此基础上提供 LLM 推理和相关工具。

## 6. 多硬件决策

### 优先看工作负载

单用户本地：

- 可评估 Apple Silicon / consumer GPU，前提是模型、内存和目标延迟匹配。

高并发：

- 更关注吞吐、KV Cache 和调度。

大模型：

- 更关注显存 / 统一内存、Tensor Parallel。

训练：

- 还需要考虑反向传播和 optimizer state。

## 7. 统一抽象

跨硬件时尽量保持：

```text
上层 OpenAI-compatible API
        ↓
推理服务层
        ↓
硬件 Backend
```

这样可减少业务层对硬件的直接依赖；仍需能力协商与一致性测试，尤其是量化、工具调用、输出格式和流式行为。

## 8. 版本规则

驱动、runtime、PyTorch、推理框架、硬件插件都属于高时效内容。

仓库只保留架构关系，不固化版本号。

来源：<https://github.com/datawhalechina/self-llm>

## 9. 先估容量，再测性能

假设模型有 30 亿参数，FP16 仅权重约需 `3×10^9×2=6×10^9` 字节，即约 5.59 GiB；理想 4-bit 打包权重约 1.40 GiB，实际还要加 scale/zero-point、未量化层与对齐。以上均不含 KV、激活、运行时和操作系统内存，不能用该数字作为“必然能装下”的结论。

迁移硬件的最小对照：保留同一模型/模板/输入 → 检查算子能否执行 → 比较输出格式和任务分数 → 测冷启动、首 Token、持续生成与峰值内存 → 再测代表性长输入。浮点结果不完全相同可接受，但任务质量退化必须记录。

**自检**：统一内存是否等于没有内存上限或搬运代价？

**核对**：不是。CPU/GPU 共享容量，仍受可用内存、带宽、调度、临时张量和系统占用约束；频繁交换到磁盘会严重拖慢任务。

## 10. 驱动、框架构建与执行设备分开检查

使用当前项目安装的PyTorch时：

```python
import torch

print("PyTorch：", torch.__version__)
print("框架构建CUDA版本：", torch.version.cuda)
print("CUDA可用：", torch.cuda.is_available())
mps = getattr(torch.backends, "mps", None)
print("MPS可用：", bool(mps and mps.is_available()))
if torch.cuda.is_available():
    device = "cuda"
elif mps and mps.is_available():
    device = "mps"
else:
    device = "cpu"
x = torch.tensor([1.0, 2.0, 3.0], device=device)
assert float((x * x).sum().cpu()) == 14.0
print("本次执行设备：", x.device)
```

输出版本与设备依环境而变，点积应为14。macOS CUDA为False不等于没有可用GPU；安装了CPU构建、驱动不适配、设备未透传、权限或库导入失败也会影响检测。

Linux/NVIDIA可先查看 `nvidia-smi` 的设备和驱动信息，它显示的CUDA能力不是主机安装的CUDA toolkit版本。框架wheel常带所需用户态运行库，编译自定义扩展还可能需要nvcc/toolkit；新驱动通常兼容某些旧运行时，具体依官方矩阵与功能要求，不采用“两个CUDA版本不相等就必坏”的规则。

## 11. 公平计时：计算与传输分别测量

下面是可运行的小规模比较，需已安装PyTorch；无GPU时只给CPU结果，不会伪造加速倍数：

```python
import statistics
import time
import torch

n = 256
cpu_a = torch.randn(n, n)
cpu_b = torch.randn(n, n)
devices = ["cpu"]
if torch.cuda.is_available():
    devices.append("cuda")
elif getattr(torch.backends, "mps", None) and torch.backends.mps.is_available():
    devices.append("mps")

def sync(device):
    if device == "cuda":
        torch.cuda.synchronize()
    elif device == "mps":
        torch.mps.synchronize()

for device in devices:
    a, b = cpu_a.to(device), cpu_b.to(device)
    for _ in range(3):
        c = a @ b
    sync(device)
    samples = []
    for _ in range(5):
        sync(device)
        start = time.perf_counter()
        c = a @ b
        sync(device)
        samples.append(time.perf_counter() - start)
    reference = cpu_a @ cpu_b
    assert torch.allclose(c.cpu(), reference, rtol=1e-3, atol=1e-3)
    print(device, "计算耗时中位数：", statistics.median(samples))
```

此例在计时之外做初始化、传输和warm-up，故测“数据已就位的矩阵乘法”；端到端实际任务需另测读取、搬运、排队和输出。小矩阵可能CPU更快；计时依dtype、计算模式、线程数、形状、设备和负载，不能使用原站“8小时对10分钟”的动画说明当实测。

## 12. 从权重下界到运行内存

FP16每参数2字节只估算权重载荷。24 GB十进制存储除以2得到120亿参数，是不含任何额外开销的理想下界计算；绝不能据此说24 GB显存必能运行或训练12B模型。

推理还需KV、激活、临时workspace、未量化层和服务并发；训练增加梯度、优化器状态、保存的反向中间量等。减少batch/序列长、选适用的低精度、分片或checkpoint各有成本与支持条件。fp16也可能溢出/精度退化，不能保证对所有任务损失极小。

本地、已有远端、托管Notebook或租用GPU是资源路径，而不是按固定模型大小自动决定的阶梯。比较可用算子、容量、吞吐/延迟、数据边界、恢复方式、实际费用与关闭资源方式；云平台型号、免费配额和价格使用前核实。

练习：同一矩阵比较小/大形状，分别报告是否包含传输；记录设备信息与误差，说明速度差异。没有GPU时仍可完成CPU正确性与计时，GPU分支标为未运行。

增量来源：AI Engineering from Scratch，Phase00/03及相关GPU图示/检查程序，固定提交见[来源记录](../来源保全/AI-Engineering-From-Scratch.md)；2026-10-03 兼容性核对：[NVIDIA官方兼容说明](https://docs.nvidia.com/deploy/cuda-compatibility/)。

## 13. 专用引擎、精度与迁移经济不能一起归因

TensorRT-LLM是面向NVIDIA GPU的推理软件。2026-10-10官方overview描述的是PyTorch-native架构与Python LLM API，默认PyTorch backend的量化页提供FP4/FP8及多种weight/KV配置；因此旧表述“所有模型必须编译成某SKU的静态engine，库由闭源kernel组成”不足以描述当前项目。GPU后端支持与host CPU架构是两件事，不能说NVIDIA GPU推理“无ARM”；实际host/驱动/模型支持以部署版本矩阵为准。

低精度需要声明**weights、activations、KV、累加/softmax**各自的格式，不能用一个“FP4”包住全部。NVFP4和MXFP4的scale编码、block长度和实现协议不同；裸4bit参数载荷只是下界，加scale、未量化部分、对齐和workspace。开源软件、GPU算子支持与供应商运行时许可证也分别核对。FP4预量化checkpoint可直接加载的前提是模型/后端/格式兼容，不是所有“day0模型”都自动支持。

官方当前[TRT量化矩阵](https://nvidia.github.io/TensorRT-LLM/features/quantization.html)明确有**NVFP4 KV cache**：需要ModelOpt离线量化，对应例要求FP8权重/激活，且支持的模型与Blackwell硬件子类受限。此处只核验配置含义，未运行转换。不能再说“4bit KV必灾难、FP8绝对下限”，也不能反过来说当前有支持所以所有模型都无损。KV的量化scale布局、长上下文质量、元数据和kernel支持回到[数值量化](15-训练资源与数值量化实现.md)。激活“层内范围小”也不保证4bit误差小，outlier和任务质量必须测。

MoE总参数用于权重存储，active参数用于部分算术/访存，但KV架构不由active参数平方根确定。例120B模型4bit裸权重60GB，并不告诉层数、KV头、context或并发；也不告诉每步搬哪些专家、是否跨rank聚合。同样405B、4bit裸权重202.5GB只是全权重下界。能否装下需真实配置、每rank分片、可见内存、KV、scale、working memory和headroom；GB200 NVL72不是“一块192GB卡”，rack总容量也不能随意当单进程连续可用容量。

`HBM带宽/每token读取权重字节`可给明确假设的单序列memory-bound估算，batch可分摊weights但增KV/计算，MoE不同token选不同expert，算子/通信也会限制；不能乘一个固定MTP1.8×和disagg2.5×就得到真实speedup。原toy即使显示“需multi-GPU”，仍用**一张卡价格**计算总服务费，会低估成本。实际费用要计所有prefill/decode、空闲及备援卡。若prefill/decode拆池，分离吞吐与网络成本在[服务化](03-推理与服务化.md)维护；原课指Phase20实为shadow/canary，disaggregation是Phase17第17课。

迁移比较固定模型、任务质量、输入输出长、并发与SLO，报告hardware count、kernel/版本、功耗或收费时段、cold/warm/cache、队列及失败。Blackwell与Hopper、FP4与BF16、TRT与vLLM同时变化的结果只能说明**整个配置**，不能把所有差异归某一个引擎；要做逐因子对照或明确无法拆因果。原7×/$0.012/M、11–15×等榜单没有本批可比实测，不存为默认收益。

迁移盈亏以 `一次迁移投入/(原每月总成本−新每月总成本)`计算，差值非正没有正盈亏月；投入含适配、双栈运行、质量验证、值班与合同，可回滚/未来迁移成本另计。假如原年费200万、同质量/SLO的已测新年费150万、一次迁移50万，忽略折现才得约12个月；不能用假定“7×”和GPU单价直接求购买数量。采购、租用与费用承诺是不同问题，须保留实际使用方批准与预算。

## 14. 冷启动优化：找关键路径，不能删掉物理加载

### 14.1 冷的是哪个阶段

记录排队分配、节点创建/ready、镜像就位、模型从storage进入CPU/HBM、kernel/graphs/tokenizer初始化、服务ready及first forward。总时长是依赖图的**关键路径**，不是所有时段总和：重叠阶段求max，严格串行阶段相加；warmup/首request/JIT也可能在ready后发生。runAI等并发读Safetensors loader提高加载带宽，不证明第一层到位就能完整生成；first token要能走完所需网络层。

预置镜像或本地权重省下载路径，但不取消节点创建、磁盘读取与HBM传入；快照恢复也仍要从存储取数据。2026-10-10 [Modal快照文档](https://modal.com/docs/guide/memory-snapshot)指出GPU快照一般**不加速存储加载**，可能因额外开销变慢，主要省imports/JIT等初始化；多GPU程序通常不兼容，需按驱动/库与multiprocess限制核验。无用未填KV可在快照前丢弃、restore后再建；代码/配置变化、Volume内容变化与随机/唯一状态也需检查，不能把每次restore同一nonce/credential当安全默认。

暖池保持一定已ready副本，减少部分请求碰冷路径，但暖池耗尽、故障、扩容或单模型多版本仍会冷启。Modal当前用`min_containers`、`buffer_containers`、`scaledown_window`控制常驻/活跃余量/空闲存留，不沿用所有平台`min_workers`。最低常驻不代表全部流量0冷启，最终取决于突发服务需求、单副本可满足SLO的能力和新增ready时间。[Modal冷启说明](https://modal.com/docs/guide/cold-start)

存储层次通常是远端storage、本地NVMe、DRAM到HBM，局部性/布局/并发加载可缩短路径。ServerlessLLM官方OSDI24摘要的10–200×属于当时系统与workload实验，不能当今天任意serverless低延迟保证；本批摘要已读，全文PDF受403限制，未将未读细节写作已核验。[原论文入口](https://www.usenix.org/conference/osdi24/presentation/fu)

### 14.2 关键路径与快照收益的可运行算例

下例计算依赖图的最早完成时间，处理未知依赖、cycle、非有限时长；然后按源课相同人工阶段，说明快照只缩engine init并不把weight loading归零。它计算的是预算，不是GPU/云冷启测量。

```python
import math

def critical_path(stages):
    done, visiting = {}, set()
    def finish(name):
        if name in done: return done[name]
        if name not in stages or name in visiting:
            raise ValueError('未知阶段或循环依赖')
        seconds, dependencies = stages[name]
        if (isinstance(seconds, bool) or not isinstance(seconds, (int, float))
            or not math.isfinite(seconds) or seconds < 0):
            raise ValueError('阶段时长必须有限非负')
        visiting.add(name)
        start = max((finish(d) for d in dependencies), default=0.)
        visiting.remove(name)
        done[name] = start + seconds
        return done[name]
    return max((finish(n) for n in stages), default=0.)

raw = {'node': (50., []), 'image': (180., ['node']),
       'weight': (75., ['image']), 'init': (20., ['weight']),
       'first': (3., ['init'])}
assert critical_path(raw) == 328.
seeded = dict(raw, image=(0., ['node']))
assert critical_path(seeded) == 148.
snapshot = dict(raw, init=(2., ['weight']))
assert critical_path(snapshot) == 310.  # 权重/节点路径仍存在。
parallel = {'read_A': (4., []), 'read_B': (6., []),
            'ready': (2., ['read_A', 'read_B'])}
assert critical_path(parallel) == 8.  # 不是4+6+2。
for bad in ({'x': (1., ['missing'])}, {'x': (1., ['x'])},
            {'x': (float('nan'), [])}, {'x': (True, [])}):
    try: critical_path(bad)
    except ValueError: pass
    else: raise AssertionError('错误依赖/时长必须拒绝')
print('声明预算raw328/seeded148/snapshot310秒；并行关键路径8秒；坏图/时长拒绝')
```

### 14.3 暖池、迁移与恢复的完整代价

一副本每小时4.5元，连续30天常驻费用3240元；每月按实际小时数、资源数、CPU/RAM/storage/network重算。暖池盈亏还需“遭冷启的请求数×每次业务损失/extra资源成本”和真实启停规则，而非只给允许丢5请求。上游函数虽接受`cold_seconds`却不使用，且`24/request_rate`不是通用冷启次数；持续稀疏、一次burst、会话聚集与scale-down策略会给不同结果。长idle窗口可减重复启动，同时增加收费空闲，应以arrival日志回放评估。

保持暖池按**短窗峰值与控制器ready时延**定，不按日均流量或“70B下P99<60s必须1卡”。无暖池也可能通过预热计划、共享可用端点或备用路径达标；反之1暖卡在突发下也不够。对paid/trial/batch区分的是已定义业务SLO/公平队列与资源预算，不是任意给人数就保证服务质量。

迁移时可转输入/已生成token在已有weights的目的端重建KV，也可转KV或采用其他恢复方式。比较 `重算prefill时间` 与 `KVbytes/有效网络带宽+启动/协议成本`，再考虑context、并行、存储局部性、用户中断窗口和状态版本。token很长也不是必然KB；低网速可能倾向重算，高速连接和巨大前缀可能倾向转KV。外部工具副作用还需lease/idempotency/receipt，重算模型状态不能撤销已经执行的业务效果。

初始化快照只在无用户请求数据的受控生命周期拍摄，可减少泄漏面，但不会自动保证不含PII/密钥。是否包含请求KV、prompt、日志buffer和凭据要实际检查；隔离/访问审计、加密、生命周期清理、restore后生成新nonce和必要状态清洗分别落实。不能以“只是权重”或“所有快照都泄漏”代替证据。

## 15. 硬件编译与冷启两课的原练习、测验核对

**TRT/Blackwell07五项练习。** ① active权重数×字节与带宽只给声明的单序列估算，30%active未必等模型真实层/专家配置；TP、KV、batch、compute与kernel必须补齐，不用toy乘数宣布速度。② 200万年费用题缺GPU购价、能力/卡数、利用率、维护和迁移费；先测同质量SLO成本，按§13盈亏，不能求唯一“几卡”。③ 质量优先可用更高精度或只保敏感层；成本优先用匹配领域校准、QAT/蒸馏或mixed precision再评，不能保证校准恢复3分。④ MLPerf需读同任务/scenario/质量模式、模型/输入长、硬件数和submitted系统；本批未全读v6结果，不编造最小gap任务。⑤ 405B4bit裸weights202.5GB，128k KV还需L/Hkv/head/并发、page/scale、perrank和可用容量；题干不足以定是否装进NVL72，不能拿“rack”当单node/卡。

**07六道测验。** ① 7×是未在此复现的配置成绩，不作通用gap；② KV可量化但须方法/模型/矩阵和长context质量，当前NVFP4 KV已有受限支持；③ prequantized加载要兼容checkpoint/backend，不叫所有day0模型免校准；④ NVIDIA GPU依赖与host ARM支持分开，当前软件也有PyTorch路径；⑤ weights/activation/KV/accumulator分别声明，源典型组合非全模型唯一方案；⑥ 质量掉分先恢复合格baseline、重新分层评测，再比较精度/校准方案，费用低不替代正确性。

**冷启10五项练习。** ① 原break-even程序不使用cold_seconds，不能证明盈亏；用真实启停/arrival、资源小时和请求损失算warm与zero-scale总费用。② 13B/3s仅给size不能选最小stack，测各phase及burstready能力再按critical path选择；本批不承诺可达。③ 如果裸weights140GB、**有效**读速7GB/s，读阶段下界20s，4bit35GB则5s，但scale/HBM传输/初始化、firsttoken仍在路径；snapshot-backed EBS不等本地NVMe峰值。④ 论证真实快照内容和restore隔离/PII/密钥/nonce生命周期，见§14.3，不作一概批准或拒绝。⑤ 按paid/trial/batch各SLO、短窗arrival及服务率估ready数量/等待与成本，再回放突发，不能预设1/0/0就足够。

**10六道测验。** ① 3–8min只源阶段预算，不是任意70B冷启事实；② 预置data/image可省pull，仍需挂载/读取，Bottlerocket/EC2NodeClass需版本配置核验；③ GPU snapshot主要跳初始化，不直接0秒存储/HBM装载，多GPU限制另查；④ 转tokens重算与转KV的便宜程度依带宽/context/目的端weights，不总成立；⑤ warm副本以收费idle换ready，但burst超容量仍冷；⑥ 每种优化针对特定依赖，可能重叠、覆盖或新增成本，不盲叠所有层。原SVG“328→15s”“2–4s”及5秒层动画未当实测，07pipeline的equal-stage bubble算式也不是TRT推理成绩。
