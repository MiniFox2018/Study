# 03｜推理与服务化

## 1. 推理有四个常见层级

### 1.1 原生 Transformers 推理

适合：

- 验证模型能否加载；
- 调试 Tokenizer / Processor；
- 单请求实验；
- 检查模型输出格式。

优点：透明、方便调试。

缺点：默认并不针对高并发服务优化。

### 1.2 简单 HTTP API

可用 FastAPI 等框架把模型封装成内部接口。

需要自行处理：

- 请求 schema；
- streaming；
- 并发；
- 队列；
- 超时；
- 错误；
- 生命周期。

### 1.3 OpenAI-compatible API

让本地或私有模型暴露统一接口，是当前非常实用的服务抽象。

好处：

- 上层客户端与模型解耦；
- 更容易替换推理引擎；
- Agent / RAG / UI 可复用同一客户端；
- 支持统一网关。

vLLM 提供 OpenAI-compatible HTTP server，但“兼容”通常只覆盖一组接口与参数，不代表所有供应商功能完全等价。部署时需核对支持的 endpoint、工具调用、流式事件和鉴权范围。

### 1.4 高吞吐推理引擎

代表性方案：

- vLLM；
- SGLang；
- 各硬件平台适配后端。

核心目标：

- Continuous Batching；
- KV Cache 管理；
- 高并发调度；
- Tensor Parallel；
- Prefix / Prompt Cache；
- 更高 Token throughput。

## 2. 离线推理与在线服务

### 离线推理

输入一批任务，最终拿结果。

关注：

- 总吞吐；
- batch；
- GPU 利用率。

### 在线服务

请求随时到达。

关注：

- TTFT：Time To First Token；
- TPOT：Time Per Output Token；
- P50 / P95 / P99 latency；
- requests/s；
- tokens/s；
- 并发下的稳定性。

## 3. Chat Template

聊天模型需要符合其训练约定的对话序列。可以传结构化消息让模板渲染，也可以传已正确渲染的字符串；不能任意拼接角色文本后就假定等价。

消息通常需要经过：

```text
system
user
assistant
tool
...
  ↓
Chat Template
  ↓
Token Sequence
```

错误模板会导致：

- 角色混乱；
- 模型不停止；
- 思考标签错误；
- 工具调用失效；
- 微调和推理格式不一致。

因此 **Tokenizer + Chat Template 属于模型接口的一部分。**

## 4. Sampling 参数

常见参数：

- temperature；
- top_p；
- top_k；
- max_tokens；
- stop；
- repetition 相关约束。

这些参数影响生成行为，但不是模型能力本身。

生产应固定默认值，并允许按任务覆盖。

## 5. 推理性能的核心瓶颈

### Prefill

处理输入上下文。

长 Prompt 会显著增加：

- 计算；
- 显存；
- TTFT。

### Decode

逐 Token 生成。

主要受：

- KV Cache；
- 内存带宽；
- batch 调度；
- 模型大小；

影响。

## 6. KV Cache

自回归模型每一步不应重新计算全部历史 K/V。

KV Cache 通过复用历史中间结果提升生成效率。

但上下文和并发增加时，KV Cache 本身会成为显存主要消费者之一。

因此高吞吐系统必须把：

- 模型权重显存；
- KV Cache；
- activation；
- batch；

一起规划。

## 7. 服务安全

不要把开发服务器直接暴露公网。

至少考虑：

- 反向代理；
- TLS；
- API Key；
- 网络 ACL；
- 请求大小限制；
- rate limit；
- 日志脱敏；
- prompt / output 审计。

特别是推理框架自带的 API Key 不一定覆盖所有 endpoint，应按当前官方文档确认。

## 9. 读懂一次服务测量

假设请求从发送到首 Token 用 0.8 秒，之后 50 个 Token 用 2 秒生成，末 Token 在第 2.8 秒到达。首 Token 延迟 TTFT 为 0.8 秒；后续平均每 Token 时间约为 `2/50=0.04 秒`，对应解码速率 25 Token/s。统计 TPOT 时有些工具以输出总数减一作分母，必须注明定义；总请求延迟还包括网络和排队。

最小验收顺序：单条消息确认模板与停止条件 → 故意提交非法参数确认错误清晰 → 流式返回检查事件拼接 → 取消请求确认释放资源 → 小并发测质量、延迟与错误率。接口返回 200 不等于任务成功，也不能把多个进程各自加载模型当成免费的扩容。

**自检**：吞吐从每秒 100 增至 150 Token，但 P95 首 Token 从 1 秒升至 8 秒，能否称为全面改善？

**核对**：只能说总吞吐提高；交互体验可能退化。先约定延迟服务目标，再在满足目标的请求中计算有效吞吐。

## KV与推测算法的详细入口

单步解码仍需访问可见历史K/V，缓存主要避免重算旧投影与旧隐状态。完整前缀与增量结果的校验、绝对因果位置、GQA有效载荷、在线分块softmax及推测解码的修正采样由[Transformer推理与规模设计](14-Transformer推理与规模设计.md)维护。此处继续负责请求、模板、队列、超时和服务生命周期，不把CPU机制例当真实服务吞吐。

## 10. Prefill、decode与测量：常见瓶颈不是定律

Prefill对已知输入在因果mask下并行处理位置；decode通常每请求每轮新增一个或少数位置。小batch decode常受权重/KV访存影响，大batch、长context、稀疏结构与不同kernel又可能改主瓶颈。粗Roofline为`min(有效计算上限,有效带宽*算术强度)`；算术强度是实际FLOPs/搬运bytes，不是固定“batch<156即慢”。MAC按2FLOPs计，缓存复用、激活/KV读取及通信都要明确。

模型140GB低精度权重放不进单80GB设备时，不能还宣布“该设备0.4秒完成其prefill”而不说明分片/卸载/量化。理论读权重时间bytes/bandwidth也只是已给载荷与带宽下的下界，不是整个decode延迟；MoE不是每token都读全部总参数，GQA/KV也有自己的读量。原站70B型号速率/引擎排行/固定月费没有可比测量，正文不据此选型。

TTFT至少包含网络/鉴权/排队/prefill/首步decode；ITL是相邻已到达token间隔；TPOT定义分母要说明。记录p50/p95/p99是端到端实际样本的分位数，不能把各阶段p95相加当总p95。throughput按成功/满足质量与SLO的请求和token计，prefill与decode token不要混计；排队时间增长也会影响是否真正改善。

[vLLM当前speculative文档](https://docs.vllm.ai/en/latest/features/speculative_decoding/)明确针对一定工作负载下的inter-token latency。选择引擎先核对任务、版本、硬件/算子/模型与tokenizer、采样/grammar、流式/取消、量化/adapter及权限能力，再做同输入/质量/并发benchmark。服务抽象相同不保证所有能力一样。weight/KV量化和模型许可证见[训练资源与数值量化实现](15-训练资源与数值量化实现.md)，分页与精确推测机制见[Transformer推理与规模设计](14-Transformer推理与规模设计.md)。

## 11. Continuous batching、chunked prefill与取消的完整小例

static batch常固定本批成员，短请求结束后资源槽仍留给这个批次直到整体结束；若流式输出已经完成，客户端不必也被强迫等待最长请求。dynamic batching可在入队处等一段时间形成batch；continuous batching在迭代间释放完成请求槽、加入等待请求。这些机制关联但不同。

Chunked prefill把长输入切成若干块，与正在decode的请求按资源预算交错，避免长prompt一口气挤掉交互decode；它也会增加调度/边界开销。decode优先可能让prefill饥饿，所以需要公平/年龄、SLO及最大等待策略。请求到达、输入长度、输出预算、EOS、取消/deadline与cached-prefix命中都改变调度；源程序的`prompt_tokens`没用于cost，不能由其slot-step图证明GPU持续80%利用率。

下面每轮有两个**虚拟token工作单位**，最多两请求。已ready的decode各消费一个，剩余用于prefill；填满prefill这一轮不能同时免费decode。static模式保留完成槽直到整批结束，continuous可替换。D在deadline8取消，释放资源且没有首token；arrival以前不提前处理。没有真实模型、GPU、HTTP或服务器。

```python
from dataclasses import dataclass
@dataclass
class Req:
    name:str;arrival:int;prompt:int;output:int;deadline:int=10**6

def run(source,continuous=True,slots=2,budget=2):
    assert slots>0 and budget>0
    pending=sorted(source,key=lambda r:(r.arrival,r.name));queue=[];active=[];clock=0;records={};busy=[]
    while pending or queue or active:
        while pending and pending[0].arrival<=clock:
            r=pending.pop(0);queue.append(r)
            records[r.name]={'arrival':r.arrival,'prefill':r.prompt,'generated':0,'start':None,'first':None,'end':None,'status':'queued'}
        for r in active[:]:
            d=records[r.name]
            if clock>=r.deadline and d['status']!='done':d.update(status='cancelled',end=clock);active.remove(r)
        still_waiting=[]
        for r in queue:
            if clock>=r.deadline:records[r.name].update(status='cancelled',end=clock)
            else:still_waiting.append(r)
        queue=still_waiting
        if continuous:active=[r for r in active if records[r.name]['status']!='done']
        elif active and all(records[r.name]['status']=='done' for r in active):active=[]
        if continuous or not active:
            while queue and len(active)<slots:
                r=queue.pop(0);active.append(r);records[r.name].update(start=clock,status='active')
        if not pending and not queue and not active:break
        used=0;ready=[r for r in active if records[r.name]['status']=='active' and records[r.name]['prefill']==0]
        for r in ready:
            if used==budget:break
            d=records[r.name];d['generated']+=1;used+=1
            if d['first'] is None:d['first']=clock+1
            if d['generated']==r.output:d.update(status='done',end=clock+1)
        # Chunked prefill only consumes remaining virtual token budget.
        for r in active:
            if used==budget:break
            d=records[r.name]
            if d['status']=='active' and d['prefill']>0:
                take=min(d['prefill'],budget-used);d['prefill']-=take;used+=take
        busy.append(used/budget);clock+=1
        assert clock<10000
    return records,clock,sum(busy)/len(busy)
requests=[Req('A',0,3,2),Req('B',0,1,5),Req('C',2,1,1),Req('D',5,10,1,deadline=8)]
for mode in [False,True]:
    rows,T,occupancy=run(requests,mode)
    for r in requests:
        d=rows[r.name];assert d['start'] is None or d['start']>=r.arrival
        assert d['generated']<=r.output
    assert rows['D']['status']=='cancelled'
    print('continuous',mode,'virtual makespan',T,'virtual budget occupancy',round(occupancy,3))
    print({n:(d['first'],d['end'],d['status']) for n,d in rows.items()})
```

本次static/continuous虚拟makespan9/8，C的首token为9/6；两种都在8取消D。输出的budget occupancy是虚拟单位占用，不是GPU utilization或现实吞吐。改变budget、服务时长、arrival和取消条件后不预设continuous一定更快；实际需测队列/TTFT/ITL/公平性以及峰值KV，而不是把paper示意图当profiling。

## 12. Hogwild!研究协议：多流共享块与位置换算

### 12.1 与单一共享列表的区别

独立voting/分角色subtask/显式tree-of-thought有各自的汇总协议；增加worker数量不会自动提高正确率。Hogwild! Inference是另一种研究方法，其公开论文的具体机制比“无锁append到一条token列表”丰富。[原论文§3.1–3.4](https://arxiv.org/abs/2504.06261)

它保持Common cache（prompt与已完成段落）、各worker当前未完成段落的独立块。worker A的视角可以是Common→其他worker→A，B的视角是Common→其他worker→B，顺序不同；段落完成后加worker标识移入Common，再开新段落。各worker在同一forward batch并行，逐层concurrent attention可以访问其他worker当前token的KV，不是几条标准生成序列仅共享immutable system prompt。

Prompt告诉worker共同问题和块协议，论文还定期插入检查冗余的提示；观察到有些模型能调整计划，也有重复工作、忽略他人更新、小模型/长context鲁棒性下降等问题。其论文预算forward passes和accuracy，有特定任务与模型条件；source两类A/B固定选择规则并不能复現模型“涌现协作”。

### 12.2 RoPE恒等式只处理位置，不恢复相同hidden context

RoPE令Q/K按位置旋转，$R(i_q)q\cdot R(o)K = R(i_q-o)q\cdot K$。若块内K已经按其local位置旋转，拼到offset o的视图时可旋转整个K块，也可针对该块把当前Q改到i_q−o，省去重复旋转所有旧K。V通常不施加相同RoPE。source所称“完全不用调整位置即可稳定”不正确，原方法恰恰使用这个query-offset换算。

```python
import numpy as np
rng=np.random.default_rng(4);D=4
freq=np.array([1.,.1])
def rotate(x,positions):
    x=np.asarray(x,float);angle=np.asarray(positions)[...,None]*freq
    c,s=np.cos(angle),np.sin(angle);pairs=x.reshape(x.shape[:-1]+(2,2))
    a,b=pairs[...,0],pairs[...,1]
    return np.stack([a*c-b*s,a*s+b*c],-1).reshape(x.shape)
# Each block's K is stored rotated to its block-local position; V is unrotated.
blocks={}
for name,n in [('common',2),('A',2),('B',3)]:
    raw=rng.normal(size=(n,D));v=rng.normal(size=(n,D))
    blocks[name]=(rotate(raw,np.arange(n)),v)
q=rng.normal(size=D)
for worker,order in [('A',['common','B','A']),('B',['common','A','B'])]:
    total=sum(len(blocks[n][0]) for n in order);query_position=total-1
    scores_by_Q=[];scores_by_K=[];vals=[];offset=0
    for name in order:
        k,v=blocks[name]
        # R(iq)q · R(offset)K = R(iq-offset)q · K, exact rotation identity.
        scores_by_Q.extend((k@rotate(q,query_position-offset)/np.sqrt(D)).tolist())
        scores_by_K.extend((rotate(k,np.full(len(k),offset))@rotate(q,query_position)/np.sqrt(D)).tolist())
        vals.extend(v.tolist());offset+=len(k)
    assert np.allclose(scores_by_Q,scores_by_K,atol=1e-12)
    scores=np.array(scores_by_Q);weights=np.exp(scores-scores.max());weights/=weights.sum()
    output=weights@np.array(vals)
    print(worker,'layout',order,'attention output',np.round(output,5).tolist())
print('query-offset and key-block shift agree for fixed content; not causal-network hidden-state equivalence')
```

程序固定q/k内容，对A/B不同块顺序分别验证“旋转Q”和“移K块”scores一致，再做全块统一softmax。只验证数学换算和one-layer attention；没有真实LLM、跨层流水、cache共享kernel或推理协作。**位置旋转不能把在另一上下文算出的hidden/KV变成标准因果模型在新串联前缀上的相同hidden**。研究方法采用不同concurrent-attention协议，不承诺普通target的输出分布，更不具有严格推测采样的分布保证。

### 12.3 时间、算力与质量的比较条件

Amdahl粗式`T_parallel=T_serial*((1-p)+p/N)+C_coord`，所有量必须是同单位时间。若c是每worker总串行协调时间，可在已声明串行协调假设下取C_coord=N*c；若c是每步成本，则还要实际步数，并判断协调是否并行。source函数`steps_per_worker`未用，正文又混token/时间，不能据此预测真实速度。

例如虚拟T50000、p.8、N4、每worker总串行协调500，T=50000*(.2+.8/4)+4*500=22000，ratio≈2.27；T1000/p.3/c200/N4则T1575，ratio≈.635。只是明确假设下的算术，既未量任务可并行比例，也未测多worker成本。多worker每forward处理多个token，算力/内存/采样预算不同，不能仅看forward-pass数量叫同成本加速。

Speculative与多worker即使可组合，也会争相同资源、增加draft/cache成本并改变协调频率；两个观察到的speedup不能一般直接相乘。source按同“step”生成N个分类token再在两类别内去重，只量规则进度，不是wall time，也不是完整Hogwild。真实采用前需按固定总计算/时间预算、任务质量、延迟和资源比较，保留不同策略的反例，不写固定2000token或N4的拒绝/成功门槛。

## 13. 常规因果服务：snapshot版本与迟到结果

普通因果decoder的下一token/草稿基于某个确定prefix、模型revision、cache与sampling状态。两个worker拿同prefix生成结果后，若worker0先提交，worker1结果已基于陈旧prefix；一个list append锁只保证容器没坏，不能保证其logits/KV与新prefix一致。常规服务要么分request独立状态，要么明确snapshot/version检查并重算/拒绝陈旧结果。它与§12研究多流KV不同，不能把“拒绝旧prefix”写成Hogwild论文的唯一正确协议。

取消/超时/关闭时推进generation epoch，并禁止迟到结果继续送入流。每次真正提交后版本推进，cache和tokens/position/grammar状态一起提交；幂等请求/成功回执需要另有request-id与receipt记录，不能只重试网络调用又追加一次token。下面仅展示版本拒绝与取消，**没有完整幂等receipt、KV或真实推理服务**。

```python
import threading
class Session:
    def __init__(self):self.lock=threading.Lock();self.version=0;self.epoch=0;self.tokens=[];self.closed=False
    def snapshot(self):
        with self.lock:return self.epoch,self.version,tuple(self.tokens)
    def commit(self,epoch,version,new_tokens):
        with self.lock:
            if self.closed or epoch!=self.epoch or version!=self.version:return False
            self.tokens.extend(new_tokens);self.version+=1;return True
    def cancel(self):
        with self.lock:self.epoch+=1;self.closed=True
s=Session();barrier=threading.Barrier(2);first=threading.Event();results=[]
def worker(wid):
    epoch,version,prefix=s.snapshot();barrier.wait(timeout=10)
    # A fixture for pending decoding result conditioned on this snapshot.
    if wid==1:assert first.wait(timeout=10)
    ok=s.commit(epoch,version,[wid]);results.append((wid,ok))
    if wid==0:first.set()
threads=[threading.Thread(target=worker,args=(i,)) for i in [0,1]]
for t in threads:t.start()
for t in threads:t.join(timeout=10);assert not t.is_alive()
assert sorted(results)==[(0,True),(1,False)] and s.tokens==[0]
e,v,prefix=s.snapshot();s.cancel();assert not s.commit(e,v,[2]) and s.tokens==[0]
print('same-prefix racing commits',sorted(results),'cancelled generation rejects late result')
print('standard causal request snapshot contract; not Hogwild concurrent-attention implementation')
```

实际两个线程同时取版本0，worker0先提交成功，worker1旧版本提交被拒；之后cancel使其旧epoch结果无法写入。Barrier/Event只让竞态稳定复现，锁仅覆盖snapshot/commit。真实模型生成在锁外，必须绑定snapshot结果和逐请求生命周期；读者扩展时还需EOS/max tokens、KV物理回收、出错/重复回执、backpressure和worker失败处理。

## 15. 请求结果缓存：相同问题还不够

单次生成KV缓存避免重复计算历史位置；跨请求prompt cache复用相同前缀的KV；**业务结果缓存**直接复用以前的答案。前两者仍生成新输出，后者改变应用返回结果。语义向量相近不证明答案适用：今天/昨天、允许/禁止、金额100/1000、两个租户的同名制度都可能相近。源`simple_embed`是词频归一，不是语义模型；阈值.90/.98与免责声明不能替代权限、时效和任务校准。

结果key至少绑定租户/主体、授权版本、模型及revision、模板/实验variant、工具schema、输出schema、采样配置、知识版本与实际检索证据身份、完整请求。选模板/路由/检索以后才有足够信息造key；不能先按query命中再选版本。Hash只验证身份，不证明内容正确或授权；每次命中仍核当前权限和输出合同。角色、空白、顺序在代码/模板中可能有意义，不随意strip/casefold“提高命中率”。

## 16. 前缀缓存、批处理与真实流式各省什么

2026-10-07读取[OpenAI prompt caching官方文档](https://developers.openai.com/api/docs/guides/prompt-caching)确认：复用的是渲染上下文的相同前缀KV，工具定义/顺序、模型及设置变化都可能影响匹配，cached token与新输出分别计量。不同模型的门槛、显式/隐式模式与保留参数不同；不把旧“1024/50%/无配置/一小时”表格当所有模型当前契约，也不使用`user`字段代替`prompt_cache_key`。实际调用以选定版本schema和返回usage为准，本批未调用端点。

稳定system/工具/资料尽量放在可复用前缀，动态问题放后面，但先保持角色、指令优先级和语义；任意重排并非信息保真。先写后读、TTL刷新、路由容量、前缀长度以及新增工具都会改变命中。命中请求率不等token命中率：后者按sum(cached_tokens)/sum(input_tokens)计算，不先平均每题百分比；费用模型和break-even由[资源感知优化](../Agentic%20Design%20Patterns/01-核心章节/16-资源感知优化.md)统一维护。

离线Batch是供应商接受任务后异步完成，continuous batching是在线引擎调度，prompt cache是前缀算术复用，不能混称一个优化。离线必须按custom ID核成功/失败/重复/输出顺序与期限，不能把提交成功当全部生成成功。[OpenAI Batch官方说明](https://developers.openai.com/api/docs/guides/batch)的折扣/支持范围只在其当前合同下成立；正文不保存历史固定价格或通用50%节省保证。

真实流式消费上游增量事件，并处理网络断开、取消、背压、工具参数增量、终止原因与usage。先拿全答案再split词并sleep不改善上游TTFT，且破坏换行；HTTP POST的请求不能直接由只做GET的原生EventSource替代。若输出检查必须完整文本，明确先缓冲或采用分段释放策略，不能先泄露敏感片段再“最终拦截”。模型与服务延迟、fallback/重试成本和请求追踪接[案例方法论](10-案例方法论.md)。

## 12. Agent运行形状与持久恢复

2026-10-09融合Phase14第29课。先修是请求/响应、错误、任务ID与基本队列。选择入口形状要同时问：谁触发、用户是否等待、输出是否渐进、能否重复、断开后谁负责、哪些状态必须恢复。请求响应、stream、queue、event、scheduled可以组合；durable是横切的恢复属性，不是互斥的第六种运输。

| 形状 | 输入与结果如何交接 | 必须明确的失败边界 |
|---|---|---|
| 请求响应 | 本次调用等待结果 | 客户端/代理deadline、未知写效果、服务并发；30秒不是HTTP定律 |
| 渐进stream | 逐段交付内容或进度 | 接收慢、队列上限、取消、晚事件；首token快不等任务完成 |
| 队列/background | producer提交handle，worker处理并保存结果 | claim/ack/lease、重投、幂等、失败记录/重试预算；进程deque不是持久queue |
| 事件触发 | event ID与来源驱动订阅者 | 去重、顺序、replay offset、每handler隔离及审计；订阅本身不授权动作 |
| 调度触发 | schedule产生明确run ID | 时区、错过/重叠、取消、重启和旧run恢复；打印would fire不是cron |
| 持久恢复属性 | checkpoint/receipt绑定任务与版本 | 重放粒度、哪些步骤可重跑、外部副作用未知/补偿、存储持久性与权限 |

持久检查点不等外部exactly-once。队列可把未确认任务重新交付，旧worker租约过期后必须失去状态提交权；有副作用的动作需要业务key/receipt/outbox或权威核对。失败可以进DLQ，也可保存终态失败记录与可恢复通知，并非没有名为DLQ的队列就必丢失。[MCP通信与状态工程](../Agentic%20Design%20Patterns/06-专题扩展/06-MCP通信与状态工程.md)已给SQLite租约、取消、幂等和背压强例；[案例方法论](10-案例方法论.md)维护effect提交后重启核回执，避免重复实现。

源QueueRuntime单进程deque、即时retry/内存DLQ，没有持久ack或故障恢复；同attempt可能调用fail_policy两次，对非确定/有状态policy可得到互相冲突的结果。正确做法是一attempt取得一次观察并记录，再按预定可重试类型/预算/退避决定。原题“加DLQ”在源码已存在，新的学习价值是寿命与恢复条件。

源streaming是先构造完整steps列表再yield，不能证明真实模型/socket已被暂停；EventBus同步依次回调，一个异常可影响余下handler；Cron只打印时刻。真正背压应限制producer、缓冲与consumer，明确哪些progress可替换、final不可丢，absolute deadline不被进度无限延长。用户讲话的cancel/epoch由[交互专题](../Agentic%20Design%20Patterns/06-专题扩展/03-交互与动作空间.md)维护，已播放与排队内容分开。

可观察性应关联trigger/run/task/attempt、queue等待、处理/导出、错误与效果，但不强制只用某三个产品才能debug。框架checkpoint、Actor隔离、managed服务、Flow触发都有自己的配置与责任，详见[框架合同](../Agentic%20Design%20Patterns/02-附录/C-智能体框架快速概览.md)。下一tick要明确启动新run还是恢复旧run，不能只靠同一个cron名字猜测。

## 多副本与跨区域：缓存局部性和灾备

先修是前文KV、TTFT、排队和请求准入。单请求KV保存历史计算，prefix cache在**相同且兼容的完整前缀**之间复用，replica router决定请求落到哪里。普通轮询分散请求，可能损失复用；它也可能在没有共享前缀或热点拥塞时合理，所以不能把“轮询总错误”作为结论。

缓存索引至少关联模型/权重revision、tokenizer与渲染后的token序列、adapter、位置/attention规则、KVdtype/layout与并行分片，以及获准共享scope。最长匹配长度决定剩余prefill，不是“前512token hash相同就整个prompt命中”。引擎新增/驱逐事件、实例重启epoch和观测时刻用于维护索引；事件滞后意味着可能miss，不能把metadata命中当GPU仍有完整块。实际加载需验证块完整和兼容，失败按重算/明确失败策略处理。

候选先过地域、授权、模型能力和健康准入，再比较一个带单位的估计：

$$\widehat{TTFT}_r=T_{network,r}+T_{queue,r}+T_{residual\ prefill,r}+T_{first\ decode,r}.$$

各项单位都是时间，残余prefill由未命中token和所测工作负载服务率估计；队列长度本身不是毫秒。缓存最大命中也可能排在热点长队后，network与queue的增量可能抵消省下的prefill。估计服务率会随batch/长度/硬件变，应记录实际TTFT与预测误差，并关注goodput、公平性和成本。源80/800ms、75ms等只是构造数；同样题设中远端80+75=155ms比本地800ms小，720ms节省并没有被440ms“淹没”。RTT已经是往返，按协议确认实际经过几次往返后再加，不自动乘二。

[GORGO v1 §3与§7](https://arxiv.org/html/2602.11688v1)选读于2026-10-10：将prefix overlap、测得网络时延和admission/queue状态共同转为路由成本；轻量索引是近似，状态新鲜度和少量region实验限制泛化。它路由请求而非自动跨区复制KV，TTFT最优也可能牺牲吞吐。这份方法支持联合估计，不支持本课程任何固定跨区阈值。

以下完整离线程序只检查可信题设snapshot的筛选、过期与时间比较。`hit_tokens`是假设已核的匹配数，不会真正哈希/加载KV；事件过期按miss估，不等测过缓存TTL。region与KV合同来自可信宿主，程序不是授权服务、路由器或跨区性能实验。

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class Snapshot:
    name: str
    region: str
    model_revision: str
    adapter_revision: str
    kv_layout: str
    observed_at: int
    hit_tokens: int
    queue_ms: int
    network_ms: int

def estimate(req, candidates, now, max_age=10):
    if type(now) is not int or type(max_age) is not int or max_age < 0:
        raise ValueError('时钟或事件新鲜度')
    total = req['tokens']
    if type(total) is not int or total < 1:
        raise ValueError('token 数')
    rows = []
    for c in candidates:
        if c.region not in req['allowed_regions']:
            continue
        same = (c.model_revision, c.adapter_revision, c.kv_layout) == req['kv_contract']
        if not same:
            continue
        for n in (c.observed_at, c.hit_tokens, c.queue_ms, c.network_ms):
            if type(n) is not int or n < 0:
                raise ValueError('snapshot 数值')
        if c.hit_tokens > total or c.observed_at > now:
            raise ValueError('无效匹配长度或未来事件')
        # 过期事件不能声称命中，保留可服务候选但按 miss 估算。
        hit = c.hit_tokens if now-c.observed_at <= max_age else 0
        # 题设线性残余prefill，每token 2ms，固定首token额外5ms。
        ms = c.network_ms + c.queue_ms + 2*(total-hit) + 5
        rows.append((ms, c.name, hit))
    if not rows:
        raise RuntimeError('无允许且KV兼容的候选')
    return min(rows)

req = {'tokens':400,'allowed_regions':{'EU'},
       'kv_contract':('model-r1','adapter-r1','layout-r1')}
local = Snapshot('local','EU',*req['kv_contract'],95,0,0,0)
remote = Snapshot('remote','EU',*req['kv_contract'],95,400,0,75)
us = Snapshot('us','US',*req['kv_contract'],95,400,0,0)
assert estimate(req,[local,remote,us],100) == (80,'remote',400)
assert estimate(req,[local,remote],106)[1] == 'local'  # TTL/事件新鲜度边界
busy = Snapshot('busy','EU',*req['kv_contract'],95,400,800,75)
assert estimate(req,[local,busy],100)[1] == 'local'
other = Snapshot('wrong-adapter','EU','model-r1','adapter-r2','layout-r1',95,400,0,0)
assert estimate(req,[local,other],100)[1] == 'local'
try:
    estimate(req,[us,other],100)
except RuntimeError:
    pass
else:
    raise AssertionError('不得为了缓存命中绕过region/adapter合同')
bad = Snapshot('bad','EU',*req['kv_contract'],95,401,0,0)
try:
    estimate(req,[bad],100)
except ValueError:
    pass
else:
    raise AssertionError('matched tokens不得大于输入')
print('地域与KV合同先筛；事件过期按miss；网路/队列/残余prefill联合比较通过')
```

灾备恢复的是**可重新运行的服务**，不是只保存权重。模型仓库的权重/分片索引、config、tokenizer/词表、chat template、RoPE和量化metadata，adapter权重与映射，加镜像digest/依赖锁、engine启动配置、部署/网络/存储、secret引用与访问策略，都进入带hash和版本的manifest。应实际在隔离恢复环境加载、做固定输入/输出与权限检查，记录RTO、RPO、冷缓存恢复和SLO；目标由业务需要给出，不照搬“每季度/22分钟”。源32%DR失败及银行/医疗案例没有一手证据，淘汰其数字，保留漏配风险。

[Bedrock跨区官方文档](https://docs.aws.amazon.com/bedrock/latest/userguide/cross-region-inference.html)核对的是inference profile定义的地域路由与容量；它不等应用持有服务方内部KV索引。对托管端点，使用其允许配置并测端到端行为，不能再“在内部加自管replica router”。数据处理边界应由适用法律/合同与可信政策定义，不能由请求出生地直接推出法律许可或无条件违例。

**来源图与源码**：`router.svg`表达先hash/lookup再比network的层级，保留关系而不收32%等数字。`cache-aware-router`动画2.4秒预设第二副本有P，不模拟负载、租户、TTL或SLO。源码的queue更新从0不能增加，`set.pop()`驱逐无LRU合同且可能受进程hash随机化影响；没有prompt长度变量、政策过滤和KV兼容验证，不能用它作交叉点或当前产品验证。固定production-stack [README](https://github.com/vllm-project/production-stack/blob/4e076e8de3698a3729b575e3a5ade65ffbb929cf/README.md)把prefix-aware标WIP并指向Python router；源“Rust O(1)成熟events路径”没有由此成立。
### 原11课五项练习的参考判断

1. **75ms RTT下多长prompt跨区值得？** 源程序把cold/hit固定800/80ms且没有prompt_length，不能求长度交叉点。先核地域许可，再比较 local_queue+local_residual_prefill 与 remote_network+remote_queue+remote_residual_prefill。题设都不排队时，80+75=155<800；若新增网路和排队超过720ms才输。RTT本来是往返，不能自动再乘2。
2. **命中率70%降到12%，怎样诊断？** 查三类：模板/模型/adapter/tokenizer版本变化，用cache key与matched token分布确认；缩容、重启、驱逐或路由变更，用KV事件、miss原因和实例版本确认；输入分布/租户/长度变化，用同scope流量切片确认。请求命中率和token命中率分别算，避免只比较一个平均值。
3. **70B AWQ和5个LoRA的恢复清单？** 以可恢复的目录和哈希清单记录权重各分片/索引、config、tokenizer与词表、chat template、RoPE/量化参数与必要scales/zeros、5个adapter权重/config及路由映射，另保引擎版本、依赖锁、镜像digest、启动参数、部署/网络/存储/密钥引用。密钥不写进公开manifest，恢复后验证加载、模板、已知输入输出及性能/RTO/RPO。三类清单不是三个固定文件。
4. **Bedrock跨区推理是否足够满足严格TTFT？** 官方inference profile定义可路由地域和容量，不提供本课程意义的应用KV事件索引保证。托管用户不能擅自把内部replica router加到服务方内部；按允许的profile、实测端到端TTFT/尾延迟和地域约束验收。只有自管replica才可决定其缓存路由，不能以产品名称代替性能证据。
5. **巴黎请求命中US缓存就发送吗？** 先按可信政策筛allowed regions，来源地不是唯一规则。若批准的处理边界只含EU，则US候选拒绝；若依法/合同允许US，再比较时延。GDPR并非一概禁止任何跨境处理，具体法律判定交给适用规则，不写无条件法律结论。

### 原11课六题中文自检

1. **轮询为何影响缓存？** 它可能把相同前缀发到无缓存副本而重算，但并非任何工作负载下都“有害”；不共享前缀时收益可能小。
2. **缓存路由需要何种信号？** 兼容的完整前缀/块身份和新增/驱逐/实例健康事件，加队列/容量及事件新鲜度；只哈希512token未必足够。
3. **80/800ms差距可普遍记忆吗？** 10倍只是源题设，无实测配置/primary；保留cached与cold的机制，测同模型和负载。
4. **为什么跨区可能更慢？** 网路+排队+残余prefill共同决定；源说440ms超过节省720ms为算术错误，RTT也不再乘2。
5. **32%灾备漏文件是否事实？** 缺少一手统计，不收这个百分比；保留tokenizer/模型/量化/engine/部署全清单和实际restore验证。
6. **Bedrock跨区等于KV-aware router吗？** 官方profile定义地域路由/容量；不承诺应用可见KV索引，且托管用户不能配置内部replica。


## 端侧推理：容量、带宽、运行时与隐私

端侧推理需要同时通过**内存容量、有效带宽/计算、运行时算子、持续功耗/温度、产品隐私与延迟**几道检查。小batch密集模型decode常受权重读取约束，但MoE只激活部分专家，较大batch会摊薄权重读取，长context还读KV；不能把“全部权重每token读一遍”当所有结构与场景的定律。

在明确的单序列密集模型题设中，纯量化权重近似 $W=P\times b/8$ 字节，权重读下界 $T_{weight}=W/B_{effective}$ 秒，理想权重限制速率约 $B_{effective}/W$ token/s。7B、4bit不计metadata时为3.5GB，50GB/s时至少70ms、约14.3token/s；77GB/s时约22token/s。这里未加解量化、KV/激活、算子与同步，厂商标称峰值bandwidth也不等应用有效bandwidth。TOPS不代替模型所需precision/算子支持，也不保证吞吐。

总内存至少由实际weight artifact、KV、激活/workspace、编译/转换临时buffer、应用和OS组成。标准GQA载荷 $M_{KV}=2LBTH_{kv}d_hs$，L层、B序列、T历史token、Hkv头、dh每头维度、s每元素字节；TP分片、padding、paged block和量化metadata另加。模型标称128K context只表达模型支持范围，不能推出手机可容纳。长context还影响注意力读取和prefill，减context可能损失证据与答案能力，须回归而非只防OOM。

| 路径 | 实際需要核的合同 | 不能由名字推断的事实 |
|---|---|---|
| Core ML / Apple ANE | artifact、支持算子、compute units、OS/设备、量化与分段 | 全模型一定跑ANE、统一内存绝无复制/同步 |
| PyTorch MPS / Metal GPU | Metal GPU backend、精度/算子、所用runtime | MPS就是ANE，或某C++ Metal backend必使用MPS |
| Qualcomm QNN / AI Hub | 具体SoC、模型artifact、SDK/backend、算子与量化 | 任意INT4模型在任何Hexagon可加载 |
| WebLLM / WebGPU | adapter/device/features、MLC模型与匹配wasm、worker/缓存 | 浏览器版本号等于可用，直接GGUF加载通用 |
| Jetson / 对应GPU runtime | 板卡内存、JetPack/引擎/模型兼容、功耗档与散热 | Nano/Orin Nano/AGX/Thor互换artifact或固定tok/s |

[Apple官方MPS说明](https://developer.apple.com/metal/pytorch/)确认MPS用于GPU；[WebLLM官方入口](https://webllm.mlc.ai/docs/)与固定[模型配置](https://github.com/mlc-ai/web-llm/blob/fb3a7fc2149e21fd926bd29a611bf8cfda8a4846/src/config.ts)显示MLC模型artifact及相应WebGPU wasm。上述是2026-10-10选读的支持边界，不是安装/设备验证。源38/45TOPS、41tok/s、覆盖70–75%、星数与具体型号默认推荐未保留为当前保证。

实际设备验收先能力探测，再用所选artifact测cold download/load、prefill、首token、decode/ITL、峰值memory、持续热降频、取消/断网和结果质量。后台worker隔离重计算能保护UI，但不保证总内存或速度。浏览器缺WebGPU时可以降低本地模型、说明无法执行或在获准后用服务端；“OpenAI-compatible”外形不解除离线/私有要求，不能静默上传。语音链路须纳入STT、端点检测、模型、TTS和音频播放，本地只省部分网络，500ms不是必得结果。

**图与代码**：静态`edge-targets.svg`把WebGPU写GGUF，与正文MLC说法冲突，按固定官方artifact更正。动态图`edge-bandwidth-pipe`仅0.9/1.6秒粒子和预置带宽，未测内存。源Python的observed表无具体benchmark证据，且其8B/4.7GB与练习7B/3.5GB题设不同；效率比仅相对所假定带宽上界，不能证明compute不重要。跨硬件的完整部署原理接[跨硬件部署](09-跨硬件部署.md)，此处补的是端侧合同与测量。
### 原12课五项练习的参考判断

1. **7B Q4、77GB/s的decode估计？** 纯权重题设大小7e9×4/8=3.5GB，理想单序列仅权重读取上界77/3.5=22tok/s；若给定6–8tok/s，相对该简化上界约27–36%。实际量化metadata、KV/激活、kernel、热/功耗和MoE改变流量，不能把它当硬件测量或“只需优化runtime”的证明。源代码用8B/4.7GB，需分清题设。
2. **浏览器无WebGPU如何fallback？** 能力探测navigator.gpu并请求adapter/device，检查所需features、内存和模型编译artifact；失败可提供较小本地方案、明确不能本地执行或用户许可的服务器路径。相同API外形不保证privacy/功能等价，离线/本地隐私要求下不能静默上传。不能仅按浏览器版本放行。
3. **iOS 4K上下文、4GB活跃内存怎样选？** 以模型实际artifact加KV公式2×L×B×T×Hkv×dh×bytes、激活workspace、转换buffer、应用/OS余量核算，再在目标最差设备测prefill、decode、热、峰值memory。举例1B Q4纯权重0.5GB，若16层、8KV头、64head维、FP16、B1、4K则KV约134MB；只是预算样例，不保证某iPhone跑得下。
4. **不同Jetson容量怎样统一？** 统一应用请求/响应/取消/验收合同，后端按设备选择可支持的模型、格式、runtime和限制；质量差异明确测试。量化和engine artifact可能分机型编译，不能把gpt-oss20b/40tok/s写成无版本通用能力，也不能把原始Jetson Nano与Orin Nano混同。
5. **WebLLM是否适合生产？** 用支持设备矩阵、模型/wasm版本、WebGPU features、首次下载/缓存/断网、峰值内存、worker UI隔离、错误/取消与隐私测试决定。官方runtime可浏览器本地执行，并不等每浏览器每设备可用。课程70–75%覆盖、41tok/s、星数没有可复核统计，不作为验收。

### 原12课六题中文自检

1. **移动decode为什么常慢？** 低batch密集模型可受权重/KV访存带宽限制，同时容量、kernel、热、功耗也影响；不是compute永远次要。
2. **统一内存等于没有拷贝吗？** 共享物理pool可减少显式搬运，但layout转换、同步/cache一致性及backend选择仍需检查。MPS为GPU，不是ANE。
3. **WebLLM可直接载GGUF吗？** 核当前配置的MLC模型artifact与匹配WebGPU wasm；源静态图/output的GGUF建议与正文冲突，不作为直接输入保证。
4. **手机WebGPU覆盖70–75%成立吗？** 缺可复核统计，浏览器/device/features动态探测和测试矩阵才是依据。
5. **长context为何容易OOM？** 权重、随T增长的KV、workspace、模型/format临时buffer和OS共同占memory，不能从模型最大context推出设备支持。
6. **本地语音一定低于500ms吗？** 本地免去模型网络往返但STT、prefill、TTS、音频IO/排队和热仍耗时，需端到端预算与设备测量。


## 两层缓存：可用时间、计费分区和答案有效性

已有§15负责精确业务结果cache，§16负责prompt cache，TTL成本程序由[资源感知优化](../Agentic%20Design%20Patterns/01-核心章节/16-资源感知优化.md)维护。两层省的工作不同：**prefix/KV命中**仍处理新后缀并生成新回答；**结果cache命中**直接复用旧回答，必须证明它在本次权限、证据、时效与输出合同下仍适用。语义embedding相近只产生候选，不证明可代用。

计费要分普通输入U、cache read R、cache write W与output O。按适用供应商的互斥计量定义，简单费用为 $(Up_u+Rp_r+Wp_w+Op_o)/10^6$；若total input已经含read/write，则先拆分普通部分，不能对同token再加一遍完整input费用。token命中率为全窗口sum(R)/sum(total input)，请求命中率为有hit的请求占相应分母；输出/工具/存储/检索/judge及failed/unknown attempts独立入账。

2026-10-10重新选读[OpenAI Prompt Caching](https://developers.openai.com/api/docs/guides/prompt-caching)：当前合同按模型代际区分显式/隐式缓存与保留参数，有些路径有cache write价格；`usage.input_tokens_details.cached_tokens`和适用的`cache_write_tokens`需与实际版本schema核对，Chat Completions字段形状另核。早期路径的`prompt_cache_retention`不等所有新路径的`prompt_cache_options.ttl`。具体价、最小长度和选择的breakpoint由所用模型文档给出，不保“全自动/没有flag/统一10倍便宜”。这是接口差异说明，不是模型推荐或迁移任务。

[Claude官方缓存机制](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)此次核的是block标记、TTL、相同前缀和并发可用时间。首响应开始后缓存才可供后续请求使用；首写前并发可能miss，但不是所有并发必然N次write或固定5–10倍账单。若先发一条等首响应再fanout，会改变关键路径；预热也可能收费/过期。single-flight只可在相同授权scope和完整请求合同下合并，不能把不同用户“语义相近”请求混成一次。

稳定system/tools/参考资料置前，动态日期/request-ID/问题置后，应保角色和指令语义。动态位置变化会使包含该位置的缓存断点不匹配；更早前缀只有在所用机制已写入且本次会查询的兼容断点、最小长度和留存条件都满足时才可命中。当前OpenAI新路径若隐式只在整个最新消息末尾写入，末尾包含动态内容，又未在静态内容末尾另设断点，则相同静态前缀也可能无法复用。显式在稳定内容后设断点才提供该边界，仍需实际usage核查；不能笼统称“有日期就0hit”或“把日期放后面就必hit”。5m/1h选择须按实际arrival、读是否续期、驱逐/路由和read/write费求总账；频繁访问不断延长5m时，1h不必更省。容量/留存/撤权与“缓存中能访问的秘密”仍要按政策管理。

语义cache以已授权、版本匹配、实体/时间/数值/否定条件过滤后，再查embedding近邻，独立集同时测错误复用损失、precision和coverage。0.95不是95%正确，0.85不是通用危险边界；取模型、语料、任务及代价的校准结果。字符串词hash/词频模拟无法证明“同义”；源TS还去掉非a-z0-9，中文提示可变成零向量。高风险任务选择miss也合理，精确cache作为基线。

**源码和图边界**：Py不使用`arrived_at`/TTL/threshold，还把500次loop变成500个波次（实际请求更多）；parallel miss不进入set不能模拟延迟首写。TS建LRU但模拟不用其读写/过期，L1四个FAQ预热+随机hit不是学得语义命中。两边把整个prompt都按cached价、不拆dynamic suffix而低估费用。静态两层关系有效，动态图3.6秒固定三hit一miss、“近零成本”和固定比例不是实验；batch叠加仍要按下一节接口和实际usage算，不能把每请求总账都乘.1。
### 原14课五项练习的参考判断

1. **并行缓存标记切换能证明省多少吗？** 源Py并不使用arrived_at或TTL，is_parallel_wave miss不加入cache，假定永远未写而不是模拟写完成；TS虽有LRU对象但未用其get/set。仅表明题设成本不同，不能给真实5–10x。应以同前缀实际并发到达、首次缓存可用、ttl/驱逐与usage账单对账。

5. **十路query如何cache友好又不增延迟？** 没有同时保证的方案：wait-first可能增加关键路径，预热可能收费/过期/没有命中。Anthropic官方要求首个响应开始后缓存才可用；稳定prefix、single-flight、已授权预热及流量调度分别权衡。不要合并本该隔离的租户或篡改工具步骤。以端到端deadline和完整费用实测选择。

### 原14课六题中文自检

## Prefill/Decode拆分：干扰隔离和KV传输

先修为前文prefill/decode、排队和GQA/KV载荷。长prefill与持续decode共置可能互相干扰，chunked prefill/调度也可以缓解；**PD拆分**把计算新输入状态和生成后续token分成池，获得独立排队、资源配置与扩缩容的自由，同时新增KV转移、同步与故障管理。低batch密集模型常表现prefill计算/decode访存受限，但batch/context/MoE/kernel/communication会改变瓶颈，不能由常见描述推出“共置总浪费”。

请求从frontend/router选prefill工作者；prefill产出带request/version/模型adapter/位置布局的KV，由所选transport传到兼容decode工作者，加载校完整后继续生成。prefix已经兼容驻留时可以减少需要prefill的范围，不是“凡hash hit就跳过所有步骤”。迁移/取消/worker替换要绑定generation epoch，旧数据/迟到token不能混入新请求；传输失败可明确终止或按可重算状态恢复，不能读半份KV输出。

粗payload为 $M_{KV}=2LBTH_{kv}d_hs$，transfer下界为 $M_{KV}/B_{effective}$，额外有lookup/建立连接/排队/pack/unpack/同步。batch、TP/PP分片、dtype/layout与padding、prefix局部命中分别记清；权重量化位宽不自动等KV位宽。若题设KV500MB，有效100GB/s纯搬5ms、10GB/s纯搬50ms，只是下界。pipeline可重叠部分I/O，但被同一link/内存资源限制时无法消掉开销。

同输入长度I、输出O下，简化两方案总time差为：

$$\Delta T=T_{transfer}+T_{sync}+(T_{queue,PD}-T_{queue,colo})+(T_{prefill,PD}-T_{prefill,colo})+(T_{decode,PD}-T_{decode,colo}).$$

比较同模型、总硬件/费用、到达分布、并发、质量和SLO。若PD的prefill速度相同且decode只因换硬件变快，不能把加速全归拆分。源程序两边prefill同40token/ms，decode.1→.18被预设，I与O一起变；固定O时I增长只增加transfer，根本不能证明“prompt越长就必越值”。没有queue/多请求/资源价格就不能宣称throughput、goodput或年省30–40%。

配置比例由joint输入/输出分布、arrival/burst、各pool有效服务率、KV容量和failure headroom求出，并检查TTFT/TPOT/整请求尾延迟。只知P99 input8K、output300不足决定2:1，固定512/200/4GPU门槛不保留。按部署的网络backend及设备核可用性，NIXL是传输抽象，不保证所有环境自动从RDMA退到TCP。

[Dynamo官方入口](https://docs.nvidia.com/dynamo/latest/)2026-10-10选读显示开源、可配vLLM/SGLang/TensorRT-LLM并可Kubernetes/local等部署；不是无需运维的managed服务。llm-d也是协调引擎/调度/部署的方案，选择依据当前具体engine、controller、网络/存储、upgrade和观测能力；planner只有在profile可靠、容量可用、控制环有效时帮助SLO。MoE专家FFN和attentionKV不同，expert分布/通信可能改变各池效率，却不意味着KV头数量增或拆分必双赢。

**图与代码**：`disagg.svg`两池/KV箭头可保留，30x/50x、真实案例$2M→1.2M、未来模型结构未经独立可比核验不保留。动态4+4GPU、1.6秒方块转移只是过程图，没有真实SLO。源正文自称internal composite的30–40%又在output要求“引用published case”，证据自相矛盾，不将它作为来源实证。
### 原17课五项练习的参考判断

1. **多长prompt下PD拆分胜？** 源prefill吞吐两边同40token/ms，差值只有KVtransfer+更快decode，output又随prompt一起变，不能证明prompt单变量阈值；在output固定时prompt增长反而增transfer。测同模型/hardware容量、并发、到达、SLO及完整费用，比较chunked/colocated和PD，门槛由workload决定。
2. **8K前缀P99、300输出的RAG如何定pool？** 先拿joint输入/输出分布和arrival/burst，固定模型/GQA/KVdtype、TP/PP、SLO，然后profile各池服务率、队列、KV容量及transfer/p99并求配置。P99 prefix和一个平均输出不足决定2:1；峰值两池、冷启/故障容量也要验收。
3. **Kubernetes团队怎样选Dynamo/llm-d？** 两者都可走Kubernetes且需要运行治理；Dynamo不是无需运维的托管服务。按实际引擎版本、scheduler、controller、网络backend、部署/升级可回滚与SLO调节支持比较，不以团队语言偏好或产品标签给无证据唯一答案。

5. **MoE不同expert怎样影响PD？** expert按token激活的FFN权重/通信和attention KV是不同对象；MoE不必增加Hkv或tokenKVsize。不同batch的专家倾斜、all-to-all与权重驻留改变prefill/decode效率，需分别profile；不要把expertcache与attentioncache混称，也不从MoE推出拆分必有双倍收益。

### 原17课六题中文自检

1. **prefill计算、decode访存是定律吗？** 常见低batch现象不是定律，batch/context/kernel/MoE/通信会改变瓶颈；同卡并置可通过chunking减干扰。
2. **NIXL是什么？** 异构存储/网络transfer抽象，实际backend版本/硬件支持核验；不是任何部署自动RDMA/TCP fallback。

4. **Dynamo托管、llm-d K8s是否互斥？** Dynamo也是开源自管框架且可Kubernetes，两者以组件/engine/network/ops能力比较。
5. **Planner是否自动保证SLO？** profile和规划需可靠workload/时延/容量及部署支持，不能把名字当自动满足请求deadline。
6. **KV router如何组合PD？** 定位兼容residentprefix或决定prefill并传KV；路由/transfer/排队可能共享瓶颈，组合不自动增益。


## KV卸载：页、块、分层存储和恢复

GPU中的KV页是模型中间状态；把它转到host或其他层后再加载，可能避免重复prefill，也可能用在抢占恢复或PD传输。**KV卸载不等weight CPU offload**，后者搬模型参数；也不等持久保存业务答案。层级可包含GPU、local host RAM、local NVMe、remote RAM/disk/object storage，容量更大不自动更快或无限。

原生local offload降低节点内实现范围；LMCache作为KV管理/搬运层可支持local或remote、多引擎/跨query和PD，不能规定“少于两个引擎一律不能用”。设计比较兼容引擎/模型/KVlayout/adapter、数据共享scope、load/store资源、容量/驱逐、失败回退和运维，再测真正重复prefill和SLO goodput。LoRA可能改attention/hidden state，同base不证明KV相同；共享prefix的full模型/adapter合同已在上文保持，不能跨租户/adapter盲复用。

[LMCache v2 §4–6](https://arxiv.org/html/2510.09665v2)此次选读的机制是connector准备token及页metadata、token processor找尚未存/匹配部分、storage/transfer执行store/load、controller lookup状态。小paged数据分散时I/O不能饱和，用较大chunk聚合拷贝；多层pipeline在第n层计算时预取n+1层，排队间隙可预取较慢层。decode新增KV可缓冲后分批存，引用计数减少同数据重复复制；这些是资源策略，仍需检查stream依赖、完整性与buffer寿命，不是“异步所以免费”。

[官方vLLM Jan8博客](https://blog.vllm.ai/2026/01/08/kv-offloading-connector.html)选读确认0.9扩展异步connector API、0.11引入offloading connector，0.12改变物理布局优化搬运；Jan8是博客日期，不是0.11发布日。博客微benchmark固定H100、模型、layout、GPU prefix cache禁用等条件，性能改善不能移作全部版本/真实流量结论。DMA与custom kernel也会竞争不同资源，后者可能干扰计算；命中率低、块小或拥塞时方案可能更差。

监控应区分总GPU memory与KV block pool占用、匹配token、load/store bytes/latency/error、preemption、重新prefill、queue和goodput。`gpu-memory-utilization`配置预算不是当前KV真实利用率；预分配HBM很高不等迫近抢占，也不能普遍以92%报警。读取路径比较“加载完整兼容块+同步”和实际重算，权衡各tier真实吞吐/尾时延；cache outage应有限等待后重算或明确失败，警惕同时miss造成风暴。层级副本/分片与metadata HA需做实际故障演练，不能只列架构就说已验。

**源码与图**：Python 900blocks容量变量没有参与状态，prefix ID跨2K/4K/8K都算完整hit、cache `set`几乎无限，未模拟抢占/容量或HBM扫描；它不能求HBM break-even。静态stack层级可以解释CPU/存储与engine关系，但Ceph/S3不是无限容量；“offload不user-facing”只限已满足重叠条件。source动态key `zero-sharding`实际讲ZeRO optimizer/grads/params训练分片，完全不对应LMCache，已排除该知识错配，训练原理仍在[计算性能与并行训练](../AI%20算法基础/深度学习专题/06-计算性能与并行训练.md)。固定[production-stack README](https://github.com/vllm-project/production-stack/blob/4e076e8de3698a3729b575e3a5ade65ffbb929cf/README.md)支持Helm reference stack，roadmap/WIP不是已经实现并验收的Rustrouter/operator/所有autoscale能力。
### 原18课五项练习的参考判断

1. **HBM利用率多高LMCache才值得？** 源hbm_capacity_blocks_per_engine=900未使用，也没有HBM sweep/preemption状态；set保留prefix不衡量bytes，不能回答交叉点。测KV可用blocks/占用、抢占和重复prefill、host存取时间、命中与SLO goodput，GPU总memory中权重占用也须分开。

3. **共享cache HA怎样设计？** cache可丢时回退重算而非返回不完整KV，做好超时、隔离/熔断、容量预留和cold miss风暴；本地cache/副本/分片/metadata可按适用版本布置，校完整块/模型身份/epoch后才加载。backup缓存不是业务结果持久ledger，不能用“多个副本”宣称HA已验收。
4. **500MB在机械Ceph读取比prefill快吗？** 需实际有效bandwidth和固定latency。题设100MB/s则理想5s，若prefill题设100ms就慢50倍；并发/尾延迟/页布局会更差或受pipeline影响。未测Ceph不能给固定收益。优先比较实际重算与load，不只看存储容量大。
5. **异步offload免费吗？** 拷贝消耗PCIe/网路/CPU/GPU buffer、stream同步及存储资源，能与compute重叠也不消失。miss/load/竞争/失败常在关键路径；官方0.9扩展异步API、0.11connector、0.12layout优化不能混成Jan2026首次发布0.11。按固定版本查speculation/scheduling/恢复限制。

## 网关：准入、失败预算、限流和证据

网关集中provider适配、准入、速率/并发/费用限制、retry/fallback、secret引用、观测与可配置过滤，减轻应用重复处理，同时成为新的共同故障域和数据出口。不同产品的module、edition、部署和版本决定能力，统一API外形不等媒体/工具/stream/usage/停止原因完全一致。网关、日志、模型与子处理方都要满足同一数据policy，self-host也不自动合规。

鉴权边界将可信tenant/actor映射到路线和额度；凭据用受控secret store与最小权限引用、轮换/撤销，不在prompt/日志里。高熵API key可保存校验摘要，source的toy密钥只是示例；`timingSafeEqual`的一次digest比较并不证明整个端点恒定时长或认证健全，还需key ID/index、拒绝策略、防滥用与当前撤权。生产不会每请求遍历所有租户key来证明无侧信道。

retry与fallback共享**总deadline、attempt与费用预算**。只有已分类瞬态错误在当前允许候选内有限重试，尊重可用Retry-After和jitter，避免SDK/网关/应用层乘法重试。400格式错、401/403及policy拒绝不能通过换供应商绕过；安全拒绝不默认是质量故障。发送后timeout/stream中断可能未知，不证明未收费/未产生工具效果；已有片段不能和新模型片段拼成完整成功。效果未知先reconcile，纯模型重试也保账本。

端到端duration从请求入口到最终结果包含每次失败等待、backoff、queue、成功推理与网关处理。sourceTS只在成功返回`totalLatencyMs`，失败throw后先前provider的失败时间和退避丢失，注释声称全计不成立；还能在非retryable400后换下一provider。下面程序用明确虚拟事件检查全路径时间和停止条件，无网络、sleep、模型或部署；未来实际in-flight终止仍需实测，不以预知duration代替取消协议。

```python
def dispatch(events, deadline, max_attempts, overhead=3):
    if any(type(v) is not int or v < 1 for v in (deadline,max_attempts)):
        raise ValueError('总deadline/attempts')
    if type(overhead) is not int or overhead < 0: raise ValueError('固定开销')
    elapsed=overhead; ledger=[]; backoff=0
    for provider,status,duration in events:
        if type(duration) is not int or duration < 0: raise ValueError('时长')
        if status not in {'ok','transient','invalid','permission','unknown'}:
            raise ValueError('错误分类')
        if len(ledger)>=max_attempts: return 'attempt_limit',elapsed,ledger
        # 题设duration是已知的完整事件长度；不能从此推断实际网络可预知。
        if elapsed+backoff+duration > deadline: return 'deadline',elapsed,ledger
        elapsed+=backoff+duration
        ledger.append({'provider':provider,'status':status,'duration':duration,'backoff':backoff})
        if status=='ok': return 'accepted',elapsed,ledger
        if status in {'invalid','permission','unknown'}: return status,elapsed,ledger
        backoff=2  # 下一尝试等待，虚拟时间，无sleep和网络
    return 'exhausted',elapsed,ledger

events=[('a','transient',7),('a','transient',11),('b','ok',13)]
s,t,l=dispatch(events,50,3)
assert (s,t)==('accepted',38)  # 3+7+2+11+2+13，失败也消耗时间
assert len(l)==3 and l[2]['backoff']==2
assert dispatch(events,30,3)[0]=='deadline'
assert dispatch(events,50,2)[0]=='attempt_limit'
for status in ['invalid','permission','unknown']:
    assert len(dispatch([('a',status,7),('b','ok',1)],50,3)[2])==1
print('失败provider时长与退避全计；总deadline/attempt cap及非瞬态/unknown停止通过')
```

限流先定单位：requests/window、tokens/window、inflight和账期费用分别约束。token bucket给平均速率与burst，滑动窗口约束窗口内数量，两者都可多tenant、分布式部署；500RPS不是算法切换定律。分布式atomic限额、global provider额度、负/NaN配置拒绝、当前tier变动与未结usage需处理，计一request不限制极长prompt的token与费用。

在理想独立一次调用、三跳分别失败概率pi且均允许/无期限约束时，全失败为p1p2p3。每家5%则成功99.9875%；进入第2跳5%、第3跳.25%，fallback次数和fallback最终成功不是一指标。共享网关/network/account、相关供应商容量故障破坏独立前提。源默认3%/2%/5%导出99.997%只能作题设算术，不是可用性SLA，失败mock和固定latency不同于故障实验。

### 原19课五项练习的参考判断

1. **三provider各5%失败时availability？** 只在独立一次尝试、备用允许且无共同失败域/期限约束下，三者全失败=.05³=.000125，成功99.9875%；进入第2跳5%，进入第3跳.25%，备用成功约4.9875%。源默认.03/.02/.05是99.997%，不能把它回答5%题。真实网关/auth/网络/容量相关失败需另测。
2. **基线300ms，目标P99<200ms哪个gateway够？** 若300为同请求已有确定端到端下界，加非负开销无一个可达；若是baseline P99，不能用组件P99相加作证仍要重测并改善主要瓶颈。不能选声称2ms的产品就宣称达标。
3. **医疗自托管+PII+审计如何选？** 把数据路线/子处理方、加密、secret权限、审计完整性、访问/删除/备份、redaction误差与故障行为作为验收；OSS也不自动具备合规或某认证。Portkey或Kong的具体版本/模块逐项验证，不把regex/jailbreak分类当完整隐私保护。
4. **LiteLLM多少RPS要迁移？** 无普遍上限。Kong2025基准固定3.10/Portkey1.9.19/LiteLLM1.63.7、12CPU、WireMockproxy无auth/cache/限流，是历史受控供应商基准。实际payload、stream并发、插件/日志、timeout/retry和资源配额测SLO capacity，达不到再调优/扩容或换。
5. **free/trial/paid限流怎样设计？** 单位先定义请求、input/output token、并发和账期费用；token bucket控制平均速率+burst，sliding window控制窗口计数，公平性由quota/scheduler/tenant策略共同决定。按tier合约设容量/补充、全局provider限额、原子分布式账本、Retry-After与突发回放测试，500RPS不是算法切换定律。
