# 03｜推理与服务化

## 1. 推理有四个常见层级

### 1.1 原生 Transformers 推理

适合：

- 验证模型能否加载；
- 调试 Tokenizer / Processor；
- 单请求实验；
- 检查模型输出格式。

优点：透明、方便调试。

缺点：默认并不针对高并发服务优化。

### 1.2 简单 HTTP API

可用 FastAPI 等框架把模型封装成内部接口。

需要自行处理：

- 请求 schema；
- streaming；
- 并发；
- 队列；
- 超时；
- 错误；
- 生命周期。

### 1.3 OpenAI-compatible API

让本地或私有模型暴露统一接口，是当前非常实用的服务抽象。

好处：

- 上层客户端与模型解耦；
- 更容易替换推理引擎；
- Agent / RAG / UI 可复用同一客户端；
- 支持统一网关。

vLLM 当前仍提供 OpenAI-compatible HTTP server。执行部署时应按当前官方文档核验具体 endpoint 和安全配置。

### 1.4 高吞吐推理引擎

代表性方案：

- vLLM；
- SGLang；
- 各硬件平台适配后端。

核心目标：

- Continuous Batching；
- KV Cache 管理；
- 高并发调度；
- Tensor Parallel；
- Prefix / Prompt Cache；
- 更高 Token throughput。

## 2. 离线推理与在线服务

### 离线推理

输入一批任务，最终拿结果。

关注：

- 总吞吐；
- batch；
- GPU 利用率。

### 在线服务

请求随时到达。

关注：

- TTFT：Time To First Token；
- TPOT：Time Per Output Token；
- P50 / P95 / P99 latency；
- requests/s；
- tokens/s；
- 并发下的稳定性。

## 3. Chat Template

聊天模型不能只把字符串直接送进模型。

消息通常需要经过：

```text
system
user
assistant
tool
...
  ↓
Chat Template
  ↓
Token Sequence
```

错误模板会导致：

- 角色混乱；
- 模型不停止；
- 思考标签错误；
- 工具调用失效；
- 微调和推理格式不一致。

因此 **Tokenizer + Chat Template 属于模型接口的一部分。**

## 4. Sampling 参数

常见参数：

- temperature；
- top_p；
- top_k；
- max_tokens；
- stop；
- repetition 相关约束。

这些参数影响生成行为，但不是模型能力本身。

生产应固定默认值，并允许按任务覆盖。

## 5. 推理性能的核心瓶颈

### Prefill

处理输入上下文。

长 Prompt 会显著增加：

- 计算；
- 显存；
- TTFT。

### Decode

逐 Token 生成。

主要受：

- KV Cache；
- 内存带宽；
- batch 调度；
- 模型大小；

影响。

## 6. KV Cache

自回归模型每一步不应重新计算全部历史 K/V。

KV Cache 通过复用历史中间结果提升生成效率。

但上下文和并发增加时，KV Cache 本身会成为显存主要消费者之一。

因此高吞吐系统必须把：

- 模型权重显存；
- KV Cache；
- activation；
- batch；

一起规划。

## 7. 服务安全

不要把开发服务器直接暴露公网。

至少考虑：

- 反向代理；
- TLS；
- API Key；
- 网络 ACL；
- 请求大小限制；
- rate limit；
- 日志脱敏；
- prompt / output 审计。

特别是推理框架自带的 API Key 不一定覆盖所有 endpoint，应按当前官方文档确认。

## 8. 部署选择

```text
单机实验 → Transformers
单用户本地 → Transformers / MLX-LM / llama.cpp 等
内部轻服务 → FastAPI + 模型进程
高并发 NVIDIA → vLLM / SGLang 等
国产 NPU / AMD → 对应后端与框架适配
```

不要先选框架，再找需求。
