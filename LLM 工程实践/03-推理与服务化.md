# 03｜推理与服务化

## 1. 推理有四个常见层级

### 1.1 原生 Transformers 推理

适合：

- 验证模型能否加载；
- 调试 Tokenizer / Processor；
- 单请求实验；
- 检查模型输出格式。

优点：透明、方便调试。

缺点：默认并不针对高并发服务优化。

### 1.2 简单 HTTP API

可用 FastAPI 等框架把模型封装成内部接口。

需要自行处理：

- 请求 schema；
- streaming；
- 并发；
- 队列；
- 超时；
- 错误；
- 生命周期。

### 1.3 OpenAI-compatible API

让本地或私有模型暴露统一接口，是当前非常实用的服务抽象。

好处：

- 上层客户端与模型解耦；
- 更容易替换推理引擎；
- Agent / RAG / UI 可复用同一客户端；
- 支持统一网关。

vLLM 提供 OpenAI-compatible HTTP server，但“兼容”通常只覆盖一组接口与参数，不代表所有供应商功能完全等价。部署时需核对支持的 endpoint、工具调用、流式事件和鉴权范围。

### 1.4 高吞吐推理引擎

代表性方案：

- vLLM；
- SGLang；
- 各硬件平台适配后端。

核心目标：

- Continuous Batching；
- KV Cache 管理；
- 高并发调度；
- Tensor Parallel；
- Prefix / Prompt Cache；
- 更高 Token throughput。

## 2. 离线推理与在线服务

### 离线推理

输入一批任务，最终拿结果。

关注：

- 总吞吐；
- batch；
- GPU 利用率。

### 在线服务

请求随时到达。

关注：

- TTFT：Time To First Token；
- TPOT：Time Per Output Token；
- P50 / P95 / P99 latency；
- requests/s；
- tokens/s；
- 并发下的稳定性。

## 3. Chat Template

聊天模型需要符合其训练约定的对话序列。可以传结构化消息让模板渲染，也可以传已正确渲染的字符串；不能任意拼接角色文本后就假定等价。

消息通常需要经过：

```text
system
user
assistant
tool
...
  ↓
Chat Template
  ↓
Token Sequence
```

错误模板会导致：

- 角色混乱；
- 模型不停止；
- 思考标签错误；
- 工具调用失效；
- 微调和推理格式不一致。

因此 **Tokenizer + Chat Template 属于模型接口的一部分。**

## 4. Sampling 参数

常见参数：

- temperature；
- top_p；
- top_k；
- max_tokens；
- stop；
- repetition 相关约束。

这些参数影响生成行为，但不是模型能力本身。

生产应固定默认值，并允许按任务覆盖。

## 5. 推理性能的核心瓶颈

### Prefill

处理输入上下文。

长 Prompt 会显著增加：

- 计算；
- 显存；
- TTFT。

### Decode

逐 Token 生成。

主要受：

- KV Cache；
- 内存带宽；
- batch 调度；
- 模型大小；

影响。

## 6. KV Cache

自回归模型每一步不应重新计算全部历史 K/V。

KV Cache 通过复用历史中间结果提升生成效率。

但上下文和并发增加时，KV Cache 本身会成为显存主要消费者之一。

因此高吞吐系统必须把：

- 模型权重显存；
- KV Cache；
- activation；
- batch；

一起规划。

## 7. 服务安全

不要把开发服务器直接暴露公网。

至少考虑：

- 反向代理；
- TLS；
- API Key；
- 网络 ACL；
- 请求大小限制；
- rate limit；
- 日志脱敏；
- prompt / output 审计。

特别是推理框架自带的 API Key 不一定覆盖所有 endpoint，应按当前官方文档确认。

## 9. 读懂一次服务测量

假设请求从发送到首 Token 用 0.8 秒，之后 50 个 Token 用 2 秒生成，末 Token 在第 2.8 秒到达。首 Token 延迟 TTFT 为 0.8 秒；后续平均每 Token 时间约为 `2/50=0.04 秒`，对应解码速率 25 Token/s。统计 TPOT 时有些工具以输出总数减一作分母，必须注明定义；总请求延迟还包括网络和排队。

最小验收顺序：单条消息确认模板与停止条件 → 故意提交非法参数确认错误清晰 → 流式返回检查事件拼接 → 取消请求确认释放资源 → 小并发测质量、延迟与错误率。接口返回 200 不等于任务成功，也不能把多个进程各自加载模型当成免费的扩容。

**自检**：吞吐从每秒 100 增至 150 Token，但 P95 首 Token 从 1 秒升至 8 秒，能否称为全面改善？

**核对**：只能说总吞吐提高；交互体验可能退化。先约定延迟服务目标，再在满足目标的请求中计算有效吞吐。

## KV与推测算法的详细入口

单步解码仍需访问可见历史K/V，缓存主要避免重算旧投影与旧隐状态。完整前缀与增量结果的校验、绝对因果位置、GQA有效载荷、在线分块softmax及推测解码的修正采样由[Transformer推理与规模设计](14-Transformer推理与规模设计.md)维护。此处继续负责请求、模板、队列、超时和服务生命周期，不把CPU机制例当真实服务吞吐。

## 10. Prefill、decode与测量：常见瓶颈不是定律

Prefill对已知输入在因果mask下并行处理位置；decode通常每请求每轮新增一个或少数位置。小batch decode常受权重/KV访存影响，大batch、长context、稀疏结构与不同kernel又可能改主瓶颈。粗Roofline为`min(有效计算上限,有效带宽*算术强度)`；算术强度是实际FLOPs/搬运bytes，不是固定“batch<156即慢”。MAC按2FLOPs计，缓存复用、激活/KV读取及通信都要明确。

模型140GB低精度权重放不进单80GB设备时，不能还宣布“该设备0.4秒完成其prefill”而不说明分片/卸载/量化。理论读权重时间bytes/bandwidth也只是已给载荷与带宽下的下界，不是整个decode延迟；MoE不是每token都读全部总参数，GQA/KV也有自己的读量。原站70B型号速率/引擎排行/固定月费没有可比测量，正文不据此选型。

TTFT至少包含网络/鉴权/排队/prefill/首步decode；ITL是相邻已到达token间隔；TPOT定义分母要说明。记录p50/p95/p99是端到端实际样本的分位数，不能把各阶段p95相加当总p95。throughput按成功/满足质量与SLO的请求和token计，prefill与decode token不要混计；排队时间增长也会影响是否真正改善。

[vLLM当前speculative文档](https://docs.vllm.ai/en/latest/features/speculative_decoding/)明确针对一定工作负载下的inter-token latency。选择引擎先核对任务、版本、硬件/算子/模型与tokenizer、采样/grammar、流式/取消、量化/adapter及权限能力，再做同输入/质量/并发benchmark。服务抽象相同不保证所有能力一样。weight/KV量化和模型许可证见[训练资源与数值量化实现](15-训练资源与数值量化实现.md)，分页与精确推测机制见[Transformer推理与规模设计](14-Transformer推理与规模设计.md)。

## 11. Continuous batching、chunked prefill与取消的完整小例

static batch常固定本批成员，短请求结束后资源槽仍留给这个批次直到整体结束；若流式输出已经完成，客户端不必也被强迫等待最长请求。dynamic batching可在入队处等一段时间形成batch；continuous batching在迭代间释放完成请求槽、加入等待请求。这些机制关联但不同。

Chunked prefill把长输入切成若干块，与正在decode的请求按资源预算交错，避免长prompt一口气挤掉交互decode；它也会增加调度/边界开销。decode优先可能让prefill饥饿，所以需要公平/年龄、SLO及最大等待策略。请求到达、输入长度、输出预算、EOS、取消/deadline与cached-prefix命中都改变调度；源程序的`prompt_tokens`没用于cost，不能由其slot-step图证明GPU持续80%利用率。

下面每轮有两个**虚拟token工作单位**，最多两请求。已ready的decode各消费一个，剩余用于prefill；填满prefill这一轮不能同时免费decode。static模式保留完成槽直到整批结束，continuous可替换。D在deadline8取消，释放资源且没有首token；arrival以前不提前处理。没有真实模型、GPU、HTTP或服务器。

```python
from dataclasses import dataclass
@dataclass
class Req:
    name:str;arrival:int;prompt:int;output:int;deadline:int=10**6

def run(source,continuous=True,slots=2,budget=2):
    assert slots>0 and budget>0
    pending=sorted(source,key=lambda r:(r.arrival,r.name));queue=[];active=[];clock=0;records={};busy=[]
    while pending or queue or active:
        while pending and pending[0].arrival<=clock:
            r=pending.pop(0);queue.append(r)
            records[r.name]={'arrival':r.arrival,'prefill':r.prompt,'generated':0,'start':None,'first':None,'end':None,'status':'queued'}
        for r in active[:]:
            d=records[r.name]
            if clock>=r.deadline and d['status']!='done':d.update(status='cancelled',end=clock);active.remove(r)
        still_waiting=[]
        for r in queue:
            if clock>=r.deadline:records[r.name].update(status='cancelled',end=clock)
            else:still_waiting.append(r)
        queue=still_waiting
        if continuous:active=[r for r in active if records[r.name]['status']!='done']
        elif active and all(records[r.name]['status']=='done' for r in active):active=[]
        if continuous or not active:
            while queue and len(active)<slots:
                r=queue.pop(0);active.append(r);records[r.name].update(start=clock,status='active')
        if not pending and not queue and not active:break
        used=0;ready=[r for r in active if records[r.name]['status']=='active' and records[r.name]['prefill']==0]
        for r in ready:
            if used==budget:break
            d=records[r.name];d['generated']+=1;used+=1
            if d['first'] is None:d['first']=clock+1
            if d['generated']==r.output:d.update(status='done',end=clock+1)
        # Chunked prefill only consumes remaining virtual token budget.
        for r in active:
            if used==budget:break
            d=records[r.name]
            if d['status']=='active' and d['prefill']>0:
                take=min(d['prefill'],budget-used);d['prefill']-=take;used+=take
        busy.append(used/budget);clock+=1
        assert clock<10000
    return records,clock,sum(busy)/len(busy)
requests=[Req('A',0,3,2),Req('B',0,1,5),Req('C',2,1,1),Req('D',5,10,1,deadline=8)]
for mode in [False,True]:
    rows,T,occupancy=run(requests,mode)
    for r in requests:
        d=rows[r.name];assert d['start'] is None or d['start']>=r.arrival
        assert d['generated']<=r.output
    assert rows['D']['status']=='cancelled'
    print('continuous',mode,'virtual makespan',T,'virtual budget occupancy',round(occupancy,3))
    print({n:(d['first'],d['end'],d['status']) for n,d in rows.items()})
```

本次static/continuous虚拟makespan9/8，C的首token为9/6；两种都在8取消D。输出的budget occupancy是虚拟单位占用，不是GPU utilization或现实吞吐。改变budget、服务时长、arrival和取消条件后不预设continuous一定更快；实际需测队列/TTFT/ITL/公平性以及峰值KV，而不是把paper示意图当profiling。

## 12. Hogwild!研究协议：多流共享块与位置换算

### 12.1 与单一共享列表的区别

独立voting/分角色subtask/显式tree-of-thought有各自的汇总协议；增加worker数量不会自动提高正确率。Hogwild! Inference是另一种研究方法，其公开论文的具体机制比“无锁append到一条token列表”丰富。[原论文§3.1–3.4](https://arxiv.org/abs/2504.06261)

它保持Common cache（prompt与已完成段落）、各worker当前未完成段落的独立块。worker A的视角可以是Common→其他worker→A，B的视角是Common→其他worker→B，顺序不同；段落完成后加worker标识移入Common，再开新段落。各worker在同一forward batch并行，逐层concurrent attention可以访问其他worker当前token的KV，不是几条标准生成序列仅共享immutable system prompt。

Prompt告诉worker共同问题和块协议，论文还定期插入检查冗余的提示；观察到有些模型能调整计划，也有重复工作、忽略他人更新、小模型/长context鲁棒性下降等问题。其论文预算forward passes和accuracy，有特定任务与模型条件；source两类A/B固定选择规则并不能复現模型“涌现协作”。

### 12.2 RoPE恒等式只处理位置，不恢复相同hidden context

RoPE令Q/K按位置旋转，$R(i_q)q\cdot R(o)K = R(i_q-o)q\cdot K$。若块内K已经按其local位置旋转，拼到offset o的视图时可旋转整个K块，也可针对该块把当前Q改到i_q−o，省去重复旋转所有旧K。V通常不施加相同RoPE。source所称“完全不用调整位置即可稳定”不正确，原方法恰恰使用这个query-offset换算。

```python
import numpy as np
rng=np.random.default_rng(4);D=4
freq=np.array([1.,.1])
def rotate(x,positions):
    x=np.asarray(x,float);angle=np.asarray(positions)[...,None]*freq
    c,s=np.cos(angle),np.sin(angle);pairs=x.reshape(x.shape[:-1]+(2,2))
    a,b=pairs[...,0],pairs[...,1]
    return np.stack([a*c-b*s,a*s+b*c],-1).reshape(x.shape)
# Each block's K is stored rotated to its block-local position; V is unrotated.
blocks={}
for name,n in [('common',2),('A',2),('B',3)]:
    raw=rng.normal(size=(n,D));v=rng.normal(size=(n,D))
    blocks[name]=(rotate(raw,np.arange(n)),v)
q=rng.normal(size=D)
for worker,order in [('A',['common','B','A']),('B',['common','A','B'])]:
    total=sum(len(blocks[n][0]) for n in order);query_position=total-1
    scores_by_Q=[];scores_by_K=[];vals=[];offset=0
    for name in order:
        k,v=blocks[name]
        # R(iq)q · R(offset)K = R(iq-offset)q · K, exact rotation identity.
        scores_by_Q.extend((k@rotate(q,query_position-offset)/np.sqrt(D)).tolist())
        scores_by_K.extend((rotate(k,np.full(len(k),offset))@rotate(q,query_position)/np.sqrt(D)).tolist())
        vals.extend(v.tolist());offset+=len(k)
    assert np.allclose(scores_by_Q,scores_by_K,atol=1e-12)
    scores=np.array(scores_by_Q);weights=np.exp(scores-scores.max());weights/=weights.sum()
    output=weights@np.array(vals)
    print(worker,'layout',order,'attention output',np.round(output,5).tolist())
print('query-offset and key-block shift agree for fixed content; not causal-network hidden-state equivalence')
```

程序固定q/k内容，对A/B不同块顺序分别验证“旋转Q”和“移K块”scores一致，再做全块统一softmax。只验证数学换算和one-layer attention；没有真实LLM、跨层流水、cache共享kernel或推理协作。**位置旋转不能把在另一上下文算出的hidden/KV变成标准因果模型在新串联前缀上的相同hidden**。研究方法采用不同concurrent-attention协议，不承诺普通target的输出分布，更不具有严格推测采样的分布保证。

### 12.3 时间、算力与质量的比较条件

Amdahl粗式`T_parallel=T_serial*((1-p)+p/N)+C_coord`，所有量必须是同单位时间。若c是每worker总串行协调时间，可在已声明串行协调假设下取C_coord=N*c；若c是每步成本，则还要实际步数，并判断协调是否并行。source函数`steps_per_worker`未用，正文又混token/时间，不能据此预测真实速度。

例如虚拟T50000、p.8、N4、每worker总串行协调500，T=50000*(.2+.8/4)+4*500=22000，ratio≈2.27；T1000/p.3/c200/N4则T1575，ratio≈.635。只是明确假设下的算术，既未量任务可并行比例，也未测多worker成本。多worker每forward处理多个token，算力/内存/采样预算不同，不能仅看forward-pass数量叫同成本加速。

Speculative与多worker即使可组合，也会争相同资源、增加draft/cache成本并改变协调频率；两个观察到的speedup不能一般直接相乘。source按同“step”生成N个分类token再在两类别内去重，只量规则进度，不是wall time，也不是完整Hogwild。真实采用前需按固定总计算/时间预算、任务质量、延迟和资源比较，保留不同策略的反例，不写固定2000token或N4的拒绝/成功门槛。

## 13. 常规因果服务：snapshot版本与迟到结果

普通因果decoder的下一token/草稿基于某个确定prefix、模型revision、cache与sampling状态。两个worker拿同prefix生成结果后，若worker0先提交，worker1结果已基于陈旧prefix；一个list append锁只保证容器没坏，不能保证其logits/KV与新prefix一致。常规服务要么分request独立状态，要么明确snapshot/version检查并重算/拒绝陈旧结果。它与§12研究多流KV不同，不能把“拒绝旧prefix”写成Hogwild论文的唯一正确协议。

取消/超时/关闭时推进generation epoch，并禁止迟到结果继续送入流。每次真正提交后版本推进，cache和tokens/position/grammar状态一起提交；幂等请求/成功回执需要另有request-id与receipt记录，不能只重试网络调用又追加一次token。下面仅展示版本拒绝与取消，**没有完整幂等receipt、KV或真实推理服务**。

```python
import threading
class Session:
    def __init__(self):self.lock=threading.Lock();self.version=0;self.epoch=0;self.tokens=[];self.closed=False
    def snapshot(self):
        with self.lock:return self.epoch,self.version,tuple(self.tokens)
    def commit(self,epoch,version,new_tokens):
        with self.lock:
            if self.closed or epoch!=self.epoch or version!=self.version:return False
            self.tokens.extend(new_tokens);self.version+=1;return True
    def cancel(self):
        with self.lock:self.epoch+=1;self.closed=True
s=Session();barrier=threading.Barrier(2);first=threading.Event();results=[]
def worker(wid):
    epoch,version,prefix=s.snapshot();barrier.wait(timeout=10)
    # A fixture for pending decoding result conditioned on this snapshot.
    if wid==1:assert first.wait(timeout=10)
    ok=s.commit(epoch,version,[wid]);results.append((wid,ok))
    if wid==0:first.set()
threads=[threading.Thread(target=worker,args=(i,)) for i in [0,1]]
for t in threads:t.start()
for t in threads:t.join(timeout=10);assert not t.is_alive()
assert sorted(results)==[(0,True),(1,False)] and s.tokens==[0]
e,v,prefix=s.snapshot();s.cancel();assert not s.commit(e,v,[2]) and s.tokens==[0]
print('same-prefix racing commits',sorted(results),'cancelled generation rejects late result')
print('standard causal request snapshot contract; not Hogwild concurrent-attention implementation')
```

实际两个线程同时取版本0，worker0先提交成功，worker1旧版本提交被拒；之后cancel使其旧epoch结果无法写入。Barrier/Event只让竞态稳定复现，锁仅覆盖snapshot/commit。真实模型生成在锁外，必须绑定snapshot结果和逐请求生命周期；读者扩展时还需EOS/max tokens、KV物理回收、出错/重复回执、backpressure和worker失败处理。

## 14. 来源题目、答案与维护边界

Hogwild22原五题分别按下面标准处理：

1. 原main顺序loop，不存在同wall-time并发实测；N2更高A/B进度不证明速度。正式CPU例验证旋转/线程状态，不声称验证reasoning协作。
2. coordination_weight控制硬编码选最少category规则；降低后重复增加只证明规则行为，不能推出模型理解能力下降。target_per_category在源码未用，也不能宣称按该值停止工作。
3. T/p/N/c统一单位与串行/并行协调假设后得到§12.3数值；若c每步而非总成本必须改式。没有算法保证长任务必胜、短任务必败。
4. 原论文描述可能过于专注自身生成而未注意已解决/错误、重复推理等；明确检查冗余与重规划提示可能缓解，但不保证。小模型/长上下文鲁棒性下降也需保留，不能只写“会自协调”。
5. 合并speculative与共享块前，必须定义各worker视图、proposal概率、验证mask、段落移入Common与位置offset，以及scratch commit/rollback。简单两个速度相乘不构成实验，常规单prefix竞态例不能冒称完整组合。
