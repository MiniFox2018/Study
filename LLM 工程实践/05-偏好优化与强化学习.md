# 05｜偏好优化与强化学习

## 1. SFT 解决“会不会做”

监督微调提供标准答案，让模型学习：

- 任务格式；
- 基本能力；
- 指令跟随；
- 输出结构。

但“能生成合格答案”不等于“答案符合偏好”。

## 2. DPO 解决“哪个答案更好”

典型偏好数据：

```text
Prompt
  ├─ Chosen / Preferred
  └─ Rejected
```

DPO 直接利用偏好对优化模型，不需要显式训练独立 reward model。

工程上常见路径：

```text
Base
  ↓
SFT
  ↓
DPO
```

原因是先让模型具备基本任务能力，再优化偏好通常更稳定。

## 3. 偏好数据质量

Chosen 与 Rejected 应体现真正目标差异：

- 正确 vs 错误；
- 有帮助 vs 无帮助；
- 合规 vs 不合规；
- 格式正确 vs 格式错误；
- 结果正确且验证充分 vs 结果错误或缺必要验证；不能用篇幅长短代替质量。

如果差异只来自措辞偏好，模型也只会学到措辞偏好。

## 4. GRPO

Group Relative Policy Optimization 的核心工程思想：

1. 针对同一 Prompt 生成一组候选；
2. 对每个候选计算奖励；
3. 使用组内相对表现构造学习信号；
4. 更新策略，使高奖励响应概率提高。

原始 GRPO 用同题候选组的奖励作为基线，省去单独训练的价值模型；但仍需生成、奖励计算和策略更新。组大小、奖励归一化、裁剪、KL 项及损失归一化影响训练行为，不能把它简化成“选最好的再 SFT”。

## 5. Reward 设计

奖励决定模型会学什么。

可组合：

- 答案正确性；
- 格式；
- 可执行验证器；
- 单元测试；
- 规则匹配；
- 长度约束；
- 安全约束；
- Judge 模型。

### 奖励黑客

如果 reward 设计不完整，模型可能学会“得高分”而不是“完成任务”。

因此必须人工抽检轨迹和输出。

## 6. RL 的关键成本

相比 SFT，在线 RL 往往需要：

- 多次生成；
- reward 计算；
- 更多显存；
- 更复杂的 rollout；
- 更难的稳定性调试。

不要因为 GRPO 流行就默认使用。

## 7. DPO 与 GRPO 的选择

### DPO 更适合

- 已有可靠偏好对；
- 希望训练简单；
- 不需要在线探索；
- 目标可通过 chosen/rejected 表达。

### GRPO / Online RL 更适合

- 结果可自动验证；
- 需要探索；
- 推理任务；
- 奖励可程序化；
- 希望直接优化行为结果。

## 8. 评估要求

后训练后必须检查：

- 目标能力；
- 原能力；
- reward 与真实质量相关性；
- 输出长度变化；
- 格式投机；
- 模式坍塌；
- 安全行为；
- 成本。

## 9. 用奖励组看学习信号

同一个题目生成四个回答，正确性奖励为 `[1, 1, 0, 0]`。组均值为 0.5，若按总体标准差 0.5 归一化，优势为 `[1, 1, −1, −1]`。若四个都错，奖励全部为 0，组内相对奖励无法区分好坏；加一个数值 ε 防止除零并不能凭空产生有用信号。实际库对标准差、长度归一化及其他奖励的定义需单独记录。

设计奖励时，先人工构造反例：格式正确但答案错、答案正确但夹带无关文字、很长却重复、利用测试脚本漏洞的输出。测试奖励是否给出符合目标的排序，再训练。训练后在未参与奖励调试的题目上评价真正成功率。

**自检**：DPO 与 GRPO 都能使用偏好/奖励信息，为什么成本不同？

**核对**：标准离线 DPO 使用已有偏好对计算损失；在线 GRPO 需用策略反复生成候选并评分。它们都可能学到标注或奖励的漏洞，都不保证提升未覆盖的能力。
