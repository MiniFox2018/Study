# 01｜开源模型工程全流程

## 1. 先区分“模型研究”和“模型工程”

模型研究关注：

- 架构；
- 训练目标；
- 优化算法；
- 模型能力。

模型工程关注：

- 模型能否被可靠下载和加载；
- 当前硬件能否运行；
- 推理是否稳定；
- 如何提供服务；
- 是否需要微调；
- 如何验证微调真的有效；
- 如何控制显存、吞吐、延迟和成本。

一个模型“能跑起来”只是工程流程的起点。

## 2. 标准工程闭环

### 第一步：明确任务

先回答：

- 是聊天、分类、代码、Embedding、OCR、视觉问答还是语音任务？
- 需要最新知识还是稳定行为？
- 本地运行还是服务化？
- 单用户还是多并发？
- 是否允许数据离开本地？
- 是否真的需要修改模型参数？

### 第二步：选择基础模型

至少考虑：

- 模态：文本 / 图像 / 音频 / 视频；
- 参数规模；
- 上下文长度；
- 许可证；
- 推理显存；
- 训练显存；
- 目标语言与领域；
- 是否有成熟推理框架支持；
- 是否有成熟微调链路。

**不要只按榜单分数选模型。**

### 第三步：建立基线

在任何微调前先保留：

- 原始模型；
- 固定测试集；
- 固定生成参数；
- 质量指标；
- 延迟和吞吐；
- 显存占用。

否则后续无法判断改动是否真正有效。

### 第四步：服务化

先从最简单的本地推理验证正确性，再根据需求升级到：

- Python 进程；
- HTTP API；
- OpenAI-compatible API；
- 高吞吐推理服务；
- 多卡 / 多节点。

### 第五步：决定是否微调

下面是成本逐步增加的候选路径，不是训练阶段的必经顺序；RAG 解决知识访问，微调解决部分行为适配，必须先区分失败原因：

```text
Prompt / Chat Template
        ↓
RAG / Tool
        ↓
LoRA / PEFT
        ↓
Full Fine-tuning
        ↓
Preference / RL Post-training
```

如果上层方法已经解决问题，不应为了“用了微调”而微调。

### 第六步：评测与回归

任何训练后模型必须重新与基线比较：

- 能力是否提升；
- 原能力是否退化；
- 延迟是否变化；
- 显存是否变化；
- 是否出现格式漂移；
- 是否有新的安全或幻觉问题。

## 3. “教程可运行”不等于“生产可用”

生产还需要：

- 鉴权；
- 限流；
- 超时；
- 日志；
- 监控；
- 错误恢复；
- 并发控制；
- 模型版本管理；
- 灰度与回滚；
- 数据与权限隔离。

## 4. 工程原则

1. **先基线，后优化。**
2. **一次只改少量变量。**
3. **记录训练的复现条件与剩余非确定性。**
4. **所有部署必须可观测。**
5. **模型质量和系统性能分开评测。**
6. **模型版本、Tokenizer、Chat Template 必须一起管理。**
7. **高时效命令永远以当前官方文档为准。**

## 5. 第一个工程闭环：字段抽取

教学任务：把本地三条虚构记录转为 `姓名、日期、事项`。先写 10 条正常样本和 5 条边界样本，例如日期缺失、姓名重名、文本内含“忽略规则”等。人工标注答案，缺失字段规定为 `null`，不允许模型补猜。

1. 固定模型、Tokenizer、模板和生成参数；先运行原模型。
2. 验证输出能否解析、字段是否齐全、值是否有原文依据，分别计分。
3. 若错在 JSON 格式，先尝试模板或结构约束；若错在日期归一化，优先使用确定性解析器；若缺事实，补输入/检索。
4. 将改动在同一验证集上比较，最后在独立留出集验收。只有多次出现可归纳的行为缺陷，再考虑训练。

**自检**：15 条样本全部成功能否声称生产可靠？

**核对**：只能证明这个小样本上的结果。它用于查通流程，不能估计罕见失败；部署前还需覆盖真实分布、权限和并发场景。此处为练习设计，没有声明本仓库已运行模型。
