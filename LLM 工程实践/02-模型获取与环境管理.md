# 02｜模型获取与环境管理

## 1. 模型不是一个权重文件

一个可正常运行的模型通常依赖一组一致资产：

- 权重；
- config；
- tokenizer；
- processor（多模态常见）；
- generation config；
- chat template；
- 自定义代码（部分模型需要）；
- 模型许可证和使用约束。

只复制权重、不保留配置，常常无法可靠恢复。

## 2. 模型来源

常见来源包括：

- Hugging Face；
- ModelScope；
- 官方仓库或对象存储；
- 企业内部模型仓库。

工程上需要记录：

- 模型唯一标识；
- revision / commit；
- 下载时间；
- 校验信息；
- 本地缓存路径。

### 为什么要固定 revision

如果只写：

```text
download latest
```

同一脚本几个月后可能拿到不同文件。

需要复现实验时，应固定具体 revision。

## 3. 环境隔离

建议每个独立工程维护明确的：

- Python 版本；
- PyTorch 版本；
- Transformers / 推理框架版本；
- CUDA / ROCm / CANN 等运行时；
- 关键依赖锁定文件。

### 不要把“能安装”理解成“兼容”

常见冲突来自：

- PyTorch 与 CUDA；
- 推理框架与 Transformers；
- Flash Attention 与编译器；
- Triton 与 GPU 架构；
- NPU 插件与基础框架；
- 模型转换格式与 MLX-LM/其他运行时的兼容。

## 4. 环境记录的最低要求

建议每个实验记录：

```text
OS
Python
Framework
Accelerator runtime
GPU/NPU/Apple Silicon 型号
Driver
Model revision
Training/inference framework version
```

## 5. 缓存与磁盘

大模型工程会同时产生：

- 原始权重；
- 量化权重；
- Adapter；
- checkpoint；
- optimizer state；
- dataset cache；
- tokenizer cache；
- eval 输出。

因此磁盘规划也属于工程设计。

## 6. 安全注意

不要把：

- API Key；
- Hugging Face Token；
- ModelScope Token；
- 云平台密钥；

写入 Notebook、Markdown 或 Git。

统一通过：

- 环境变量；
- Secret Manager；
- 本地不入库配置；

管理。

## 7. 当前规则

具体 `pip install` 命令、镜像地址、CUDA/CANN/ROCm 版本属于高时效信息，本知识库不固化。

执行时必须重新核验模型官方说明和框架当前兼容矩阵。

来源：<https://github.com/datawhalechina/self-llm>

## 8. 可恢复的实验清单

建立一份中文实验记录，例如：

```text
任务：三字段抽取
模型标识与提交：待填入实际值
Tokenizer/模板来源：与模型同一提交，或写明例外
硬件与内存：待填
操作系统、Python、框架与驱动版本：待填
数据版本与划分：待填
输入样例与期望结果：一条正常、一条缺字段
实际结果与错误日志：运行后填写
```

下载后先比对配置中的架构、词表大小和权重分片，再检查模型卡中的许可证、输入模板和硬件要求。`trust_remote_code` 一类选项可能执行模型仓库中的 Python，不能因为“是权重下载”就默认安全；优先检查代码并固定提交。下载哈希可检验文件是否改变，不能独立证明来源可信。

**自检**：只有 Adapter 文件，缺基础模型 revision，能否保证恢复原结果？锁住 Python 包版本是否等于锁住全部运行环境？

**核对**：不能；还需要匹配的基础权重、模板、Tokenizer 与配置。驱动、内核、硬件算子和随机性也影响结果，因此应记录复现差异而不是许诺字节级一致。

## 10. 自托管引擎：兼容性筛选，再测完整工作负载

2026-10-10 融合Phase17第28课，先修本章资产/revision、[跨硬件部署](09-跨硬件部署.md)、[推理与服务化](03-推理与服务化.md)与[服务评测](06-评测与实验管理.md)。选引擎应先筛“能否正确运行”，再比较性能/成本/运维，而不是按用户数和硬件品牌返回唯一冠军。

筛选输入包括模型架构与revision、tokenizer/模板、量化格式和精度、工具/结构输出/多模态、上下文上限、目标OS/CPU指令/GPU内存/互联、实际输入输出和共享prefix分布、到达率/并发及SLO、授权数据、故障恢复与值班资源。100注册用户可能只有1并发，也可能突发100长上下文；不能把人数直接换成单GPU或分离prefill/decode。

| 候选 | 可以评估的优势 | 必须实际核的条件 |
| --- | --- | --- |
| llama.cpp | 本地/CPU/Metal等路径、GGUF及量化配置 | 模型架构、设备后端、精度、context/并发与内存 |
| Ollama | 模型管理、API和本地工作流，支持队列/并行配置 | 实际引擎与模型路径、并发上下文内存、过载拒绝、认证/网络与运维 |
| vLLM | 请求调度、批处理和多设备服务候选 | GPU/CPU后端支持、模型/量化、驱动与版本、实际SLO合格吞吐 |
| SGLang | prefix复用、结构生成与多轮工作负载候选 | 支持架构/硬件、cache命中/隔离、调度与真实完整费用 |
| TensorRT-LLM | NVIDIA设备优化候选 | 具体GPU/精度/kernel支持、构建/模型适配和运维，不只Blackwell |
| TGI | 既有部署和HF生态 | 当前维护范围、安全修补/模型支持、迁移收益与风险 |

[vLLM CPU官方页面](https://docs.vllm.ai/en/stable/getting_started/installation/cpu/)实际有CPU后端及架构/OS条件，因此原“CPU only排除vLLM、仅llama.cpp竞争”错误。[Ollama FAQ](https://docs.ollama.com/faq)说明多模型及同模型并行、内存关联、queue与过载行为，不能以超过1并发就判不可用。源固定慢15–30%/三倍差、400000GPU部署量、某硬件吞吐冠军都缺同条件实测，不用来替选择。

[TGI官方README固定提交](https://github.com/huggingface/text-generation-inference/blob/b4adbf2f6e2e721280bd0ea5f91d70f7d033f5ed/README.md)当前为maintenance mode，接受小bug/doc/维护任务并推荐下游引擎。新项目要考虑长期模型/功能支持；既有项目先审安全修复、维护能力与迁移兼容，不因维护标签立即拆掉正常系统。没有证据证明应在6个月内迁移；具体日期和版本号只在确需时从官方commit核。

开发可以用轻量环境快速试prompt，但staging应尽量匹配**生产引擎、硬件族、量化、tokenizer/template、调度与协议**，否则只是功能近似，不能验生产性能。Ollama→llama.cpp→vLLM不是固定标准流水线。GGUF与HF权重容器不同，量化会丢精度；把已量化GGUF重包safetensors不能恢复原高精度权重。保原始revision再分别生成适配产物，记转换工具/版本、精度与校验值，并用固定输入核输出和质量差异。

候选对比先跑受控代表性任务，确认准确性和权限，再逐档测冷/暖TTFT、TPOT、端到端延迟、goodput、拒绝/失败、显存/RSS、GPU利用与完整TCO；报告平均及P95/P99、不成功样本和复现条件。prefix-heavy值得试SGLang/vLLM的相应cache配置，但高跨租户复用先核数据授权和缓存隔离，不用命中率解释一切。跨AMD/NVIDIA可不同后端分池，统一服务契约/版本追踪；不是为“统一”强制所有设备使用同一kernel。

### 第28课：五项原练习与六题参考

1. **原selector符合实际吗？** 它按硬件/scale/关键词返回预设引擎，没有测质量、内存、驱动或吞吐；未知输入可能engine=None但仍给推广说明。正确输出是符合/不符合/待核候选及证据，不叫自动选型验收。
2. **12 H100与8 MI300X怎样选？** 查具体模型/量化和CUDA/ROCm后端矩阵，按设备分池测候选、统一API与对照任务；TRT-LLM不作为AMD后端，但NVIDIA池可另评，不必全场一个engine。
3. **既有TGI怎样迁移？** 建接口/模板/错误/usage/流式契约与SLO基线，验证新候选、影子/金丝雀、缓存状态和回退，然后按收益/风险决定；maintenance影响新增支持，不自动否定现有系统。
4. **Ollama开发到vLLM生产变化是什么？** 权重产物和精度、tokenizer/模板、采样/工具schema、流式/usage、认证/并发/限流、指标与恢复都须匹配验证，不只改base URL或文件扩展名。
5. **8K共享prefix的RAG怎样选？** 先确认哪些内容能在何种tenant/user范围共享，测prefix命中、长输入prefill、decode长度、路由局部性/热度和缓存失效；选SGLang/vLLM等候选做同质量SLO基准，不据源名称就搭最大复杂stack。

六题：①Ollama是方便的本地候选，不是唯一选择。②当前TGI maintenance有官方说明，影响维护策略而非自动失效。③CPU不强制llama.cpp，vLLM也有条件CPU后端。④RadixAttention使SGLang成为prefix候选，但优势需要同条件测。⑤开发/预生产/生产的权重容器/精度和引擎不同则须单独验证，不能说同GGUF/HF天然等价。⑥Ollama有并行，是否生产适用依性能/权限/恢复与团队能力，不用固定慢幅或>1并发禁令。
