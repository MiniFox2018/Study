# 03｜问题排查、搜索与学习方法

## 1. 第一任务不是找“万能修复按钮”

故障排查本质是缩小可能原因。

推荐顺序：

1. 明确现象；
2. 明确预期；
3. 记录环境；
4. 找到稳定复现步骤；
5. 收集错误信息；
6. 提出几个可能原因；
7. 一次只改变一个变量；
8. 验证结果；
9. 记录最终原因与修复方式。

一上来就重装软件、清注册表、重装系统，即使问题消失，也很可能没有知道真正原因。

## 2. 把“不能用”写成可诊断的问题

好的问题应包含：

- 软件/系统版本；
- 从什么时候开始；
- 具体操作；
- 实际结果；
- 预期结果；
- 完整错误文字或截图；
- 最近改动；
- 已尝试措施；
- 是否稳定复现。

例如：“Windows 上双击某项目 app.exe 后窗口闪退；事件日志显示某 DLL 加载失败；昨天升级驱动后开始出现；同目录另一版本可运行。”这已经把搜索空间大幅缩小。

## 3. 先保存错误原文

优先保存错误代码、异常名称、日志、时间、崩溃模块、命令输出、截图和可重现输入。

技术问题中，一个完整错误码往往比一段主观描述更有价值。

## 4. 搜索时使用高信息密度关键词

有效搜索通常由：

产品/组件 + 错误原文 + 环境 + 关键动作

组成。

搜索结果优先级：

1. 官方文档/官方 issue；
2. 上游项目仓库；
3. 高质量技术社区；
4. 有证据和版本上下文的博客；
5. 聚合转载；
6. 无来源“万能修复”文章。

发布时间不是唯一标准，但涉及 UI、API、驱动、安装和云服务时，时间非常重要。

## 5. 怎样判断教程质量

至少检查作者、是否引用官方资料、更新时间、适用版本、是否解释原理、是否写风险和回滚、评论/issue 是否指出失效，以及是否只是机器翻译/洗稿。

官方文档通常最权威，但不一定最适合入门。高质量学习往往是“教程建立模型，官方文档校验细节”。

## 6. 提问的艺术

向人求助时：

- 给出最小复现；
- 隐去密码、Token、身份证、私钥等敏感内容；
- 代码使用文本而不是模糊截图；
- 说明已经查过什么；
- 不要预设原因，例如“肯定是 Windows 的 bug”。

提问质量本身也是排障能力。

## 7. AI 可以帮助排障，但不能代替证据

AI 擅长解释错误信息、设计排查树、整理日志、生成搜索关键词、解释官方文档和编写小型诊断脚本。

AI 容易失败在：

- 编造不存在的设置/命令；
- 把旧版本步骤说成当前步骤；
- 根据一个症状过度确定原因；
- 忽略平台差异；
- 给出具有破坏性的命令。

正确工作流是：

现象与日志 → AI 提出假设 → 官方文档/实测验证 → 一次改一个变量 → 回滚或确认。

不要直接执行涉及删除、磁盘、注册表、权限、固件、账户和加密的高风险命令。

## 8. 蓝屏：Stop Code 只是分类，不是最终病因

Windows 蓝屏表示内核发现无法安全继续运行的严重错误。

同一个 Stop Code 可能由驱动、内存、存储、硬件、内核组件、第三方安全软件、超频或不稳定配置等多种因素触发。

因此“搜蓝屏代码然后按第一篇文章操作”不是可靠诊断。

## 9. 内存转储为什么有价值

系统崩溃时可以保存 dump，其中可能包含 bug check code、CPU/线程上下文、内核调用栈、已加载模块、驱动信息和部分或全部内存状态。

常见级别从小型转储到内核/自动/活动/完整转储不等。信息越多，文件通常越大。

对普通蓝屏排查，小型或自动/内核转储往往比完全不留证据有价值得多。

## 10. WinDbg 的正确理解

WinDbg 是微软调试器。分析 dump 时常见入口是 !analyze -v。

但不要只盯 PROCESS_NAME、MODULE_NAME、IMAGE_NAME 就宣布某程序是罪魁祸首。

原因：

- 当前进程可能只是受害者；
- ntoskrnl.exe 等内核模块频繁出现在栈中，并不意味着内核本身坏了；
- 驱动栈、异常参数、调用栈、符号解析和硬件测试都可能需要结合；
- 多次 dump 的共同模式比单次结果更可信。

正确方式是把 dump 当作证据之一，而不是自动判决书。

## 11. 一套蓝屏排查树

1. 保存最近几次 dump；
2. 记录是否发生在相同动作；
3. 用 WinDbg 初步分析；
4. 比较多次 dump 是否指向共同驱动/模块；
5. 检查最近驱动、系统、硬件和 BIOS/固件变化；
6. 查看设备管理器和事件日志；
7. 需要时做内存、存储和稳定性测试；
8. 更新或回退有明确证据关联的驱动；
9. 每次修改后观察是否复现；
10. 涉及硬件保修或重要数据时，先备份再继续测试。

## 12. 重装系统为什么不是首选

重装可以同时清除很多变量，因此容易让软件层问题消失，但它也会破坏现场、无法确认根因、耗费恢复时间、可能丢数据，而且无法修复真实硬件问题。

它可以是最后手段，而不是第一诊断手段。

## 13. 学一个软件时，建立“可迁移模型”

不要只记按钮位置。优先理解：

- 它解决什么任务；
- 输入和输出是什么；
- 数据保存在哪里；
- 什么是项目/文档/工作区；
- 常用快捷键；
- 配置和插件在哪里；
- 如何备份、导出和恢复；
- 出问题时日志在哪里；
- 官方文档在哪里。

这样版本换界面时仍能快速迁移。

## 14. 最小练习

选择自己最近遇到的一个真实问题，写出环境、复现步骤、错误原文、三个可能原因、每个原因的验证动作和最终证据。

没有真实问题时，可以用应用崩溃、磁盘空间不足或网络失败作为模拟案例。

## 15. 从收藏链接走向可检查的阅读集合

收藏夹可以保留注意力线索，却不能代替阅读记录。先区分“保存过、待核验、正在读、读过、能解释、能独立应用”；AI整理出的目录和完成的资料吸收，也不自动把你的学习状态改成已掌握。

一个可本地实现的四阶段流程是：保留原始收藏及层级，按明确URL策略分组，用可解释规则排序，再单独导出阅读顺序和自报进度。下面只讨论资料整理，不访问链接，也不依赖远程模型。

### 15.1 导入时保留来源，而非只留下一个新标题

先把浏览器导出格式转换到明确的输入边界。例如JSON树中的文件夹含title/children，书签含唯一id、title、url和可选notes：

```json
[
  {"title":"地图","children":[
    {"title":"基础","children":[
      {"id":"a","title":"Map basics","url":"https://EXAMPLE.invalid:443/maps#intro","notes":"Read this map first"}
    ]}
  ]}
]
```

展开后的a保留`folders=["地图","基础"]`及原URL，而非将它改写后覆盖。每次递归复制祖先数组，不能让兄弟节点共用一个可变路径；分组后的成员也应独立复制。重复id、缺标题、非字符串notes、URL凭据或不支持协议应在入口报错，空集合则是合法结果。

设置树深、节点数和输入大小上限；区分folder/bookmark两种对象，避免一个意外children字段让书签悄悄被当文件夹。示例项目的32层是教学限制，不是浏览器统一标准。它只读上述JSON树，没有实现任意Netscape书签HTML导入；增加适配器时也要回到同样的数据校验边界。

### 15.2 按策略归一URL，不捏造内容去重

保留原URL，另算group_key，记录策略版本及分组原因。示例策略使用URL解析器的规范表示，再删除fragment：

| 原地址/差别 | 该策略的结果 | 应保留的判断 |
|---|---|---|
| `https://EXAMPLE.invalid:443/maps#intro`与同页`#scale` | 分为同一文档组 | 仍保两份原地址和原先阅读位置 |
| `/maps?view=print`与`/maps` | 不合并 | query可能改变页面，不能凭参数名字删除 |
| `/Maps`与`/maps` | 不合并 | 不假定服务端路径忽略大小写 |
| `/maps/`与`/maps` | 不合并 | 不假定服务端会重定向到同一内容 |
| HTTP与HTTPS | 不合并 | 协议是身份的一部分 |

即使两个group_key相同，也只证明“当前规则将它们归为一组”。没有下载正文或核内容摘要，不能称逐字内容相同；网站本身也可能已更新。对于用`#route`切换内容的单页应用，删除fragment可能误合不同页面，需要例外策略。原网址、各成员标题、备注、来源文件夹和合并关系都要保留，以便撤回或重分组。

样本12份收藏得到11个文档组，表示有一组两成员，不表示已经读了11篇，也不表示访问过这些URL。组内原始记录和展示主记录分开维护，不能只保首条然后永久丢掉第二条备注。

### 15.3 关键词分数是相关性线索，不是先修关系

对用户指定主题的每个不重复关键词w，可给一个组计算：

```text
score(w) = 3 × [任一成员标题包含完整token w]
         + 1 × [任一成员备注包含完整token w]
topic_score = 该主题所有不同关键词分数之和
```

标题Map basics命中map得3，备注Read this map first再得1，合计4；同一个标题重复保存不会再加3。Mapping是另一个token，不命中map。新保存的备注如果带来此前没有的关键词证据，组分数仍可变化。每次命中保留“哪个主题、哪个词、标题/备注各得几分”，让用户知道为什么排到前面。

同一关键词出现在不同主题时，示例会分别计分，不能把总分叫“全局关键词去重计数”。零分资料保留，表示规则未命中，不表示没有价值。权重3/1也是透明的教学规则，没有证明标题一定比备注可靠三倍。

实现的连续Unicode字母/数字段匹配不等于中文分词、词形还原或短语理解。“地图基础”未必能命中“地图”；前后空格、组合字符和多词关键词都需要明确规范化与匹配政策。分数相同用稳定ID排序时，也要固定比较规则，不能依赖各环境不同的默认locale排序。

最关键的是：关键词越相关，不代表越适合先读。它没有验证专业性、时效、难度和先修知识。可在排序后人工补“矩阵乘法→线性变换→注意力”的先修边；需要自动排序时，先检查依赖缺项和环，再对已经满足先修的候选按相关性排序。示例项目把先修边列为扩展，并未实现这个图算法。

### 15.4 进度与收藏内容分别版本化

最小进度文件可以保存：

```json
{"schemaVersion":1,"order":["b","a"],"completed":["a"]}
```

order必须是当前ID的完整置换；不得漏项、重复或混入旧ID。completed是唯一已知ID的子集。对当前集合`[a,b]`，该文件表示先显示b再显示a，并将a勾为已读；`[a,a]`不能作为合法顺序。

只有ID相同仍不够：如果a被复用于另一URL，旧完成状态可能套到新内容。实际系统还应绑定收藏内容摘要、去重策略版本与稳定组身份，新增/删除/重新分组时输出迁移冲突。以“第一份保存记录的ID”作组ID实现简单，但成员顺序变动可能改变身份，不宜隐瞒这一点。

页面的移动和勾选先改变内存状态；要下载progress.json并再次导入，才能跨这两次运行恢复。它不自动等于持久数据库、多端同步或真实阅读证据。Read勾选更不是理解/复习/应用验收；可以另记复述、检查题、实践结果和下一次复习日期。

展示文本可用textContent，嵌入JSON需避免关闭script的数据变成代码；链接href还必须经过协议校验，文本转义不能代替URL校验。文件下载、导入成功和收藏全部有效也分别验收，不把生成了HTML当成链接可访问或资料仍正确。

### 15.5 自检与实践

先用三条自造收藏手算组和分数，再导出进度；不用抓取网页就能核数据合同。回答：删除所有query能否安全去重？同ID一定是同版资料吗？零分资料是否无用？Read是否证明掌握？参考判断均是否；分别需要语义政策、内容版本、更多价值依据和实际学习证据。

原样本的独立静算为12条、11组、分数总和27；两个5分项初始按ID排，页面截图中的顺序还包含作者点击移动后的编辑结果，不能拿它反驳初始排序规则。动态效果与静态输入分别保存。本库没有操作读者的真实收藏，也没有访问这些示例链接。

## 16. 从“相关资料”到“可行学习路线”

收藏整理回答“哪些材料可能相关”；学习路径还要回答“必须先学什么、这次时间够不够、没选上的目标为何没覆盖”。先把用户明确给出的目标与资源目录转成约束，再计算顺序。算法不能仅凭收藏、标签、点击或AI整理的笔记推断读者已经掌握某项知识。

这里使用小目录的精确规划作为可手算的工程例子。四阶段分别建立目录、计算先修闭包、按预算比较路线、导出并校验自报进度。它不依赖模型或网络，也没有测量授课质量和学习者能力；适合工作坊、课程模块和个人短期阅读清单，不能直接作为职业能力认证。

### 16.1 阶段一：让资源与先修关系成为可校验的数据

每份资源至少保留：稳定的`id`、`title`、正整数`minutes`、目标集合`goals`、先修ID集合`prerequisites`。标题服务于展示，ID服务于关联；把标题直接当ID容易因改名破坏进度。

| ID | 资源 | 时间/分钟 | 满足的目标 | 先修 |
|---|---|---:|---|---|
| basics | 坐标基础 | 15 | 无直接目标 | 无 |
| collect | 采集邻里坐标点 | 25 | collect | basics |
| publish | 发布社区地图 | 30 | map | collect |
| quick-map | 制作纸面地图 | 45 | map | 无 |
| advanced | 覆盖分析 | 40 | analysis | statistics、collect |

目录里没有statistics。这不是一份零分钟课程，而是待补的外部先修。可在外部完成情况中明确声明已满足；不能偷偷删除这条边，让advanced看起来可行。

如果用边`先修→后续资源`作图，例子有`basics→collect→publish`，还有`collect→advanced`与`statistics→advanced`。代码中的prerequisites则从后续资源反查先修，遍历方向相反；须把约定写清楚。

入口校验要做三件事：

1. 检查资源字段与身份：ID和标题为非空字符串，ID唯一；参考实现未剥离仅含空白的名字，应按实际输入政策另核；minutes是正整数而不是布尔值；goals和prerequisites都是由非空字符串组成、元素不重复的列表；列表本身可以为空。先深复制，避免外部调用者修改输入后悄悄改变目录。
2. 保留外部先修缺项。未知ID是一类可解释状态，不与“目录内存在的环”混为一谈。
3. 用三色DFS检测已知资源的环：未访问、正在递归、已完成。重新遇到“正在递归”的节点说明存在先修环；共享先修多次遇到“已完成”节点则正常。`a需要b，b需要a`应拒绝，`b和c都需要a`不应误报。

该教学实现将目录限制为18项，因为后续采用指数规模的精确搜索。18不是学习科学阈值，也不是图算法本身的限制。真实入口还需限制文件大小、字符串长度、嵌套深度和允许字段，并验证最外层是资源列表、每个元素是对象；来源实现主要校验字段，没有把所有畸形JSON都统一转换成ValueError。

### 16.2 阶段二：先求依赖闭包，再讨论这条路线是否值得学

目标资源的先修闭包是“要做它，还必须做的所有尚未完成资源”。DFS后序遍历自然得到先修在前的顺序：先访问它的先修，最后加入该资源。维护seen防止共享先修重复进入路线。示意算法如下；输入目录已通过环检测：

```text
path_for(目录, 目标ID, 已完成集合):
    已见 = 空集合；步骤 = 空列表；缺项 = 空集合
    访问(ID):
        如果ID已完成或已见：返回
        记为已见
        如果ID不在目录：加入缺项，返回
        按稳定ID顺序访问它的每个先修
        将ID加入步骤
    访问(目标ID)
    时间 = 步骤中每项minutes之和
    返回 步骤、排序后的缺项、时间、可行=(缺项为空)
```

在没有已完成资源时：

| 查询 | 已知步骤 | 计入的时间 | 缺项 | 可行性 |
|---|---|---:|---|---|
| publish | basics、collect、publish | 70 | 无 | 可行 |
| advanced | basics、collect、advanced | 80 | statistics | 不可行 |
| unknown-course | 无 | 0 | unknown-course | 不可行 |

advanced的80分钟只是目录中已知部分，不能称其完整学习成本为80分钟；statistics缺项的时间、内容和有效性尚未知。若basics已完成，publish路线变为collect、publish，共55分钟。若明确已完成外部statistics，advanced可行，但仍需basics、collect、advanced的80分钟。

来源将completed视为调用方认可的先修边界：它能满足目录外ID，也会直接截断已完成资源的继续追溯。因此，如果调用方错误声明publish已完成而从未完成collect，算法不会回头证明这个声明是真的。正式系统应把“自报已学”“测验通过”“复习后仍能完成任务”等状态和证据分开管理；不要把这个简化completed集合称为可靠能力模型。

path_for不接收预算。80分钟的可行闭包可能超过本次75分钟预算；“缺先修”与“时间不够”必须分开解释。

### 16.3 阶段三：比较整条闭包，避免独立选课后才发现超时

设用户请求的目标集合为G，已完成资源集合为D，候选新资源集合为S。合法方案要满足：S中的每一项，其先修已在D或S中；新增时间`T(S)=Σ minutes(r)`不超过预算B。已完成资源提供的目标也参与覆盖，但不重复收费。

定义覆盖为`C(S)=(S和D中已知资源的goals并集)∩G`。来源采用明确的字典序目标：先最大化不同目标数`|C(S)|`，再最小化T(S)，最后按确定性的先修顺序ID序列打破平局。它没有给目标设权重，也没有区分同一目标下课程的深度、教学质量与测验效果。

实现不把每条路线的分钟直接相加，而是合并其资源ID集合再求和。例如collect闭包40分钟，publish闭包70分钟；同时要这两个目标，合并后仍是70分钟，不能误算110分钟。否则共享的basics和collect会被收费两遍。

一种可检查的精确策略是：

```text
候选路线 = 对每个能覆盖至少一个请求目标的资源求闭包
将有缺项的路线单独记录；只让无缺项路线参与规划
方案表最初只有空方案（它仍可能拥有已完成资源提供的目标）
对每条候选路线：
    冻结当前方案表的一份快照
    对快照中的每个方案：
        新成员集合 = 旧成员集合 ∪ 路线步骤集合
        若新集合未出现且总时间不超预算：
            重新构造先修顺序、覆盖目标、未覆盖目标
            将结果存入方案表
按 (-覆盖数, 分钟, 步骤ID序列) 排序，取最佳与前3个不同方案
```

冻结一轮的旧方案可避免在同一遍迭代中把新方案反复当旧方案扩展。用frozenset一类不可变集合标识方案，防止不同组合顺序把相同资源集合重复统计。n项资源最多有`2^n`种子集，18项是262144种；实际还受预算和闭包合并去重影响。这仍是小规模精确方法，不能对几万篇收藏照搬全子集搜索。

样例请求`[map, collect, analysis]`、预算75分钟、没有既往完成时，实际有学习价值的可行候选比较为：

| 方案 | 分钟 | 覆盖 | 未覆盖 | 解释 |
|---|---:|---|---|---|
| basics→collect→publish | 70 | collect、map | analysis | 覆盖2个目标，最佳 |
| basics→collect | 40 | collect | analysis、map | 覆盖1个，时间比下一项少 |
| quick-map | 45 | map | analysis、collect | 覆盖1个，可作为另一方向 |
| 空方案 | 0 | 无 | 3个目标 | 合法保底，不表示学到了内容 |

advanced因为statistics缺失不参与可行方案排序，`unmet_prerequisites`仍应记录`target=advanced, missing=[statistics]`。即便map有其他可行路线，某条路线缺先修也不能因目标已被覆盖而从缺项说明中消失。反过来，这份缺项清单含有未选路线的情况，不意味着整个最佳路线不可行。

该样例原始闭包基础是70分钟，不是90分钟。预算0或39时最佳为空；预算40到69时最佳为basics、collect；预算70起能覆盖collect和map。若basics已完成，collect门槛降为25分钟，publish闭包降为55分钟。若statistics已完成而预算仍75，缺项消失，analysis仍因需要80分钟未覆盖；预算增到110时可把basics、collect、advanced、publish全部纳入，覆盖三个目标。

这里的`alternatives`是排序后的前3项，**包含best本身**，不是best之外再给3个备选。消费者应明示这一合同，避免界面重复展示四条或错称四个不同方案。

“覆盖两个目标”仅表示目录标签覆盖，不等于掌握两个技能。若用户只要map，quick-map的45分钟会胜过publish闭包的70分钟，但这不证明纸面地图与发布平台在真实能力上等价；需要先修订目标定义、质量门槛或必修约束，再重新求解。

### 16.4 阶段四：把计划、进度与实际学习证据分开

导出时保留`schema_version=1`、目录/目标/预算/旧完成状态的fingerprint、有序path、alternatives、未满足先修、planned_minutes和remaining_minutes。path每项保原ID、先修、时间、标题、goals、completed和reason，让课程平台按数组顺序导入，而不是自己再按标题排序。参考export只浅复制记录，goals/prerequisites列表仍可与目录共享；对可修改的外部消费者要深复制或使用不可变快照，不能将目录入口的一次deepcopy当作整条管线都不可变。

来源的reason有两类：当前资源本身覆盖目标时写出交集；否则写“所选目标的先修”。这解释的是选择依据，不是推荐理由的全部细节。需要更精确时，可增加“为哪个目标、哪条先修边而入选”，以及被更便宜方案替代的原因。

75分钟样例原计划是70分钟。给这份计划回传：

```json
{
  "fingerprint": "21e0bf3eebd4b2e2e7e335fae95ea604d9c63de41046352065cde5aec2e360ef",
  "completed": ["basics"]
}
```

原planned_minutes保持70；basics变为已完成，remaining_minutes变为55。回执只将原计划中的步骤标记完成，不重新选路线，不把未用的5分钟自动分给另一个目标。若要按新的既往完成状态重规划，应明确另起一次规划并产生新指纹。

导入至少检验：

- 指纹与当前原计划一致，防止目录、预算或旧完成状态变动后套用陈旧回执；
- completed没有重复ID，且只包含当前最佳计划的步骤；不能凭回执加入另一个备选路线；
- 每个新增完成项的先修，已经在旧完成集合或同一批新增完成集合中。

所以`completed=[publish]`应被拒绝；`[basics,collect]`可接受，剩30分钟；把三项一起提交可接受，剩0分钟。但来源实际上按**整批集合**检查依赖，不检查数组顺序或学习时间戳，`[publish,collect,basics]`也满足同一集合约束。不能说它验证了“先做完基础再做发布”的真实学习顺序。

来源指纹以Python的`json.dumps(sort_keys=True)`序列化目录、目标列表、预算和排序后的旧完成ID，再取SHA-256。对固定样例，自写数据复算得到上面的值，与作者截图里的指纹一致；这只是静态数据一致性检查。列表顺序仍影响指纹：调换goals顺序即便目标集合相同，也可能使旧回执失效。这不是标准化JSON规范或电子签名；只要可以改写本地数据，就能另算指纹，不能由它证明学习者身份、真实学习过程或测验成功。

入口还应明确completed必须是字符串ID列表、decisions必须是对象、列表长度受限。来源对这些类型的验证不足：某些短字符串会被set当字符集合，混合类型、对象或缺字段可能触发TypeError、AttributeError、KeyError，而不是API承诺的统一ValueError。不要把“固定样例通过”写成“任意不可信输入均安全拒绝”。

导出的path只含本次未完成步骤，不把原先完成的目录内/外资源再抄一遍。跨平台消费时必须同时保留计划指纹绑定的旧完成上下文，否则消费者可能看到prerequisite不在path中就误判缺项，或无根据地视其已满足。

HTML只负责展示、编辑和下载decisions.json；下载前的JSON.parse检查语法，不检查依赖、身份或指纹。必须回到可信导入器校验后才更新状态。表格/textarea中的文本应HTML转义，程序交换仍用JSON。来源CLI依次写JSON、缺项JSON和HTML，没有事务式发布；正式工具宜把同一结果快照写进临时目录、全部成功后再发布，避免只生成一半的产物被当完整计划。

### 16.5 图示、测试与实践边界

来源的四幅交互图标题分别对应目录、闭包、排序和进度，但四个calculate函数实际相同：只按“basics是否完成”和时间阈值，在空路线、collect路线、publish完整路线间切换。它们没有运行完整目录校验、statistics缺项判断、多个目标组合搜索、指纹或完成回执导入；第4幅图的变化也不是实际进度导入成功。图可用于手算预算门槛，不能替代四阶段实现或测试。

四份阶段测试各5个方法，共20个，仅静态阅读。它们覆盖身份/环/零时长、简单闭包/外部完成、便宜路线/预算/已有目标、回执门禁/陈旧指纹/JSON往返，但没完整覆盖18项边界、布尔时长、所有畸形类型、多路线共享先修、同批逆序进度及输出中断。作者2026-10-09日志记录参考实现四阶段通过；本次没有运行原程序、评分器、CLI、源JS或网页交互，也没有据此改变用户学习状态。

可用以下练习自检；先自己预测，再看判断标准：

1. 想同时完成collect与map，能否把40和70相加判超时？**不能。** 合并ID后共享先修只算一次，总70。
2. advanced已知部分80分钟，但statistics不在目录，是否可以列为80分钟可行路线？**不能。** 缺项时间未知；补上资源或声明可信既往完成后才可重算。
3. 预算75且statistics已完成，analysis为何仍未覆盖？**不是缺项，而是其闭包需80分钟。** 应分别解释约束。
4. `[publish,collect,basics]`全部同批提交是否被该实现拒绝？**不会。** 它检查集合闭包，不证明历史顺序。需要时间顺序就增加独立事件合同。
5. matching fingerprint和remaining_minutes=0是否证明掌握？**都不能。** 它们证明计划版本与自报状态一致；掌握应另有复述、测验、实际任务与复习证据。
6. 当目录扩展到1000项时，是否只把18改成1000？**不能。** 先明确目标权重、必修/互斥约束、时间不确定性和规模，再选择有界搜索、整数规划或可解释近似方案，并标注是否找到最优解；不能维持“精确最优”的名义却悄悄改成贪心。
