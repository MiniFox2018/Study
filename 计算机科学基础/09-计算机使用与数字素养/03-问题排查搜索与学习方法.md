# 03｜问题排查、搜索与学习方法

## 1. 第一任务不是找“万能修复按钮”

故障排查本质是缩小可能原因。

推荐顺序：

1. 明确现象；
2. 明确预期；
3. 记录环境；
4. 找到稳定复现步骤；
5. 收集错误信息；
6. 提出几个可能原因；
7. 一次只改变一个变量；
8. 验证结果；
9. 记录最终原因与修复方式。

一上来就重装软件、清注册表、重装系统，即使问题消失，也很可能没有知道真正原因。

## 2. 把“不能用”写成可诊断的问题

好的问题应包含：

- 软件/系统版本；
- 从什么时候开始；
- 具体操作；
- 实际结果；
- 预期结果；
- 完整错误文字或截图；
- 最近改动；
- 已尝试措施；
- 是否稳定复现。

例如：“Windows 上双击某项目 app.exe 后窗口闪退；事件日志显示某 DLL 加载失败；昨天升级驱动后开始出现；同目录另一版本可运行。”这已经把搜索空间大幅缩小。

## 3. 先保存错误原文

优先保存错误代码、异常名称、日志、时间、崩溃模块、命令输出、截图和可重现输入。

技术问题中，一个完整错误码往往比一段主观描述更有价值。

## 4. 搜索时使用高信息密度关键词

有效搜索通常由：

产品/组件 + 错误原文 + 环境 + 关键动作

组成。

搜索结果优先级：

1. 官方文档/官方 issue；
2. 上游项目仓库；
3. 高质量技术社区；
4. 有证据和版本上下文的博客；
5. 聚合转载；
6. 无来源“万能修复”文章。

发布时间不是唯一标准，但涉及 UI、API、驱动、安装和云服务时，时间非常重要。

## 5. 怎样判断教程质量

至少检查作者、是否引用官方资料、更新时间、适用版本、是否解释原理、是否写风险和回滚、评论/issue 是否指出失效，以及是否只是机器翻译/洗稿。

官方文档通常最权威，但不一定最适合入门。高质量学习往往是“教程建立模型，官方文档校验细节”。

## 6. 提问的艺术

向人求助时：

- 给出最小复现；
- 隐去密码、Token、身份证、私钥等敏感内容；
- 代码使用文本而不是模糊截图；
- 说明已经查过什么；
- 不要预设原因，例如“肯定是 Windows 的 bug”。

提问质量本身也是排障能力。

## 7. AI 可以帮助排障，但不能代替证据

AI 擅长解释错误信息、设计排查树、整理日志、生成搜索关键词、解释官方文档和编写小型诊断脚本。

AI 容易失败在：

- 编造不存在的设置/命令；
- 把旧版本步骤说成当前步骤；
- 根据一个症状过度确定原因；
- 忽略平台差异；
- 给出具有破坏性的命令。

正确工作流是：

现象与日志 → AI 提出假设 → 官方文档/实测验证 → 一次改一个变量 → 回滚或确认。

不要直接执行涉及删除、磁盘、注册表、权限、固件、账户和加密的高风险命令。

## 8. 蓝屏：Stop Code 只是分类，不是最终病因

Windows 蓝屏表示内核发现无法安全继续运行的严重错误。

同一个 Stop Code 可能由驱动、内存、存储、硬件、内核组件、第三方安全软件、超频或不稳定配置等多种因素触发。

因此“搜蓝屏代码然后按第一篇文章操作”不是可靠诊断。

## 9. 内存转储为什么有价值

系统崩溃时可以保存 dump，其中可能包含 bug check code、CPU/线程上下文、内核调用栈、已加载模块、驱动信息和部分或全部内存状态。

常见级别从小型转储到内核/自动/活动/完整转储不等。信息越多，文件通常越大。

对普通蓝屏排查，小型或自动/内核转储往往比完全不留证据有价值得多。

## 10. WinDbg 的正确理解

WinDbg 是微软调试器。分析 dump 时常见入口是 !analyze -v。

但不要只盯 PROCESS_NAME、MODULE_NAME、IMAGE_NAME 就宣布某程序是罪魁祸首。

原因：

- 当前进程可能只是受害者；
- ntoskrnl.exe 等内核模块频繁出现在栈中，并不意味着内核本身坏了；
- 驱动栈、异常参数、调用栈、符号解析和硬件测试都可能需要结合；
- 多次 dump 的共同模式比单次结果更可信。

正确方式是把 dump 当作证据之一，而不是自动判决书。

## 11. 一套蓝屏排查树

1. 保存最近几次 dump；
2. 记录是否发生在相同动作；
3. 用 WinDbg 初步分析；
4. 比较多次 dump 是否指向共同驱动/模块；
5. 检查最近驱动、系统、硬件和 BIOS/固件变化；
6. 查看设备管理器和事件日志；
7. 需要时做内存、存储和稳定性测试；
8. 更新或回退有明确证据关联的驱动；
9. 每次修改后观察是否复现；
10. 涉及硬件保修或重要数据时，先备份再继续测试。

## 12. 重装系统为什么不是首选

重装可以同时清除很多变量，因此容易让软件层问题消失，但它也会破坏现场、无法确认根因、耗费恢复时间、可能丢数据，而且无法修复真实硬件问题。

它可以是最后手段，而不是第一诊断手段。

## 13. 学一个软件时，建立“可迁移模型”

不要只记按钮位置。优先理解：

- 它解决什么任务；
- 输入和输出是什么；
- 数据保存在哪里；
- 什么是项目/文档/工作区；
- 常用快捷键；
- 配置和插件在哪里；
- 如何备份、导出和恢复；
- 出问题时日志在哪里；
- 官方文档在哪里。

这样版本换界面时仍能快速迁移。

## 14. 最小练习

选择自己最近遇到的一个真实问题，写出环境、复现步骤、错误原文、三个可能原因、每个原因的验证动作和最终证据。

没有真实问题时，可以用应用崩溃、磁盘空间不足或网络失败作为模拟案例。

## 15. 从收藏链接走向可检查的阅读集合

收藏夹可以保留注意力线索，却不能代替阅读记录。先区分“保存过、待核验、正在读、读过、能解释、能独立应用”；AI整理出的目录和完成的资料吸收，也不自动把你的学习状态改成已掌握。

一个可本地实现的四阶段流程是：保留原始收藏及层级，按明确URL策略分组，用可解释规则排序，再单独导出阅读顺序和自报进度。下面只讨论资料整理，不访问链接，也不依赖远程模型。

### 15.1 导入时保留来源，而非只留下一个新标题

先把浏览器导出格式转换到明确的输入边界。例如JSON树中的文件夹含title/children，书签含唯一id、title、url和可选notes：

```json
[
  {"title":"地图","children":[
    {"title":"基础","children":[
      {"id":"a","title":"Map basics","url":"https://EXAMPLE.invalid:443/maps#intro","notes":"Read this map first"}
    ]}
  ]}
]
```

展开后的a保留`folders=["地图","基础"]`及原URL，而非将它改写后覆盖。每次递归复制祖先数组，不能让兄弟节点共用一个可变路径；分组后的成员也应独立复制。重复id、缺标题、非字符串notes、URL凭据或不支持协议应在入口报错，空集合则是合法结果。

设置树深、节点数和输入大小上限；区分folder/bookmark两种对象，避免一个意外children字段让书签悄悄被当文件夹。示例项目的32层是教学限制，不是浏览器统一标准。它只读上述JSON树，没有实现任意Netscape书签HTML导入；增加适配器时也要回到同样的数据校验边界。

### 15.2 按策略归一URL，不捏造内容去重

保留原URL，另算group_key，记录策略版本及分组原因。示例策略使用URL解析器的规范表示，再删除fragment：

| 原地址/差别 | 该策略的结果 | 应保留的判断 |
|---|---|---|
| `https://EXAMPLE.invalid:443/maps#intro`与同页`#scale` | 分为同一文档组 | 仍保两份原地址和原先阅读位置 |
| `/maps?view=print`与`/maps` | 不合并 | query可能改变页面，不能凭参数名字删除 |
| `/Maps`与`/maps` | 不合并 | 不假定服务端路径忽略大小写 |
| `/maps/`与`/maps` | 不合并 | 不假定服务端会重定向到同一内容 |
| HTTP与HTTPS | 不合并 | 协议是身份的一部分 |

即使两个group_key相同，也只证明“当前规则将它们归为一组”。没有下载正文或核内容摘要，不能称逐字内容相同；网站本身也可能已更新。对于用`#route`切换内容的单页应用，删除fragment可能误合不同页面，需要例外策略。原网址、各成员标题、备注、来源文件夹和合并关系都要保留，以便撤回或重分组。

样本12份收藏得到11个文档组，表示有一组两成员，不表示已经读了11篇，也不表示访问过这些URL。组内原始记录和展示主记录分开维护，不能只保首条然后永久丢掉第二条备注。

### 15.3 关键词分数是相关性线索，不是先修关系

对用户指定主题的每个不重复关键词w，可给一个组计算：

```text
score(w) = 3 × [任一成员标题包含完整token w]
         + 1 × [任一成员备注包含完整token w]
topic_score = 该主题所有不同关键词分数之和
```

标题Map basics命中map得3，备注Read this map first再得1，合计4；同一个标题重复保存不会再加3。Mapping是另一个token，不命中map。新保存的备注如果带来此前没有的关键词证据，组分数仍可变化。每次命中保留“哪个主题、哪个词、标题/备注各得几分”，让用户知道为什么排到前面。

同一关键词出现在不同主题时，示例会分别计分，不能把总分叫“全局关键词去重计数”。零分资料保留，表示规则未命中，不表示没有价值。权重3/1也是透明的教学规则，没有证明标题一定比备注可靠三倍。

实现的连续Unicode字母/数字段匹配不等于中文分词、词形还原或短语理解。“地图基础”未必能命中“地图”；前后空格、组合字符和多词关键词都需要明确规范化与匹配政策。分数相同用稳定ID排序时，也要固定比较规则，不能依赖各环境不同的默认locale排序。

最关键的是：关键词越相关，不代表越适合先读。它没有验证专业性、时效、难度和先修知识。可在排序后人工补“矩阵乘法→线性变换→注意力”的先修边；需要自动排序时，先检查依赖缺项和环，再对已经满足先修的候选按相关性排序。示例项目把先修边列为扩展，并未实现这个图算法。

### 15.4 进度与收藏内容分别版本化

最小进度文件可以保存：

```json
{"schemaVersion":1,"order":["b","a"],"completed":["a"]}
```

order必须是当前ID的完整置换；不得漏项、重复或混入旧ID。completed是唯一已知ID的子集。对当前集合`[a,b]`，该文件表示先显示b再显示a，并将a勾为已读；`[a,a]`不能作为合法顺序。

只有ID相同仍不够：如果a被复用于另一URL，旧完成状态可能套到新内容。实际系统还应绑定收藏内容摘要、去重策略版本与稳定组身份，新增/删除/重新分组时输出迁移冲突。以“第一份保存记录的ID”作组ID实现简单，但成员顺序变动可能改变身份，不宜隐瞒这一点。

页面的移动和勾选先改变内存状态；要下载progress.json并再次导入，才能跨这两次运行恢复。它不自动等于持久数据库、多端同步或真实阅读证据。Read勾选更不是理解/复习/应用验收；可以另记复述、检查题、实践结果和下一次复习日期。

展示文本可用textContent，嵌入JSON需避免关闭script的数据变成代码；链接href还必须经过协议校验，文本转义不能代替URL校验。文件下载、导入成功和收藏全部有效也分别验收，不把生成了HTML当成链接可访问或资料仍正确。

### 15.5 自检与实践

先用三条自造收藏手算组和分数，再导出进度；不用抓取网页就能核数据合同。回答：删除所有query能否安全去重？同ID一定是同版资料吗？零分资料是否无用？Read是否证明掌握？参考判断均是否；分别需要语义政策、内容版本、更多价值依据和实际学习证据。

原样本的独立静算为12条、11组、分数总和27；两个5分项初始按ID排，页面截图中的顺序还包含作者点击移动后的编辑结果，不能拿它反驳初始排序规则。动态效果与静态输入分别保存。本库没有操作读者的真实收藏，也没有访问这些示例链接。
