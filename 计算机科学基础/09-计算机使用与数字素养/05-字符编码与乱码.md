# 05｜字符编码与乱码

## 1. 电脑只存数字，文字需要约定

文本处理至少有三层：

字符 → 码位 → 字节编码

例如一个抽象字符需要先在字符集合中得到编号，再按某种编码方式转换成实际字节。

把这三层混在一起，是理解乱码时最常见的困难。

## 2. 二进制、十六进制为什么重要

一字节通常是 8 bit，可表示 0～255。

二进制适合解释位结构，但太长；十六进制每一位正好对应 4 bit，所以调试编码时非常常见。

例如十六进制 E7 9B 98 由三个字节组成。

## 3. ASCII：历史基础

ASCII 为英文字母、数字、标点和控制字符分配编号，原始核心只需要 7 bit。

它的重要意义是：

- 奠定文本编码基础；
- UTF-8 保持 ASCII 0～127 的字节兼容；
- 很多协议和编程语言语法仍以 ASCII 子集为基础。

ASCII 无法直接表示中文等大量文字。

## 4. 代码页与“各说各话”的年代

在 Unicode 普及前，不同地区发展了不同字符集和编码。

例如中文环境中使用过 GB 系列编码。

如果程序 A 用一种代码页写字节，程序 B 用另一种代码页解释，同一组字节就会被解读为不同字符，形成乱码。

这就是“字节没坏，解释规则错了”。

## 5. Unicode 解决的是“统一字符编号”

Unicode 为字符分配 code point，通常写成 U+XXXX。

注意：Unicode 码位不是某种具体磁盘字节格式。

同一个 Unicode 字符可以用 UTF-8、UTF-16、UTF-32 等不同编码序列表示。

## 6. UTF-8

UTF-8 是变长编码：

- ASCII 范围使用 1 字节；
- 其他字符使用 2～4 字节。

它的关键优势：

- 与 ASCII 兼容；
- 自同步特征较好；
- 不需要用端序解释单个字节；
- 网络和跨平台生态广泛。

例如“U盘”在 UTF-8 中：

U → 55  
盘 → E7 9B 98

“盘”占 3 字节。

## 7. UTF-16

UTF-16 以 16 bit code unit 为基础。

BMP 中多数常用字符用一个 16 bit 单元；更高码位使用 surrogate pair 两个 code unit。

因此：

- 一个 Unicode 字符不一定等于一个 UTF-16 单元；
- 某些语言/运行时的字符串 length 统计 code unit，不一定是用户感知字符。

UTF-16 还涉及大小端序；某些文件会用 BOM 指示端序。

## 8. UTF-32

UTF-32 固定每个 code point 用 32 bit 表示，索引直观，但空间开销大，实际文本交换中远不如 UTF-8 常见。

即使 UTF-32 固定 code point 宽度，也不能推出“一个用户看到的字符固定一个整数”，因为组合字符、emoji 序列等会让一个 grapheme 由多个 code point 组成。

## 9. GB18030

GB18030 是中国国家标准编码体系，能够表示广泛 Unicode 字符，并保持对早期 GB 编码的兼容。

在中国的软件、政企系统和历史数据中仍可能遇到。

因此现实中不能简单认为“所有文本都是 UTF-8”。

## 10. 字体不是编码

Unicode 决定“这是哪个字符”；字体决定“这个字符画成什么样”。

同一个码位可以因地区字体差异显示成不同字形。

反过来，长得很像的符号可能完全是不同码位，例如：

- 拉丁字母与西里尔字母的相似字符；
- 中文全角标点与 ASCII 半角标点；
- 各类兼容字符。

这会影响搜索、用户名、文件名、域名安全和程序解析。

## 11. 全角与半角不是单纯显示宽度

很多全角标点和半角标点是不同 Unicode 字符。

因此程序要求英文逗号 "," 时，输入中文逗号 "，" 可能报错。

排查“看起来一样但程序不认”时，应检查实际码位。

## 12. 乱码的三种常见来源

### 用错解码方式

文件实际是 UTF-8，却按 GBK 或其他编码读取。

### 错误转换后再次保存

原始字节被错误解释，再保存成新的字节，原始信息可能已经不可逆丢失，需要从备份或原来源恢复。

### 字体缺少字形

此时常出现方框/tofu，而不是典型乱码。字符码可能完全正确，只是字体不会画。

## 13. 如何修复乱码

先不要保存覆盖原文件。

步骤：

1. 保留原始字节副本；
2. 判断来源系统和可能编码；
3. 用编辑器尝试按不同编码重新打开，而不是转换后覆盖；
4. 找到正确显示后再明确转存为 UTF-8；
5. 程序中显式指定编码；
6. 跨系统传输时确认协议/文件格式是否自带编码声明。

## 14. 如何预防

- 新项目默认 UTF-8，除非协议要求其他编码；
- 文件读写显式指定 encoding；
- 数据库确认字符集和 collation；
- HTTP 正确声明 Content-Type/charset；
- CSV 与旧 Office 流程尤其注意编码；
- 不依赖系统默认编码；
- 测试中文、emoji、全角标点和组合字符。

## 15. 文本长度的三个不同问题

处理字符串时要问：

- 多少字节？
- 多少 code point？
- 用户眼里多少 grapheme cluster？

这对截断、用户名限制、光标移动、数据库字段和 UI 都很重要。

## 16. 最小练习

1. 用十六进制查看一个包含中文和英文的 UTF-8 文本。
2. 将同一文件故意按错误编码打开，观察乱码但不要覆盖。
3. 比较 "," 与 "，" 的 Unicode 码位。
4. 找一个 emoji，检查它占多少 UTF-8 字节、多少 code point。
5. 用两个不同字体显示同一段中日韩文本，观察“码位相同、字形可不同”。
