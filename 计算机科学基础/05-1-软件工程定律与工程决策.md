> 来源：用户提供的 *Laws of Software Engineering - Printable Card Deck*（28 页，56 张定律卡）。  
> 本文按原资料的 7 个分组完整吸收：Architecture、Teams、Planning、Quality、Scale、Design、Decisions。  
> 原卡牌以“命题 + 3 条要点”为主；下面保留其知识骨架，并增加中文解释、适用边界与工程用法，使本页可以独立学习。  
> **Study 补充说明**：这些内容混合了理论定律、工程经验、组织行为启发式和认知偏差。名称里有 “Law” 不等于它们都具有数学定理级别的普适性；实际使用时应把它们当作检查假设与设计取舍的工具。

### 使用方法

遇到工程问题时，不需要背诵 56 条。先问四类问题：

1. **系统**：我是否把复杂度、依赖或故障假设藏起来了？
2. **团队**：瓶颈是代码，还是沟通、所有权和关键人风险？
3. **计划**：估计、指标和“快完成”是否正在误导判断？
4. **决策**：我是在依据事实、约束和实验，还是依据惯性、投入和自信？

# 一、Architecture｜架构

## 1. Hyrum's Law｜海勒姆定律

**命题**：当 API 用户足够多时，系统所有可观察行为都会有人依赖。

**原资料要点**
- 可观察行为会逐渐形成事实上的隐式契约。
- 即使是 bug，也可能被外部调用方依赖；修复它可能成为破坏性变更。
- 真正的 API 不只等于文档规范，还包括用户在真实环境里观察到的行为。

**工程用法**
- 发布公共 API 时，尽量缩小可观察面，明确哪些行为受保证。
- 修改默认值、错误码、排序、时序、空值处理、边界输出时，都应按兼容性变更审视。
- 对“本来就不该依赖”的行为，也要先调查实际依赖再决定迁移策略。

**边界**
- 这不是要求永远保留错误，而是提醒：修复错误也需要兼容性设计、废弃期或迁移说明。

## 2. Gall's Law｜盖尔定律

**命题**：能工作的复杂系统，通常由能工作的简单系统逐步演化而来。

**原资料要点**
- 复杂系统应从更小、已验证的核心逐步扩展。
- “一次性大设计”会把过多未知量叠在一起，难以及时验证。
- 每一次扩展都应接受真实环境检验。

**工程用法**
- 先做最小可运行纵切片，再增加缓存、分布式、插件化、异步化等复杂结构。
- 迁移大系统时优先采用可验证的增量替换，而不是先构造“完美终局”。

**边界**
- “从小做起”不代表无架构；仍需预先识别不可逆约束，例如数据模型、安全边界和合规要求。

## 3. Law of Leaky Abstractions｜抽象泄漏定律

**命题**：所有非平凡抽象都会在某些场景泄漏底层细节。

**原资料要点**
- 抽象会在边界条件、故障或性能问题中暴露底层机制。
- 使用高级工具并不意味着可以完全不懂下层原理。
- 抽象仍然必要，但设计时要考虑它失效时怎么办。

**工程用法**
- ORM 使用者仍应理解 SQL、事务和索引。
- 容器使用者仍应理解进程、文件系统、网络和资源限制。
- 云 SDK 使用者仍应理解超时、重试、幂等和配额。

**边界**
- 目标不是“拒绝抽象”，而是保持足够的下层心智模型用于诊断。

## 4. Tesler's Law｜特斯勒定律 / 复杂度守恒

**命题**：每个应用都存在一定不可约复杂度；复杂度可以转移，但不能凭空消失。

**原资料要点**
- 系统总有一部分复杂度无法删除。
- 如果用户需要承担太多步骤，说明复杂度被转移到了错误位置。
- 好设计往往把复杂度吸收到系统内部，让使用体验保持简单。

**工程用法**
- 把校验、默认配置、兼容处理和自动恢复放在更适合承担复杂度的一侧。
- API 设计要明确：复杂度由调用方、平台层还是基础设施层承担。

**边界**
- 内部“吸收复杂度”也有成本；不要为了表面简单制造不可维护的黑箱。

## 5. CAP Theorem｜CAP 定理

**命题**：发生网络分区时，分布式系统无法同时保证强一致性与完全可用性。

**原资料要点**
- 卡牌用 Consistency、Availability、Partition tolerance 三者的取舍解释 CAP。
- 网络分区无法被工程上彻底排除，因此真正困难的选择通常发生在分区期间的一致性与可用性之间。
- 数据系统的取舍应结合业务语义判断。

**工程用法**
- 先定义“一致”到底指线性一致、会话一致、最终一致还是业务层不变量。
- 再定义“可用”的服务承诺和分区时允许的降级。
- 对库存、支付、社交 Feed 等不同场景，不应套用同一策略。

**Study 边界补充**
- 不要把数据库永久贴成简单的“CP/AP”标签；实际行为会受配置、读写级别、拓扑与具体操作影响。

## 6. Second-System Effect｜第二系统效应

**命题**：一个小而成功的系统之后，团队容易设计出过度工程化、功能膨胀的“第二系统”。

**原资料要点**
- 第一版受约束而保持克制；第二版常失去这种纪律。
- 成功会带来自信膨胀，团队低估更大范围的复杂性。
- 对承诺“一次重写解决全部问题”的方案要特别警惕。

**工程用法**
- 重写前先写出旧系统真正不能解决的问题。
- 强制列出“第二版不做什么”。
- 优先替换痛点最大的子系统，不要把所有历史愿望塞进一次重构。

## 7. Fallacies of Distributed Computing｜分布式计算八大谬误

**命题**：设计分布式系统时，不能假设网络可靠、延迟为零、带宽无限、网络安全、拓扑不变、只有一个管理员、传输成本为零或网络同质。

**原资料要点**
- 这些“理想化网络假设”都应默认不成立。
- 本地正常的程序，在延迟、丢包、拓扑变化下可能严重失败。
- 超时、重试、加密、动态发现等不是附加项，而是分布式设计的一部分。

**工程用法**
- 为每个远程调用设置超时与失败语义。
- 重试前先判断幂等性，避免重复扣款/重复创建。
- 把依赖失联、部分成功、乱序、重复消息当成正常设计输入。

## 8. Law of Unintended Consequences｜非预期后果定律

**命题**：修改复杂系统时，应预期出现未计划的副作用。

**原资料要点**
- 重大变更通常会产生意外结果。
- 副作用可能是正面的、负面的，甚至让原问题更严重。
- 一个模块的修复可能破坏另一个暗中依赖旧行为的模块。

**工程用法**
- 变更前做影响面分析，变更后看业务与系统指标。
- 对高风险修改采用灰度、特性开关、快速回滚。
- 把“没有想到”转化为测试和监控的新输入。

## 9. Zawinski's Law｜扎文斯基定律

**命题**：流行软件容易持续扩张功能，最后试图成为“什么都能做的平台”。

**原资料要点**
- 软件成功后会不断累加功能。
- 用户长时间停留在一个产品中，会推动它承担越来越多工作。
- 添加功能容易，拒绝错误功能更难。

**工程用法**
- 用产品边界、核心场景和维护成本审查新功能。
- 为每项能力定义所有者、退出机制和成功指标。
- 定期删除低价值功能，而不是只加不减。

# 二、Teams｜团队

## 10. Conway's Law｜康威定律

**命题**：组织设计出来的系统，往往映射组织自身的沟通结构。

**原资料要点**
- 软件边界容易镜像组织边界。
- 组织孤岛会变成代码和系统孤岛。
- 想得到目标架构，有时需要反向调整团队结构（Inverse Conway）。

**工程用法**
- 服务边界、代码所有权和团队职责尽量一致。
- 如果两个模块必须高频协同，却由完全隔离的团队负责，架构摩擦会持续出现。

## 11. Brooks's Law｜布鲁克斯定律

**命题**：给已经延期的软件项目增加人手，可能让它更晚。

**原资料要点**
- 新成员需要上手时间。
- 新成员会占用资深成员解释、评审和协调的能力。
- 项目滑坡时，缩范围或调时间往往比机械扩编更有效。

**工程用法**
- 先区分工作能否并行拆分，再决定是否增员。
- 对临近交付的关键路径，优先减少依赖和范围。

**边界**
- 它不是说“永远不能加人”；如果任务可独立拆分、时间窗口足够长、 onboarding 成本可控，增员仍可能有效。

## 12. Dunbar's Number｜邓巴数

**命题**：人类能稳定维护的社会关系数量存在认知上限，常被近似描述为约 150。

**原资料要点**
- 组织规模扩大后，非正式协调会变得困难。
- 超过一定规模后，需要更明确的结构和机制。
- 真正高效的日常工作小组应远小于 150，卡牌给出 5–15 的量级提示。

**工程用法**
- 不把“所有人都和所有人沟通”当组织设计。
- 用小团队、明确接口和文档降低沟通组合爆炸。

**边界**
- 150 是经验性量级，不应当作组织设计的精确阈值。

## 13. Ringelmann Effect｜林格曼效应

**命题**：群体越大，个人平均贡献可能下降。

**原资料要点**
- 大组容易出现社会性懈怠。
- 人数增加也会增加协调开销。
- 小而聚焦、所有权清晰的团队往往更有效。

**工程用法**
- 对模块、项目和 incident 明确 DRI/Owner。
- 不用“拉更多人进群”代替问题分解。

## 14. Price's Law｜普赖斯定律

**命题**：卡牌用“参与者数量的平方根完成约一半工作”描述贡献高度不均衡。

**原资料要点**
- 少数核心贡献者可能承担很大比例产出。
- 在较大组织里，关键贡献者离开会有不成比例的影响。
- 需要识别并降低知识集中风险。

**工程用法**
- 用代码评审、结对、文档、轮岗把关键知识扩散。
- 不把高绩效个体变成唯一的审批口或救火点。

**边界**
- 这是启发式，不是可靠的人员绩效公式；不能用来机械排名或推导裁员比例。

## 15. Putt's Law｜普特定律

**命题**：技术理解与管理权力之间可能出现脱节。

**原资料要点**
- 管理者可能不了解技术细节，技术专家也未必承担管理职责。
- 脱节会产生不现实工期和工程师被忽视感。
- 技术负责人、架构负责人、CTO 等桥梁角色可以减少这种断层。

**工程用法**
- 技术决策应让承担后果的人参与。
- 项目排期同时需要业务优先级与工程估算，不由单一角色独断。

## 16. Peter Principle｜彼得原理

**命题**：层级组织中，员工可能不断因当前岗位表现好而晋升，直到进入一个自己不擅长的岗位。

**原资料要点**
- 晋升常奖励当前表现，而非下一岗位匹配度。
- 优秀工程师不一定自动成为优秀经理。
- IC（Individual Contributor）与管理双通道可减少被迫转管理的问题。

**工程用法**
- 晋升前按目标岗位能力评估。
- 给技术专家提供不转管理也能成长的路径。

## 17. Bus Factor｜巴士因子

**命题**：衡量至少失去多少关键成员后，项目会陷入严重困难。

**原资料要点**
- Bus factor = 1 意味着知识存在单点故障。
- 结对、评审和文档可以扩散知识。
- 目标不是人人都懂一切，而是关键路径不依赖唯一一个人。

**工程用法**
- 识别部署、密钥、架构、数据库迁移、客户知识等单点。
- 对关键流程至少安排第二位能独立执行的人。

## 18. Dilbert Principle｜呆伯特原则

**命题**：这是一条讽刺性管理观察：组织有时会把弱绩效人员升入管理岗位，以减少其对具体工作的直接影响。

**原资料要点**
- 这种做法可能把问题从执行层转移到管理层。
- 结果可能既损失一个生产岗位，又产生管理问题。
- 双职业通道与清晰的岗位能力标准有助于避免这种错误激励。

**边界**
- 它是讽刺性启发，不应作为对真实个体或组织的事实判断。

# 三、Planning｜计划

## 19. Premature Optimization｜过早优化

**命题**：在没有证据表明某处是瓶颈前就优化，往往浪费时间并增加复杂度。

**原资料要点**
- 大多数代码不是性能热点。
- 先写清晰、正确的代码，再通过 profiling 找真实热点。
- 过早优化容易在需求和瓶颈尚不清楚时引入缺陷与刚性。

**工程用法**
- 先设性能预算和测量方法。
- 优化前后都要有基准数据。
- 不为了“可能更快”牺牲可读性和正确性。

## 20. Parkinson's Law｜帕金森定律

**命题**：工作会扩张到填满可用时间。

**原资料要点**
- 宽松期限会诱发拖延或低价值打磨。
- 额外时间常被用于“镀金”而非关键价值。
- Time-box 是一种直接对策。

**工程用法**
- 为探索任务设时间盒，到点做继续/停止决策。
- 把“完成定义”写清楚，避免无休止润色。

## 21. Ninety-Ninety Rule｜90/90 法则

**命题**：前 90% 的代码占 90% 时间，剩余 10% 又会占另外 90% 时间；它用夸张方式强调“最后一点”常非常耗时。

**原资料要点**
- 边界情况、bug、打磨和集成可能与主体开发一样费时。
- “快完成了”是高风险状态。
- 原始估算常忽略收尾成本。

**工程用法**
- 估算要包含测试、集成、迁移、文档、发布和回滚准备。
- 进度不要只用“功能写了多少”判断。

## 22. Hofstadter's Law｜霍夫施塔特定律

**命题**：事情总比预期耗时更久，即使你已经考虑了这条规律。

**原资料要点**
- 开发者会反复低估工作。
- 隐藏任务和集成问题往往在执行过程中才暴露。
- 缓冲也可能被消耗。

**工程用法**
- 用历史数据、任务拆分和不确定性区间估算。
- 把高风险依赖提前验证，而不是只在总工期上乘一个系数。

## 23. Goodhart's Law｜古德哈特定律

**命题**：当一个指标变成目标，它就容易失去作为好指标的价值。

**原资料要点**
- 人会优化数字，而不是原本想改善的结果。
- 工单数、覆盖率、velocity 等在成为硬目标后都可能被“做指标”。
- 指标应与定性判断和真实结果结合。

**工程用法**
- 用成组指标防止单指标被钻空子。
- 关注指标背后的用户结果和系统结果。
- 指标异常时先问“行为是否被目标扭曲”。

## 24. Gilb's Law｜吉尔布定律

**命题**：对重要事物，即使只能做近似测量，也通常比完全不测更好。

**原资料要点**
- 近似测量优于完全失明。
- 代码质量等抽象概念可以用代理指标观察。
- 测量体系可以先粗后细。

**工程用法**
- 把不可直接观测的目标拆成可观察信号，例如变更失败率、恢复时间、缺陷逃逸率。
- 不把代理指标误当成目标本身，和 Goodhart's Law 一起使用。

# 四、Quality｜质量

## 25. Boy Scout Rule｜童子军规则

**命题**：离开代码时，让它比你接手时稍微更好。

**原资料要点**
- 每次改动顺手清理一个附近的小问题。
- 小改善长期复利。
- 这会形成“所有人都对代码质量负责”的文化。

**工程用法**
- 小范围命名、重复逻辑、死代码和测试缺口可在相关改动中顺手修复。
- 不要把小改动扩大成无边界重构。

## 26. Murphy's Law / Sod's Law｜墨菲定律

**命题**：凡是可能出错的事情，在足够长时间和足够多运行次数下都应被当作可能发生。

**原资料要点**
- 代码中的失败路径迟早会被触发。
- 需要输入验证、错误处理和合理降级。
- 边界情况应由测试发现，而不是等生产环境替你发现。

**工程用法**
- 设计“失败时发生什么”，而不是只设计 happy path。
- 对磁盘满、网络断、权限不足、重复请求、无效输入做显式处理。

## 27. Postel's Law｜波斯特尔定律

**命题**：发送方严格遵守规范，接收方对输入中的小差异保持一定宽容。

**原资料要点**
- 严格输出、适度宽容输入可以提高互操作性。
- 但过度宽容会掩盖上游缺陷。
- 过度宽容也可能引入安全风险。

**工程用法**
- 对协议兼容问题区分“可安全归一化”和“必须拒绝”。
- 安全边界、签名、权限、金额等关键输入不应模糊解析。

## 28. Broken Windows Theory｜破窗理论

**命题**：长期不修的小问题会传递“低质量可以接受”的信号，并诱发更多问题。

**原资料要点**
- 一个未修问题会影响团队对质量底线的判断。
- 干净代码库更容易促使后来者保持整洁。
- 趁问题还小时处理，避免质量螺旋下降。

**工程用法**
- 为已知缺陷、弃用接口和临时绕过设置负责人和清理条件。
- 不让 TODO 永久失去上下文。

## 29. Technical Debt｜技术债

**命题**：技术债是那些让后续软件开发变慢的设计与实现负担。

**原资料要点**
- 快捷方案等于向未来借时间，并可能产生“利息”。
- 长期忽视会让后续每次修改都更慢。
- 有意识、带偿还计划的技术债可以是合理权衡。

**工程用法**
- 记录债务的原因、影响范围、触发还债条件和退出计划。
- 区分“有意取舍”与“未知混乱”。

## 30. Linus's Law｜Linus 定律

**命题**：足够多、真正投入的审查者可以让更多 bug 更快暴露。

**原资料要点**
- 扩大审查者池能增加不同专业视角。
- 开放代码有助于加快缺陷发现。
- 前提是有人主动阅读和验证，而不是“理论上很多人能看”。

**工程用法**
- 高风险代码引入第二视角、安全审查和领域专家。
- 不把“代码公开”本身等同于“已经审过”。

## 31. Kernighan's Law｜柯尼汉定律

**命题**：调试通常比写出代码更困难；如果写代码时已经用尽聪明程度，之后会更难调试。

**原资料要点**
- 过度巧妙的代码提高诊断成本。
- 可读、简单的代码能在调试期反复回收收益。
- 可维护性也是性能之外的重要工程效率。

**工程用法**
- 优先透明控制流、清晰命名和可观察状态。
- 对复杂优化保留测试、基准和解释文档。

## 32. Testing Pyramid｜测试金字塔

**命题**：测试组合应以大量快速单元测试为底层，较少集成测试，少量 UI/E2E 测试。

**原资料要点**
- 大多数缺陷应尽量在更便宜、更快的层级捕获。
- 过多 UI 测试会让测试套件慢且脆弱。
- 不同层次测试承担不同风险。

**工程用法**
- 单元测试验证局部逻辑；集成测试验证边界；E2E 保护关键用户路径。
- 不追求固定比例，按失败成本和系统形态调整。

## 33. Pesticide Paradox｜杀虫剂悖论

**命题**：长期只运行同一批测试，发现新缺陷的能力会下降。

**原资料要点**
- 固定测试集不能覆盖它从未探索过的路径。
- 新功能和新故障模式要求测试持续演化。
- 回归测试应不断补充真实缺陷案例。

**工程用法**
- 每次生产缺陷都问：能否沉淀为自动化回归测试？
- 结合 property-based、fuzz、随机化或场景扩展寻找旧用例之外的问题。

## 34. Lehman's Laws of Software Evolution｜莱曼软件演化定律

**命题**：与现实世界持续交互的软件必须不断演化，而演化本身会带来复杂度和组织限制。

**原资料要点**
- 现实世界变化，软件不演化就会逐渐失去适用性。
- 每次变更会增加复杂度，除非持续重构与简化。
- 团队吸收变化的能力有限。

**工程用法**
- 把重构、升级和清理视为持续维护，而不是偶发“技术专项”。
- 评估变更吞吐量时同时考虑认知负担和系统复杂度。

## 35. Sturgeon's Law｜斯特金定律

**命题**：卡牌以“90% 的东西质量不高”提醒：多数功能、想法或代码路径的价值并不相等。

**原资料要点**
- 关键不是平均分配精力，而是识别高价值少数。
- 把所有工作视为等价值会增加复杂度并拖慢交付。
- 需要持续筛选、删减和聚焦。

**边界**
- “90%”是修辞性经验法则，不应当作精确统计比例。

# 五、Scale｜规模

## 36. Amdahl's Law｜阿姆达尔定律

**命题**：并行化能带来的加速上限，受无法并行的串行部分限制。

**核心公式**

[
S(N)=rac{1}{(1-P)+rac{P}{N}}
]

- (P)：可并行比例；
- (N)：并行处理单元数量；
- (1-P)：串行比例；
- (S(N))：理论加速比。

**原资料要点**
- 串行部分给总加速设置硬上限。
- 增加核心只能暴露瓶颈，不能消灭串行路径。
- 类似逻辑也适用于组织审批：单一审批点会限制整体吞吐。

**小例子**
如果 95% 可并行，5% 必须串行，即使处理器数量趋于无限，加速上限也只有 (1/0.05=20) 倍。

## 37. Gustafson's Law｜古斯塔夫森定律

**命题**：当计算资源增加时，如果同时扩大问题规模，并行系统可以处理更大的工作量，而不仅是把固定任务做得更快。

**原资料要点**
- 更多处理器可以在相同时间内处理更大的问题。
- 评估并行系统时，不应只固定工作量。
- “扩展问题规模”是 scale-out 价值的重要视角。

**与 Amdahl 的关系**
- Amdahl：固定问题规模，问“最多能加速多少？”
- Gustafson：固定可接受时间，问“资源增加后能解决多大的问题？”

## 38. Metcalfe's Law｜梅特卡夫定律

**命题**：卡牌用“网络价值与用户数平方成比例”描述网络效应的非线性增长。

**原资料要点**
- 新用户会增加与已有用户的潜在连接。
- 网络增长可能带来非线性价值。
- 用户流失也可能造成非线性价值下降。

**边界**
- 这是网络效应模型，不是所有产品的精确估值公式；连接是否真正有价值、网络是否分群、负外部性等都会改变结果。

# 六、Design｜设计

## 39. YAGNI｜You Aren't Gonna Need It

**命题**：在真正需要之前，不要预先加入功能。

**原资料要点**
- 不要为尚未出现的需求写代码。
- 猜测性的 hook、扩展点和抽象会增加当前复杂度。
- 延后实现的前提，是未来确有能力低成本增加。

**工程用法**
- 当前需求驱动结构，预留“容易改”而不是“把所有未来都做出来”。
- 对无法逆转的底层约束，仍需要前置设计。

## 40. DRY｜Don't Repeat Yourself

**命题**：同一份知识应有单一、明确、权威的表示。

**原资料要点**
- DRY 的对象是“知识”，不只是长得像的代码。
- 同一业务规则复制多份，会让修复必须同步修改多处。
- 去重应围绕同一事实来源，而不是盲目追求代码行数少。

**边界**
- 两段代码现在相似，不代表表达的是同一知识。过早抽象会把未来变化方向不同的逻辑错误绑在一起。

## 41. KISS｜Keep It Simple, Stupid

**命题**：在满足要求的前提下，优先更简单的设计。

**原资料要点**
- 简单代码更容易理解、调试和交接。
- 不要为了“聪明”增加不必要结构。
- 不要为假想未来问题牺牲当前可理解性。

**工程用法**
- 同等满足约束时，优先依赖更少、状态更少、层级更少的方案。

## 42. SOLID Principles｜SOLID 原则

**五项原则**
1. SRP：Single Responsibility，单一职责；
2. OCP：Open/Closed，对扩展开放、对修改关闭；
3. LSP：Liskov Substitution，里氏替换；
4. ISP：Interface Segregation，接口隔离；
5. DIP：Dependency Inversion，依赖倒置。

**原资料要点**
- 目标是降低耦合、提高可维护与可扩展性。
- 合理使用可让扩展更少破坏已有实现。
- 过度套用会制造无收益的抽象层。

**工程用法**
- SOLID 是诊断语言，不是“类越多越好”。
- 只有变化压力真实存在时再引入对应抽象。

## 43. Law of Demeter｜迪米特法则

**命题**：对象应主要与自己的直接协作者交互，而不是穿透多层对象结构。

**原资料要点**
- 类似 `a.b.c.do()` 的深链会让调用方依赖内部结构。
- 这种耦合让中间对象变化传播到远处。
- 可以由邻居提供更稳定的包装方法。

**工程用法**
- 让对象暴露意图级操作，而不是让外部代码遍历内部对象图。

## 44. Principle of Least Astonishment｜最小惊讶原则

**命题**：软件与接口应尽量符合用户和开发者已有心智模型，减少意外。

**原资料要点**
- 行为应与常见预期一致。
- 遵循平台惯例是降低惊讶的最快方式之一。
- API/UI 的“意外行为”会直接增加误用和不信任。

**工程用法**
- 命名、默认值、错误行为、删除操作、返回值都应尽量符合领域习惯。
- 如果必须反直觉，必须让差异显式可见。

# 七、Decisions｜决策

## 45. Dunning-Kruger Effect｜邓宁-克鲁格效应

**命题**：知识不足时，人可能无法准确识别自己的知识缺口，从而产生失准的自我评估。

**原资料要点**
- 初学阶段的高自信不等于掌握。
- 学习深入后，发现未知会让判断更谨慎。
- 专业判断更常使用范围、条件和权衡，而非绝对口号。

**工程用法**
- 重要技术决策要求证据、原型和反例，不以“我很确定”代替验证。

**边界**
- 不应拿这一效应给别人贴标签；它更适合用来检查自己的认知校准。

## 46. Hanlon's Razor｜汉隆剃刀

**命题**：面对问题时，先考虑错误、误解或疏忽等更普通原因，不急于推断恶意。

**原资料要点**
- 故障首先从简单的人为和配置错误排查。
- 代码评审中用问题和证据沟通，而不是先责备。
- 这有助于减少无依据的动机推断。

**边界**
- 它不是“永远排除恶意”；安全事件仍应按威胁模型验证。

## 47. Occam's Razor｜奥卡姆剃刀

**命题**：在同样能解释证据的方案里，优先假设更少、更简单的解释。

**原资料要点**
- 调试从简单可能性开始。
- 设计上多一个部件就多一个故障点。
- 更多功能通常也意味着更多复杂度。

**边界**
- “简单”不能压过证据；现实本身复杂时，过度简化也会错。

## 48. Sunk Cost Fallacy｜沉没成本谬误

**命题**：过去已经投入的时间和成本，不应成为继续错误选择的理由。

**原资料要点**
- 项目是否继续，应基于未来收益与未来成本。
- 健康团队应能停止或转向失败项目。
- 可提前设置明确复盘点与退出条件。

**工程用法**
- 决策记录中把“已花多少钱”与“从现在继续还要花多少、能得到什么”分开。

## 49. The Map Is Not the Territory｜地图不是疆域

**命题**：模型、图表、文档和架构图是现实的表示，不是现实本身。

**原资料要点**
- 蓝图不能替代运行系统。
- 真实代码和基础设施会暴露模型没有覆盖的因素。
- 当事实与模型冲突时，应该更新模型。

**工程用法**
- 以运行时观测、测试和生产证据校正设计文档。
- 架构图必须能追上实际依赖，否则只是一张历史图片。

## 50. Confirmation Bias｜确认偏误

**命题**：人倾向寻找支持自己原有观点的信息，并忽视反证。

**原资料要点**
- 调试时应主动问：如果我的假设是错的，会看到什么？
- 测试、事实和不同意见可以帮助抵消偏误。
- 不要只收集能证明自己方案正确的数据。

**工程用法**
- 设计实验时先写“什么结果会让我放弃当前假设”。

## 51. Hype Cycle & Amara's Law｜炒作周期与阿马拉定律

**命题**：人们常高估技术的短期影响，又低估它的长期影响。

**原资料要点**
- 新技术早期容易被过度承诺。
- 真正长期改变往往需要基础设施、成本和组织实践成熟。
- 工具选型应看可验证价值，不只看热度。

**工程用法**
- 把“新闻热度”“试验可行”“生产可靠”“经济可持续”分开评估。

## 52. Lindy Effect｜林迪效应

**命题**：对某些非易耗事物，已经持续存在越久，未来继续存在的概率往往也越高。

**原资料要点**
- 久经使用的技术通常已经经过更多真实场景筛选。
- 基础技能、算法、SQL、核心语言等具有较强长期价值。
- 时间会淘汰大量脆弱、无价值的短期方案。

**边界**
- “老”不等于“更好”，也不意味着旧技术永远安全或适用；仍需看维护状态、生态和具体约束。

## 53. First Principles Thinking｜第一性原理思考

**命题**：把复杂问题拆到基础事实和不可再省略的约束，再从这些事实重新构建方案。

**原资料要点**
- 先质疑默认假设。
- “行业一直这样做”不是充分理由。
- 估算和设计可以从基础量、约束与成本重新推导。

**工程用法**
- 对“必须用微服务”“必须上某框架”等结论，先还原真实需求：吞吐、隔离、团队边界、部署频率、合规等。

## 54. Inversion｜反演思考

**命题**：从相反结果出发，反向推导哪些因素会导致失败，再设计避免方案。

**原资料要点**
- 想实现目标时，也列出“怎样一定会失败”。
- Pre-mortem：假设项目已经失败，再写出原因。
- 从“API 怎样会被滥用/打爆”思考，可推导验证、限流等设计。

**工程用法**
- 上线前问：如果明天发生严重事故，最可能是哪三种路径？

## 55. Pareto Principle｜帕累托原则 / 80-20 法则

**命题**：很多系统中，少数原因贡献了大部分结果。

**原资料要点**
- 少数 bug 可能导致大部分崩溃。
- 不应平均分配优化精力，应先找到高影响区域。
- 实际比例未必恰好 80/20，应以数据确认。

**工程用法**
- 按故障量、用户影响、调用量和成本排序，再处理“关键少数”。

## 56. Cunningham's Law｜坎宁安定律

**命题**：在协作环境里，给出一个可批评的答案、草稿或原型，往往比只提开放问题更容易得到具体反馈。

**原资料要点**
- 明确主张会触发更具体的纠正。
- 草案和原型为讨论提供共同对象。
- 纯问题有时因为上下文不足而得不到回应。

**工程用法**
- 设计评审不要只说“大家有什么想法”，而是提交一个带假设、取舍和待验证点的初稿。

**边界**
- 不要故意传播错误信息；工程实践应理解为“用可修改草案促进反馈”。

# 八、把 56 条变成工程检查表

## 架构评审前

- 这个接口有哪些“未写进文档但可被观察”的行为？→ Hyrum
- 是否从最小可运行系统逐步长出来？→ Gall
- 哪些抽象在故障时会泄漏？团队是否理解下层？→ Leaky Abstractions
- 复杂度被谁承担？→ Tesler
- 网络分区、延迟、失败和重试是否被当成常态？→ CAP / Distributed Fallacies
- 大重写是否正在变成 Second-System Effect？
- 变更是否准备了灰度、指标和回滚？→ Unintended Consequences

## 团队与项目评审前

- 增加人手真的能并行，还是只会增加沟通？→ Brooks / Ringelmann
- 架构边界与团队边界是否冲突？→ Conway
- 是否有知识单点？→ Bus Factor
- 是否把绩效优秀等同于适合管理？→ Peter
- 指标是否被当成目标而扭曲行为？→ Goodhart
- “90% 完成”是否遗漏测试、迁移和发布？→ Ninety-Ninety / Hofstadter

## 代码评审前

- 是不是为了未来猜测引入了抽象？→ YAGNI
- 是否真正重复了“知识”，而不是仅仅代码长得像？→ DRY
- 能否用更简单方案？→ KISS / Occam
- 是否穿透太多对象层级？→ Demeter
- 代码是否聪明到未来难调？→ Kernighan
- 修改附近是否能顺手做一个小清理？→ Boy Scout

## 故障与质量复盘前

- 是否只设计 happy path？→ Murphy
- 是否把容错做得过度宽松？→ Postel
- 技术债是否有明确偿还触发条件？→ Technical Debt
- 测试是否长期不变？→ Pesticide Paradox
- 生产事实是否推翻了原模型？→ Map Is Not the Territory
- 我们是否只找支持原判断的证据？→ Confirmation Bias
- 能否从“怎样再次失败”反推防线？→ Inversion

# 九、学习自测

1. 为什么“修 bug”也可能是 breaking change？请用 Hyrum's Law 解释。
2. 一个服务为了“简化客户端”把大量重试和容错塞到服务端，这体现了哪条复杂度原则？什么时候会过头？
3. 为什么 CAP 不能简单理解成“数据库永远只能选两个字母”？
4. 为什么一个延期项目增加 5 位开发者，不一定会加速？
5. 你的项目 Bus Factor 是多少？最危险的知识单点在哪里？
6. “测试覆盖率必须 95%”为什么可能触发 Goodhart's Law？
7. 请写一个你遇到过的技术债，并写出“本金、利息、还债触发条件”。
8. Amdahl's Law 中，如果 10% 串行，理论最大加速是多少？答：10 倍。
9. DRY 为什么不等于“任何两段相似代码都必须抽象成一个函数”？
10. 选一个近期技术热点，分别用 Amara's Law、Lindy Effect、First Principles Thinking 分析一次。
11. 写一个 pre-mortem：假设你当前项目三个月后失败，列出 5 个可能原因，再映射到可以提前做的防线。
12. 找一个团队指标，说明它在什么条件下会从“测量”变成“目标”，以及怎样防止被游戏化。
