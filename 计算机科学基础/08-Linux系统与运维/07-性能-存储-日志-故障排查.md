# 07｜性能、存储、日志与故障排查

## 1. 先判断瓶颈属于哪一层

常见资源维度：

~~~text
CPU
memory
disk capacity
disk I/O
filesystem/inode
network
process limits
service dependency
application
~~~

不要看到“系统慢”就先清缓存、重启或改 sysctl。

## 2. 第一屏系统状态

进入故障主机后：

~~~bash
uptime
top
free -h
df -h
df -i
systemctl --failed
journalctl -p warning -b
~~~

这能快速发现：

- load 是否异常；
- CPU 是否饱和；
- memory/swap 是否紧张；
- 磁盘或 inode 是否满；
- 服务是否失败；
- 本次启动是否有明显错误。

## 3. Load Average

uptime/top 的 load average 不是 CPU 百分比。

Linux load 通常包括：

- 正在 CPU 上运行/等待 CPU 的任务；
- 不可中断睡眠任务，常见于 I/O 等待。

因此高 load + 低 CPU 利用率可能是 I/O 或内核等待，而不是 CPU 不够。

判断时结合 CPU 核数、vmstat、ps 状态、iostat 和 D 状态进程。

## 4. top/htop

重点观察：

- user/system/idle/iowait；
- load average；
- 内存和 swap；
- 每进程 CPU；
- 每进程内存；
- 进程状态。

不要只看 top 排名第一的进程，需要确认它是症状还是根因。

## 5. ps

~~~bash
ps aux
ps -eo pid,ppid,user,stat,%cpu,%mem,rss,etime,cmd --sort=-%cpu
ps -eo pid,stat,wchan:32,cmd
~~~

STAT 和 wchan 可以帮助分析 D/S 状态在等待什么。

## 6. free：Linux 内存不要只看 free 列

~~~bash
free -h
~~~

Linux 会积极使用空闲内存做 page cache。

真正关心：

- available；
- swap 使用；
- memory pressure；
- OOM；
- 应用 working set。

“free 很少”不自动等于“内存不足”。

## 7. vmstat

~~~bash
vmstat 1
~~~

常看：

- r：可运行队列；
- b：阻塞任务；
- si/so：swap in/out；
- us/sy/id/wa：CPU；
- bi/bo：块设备 I/O。

连续采样比只看一行更有意义。

## 8. OOM

内存耗尽时可能触发 OOM killer。

~~~bash
journalctl -k | grep -i oom
dmesg | grep -i oom
~~~

需要区分：

- 主机全局 OOM；
- cgroup/container memory limit OOM；
- 应用自己抛出的内存异常。

解决方案可能是修复泄漏、降低并发、调优缓存或提高合理内存，而不是简单关闭 OOM 机制。

## 9. 磁盘容量：df 与 du

~~~bash
df -h
du -xhd1 /var
du -xhd1 /var/log
~~~

df 看文件系统使用量，du 累加可见文件大小。

两者差异大时考虑：

- 已删除但仍被进程打开的文件；
- mount 覆盖；
- sparse file；
- snapshots；
- reserved blocks。

## 10. inode

还有磁盘容量但不能创建文件，可能是 inode 用完：

~~~bash
df -i
~~~

大量极小文件、缓存目录、邮件队列等可能消耗 inode。

## 11. lsblk、blkid、mount

~~~bash
lsblk -f
blkid
findmnt
mount
~~~

它们回答设备和分区、文件系统类型/UUID、当前挂载关系和 mount options。

## 12. /etc/fstab

fstab 描述持久挂载。

优先使用 UUID/LABEL，而不是依赖易变化的 /dev/sdX 名称。

修改后应先验证：

~~~bash
sudo mount -a
~~~

远程主机上错误 fstab 可能导致下次启动失败，修改前需要保留恢复路径。

## 13. 卸载失败

~~~bash
umount /mountpoint
~~~

提示 busy 时，先找占用者：

~~~bash
lsof +D /mountpoint
fuser -vm /mountpoint
~~~

不要在不知道写入状态时强制卸载。

## 14. iostat

~~~bash
iostat -xz 1
~~~

关注：

- throughput；
- IOPS；
- await；
- queue；
- utilization。

指标含义与存储设备类型有关。NVMe、网络块存储和机械盘不能套同一阈值。

## 15. iotop

iotop 按进程观察 I/O 活动。

适合发现谁持续写盘、谁在大量读、异常日志写入以及数据库/备份竞争。

内核和发行版权限要求可能不同。

## 16. 文件描述符

服务出现 Too many open files 时：

~~~bash
ulimit -n
cat /proc/PID/limits
lsof -p PID
ss -s
~~~

systemd 服务还可能有 LimitNOFILE 等独立配置。

提高 limit 前先判断是否存在连接泄漏或文件句柄泄漏。

## 17. /proc 是排障宝库

常见：

~~~text
/proc/PID/status
/proc/PID/cmdline
/proc/PID/environ
/proc/PID/fd/
/proc/PID/maps
/proc/meminfo
/proc/loadavg
/proc/net/
~~~

读取进程 environ 可能暴露 secret，应谨慎处理。

## 18. dmesg 与 kernel journal

硬件、驱动、文件系统、OOM、网络驱动等内核事件可通过：

~~~bash
dmesg
journalctl -k
~~~

重点搜索 error、fail、timeout、reset、I/O error、文件系统错误、OOM 和 segfault。

## 19. systemd 日志

服务问题：

~~~bash
systemctl status service
journalctl -u service -b
journalctl -u service --since '30 min ago'
~~~

结构化日志比只 tail 传统日志文件更适合现代 systemd 主机。

## 20. 时间线比单点截图重要

性能问题要连续采样。

~~~bash
vmstat 1 60
iostat -xz 1 60
pidstat 1
~~~

一次 top 只能表示瞬间，可能错过周期性 spike、GC、定时任务、backup 或队列积压。

## 21. 网络性能与系统性能联合看

系统慢可能来自远端依赖：

~~~bash
ss -s
ss -ant
ip -s link
ping host
~~~

还要区分 DNS 慢、TCP 建连慢、TLS 慢、服务处理慢、丢包/重传和网络队列。

## 22. 日志导致磁盘打满

典型路径：

~~~text
应用异常
→ 高频 error
→ 日志持续增长
→ /var 满
→ 服务/数据库无法写
→ 更大故障
~~~

所以日志系统需要 rotation、retention、rate limit、容量告警、中央采集，并避免 secret/PII 泄漏。

## 23. sysctl

sysctl 用于调整内核运行参数。

~~~bash
sysctl key
sysctl -a
~~~

调优原则：

1. 先有可观测数据；
2. 明确参数作用域；
3. 查目标内核官方文档；
4. 一次只改少量；
5. 保存前后指标；
6. 准备回滚。

不要复制“万能 Linux 性能调优 sysctl.conf”。

## 24. 常见故障决策树

### CPU 高

~~~text
top/ps 定位进程
→ user 还是 system CPU
→ 单线程还是多线程
→ profiler/strace/perf（需要时）
→ 是否重试循环/压缩/加密/GC
~~~

### 内存高

~~~text
free/vmstat
→ top/ps RSS
→ cgroup limit
→ OOM 日志
→ heap/allocator/profile
→ cache vs leak
~~~

### 磁盘满

~~~text
df -h / df -i
→ du
→ deleted-open file
→ logs/cache
→ snapshots/containers
→ 扩容或清理
~~~

### I/O 慢

~~~text
iostat
→ iotop/pidstat
→ D state
→ device/kernel log
→ filesystem/storage backend
~~~

### 服务挂了

~~~text
systemctl status
→ journalctl
→ config
→ identity/permission
→ port
→ dependency
→ storage/network
~~~

## 25. 生产排障原则

- 先收集证据，再改变系统；
- 优先可逆操作；
- 记录时间线；
- 不把 restart 当根因分析；
- 任何清理动作先确认数据属性；
- 任何 kill -9 前先考虑一致性；
- 任何 sysctl/ulimit 扩大前先找根因；
- 修复后验证监控和告警是否能提前发现同类问题。
