# 05｜软件包、构建与开发环境

## 1. 软件安装不是“把文件复制进去”

一个发行版软件包通常包含：

- 程序文件；
- 共享库依赖；
- 配置模板；
- systemd unit；
- 用户/组创建逻辑；
- 数据库或缓存更新；
- 签名与来源信息；
- 升级/卸载元数据。

因此优先使用发行版包管理器，而不是到处下载未知脚本。

## 2. 包管理器的共同模型

~~~text
repository
→ metadata/index
→ package + signature
→ dependency resolution
→ download
→ verify
→ install
→ database records
~~~

不同发行版命令不同，但模型相同。

## 3. Debian/Ubuntu：APT

~~~bash
sudo apt update
apt search package
apt show package
sudo apt install package
sudo apt remove package
sudo apt autoremove
~~~

apt update 更新可用包索引；apt upgrade 升级已安装包，两者不是一回事。

系统自动化中还应理解 apt-get/dpkg 的底层角色，但日常交互用 apt 即可。

## 4. APT 第三方源的现代安全做法

旧教程经常使用 apt-key，该工具已被废弃。

新的原则：

- 第三方仓库密钥放到独立 keyring；
- 使用 Signed-By 将仓库限制到指定密钥；
- 不把任意第三方 key 加入全局信任；
- 优先发行方正式文档；
- 仓库 URL 使用 HTTPS；
- 定期清理不用的软件源。

核心目的是缩小“一个 key 可以信任所有仓库”的范围。

## 5. Fedora/RHEL 系：DNF/RPM

现代实践以 dnf 为主：

~~~bash
dnf search package
sudo dnf install package
sudo dnf remove package
sudo dnf upgrade
rpm -q package
~~~

旧资料大量出现 yum。现代系统上可能提供兼容入口，但新知识应以 dnf 体系理解。

旧 CentOS 5/6/7 repo 文件、镜像地址和一键换源脚本不进入主知识库。

## 6. Arch、openSUSE、NixOS

### Arch

pacman 管理官方仓库；AUR 是社区构建描述集合，不等于官方审计仓库。使用 AUR 前要检查 PKGBUILD。

### openSUSE

zypper 管理 RPM 包；YaST 提供统一系统管理界面。

### NixOS

Nix 强调：

- 声明式；
- 不可变 store；
- 多版本共存；
- 可回滚；
- 可复现开发环境。

具体 channel/flake 命令可能演进，但“声明式系统状态”是长期价值。

## 7. 安装软件的优先级

通常：

~~~text
发行版官方仓库
→ 软件官方仓库
→ 可信容器/独立包格式
→ 官方二进制发布
→ 源码编译
→ 来源不明的一键脚本：不执行，先核实来源和内容
~~~

越靠后，升级、审计和卸载成本通常越高。

## 8. 手工安装二进制

常见位置：

- /usr/local/bin：本机管理员安装、全局使用；
- /opt/app：独立第三方应用；
- ~/.local/bin：单用户工具。

不要把自定义文件随意覆盖 /usr/bin 中由包管理器维护的文件。

## 9. 源码编译的通用流程

经典 Autotools 风格：

~~~bash
./configure --prefix="$HOME/.local"
make -j2
# 先按项目说明运行测试、检查安装清单，再考虑 make install
~~~

现代项目也可能使用 CMake、Ninja、Meson、Cargo、Go toolchain 或语言自己的构建工具。

真正要掌握的是：

~~~text
获取源码
→ 验证版本/签名
→ 安装 build dependencies
→ configure
→ compile
→ test
→ install/package
→ verify
~~~

## 10. 为什么不建议无脑 make install

手工安装可能导致：

- 包管理器不知道安装了哪些文件；
- 卸载困难；
- 升级覆盖冲突；
- 依赖无法追踪；
- /usr/local 与系统包混杂。

生产环境更推荐把源码构建结果封装成发行版包、容器镜像、明确的 /opt 目录发布物或其他可回滚 artifact。

## 11. Make、CMake 与 Ninja

### Make

通过规则描述输入、输出和依赖：

~~~text
target: prerequisites
    recipe
~~~

Makefile 的价值是增量构建和依赖图，而不是把编译命令单纯放进文件。

### CMake

跨平台生成构建系统，适合中大型 C/C++ 项目。

推荐 out-of-source build：

~~~bash
cmake -S . -B build
cmake --build build
ctest --test-dir build
~~~

### Ninja

专注快速执行构建图，常作为 CMake 等工具生成的后端。

## 12. 静态链接与动态链接

### 静态链接

依赖代码更多进入最终二进制。

优点：

- 部署简单；
- 运行时外部库依赖少。

代价：

- 文件更大；
- 安全更新可能需要重新构建整个程序；
- 某些系统库和插件机制不适合完全静态化。

### 动态链接

程序运行时加载共享库。

~~~bash
readelf -d binary
# 仅对可信、匹配本机 ABI 的程序使用 ldd
ldd binary
ldconfig -p
~~~

动态链接问题常表现为“在编译机可运行，部署机找不到 .so”。不要对不可信二进制执行 `ldd`：某些实现/场景可能运行其解释器。先用 `readelf -d` 或 `objdump -p` 做静态依赖检查；它们的结果也不等同于运行时完整依赖解析。

## 13. 编译器和运行时边界

需要区分：

- source compatibility；
- ABI compatibility；
- CPU architecture；
- libc；
- runtime version；
- dynamic linker。

“都是 Linux”不保证二进制可以在所有发行版直接运行。

## 14. 交叉编译

交叉编译是“在 A 平台生成 B 平台可执行文件”。

常见场景：

- x86_64 主机编译 aarch64；
- Linux 编译嵌入式目标；
- 多架构容器镜像。

必须明确：

~~~text
build platform
host/target platform
compiler triplet
sysroot
target libraries
~~~

## 15. Python 环境

不要把系统 Python 当作项目依赖垃圾桶。

项目优先使用虚拟环境：

~~~bash
python -m venv .venv
source .venv/bin/activate
python -m pip install ...
~~~

现代 Python 项目逐渐以 pyproject.toml 描述构建和依赖元数据；requirements.txt 仍广泛用于锁定/部署场景。

uv、pip-tools、Poetry 等属于工具层，具体选择可以变化，核心是：

- 项目依赖隔离；
- 明确版本；
- 可重现安装；
- 不破坏系统包管理器维护的 Python。

## 16. Conda

Conda 同时管理环境和二进制包，适合科学计算、多 Python 版本和非 Python 原生依赖。

Anaconda、Miniconda 及其他发行方式会变化，长期知识是“环境与包独立于系统 Python”。

## 17. 软件服务部署的通用模板

dunwu 仓库包含大量 JDK、Tomcat、Kafka、RocketMQ、Nacos、Elastic、GitLab、Jenkins、FastDFS 等安装脚本。具体版本和脚本大多不适合直接复用，但背后的部署流程具有长期价值。

统一抽象为：

~~~text
确定版本与来源
→ 验证 artifact
→ 建立专用用户/组
→ 规划 /opt /etc /var/lib /var/log
→ 安装
→ 写最小配置
→ 设置权限
→ systemd unit
→ 开放必要端口
→ health check
→ 日志/指标
→ 备份与恢复
→ 升级与回滚
~~~

掌握这个模板后，不需要保存每个旧中间件的一键脚本。

## 18. 配置文件管理

配置应做到：

- 明确默认值与自定义值；
- 不把 secret 提交到仓库；
- 使用模板或配置管理工具；
- 变更可审计；
- 修改前备份；
- 支持验证语法；
- 服务重载前先检查配置。

典型流程：

~~~text
配置生成
→ syntax check
→ atomic replace
→ reload
→ health check
→ rollback if failed
~~~

## 19. 安装脚本安全

执行网络下载的一键脚本前至少要问：

- 域名和 TLS 是否可信；
- 脚本是否可先下载审查；
- 是否需要 root；
- 会修改哪些仓库、用户、服务和防火墙；
- 是否 pin 版本；
- 是否可回滚；
- 是否把 secret 写进日志。

生产环境优先可审计、可重复的安装方式。

## 20. 旧教程如何处理

以下内容作为历史兼容知识，不作为新部署默认：

- CentOS 5/6/7 专用 repo；
- yum-only 脚本；
- JDK 8/Tomcat 8 固定下载链接；
- 固定版本 ELK、Kafka、RocketMQ、Nacos 安装脚本；
- 手工替换系统源；
- 关闭防火墙/SELinux 以换取“安装成功”；
- 旧 Docker 安装脚本。

需要某产品时，应重新核验该产品和目标发行版的当前官方安装方法。

## 21. 小实验：构建与安装分开

在空练习目录准备 `main.cpp`：

~~~cpp
#include <iostream>
int main() { std::cout << "构建成功\n"; }
~~~

再保存 `CMakeLists.txt`：

~~~cmake
cmake_minimum_required(VERSION 3.16)
project(study_hello LANGUAGES CXX)
add_executable(study_hello main.cpp)
target_compile_features(study_hello PRIVATE cxx_std_17)
~~~

~~~bash
cmake -S . -B build
cmake --build build
./build/study_hello
~~~

前提是已有 CMake 和 C++ 编译器；在 macOS/Linux 的单配置生成器下输出 `构建成功`。多配置生成器还需指定 `--config Debug` 并使用相应产物路径。本例只构建到项目目录，不安装系统文件，也没有注册 CTest 测试，不能把 `ctest` 的“没有测试”当作通过测试。

自测：删除 build 能否重新构建？答：源文件与构建描述完整且工具链可用时可以；这正是把产物和源文件分开的意义。
