# 03｜用户、权限与文件系统

## 1. Linux 的用户模型

Linux 用 UID/GID 而不是用户名字符串做最终权限判断。

关键概念：

- UID：用户 ID；
- GID：主组 ID；
- supplementary groups：附加组；
- root：UID 0；
- system account：供服务运行的非交互账户；
- normal user：日常登录用户。

查看当前身份：

~~~bash
whoami
id
groups
~~~

## 2. /etc/passwd、/etc/shadow、/etc/group

/etc/passwd 保存账户元数据，例如：

~~~text
name:x:uid:gid:comment:home:shell
~~~

现代 Linux 不在 /etc/passwd 保存密码哈希，而是放在权限更严格的 /etc/shadow。

/etc/group 保存组信息。

不要直接手工修改这些文件作为常规管理方式；使用 useradd、usermod、groupadd、passwd 等工具。

## 3. 系统用户

服务通常不应以 root 运行，而是使用独立系统用户，例如 Web、数据库、监控服务各自拥有最小权限。

系统用户的 UID 区间由发行版约定，不是 Linux 内核硬性定义。

很多系统用户：

- 没有可登录密码；
- shell 为 nologin/false；
- 家目录不存在或用于服务数据。

不要因为“不认识”就删除。

## 4. root、sudo 与 su

### root

root 拥有广泛系统权限。长期原则是尽量缩短以 root 身份操作的时间。

### sudo

sudo 让被授权用户以其他身份运行指定命令。

~~~bash
sudo command
sudo -u serviceuser command
sudo -i
~~~

sudo 的价值不是“省去 root 密码”，而是：

- 可审计；
- 可细粒度授权；
- 不必共享 root 凭证；
- 可以限制命令。

### su

su 用于切换用户。

~~~bash
su - username
~~~

带 - 通常会创建更接近目标用户登录环境的 shell。

### NOPASSWD

免密 sudo 会扩大凭证被滥用后的影响范围。若必须使用，应只授权必要命令，而不是无条件 ALL。

## 5. 用户与组管理

典型工具：

~~~bash
useradd
usermod
userdel
groupadd
groupmod
groupdel
passwd
~~~

发行版可能提供更高层 adduser。脚本和跨发行版文档应注意差异。

常见任务：

~~~bash
usermod -aG group user
passwd user
~~~

修改组成员关系后，现有会话不一定立即获得新组，需要重新登录或创建新会话。

## 6. 文件权限的三组主体

ls -l 示例：

~~~text
-rwxr-x--- 1 alice dev 1234 file
~~~

权限主体：

- u：owner；
- g：group；
- o：others。

权限：

- r：read；
- w：write；
- x：execute/search。

## 7. 文件和目录的 rwx 含义不同

### 普通文件

- r：读取内容；
- w：修改内容；
- x：执行。

### 目录

- r：列出目录项名称；
- w：修改目录项；创建、删除、重命名一般还需要目录的 x 权限，并受 sticky bit、ACL 等约束；
- x：进入目录、访问目录内已知名称。

很多权限问题来自忽略目录的 x 权限。

## 8. chmod

符号方式：

~~~bash
chmod u+x script.sh
chmod g-w file
chmod o-rwx secret
~~~

八进制方式：

~~~text
r = 4
w = 2
x = 1
~~~

例如：

~~~bash
chmod 755 tool
chmod 640 config
~~~

不要把 777 当“解决权限问题”的通用答案。

## 9. chown 与 chgrp

~~~bash
chown user file
chown user:group file
chown -R user:group dir
chgrp group file
~~~

递归修改生产目录前先确认路径、挂载点和符号链接行为。

## 10. umask

umask 决定新建文件/目录默认权限需要屏蔽哪些位。

它不是直接“设置最终权限”，而是影响创建时的默认模式。

理解 umask 对服务创建日志、共享目录和多用户环境很重要。

## 11. 特殊权限位

### setuid

可执行文件运行时使用文件所有者的有效 UID。

典型风险：setuid root 程序一旦存在漏洞，可能形成提权路径。

### setgid

对可执行文件会影响有效 GID；对目录常用于让新文件继承目录组，适合团队共享目录。

### sticky bit

常见于 /tmp。目录可被多人写，但删除/重命名通常要求是文件所有者、目录所有者或具有相应特权；它不是简单地只看文件自身的写权限。

## 12. 实际 UID 与有效 UID

进程可能同时有：

- real UID：谁启动了它；
- effective UID：当前权限判断使用的身份。

setuid 程序、sudo 等机制会利用这一模型。

## 13. ACL

传统 owner/group/others 不够时，可以使用 POSIX ACL 做更细的授权：

~~~bash
getfacl file
setfacl -m u:alice:rw file
~~~

ACL 是“补充权限模型”，不是替代基本 rwx。

## 14. Linux capabilities

root 权限可以拆成多种 capability，例如绑定低端口、修改网络等。

相比让整个进程以 root 运行，能力拆分能缩小权限范围。

查看和设置常用：

~~~bash
getcap file
setcap ...
~~~

实际生产中应坚持最小权限。

## 15. inode、硬链接与符号链接

文件名属于目录项，真正的数据对象由 inode 表示。

因此：

- mv 在同一文件系统中通常只是修改目录项；
- 硬链接共享 inode；
- rm 删除的是一个名字，只有最后一个链接消失且没有进程持有文件时，空间才真正可回收；
- 已删除但仍被进程打开的大文件可能继续占磁盘。

排查“df 很满但找不到大文件”时可用 lsof 查看 deleted 文件。

## 16. Linux 文件系统层次

常见目录：

| 路径 | 主要用途 |
|---|---|
| / | 根目录 |
| /etc | 系统与服务配置 |
| /usr | 大部分用户空间程序与共享数据 |
| /usr/local | 本机管理员手工安装的软件 |
| /var | 可变数据、日志、缓存、队列 |
| /home | 普通用户家目录 |
| /root | root 家目录 |
| /tmp | 临时文件 |
| /run | 本次启动期间的运行时状态 |
| /opt | 可选/第三方软件 |
| /srv | 服务提供的数据 |
| /dev | 设备节点 |
| /proc | 进程与内核状态的伪文件系统 |
| /sys | 设备和内核对象的 sysfs |
| /boot | 启动相关文件 |

不要用 Windows 的“C 盘/D 盘”心智模型理解 Linux。不同存储设备通过 mount 挂到统一目录树。

## 17. /proc 与 /sys

### /proc

提供进程和内核运行状态，例如：

~~~text
/proc/PID/
/proc/cpuinfo
/proc/meminfo
/proc/mounts
~~~

### /sys

暴露设备、驱动、总线和内核对象信息。

这两个目录多数内容不是磁盘普通文件，而是内核动态提供的接口。

## 18. 执行失败不都叫 Permission denied

常见原因：

1. 文件没有 x 权限；
2. 所在目录缺少 x；
3. 文件系统以 noexec 挂载；
4. SELinux/AppArmor 阻止；
5. 二进制架构不兼容或格式错误通常是 `Exec format error`；
6. 解释器/shebang 不存在可能显示 `No such file or directory`，即使脚本本身存在。

前四类常表现为权限拒绝，后两类要检查文件类型、架构和解释器路径。

不要只看到 Permission denied 就直接 chmod 777。

## 19. Login shell 与权限环境

sudo、su、SSH、图形终端、cron、systemd 启动的进程，其：

- HOME；
- PATH；
- 当前目录；
- shell；
- 环境变量；

可能完全不同。

调试“手工运行成功、服务运行失败”时，必须比较执行身份和环境。

## 20. 安全原则

权限问题优先采用：

~~~text
确认进程身份
→ 确认文件 owner/group
→ 确认目录逐级 x 权限
→ 确认 rwx/ACL
→ 确认 SELinux/AppArmor
→ 再考虑调整权限
~~~

目标是找到最小必要授权，不是扩大所有人的权限。

## 21. 小实验：umask 是按位屏蔽

在普通用户下运行，子 shell 退出后不会改变当前 shell 的 umask：

~~~bash
(
    study_dir=$(mktemp -d)
    umask 027
    touch "$study_dir/note"
    mkdir "$study_dir/subdir"
    ls -ld "$study_dir/note" "$study_dir/subdir"
    printf '练习目录：%s\n' "$study_dir"
)
~~~

在没有额外默认 ACL 的常见环境中，文件通常为 `rw-r-----`（640），子目录为 `rwxr-x---`（750）：创建请求分别为 666、777，再按位屏蔽 027。它不是十进制减法，`touch` 也不会给普通文件自动添加执行位。

自测：文件设为 444 就一定不能被删除吗？答：不一定。删除名字主要由父目录写/执行权限决定，再受 sticky bit、ACL、只读挂载等约束。练权限使用自己的临时目录，不对系统目录递归 chmod。
