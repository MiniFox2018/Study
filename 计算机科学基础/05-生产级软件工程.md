# 05｜生产级软件工程

## 1. 目标

生产软件不是“能跑”，而是：

- 可读；
- 可测试；
- 可部署；
- 可观测；
- 可回滚；
- 可维护。

## 2. Linux 与命令行

长期需要掌握的是抽象：

- process / signal；
- stdin/stdout/stderr；
- pipe；
- file permission；
- environment variable；
- shell composition；
- process inspection；
- network diagnostics。

不固化某个发行版或工具的短期 UI。

## 3. Git

核心对象：

```text
working tree
→ index
→ commit
→ branch/ref
→ remote
```

重要实践：

- 小而完整的 commit；
- 清晰 commit message；
- branch 生命周期短；
- review 前先自检；
- 能解释 merge/rebase 的差别；
- 不把生成物、密钥和大文件误提交。

## 4. Codebase Design

高质量代码库要控制：

- module boundaries；
- dependency direction；
- public interface；
- configuration；
- error handling；
- side effects。

原则：

> 让局部修改尽量保持局部影响。

避免“方便起见”的跨层引用逐步把系统耦合成一团。

## 5. Testing

测试金字塔可理解为：

- unit：便宜、定位快；
- integration：验证组件边界；
- end-to-end：验证关键用户路径。

此外还应有：

- property / invariant test；
- regression test；
- contract test；
- performance test。

测试不是追求覆盖率数字，而是保护高风险行为。

## 6. CI/CD

CI 负责持续验证：

```text
lint
→ type/static checks
→ tests
→ build
→ security scan
```

CD 再负责：

- artifact；
- staging；
- canary / blue-green；
- rollout；
- rollback。

## 7. Container

容器解决的是可重复运行环境和隔离，不等于完整运维系统。

生产中还要关心：

- image provenance；
- resource limit；
- secret；
- network；
- persistent storage；
- health check。

完整容器知识已独立整理到 [容器化与 Docker](./07-容器化与Docker/README.md)，这里不再重复维护。

## 8. Observability

三类信号：

- logs：发生了什么；
- metrics：系统总体状态；
- traces：一次请求跨组件经历什么。

关键原则是让异常可以被定位，而不是只知道“出错了”。

## 9. Configuration 与 Secret

配置应与代码分离；秘密信息不应硬编码或提交 Git。

需要明确：

- environment；
- validation；
- default；
- ownership；
- rotation。

## 10. Coding Agent 的正确位置

AI 编码 Agent 可以加速：

- 搜索代码；
- 生成候选补丁；
- 测试；
- 重构；
- 文档；

但不能替代：

- 需求边界；
- architecture ownership；
- correctness verification；
- security review；
- production accountability。

使用 Agent 时，应给出明确上下文、验收标准和测试闭环。

来源：Compendium Chapter 15；去除具体工具版本，只保留长期工程方法。

## 11. 一个小功能怎样达到可维护状态

以“读取成绩文件并返回平均分”为例：输入契约先规定空文件如何处理、分数范围、坏行是报错还是跳过。解析函数接受文本并返回结果，文件 I/O 在外层处理；这样单元测试不必启动数据库或网络。

必要案例包括正常两行、空输入、非法字符、越界分数。集成测试再检查真实文件权限/编码失败。部署记录应能连接源码 commit、构建产物、配置版本与观察到的错误率。

自测：回滚二进制是否自动恢复已修改数据库？答：不会。存在数据迁移时，必须设计新旧版本兼容、备份恢复或可逆迁移；“有上一个镜像”不等于所有状态都可回滚。

学习记录用中文写清楚需求、测试证据和残留限制。一次修复应先让失败案例稳定复现，再确认修复后通过，避免把“程序能启动”当全部验收。

## 12. 软件工程定律：把经验变成决策检查表

生产级工程除了工具链，还需要一组能帮助识别风险和权衡的心智模型。用户提供的 *Laws of Software Engineering* 卡牌已完整整理为独立章节：

- [软件工程定律与工程决策](./05-1-软件工程定律与工程决策.md)

该章节覆盖 56 条定律/原则/启发式，分为：

```text
Architecture
→ Teams
→ Planning
→ Quality
→ Scale
→ Design
→ Decisions
```

学习时不要把“Law”都当成同一种强度的科学定律。可以分成四类理解：

1. **硬约束/形式化关系**：例如 CAP、Amdahl；
2. **工程设计原则**：例如 YAGNI、DRY、KISS、SOLID、Testing Pyramid；
3. **组织与项目启发式**：例如 Conway、Brooks、Bus Factor、Peter；
4. **认知与决策工具**：例如 Goodhart、Sunk Cost、Confirmation Bias、First Principles、Inversion。

最有用的学习方式不是背定义，而是在真实变更前把它们变成问题：

- API 的未文档行为是否已经有人依赖？→ Hyrum
- 这次重写是否在重复 Second-System Effect？
- 增加人手会提高并行度，还是只增加沟通？→ Brooks
- 指标是否已经从“测量”变成“目标”？→ Goodhart
- 这段抽象是真的减少知识重复，还是只是为了 DRY 而 DRY？
- 当前判断有没有主动寻找反证？→ Confirmation Bias
- 如果项目三个月后失败，最可能怎么失败？→ Inversion

这一页承担软件工程“怎么做”的主线；05-1 章节补充“为什么这些取舍经常出错，以及评审时如何检查”。
