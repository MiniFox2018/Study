# 05｜生产级软件工程

## 1. 目标

生产软件不是“能跑”，而是：

- 可读；
- 可测试；
- 可部署；
- 可观测；
- 可回滚；
- 可维护。

## 2. Linux 与命令行

长期需要掌握的是抽象：

- process / signal；
- stdin/stdout/stderr；
- pipe；
- file permission；
- environment variable；
- shell composition；
- process inspection；
- network diagnostics。

不固化某个发行版或工具的短期 UI。

## 3. Git

核心对象：

```text
working tree
→ index
→ commit
→ branch/ref
→ remote
```

重要实践：

- 小而完整的 commit；
- 清晰 commit message；
- branch 生命周期短；
- review 前先自检；
- 能解释 merge/rebase 的差别；
- 不把生成物、密钥和大文件误提交。

## 4. Codebase Design

高质量代码库要控制：

- module boundaries；
- dependency direction；
- public interface；
- configuration；
- error handling；
- side effects。

原则：

> 让局部修改尽量保持局部影响。

避免“方便起见”的跨层引用逐步把系统耦合成一团。

## 5. Testing

测试金字塔可理解为：

- unit：便宜、定位快；
- integration：验证组件边界；
- end-to-end：验证关键用户路径。

此外还应有：

- property / invariant test；
- regression test；
- contract test；
- performance test。

测试不是追求覆盖率数字，而是保护高风险行为。

### 5.1 预期答案从哪里来，偶发失败怎样处理

Test Oracle指判断结果对错的依据，可以是业务规格、可手算的不变量、经过独立核查的参考实现或人工标注。生成代码的模型再说“我检查过了”，并不会自动产生独立依据。例如平均分输入 `[60, 80]` 应为70，空输入如何处理则先由需求规定；拿同一段待测代码生成预期值，可能把同一个错误复制进测试。

还可使用变形关系：不改变记录内容的行重排不应改变总量；数量和单位同时正确换算后，物理结果应等价。但时间排序任务本来就可能依赖顺序，不能套用重排不变。关系来自任务合同，检出不一致很有用，通过有限关系仍不证明全部答案正确。

Flaky test表现为看似等价的条件下时而通过、时而失败。保存第一次失败的输入、seed、时钟、测试顺序、并发调度、依赖与环境；区分测试未清理共享状态、时序断言过紧，以及产品真实的间歇并发错误。可以用受控重复定位条件，不能只重跑到一次绿灯后删掉失败。确需临时隔离时，记录负责人、原因、修复期限和被移出发布门的风险，继续观察结果。[pytest的Flaky tests说明](https://docs.pytest.org/en/stable/explanation/flaky.html)列出状态、并行顺序及断言等常见成因（2026-10-16核对相应段落，未安装或运行插件）。

**自检**：同一请求偶尔扣款两次，测试重跑后通过，能否称“测试不稳定”并删除？不能。先保失败与真实效果证据，尝试受控复现，核对幂等和并发；偶发只描述出现方式，不免除产品缺陷。第11节的小功能也应先明确oracle，再用失败和修复后的对应输入验收。

## 8. Observability

三类信号：

- logs：发生了什么；
- metrics：系统总体状态；
- traces：一次请求跨组件经历什么。

关键原则是让异常可以被定位，而不是只知道“出错了”。

## 9. Configuration 与 Secret

配置应与代码分离；秘密信息不应硬编码或提交 Git。

需要明确：

- environment；
- validation；
- default；
- ownership；
- rotation。

## 11. 一个小功能怎样达到可维护状态

以“读取成绩文件并返回平均分”为例：输入契约先规定空文件如何处理、分数范围、坏行是报错还是跳过。解析函数接受文本并返回结果，文件 I/O 在外层处理；这样单元测试不必启动数据库或网络。

必要案例包括正常两行、空输入、非法字符、越界分数。集成测试再检查真实文件权限/编码失败。部署记录应能连接源码 commit、构建产物、配置版本与观察到的错误率。

自测：回滚二进制是否自动恢复已修改数据库？答：不会。存在数据迁移时，必须设计新旧版本兼容、备份恢复或可逆迁移；“有上一个镜像”不等于所有状态都可回滚。

学习记录用中文写清楚需求、测试证据和残留限制。一次修复应先让失败案例稳定复现，再确认修复后通过，避免把“程序能启动”当全部验收。

## 12. 软件工程定律：把经验变成决策检查表

生产级工程除了工具链，还需要一组能帮助识别风险和权衡的心智模型。用户提供的 *Laws of Software Engineering* 卡牌已完整整理为独立章节：

- [软件工程定律与工程决策](./05-1-软件工程定律与工程决策.md)

该章节覆盖 56 条定律/原则/启发式，分为：

```text
Architecture
→ Teams
→ Planning
→ Quality
→ Scale
→ Design
→ Decisions
```

学习时不要把“Law”都当成同一种强度的科学定律。可以分成四类理解：

1. **硬约束/形式化关系**：例如 CAP、Amdahl；
2. **工程设计原则**：例如 YAGNI、DRY、KISS、SOLID、Testing Pyramid；
3. **组织与项目启发式**：例如 Conway、Brooks、Bus Factor、Peter；
4. **认知与决策工具**：例如 Goodhart、Sunk Cost、Confirmation Bias、First Principles、Inversion。

最有用的学习方式不是背定义，而是在真实变更前把它们变成问题：

- API 的未文档行为是否已经有人依赖？→ Hyrum
- 这次重写是否在重复 Second-System Effect？
- 增加人手会提高并行度，还是只增加沟通？→ Brooks
- 指标是否已经从“测量”变成“目标”？→ Goodhart
- 这段抽象是真的减少知识重复，还是只是为了 DRY 而 DRY？
- 当前判断有没有主动寻找反证？→ Confirmation Bias
- 如果项目三个月后失败，最可能怎么失败？→ Inversion

这一页承担软件工程“怎么做”的主线；05-1 章节补充“为什么这些取舍经常出错，以及评审时如何检查”。

## 15. AI辅助值班：证据、假设与修复授权

2026-10-10 融合Phase17第23课。先修为本章logs/metrics/traces、版本化部署与[工具授权](../Agentic%20Design%20Patterns/06-专题扩展/07-工具授权与发布治理.md)。AI可把事故窗口内日志、指标、拓扑、近期变更与runbook汇成证据，减少人工搜索；核心工作是把“症状”“假设”“因果证据”“可执行动作”分开。

例如KV分配失败与显存98%同时出现，支持容量压力假设，却不直接证明谁先发生或哪个变更造成。日志Agent给event ID/可信时间/服务/版本，指标Agent给查询、窗口、基线与缺失，runbookAgent给适用版本、前提和过往处置效果；supervisor列相符及矛盾证据、其他假设与下一条低风险验证。三段自由文本的前30字符相同不表示相同原因，自报0.88也不是校准概率。两个模型读取同日志可能共享错误，赞同不能充当生产批准。

事故流程先指派明确负责人，记录影响和严重性；先缓解，再持续定位根因，交接时保时间线与未解决分支。只读调查也可能泄露数据、增加查询负载，需按租户和事故对象给工具最小权限。自动修复依预批准策略检查**具体对象、当前健康、前提、爆炸半径、预算、租约/版本、重复执行和撤权**。重启唯一副本或有未落盘状态的Pod同样危险；“restart”这个名称不自动安全。调整GPU限额可能改变质量/容量和重启行为，应单独审核，不能埋在“安全重启”里。

结构化runbook可以用普通Markdown维护，包含：适用服务/版本、症状与SLI、最近变更、证据查询与时间窗、假设和反例、允许动作及前提、对象范围、批准/执行责任、检查/终止/回退、效果回执、审计和最后核验日期。过往runbook成功不证明今天适用；RAG按版本/权限检索，保留废弃标记和修订原因。

预测预警另需评价precision、recall、假警报/日、提前量分布、漏报严重性和时间留出，区分事故前可获得信号与事后信息泄漏。预测可触发人工检查、预排空或有限扩容，各自须事先授权；一个可检索的风险看板也有价值，不必把预测直接接高风险自动执行。源“MIT预测89%且提前10–15分钟”没有具体论文/数据入口，未采纳；同样不采纳固定2026企业自动failover比例、事件少于10/月就不可用或固定12周交付。

### 第23课：原练习与六题参考

1. **日志与指标意见不同怎么处理？** 对齐事故/服务/时间窗，查缺失与单位，保多个假设和可区分验证；原supervisor按字符串前缀分组、按自报分数排序，既无语义合并也无反证，默认动作不能由排序结果自动接纳。
2. **定义三种可自动修复动作。** 单健康冗余副本的受限重启、兼容版本的受限回退、预算内受限扩容可以作为候选，但每种都要对象绑定、当前健康、效果核对、失效/终止与权限，不称普遍安全动作。
3. **结构化runbook怎样填？** 按本节字段对一个具体服务填真实query/探针、版本和阈值；未知处明确待核，不生成会直接执行的通用kubectl命令。只读验证和写动作分栏。
4. **提前12分钟预警怎样决策？** 基于可校准的概率、事故损失与处置损失决定是否page/人工查/有界预排空；假阳性排空也可能造成事故。没有真实预测质量时先只读或影子验证，保提前量。
5. **三人团队怎样选？** 比较重复调查的时间、可观测性、runbook质量、数据权限与维护成本；先验证一条有用的只读事故工作流，再决定加工具/协作/修复，不按人头和年份机械判断。

原六题：①supervisor+专业调查+人类判断是一种可用结构，非唯一标准。②restart/revert/scale只有符合当前授权和前提才可执行。③双模型赞同增加一个交叉信号，不能证明根因或放行。④运行手册和复盘帮助跨人员保留经验，但向量库不是必要前提。⑤原MIT数字未核验，不作为正确学习答案。⑥预测的价值与处置策略、假警报和可观察反馈相关，未授权时不可直接动作。

## 16. 可控故障注入：SLO预算与终止条件

Phase17第24课的长期价值是**通过有界试验检验恢复假设**，不是随机破坏生产。先在受控环境说明稳态、待检故障、受影响对象/用户、时长、恢复标准、观测数据、终止阈值和负责人；已存在事故或重要观测缺失时保留暂停。控制、目标、安全与观测是职责，反馈进入代码/runbook/依赖图改进，不必机械部署四套工具。

SLI是好事件/有效事件或指定延迟/质量条件，SLO是规定窗口的目标。对请求成功率SLO S，允许坏事件比例为1−S，burn rate $B=e/(1-S)$，e是**同口径窗口观察错误率**；不同window和流量构成不能混用。99.9%目标且e=.002，B=2，不是相对健康基线.0005得到4。固定流量近似下，窗口w消耗全账期T的预算比例约 $B w/T$；真实变流量需用实际有效请求数和剩余额度。

[Google SRE多窗口方法](https://sre.google/workbook/alerting-on-slos/)在其30天、99.9%例中给长短窗口并用的参数，1h/5min且B14.4对应约2%预算；这些是设计例不是所有服务阈值。低流量下一个失败就能给很高比例，需要考虑业务损失、合成流量和长窗口。安全策略同时限制额外错误预算、用户严重后果、范围、持续时长和监控心跳，任一明确风险超限都可停止；不能要求“burn大且范围大”同时满足才停止。

### 完整离线例：独立停止门禁与缺数据

程序只核一条教学策略，窗口和阈值已由题设固定：范围最多20%、最大burn=2、99.9%请求SLO。真实系统需另外估监控延迟、双窗口、在途/恢复和业务伤害；它未执行故障。这里把str所表示的十进制SLO与阈值用Fraction精确比较，避免数值容差比一个极小阈值还大。这只是政策算术精确，不表示观测没有误差。HOLD表示不得开始或扩大；若故障已在注入，应先停止注入并核恢复，不在无流量时继续。

```python
import math
from fractions import Fraction as Q

def decision(errors,total,affected,slo=.999,burn_cap=2,scope_cap=.2,observable=True):
    if type(errors) is not int or type(total) is not int or not 0<=errors<=total or total<=0:
        return 'HOLD: 样本无效或无流量'
    numbers=(affected,slo,burn_cap,scope_cap)
    if any(type(x) is bool or not isinstance(x,(int,float)) or not math.isfinite(x) for x in numbers):
        return 'HOLD: 非法参数'
    if not (0<=affected<=1 and 0<slo<1 and burn_cap>0 and 0<scope_cap<=1):
        return 'HOLD: 范围无效'
    if type(observable) is not bool or not observable:
        return 'ABORT: 失去观察'
    burn=Q(errors,total)/(1-Q(str(slo)))
    reasons=[]
    if burn>Q(str(burn_cap)): reasons.append('burn')
    if Q(str(affected))>Q(str(scope_cap)): reasons.append('scope')
    return 'ABORT: '+','.join(reasons) if reasons else 'CONTINUE: 当前窗口满足策略'

assert decision(40,10000,.01).startswith('ABORT: burn')
assert decision(1,10000,.3).startswith('ABORT: scope')
assert decision(20,10000,.2).startswith('CONTINUE')  # 恰好burn=2/范围=.2
assert decision(1,10**15,.01,burn_cap=1e-13).startswith('ABORT: burn')
assert decision(0,10000,.01,observable=False).startswith('ABORT')
for e,n,a in [(True,100,.1),(0,0,.1),(0,100,float('nan')),(0,100,True)]:
    assert decision(e,n,a).startswith('HOLD')
print('精确边界与极小cap反例通过；小范围高burn和范围越界独立停止，缺数据不通过')
```

提供商429可以是限流，不等供应商宕机；模拟时分别注入持续限流、慢响应、网络中断、部分stream中断和错误状态。故障转移仍检查备用质量、数据授权、协议与成本，不能把任何第二供应商当自动可用。KV压力/驱逐可能引起重算/排队，需区分普通请求长度上限、prefill/decode内存和恢复轨迹。“巨大UTF-8码点”不是准确技术描述，Unicode标量有范围，应测试已定义的超长、非法编码或实际解析器复杂度，不虚构万能tokenizer bomb。

故障有experiment ID、对象和可信时间线，结合独立服务指标看全局/范围内影响，不能仅因为请求有标签就断定全部根因属于试验。抑制的是可识别重复噪声，严重事件与试验外真实事故仍报警。终止故障也不自动撤销已发生的写入或清理注入，需要验证恢复和补偿。[AWS FIS](https://docs.aws.amazon.com/fis/latest/userguide/stop-conditions.html)明确可用CloudWatch alarm停止且停止后的实验不能resume；工具支持“none”不代表无门禁是本系统可接受配置。

### 第24课：原练习与六题参考

1. **哪个原模拟停止？** 其burn按expected .0005计算，provider .015/.0005=30且scope=.30>.20，停止。pod .002/.0005=4、scope.05，malformed .04/.0005=80、scope.10，都因AND条件放行。正式例改按SLO允许率并独立门禁；不能说源码验证了小范围灾难安全。
2. **RAG服务五个受控实验。** 依次候选：一冗余decode副本失效、网关→提供商慢/断、429与有限重试、预定输入上限、KV驱逐压力。每项写故障对象/上界、预计降级、成功/停止、独立probe和恢复；先在staging验证，不实际注入。
3. **暂停后怎样分辨根因？** 对齐experiment与自然故障时间，比较未注入对照/依赖链/最近变更，检查监控本身异常；可能有叠加事故，不因为标签或时间相关就只归因chaos。
4. **生产还是staging？** staging先验证工具/门禁/恢复；生产用于环境差异确需验证且已有授权、容量、值班和可限制对象时。不能以“完整演练”跳过风险评估或当前事故。
5. **三个特殊故障。** KV压力触发preemption/recompute、部分SSE与token/usage丢失、长输入/工具循环造成资源放大；各需要对应注入/测量，网络断包不能穷尽它们。

六题：①SLI/SLO、观测、恢复/runbook/值班是必要准备例，还需具体授权与范围。②控制/目标/安全/观测加反馈是职责分工。③burn=窗口错误率/(1−SLO)，阈值按错误预算/风险设置，非统一2×健康基线。④KV驱逐压力是可检场景。⑤周期按变更/风险与恢复缺口安排，周/月/季不是规范要求。⑥恶意/异常输入可能耗资源，需明确合法码点、大小和被测解析器。

planes.svg与i4-chaos-guard解释控制/安全观察，但源图按时序预设两故障落地、第三被拦，无指标计算。CNCF的[Litmus孵化公告](https://www.cncf.io/blog/2022/01/11/litmuschaos-becomes-a-cncf-incubating-project/)和[Chaos Mesh孵化公告](https://www.cncf.io/blog/2022/02/16/chaos-mesh-moves-to-the-cncf-incubator/)分别确认2022年进入Incubating，源Graduated/Sandbox缺少正确依据；成熟度本身不保证本服务故障注入安全。源码duration没有参与预算，任何“COMPLETED”只是if结果，不是实际故障与恢复成功。本批没有生产演练或云操作。


## 17. 排障证据图：从受影响对象走到可审的修复提案

2026-10-11 融合 Phase19 第06课，补本章15节AI值班的对象关系与交互批准。目标是把事故窗口内的资料变成**有出处、可反证、范围明确的假设**，然后由独立执行责任方处理具体提案。五分钟和80%是原项目目标，未被课程demo证明，不是部署SLO或生产效果承诺。

### 17.1 对象身份、关系和时间窗

图节点用cluster/namespace/kind/UID/resourceVersion与采样时刻标识，避免两个namespace同名Pod覆盖；name可显示但不当全局identity。ownership通过ownerReferences保方向，例如Deployment→ReplicaSet→Pod；Pod→Node是调度关系。Service通过selector及实际endpoints关联后端，不把Service简单看成直接拥有Deployment。kube-state-metrics提供对象状态指标，可作输入，但完整拓扑还需API对象/关系与变化时间。

告警在Deployment时，受预算限制地BFS至ReplicaSet、Pod和Node，记录访问路径、边来源、深度/节点上限；关联受影响时间窗的metrics/logs/traces、近期rollout与基线。源Python neighbors只查一跳，拿Deployment无法走到Node，图上多跳动画不是实现；本章的方法需要显式队列、visited和数据新鲜度。旧节点重建产生新UID时，旧批准不能继续操作新对象。

例：checkout错误突然上升且十四分钟前rollout。先核错误率分子/分母、接口切片与时间对齐，再查新旧版本的Pod错误/健康、未更新服务对照、节点压力和依赖DNS。5xx请求rate单独不是错误率，需要同窗口总请求rate分母。假设“bad rollout”有部署和日志支持，仍要列反证：同版本旧Pod正常、错误发生更早或只在一个Node。排序可用近期性、特异性、路径与独立证据，但固定加权分不是因果概率，重复引用同日志不能伪造多项支持。

### 17.2 最小读取权限与修复执行器

Kubernetes RBAC核资源、API group、namespace及动词，不是kubectl命令词。`describe`是客户端聚合查询，真实只读通常按需给get/list/watch，Pod日志单独给`pods/log`；read-only的Secrets读取仍泄露敏感信息，不应随对象查询一起授予。Role在namespace生效，ClusterRole的最终范围依RoleBinding/ClusterRoleBinding决定。[官方RBAC资源和子资源例](https://kubernetes.io/docs/reference/access-authn-authz/rbac/#referring-to-resources)。

调查Agent只创建proposal，不持rollback/scale/delete执行凭据。proposal记录incident ID、cluster/namespace/UID、当前revision、动作和完整参数、证据、预期效果/范围、恢复/停止条件与期限。独立执行器核当前授权、健康和对象版本，接受具体绑定批准后原子claim；执行结果的未知/失败/恢复单独回报，不把HTTP200或“approved”当实际恢复。具体签名、撤权与效果对账继续复用[工具授权](../Agentic%20Design%20Patterns/06-专题扩展/07-工具授权与发布治理.md)。

### 17.3 Slack按钮为何还不是有效批准

Slack用raw body、timestamp和v0 HMAC basestring验来源，并核五分钟时间差及安全比较；验签前不能重编码form或JSON。[Slack官方签验步骤](https://docs.slack.dev/authentication/verifying-requests-from-slack/)。时间窗不阻止窗内重复请求；执行端还要核workspace/app、点击者身份及当前oncall角色、具体proposal版本/摘要、允许action、deadline与一次消费。正文表明“Alice点击批准”不等源Python传任意approver字符串就获得权限。

正常链：创建P42/UID7/rev42回退提案→展示证据和影响→有效人类批准该摘要→执行前核仍rev42→claim并执行→记录真实回执→独立SLI确认恢复。若期间部署变rev43、撤权或已执行，拒绝旧批准；未知effect进入对账。unknown incident或unknown action不能当ignore后偷偷执行。response_url是受信响应通道，保存/发送需受允许origin和资料策略限制，不在公开trace泄露。

源TS只按OOM/CrashLoop关键词返回固定说明和outbound意图列表，任意inc42都可mock批准；没有真实Slack消息、图谱查询或MCP修复。OOMKilled涉及limit/实际内存/节点压力等原因，单据此推断request太低不够；readiness失败通常影响流量资格，不引起重启，CrashLoop要区分liveness/startup及进程退出。故障测试套件应覆盖这些反例及错namespace、旧UID、无证据、批准重放与效果未知；排障top-k、查询负担、尾部耗时与最终SLO恢复分别测。审计的considered/blocked/approved/claimed/outcome留在可信边界，内存list不是不可篡改日志。

## 18. 签名Webhook：先可靠接收，再明确处理

外部系统用HTTP回调通知“报告已上传”，接收者可能先保存再交给Agent处理。发送端没收到响应会重试，服务也可能在写盘后、回响应前崩溃，因此至少分清三种身份：

- **delivery ID**：一次传输投递的身份，重试通常沿用它；
- **business event ID**：正文中实际业务事件的身份，不同投递也可能指向同一事件；
- **processing run ID**：接收方一次明确处理/重放的身份，同一投递可以经批准产生新的处理轮次。

验签回答“这些字节是否符合当前密钥与协议”，收件箱回答“是否可靠接收过这次投递”，处理回执回答“本地这次处理生成过什么”。它们都不能独立证明外部业务效果恰好发生一次。第17.3节Slack的具体协议与本节自有教学格式分别理解，不混用签名串。

### 18.1 保留原始字节，再解释业务JSON

从请求中读取方法、投递ID、时间戳、签名和**有上限的原始正文**。例如 `{"a":1}\n` 与 `{ "a" : 1 }\n` 表达相同对象，但签名输入字节不同；验签前不能解析后重新序列化，也不能删除文件末尾换行。

可用的读取合同：POST；ID只允许明确的ASCII字符与长度；时间戳为规范int64十进制秒，拒绝前导零、正号、空白等非规范形式；正文1～65536字节。读65537字节可发现超限，不能先无限读完再检查。头部大小、慢读、连接数、解压后的大小和总截止时间仍需HTTP栈/应用限制。

读入合法不等于验签成功；验签成功也不等于业务JSON有效。正文可能是任意已认证字节，后续处理器再要求对象中有eventId与data，非法业务结构记处理失败，不伪造“没有收到”。不要在错误正文回显密钥、原始负载或内部文件路径。

### 18.2 HMAC还需要无歧义的待签名编码

HMAC-SHA256使用双方共享的秘密对**一段字节串**作认证；不是加密，也不是只有发送者才能生成的公开签名。掌握同一密钥的接收者也能生成MAC。密钥应有足够随机性、按来源/环境隔离、可轮换；“长度至少16字节”只是本课检查，并不证明它有足够熵。MAC用安全比较函数，如Go的 `hmac.Equal`，不能以普通字符串比较替代。[Go官方HMAC说明](https://pkg.go.dev/crypto/hmac)。

来源v1把 `十进制时间戳 + "." + deliveryID + "." + rawBody` 作为消息。但ID允许句点，正文又允许任意字节，编码不是一一对应：

```text
时间相同，ID=a，正文=1.23    → 1770000000.a.1.23
时间相同，ID=a.1，正文=23   → 1770000000.a.1.23
```

两种ID都合规，两个正文甚至都是有效JSON数值，却形成相同MAC输入。这是**字段编码歧义**，不需要破解HMAC；来源只修改ID或只修改正文的测试不能发现“同时改变字段边界”的反例。接收层接受原始字节，即使后续业务处理器要求对象，这个认证边界仍然有缺口。

修正方法是采用供应商明确规定且无歧义的格式；自行设计时可固定字段长度，或对各字段加长度前缀，并包含版本/用途域分隔。若改变格式，升级版本并明确迁移；不能静默修改一个既有供应商的协议。

下面自有例使用4字节大端长度前缀和用途前缀，测试歧义、原字节和时间窗；**它不是来源v1，也不是任何服务的标准接口**。不提供密钥管理、HTTP、轮换或持久接收实现。

```python
"""自有有限CPU例：原教学拼接的歧义与长度前缀修正；无网络/文件收件箱。"""
import hashlib
import hmac
import re

VALID_ID = re.compile(r"[A-Za-z0-9][A-Za-z0-9._-]{0,127}", re.ASCII)

def fields(stamp, delivery_id, body):
    if type(stamp) is not int or not -(2**63) <= stamp < 2**63:
        raise ValueError("int64秒")
    if type(delivery_id) is not str or not VALID_ID.fullmatch(delivery_id):
        raise ValueError("投递ID")
    if type(body) is not bytes or not 1 <= len(body) <= 65536:
        raise ValueError("原始正文")
    return str(stamp).encode("ascii"), delivery_id.encode("ascii"), body

def ambiguous(stamp, delivery_id, body):
    return b".".join(fields(stamp, delivery_id, body))

def framed(stamp, delivery_id, body):
    # 这是另一个自有教学格式，不冒充v1或任何供应商协议。
    return b"study-webhook-v2\0" + b"".join(
        len(part).to_bytes(4, "big") + part
        for part in fields(stamp, delivery_id, body)
    )

def tag(key, message):
    if type(key) is not bytes or len(key) < 16:
        raise ValueError("教学最小密钥长度")
    return hmac.digest(key, message, "sha256")

def verify(key, stamp, delivery_id, body, signature, now, skew=300):
    fields(stamp, delivery_id, body)
    if type(now) is not int or not -(2**63) <= now < 2**63:
        raise ValueError("当前int64秒")
    if type(skew) is not int or not 0 <= skew <= 3600:
        raise ValueError("时间窗")
    if type(signature) is not bytes or len(signature) != 32:
        return False
    if not now-skew <= stamp <= now+skew:
        return False
    return hmac.compare_digest(tag(key, framed(stamp, delivery_id, body)), signature)

key = b"owned-test-key-not-for-production"
now = 1770000000
left = (now, "a", b"1.23")
right = (now, "a.1", b"23")
assert left != right and ambiguous(*left) == ambiguous(*right)
assert tag(key, ambiguous(*left)) == tag(key, ambiguous(*right))
assert framed(*left) != framed(*right)
sig = tag(key, framed(*left))
assert verify(key, *left, sig, now)
assert not verify(key, *right, sig, now)
assert not verify(key, now, "a", b"1.23\n", sig, now)
for offset, accepted in [(-301, False), (-300, True), (300, True), (301, False)]:
    stamp = now + offset
    signed = tag(key, framed(stamp, "a", b"1.23"))
    assert verify(key, stamp, "a", b"1.23", signed, now) == accepted
print("点分隔不同字段同签名反例成立；长度前缀区分ID/正文，原字节和时间窗边界通过")
```

### 18.3 在确认接收之前持久化

接收链可写成：限量读原字节 → 验证头部/签名/时间窗 → 以投递身份原子接收 → 确认接收 → 独立处理。

来源本地文件算法的作用是解释持久化与并发：

1. 在可信收件目录内创建私有临时文件，完整写入schemaVersion、delivery ID、原始body、摘要和首次acceptedAt。
2. 同步文件内容并检查写入/关闭错误。
3. 用**不能覆盖已有目标**的原子发布操作把临时文件发布为正式记录。来源用同目录硬链接；普通覆盖rename不具有同样去重语义。
4. 同步目录项，成功后才能宣称可靠接收；临时路径可清理，崩溃遗留的`.pending`不算正式记录。
5. 若目标已存在，重新读并校验既有记录；同ID同字节返回原acceptedAt，不覆盖；同ID异字节明确冲突。

为什么不能先 `exists()` 再 `write()`：两个并发请求都可能看到不存在，随后互相覆盖。必须让“第一次发布”由文件系统原子原语或数据库唯一约束裁决，再核对胜出记录。来源12个并发同ID测试只覆盖一个受控场景，不是所有文件系统崩溃语义的证明。Go的[Link](https://pkg.go.dev/os#Link)、[File.Sync](https://pkg.go.dev/os#File.Sync)提供基础操作；具体耐久性依操作系统、文件系统和存储兑现，不能推广到任意网络盘。

若链接已经建立但随后的目录同步失败，发布可能已经发生；请求返回500不证明“未接收”。后续认证重试仍按同ID回读对账，不能覆盖或换ID来掩盖未知结果。

文件名可使用ID的SHA-256来减少路径注入，但不能因此信任整个存储目录。已有目录权限不会因 `MkdirAll(...,0700)` 自动收紧；可写祖先、符号链接与替换风险另核。新文件0600也不等于已加密。正文在JSON中被base64编码只是编码，敏感原文仍在，不能当脱敏上下文交给模型。

### 18.4 首次、重复、冲突与业务完成分别回报

| 来的请求 | 接收层处理 | 不能推导的结论 |
|---|---|---|
| 新ID、有效认证、正文A | 本地可靠接收后示例返回202 | 业务动作尚未执行 |
| 同ID、有效认证、同正文A | 返回已有记录，示例200 | 不能证明处理器已成功或无需重试 |
| 同ID、正文B、沿用A签名 | 认证失败，示例401 | 不能进入存储比较后接受 |
| 同ID、正文B、有B的有效签名 | 身份冲突，示例409 | 不能悄悄覆盖A |
| 不同ID、相同business event | 可是两次不同投递 | 业务是否应去重由下游政策决定 |

**摘要不是存储真实性证明。** LoadEntry核schema、ID和body摘要能发现部分损坏；若攻击者可同时修改正文和摘要，它并不能验证原始签名。来源接收记录未保存完整验签信封，重放依赖受保护的本地存储与接收链。需要独立重验时，按政策保存必要的签名版本、原始时间戳、key ID等证据，并考虑密钥轮换与留存，不能保秘密密钥本身在记录内。

### 18.5 显式重放与处理回执

处理器只加载已接收记录，再解析业务对象。回执以 `(deliveryID, runID)` 唯一标识，绑定body摘要、businessEventID、处理时间和输出payload。同一run重试必须回原回执；换run是新的明确处理，不是伪造另一条传输。

例如delivery-1携business-42，run review-1生成一份回执；重复review-1不新建，review-2可按明确授权重新处理。delivery-2也携business-42时，传输身份不同，仍需业务层决定是否已完成同一业务动作。

来源processing只生成本地JSON，不调用外部系统。若改成发邮件/改工单，可能出现外部动作完成而回执未落盘；重试又做一次。解决需外部幂等键、事务性outbox/队列与效果回读，具体恢复沿[异常处理和恢复](../Agentic%20Design%20Patterns/01-核心章节/12-异常处理和恢复.md)。不能把本地文件原子创建推广成外部exactly-once。

重复回执也须核schema、投递/run身份、源body摘要、业务ID和payload；仅比较文件存在不够。来源使用JSON压缩后字节比较payload，只去无意义空白，不实现对象键序无关的语义等价。`data:null`与缺data、空eventId、重复JSON键及业务字段类型要有单独合同，来源最小解析不替代完整业务schema。
