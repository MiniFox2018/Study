# 05｜生产级软件工程

## 1. 目标

生产软件不是“能跑”，而是：

- 可读；
- 可测试；
- 可部署；
- 可观测；
- 可回滚；
- 可维护。

## 2. Linux 与命令行

长期需要掌握的是抽象：

- process / signal；
- stdin/stdout/stderr；
- pipe；
- file permission；
- environment variable；
- shell composition；
- process inspection；
- network diagnostics。

不固化某个发行版或工具的短期 UI。

## 3. Git

核心对象：

```text
working tree
→ index
→ commit
→ branch/ref
→ remote
```

重要实践：

- 小而完整的 commit；
- 清晰 commit message；
- branch 生命周期短；
- review 前先自检；
- 能解释 merge/rebase 的差别；
- 不把生成物、密钥和大文件误提交。

## 4. Codebase Design

高质量代码库要控制：

- module boundaries；
- dependency direction；
- public interface；
- configuration；
- error handling；
- side effects。

原则：

> 让局部修改尽量保持局部影响。

避免“方便起见”的跨层引用逐步把系统耦合成一团。

## 5. Testing

测试金字塔可理解为：

- unit：便宜、定位快；
- integration：验证组件边界；
- end-to-end：验证关键用户路径。

此外还应有：

- property / invariant test；
- regression test；
- contract test；
- performance test。

测试不是追求覆盖率数字，而是保护高风险行为。

### 5.1 预期答案从哪里来，偶发失败怎样处理

Test Oracle指判断结果对错的依据，可以是业务规格、可手算的不变量、经过独立核查的参考实现或人工标注。生成代码的模型再说“我检查过了”，并不会自动产生独立依据。例如平均分输入 `[60, 80]` 应为70，空输入如何处理则先由需求规定；拿同一段待测代码生成预期值，可能把同一个错误复制进测试。

还可使用变形关系：不改变记录内容的行重排不应改变总量；数量和单位同时正确换算后，物理结果应等价。但时间排序任务本来就可能依赖顺序，不能套用重排不变。关系来自任务合同，检出不一致很有用，通过有限关系仍不证明全部答案正确。

Flaky test表现为看似等价的条件下时而通过、时而失败。保存第一次失败的输入、seed、时钟、测试顺序、并发调度、依赖与环境；区分测试未清理共享状态、时序断言过紧，以及产品真实的间歇并发错误。可以用受控重复定位条件，不能只重跑到一次绿灯后删掉失败。确需临时隔离时，记录负责人、原因、修复期限和被移出发布门的风险，继续观察结果。[pytest的Flaky tests说明](https://docs.pytest.org/en/stable/explanation/flaky.html)列出状态、并行顺序及断言等常见成因（2026-10-16核对相应段落，未安装或运行插件）。

**自检**：同一请求偶尔扣款两次，测试重跑后通过，能否称“测试不稳定”并删除？不能。先保失败与真实效果证据，尝试受控复现，核对幂等和并发；偶发只描述出现方式，不免除产品缺陷。第11节的小功能也应先明确oracle，再用失败和修复后的对应输入验收。

## 8. Observability

三类信号：

- logs：发生了什么；
- metrics：系统总体状态；

## 9. Configuration 与 Secret

配置应与代码分离；秘密信息不应硬编码或提交 Git。

需要明确：

- environment；
- validation；
- default；
- ownership；
- rotation。

配置漂移是“按声明与覆盖规则算出的应有配置”和“从运行环境取得的配置”之间的差异。它能提示排障方向，却不直接说明哪一方正确：声明可能过期，采集可能不完整，运行环境也可能确实被误改。先核对象、环境、版本、时间与采集权限，再判断是否需要修改配置。已有的配置与Secret原则保留，本节补全如何比较和解释。

### 9.1 先把输入合同说清楚

采用一个易于审计的最小合同：`layers` 是有序配置层，每层有唯一的非空 `name` 和 `values`；`observed` 是观测到的键值表；`sensitive` 可列出需要脱敏的额外精确键名。`values` 和 `observed` 的值只能是 JSON 标量：null、字符串、布尔值、有限范围内的数值。`layers:[]`、空键值表允许；缺少必需字段、null映射、空白键、键内换行或NUL、重复层名、未知结构字段、尾随第二个JSON值应拒绝。

这是**平面键合同**。`db.host` 只是含点号的一个键，不自动代表 `db` 对象中的 `host`。对象与数组都拒绝，因而不暗中约定深层合并、数组拼接、按索引覆盖或删除。环境层名 `env:TIMEOUT` 只是来源标识，不会读取系统环境变量，更不会展开 `$HOME` 等字符串。需要读取真实文件、环境变量、CLI参数时，先由适配器采集、解析类型，再按明确顺序构造这些层。

若上游是嵌套JSON，适配器必须另定无碰撞的路径编码，例如不能把原键 `a.b` 与对象 `a` 下的键 `b` 都扁平化为 `a.b`。数组需明确整体替换还是按元素身份合并；没有此合同就拒绝，不能借用本例假装已经支持。若还需要“删除键”，增加显式删除操作，不能把null偷偷改成删除。

来源参考实现使用 Go `encoding/json` v1 解到 `any`，数值成为 `float64`。这会使 `9007199254740992` 与 `9007199254740993` 落到同一个二进制浮点数，无法可靠比较这类整数ID。精确数值系统需要在输入和比较合同中一并选择 `json.Number`、定长整数或十进制表示；不能只换解码选项却仍让验证器仅接受 `float64`。`1` 与 `1.0` 在该参考实现中数值相同，`"1"` 与 `1`、`true` 与 `1` 则不同。

`DisallowUnknownFields` 也不等于严格JSON模式验证：来源没有额外拒绝重复JSON成员，结构字段仍按v1规则接受大小写不敏感匹配，非法UTF-8字符串可被替换字符修复。需要消除这些歧义时，应在解码边界明确检测并拒绝，而不能把“不在单元测试中”当作没有问题。[Go JSON官方文档](https://pkg.go.dev/encoding/json#Unmarshal)说明这些解码语义；2026-10-23仅核对应条目，未运行Go程序。

### 9.2 按声明顺序解析，而不是按文件名猜优先级

设每个键的解析结果为 `Effective(value, history)`。依次遍历层；看到键就把它的有效值替换为当前层值，并在该键的历史末尾追加 `(层名, 值)`。不含该键的后续层不改变它。

例如默认层 `timeout=30, region="local"`，随后环境层 `timeout=5`，结果为 `timeout=5`、历史 `[(defaults.json,30),(env:TIMEOUT,5)]`，`region` 仍是 `local`。如果最后一层是 `timeout=null`，结果是“键存在、值为null”，历史保留全部三次声明。这与根本没有声明timeout、或声明空字符串不同。

层顺序属于输入合同，不从名字、目录层级或“环境通常更重要”推测。历史让学习者回答“最终值来自哪一层”“哪一层被遮蔽”“删去某个覆盖会暴露什么旧值”。但输入层名只是调用方标签，不是文件真实性证明；不能凭写了 `production.yaml` 就认定真的读过该文件。解析中间结果保留原始秘密，不能直接记录到公共日志或交给模型。

### 9.3 先判断键是否存在，再比较值

比较有效键集合与观测键集合的并集，一键一行，最后按键名稳定排序。存在性和取出的值分开保存，不能用 `value==null` 代替“缺失”。四类判断如下：

| 应有侧存在 | 观测侧存在 | 值关系 | 类别 |
|---|---|---|---|
| 否 | 是 | 无需比较 | unexpected：观测多出了声明外键 |
| 是 | 否 | 无需比较 | missing：缺少应有键 |
| 是 | 是 | 同类型且值相等 | equal |
| 是 | 是 | 其余情况 | changed |

并集没有“两侧都不存在”的行。只要有任意非equal行，总体 `drift=true`。这只表示差异存在，不表示所有差异都必须阻断发布。

完整小例（下面都是JSON数据，不是需要执行的程序）：

```json
{
  "layers": [
    {"name": "defaults.json", "values": {"timeout": 30, "nullable": 1, "region": "local", "api_token": "demo-old"}},
    {"name": "env:TIMEOUT", "values": {"timeout": 5, "nullable": null}}
  ],
  "observed": {"timeout": 30, "nullable": null, "api_token": "demo-new", "extra": false}
}
```

按键排序的结果：`api_token=changed`，`extra=unexpected`，`nullable=equal`，`region=missing`，`timeout=changed`。timeout的有效值5来自环境层，但观测仍是30；region缺失并不是region显式为null。nullable的null覆盖1后，两侧都存在null，所以相等。所有值都为空或为0也不能用真假值判断存在性。

来源v1报告对缺失的一侧也序列化为null，因此只看 `expected`/`observed` 字段无法区分缺失和显式null，必须结合 `kind`。更强的后续schema可直接增加 `expectedPresent`、`observedPresent`，并递增版本；消费者应拒绝未知版本或显式降级，不能静默套用旧含义。

### 9.4 先分类，再脱敏，包括历史值

如果先把所有秘密都替换为同一个 `[REDACTED]` 再比较，旧token和新token会被误判为相等。正确顺序是：在受信边界内用原值判断类别，再构造可导出副本，将敏感键的应有值、观测值、每一条历史值一并替换。不要只遮最终值，却让旧密码藏在history里。

最小启发式可对键名做不区分大小写的子串匹配：`password`、`secret`、`token`、`api[_-]?key`、`credential`，再并上调用者提供的敏感精确键名列表。比如 `api_token` 的两个值显示都为 `[REDACTED]`，类别仍为changed；观测中突然出现的 `TOKEN` 也应脱敏，history为空；同一个密码两侧相等则为equal且仍脱敏。缺失侧没有秘密，保持null，不伪造为遮蔽值。

启发式有漏报和误报。`opaque="真实秘密"` 不会自动命中，需显式列入sensitive；`tokenCount` 可能被遮得过宽。显式列表在参考实现中按原键精确匹配，大小写不同不是同一项。脱敏仍保留键名、来源名、变化类别、历史层数和非敏感值，足以暴露某些系统结构或变化信息；它不是匿名化或通用数据防泄漏方案。层名中不得放密码、带凭证URL或原始Secret环境值，公开报告也需按对象权限分发。

### 9.5 导出是数据边界，不是授权边界

最小报告保留 `schemaVersion:1`、`drift`、`changes`；每行有 `key/kind/expected/observed/history/redacted`。导出器只序列化已脱敏报告，避免顺手把原Input或Effective加入debug字段。稳定键顺序利于审查和差异对比；稳定序列化不等于签名、不可篡改审计或完整采集证明。

来源CLI的约定是：成功导出且没有阻断检查时返回0；启用 `--check` 且检测到漂移返回2；输入或I/O失败返回1。它默认即使有漂移也可返回0，消费者必须同时理解参数和report语义。`go run` 是包装器，不应拿它的退出码证明构建后二进制精确返回2；本次未运行原CLI。更细的CI政策可只把allowlist内的键或特定类别视为阻断，并在报告中保存所用政策版本。检测失败与检测后发现漂移要分别处理。

参考CLI用 `os.ReadFile` 把文件读完后才检查1MiB，因此它限制“接受的文档大小”，没有形成读取时内存上限。面向不可信大输入时要在读取入口限流，读至上限加一字节即拒绝，并另限键数、层数与字符串长度。错误信息也不能把秘密原值回显。

`os.WriteFile(...,0600)` 对新文件按该模式创建，但不会收紧已有文件权限；多次系统调用中失败可能留下部分写入。不能把“指定0600”写成“所有落地文件始终只有本人可读且原子保存”。需要保护的实际路径、目录权限、符号链接策略、已有文件模式以及临时文件/原子替换/必要持久化，应分别设计核验。[Go os.WriteFile官方文档](https://pkg.go.dev/os#WriteFile)支持前述权限与部分写入边界，2026-10-23核对应条目，未做文件系统实验。

报告里没有采集时间、环境对象UID、配置revision、采集完整性、源文件摘要或签名；所以这是“基于提供输入得出的解释”，还不是生产现场的独立凭证。实际接入可外置受信信封保存对象、时间、期望revision、观测revision、来源commit和采集范围。秘密明文或低熵秘密的裸摘要不能为了追溯随意放进公开信封。

模型可以据此解释“为什么timeout预期5而实际30”，却不能仅因drift=true执行覆盖。修复提案应绑定具体对象、当前revision、动作及影响、回退/停止条件和批准；执行前再次检查revision与权限，观察独立结果。期间revision变化，旧提案应重新计算。这些属于本仓库已有工具授权与发布治理机制；本来源的比较器没有实现修订、审批、执行器或恢复验证。

### 9.6 四阶段如何自验，哪些仍未得到证明

第一阶段验输入边界；第二阶段验有效值和按键覆盖历史；第三阶段验四类差异、类型、存在性和脱敏；第四阶段验只导出报告、schema、稳定性与CI错误分类。建议先手算小输入，再用独立期望值核输出，避免以被测实现本身生成答案。

来源4份测试共有21个顶层Test函数（6/5/5/5）：覆盖正常输入、未知字段、重复层名、嵌套值、尾随JSON、大小限制；覆盖后层优先、历史、null、无关键和空层；覆盖changed、missing-null、unexpected秘密、equal秘密和排序/显式敏感键；覆盖schema、当前与历史秘密、消费者与稳定导出。没有直接核CLI真实退出码、旧文件权限、原子写入、读取前限额、大整数精度、重复JSON成员、源身份真实性或并发revision。单测数量与作者PASS日志不能替代这些验收。

练习与参考答案：

1. 默认层 `x=1`，环境层 `x=null`，观测无x，是什么类别？答案：missing；有效配置中x存在且为null，观测缺少，不是equal。
2. expected为 `true`、observed为 `1`，能不能按“都非零”判相等？答案：不能，布尔与数值类型不同，应changed。
3. 两个token显示均为 `[REDACTED]`，是否应改成equal？答案：不能，类别由脱敏前值决定。
4. 所有changes为equal是否证明环境完整一致？答案：仅对给定输入和采集合同成立，未采集范围、时间漂移、精度丢失与源真实性仍需独立检查。
5. 配置已从revision7变8，是否执行revision7报告生成的批准提案？答案：拒绝旧绑定，重新采集、比较与批准；此机制不是来源CLI自带能力。
6. 输出路径原来是0644，再用0600参数写入是否已经安全？答案：不能，WriteFile不改变既有权限；需按文件系统策略明确处理，实际核验。

## 11. 一个小功能怎样达到可维护状态

以“读取成绩文件并返回平均分”为例：输入契约先规定空文件如何处理、分数范围、坏行是报错还是跳过。解析函数接受文本并返回结果，文件 I/O 在外层处理；这样单元测试不必启动数据库或网络。

## 15. AI辅助值班：证据、假设与修复授权

2026-10-10 融合Phase17第23课。先修为本章logs/metrics/traces、版本化部署与[工具授权](../Agentic%20Design%20Patterns/06-专题扩展/07-工具授权与发布治理.md)。AI可把事故窗口内日志、指标、拓扑、近期变更与runbook汇成证据，减少人工搜索；核心工作是把“症状”“假设”“因果证据”“可执行动作”分开。

例如KV分配失败与显存98%同时出现，支持容量压力假设，却不直接证明谁先发生或哪个变更造成。日志Agent给event ID/可信时间/服务/版本，指标Agent给查询、窗口、基线与缺失，runbookAgent给适用版本、前提和过往处置效果；supervisor列相符及矛盾证据、其他假设与下一条低风险验证。三段自由文本的前30字符相同不表示相同原因，自报0.88也不是校准概率。两个模型读取同日志可能共享错误，赞同不能充当生产批准。

事故流程先指派明确负责人，记录影响和严重性；先缓解，再持续定位根因，交接时保时间线与未解决分支。只读调查也可能泄露数据、增加查询负载，需按租户和事故对象给工具最小权限。自动修复依预批准策略检查**具体对象、当前健康、前提、爆炸半径、预算、租约/版本、重复执行和撤权**。重启唯一副本或有未落盘状态的Pod同样危险；“restart”这个名称不自动安全。调整GPU限额可能改变质量/容量和重启行为，应单独审核，不能埋在“安全重启”里。

结构化runbook可以用普通Markdown维护，包含：适用服务/版本、症状与SLI、最近变更、证据查询与时间窗、假设和反例、允许动作及前提、对象范围、批准/执行责任、检查/终止/回退、效果回执、审计和最后核验日期。过往runbook成功不证明今天适用；RAG按版本/权限检索，保留废弃标记和修订原因。

预测预警另需评价precision、recall、假警报/日、提前量分布、漏报严重性和时间留出，区分事故前可获得信号与事后信息泄漏。预测可触发人工检查、预排空或有限扩容，各自须事先授权；一个可检索的风险看板也有价值，不必把预测直接接高风险自动执行。源“MIT预测89%且提前10–15分钟”没有具体论文/数据入口，未采纳；同样不采纳固定2026企业自动failover比例、事件少于10/月就不可用或固定12周交付。

### 第23课：原练习与六题参考

1. **日志与指标意见不同怎么处理？** 对齐事故/服务/时间窗，查缺失与单位，保多个假设和可区分验证；原supervisor按字符串前缀分组、按自报分数排序，既无语义合并也无反证，默认动作不能由排序结果自动接纳。
2. **定义三种可自动修复动作。** 单健康冗余副本的受限重启、兼容版本的受限回退、预算内受限扩容可以作为候选，但每种都要对象绑定、当前健康、效果核对、失效/终止与权限，不称普遍安全动作。
3. **结构化runbook怎样填？** 按本节字段对一个具体服务填真实query/探针、版本和阈值；未知处明确待核，不生成会直接执行的通用kubectl命令。只读验证和写动作分栏。
4. **提前12分钟预警怎样决策？** 基于可校准的概率、事故损失与处置损失决定是否page/人工查/有界预排空；假阳性排空也可能造成事故。没有真实预测质量时先只读或影子验证，保提前量。
5. **三人团队怎样选？** 比较重复调查的时间、可观测性、runbook质量、数据权限与维护成本；先验证一条有用的只读事故工作流，再决定加工具/协作/修复，不按人头和年份机械判断。

原六题：①supervisor+专业调查+人类判断是一种可用结构，非唯一标准。②restart/revert/scale只有符合当前授权和前提才可执行。③双模型赞同增加一个交叉信号，不能证明根因或放行。④运行手册和复盘帮助跨人员保留经验，但向量库不是必要前提。⑤原MIT数字未核验，不作为正确学习答案。⑥预测的价值与处置策略、假警报和可观察反馈相关，未授权时不可直接动作。

## 16. 可控故障注入：SLO预算与终止条件

Phase17第24课的长期价值是**通过有界试验检验恢复假设**，不是随机破坏生产。先在受控环境说明稳态、待检故障、受影响对象/用户、时长、恢复标准、观测数据、终止阈值和负责人；已存在事故或重要观测缺失时保留暂停。控制、目标、安全与观测是职责，反馈进入代码/runbook/依赖图改进，不必机械部署四套工具。

SLI是好事件/有效事件或指定延迟/质量条件，SLO是规定窗口的目标。对请求成功率SLO S，允许坏事件比例为1−S，burn rate $B=e/(1-S)$，e是**同口径窗口观察错误率**；不同window和流量构成不能混用。99.9%目标且e=.002，B=2，不是相对健康基线.0005得到4。固定流量近似下，窗口w消耗全账期T的预算比例约 $B w/T$；真实变流量需用实际有效请求数和剩余额度。

[Google SRE多窗口方法](https://sre.google/workbook/alerting-on-slos/)在其30天、99.9%例中给长短窗口并用的参数，1h/5min且B14.4对应约2%预算；这些是设计例不是所有服务阈值。低流量下一个失败就能给很高比例，需要考虑业务损失、合成流量和长窗口。安全策略同时限制额外错误预算、用户严重后果、范围、持续时长和监控心跳，任一明确风险超限都可停止；不能要求“burn大且范围大”同时满足才停止。

### 完整离线例：独立停止门禁与缺数据

程序只核一条教学策略，窗口和阈值已由题设固定：范围最多20%、最大burn=2、99.9%请求SLO。真实系统需另外估监控延迟、双窗口、在途/恢复和业务伤害；它未执行故障。这里把str所表示的十进制SLO与阈值用Fraction精确比较，避免数值容差比一个极小阈值还大。这只是政策算术精确，不表示观测没有误差。HOLD表示不得开始或扩大；若故障已在注入，应先停止注入并核恢复，不在无流量时继续。

```python
import math
from fractions import Fraction as Q

def decision(errors,total,affected,slo=.999,burn_cap=2,scope_cap=.2,observable=True):
    if type(errors) is not int or type(total) is not int or not 0<=errors<=total or total<=0:
        return 'HOLD: 样本无效或无流量'
    numbers=(affected,slo,burn_cap,scope_cap)
    if any(type(x) is bool or not isinstance(x,(int,float)) or not math.isfinite(x) for x in numbers):
        return 'HOLD: 非法参数'
    if not (0<=affected<=1 and 0<slo<1 and burn_cap>0 and 0<scope_cap<=1):
        return 'HOLD: 范围无效'
    if type(observable) is not bool or not observable:
        return 'ABORT: 失去观察'
    burn=Q(errors,total)/(1-Q(str(slo)))
    reasons=[]
    if burn>Q(str(burn_cap)): reasons.append('burn')
    if Q(str(affected))>Q(str(scope_cap)): reasons.append('scope')
    return 'ABORT: '+','.join(reasons) if reasons else 'CONTINUE: 当前窗口满足策略'

assert decision(40,10000,.01).startswith('ABORT: burn')
assert decision(1,10000,.3).startswith('ABORT: scope')
assert decision(20,10000,.2).startswith('CONTINUE')  # 恰好burn=2/范围=.2
assert decision(1,10**15,.01,burn_cap=1e-13).startswith('ABORT: burn')
assert decision(0,10000,.01,observable=False).startswith('ABORT')
for e,n,a in [(True,100,.1),(0,0,.1),(0,100,float('nan')),(0,100,True)]:
    assert decision(e,n,a).startswith('HOLD')
print('精确边界与极小cap反例通过；小范围高burn和范围越界独立停止，缺数据不通过')
```

提供商429可以是限流，不等供应商宕机；模拟时分别注入持续限流、慢响应、网络中断、部分stream中断和错误状态。故障转移仍检查备用质量、数据授权、协议与成本，不能把任何第二供应商当自动可用。KV压力/驱逐可能引起重算/排队，需区分普通请求长度上限、prefill/decode内存和恢复轨迹。“巨大UTF-8码点”不是准确技术描述，Unicode标量有范围，应测试已定义的超长、非法编码或实际解析器复杂度，不虚构万能tokenizer bomb。

故障有experiment ID、对象和可信时间线，结合独立服务指标看全局/范围内影响，不能仅因为请求有标签就断定全部根因属于试验。抑制的是可识别重复噪声，严重事件与试验外真实事故仍报警。终止故障也不自动撤销已发生的写入或清理注入，需要验证恢复和补偿。[AWS FIS](https://docs.aws.amazon.com/fis/latest/userguide/stop-conditions.html)明确可用CloudWatch alarm停止且停止后的实验不能resume；工具支持“none”不代表无门禁是本系统可接受配置。

## 17. 排障证据图：从受影响对象走到可审的修复提案

2026-10-11 融合 Phase19 第06课，补本章15节AI值班的对象关系与交互批准。目标是把事故窗口内的资料变成**有出处、可反证、范围明确的假设**，然后由独立执行责任方处理具体提案。五分钟和80%是原项目目标，未被课程demo证明，不是部署SLO或生产效果承诺。

### 17.1 对象身份、关系和时间窗

图节点用cluster/namespace/kind/UID/resourceVersion与采样时刻标识，避免两个namespace同名Pod覆盖；name可显示但不当全局identity。ownership通过ownerReferences保方向，例如Deployment→ReplicaSet→Pod；Pod→Node是调度关系。Service通过selector及实际endpoints关联后端，不把Service简单看成直接拥有Deployment。kube-state-metrics提供对象状态指标，可作输入，但完整拓扑还需API对象/关系与变化时间。

告警在Deployment时，受预算限制地BFS至ReplicaSet、Pod和Node，记录访问路径、边来源、深度/节点上限；关联受影响时间窗的metrics/logs/traces、近期rollout与基线。源Python neighbors只查一跳，拿Deployment无法走到Node，图上多跳动画不是实现；本章的方法需要显式队列、visited和数据新鲜度。旧节点重建产生新UID时，旧批准不能继续操作新对象。

例：checkout错误突然上升且十四分钟前rollout。先核错误率分子/分母、接口切片与时间对齐，再查新旧版本的Pod错误/健康、未更新服务对照、节点压力和依赖DNS。5xx请求rate单独不是错误率，需要同窗口总请求rate分母。假设“bad rollout”有部署和日志支持，仍要列反证：同版本旧Pod正常、错误发生更早或只在一个Node。排序可用近期性、特异性、路径与独立证据，但固定加权分不是因果概率，重复引用同日志不能伪造多项支持。

### 17.2 最小读取权限与修复执行器

Kubernetes RBAC核资源、API group、namespace及动词，不是kubectl命令词。`describe`是客户端聚合查询，真实只读通常按需给get/list/watch，Pod日志单独给`pods/log`；read-only的Secrets读取仍泄露敏感信息，不应随对象查询一起授予。Role在namespace生效，ClusterRole的最终范围依RoleBinding/ClusterRoleBinding决定。[官方RBAC资源和子资源例](https://kubernetes.io/docs/reference/access-authn-authz/rbac/#referring-to-resources)。

调查Agent只创建proposal，不持rollback/scale/delete执行凭据。proposal记录incident ID、cluster/namespace/UID、当前revision、动作和完整参数、证据、预期效果/范围、恢复/停止条件与期限。独立执行器核当前授权、健康和对象版本，接受具体绑定批准后原子claim；执行结果的未知/失败/恢复单独回报，不把HTTP200或“approved”当实际恢复。具体签名、撤权与效果对账继续复用[工具授权](../Agentic%20Design%20Patterns/06-专题扩展/07-工具授权与发布治理.md)。

### 17.3 Slack按钮为何还不是有效批准

Slack用raw body、timestamp和v0 HMAC basestring验来源，并核五分钟时间差及安全比较；验签前不能重编码form或JSON。[Slack官方签验步骤](https://docs.slack.dev/authentication/verifying-requests-from-slack/)。时间窗不阻止窗内重复请求；执行端还要核workspace/app、点击者身份及当前oncall角色、具体proposal版本/摘要、允许action、deadline与一次消费。正文表明“Alice点击批准”不等源Python传任意approver字符串就获得权限。

正常链：创建P42/UID7/rev42回退提案→展示证据和影响→有效人类批准该摘要→执行前核仍rev42→claim并执行→记录真实回执→独立SLI确认恢复。若期间部署变rev43、撤权或已执行，拒绝旧批准；未知effect进入对账。unknown incident或unknown action不能当ignore后偷偷执行。response_url是受信响应通道，保存/发送需受允许origin和资料策略限制，不在公开trace泄露。

源TS只按OOM/CrashLoop关键词返回固定说明和outbound意图列表，任意inc42都可mock批准；没有真实Slack消息、图谱查询或MCP修复。OOMKilled涉及limit/实际内存/节点压力等原因，单据此推断request太低不够；readiness失败通常影响流量资格，不引起重启，CrashLoop要区分liveness/startup及进程退出。故障测试套件应覆盖这些反例及错namespace、旧UID、无证据、批准重放与效果未知；排障top-k、查询负担、尾部耗时与最终SLO恢复分别测。审计的considered/blocked/approved/claimed/outcome留在可信边界，内存list不是不可篡改日志。

## 18. 签名Webhook：先可靠接收，再明确处理

外部系统用HTTP回调通知“报告已上传”，接收者可能先保存再交给Agent处理。发送端没收到响应会重试，服务也可能在写盘后、回响应前崩溃，因此至少分清三种身份：

- **delivery ID**：一次传输投递的身份，重试通常沿用它；
- **business event ID**：正文中实际业务事件的身份，不同投递也可能指向同一事件；
- **processing run ID**：接收方一次明确处理/重放的身份，同一投递可以经批准产生新的处理轮次。

验签回答“这些字节是否符合当前密钥与协议”，收件箱回答“是否可靠接收过这次投递”，处理回执回答“本地这次处理生成过什么”。它们都不能独立证明外部业务效果恰好发生一次。第17.3节Slack的具体协议与本节自有教学格式分别理解，不混用签名串。

### 18.1 保留原始字节，再解释业务JSON

从请求中读取方法、投递ID、时间戳、签名和**有上限的原始正文**。例如 `{"a":1}\n` 与 `{ "a" : 1 }\n` 表达相同对象，但签名输入字节不同；验签前不能解析后重新序列化，也不能删除文件末尾换行。

可用的读取合同：POST；ID只允许明确的ASCII字符与长度；时间戳为规范int64十进制秒，拒绝前导零、正号、空白等非规范形式；正文1～65536字节。读65537字节可发现超限，不能先无限读完再检查。头部大小、慢读、连接数、解压后的大小和总截止时间仍需HTTP栈/应用限制。

读入合法不等于验签成功；验签成功也不等于业务JSON有效。正文可能是任意已认证字节，后续处理器再要求对象中有eventId与data，非法业务结构记处理失败，不伪造“没有收到”。不要在错误正文回显密钥、原始负载或内部文件路径。

### 18.2 HMAC还需要无歧义的待签名编码

HMAC-SHA256使用双方共享的秘密对**一段字节串**作认证；不是加密，也不是只有发送者才能生成的公开签名。掌握同一密钥的接收者也能生成MAC。密钥应有足够随机性、按来源/环境隔离、可轮换；“长度至少16字节”只是本课检查，并不证明它有足够熵。MAC用安全比较函数，如Go的 `hmac.Equal`，不能以普通字符串比较替代。[Go官方HMAC说明](https://pkg.go.dev/crypto/hmac)。

来源v1把 `十进制时间戳 + "." + deliveryID + "." + rawBody` 作为消息。但ID允许句点，正文又允许任意字节，编码不是一一对应：

```text
时间相同，ID=a，正文=1.23    → 1770000000.a.1.23
时间相同，ID=a.1，正文=23   → 1770000000.a.1.23
```

两种ID都合规，两个正文甚至都是有效JSON数值，却形成相同MAC输入。这是**字段编码歧义**，不需要破解HMAC；来源只修改ID或只修改正文的测试不能发现“同时改变字段边界”的反例。接收层接受原始字节，即使后续业务处理器要求对象，这个认证边界仍然有缺口。

修正方法是采用供应商明确规定且无歧义的格式；自行设计时可固定字段长度，或对各字段加长度前缀，并包含版本/用途域分隔。若改变格式，升级版本并明确迁移；不能静默修改一个既有供应商的协议。

下面自有例使用4字节大端长度前缀和用途前缀，测试歧义、原字节和时间窗；**它不是来源v1，也不是任何服务的标准接口**。不提供密钥管理、HTTP、轮换或持久接收实现。

```python
"""自有有限CPU例：原教学拼接的歧义与长度前缀修正；无网络/文件收件箱。"""
import hashlib
import hmac
import re

VALID_ID = re.compile(r"[A-Za-z0-9][A-Za-z0-9._-]{0,127}", re.ASCII)

def fields(stamp, delivery_id, body):
    if type(stamp) is not int or not -(2**63) <= stamp < 2**63:
        raise ValueError("int64秒")
    if type(delivery_id) is not str or not VALID_ID.fullmatch(delivery_id):
        raise ValueError("投递ID")
    if type(body) is not bytes or not 1 <= len(body) <= 65536:
        raise ValueError("原始正文")
    return str(stamp).encode("ascii"), delivery_id.encode("ascii"), body

def ambiguous(stamp, delivery_id, body):
    return b".".join(fields(stamp, delivery_id, body))

def framed(stamp, delivery_id, body):
    # 这是另一个自有教学格式，不冒充v1或任何供应商协议。
    return b"study-webhook-v2\0" + b"".join(
        len(part).to_bytes(4, "big") + part
        for part in fields(stamp, delivery_id, body)
    )

def tag(key, message):
    if type(key) is not bytes or len(key) < 16:
        raise ValueError("教学最小密钥长度")
    return hmac.digest(key, message, "sha256")

def verify(key, stamp, delivery_id, body, signature, now, skew=300):
    fields(stamp, delivery_id, body)
    if type(now) is not int or not -(2**63) <= now < 2**63:
        raise ValueError("当前int64秒")
    if type(skew) is not int or not 0 <= skew <= 3600:
        raise ValueError("时间窗")
    if type(signature) is not bytes or len(signature) != 32:
        return False
    if not now-skew <= stamp <= now+skew:
        return False
    return hmac.compare_digest(tag(key, framed(stamp, delivery_id, body)), signature)

key = b"owned-test-key-not-for-production"
now = 1770000000
left = (now, "a", b"1.23")
right = (now, "a.1", b"23")
assert left != right and ambiguous(*left) == ambiguous(*right)
assert tag(key, ambiguous(*left)) == tag(key, ambiguous(*right))
assert framed(*left) != framed(*right)
sig = tag(key, framed(*left))
assert verify(key, *left, sig, now)
assert not verify(key, *right, sig, now)
assert not verify(key, now, "a", b"1.23\n", sig, now)
for offset, accepted in [(-301, False), (-300, True), (300, True), (301, False)]:
    stamp = now + offset
    signed = tag(key, framed(stamp, "a", b"1.23"))
    assert verify(key, stamp, "a", b"1.23", signed, now) == accepted
print("点分隔不同字段同签名反例成立；长度前缀区分ID/正文，原字节和时间窗边界通过")
```

窗口例如当前秒为T、容差300秒，T−300与T+300可接收，T±301拒绝；这是约定的闭区间。时间窗缩短可重放的时间，却不阻止窗内重复；仍需delivery ID去重。时间单位、时钟同步、极值溢出与允许未来偏差都要明确。失败重试超过窗口时应按供应商重签/重投规则处理，不能因为它“以前收到过”就绕过认证。

### 18.3 在确认接收之前持久化

接收链可写成：限量读原字节 → 验证头部/签名/时间窗 → 以投递身份原子接收 → 确认接收 → 独立处理。

来源本地文件算法的作用是解释持久化与并发：

1. 在可信收件目录内创建私有临时文件，完整写入schemaVersion、delivery ID、原始body、摘要和首次acceptedAt。
2. 同步文件内容并检查写入/关闭错误。
3. 用**不能覆盖已有目标**的原子发布操作把临时文件发布为正式记录。来源用同目录硬链接；普通覆盖rename不具有同样去重语义。
4. 同步目录项，成功后才能宣称可靠接收；临时路径可清理，崩溃遗留的`.pending`不算正式记录。
5. 若目标已存在，重新读并校验既有记录；同ID同字节返回原acceptedAt，不覆盖；同ID异字节明确冲突。

为什么不能先 `exists()` 再 `write()`：两个并发请求都可能看到不存在，随后互相覆盖。必须让“第一次发布”由文件系统原子原语或数据库唯一约束裁决，再核对胜出记录。来源12个并发同ID测试只覆盖一个受控场景，不是所有文件系统崩溃语义的证明。Go的[Link](https://pkg.go.dev/os#Link)、[File.Sync](https://pkg.go.dev/os#File.Sync)提供基础操作；具体耐久性依操作系统、文件系统和存储兑现，不能推广到任意网络盘。

若链接已经建立但随后的目录同步失败，发布可能已经发生；请求返回500不证明“未接收”。后续认证重试仍按同ID回读对账，不能覆盖或换ID来掩盖未知结果。

文件名可使用ID的SHA-256来减少路径注入，但不能因此信任整个存储目录。已有目录权限不会因 `MkdirAll(...,0700)` 自动收紧；可写祖先、符号链接与替换风险另核。新文件0600也不等于已加密。正文在JSON中被base64编码只是编码，敏感原文仍在，不能当脱敏上下文交给模型。

### 18.4 首次、重复、冲突与业务完成分别回报

| 来的请求 | 接收层处理 | 不能推导的结论 |
|---|---|---|
| 新ID、有效认证、正文A | 本地可靠接收后示例返回202 | 业务动作尚未执行 |
| 同ID、有效认证、同正文A | 返回已有记录，示例200 | 不能证明处理器已成功或无需重试 |
| 同ID、正文B、沿用A签名 | 认证失败，示例401 | 不能进入存储比较后接受 |
| 同ID、正文B、有B的有效签名 | 身份冲突，示例409 | 不能悄悄覆盖A |
| 不同ID、相同business event | 可是两次不同投递 | 业务是否应去重由下游政策决定 |

**摘要不是存储真实性证明。** LoadEntry核schema、ID和body摘要能发现部分损坏；若攻击者可同时修改正文和摘要，它并不能验证原始签名。来源接收记录未保存完整验签信封，重放依赖受保护的本地存储与接收链。需要独立重验时，按政策保存必要的签名版本、原始时间戳、key ID等证据，并考虑密钥轮换与留存，不能保秘密密钥本身在记录内。

### 18.5 显式重放与处理回执

处理器只加载已接收记录，再解析业务对象。回执以 `(deliveryID, runID)` 唯一标识，绑定body摘要、businessEventID、处理时间和输出payload。同一run重试必须回原回执；换run是新的明确处理，不是伪造另一条传输。

例如delivery-1携business-42，run review-1生成一份回执；重复review-1不新建，review-2可按明确授权重新处理。delivery-2也携business-42时，传输身份不同，仍需业务层决定是否已完成同一业务动作。

来源processing只生成本地JSON，不调用外部系统。若改成发邮件/改工单，可能出现外部动作完成而回执未落盘；重试又做一次。解决需外部幂等键、事务性outbox/队列与效果回读，具体恢复沿[异常处理和恢复](../Agentic%20Design%20Patterns/01-核心章节/12-异常处理和恢复.md)。不能把本地文件原子创建推广成外部exactly-once。

重复回执也须核schema、投递/run身份、源body摘要、业务ID和payload；仅比较文件存在不够。来源使用JSON压缩后字节比较payload，只去无意义空白，不实现对象键序无关的语义等价。`data:null`与缺data、空eventId、重复JSON键及业务字段类型要有单独合同，来源最小解析不替代完整业务schema。

## 19. 数据库迁移：先在副本验证，再形成可审查的发布证据

数据库迁移会改变持久状态。程序版本退回去了，已经删除的行、改变的列、递增序号和不兼容的数据未必回来。一次有价值的演练应回答四个不同问题：迁移在这个快照上能否执行；迁移后的业务不变量是否成立；明确给出的反向脚本能否恢复所捕获的状态；这些证据是否足够交给独立的发布决策。

这里的具体教学实现是Python标准库sqlite3与本地SQLite文件，不是PostgreSQL/MySQL通用迁移平台，也没有生产部署执行器。流程是：以只读连接打开源库→使用SQLite backup复制到内存→在副本执行迁移→记录迁移后状态→在同一副本执行声明的回滚→输出JSON收据和HTML。以下SQL只用于说明和静态推导，本次未执行来源SQL或程序。

### 19.1 阶段一：快照要同时描述结构、内容与序列

仅记录表名和COUNT(*)很容易漏掉损坏：两行仍是两行，但其中一个姓名或金额已经被替换。至少把结构快照与数据快照分开：

| 维度 | 教学实现捕获什么 | 能回答什么 | 仍不能回答什么 |
|---|---|---|---|
| schema | sqlite_master中的type、name、tbl_name、CREATE SQL，按类型/名称排序 | 表、索引、视图、触发器等定义文本是否变化 | 对象语义等价、未来行为等价、所有数据库配置 |
| tables | 每张被纳入表的行数与排序后整行内容SHA-256 | 行数变化及许多等行数内容变化 | 未被读取的隐藏身份、未纳入表或数据库外副作用 |
| sequences | sqlite_sequence存在时，按表名记录name、seq | AUTOINCREMENT后续分配基线是否恢复 | 所有物理页、连接级状态或业务ID策略 |

“只读源连接”与“迁移只作用于内存副本”是两个边界。前者用SQLite URI的`mode=ro`，后者不能只靠另起一个文件名，而要确保实际执行SQL的连接确实指向副本。SQLite的backup API用于取得数据库快照，比简单复制一个可能处于WAL模式的主文件更适合表达数据库状态；备份操作本身和后续完整性检查仍需单独验收。[SQLite backup说明](https://www.sqlite.org/backup.html)

行哈希的教学策略是：把每个SELECT *结果行转成紧凑JSON字符串；BLOB转成带blob标签的十六进制对象；字符串保留Unicode；把所有行字符串排序，以换行连接后取SHA-256。排序让结果不依赖扫描顺序，保留重复行则让它描述多重集合，而不是把相同行去重。

例子中的源表与两行是：

```sql
CREATE TABLE attendees(id INTEGER PRIMARY KEY, name TEXT NOT NULL);
-- 用于推导的行：(1, 'Ada')、(2, 'Mira')。
```

对应的有序行投影为：

```text
[1,"Ada"]
[2,"Mira"]
```

两行投影的SHA-256是`50c216fc29487e785b0d284137ab0d8882d2535e00f7b288f2a1091798e40191`。交换输入行顺序不改变这个值；把Mira替换为Other仍有两行，但哈希不同；多加一份Mira行也会改变结果。这个核对只运行了自写的列表/JSON/hash计算，没有连接SQLite。

实现完整性还要注意两个真实缺口：

- 源代码用`name NOT LIKE 'sqlite_%'`过滤内部对象，但LIKE中的下划线匹配任意单字符。因此合法名称sqliteXdemo也会被排除，而SQLite保留的是字面sqlite_前缀。被漏掉的表可能连丢失都不出现在快照比较里。应采用明确的字面前缀政策并核对大小写，不能把上述LIKE模式当字面下划线。[SQLite LIKE](https://www.sqlite.org/lang_expr.html#like)、[表名保留前缀](https://www.sqlite.org/lang_createtable.html)
- `SELECT *`读取声明的列，不代表纳入普通rowid表的隐藏rowid。对`CREATE TABLE t(x)`，只改变隐藏rowid而让x不变，教学行投影可能完全相同；若应用依赖rowid，这就是有意义的状态变化。INTEGER PRIMARY KEY作为rowid别名的表与WITHOUT ROWID表又有不同情况，应先声明支持范围，再决定是否显式捕获可访问的rowid。[SQLite rowid](https://www.sqlite.org/lang_createtable.html#rowid)

快照还没有覆盖temp schema、连接级PRAGMA、所有数据库头部属性与物理布局。schema按SQL文本比较很严格：语义等价而文本不同也可能被报变化。因此更准确的结论是“捕获投影相等/不等”，而不是“完整数据库在任何意义上等价/不等价”。

### 19.2 阶段二：副本执行也需要权限、事务与资源边界

来源对副本连接安装SQLite authorizer，拒绝ATTACH、DETACH、全部PRAGMA、虚拟表创建/删除，以及load_extension、readfile、writefile等指定函数。它不是靠扫描SQL里有没有危险关键词，而是利用SQLite准备/执行过程中的授权动作来裁决。拒绝ATTACH尤其重要，否则脚本可能把另一个文件挂进来并写入。

这仍只是SQL引擎内的政策，不是操作系统沙箱，也不是所有资源都有限制。来源没有给内存副本、行字符串缓存、排序、备份等待及所有输入大小提供总预算。快照把整表内容存入列表再排序，大表可能用掉大量内存；“数据库复制到内存”不能自动理解为轻量。

对每次SQL执行，来源设置一个距当前单调时钟2秒的deadline，并每约1000条SQLite虚拟机指令检查一次。它是协作式中断，不是整个工具的严格两秒墙钟上限；备份、数据哈希以及未触发回调的等待/工作不在这个保证里。迁移和回滚各有一次独立执行预算。

事务控制必须说清楚。该实现调用executescript，但没有自动把每份脚本包进BEGIN/COMMIT。Python3.10文档明确：它会先提交待定事务，其他事务控制由脚本自己提供。因此多语句脚本第二句失败时，不能推断第一句已经自动撤销。[Python3.10 executescript](https://docs.python.org/3.10/library/sqlite3.html#sqlite3.Cursor.executescript)

例如仅作为静态反例：

```sql
ALTER TABLE attendees ADD COLUMN city TEXT;
-- 假设接下来这一句发生SQL错误：
UPDATE not_a_table SET x=1;
```

返回应同时保留`applied=false`、error和实际after，而不是遇错就伪造after=before。即便脚本显式BEGIN后出错，after在当前连接上看到的也可能是尚未提交的局部状态；来源没有导出in_transaction状态，不能从一份after投影推出哪些状态曾经持久提交。

这里的applied表示“脚本调用没有返回SQL错误”。由于所有操作在一次性内存副本里，它不表示生产库已迁移、数据已持久落盘或部署已批准。空SQL/非字符串在来源里会抛ValueError；其他SQLite错误大多转换成报告中的error。外层还应有严格JSON/路径/规则类型校验，不能把这两种失败路径混成统一收据。

连接级配置也是演练环境的一部分。比如SQLite外键执行需要为连接明确启用；备份数据文件不等于复制另一个连接的设置。来源新建副本连接但没有建立外键配置合同，又禁止脚本PRAGMA，所以不能仅因CREATE TABLE写着FOREIGN KEY就声称本次演练实际检查了引用完整性。应由可信执行器在装上用户脚本政策之前建立并记录必要设置，必要时执行专门的外键检查；不能从默认配置猜结果。[SQLite外键启用](https://www.sqlite.org/foreignkeys.html)

### 19.3 阶段三：回滚脚本跑完与状态恢复是两件事

回滚验证应在同一个副本上完成“before→forward→after→rollback→restored”。另起一个全新原副本去跑rollback，会测错对象，尤其容易掩盖前向迁移已经删除的数据。来源不自动编造反向SQL，只接受明确给出的rollback；前向失败时不执行它，rollback_error写明forward migration failed。

来源将可逆性定义为三个条件同时成立：

```text
reversible = 前向SQL成功
          且回滚SQL成功
          且before快照 == restored快照
```

最后的相等包括结构列表、各表的行数/内容哈希、AUTOINCREMENT序列，而不是只看最后一条SQL是否返回0。

原样例前向脚本与声明回滚是：

```sql
-- forward
ALTER TABLE attendees ADD COLUMN city TEXT;
DELETE FROM attendees WHERE id=2;

-- rollback，声明者只撤销新增列
ALTER TABLE attendees DROP COLUMN city;
```

在支持上述DDL语法的SQLite版本上，静态推导为：

| 时点 | 可见业务行 | 行数 | 说明 |
|---|---|---:|---|
| before | (1,Ada)、(2,Mira) | 2 | 原两名参与者 |
| after | (1,Ada,NULL) | 1 | 新city列存在，Mira已删 |
| restored | (1,Ada) | 1 | 列撤回了，Mira没有回来 |

三个行投影哈希分别为原值`50c216…`、迁移后`785b2c…`、回滚后`a239fa…`。所以SQL可能两次都无语法/执行错误，却仍有`reversible=false`。作者截图也显示forward_applied=True、rollback_reversible=False、release_ready=False、两个error均None；这是作者捕获结果，不是本次实际执行记录。

即便把行数补回两行也不够：删除Mira后插入Other不叫恢复。AUTOINCREMENT序列也类似：行与定义相同，而seq从2变为3，后续自动ID行为可能不同，教学精确快照比较仍应失败。

反向脚本不能可靠重建被销毁而没有留证的数据。实际需要在设计阶段选择保留可撤销信息、备份恢复或向前修复方案，并验证新旧应用版本的读写兼容。不能在回滚失败之后让AI凭常识“补一条INSERT”来声称数据恢复；应从受控备份或已知迁移前状态恢复，并把人工决策独立记录。

这份判断只针对这一个输入快照、这个SQLite实现与指定脚本。它没有覆盖生产并发写入、长锁、磁盘故障、复制、跨库事务、应用兼容、恢复时间目标，不能把一次reversible=true推广为“生产迁移安全”。反过来，由于快照是有边界的投影，隐藏rowid、遗漏表或连接配置等差异还可能被漏检。

### 19.4 阶段四：收据门槛、业务不变量与人工批准分别记录

该教学receipt检查的是**after**的不变量，再结合before/restored的可逆性形成release_ready。不同字段含义如下：

| 不变量字段 | 检查 | 典型边界 |
|---|---|---|
| table | after里必须存在该表 | 只写table的规则只检查存在，不检查内容 |
| min_rows / max_rows | after行数在非负整数界内 | 数量界不是数据质量证明 |
| same_rows=true | before和after行数相等 | 相同数量但值替换仍可通过 |
| preserve_data=true | before和after整行哈希相同 | 适合列投影不变的表；加一个NULL列也会改变整行哈希 |

样例规则为`{table:attendees, same_rows:true, min_rows:2}`。after只有一行，所以同时出现below min_rows与row count changed。最终有两个独立失败：after业务约束失败，且rollback没恢复丢失行。不能把它们只压成一句“回滚失败”。

还有一个很重要的反例：前向删除一行，回滚准确插回原值，那么reversible可能为真；但same_rows检查的是after，仍应失败，所以release_ready为假。这避免把“事后能恢复”误当“迁移后可以接受”。

来源计算：

```text
release_ready = reversible 且 每条invariant_results都通过
```

invariants=[]时，all([])为真，因此只要可逆就可能得到release_ready=true。形式上符合这份合同，但没有证明任何未声明的业务要求。发布门禁应明确必需规则集合，不能靠空列表把要求绕过去。min/max若彼此矛盾，来源会让结果失败而非预先报规则矛盾；正式入口可更早拒绝。布尔开关必须是真布尔值，数值界不接受bool冒充整数，未知规则字段应拒绝。

输出rehearsal.json应保留before、after、restored、前向/回滚错误、schema_diff、各条不变量及最终标志；schema-diff.json是其结构差异视图，HTML供人审阅。**schema_diff为空不代表数据没变**：DELETE和UPDATE可以只改行内容。结构差异按对象type:name和CREATE SQL文本比较，不是语义迁移解释器，也没有逐行差异定位。

实际发布消费合同还缺少源快照身份、迁移/回滚脚本摘要、运行器与SQLite版本、策略配置、时间和批准主体等绑定信息。教学receipt的schema_version=1和布尔值不具备防伪能力，不能接收任意人手写的release_ready=true就发布。部署批准必须由独立且已有授权的门禁读取可信收据、核对候选脚本与目标快照，再记录具体决策；这份工具本身没有批准按钮、签名批准或生产应用动作。

CLI在没有database字段时会在输出目录创建作者样例SQLite文件，而不是读取真实业务库；有database时按输入JSON所在目录解析数据库路径。它会避免数据库路径与三个输出文件的字面路径相同，但没有完整防护输出叶子符号链接/硬链接指向源库或输入JSON。write_text会沿现有文件目标写入，因此不能把这项字面检查推广成“所有文件路径下源输入绝不可能被覆盖”。工程上应分离只读输入与私有新输出目录、验证实际文件身份、拒绝不受支持的别名，并先写临时产物再完整发布。

### 19.5 四阶段实践、自检与证据边界

把一轮演练练习拆成四个可核检查点：

1. 先预测快照：有哪几个对象、多少行、哪些字段和序列参与身份；再解释一个同数量内容变化反例。
2. 在授权的隔离测试环境设计前向脚本成功、第二句失败、被authorizer拒绝三类用例；为失败后的after作预测，而不是只看exit code。
3. 分别设计完全恢复、数量恢复但值不对、SQL回滚报错、序列不同四种结果，检查reversible的三条件。
4. 固定业务不变量与脚本/数据版本，再阅读JSON收据和HTML；区分可逆、业务合格与独立发布批准。

参考问答：

- 只新增一列后，preserve_data为何也可能失败？**整行投影加了列。** 需指定被保护业务列的比较政策，而不是直接删除保护要求。
- schema_diff为空，是否可以跳过数据核对？**不能。** UPDATE可在结构不变时破坏内容。
- 前向DELETE、准确回滚INSERT，release_ready一定为真吗？**不一定。** 若after违反same_rows或其他不变量仍失败。
- WHERE name NOT LIKE 'sqlite_%'能否准确识别内部前缀？**不能。** '_'是通配，合法sqliteXdemo也会被排除。
- 两秒deadline是否保证内存复制、排序和整个进程两秒结束？**不能。** SQL协作中断与整次资源预算不同。
- 回滚投影相同能否直接批准生产迁移？**不能。** 还需快照/脚本/运行身份绑定、完整业务要求、环境兼容、恢复目标与有权决策。

四份阶段测试共20个方法，仅静态阅读：覆盖简单快照、等数量异值、ALTER、源文件单例字节不变、ATTACH/PRAGMA拒绝、错误SQL、可逆/丢数据/错误回滚以及不变量组合；未验证所有路径别名、隐藏rowid、LIKE过滤遗漏、WAL并发、外键、超时和巨大数据边界。作者2026-10-09日志的四阶段通过与本次阅读分记，不代表本次运行或用户已完成练习。

四幅交互图也共用同一个行数算式：删除数截到原行数，再计算迁移后行数与“恢复数”相加。默认2→1→1失败；把恢复数调成1可以让回滚计数恢复为2，但迁移后same_rows仍失败。图自己也提示计数通过后还要核schema/content；它没有打开SQLite、执行SQL、计算内容哈希或接收真实批准。不能用绿色或动画替代收据。
