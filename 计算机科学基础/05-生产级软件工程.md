# 05｜生产级软件工程

## 1. 目标

生产软件不是“能跑”，而是：

- 可读；
- 可测试；
- 可部署；
- 可观测；
- 可回滚；
- 可维护。

## 2. Linux 与命令行

长期需要掌握的是抽象：

- process / signal；
- stdin/stdout/stderr；
- pipe；
- file permission；
- environment variable；
- shell composition；
- process inspection；
- network diagnostics。

不固化某个发行版或工具的短期 UI。

## 3. Git

核心对象：

```text
working tree
→ index
→ commit
→ branch/ref
→ remote
```

重要实践：

- 小而完整的 commit；
- 清晰 commit message；
- branch 生命周期短；
- review 前先自检；
- 能解释 merge/rebase 的差别；
- 不把生成物、密钥和大文件误提交。

## 4. Codebase Design

高质量代码库要控制：

- module boundaries；
- dependency direction；
- public interface；
- configuration；
- error handling；
- side effects。

原则：

> 让局部修改尽量保持局部影响。

避免“方便起见”的跨层引用逐步把系统耦合成一团。

## 5. Testing

测试金字塔可理解为：

- unit：便宜、定位快；
- integration：验证组件边界；
- end-to-end：验证关键用户路径。

此外还应有：

- property / invariant test；
- regression test；
- contract test；
- performance test。

测试不是追求覆盖率数字，而是保护高风险行为。

## 6. CI/CD

CI 负责持续验证：

```text
lint
→ type/static checks
→ tests
→ build
→ security scan
```

CD 再负责：

- artifact；
- staging；
- canary / blue-green；
- rollout；
- rollback。

## 7. Container

容器解决的是可重复运行环境和隔离，不等于完整运维系统。

生产中还要关心：

- image provenance；
- resource limit；
- secret；
- network；
- persistent storage；
- health check。

完整容器知识已独立整理到 [容器化与 Docker](./07-容器化与Docker/README.md)，这里不再重复维护。

## 8. Observability

三类信号：

- logs：发生了什么；
- metrics：系统总体状态；
- traces：一次请求跨组件经历什么。

关键原则是让异常可以被定位，而不是只知道“出错了”。

## 9. Configuration 与 Secret

配置应与代码分离；秘密信息不应硬编码或提交 Git。

需要明确：

- environment；
- validation；
- default；
- ownership；
- rotation。

## 10. Coding Agent 的正确位置

AI 编码 Agent 可以加速：

- 搜索代码；
- 生成候选补丁；
- 测试；
- 重构；
- 文档；

但不能替代：

- 需求边界；
- architecture ownership；
- correctness verification；
- security review；
- production accountability。

使用 Agent 时，应给出明确上下文、验收标准和测试闭环。

来源：Compendium Chapter 15；去除具体工具版本，只保留长期工程方法。

## 11. 一个小功能怎样达到可维护状态

以“读取成绩文件并返回平均分”为例：输入契约先规定空文件如何处理、分数范围、坏行是报错还是跳过。解析函数接受文本并返回结果，文件 I/O 在外层处理；这样单元测试不必启动数据库或网络。

必要案例包括正常两行、空输入、非法字符、越界分数。集成测试再检查真实文件权限/编码失败。部署记录应能连接源码 commit、构建产物、配置版本与观察到的错误率。

自测：回滚二进制是否自动恢复已修改数据库？答：不会。存在数据迁移时，必须设计新旧版本兼容、备份恢复或可逆迁移；“有上一个镜像”不等于所有状态都可回滚。

学习记录用中文写清楚需求、测试证据和残留限制。一次修复应先让失败案例稳定复现，再确认修复后通过，避免把“程序能启动”当全部验收。

## 12. 软件工程定律：把经验变成决策检查表

生产级工程除了工具链，还需要一组能帮助识别风险和权衡的心智模型。用户提供的 *Laws of Software Engineering* 卡牌已完整整理为独立章节：

- [软件工程定律与工程决策](./05-1-软件工程定律与工程决策.md)

该章节覆盖 56 条定律/原则/启发式，分为：

```text
Architecture
→ Teams
→ Planning
→ Quality
→ Scale
→ Design
→ Decisions
```

学习时不要把“Law”都当成同一种强度的科学定律。可以分成四类理解：

1. **硬约束/形式化关系**：例如 CAP、Amdahl；
2. **工程设计原则**：例如 YAGNI、DRY、KISS、SOLID、Testing Pyramid；
3. **组织与项目启发式**：例如 Conway、Brooks、Bus Factor、Peter；
4. **认知与决策工具**：例如 Goodhart、Sunk Cost、Confirmation Bias、First Principles、Inversion。

最有用的学习方式不是背定义，而是在真实变更前把它们变成问题：

- API 的未文档行为是否已经有人依赖？→ Hyrum
- 这次重写是否在重复 Second-System Effect？
- 增加人手会提高并行度，还是只增加沟通？→ Brooks
- 指标是否已经从“测量”变成“目标”？→ Goodhart
- 这段抽象是真的减少知识重复，还是只是为了 DRY 而 DRY？
- 当前判断有没有主动寻找反证？→ Confirmation Bias
- 如果项目三个月后失败，最可能怎么失败？→ Inversion

这一页承担软件工程“怎么做”的主线；05-1 章节补充“为什么这些取舍经常出错，以及评审时如何检查”。

## 15. AI辅助值班：证据、假设与修复授权

2026-10-10 融合Phase17第23课。先修为本章logs/metrics/traces、版本化部署与[工具授权](../Agentic%20Design%20Patterns/06-专题扩展/07-工具授权与发布治理.md)。AI可把事故窗口内日志、指标、拓扑、近期变更与runbook汇成证据，减少人工搜索；核心工作是把“症状”“假设”“因果证据”“可执行动作”分开。

例如KV分配失败与显存98%同时出现，支持容量压力假设，却不直接证明谁先发生或哪个变更造成。日志Agent给event ID/可信时间/服务/版本，指标Agent给查询、窗口、基线与缺失，runbookAgent给适用版本、前提和过往处置效果；supervisor列相符及矛盾证据、其他假设与下一条低风险验证。三段自由文本的前30字符相同不表示相同原因，自报0.88也不是校准概率。两个模型读取同日志可能共享错误，赞同不能充当生产批准。

事故流程先指派明确负责人，记录影响和严重性；先缓解，再持续定位根因，交接时保时间线与未解决分支。只读调查也可能泄露数据、增加查询负载，需按租户和事故对象给工具最小权限。自动修复依预批准策略检查**具体对象、当前健康、前提、爆炸半径、预算、租约/版本、重复执行和撤权**。重启唯一副本或有未落盘状态的Pod同样危险；“restart”这个名称不自动安全。调整GPU限额可能改变质量/容量和重启行为，应单独审核，不能埋在“安全重启”里。

结构化runbook可以用普通Markdown维护，包含：适用服务/版本、症状与SLI、最近变更、证据查询与时间窗、假设和反例、允许动作及前提、对象范围、批准/执行责任、检查/终止/回退、效果回执、审计和最后核验日期。过往runbook成功不证明今天适用；RAG按版本/权限检索，保留废弃标记和修订原因。

预测预警另需评价precision、recall、假警报/日、提前量分布、漏报严重性和时间留出，区分事故前可获得信号与事后信息泄漏。预测可触发人工检查、预排空或有限扩容，各自须事先授权；一个可检索的风险看板也有价值，不必把预测直接接高风险自动执行。源“MIT预测89%且提前10–15分钟”没有具体论文/数据入口，未采纳；同样不采纳固定2026企业自动failover比例、事件少于10/月就不可用或固定12周交付。

### 第23课：原练习与六题参考

1. **日志与指标意见不同怎么处理？** 对齐事故/服务/时间窗，查缺失与单位，保多个假设和可区分验证；原supervisor按字符串前缀分组、按自报分数排序，既无语义合并也无反证，默认动作不能由排序结果自动接纳。
2. **定义三种可自动修复动作。** 单健康冗余副本的受限重启、兼容版本的受限回退、预算内受限扩容可以作为候选，但每种都要对象绑定、当前健康、效果核对、失效/终止与权限，不称普遍安全动作。
3. **结构化runbook怎样填？** 按本节字段对一个具体服务填真实query/探针、版本和阈值；未知处明确待核，不生成会直接执行的通用kubectl命令。只读验证和写动作分栏。
4. **提前12分钟预警怎样决策？** 基于可校准的概率、事故损失与处置损失决定是否page/人工查/有界预排空；假阳性排空也可能造成事故。没有真实预测质量时先只读或影子验证，保提前量。
5. **三人团队怎样选？** 比较重复调查的时间、可观测性、runbook质量、数据权限与维护成本；先验证一条有用的只读事故工作流，再决定加工具/协作/修复，不按人头和年份机械判断。

原六题：①supervisor+专业调查+人类判断是一种可用结构，非唯一标准。②restart/revert/scale只有符合当前授权和前提才可执行。③双模型赞同增加一个交叉信号，不能证明根因或放行。④运行手册和复盘帮助跨人员保留经验，但向量库不是必要前提。⑤原MIT数字未核验，不作为正确学习答案。⑥预测的价值与处置策略、假警报和可观察反馈相关，未授权时不可直接动作。

静态multi-agent.svg与i4-incident-agents都呈现专业查询→假设→人工门禁；动态图批准是预设，未发生真人审查。原Python输入checkout就返回固定日志，指标/runbook与输入几乎无关，字符串分组和置信度不是真实调查；两条同组会自动批准固定restart+lower-limit，与图/正文人类门禁有冲突。本批没采生产日志、未运行源程序或修复服务。

## 16. 可控故障注入：SLO预算与终止条件

Phase17第24课的长期价值是**通过有界试验检验恢复假设**，不是随机破坏生产。先在受控环境说明稳态、待检故障、受影响对象/用户、时长、恢复标准、观测数据、终止阈值和负责人；已存在事故或重要观测缺失时保留暂停。控制、目标、安全与观测是职责，反馈进入代码/runbook/依赖图改进，不必机械部署四套工具。

SLI是好事件/有效事件或指定延迟/质量条件，SLO是规定窗口的目标。对请求成功率SLO S，允许坏事件比例为1−S，burn rate $B=e/(1-S)$，e是**同口径窗口观察错误率**；不同window和流量构成不能混用。99.9%目标且e=.002，B=2，不是相对健康基线.0005得到4。固定流量近似下，窗口w消耗全账期T的预算比例约 $B w/T$；真实变流量需用实际有效请求数和剩余额度。

[Google SRE多窗口方法](https://sre.google/workbook/alerting-on-slos/)在其30天、99.9%例中给长短窗口并用的参数，1h/5min且B14.4对应约2%预算；这些是设计例不是所有服务阈值。低流量下一个失败就能给很高比例，需要考虑业务损失、合成流量和长窗口。安全策略同时限制额外错误预算、用户严重后果、范围、持续时长和监控心跳，任一明确风险超限都可停止；不能要求“burn大且范围大”同时满足才停止。

### 完整离线例：独立停止门禁与缺数据

程序只核一条教学策略，窗口和阈值已由题设固定：范围最多20%、最大burn=2、99.9%请求SLO。真实系统需另外估监控延迟、双窗口、在途/恢复和业务伤害；它未执行故障。这里把str所表示的十进制SLO与阈值用Fraction精确比较，避免数值容差比一个极小阈值还大。这只是政策算术精确，不表示观测没有误差。HOLD表示不得开始或扩大；若故障已在注入，应先停止注入并核恢复，不在无流量时继续。

```python
import math
from fractions import Fraction as Q

def decision(errors,total,affected,slo=.999,burn_cap=2,scope_cap=.2,observable=True):
    if type(errors) is not int or type(total) is not int or not 0<=errors<=total or total<=0:
        return 'HOLD: 样本无效或无流量'
    numbers=(affected,slo,burn_cap,scope_cap)
    if any(type(x) is bool or not isinstance(x,(int,float)) or not math.isfinite(x) for x in numbers):
        return 'HOLD: 非法参数'
    if not (0<=affected<=1 and 0<slo<1 and burn_cap>0 and 0<scope_cap<=1):
        return 'HOLD: 范围无效'
    if type(observable) is not bool or not observable:
        return 'ABORT: 失去观察'
    burn=Q(errors,total)/(1-Q(str(slo)))
    reasons=[]
    if burn>Q(str(burn_cap)): reasons.append('burn')
    if Q(str(affected))>Q(str(scope_cap)): reasons.append('scope')
    return 'ABORT: '+','.join(reasons) if reasons else 'CONTINUE: 当前窗口满足策略'

assert decision(40,10000,.01).startswith('ABORT: burn')
assert decision(1,10000,.3).startswith('ABORT: scope')
assert decision(20,10000,.2).startswith('CONTINUE')  # 恰好burn=2/范围=.2
assert decision(1,10**15,.01,burn_cap=1e-13).startswith('ABORT: burn')
assert decision(0,10000,.01,observable=False).startswith('ABORT')
for e,n,a in [(True,100,.1),(0,0,.1),(0,100,float('nan')),(0,100,True)]:
    assert decision(e,n,a).startswith('HOLD')
print('精确边界与极小cap反例通过；小范围高burn和范围越界独立停止，缺数据不通过')
```

提供商429可以是限流，不等供应商宕机；模拟时分别注入持续限流、慢响应、网络中断、部分stream中断和错误状态。故障转移仍检查备用质量、数据授权、协议与成本，不能把任何第二供应商当自动可用。KV压力/驱逐可能引起重算/排队，需区分普通请求长度上限、prefill/decode内存和恢复轨迹。“巨大UTF-8码点”不是准确技术描述，Unicode标量有范围，应测试已定义的超长、非法编码或实际解析器复杂度，不虚构万能tokenizer bomb。

故障有experiment ID、对象和可信时间线，结合独立服务指标看全局/范围内影响，不能仅因为请求有标签就断定全部根因属于试验。抑制的是可识别重复噪声，严重事件与试验外真实事故仍报警。终止故障也不自动撤销已发生的写入或清理注入，需要验证恢复和补偿。[AWS FIS](https://docs.aws.amazon.com/fis/latest/userguide/stop-conditions.html)明确可用CloudWatch alarm停止且停止后的实验不能resume；工具支持“none”不代表无门禁是本系统可接受配置。

### 第24课：原练习与六题参考

1. **哪个原模拟停止？** 其burn按expected .0005计算，provider .015/.0005=30且scope=.30>.20，停止。pod .002/.0005=4、scope.05，malformed .04/.0005=80、scope.10，都因AND条件放行。正式例改按SLO允许率并独立门禁；不能说源码验证了小范围灾难安全。
2. **RAG服务五个受控实验。** 依次候选：一冗余decode副本失效、网关→提供商慢/断、429与有限重试、预定输入上限、KV驱逐压力。每项写故障对象/上界、预计降级、成功/停止、独立probe和恢复；先在staging验证，不实际注入。
3. **暂停后怎样分辨根因？** 对齐experiment与自然故障时间，比较未注入对照/依赖链/最近变更，检查监控本身异常；可能有叠加事故，不因为标签或时间相关就只归因chaos。
4. **生产还是staging？** staging先验证工具/门禁/恢复；生产用于环境差异确需验证且已有授权、容量、值班和可限制对象时。不能以“完整演练”跳过风险评估或当前事故。
5. **三个特殊故障。** KV压力触发preemption/recompute、部分SSE与token/usage丢失、长输入/工具循环造成资源放大；各需要对应注入/测量，网络断包不能穷尽它们。

六题：①SLI/SLO、观测、恢复/runbook/值班是必要准备例，还需具体授权与范围。②控制/目标/安全/观测加反馈是职责分工。③burn=窗口错误率/(1−SLO)，阈值按错误预算/风险设置，非统一2×健康基线。④KV驱逐压力是可检场景。⑤周期按变更/风险与恢复缺口安排，周/月/季不是规范要求。⑥恶意/异常输入可能耗资源，需明确合法码点、大小和被测解析器。
