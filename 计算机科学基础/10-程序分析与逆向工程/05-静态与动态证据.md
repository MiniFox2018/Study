# 静态与动态证据

本章解决一个具体问题：一份反编译报告说“参数是int、结果是5、函数已验证”，这三句话各由什么支持？先读[布局](01-二进制布局与装载地址.md)、[指令与ABI](02-指令ABI与编译惯用法.md)和[控制流/IR](03-控制流与中间表示.md)，再把结论、依据与尚未知道的部分分别记录。

## 1. 观察到工具输出，不等于观察到程序行为

| 证据 | 可以直接说什么 | 不能直接升级成什么 |
|---|---|---|
| 文件头/原字节 | 某摘要文件在某范围有这些值 | 文件已成功运行、指令一定可达 |
| 工具反汇编/伪C | 固定工具与配置返回了这段文本 | 函数原型、类型和行为已正确恢复 |
| 指令/ABI推导 | 在明确机器语义和前提下可推出某关系 | 任意编译器/平台/输入都相同 |
| 一次受控执行 | 在该目标、环境和输入下得到结果/异常 | 其他目标或所有输入都相同 |
| 一组差分测试 | 已执行案例在约定观察维度一致 | 全定义域等价或没有其它副作用 |
| 形式化证明 | 在模型、假设与证明范围内成立 | 模型外的库、设备、并发和环境也已证明 |

例如工具打印`unsigned long long v1; v1 = a0 * 1717986919`，首先是“看到了工具文本”。若a0与常量先按32位int相乘，再赋64位，不能当作机器先符号扩展再64位乘法。源码或工具输出中的“observed”标签，也必须说明观察的是文本还是行为。

静态推导不需要一律降级为无效猜测。正确的做法是声明前提：例如[常数除法推导](02-指令ABI与编译惯用法.md#常数除法推导)在固定位宽与定义域下有明确误差界；执行几个样本可检查实现，却不是该数学结论唯一合法来源。反过来，一次运行也不能覆盖没有执行的路径。

## 2. 每条结论绑定目标、问题和环境

一份可复核的收据至少保留：

1. **目标身份**：完整文件摘要、容器/架构、函数与地址坐标、读取范围；路径和名称只辅助定位。
2. **操作与问题**：读取字节、分析CFG、推断原型、运行哪个输入，或者比较哪两个候选；不能让无关观察关闭另一个问题。
3. **方法环境**：工具/后端版本、选项与分析profile、编译器/flags、运行架构/系统、依赖摘要；未取得的字段写未知。
4. **原始观察**：输入、输出、退出状态、异常、截断/超时和工具诊断；预期结果另放，不能用预期值覆盖原始值。
5. **推导与覆盖**：由哪些观察推出什么结论、适用域、未覆盖项、何时需要重新核验。

下面只是本库自定义模式示意，不是已经发生的运行，也不是REA统一schema：

```json
{
  "schema": "study-evidence/v1",
  "subject": {"sha256": "<完整文件SHA256>", "arch": "x86_64"},
  "operation": {"kind": "static-byte-read", "section": ".text", "offset": 16, "size": 5},
  "method": {"reader": "<名称与版本>", "profile": "<固定配置摘要>"},
  "observation": {"bytes": "<实际五字节>", "status": "<完整或截断>"},
  "claims": [{"kind": "observed-text", "statement": "<实际观察>"}],
  "assumptions": [],
  "limitations": ["未执行目标指令", "未由这次读取证明整个函数行为"]
}
```

名称相同但摘要不同，是不同目标。将源码在Apple arm64上重新编译并运行，不能写成执行了原x86 ELF对象；相同参数/结果也不自动消除架构、编译器和产物差异。loader应用重定位后的内存字节与原文件字节不同，也需记录映射与变换，而不是直接判其中一个文件被篡改。

## 3. confidence与authority各自描述什么

置信标签描述推断程度，来源/权限标签描述信息从哪里来。工具自动填“observed”“controlled replay”，不能代替目标绑定、方法资格和完整结果检查；高置信的错误目标仍不是当前问题的证据。

接纳一条验证证据前核同一组条件：目标摘要、候选摘要、输入和问题匹配，所需环境成立，操作确实完成，退出/异常按合同处理，结果没有被截短，证据出处可信。不能只检查函数名、args、result或一个authority枚举。

原课实现中，某些promotion/claim查询没有完整核subject、环境、退出状态或当前问题，可能误用另一版本的运行。这里保留的是“分层记录和准入”的方法，不将其代码当可直接套用的通用证据系统。

工具私有术语也要按合同读。例如Ghidra导出中的`is_dead`可能指特定AST标志，同时该项仍属于一个实际block；不能据此认定机器代码不可达。Ghidra某gcc模型的内部调用约定名字可写`__stdcall`，仍按其RDI/RSI等输入规则解释，不能只靠显示名判成Windows ABI。地址空间也要保留，stack空间的负offset不是程序VA。

## 4. 未知是一个可继续调查的状态

| 情形 | 应记录的状态 |
|---|---|
| 工具明确不支持某操作 | 已知能力限制；该操作结果仍未取得 |
| 查询成功但返回空列表 | 在本次查询/profile/范围内没有记录；不保证全局不存在 |
| 函数入口或间接目标未恢复 | 未知边/未覆盖字节，继续收集证据 |
| 运行超时、输出损坏或环境不匹配 | 未完成或不合格证据，不能按结果值晋升 |
| 新证据与旧结论冲突 | 保留冲突，检查身份、方法、环境与前提后修订 |

一个unknown应写成具体问题，例如“这五项表是否全部限制在合法索引范围内”，附所需证据、责任操作和关闭条件。新增无关的受控运行、降低原门槛或清空unknown列表，都不算解决它。

修订unknown时，先验证新状态和新证据资格，再原子地发布revision；不要先写mutation后校验，失败留下孤立记录。提高关闭条件后，旧resolution应重新核资格；不能让旧的低门槛验证悄悄继续有效。

## 5. 内容摘要、哈希链与身份的区别

摘要可绑定一份内容，不能证明内容真实、作者身份或操作执行过。哈希链能暴露与受信锚点不一致的修改；有权重写整条链的人也能重算所有hash。需要更强审计时，将记录与可信签名/外部锚点、权限和持久事务结合，明确谁能写入和谁复核。

记录应不可变或返回副本。若ledger存入可变dict，外部仍能直接修改，便可能绕过revision；导入前先完整校验schema、ID、引用完整性、目标与resolution资格，再一次提交，失败不留下半导入状态。只校验hash一致，不保证链接的mutation真的对应当前revision。

签名和ID计算还要冻结规范化合同。RFC8785 JCS规定数字表示、字段排序和合法输入；不是“禁止float＋json.dumps(sort_keys=True)”就完成。Python任意大整数、Unicode码点排序、重复key被解析器吞掉和非法Unicode，都可能使不同实现得到不同字节。比如UTF-16键排序与Python码点排序，对补充字符和某些BMP字符的相对次序不同。先解析成dict后，丢失的重复key通常已无法追溯。[JCS必要规则](https://www.rfc-editor.org/rfc/rfc8785#section-3)。

若教学系统只支持一个更窄的ASCII/整数JSON子集，可以明确命名为自己的序列化合同、限制输入并保测试向量；不能因此宣称实现了通用JCS或跨schema共享同一Evidence ID配方。

## 6. 缓存命中不等重新验证

分析缓存键应绑定目标摘要、工具/后端/profile、操作、参数和schema版本；结果本身也要检查确实对应这些身份。把新路径改写成旧路径后重放一份工具快照，只是受控重放，不是新工具运行。

失效语义要覆盖实际读取与导出，而不是只禁止export、仍允许旧lookup。目标、工具、配置、问题或要求环境变化时重新判定；旧记录可以保留为历史证据，但不能被当当前验证。未声明格式版本而宽松兼容的快照，也不能以“规范说必须有版本”反推文件已验证。

### 缓存写入前失效，与证据保留分开

目标私有副本、内存答案缓存和可保存的分析快照不是同一种东西。副本供分析器读取，答案缓存保存某个精确问题的结果，快照文件则可连同目标身份、profile和证据包持久化；它仍不是完整分析数据库。

例如先查询函数A，再修改分析数据库中的A名称。修改请求发出后连接中断，并不能确定服务端是否已改名。因此不可等“修改成功的回复”才使旧缓存失效。保守方法是在派发写操作前失效，并让失败回复也保持失效，直到恢复到明确的新会话状态。原证据可作为历史记录保留，但不能继续作为当前未修改数据库的精确快照。

缓存资格也要排除隐式游标与会话状态。查询xrefs时不给address、读取current_procedure，或者依赖当前document的请求，不能仅凭工具名命中旧缓存。把问题参数补全并绑定目标/profile之后，才有可比较的键。一次已启动分析器上的新查询很快，不足以证明缓存命中；手册的捕获就没有实际重放相同问题。

### 交换证据时，原记录与脱敏副本分别绑定

文件字节摘要、语义记录ID、证据包canonical摘要和展示副本摘要回答不同问题。路径只要出现在参与ID的parameters、normalized_result、locations或嵌套记录中，替换它就可能改变语义ID；“subject.local_path不参与ID”并不允许替换文件内全部路径后继续使用原ID。

本库对手册捕获中26种不同的完整记录内容，用明确的ASCII键、安全整数、无浮点数据子集核了其序列化与投影：21种匹配原ID，5种不匹配。问题涉及容器检查的嵌套路径、Wasm参数路径、过滤后的JavaScript父记录及两个路径被替换的视图。手册称仅两份不匹配不够准确；不匹配的副本仍可作为有变换说明的学习材料，不能直接叫“原完整可校验证据”。

这项检查不是运行REA，也不是认证作者或真实执行。其投影规则另按[REA固定源码](https://github.com/morluto/rea/blob/3b79af28e80785afce9f5998d8f03289402a1847/src/domain/evidence.ts)定点核：去掉记录自身ID，仅保顶层subject的digest/format/architecture，coverage为null时省略，其余所列语义字段参与。

一份可交换记录应分别保留原始记录标识、变换类型/位置、变换后文件摘要以及验证结果。删除字段后若无法重算原ID，就明确写“删减展示版，父记录未随附”；不要重算一个新ID却仍冒称原作者原记录。

手册的O1证据包副本为178206字节，在所核子集中等于178205字节canonical内容加换行，摘要因此不同。捕获脚本另一个same_bytes比较却涉及未脱敏的原导出文件，不能把该布尔值的唯一原因都归为换行。比较前先列两边具体文件、变换和口径，比解释一个模糊的“相同”更可靠。

### 持久未知与证据包的生命周期

未知记录可以用问题、领域与目标范围形成稳定身份，每次修订保留前序摘要，并用expected_revision检查并发。假设甲乙同时读到revision1，甲先写成2，乙再带expected_revision1提交应冲突；乙需要重新读取合并，而不是覆盖甲的证据。

状态改成resolved之前，核关闭条件与实际证据是否回答该问题。记录一次“分析者决定关闭”的mutation，只证明记录过这个意图。即使附了observed类型的ID，也还需核目标、问题、环境、权限和证据内容；无关ID或空运行不能关闭问题。

证据包是多份记录及其引用的交换集合，应校验记录身份、引用闭包、重复冲突、修订链和目标范围。bundle没有库存完整性标记时，一条记录只出现在左边不能直接叫“程序删掉了这个行为”，可能仅是右边没有采集它。按记录ID比包，与按两个版本的同一函数比行为，是两种任务。

会话关闭还可能清空内存账本。先导出再关闭，重新打开目标后要明确哪些证据是历史导入、哪些是新采集。手册的8记录包导入只新增6，是因为两份源记录早已由比较操作补回；不能据新增少于文件记录数就判丢失，也不能据unknown计数0认定没有待研究问题。

## 7. 先计划观察，再启动调试

动态分析把静态问题落实到某次执行的具体状态。先固定目标与debug文件摘要、架构、优化等级、输入、依赖和启动环境，再为每条claim写观察点和判据。例如“这次进入bump时，首参指向的balance为250，by为5”，可以在经过核对的入口附近读取寄存器和对象；“所有输入都只写一次”则需要更强的覆盖或静态证明，不能由单次断点替代。

符号名断点会解析为一个或多个位置，可能跳过序言或对应多份实例；核实际地址及此前指令是否已修改待观察参数。按地址设断点则要区分模块文件地址、链接VA和运行时load address，记录slide。名字存在、断点创建、位置resolved、实际命中是四个不同阶段。[LLDB断点说明](https://lldb.llvm.org/use/tutorial.html#setting-breakpoints)。

软件断点通常用陷阱指令临时替换目标指令：x86-64常见一字节INT3，arm64常见四字节BRK；调试器负责恢复并继续，报告PC的含义按架构和调试器实现核。硬件数据watchpoint用有限的地址比较资源，所需槽数受地址、长度、对齐与硬件限制影响。本例作者机器报告4个硬件watchpoint，不是所有arm64机器的固定能力。

批处理可把计划保存成命令文件，用LLDB的`-b -s 文件`运行，并记录stdout/stderr、命令退出状态、进程退出状态和超时。原课设置`interpreter.stop-command-source-on-error false`，让进程退出后多余的continue报错仍能执行最后的断点列表；这不允许忽略所有错误，应区分预期的“进程已退出”和真正破坏观测的失败。[LLDB批处理选项](https://lldb.llvm.org/man/lldb.html)。

stop hook适合在暂停时统一读取寄存器、受限内存和frame变量。本课hook输出先于stop frame文字出现，解析器需把同一事件的材料正确连接；真实记录最好带PID/TID、stop ID、模块身份、PC和每次读取的有效地址/长度。不能把两个不连续memory区按地址排序拼成连续数组，也不能将上次失败读取留下的值附到下一次停顿。

## 8. GDB与LLDB的操作对应

下表是学习操作的对照，作用对象为你有权调试的自建程序。地址仅为形式示例，使用时替换为本次构建实际位置；此处没有执行这些命令。参数和别名可能随版本变化，先用对应`help`核当前支持的选项。[官方命令映射](https://lldb.llvm.org/use/map.html)。

| 任务 | GDB | LLDB |
|---|---|---|
| 函数断点 | `break bump` | `breakpoint set -n bump` |
| 文件行断点 | `break account.c:13` | `breakpoint set -f account.c -l 13` |
| 地址断点 | `break *ADDR` | `breakpoint set -a ADDR` |
| 限定模块 | 按该构建符号/地址限定 | `breakpoint set -a ADDR -s MODULE` |
| 条件断点 | `condition 1 by == 5` | `breakpoint modify -c 'by == 5' 1` |
| 断点命令 | `commands 1`后输入命令并end | `breakpoint command add 1` |
| 每次停止的hook | `define hook-stop`后end | `target stop-hook add -o 'register read x0'` |
| 断点状态与计数 | `info breakpoints` | `breakpoint list` |
| 变量写监视 | `watch a->balance` | `watchpoint set variable a->balance` |
| 地址区域监视 | `watch *(int *)ADDR` | `watchpoint set expression -- ADDR`，另明确所需字节长度 |
| 监视点状态 | `info breakpoints` | `watchpoint list -v` |
| 启动 | `run` | `process launch`或run |
| 从首指令停止 | `starti` | `process launch --stop-at-entry` |
| 继续 | `continue` | `process continue`或continue |
| 源码级进入/越过调用 | `step` / `next` | `thread step-in` / `thread step-over` |
| 指令级进入/越过调用 | `stepi` / `nexti` | `thread step-inst` / `thread step-inst-over` |
| 跑到当前函数返回 | `finish` | `thread step-out` |
| 栈回溯 | `bt` | `thread backtrace` |
| 全部寄存器 | `info registers` | `register read` |
| 单个寄存器 | `p $x0` | `register read x0` |
| 读取8个4字节word | `x/8xw ADDR` | `memory read -s4 -fx -c8 ADDR` |
| 参数/局部变量 | `info args` / `info locals` | `frame variable --no-locals` / `frame variable --no-args` |
| 一个变量 | `print a->balance` | `frame variable a->balance` |
| 表达式求值 | `print by + 1` | `expression by + 1` |
| 当前函数/指定函数反汇编 | `disassemble` / `disassemble bump` | `disassemble --frame` / `disassemble --name bump` |
| 地址对应符号 | `info symbol ADDR` | `image lookup --address ADDR` |
| 附加已获授权进程 | `attach PID` | `process attach --pid PID` |
| 保存core | 调试器内`gcore corefile` | `process save-core --style stack corefile`，核平台/style支持 |
| 打开core | 终端`gdb program corefile` | 终端`lldb -c corefile program` |
| 调试器Python | `python print(1)` | `script print(1)` |
| 退出 | `quit` | `quit` |

几个动作虽然都能“打印”，含义不同。frame variable按debug位置读取，并非通用表达式执行器；expression可调用目标函数，从而改变被观察程序，不能与纯读取混同。调试器中的Python也会执行脚本，不因为它在调试器里就可以忽略来源与副作用。裸地址watch expression默认区域大小可能是指针大小，监视4字节字段时须明确长度，不要靠默认值猜。

单步、停止、读内存和watchpoint都会扰动执行时序；并发程序尤其不能把“调试时未出现竞态”当作没有竞态。源码行号也不等于单条指令：源码级step可能跨过多条机器指令，优化会移动或消去变量。

## 9. 手解一次调试观察

本课作者在2026-10-14用LLDB捕获了Mach-O arm64的account-O0。第一次bump暂停时，x0为0x16fdfe008，x1为5，PC为0x1000004bc；这是函数起点之后12字节。核此前序言只保存参数，才可以把此处寄存器用于该参数检查。

从x0开始，前八个4字节word为`73 fa 09 00 00 3ff40000 719 01`，这里每项按日志中的完整32位十六进制word理解：

| 相对偏移 | 按本例小端/字段宽度解释 | 得到的观察 |
|---|---|---|
| 0 | 取首word低1字节 | kind='s'，其他字节不能当成员 |
| 4 | 32位有符号整数 | balance=250 |
| 8 | 取低2字节并按有符号解释 | code=9 |
| 16 | 合并0x00000000与0x3ff40000 | IEEE-754 double 1.25 |
| 24 | 合并0x00000719与0x00000001 | label指针0x100000719 |

这32字节与同stop的frame变量字段一致。它支持该次观察中的布局与值相容，不单独证明对象总大小，也不说明padding总是零。本轮只对原日志重新解码，没有重新运行LLDB。

watchpoint记录地址为x0+4、长度4、类型modify，出现old=250/new=255。停顿PC为0x1000004d0，原文件在前一条0x1000004cc有对应store。结合by=5支持“这次被记录的修改将250变为255”；只见一次modify事件，不自动等于所有store恰一次，因为同值写入、未覆盖时段、线程或watch过滤可能不可见。

classify的第一分支字0x36f800a8解为`tbz w8,#31,target`，目标0x100000504。bit31为0时跳转，即本例32位balance非负；负值则落到0x1000004f4。原日志对100、255、−40分别显示目标、目标、落空路径。第二分支比较200，100走`<=200`的目标，255走落空。不能仅凭“看到了target的断点”判整个通用CFG正确，还要核这次激活、寄存器来源和中间控制流。

O0日志共11次停顿，三个函数入口计数为1、3、1，进程exit=0；O2日志同样打印分类与总和，却零次停顿。O2原字节中main仅有四个BL到外部stub，业务结果已常量化，三个业务函数的独立副本仍存在于符号表。这次日志和静态调用点相互支持“当前main没有进入这些独立副本”，不是“函数从此对所有调用者都无用”。

还有两处不能照单全收。原hook每次从x0固定读96字节；当x0指向rows[1]时，原三元素数组只剩64字节，后32字节来自数组之外的栈；当指向rows[2]时越界部分更多。分析读取虽能返回这些字节，也不能称它们是更多account元素。另在sum_balances刚暂停时，局部sum的初始化指令尚未执行，frame显示1876942928只是该时刻的未初始化槽内容，不是函数计算结果315。

## 10. 三态判定要有覆盖门槛

confirmed表示该次合格观测支持指定范围的claim，refuted表示合格反例与其冲突，not-observed表示现有材料不足以测试。对象、输入、构建、预期参数集合与必要字段应先匹配，再判断结果。

| 材料状态 | 合理判定 |
|---|---|
| 有效stop读取到参数，与预先定义的同一参数匹配 | 此stop参数claim可confirmed |
| 完整同一stop读到相反值 | 对该claim构成refuted，同时核类型/符号扩展/时机 |
| 没有参数字段、count未读取、memory有空洞 | not-observed，不让空循环返回成功 |
| 函数断点有位置但未resolved/被禁用/设得太晚 | 不能把零命中当作未调用证据 |
| 布局有多个字段缺测，只有一个字段一致 | 只确认该字段，整体仍有未观察部分 |
| 进程未结束、发生截断或尚未到调用处 | 调用次数claim仍未完成 |

对“本次运行从未进入某入口”这种否定观察，至少核：所有相关位置和模块正确、观察时段覆盖整个相关运行、断点始终启用且没有过滤漏报、线程/子进程范围明确、捕获完整，并核实际终止原因。对“由main调用”的claim还要知道caller，而非只数全进程的入口stop。进程有退出状态不代表这些条件都满足。

汇总也不能只把一条confirmed覆盖所有not-observed。若claim是“每个相关入口参数都满足条件”，需要列出必需入口集合及每项状态；某项缺观察，整体就不能宣称全部确认。存在合格反例时保留反例，修订原claim范围；不要删掉unknown来得到绿色报告。

原课程harness有值得保留的反向测试思路：改一个寄存器值，应能被判不一致；删掉watchpoint的old值，应降为未观察。但代码还存在空arguments直接confirmed、缺count默认为0、无对照或无sum输出仍可判stride确认、未核所有断点resolved便判calls反例等路径。因此这里吸收三态与证据覆盖的方法，不把原自动评分器当完整验证系统。

## 11. core、trace与确定性重放各能回答什么

core是某时刻保存的寄存器和部分或全部映像信息；实际保存范围由平台、style、映射与配置决定。读取时保留可执行文件、debug文件、相关映像的身份，区分“指针值在core里”“所指字节在core或可信关联文件里”“调试器能按某种格式显示”。空字符串显示、不可读、optimized out与实际零长度字符串是不同状态。

本课作者保存stack-style core后，加载日志能显示bump/main/start回溯、balance=250和label指针，但字符串被显示为空。其保存日志明确警告没有包含相关映像副本。由于原core文件没有提交，本库无法独立重查它究竟包含哪些段，也不能把`label=""`当程序原值。full style通常会增加保存范围与文件体积，也应核具体支持和实际覆盖，不能只看style名字便认为所有可观察状态都已保存。

| 工具/方式 | 主要观察 | 不能替代的证据 |
|---|---|---|
| debugger | 暂停时的寄存器、内存、栈与事件 | 未执行路径或所有线程的无扰动行为 |
| strace等syscall追踪 | 实际发起的系统调用及返回 | 每个源码函数/库函数是否调用 |
| ltrace等库调用追踪 | 受其机制覆盖的动态库调用 | 静态链接、内联、绕过该边界的所有调用 |
| bpftrace/DTrace等探针 | 按探针位置收集内核/用户事件 | 探针外的完整程序状态与覆盖 |
| 文本transcript | 已保存命令与输出 | 能从任意时刻确定性重放整个执行 |
| rr等record/replay | 在支持环境中记录运行并确定性重放 | 不支持的平台/硬件/系统边界 |

一行printf可能被缓冲或与其他输出合并，不必对应一次write syscall。trace也会带来开销和时序改变。rr的硬件计数器、Linux环境、CPU与虚拟化支持需按实际环境核，不能从“Docker里是Linux”推出一定能用，也不把作者机器当时的虚拟化限制写成永久结论。

## 12. 环境失败归环境，不替程序作结论

Linux调试权限涉及ptrace访问检查、用户/能力、namespace、目标状态及LSM/Yama策略，不能把某发行版的ptrace_scope值当所有系统默认。macOS调试涉及task port、异常通知、debugger身份、目标签名/hardened配置与sandbox等。某次attach错误只能证明该操作在该环境失败，不能仅凭错误字符串认定所有机器都受同一个原因阻断。[Linux ptrace权限检查](https://man7.org/linux/man-pages/man2/ptrace.2.html)。

macOS中debugger侧调试能力与目标侧get-task-allow属于不同对象；签名为adhoc不自动证明可以任意附加，启动自建程序成功也不说明对其他目标均有相同权限。分析笔记应记录实际签名/启动结果和平台文档依据；原课的重签、提权及系统设置命令没有在本任务中执行，也不作为学习流程默认步骤。

遇到不可启动、未设监视点或目标变量位置不可用，留下对应unknown并继续能完成的静态核对。优化后的变量可由常量/位置列表描述，也可能已消去；“看不到变量”不证明源程序从未包含它。“本次因权限未运行”更不能写成“动态验证通过”。
