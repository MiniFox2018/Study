# 链接、装载与无符号分析

读完[二进制布局与装载地址](01-二进制布局与装载地址.md)后，已经可以找到文件中的指令；本章继续回答：外部函数地址尚未确定时，调用为什么还能链接？文件里的一个“指针”究竟是地址、名字索引还是修复记录？没有普通符号表，怎样找函数并谨慎命名？

本章的地址算例来自固定教材提交`1a8c4fd`的受控样本，采用文件坐标或链接地址时会明确说明。作者工具输出、本库对文件字节的静态核对、实际操作系统装载是三种不同证据。这里没有运行来源程序，也没有验证手工ELF、PE映像能在目标系统执行。

## 1. 先分清链接器、装载器和分析工具

编译器产生对象文件，里面可以保留“此位置引用某符号”的重定位记录。静态链接器选择输入、合并布局、解析符号、应用能够当时完成的重定位，并生成仍需装载时处理的动态信息。装载器建立内存映像；动态链接器按依赖、查找规则、版本及绑定方式解析剩余引用，完成必要修复。分析工具读取其中的某些结构，再结合指令推断程序意义。

因此，“对象中有一条重定位”“链接映像中有一个导入槽”“反编译器显示函数名”“程序实际进入该函数”分别回答不同问题。一个函数可能有多个调用点，共用一个槽；一个依赖库也可能没有被当前执行路径用到。静态链接进自己的业务函数，并不代表整个可执行文件没有动态依赖：本课名为`static-arm64-O2`的程序仍导入`puts`、`printf`与栈保护相关符号。

| 对象/映像 | 主要查询入口 | 最容易混淆的事情 |
|---|---|---|
| ELF ET_REL | 节、符号、REL/RELA | 节内偏移当成已装载地址 |
| ELF动态映像 | program headers、PT_DYNAMIC、动态符号与重定位 | 只认节名，忽略运行时不依赖普通节表 |
| COFF对象 | 20字节文件头、节、符号、辅助记录、重定位 | 当成带MZ头的PE映像 |
| PE映像 | PE头、可选头、节和data directories | RVA直接当文件偏移或运行时VA |
| Mach-O | load commands、segment/section、绑定/导出信息 | 把链式修复编码当已解析指针 |

开始一份分析报告时记录文件摘要、格式/架构/位数/端序、对象或映像类型、构建命令及来源；记录你实际解析过的表和拒绝的格式。工具能打开文件，只说明它处理了部分结构。

## 2. ELF链接决策：重定位类型还不是最终调用形态

### 从公式到链接结果

沿用前章的S、A、P、L，并以B表示装载偏移，x86-64常见规则如下。实际字段能否容纳结果、符号能否在链接时绑定，还要另行判断。

| 类型 | 关键含义 | 不能直接推出的结论 |
|---|---|---|
| R_X86_64_PC32 | 写入S+A−P，32位PC相对值 | 每次都引用函数，或每次都要再加4 |
| R_X86_64_PLT32 | 使用L+A−P的调用/跳转引用；满足绑定条件时可由链接器直接解析 | 看见此类型就必有PLT；符号出现在输入中就必定direct |
| R_X86_64_64 | 写入S+A的64位绝对引用 | 最终一定变为RELATIVE |
| R_X86_64_RELATIVE | 装载时按B+A修复，不按普通符号名查找 | 所有动态修复都属于它 |
| R_X86_64_GLOB_DAT / JUMP_SLOT | 将解析后的符号地址写入对应位置；后者服务调用槽绑定 | r_offset是原始call指令地址 |

`PLT32`也可能用于尾跳转，不能以重定位名代替解码。即使某共享对象内定义了同名函数，该引用是否可直接绑定，仍涉及符号的局部/全局身份、weak、visibility、可抢占性和链接选项。两个对象各自的局部同名符号不是同一个定义；不要把所有名字塞进一个集合来实现符号解析。

例如，在本课`main-x86_64-O1.o`中，`.text+0x2d`的记录为`R_X86_64_PLT32 puts-0x4`，另有对`grade`、`total`等的同类记录。将同批业务对象按示例的非抢占假设一起链接，业务函数可以直接调用，而`puts`和`printf`保留外部绑定。这个教学规划统计为16项in-place、4项direct、4个PLT调用引用、2项relative；PLT调用引用按名字去重后只需两个普通入口。这里的“4个引用”与“2个入口”必须分开。

经典x86-64布局下，n个外部函数对应`.plt`的`16×(n+1)`字节、`.got.plt`的`8×(n+3)`字节、`.rela.plt`的`24×n`字节。它解释本样本n=2时的48、40、48字节；遇到其他PLT形式、链接器优化、IBT或零入口情形，应读实际布局。原课程把此规划与另一个手工tiny文件比较大小，后者导入的是`puts/exit`，不是`puts/printf`；入口数量相同只验证大小算式，不能称“这一组对象确实链接成了那个tiny文件”。

32位绝对重定位是否能用于某PIE，要同时核目标表达式、范围和链接约束；“只要出现32/32S就一概非法”过强。同样，绝对函数指针是否能用RELATIVE，取决于最终绑定，动态符号解析仍可能必要。[x86-64 psABI重定位定义](https://gitlab.com/x86-psABIs/x86-64-ABI/-/raw/master/x86-64-ABI/object-files.tex)、[gABI动态符号查找与绑定](https://refspecs.linuxfoundation.org/elf/gabi4+/ch5.dynamic.html)。

### 动态信息从哪里读

装载视角从PT_LOAD、PT_INTERP和PT_DYNAMIC开始：普通动态可执行程序的PT_INTERP可指定解释器；不要要求所有共享库或所有ET_DYN都具有它。动态数组通常以DT_NULL结束，并用不同tag表达地址、大小或字符串索引。

| 信息 | 需要配套读取的字段 |
|---|---|
| 依赖名字 | DT_NEEDED的字符串表偏移，以及DT_STRTAB、DT_STRSZ |
| 动态符号 | DT_SYMTAB、DT_SYMENT，名字再索引字符串表；符号数量须有可靠边界来源 |
| 普通动态重定位 | DT_RELA/RELASZ/RELAENT，或对应REL字段 |
| PLT绑定重定位 | DT_JMPREL、DT_PLTRELSZ、DT_PLTREL；先判断REL还是RELA |
| GOT及绑定策略 | DT_PLTGOT，BIND_NOW及相关flags |

每个“地址＋长度”先换算为完整的文件支撑范围。不能起点有效就任意切片，也不能让DT_NEEDED的字符串越过DT_STRSZ继续在整个文件找零。普通`.symtab`和节表缺失后，动态链接所需的信息仍可能存在；依赖`.dynsym`节名的教学解析器不等于已经支持无节表映像。DT_NEEDED列出依赖，不自动证明每个未定义名字最终由哪一个库提供；符号版本、查找作用域和运行配置都可能影响提供者。

## 3. 用实际字节走完一次经典PLT调用

本课手工`tiny-dyn-x86_64`是ELF64 ET_DYN，下面均使用链接VA；它的相应PT_LOAD恰有同值文件偏移，这个巧合不能推广。

| 位置 | 字节或记录 | 如何理解 |
|---|---|---|
| 0x227 | `e8 d4 ff ff ff` | call的下一指令在0x22c，位移为−0x2c，目标0x200 |
| puts@plt，0x200 | `ff 25 d2 0e 00 00` | RIP相对间接jmp；0x206+0xed2=0x10d8 |
| GOT槽，0x10d8 | 文件中初值0x206 | 指向本PLT入口内部的push，尚非libc中puts的地址 |
| 0x206 | `68 00 00 00 00` | push对应绑定记录索引0 |
| 0x20b | `e9 e0 ff ff ff` | 下一指令0x210，加−0x20，进入0x1f0的PLT0 |
| .rela.plt | r_offset=0x10d8，JUMP_SLOT puts | 指明需要被解析/写入的槽 |

PLT0在0x1f0用RIP相对push访问GOT+8，即`0x1f6+0xed2=0x10c8`；随后在0x1f6用间接jmp访问GOT+16，即`0x1fc+0xed4=0x10d0`。经典延迟绑定路径由动态链接器先建立这些保留槽，再让第一次调用经解析器处理对应重定位，回写真正函数地址；后续调用经过同一个PLT入口直接跳到已解析目标。

这里不能把文件中的GOT初值直接当成“运行后第一次会访问的绝对地址”：PIE还涉及装载偏移和动态链接器初始化。若采用启动时绑定，解析会提前完成，程序的第一次调用就不会走延迟解析的长路径。不同PLT实现也可能不具有这段16字节模板。[x86-64 psABI程序加载定义](https://gitlab.com/x86-psABIs/x86-64-ABI/-/raw/master/x86-64-ABI/dl.tex)。

### RELRO与NOW分别解决什么

NOW要求提前完成相应绑定；RELRO声明某段内存在必要重定位后应变为只读。两者相关，但含义不同。只看到`-z now`不能宣布full RELRO，只有PT_GNU_RELRO也不能宣布所有调用槽都受保护。

分析时先列出RELRO区间，再核被关注槽位是否落入区间，以及NOW类标志和目标装载器行为。常见partial/full分类取决于布局与绑定策略；动态链接器最终落实页保护，页大小/边界也会影响实际保护范围。本课tiny没有展示一份可据此认定full RELRO的运行证据。[GNU ld的relro及now选项](https://sourceware.org/binutils/docs/ld/Options.html)。

## 4. COFF对象和PE映像：名字、槽位与基址

### COFF对象为什么不能交给只认PE的读取器

普通COFF对象从20字节file header开始；本课x86-64样本采用40字节节记录、18字节符号记录和10字节重定位记录。符号后可跟多个辅助记录，这些记录占符号表索引，遍历时必须按`1+aux_count`前进；重定位的SymbolTableIndex指的是原表索引，不是“过滤后第几个普通符号”。

本课`main-x86_64.obj`声明37条含辅助项的符号记录；`.file`的辅助项保存源文件名。节名可通过`/十进制偏移`指向字符串表，符号名也有短名与字符串表偏移两种表示。多个`.rdata`节可以分别存在，COMDAT选择信息在辅助记录中；不要只以节名作唯一字典key。

其`.text`中14条引用使用IMAGE_REL_AMD64_REL32，数据中另有ADDR64。对REL32，隐式addend来自被修改字段，PC基准与字段尾的关系按该重定位定义处理；不能因为它与ELF PC32落在相同节偏移，就认定两条记录的原始addend相同。以P为4字节字段的地址、A为其中的原始有符号值，普通REL32可写为`S+A−(P+4)`；REL32_n再把基准后移n字节。本课COFF ledger在字段0x36存0x28，故表达式为`S+0x28−(P+4)`；ELF同位置的显式addend为0x10，但它引用的是不同的只读数据布局，不能只比较两个数字就判错误。只支持普通COFF布局的教学读取器不自动支持bigobj、重定位数量溢出和任意损坏文件。

### 从RVA找到真正的文件范围

PE映像有MZ头，文件0x3c保存PE签名的文件偏移；签名后是COFF header，再跟映像必需的optional header。PE32+的magic为0x20b。读取目录时同时受SizeOfOptionalHeader与NumberOfRvaAndSizes限制，不能默认永远有16个有效目录。

设节的VirtualAddress为V、PointerToRawData为F、SizeOfRawData为R。请求从RVA X读取N字节，只有确认整个请求在该节文件支撑区域内，才能用`F+(X−V)`读取；若VirtualSize大于R，多出来的映像空间是零填充，不能继续读文件后面的无关字节。头部RVA、重叠节和非法范围另行处理。

目录项也不一律使用RVA：Certificate Table使用文件偏移。即使字段名看似virtual address，也应按目录定义解释。PE的普通COFF符号表在现代映像中通常不使用，不等于此格式从不允许相关字段；调试信息可能在映像内，也可能由调试目录引用外部文件，不能笼统说“所有调试信息都在PDB里”。[Microsoft PE/COFF规范](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format)。

### 一次IAT调用的完整路线

本课手工PE32+示例的ImageBase为0x140000000、入口RVA为0x1000。导入描述符在RVA 0x2000，指向`msvcrt.dll`，ILT位于0x2028，IAT位于0x2040。PE32+的查找项为64位：最高位区分ordinal/name，名字方式经过hint/name记录，hint只是查找提示。

文件中ILT与IAT都含`0x2058、0x2060、0`，前两个是hint/name记录的RVA，分别对应`puts/exit`；普通导入绑定会将IAT项更新为函数VA。调用点在RVA 0x100b，字节`ff 15 2f 10 00 00`，下一指令在0x1011，因此槽位是`0x1011+0x102f=0x2040`。运行时指令位置与槽位都随映像装载，不能把槽里的文件初值误读成代码地址。

普通导入通常在入口运行前处理，但PE也支持delay imports。分析报告应标明普通导入与延迟导入各自的目录和机制，不从本样本只有普通IAT推断所有PE都没有延迟绑定或调用跳板。导入遍历还要处理全零终止描述符、声明范围、ordinal与保留位；OFT/ILT缺失等情况不能交给无限循环去“碰到异常再说”。

PE导出则沿名字表、ordinal表和地址表关联；只枚举有名字项会漏掉仅按ordinal导出的项。地址落入导出目录声明的范围时，可能指向`DLL.名称`或`DLL.#序号`的forwarder字符串，而不是函数体；不要以整个`.rdata`或整个节的范围代替导出目录范围。

最后，基址重定位解决的是某些存储值随实际装载基址改变的问题，不等于导入解析。样本`.data`含一个指向字符串的绝对VA，`.reloc`块标记DIR64位置；若基址移动Δ，按该类型对目标存储值加Δ。块内ABSOLUTE项是填充，不应也执行指针修补。读取器须检查块至少有8字节头、长度推进为正、整块不越界及条目大小合理，否则block_size=0可能导致循环不前进。

## 5. Mach-O：stub、绑定索引和链式修复

### 三种索引要分开

Mach-O可从LC_LOAD_DYLIB等命令得依赖，从符号/间接符号表或chained imports得导入，从exports trie得导出。两级命名空间下，符号可携带library ordinal；它指定依赖身份，不等于全进程按名字搜索，特殊ordinal还需按具体表的规则解释。

要区分：间接符号表索引、chained imports表索引、依赖库ordinal。它们可以完全不同。本课`_puts`在原始nlist的索引为10，chained import索引为7，后者的库ordinal为2，对应`/usr/lib/libSystem.B.dylib`。省略表身份，只写“序号7”，会把后续追踪带错。

### 从BL到__got

本课`ledger_main`的调用点在链接VA 0x1000005a0，指令字0x9400003d。BL的imm26按符号扩展后左移2位，以当前指令地址为基准，目标为`0x1000005a0+0x3d×4=0x100000694`。

该处12字节stub为`30 00 00 90 10 1e 40 f9 00 02 1f d6`，对应ADRP、LDR、BR：ADRP生成0x100004000这一页的链接地址，LDR从其偏移0x38读取槽值，BR进入该槽指向的位置。即槽的链接VA为0x100004038；它的文件偏移在这个构建中为0x4038。要验证stub模式，还须检查三条指令的寄存器联系、pointer section步长与间接符号表边界，而非只看三个opcode。

### 文件里的0x8010000000000007为何不是指针

LC_DYLD_CHAINED_FIXUPS指向修复元数据。先读header中的starts/imports/symbols偏移和格式，再读各segment的page starts，最后按pointer_format解释链字。本课采用format 6，即DYLD_CHAINED_PTR_64_OFFSET；不能套用ARM64E的鉴权指针布局。

对于本例的bind字，位0–23给imports索引，位24–31为此格式的8位addend，位32–50保留，位51–62为next，位63为bind。Apple对应结构把这个8位addend定义为0–255；不要照ARM64E的另一类有符号addend直接符号扩展。这里addend=0，索引7找到`_puts`，next=2表示向后走`2×4=8`字节。这里的“4”是链步长单位，槽自身仍是8字节。

第一个槽从文件0x4000开始；12个链字覆盖0x4000至0x4058，其中10个bind、2个rebase。最后一个rebase的低目标值为0x6db，本例high8=0，format 6按映像相对目标解释，故链接目标为`0x100000000+0x6db=0x1000006db`，实际运行还要结合装载位置。其他格式对target、高8位、addend、鉴权及stride的定义不同，不能把“取低36位再加基址”做成通用解码器。[Apple固定版本fixup-chains.h](https://github.com/apple-oss-distributions/dyld/blob/fd8d0c4d52320ebf64db34f3cb280310d905c5ae/include/mach-o/fixup-chains.h)。

链遍历需要同时满足：starts范围、segment索引、page大小与起点、整个槽的文件范围、next在所属页/允许范围内、终止或明确报错。START_NONE表示无链，MULTI标记需要按格式处理多起点。segment_offset描述内存关系，不能无条件当文件偏移；应先定位segment再用其fileoff映射。达到人为步数上限应报告读取不完整，不能悄悄当作成功终止。imports还可能采用带addend的其他格式，symbols也可能压缩；不支持就明确停在该处。

### 与旧式lazy binding比较

相同课程还保存一个`-no_fixup_chains`构建：它通过LC_DYLD_INFO_ONLY描述bind/rebase/lazy-bind流，并有`__stub_helper`和`__la_symbol_ptr`。记录中7个lazy槽起初指向helper，后续由绑定过程更新；chained构建则用另一套元数据。两者的section与地址布局不同，因此只能按各自构建追踪，不可把nochain捕获的地址塞进chain报告。此比较帮助理解旧新机制，不是要求今天的macOS程序都使用相同的默认布局。

## 6. 剥离以后，哪些信息还能用

strip的效果由工具、版本、选项、对象类型与链接布局共同决定。GNU strip的debug-only与all选项不同，还可明确移除某些节；不要把“.comment一定消失”“所有ALLOC节永远逐字节不变”“无符号就无法动态绑定”当规则。[GNU strip选项](https://sourceware.org/binutils/docs/binutils/strip.html)。

普通符号与装载所需的导出/绑定元数据承担不同职责。本课Mach-O dylib在剥离后普通符号从5条变为0条，但exports trie仍列出四个业务函数，LC_FUNCTION_STARTS仍有四个起点。LIEF展示的`symbols 4`来自它的抽象视图，不能与“LC_SYMTAB的nsyms=0”直接判冲突；先核工具统计的来源。

| 固定构建前后 | 普通符号记录数 | 函数起点表数量 | 本库静态核对 |
|---|---|---|---|
| ledger_main | 12→10 | 1→1 | __text字节和链接地址相同 |
| libledger.dylib | 5→0 | 4→4 | __text字节和链接地址相同 |
| static-arm64-O0 | 13→6 | 5→5 | __text字节和链接地址相同 |
| static-arm64-O2 | 13→6 | 5→5 | __text字节和链接地址相同 |

记录数可能包含STAB等特殊项；`nm`过滤后的可见名字数量不一定等于nsyms。作者保存的三个运行日志均显示`odd`、`2`、`50 3 10 B`及exit=0，说明其相应环境下这个默认输入路径的观察；日志相同不能证明全部输入下行为等价。本库未重跑这些程序。

比较剥离前后时，分别列出：文件摘要与布局变化、符号/字符串差异、动态导入导出、函数/展开元数据、代码与被关注数据区、实际测过的输入及环境。修改符号和链接编辑数据可能改变文件整体摘要；“摘要改变”和“该段代码改变”也要分开。

## 7. 找到函数起点，仍需知道它漏了什么

| 方法 | 为什么有用 | 主要漏报/误报来源 |
|---|---|---|
| 普通符号 | 有名字，某些格式还有size | 剥离、别名、内联、边界为零或未知 |
| LC_FUNCTION_STARTS等元数据 | 链接器直接留下起点 | 可能缺失/不完整；有起点不等有名字和精确终点 |
| 展开/异常处理记录 | 给特定代码范围和恢复规则 | 叶函数可能无记录；一段函数可拆成多段 |
| 固定序言扫描 | 实现简单，适合提出候选 | 优化后省略栈帧；相似字节也可能在函数内部或数据中 |
| 直接调用目标＋入口 | 给静态引用候选 | 间接调用、尾跳转、未引用函数；扫描数据可生造BL |
| 签名匹配 | 已知构建的代码识别/命名 | 编译变化、碰撞、掩码过多、边界候选错误 |

在两个受控arm64构建中，已知五个函数。O0的`sub sp,sp,#imm`扫描命中5/5；O2只有main仍匹配，降至1/5。固定`stp x29,x30,[sp,#-0x10]!`模板两个构建均为0/5，因为编译器没有按这个模板生成函数。LC_FUNCTION_STARTS与直接BL目标加入口在这两个样本都得到5/5；这不保证未知文件也如此。

O2起点表相对__TEXT的ULEB128增量是`0x500、0xf4、0x18、0x3c、0xf8`，累加得到`0x500、0x5f4、0x60c、0x648、0x740`，再加链接基址。零增量终止，连第一个零也不应当作一个函数；ULEB读取应限制位数、字节数和声明数据范围。

评分使用去重后的候选集合F和受控参考集合T：TP=|F∩T|，FP=|F−T|，漏报=|T−F|；precision=TP/|F|，recall=TP/|T|，分母为0时报告不适用及原因。未剥离同构建的符号可作这个实验的参考，仍要核符号是否真是函数和两份文件的地址/代码关系；未知程序没有这样的参考时，不能凭空报“召回率100%”。函数终点也不能一律取下一起点，padding、热冷拆分和共享代码都需考虑。

## 8. 函数签名：把冲突留为冲突

一种FLIRT式思路是从已知对象产生签名：取前32字节的固定/可变模式，把重定位影响的字节标为可变；再取32字节之后、遇到第一个可变位置之前的一段计算CRC；结合函数长度、后续差异字节及引用名称处理冲突。识别出的名字是受条件约束的匹配结果，不证明原始源码或行为等价。[Hex-Rays的FLIRT原理说明](https://docs.hex-rays.com/user-guide/signatures/flirt/ida-f.l.i.r.t.-technology-in-depth)。

本课O2中`grade`和`grade_label`因为内联产生相同32字节前缀，后续4字节CRC也相同，为0x9aaf。二者候选长度为60和72字节，在偏移44分别是0x20和0x28。本库从对象字节和重定位重新计算了这个碰撞，并将两批共10个函数的所有未掩码字节与已链接代码比较，结果一致。这个实验说明“前缀＋CRC”仍可能不足。

正确的匹配过程应是：先验证候选起点、最大读取范围和最短长度；过滤前缀/CRC不符项；按已声明的尾部及引用约束继续过滤；若只剩一个符合全部必要条件的候选，才赋予相应名字。剩余多个、约束无法读取或遇到不支持的重定位时，输出候选集合与unknown。别用`hits[:1]`把歧义消掉；课程原实现正有这种回退，尽管它自己的Skill明确禁止给未消歧的碰撞命名。

还有三个实现细节容易被忽略：

- 引用名称必须同时保留真实引用偏移。本课`grade`引用记录的相对偏移为36、40；输出`.pat`时却枚举成0、1。这样的文本只能叫教学形状，不能声称是完整兼容的FLIRT文件。
- 掩掉整条4字节ARM重定位指令是一种保守简化；其中可能仍含稳定opcode信息。掩码越宽，辨识力通常越弱；未知重定位宽度不能猜。
- CRC16有多种参数，本课采用反射多项式0x8408、初值0xffff、最终取反并交换输出两字节的约定，ASCII `123456789`得到0x6e90。只写“CRC16”不足以复现。短函数、CRC长度上限、尾部短读与格式编码还需独立处理。

把同一来源的测试文件也读完，才能看到它没有验证什么：一处assert表达式带`or True`，必然成功；另一处matcher即便没有唯一winner仍选首个名字。测试数量、作者预期和健壮性证明不能混用。

## 9. 一份能复查的实际报告

可以按下面顺序记录你有权分析的自建程序；这里只给学习流程，不要求运行仓库中的陌生脚本。

1. 固定目标身份、架构/格式、构建参数、工具版本，以及剥离前后是否确为同一次构建。
2. 读装载布局与动态目录，列出依赖、名字/版本、提供者证据、绑定槽和绑定时机；未证明提供者的名字单独保留。
3. 追踪一次调用，逐个记录“调用指令→stub/PLT→槽→解析记录→装载后的含义”，手算每个位移并核文件坐标。
4. 从对象的重定位提出链接决策，写明符号解析假设；与对应链接产物比较，区分引用数量、唯一槽数量和字节大小。
5. 比较剥离前后具体表与代码；有运行观察时，绑定输入和环境，不用单个输出代替等价证明。
6. 分开报告起点候选、范围候选和名称候选。受控实验给集合评分；真实未知目标给证据和不确定性。
7. 为每个冲突、未支持格式、截断读取和不同工具的统计口径保留unknown，并说明能补充哪种证据。

| 自测问题 | 判断依据 |
|---|---|
| PLT32符号在本次输入中有定义，是否一定无PLT？ | 还要核符号身份、绑定与可抢占性，不能只查名字集合 |
| 文件GOT槽为0x206，能否说puts运行在0x206？ | 这是本样本的初始解析路径值，须结合装载偏移与绑定 |
| PE读取起点在节内，但末尾跨过RawData，是否有效？ | 不能作为连续原文件切片；区别零填充、跨区和非法范围 |
| 链字next=2，是否下一个槽在2字节之后？ | 本例format 6 stride=4，应前进8字节 |
| stripped dylib普通符号0条，为何仍有四个导出？ | 查exports trie及统计口径；普通符号表与动态导出不同 |
| O2固定序言只找出1/5，意味着另四个函数被删除？ | 编译器可能生成无该模板的叶函数；结合起点表与代码 |
| 两签名CRC相同，可否选列表第一个？ | 需要额外约束；不能唯一消歧就保持unknown |
