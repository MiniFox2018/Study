# 数据布局与类型恢复

机器指令没有`balance`这样的成员名，却会留下“从某个基址加4的位置读4字节”“每轮地址增加32”“加载出的值又用于访存”等线索。本章学习怎样把这些线索整理为候选数据布局，再用ABI、调用点、DWARF与C++元数据核对；重点是让每个结论都能回答“依据在哪里，还可能有什么解释”。

先读[指令与ABI](02-指令ABI与编译惯用法.md)、[控制流与IR](03-控制流与中间表示.md)，遇到对象文件的重定位和虚表零占位，可回查[文件布局](01-二进制布局与装载地址.md)与[链接装载](07-链接装载与无符号分析.md)。本章固定例来自第41课的x86-64 Linux目标对象；原作者在arm64 macOS运行的结果另行标注。

## 1. 从一次访问出发，不急着给它起类型名

AT&T形式的`addl 0x4(%rax), %ecx`读4字节内存并与ECX相加。对应字节`03 48 04`中，03是ADD的相应opcode，ModRM 0x48拆成`01 001 000`：有8位displacement，目的寄存器ECX，内存基址RAX；最后的04是位移4。

如果数据流已经证明RAX来自被分析对象的起点，这条指令支持“对象基址+4处被当作32位算术操作数读取”。它本身不能证明该处恰好对应一个C成员，不能证明名字为balance、声明类型为int、对象总长32或其余字节全是padding。它也可能访问嵌套子对象、数组中的一个值，或经过强制转换的区域。没有证明RAX的来源，就连“这是第一个参数的字段”也要保留为假设。

本课`bump`的O0对象有完整的来源链：RDI写到`[RBP−8]`，该槽再读入RAX，然后访问`[RAX+4]`。在System V AMD64约定下，RDI承载首个相应参数；调用点与调试类型进一步支持它是account指针。随后`movl %ecx,0x4(%rax)`写回同一4字节区，末尾又读取返回。这样的多处访问比“反编译器显示了int”更适合充当证据。

| 指令观察 | 能记录的事实/候选 | 仍不能恢复的内容 |
|---|---|---|
| movsbl读取偏移0 | 1字节值在此被符号扩展 | 源声明一定是signed char，而非char、显式转换等 |
| movswl读取偏移8 | 2字节值在此被符号扩展 | 成员名、枚举含义、完整对象类型 |
| cvtsi2sdl读取偏移4 | 此处32位有符号整数转为double | 每条访问都使用相同源类型 |
| mulsd读取偏移16 | 此操作按8字节标量浮点解释 | 类型名是否double的某个typedef |
| movq读取偏移24，所得值用于访存 | 在该路径承担地址角色的8字节值 | 原指针声明、const、精确pointee类型及所有输入下地址有效性 |
| cmpb只比较1字节 | 比较宽度为1 | signedness；相等比较不区分有无符号 |

SSE寄存器或16字节搬运也不自动意味着源成员是向量：编译器会用它们复制多个标量或整段初始化数据。解释访存宽度应同时看opcode、操作数位置和数据流，而不是只读助记符最后一个字母。

## 2. ABI布局：先知道对齐规则，再计算padding

在本例System V AMD64普通布局下，char、short、int、double、pointer的size/alignment分别为1/1、2/2、4/4、8/8、8/8。对如下声明，成员按各自对齐放到可用的最低偏移，聚合取最严格成员对齐，总大小再补到该对齐的倍数。

```c
struct account {
    char kind;
    int balance;
    short code;
    double rate;
    const char *label;
};
```

| 成员 | 大小/对齐 | 放置偏移 | 之前新增的padding |
|---|---|---|---|
| kind | 1/1 | 0 | 无 |
| balance | 4/4 | 4 | 1–3，共3字节 |
| code | 2/2 | 8 | 无 |
| rate | 8/8 | 16 | 10–15，共6字节 |
| label | 8/8 | 24 | 无 |

末尾到32，聚合对齐8，故sizeof=32，本例无尾部padding。按double、pointer、int、short、char重排，偏移变成0、8、16、20、22，成员末尾23，再补1字节得到24。重排会改变ABI和持久化/协议布局，不能只因省空间就改公开结构。

下面是只接受明确size/alignment的计算例，不读取二进制，也不猜类型。它适用于这里的普通顺序聚合规则；packed、位域、联合、显式对齐、C++继承均需各自处理。

```python
def layout_members(fields):
    """fields为(name, size, alignment)；输出成员偏移、总大小和对齐。"""
    offset = 0
    aggregate_alignment = 1
    result = []
    for name, size, alignment in fields:
        if size <= 0 or alignment <= 0 or alignment & (alignment - 1):
            raise ValueError("大小须为正；对齐须为正的2次幂")
        offset += (-offset) % alignment
        result.append((name, offset))
        offset += size
        aggregate_alignment = max(aggregate_alignment, alignment)
    offset += (-offset) % aggregate_alignment
    return result, offset, aggregate_alignment
```

不能把alignment无条件取为size。例如`char[5]`大小5但成员对齐通常跟char一致；目标ABI还可能对某些独立数组对象施加额外对齐。已有类型也可能用alignas提高对齐，packed降低通常的填充。只看成员大小反算的“自然对齐通过”是一个适用范围很窄的检查。[System V AMD64数据表示规则](https://gitlab.com/x86-psABIs/x86-64-ABI/-/raw/master/x86-64-ABI/low-level-sys-info.tex)。

从指令推断出的“没有访问的字节”与按已知声明、ABI推导出的padding不是一回事。未访问区域也可能是被其他函数使用的成员；padding内容更不能当作稳定的序列化数据或memcmp等价依据。

## 3. 数组步长：结合循环，还要防止把展开当成大结构

O0的`sum_balances`先将i符号扩展到64位，再执行`shlq $5`，构成`list+32*i`，最后读取偏移4的4字节值。它支持这个访问模式以32字节为元素间隔。O1则使用字节索引：在`[RDI+RDX+4]`读取，RDX每轮加0x20，与移位后的count边界比较。

O2向量化后的循环更容易误读。基址暂存为`list+0xe4`，八次读取对应原list偏移4、36、68、100、132、164、196、228，每轮基址加0x100。如果不分析循环，很容易误报为八个相隔32字节的字段，进而声称结构至少232字节。

在这个已知数组例中，等距32、每轮256=8×32、八次读取的相同角色及标量尾循环共同支持“同一字段的八个元素”。把每次偏移折到候选元素内，字段偏移是4，候选步长32。若以最低偏移l归一化，公式应为`l+(offset−l)%d`；只写后面的取模会丢掉原字段偏移，错误得到0。

但上述数值关系本身还不是通用证明：一个256字节的大结构也可能有八个间隔32的成员，循环还可能跨多个对象。最大公约数只是兼容多处间隔的候选单位；GCD为32不排除实际元素是16字节、代码每次跨两个元素。要进一步核索引语义、循环范围、访问间的依赖、初始化与调用点，必要时保留多个布局。

| 证据来源 | 本例观察 | 应记录的限制 |
|---|---|---|
| scale | i左移5位 | 原索引是否逐元素变化 |
| loop-step | 每轮加32或256 | 是否展开、跨步或访问子区域 |
| offset-delta | 同轮多次读取相隔32 | 是否同字段，而非不同成员 |
| call-site | 同一数组根的+0、+32、+64被传给相关函数 | 需要证明共享根，不能仅看偏移数值相近 |

## 4. 把观察组织成布局候选

一个可复查的分析状态可以保存“root＋常量偏移＋符号索引/步长”，并为每次访问记录：对象身份、函数、指令地址、读/写/读改写、偏移、宽度、操作中的解释及原始字节。跨函数合并前，先说明它们为什么分析同一对象类型：来自同一构造/调用链、相同的已知类型元数据，或明确标注的分析者假设。

本课受控account例可逐步得到：

| 加入的函数 | 新信息 | 还不知道什么 |
|---|---|---|
| bump | 偏移4的4字节访问 | 对象末尾至少到8；总size未知 |
| sum_balances | 数组访问间隔32的证据 | 是否还有未访问成员 |
| tag | 偏移0、8的1/2字节访问 | char声明和字段语义不能仅靠指令唯一确定 |
| projected | 偏移16的8字节浮点使用，并解释偏移4 | 名称和typedef仍未知 |
| label_length | 偏移24的8字节值被用于逐字节访问 | const、精确pointee、最大字符串长度未知 |
| main | O0中同一数组根的多个元素调用 | 优化内联后要重新建立这条联系 |

实现分析器时，不应把“所有参数寄存器先当Pointer”隐藏成已经证明的类型；这只是搜索内存来源的初始假设。顺序扫描也不等于数据流分析：分支汇合需合并状态，回边需收敛，调用会破坏caller-saved值并可能修改内存，部分寄存器写入与重叠栈槽也需正确失效。RSP移动前后的同数值偏移不一定是同一个栈对象。

重叠访问可以来自联合体、位域、宽复制或不同类型的别名，先记录冲突再解释。合并同起点/同宽度的访问时也要保留路径、root和使用方式；“一个8字节值经过LEA”只说明地址算术，并不等同真实解引用。未知不要默认为void，也不要让某次候选pointer标注覆盖所有相反证据。

## 5. DWARF读取的是编译器记录，先认格式和坐标

DWARF用DIE表示类型、成员、函数、变量等实体，通过tag、attributes、父子关系及引用组成图。它能补上指令中缺失的名字和声明关系，但可能缺失、被裁剪、与目标不匹配，优化后的变量还可能仅在部分范围内有位置。使用前应绑定实际对象、构建参数和debug文件身份。

DWARF32/64描述某些长度与偏移字段的编码格式，不是目标CPU位数。本课ELF64对象里是DWARF32，目标address_size仍为8。account的`.debug_info`开头12字节如下：

| 字节 | 解码 | 说明 |
|---|---|---|
| e9 01 00 00 | unit_length=489 | 不含这4字节长度字段，单元结束于493 |
| 05 00 | version=5 | 不能按DWARF4头布局读取 |
| 01 | unit_type=compile | 其他unit_type可能有额外头字段 |
| 08 | address_size=8 | 目标地址宽度 |
| 00 00 00 00 | abbrev offset=0 | 关联本单元的缩写表 |

DIE中的缩写编号选择`.debug_abbrev`声明：tag、是否有children、各attribute的form序列。form决定消耗多少字节，attribute名称不能代替编码。子列表的零编号用于结束children；一个单元结束后，引用基准、表贡献和地址宽度要重新按其上下文处理。[DWARF 5规范，7.5节](https://dwarfstd.org/doc/DWARF5.pdf)。

| 常见form | 本例处理 | 易错点 |
|---|---|---|
| data1/data2/data4/data8 | 固定宽常量 | high_pc若为常量是长度，不能一概当地址 |
| ref4 | 相对本unit起点的DIE引用 | 后续unit不能仍以整个section开头为基准 |
| strx1 | 1字节字符串索引 | 不是直接的.debug_str偏移 |
| addrx | ULEB128地址索引 | 查对应地址表，保留ET_REL的节身份 |
| exprloc | ULEB128长度＋表达式字节 | 解析长度不等于已经执行/理解位置表达式 |
| flag_present | 值为true，不消耗DIE值字节 | 多读1字节会使后续属性全错位 |
| implicit_const | 常量在abbrev里 | 不从.debug_info再取值 |

完整读取器还需处理DWARF64、多个unit、其他form、范围/位置列表、split DWARF、位域、表达式成员位置和循环类型引用；本课程的子集实现没有因此自动覆盖它们。

## 6. 手解一个balance成员和两层索引

本例结构DIE位于`.debug_info+0x195`，成员balance在0x1a3，其9字节是`0d 10 88 01 00 00 00 05 04`。按缩写13的属性顺序解释：

1. 0d选择member缩写。
2. 10是strx1索引16，代表名字，但还不是名字字符串偏移。
3. 88 01 00 00是ref4，指向本unit的0x188，那里是int类型DIE。
4. 00、05分别编码声明文件索引和行号。
5. 04是本例常量成员位置，偏移4。

unit的str_offsets_base为8，故名字索引16要读`.debug_str_offsets`的`8+16×4=72`处。解析该处重定位后，得到0xa5，再到`.debug_str+0xa5`读出`balance`。这个对象的字符串偏移表条目在原文件中都是零占位，真实目标由`.rela.debug_str_offsets`记录提供；不处理它们，就会把所有名字误读到同一字符串。

地址索引同理：`.debug_addr`条目需先结合自己的重定位，再用addr_base、索引和目标address_size取值。本例sum_balances的addrx索引7，对应`.text+0x30`。C++对象的多个代码节都可能从偏移0开始，所以`.text+0`与`.text._ZN4RectC2Eii+0`不能因为数值相同就合并成同一地址。保留“对象＋节＋节内偏移”，待真正链接后再换成VA。

类型关系也要逐层读。label成员引用pointer_type，再引用const_type，最后指向char，表达“指向const char的指针”；若const包在pointer外面，则是“const指针”，不能靠统一在字符串最前面加const来渲染。递归结构如节点指针应保留类型图和循环引用，不无限递归展开。

函数范围同样依form决定：low_pc配常量high_pc时，后者是相对长度；high_pc为地址类时则是终点。`DW_OP_fbreg -8`表示相对该函数frame base的位置，并非永远直接等于RBP−8；本例frame_base恰为DW_OP_reg6 RBP。优化后可能需要按PC选择位置列表，不能把一段捕获中的位置套到整个函数生命周期。

本库自写窄解析从两个O0对象核对了54和78个DIE起点、上述成员与索引，并保留地址的节身份；没有执行原DWARF读取器。字段对照应分别输出无访问证据、宽度不符、操作解释冲突、pointer未证、候选冲突和匹配，不以“5/5粗粒度match”宣称连名字、const和signedness都由机器码恢复。

## 7. C++对象：虚表地址点、RTTI与调用槽

以下采用Itanium C++ ABI在本课x86-64 ELF上的简单单继承例；不是所有平台C++布局的统一图。

```cpp
struct Shape {
    virtual ~Shape() {}
    virtual int area() const = 0;
    virtual const char *name() const { return "shape"; }
};
struct Rect : Shape {
    int w, h;
    Rect(int w_, int h_) : w(w_), h(h_) {}
    int area() const override { return w * h; }
    const char *name() const override { return "rect"; }
};
```

本例Shape大小8，包含一个vptr；Rect大小16，基类子对象在0，w/h在8/12。构造函数先调用基类构造，再把Rect虚表的address point写入对象。address point是对象vptr指向的位置，不必等于虚表符号开头。

`_ZTV4Rect`符号占48字节，原对象中的指针槽是零占位，相关重定位给出内容：

| 相对虚表符号偏移 | 本例内容 | 相对address point的槽 |
|---|---|---|
| 0 | offset-to-top=0 | −2 |
| 8 | _ZTI4Rect | −1，typeinfo |
| 16 | _ZN4RectD2Ev | 0，本构建指向的析构实现 |
| 24 | _ZN4RectD0Ev | 1，deleting destructor |
| 32 | _ZNK4Rect4areaEv | 2，area |
| 40 | _ZNK4Rect4nameEv | 3，name |

本例address point为符号+16。调用序列先从对象偏移0加载vptr，再`callq *0x10(%rax)`，因此相对地址点的槽号是16/8=2。对于Rect动态对象，这个槽引用area；仅从一个未知Shape引用看这段调用，仍需知道对象动态类型，不能直接断定所有路径都调用Rect::area。

析构名字要保留区别：D0是deleting destructor，D1是complete-object destructor，D2是base-object destructor。本例虚表实际重定位到D2，简单无虚基的构建可能共用实现；不能因此把D2的名字定义改成D1。多个变体经demangle都显示相近的`~Rect()`，源码名字相同也不代表ABI入口完全相同。

RTTI中，`_ZTI4Rect`的重定位给出`__si_class_type_info`的虚表地址点、类型名字符串`_ZTS4Rect`和基类`_ZTI5Shape`；这对应本例的单个公有非虚基。复杂继承可能需要额外offset、secondary vtable、this调整和thunk，不能硬编码所有表都从+16开始、所有对象都只有一个偏移0的vptr。[Itanium C++ ABI，2.5、2.9与5.1节](https://itanium-cxx-abi.github.io/cxx-abi/abi.html)。

原Shape表的槽2为`__cxa_pure_virtual`，有助于识别纯虚项；它不是正常构造的合法Shape对象总能被直接调用的证明。构造/析构阶段的虚调用还有自身的规则，不能把“列出的所有虚表槽”当作同一调用点现实可达目标的全集。

### 名字编码能告诉你什么

`_ZNK4Rect4areaEv`可拆为：_Z前缀，N开始嵌套名字，K表示const成员函数，4Rect与4area是长度前缀名字，E结束，v表示空形参列表。`_Z8describeRK5Shapei`表示describe(Shape const&, int)。常见特殊前缀_ZTV、_ZTI、_ZTS分别用于虚表、typeinfo与typeinfo名字。

demangle帮助读名字，但不是源码恢复器；重载、模板、替换编码和构造/析构变体都需ABI规则，且并非所有函数编码都保存返回类型。只支持本课19个名字的手写解析器，不能当作通用或可安全接收任意损坏输入的demangler。Microsoft C++使用不同规则，不把Itanium的_Z命名、RTTI和槽布局移植到其对象上。

## 8. 优化和工具输出会怎样误导你

O1的shapes对象仍有describe中的间接槽调用，但本地main构造Rect后的name/area路径已内联，main最后直接准备`rect`和24交给printf，虚表没有被发射到该对象。因此“此文件无_ZTV符号”不能推出“类没有虚函数”，也不能推出整个程序没有任何虚表。

account例也展示优化会改变可用证据：O0有跨函数传参，O1在main保留栈上初始化与内联访问，O2进一步把结果折成常量。若只能看到O2的main，不能为了凑全结构而捏造已被消去的每个成员访问。

本轮发现来源工具对照并非完全受控：capture脚本的Ghidra/rizin有DWARF版本用O0-g，无DWARF版本用O1。两者既改debug也改优化，不能将所有伪代码差别归因于类型表。本库另核O1-g与O1的完整.text字节确实相同，而O0-g与O1不同；但原有Ghidra捕获不是前一对，不能替它补造一次未发生的对照运行。

原捕获仍有明确价值：Ghidra导入DWARF后能显示account/成员，某些const限定却没保留；没有类型时，它可能把相同偏移访问渲染成整数地址、char*或char**。LLDB的类型查询、pyelftools的成员列表与DWARF可相互核字段；它们是在读同一编译器记录，不是完全独立产生了相同源类型。radare2捕获出现invalid memory且类型列表未显示account，rizin也有映射警告，不能剪掉诊断只保留好看的片段。

手动给类型能改善可读性，也能制造错误的确定感。应先把候选结构应用到对应参数，再核所有读写、下游调用与边界；若新类型使另一路径不一致，记录冲突并撤回/细化假设。没有发生的新工具运行不要写成已复现，商业版本功能和价格也不从2026-10-14捕获推到今天。

## 9. 自己完成一次类型分析

建议先用已有受控例手算，再对自己有权分析的程序按同样字段记录；本库不要求安装或运行来源脚本。

1. 固定对象与构建身份，核反汇编字节确实来自这份文件；保留节坐标。
2. 从一个root和一条访问开始，记录宽度、偏移、数据流与该操作的解释，未知名字用中性字段名。
3. 收集更多访问和调用点，先证明合并对象/类型的关系，再合并字段；不要自动把每个函数首参视为同一结构。
4. 联合分析循环步长、索引尺度、展开与尾循环，给出候选元素间隔及反例，不提前写死sizeof。
5. 按目标ABI检查候选布局，区别未访问空间与已证明padding；packed、位域、union或显式对齐单列。
6. 有匹配debug构建时，按unit/form/重定位读取DWARF，逐成员对照；检查名字、const、signedness与大小的不同证据来源。
7. C++再核构造写入、虚表地址点、RTTI、槽调用和优化；把间接调用目标保留为有条件的候选。
8. 输出不确定项和下一条可减少不确定性的证据，例如同优化debug对照、更多调用点、结构初始化或合法输入的运行观察。

| 练习 | 应有的判断 |
|---|---|
| 只见偏移4的4字节访问，能否给sizeof=8？ | 只能给已观察范围下界；可能还有更多成员 |
| 将账户成员重排，计算大小 | 0/8/16/20/22，末尾23补1得到24；不是ABI兼容修改 |
| O2八处偏移与步长吻合，是否必然展开？ | 是本例有其他证据支持的解释；仍要排除多个字段/跨步访问 |
| 表中全零名字索引为何仍能恢复名字？ | 先应用对应debug重定位，再读strx间接表 |
| ELF64是否意味着DWARF64？ | 本例DWARF32、目标地址宽8，两者分开 |
| 虚调用偏移0x10为何是槽2而非槽4？ | 基准是vptr的address point，不是虚表符号开头 |
| 有-g的伪代码更像源码，是否证明全因debug？ | 先核优化与代码相同；本课捕获对并不满足 |
| 候选全部粗粒度匹配，是否恢复了完整源类型？ | 名字、const、sign与未访问成员还需分别核 |

类型恢复的进一步方法可理解为三条路线：从操作生成约束并求解，处理子类型/多态/递归类型；将多个兼容布局作为候选，用概率排序；用学习模型补名字和类型，再以实际访问与元数据验证。模型给出的可读名称只是一种候选，不能替代这些约束。原课研究百分比属于各论文数据集和评价口径，本章不把它们写成当前通用准确率。

## 从优化SSA恢复一个可解释的签名

小型反编译器可以在简化后收集仍使用的版本0寄存器：在约定的System V整数参数序列rdi、rsi、rdx、rcx、r8、r9中，最高被读位置给出所需的最少参数槽位。例如只读esi时，生成一个带未使用param_1的二参数候选，不能改成“esi就是第一参数”；也不能把补出的rdi在报告中写成实际读过。

这仍没有恢复唯一源码原型。未使用的尾参可能被优化掉，隐藏返回指针会占槽，浮点/聚合参数遵循其他分类，手写入口也可能采用自定义约定。r10等非本约定参数寄存器的入口读应成为未定义/待解释项，不能为凑声明自动加为普通参数。没有写rax就猜void也需调用者证据，返回值可能从其他载体传递。

类型推断应保留“访问形状→约束→候选”的过程：

| 优化IR中的使用 | 可以提出的候选 | 必须另核 |
|---|---|---|
| load32(base+index×4) | 在该访问点按4字节元素寻址 | base的来源、index范围、元素符号性与数组长度 |
| load/store32(base)、load/store32(base+4) | 根对象上两个32位访问区 | 是否结构、对象身份、重叠访问、隐藏成员与对齐 |
| 算术右移、符号扩展、signed除法 | 本次操作按有符号解释 | 是否显式转换、其他用途是否相反，不能只改全局类型 |
| 无符号比较守卫查表 | 该比较采用无符号关系 | 可能是将负数一起排除的惯用法，不证明源参数unsigned |
| unsigned右移或除法 | 操作的无符号解释 | C打印时的整数提升、转换位宽与返回值类型 |

record示例只访问根+0和根+4，候选可命名为field_0/field_4，保留两个32位字段。已知fixture源码的meter还有spare位于+8，普通本例布局总12字节；当前函数不访问它，所以恢复出的两字段、8字节候选不能称为完整原结构。名字reads/total和const也不是从偏移自动推出来的。

同一offset若先有8位访问、后有32位访问，应保留两条证据及可能重叠，不能用字典后写的宽度覆盖前一条。不同函数合并前先核共享root；同一web的指针和整数证据冲突、多个pointee宽度、union或packed布局，都应保候选/冲突而非靠遍历顺序决定类型。

输出C类型还需数据模型：这里long按LP64为64位，不能移植到LLP64；char的符号性不能靠8位宽度唯一决定。char/short返回的声明与报告宽度也要一致，不能声明short却统一记录32位返回。双宽除法的128位中间值需要实际类型/多精度表示，字典只支持8/16/32/64时应明确拒绝，不能崩溃或悄悄截成long。

自检时分别回答：一个寄存器读是否足以证明完整参数数目？为什么spare会丢失？`cmp; ja`是否足以把所有运算改成unsigned？参考答案分别是：只给受限模型的最低槽位证据；没有访问的成员不可见；比较只约束这次解释，其他操作和调用仍需核。
