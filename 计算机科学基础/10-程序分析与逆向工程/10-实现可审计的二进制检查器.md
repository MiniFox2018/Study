# 实现可审计的二进制检查器

本章把前面的布局、符号和链接知识组成一个静态分析项目：输入自己构建的程序文件，输出格式、区域、符号、链接关系、字符串、函数起点与构建差分。检查器读取目标的字节；它不需要执行目标，报告中也不能把静态推断写成运行观察。

先读[文件布局](01-二进制布局与装载地址.md)、[链接与无符号分析](07-链接装载与无符号分析.md)。下面采用六阶段流程，既说明如何实现，也说明每个结果应当保留哪些条件。来源参考实现和测试只在本轮静读；具体样本数字由本库独立的数据解析核对，未运行原 CLI 或评分器。

## 1. 先设计模块之间传递什么

把读文件、解释格式、分析内容和输出展示分开。底层函数返回结构化值或带位置的解析错误，CLI 统一处理输入输出；这样同一份解析结果可以供 JSON、HTML 和差分使用。

| 模块 | 输入到输出 | 主要责任 |
|---|---|---|
| formats | 原字节 → Header | 识别格式、位宽/字节序、架构、文件类型与头表位置 |
| layout | 字节与 Header → Region 列表 | 文件区域、内存区域、权限声明、文件支持长度 |
| symbols | 区域与符号表 → Symbol 列表 | 字符串表、符号身份、绑定、定义状态、可选反修饰 |
| linkage | 前述结构 → Relocation / Import / Export / Fixup | 保存索引关系并解析引用，不执行装载 |
| discovery | 字节与区域 → 字符串、入口候选及评分 | 各方法分别保留来源、范围和误报 |
| report | 分析结果 → 版本化报告 / 展示 / Diff | 校验合同、解释证据、生成安全输出 |

工程中可以用一个 ParsedImage 保存 Header、按索引组织的节、原符号表和已解析命令，避免每个函数反复解析同一文件。保留原始索引很重要：节名可能重复，符号名可能同名，COFF 的辅助符号记录也占索引。

一个区域至少有两套长度：逻辑内存长度与文件实际支持长度。一个地址至少带目标身份和地址空间；ET_REL 中还要带节身份。只用整数 0 表示“某函数起点”，会把不同代码节中的入口合在一起。

建议将状态分为“已读取的字段”“按规则推导的候选”“不支持或未知”。例如发现某符号位于代码节可以提出函数候选；保留其符号类型和来源，之后再调查是否真实入口。统一输出形状不等于所有格式已经拥有同样完整的信息。

## 2. 第一阶段：识别格式并验证头表

文件扩展名只作显示信息。识别按字节进行，但“识别到格式”和“完整解析头部”是两层检查。

| 输入 | 识别入口 | 随后的必要验证 |
|---|---|---|
| ELF64 | 7f 45 4c 46；CLASS=2、DATA=1 | 版本、头长、表偏移/数量/项宽、节字符串表索引；扩展索引明确支持或拒绝 |
| COFF object | 没有统一 magic；机器字段、零 optional-header 长度等组合 | 整个节表、符号表及字符串表范围；保持机器类型与后续重定位表一致 |
| PE32+ | MZ → 0x3c 的 e_lfanew → PE 签名 | optional magic=0x20b、完整 optional-header、目录数量和节表；目录类型区分 RVA 与文件偏移 |
| Mach-O64 | 小端字 cf fa ed fe | 32 字节头、ncmds/sizeofcmds、每命令通用长度及该命令具体最小长度 |

所有读取都先检查完整区间：起点非负，长度非负，长度不超过剩余字节。分成“起点能映射”再直接切后面的表，会允许读取跨过原区域。Python 切片越界不报错，因此不能把短切片当合法表。

以本项目固定 arm64 O2 样本为例，头中 ncmds=18、sizeofcmds=1448，命令范围是文件 [32,1480)。循环中逐条核 cmdsize≥8、按要求对齐、命令末尾不超过 1480，结束时还要核累计长度与声明一致。随后对 LC_SEGMENT_64 再核 72+80×nsects 字节，不能仅凭通用的 8 字节命令头认定它完整。

LC_MAIN 的 entryoff 要通过对应的文件到装载映射解释。本例 __TEXT.fileoff=0，入口为 0x100000000+0x5e8；一般情况要保留段文件偏移与运行时 slide，不能把“加固定基址”写成所有文件的入口公式。

实现还应维护“支持矩阵”。参考代码的头部识别接受 x86 COFF，但重定位分派在 arm64 之外选 AMD64 表；这说明头部支持不自动等于后续分析支持。遇到未实现的机器/重定位组合，输出不支持比套用另一种架构的名称可靠。

本阶段交付 Header、命令清单和错误位置。至少检查短文件、错误 e_lfanew、节表越界、零 cmdsize、具体命令过短，以及不支持的变体。没有实现 ELF32、PE32、通用 Mach-O 容器，不表示这些格式失效。

## 3. 第二阶段：区域、权限与文件熵

先从格式字段生成区域，再对文件支持的那部分计算统计。ELF 的 NOBITS、Mach-O zerofill 等区域有内存长度，但没有同等长度的文件字节；从它们的 offset 再切 size，会误读后面的其他数据。

权限字段也要解释来源：ELF program header 的 PF_R/PF_W/PF_X 是装载段声明；节的 SHF_ALLOC/WRITE/EXECINSTR 是链接属性。Mach-O 的段有 initprot/maxprot，普通节继承相关段；尚未装载的对象文件按节属性作提示，不能当实际进程权限。PE/COFF 使用各自的 MEM_READ/WRITE/EXECUTE 位。

字节熵描述一个文件区域的字节频率。设区域长 N，字节值 b 出现 n_b 次，p_b=n_b/N，则：

$$H=-\sum_{b:n_b>0}p_b\log_2 p_b.$$

单位为 bits/byte。最多 256 种字节值，因此上界为 8；非空有限样本还受不同取值数和 N 的限制。它不考虑顺序：重新排列相同字节不会改变 H。

下面是本库独立编写的完整 Python 小例，只统计传入的 bytes；空输入约定为 0：

```python
from collections import Counter
from math import log2

def byte_entropy(raw: bytes) -> float:
    if not raw:
        return 0.0
    total = len(raw)
    probabilities = (count / total for count in Counter(raw).values())
    return -sum(p * log2(p) for p in probabilities)

print(round(byte_entropy(b"tally report v3"), 4))  # 3.3736
```

这个 15 字节例子中，t、l、r、空格各出现 2 次，另七种字节各一次，所以：

$$H=4\frac{2}{15}\log_2\frac{15}{2}+7\frac{1}{15}\log_2 15\approx3.3736.$$

全零区域 H=0，aabb 的 H=1，全部 256 个字节各一次 H=8。固定 O2 样本的 768 字节 __text 得到 5.8595，而整个 50264 字节文件只有约 0.522，大量零填充会稀释全文件统计。比较时必须写清区域、分母和窗口长度。

高熵可以提示继续查看压缩、加密或其他均匀数据，也可能来自代码与普通数据；低熵也不能排除敏感内容。不能把某个阈值当“是否加密”的充分判据。原交互实验用理想概率分布计算 H，没有保证这些概率能由指定长度的整数频次实现，应当把它当公式练习。

本阶段交付区域表，至少保存 offset、内存 size、file_size、权限来源与 H。相同名字的节用索引区分；重叠区域应报告歧义，不能因为“选了最小区域”就将其变成唯一真实归属。

## 4. 第三阶段：符号索引与名字反修饰

符号解析的关键是先找对记录与字符串表，再解释名字。三种常用布局如下：

| 记录 | 大小 | 名字与关联索引 |
|---|---:|---|
| Elf64_Sym | 24 字节 | st_name 指向该符号表 sh_link 指定的字符串表；st_shndx 指向节或特殊索引 |
| COFF symbol | 18 字节 | 内联短名或字符串表偏移；后面可能跟辅助记录 |
| Mach-O nlist_64 | 16 字节 | n_strx 指向 LC_SYMTAB 的字符串表；n_sect 为节序号 |

以 ELF 的 info=0x12 为例，高四位 1 表示 global，低四位 2 表示 function。数值 value 在可重定位对象中通常是节内偏移，不能直接拿来与链接后 VA 比较。ABS、COMMON、未定义和扩展节索引应分别处理。

COFF 解析每个主记录后，跳过其辅助数量，同时保留原始记录号；重定位引用的是包括辅助记录在内的表索引。不能把压缩后的“第几个可见符号”回填到原重定位。section number 是有符号字段，-1、-2 与未定义 0 有不同含义。

读取 C 字符串时，同时验证起点与表末边界，要求 NUL 在表内；保留原字节或明确 UTF-8 替换的展示性质。名字被替换解码后，不宜再作为无损身份键。PE 文件也可能带 COFF 符号表，不能从某个小 PE 样本的空表推导所有 PE 都没有符号表。

Itanium 反修饰适合用递归下降理解。例如 _ZN5tally5resetEPNS_7CounterE：

1. _Z 是编码入口，N…E 组织嵌套名字 tally::reset。
2. 长度前缀 5、7 指定后续名字的编码长度；工程实现按规定的字节口径读取。
3. P 表示指针；后面的 N S_ 7Counter E 通过已有替换取得 tally::Counter。
4. S_、S0_ 等使用替换表，并非任意出现相同字符串就能随意重排索引。
5. 参数最终是 tally::Counter*，函数显示为 tally::reset(tally::Counter*)。

保留限定符的类型层级：P K i 可显示 int const*，K P i 则是 int* const。函数的名字、参数类型和返回类型也不是同一套信息，普通非模板函数名通常不直接编码返回类型。

子集实现可以明确不支持模板、数组、某些运算符等，并保留原名字。构造/析构变体按 ABI 语法处理：D0/D1/D2 分别涉及 deleting、complete、base destructor，不能照抄一个接受 D3 而漏 D0 的简化枚举当完整语法。还要限制递归深度、输入长度和数字字段；“未知返回 None”不等实现天然不会抛出资源或递归异常。

## 5. 第四阶段：把重定位、导入与修复槽连起来

重定位记录至少保留目标节身份、节内位置、类型、符号表索引、符号和显式/隐式加数。ELF RELA 的记录是 24 字节，r_info 高 32 位给符号索引，低 32 位给类型；REL 没有独立加数字段。COFF 的 10 字节记录也没有独立加数，不能因此假定待修补字段里的隐式加数总是 0。

例如 tally 的一条 R_X86_64_PC32 引用 tally_counter，记录位置 0x15，加数 -4。先核它属于哪份符号表和待修补节，再解释 S+A-P；记录位置不是函数调用地址，“指向代码符号”也不必然表示 call。

### PE：名字表、地址表和实际槽位

固定小 PE 的导入目录位于 RVA 0x2000，.rdata 将其映射到文件 0x400。一个 descriptor 给出 lookup table、DLL 名字与 IAT 的 RVA。按每个 lookup 项判断导入名/ordinal，再将第 i 个 IAT 槽位写成 ImageBase+IAT_RVA+8i：

| 导入 | 本例 IAT 槽位 |
|---|---|
| GetStdHandle | 0x140002048 |
| WriteConsoleA | 0x140002050 |
| ExitProcess | 0x140002058 |

它们是装载器待填的槽位，不是当前磁盘里已经存在的真实系统函数地址。读取整份 descriptor、thunk 或名字时核完整文件支持范围，并要求终止条件落在其声明边界内。一个起点能从 RVA 转到 offset，不保证后面 20 字节也合法。

导出解析还要覆盖 ordinal-only 项、一个地址的多个名字、EAT 中的空项，以及指向 export directory 范围内的 forwarder。只遍历名字表可以遗漏没有名字的导出；以“名字数不能超过地址数”拒绝文件，也可能错误拒绝别名。PE 基址重定位则是另一张表，按块大小和项宽检查，不与导入绑定混为一谈。

### Mach-O：64 位链字不是普通指针

对这里的 pointer format 6，0x8010000000000003 可以分成 bind=1、ordinal=3、next=2。next 的单位是 4 字节，因此下一位置加 8；本例导入项 3 对应 _puts。它不表示地址 0x8010000000000003。

无 bind 的链字则含 target 和 high8 等字段，按 pointer format 区分地址/偏移及基址与 slide。保留原 raw word 为 64 位整数；对 JavaScript 消费者可用十六进制字符串或明确 BigInt 转换，不能让 JSON 数值经过 Number 后悄悄丢精度。

读取链时依次核 fixups blob、starts 表、具体 segment 结构长度、页起点、每次完整 8 字节位置、segment 文件支持范围、import ordinal 和终止条件。只保证“还在同一页”不足以证明仍在原 segment 的文件字节里。特殊库 ordinal 与普通库序号也应按具体格式解码，并按所有相关 dylib load command 的原顺序解析。

加数有不同字段合同：此 64 位 bind word 的 8 位 addend 是 0～255；import format 2 的表加数是 int32_t；官方 format 3 表项声明 uint64_t。记录各字段原值，再说明如何组合，不能将一个字段的符号规则套到另一个字段。

导出 trie 需要保存前缀、子节点偏移与终结内容边界。当前 regular 导出可从基址加偏移得到地址；reexport、absolute、resolver 等标志应分别实现或标成未支持。应防循环，也要解释不可达旧节点：字符串扫描看到旧文本，不表示从 trie 根还能到达该导出。

## 6. 第五阶段：字符串、函数起点与评价

字符串输出应带 offset、编码与区域。ASCII 可打印扫描和“可打印 ASCII 字节后跟零”的 UTF-16LE 子集，是两种受限提取；后者不等完整 Unicode UTF-16 解析。还要核整个字符串跨度，避免只按首字节归属一个节。字符串位于 __cstring 不足以证明程序会打印它。

函数起点的各方法先分别输出，不急着合并：

| 方法 | 核心依据 | 要保留的限制 |
|---|---|---|
| symbols | 定义符号与代码节 | 局部标签/缺失符号/同名节，符号真值也可能不完整 |
| LC_FUNCTION_STARTS | 有界 ULEB128 增量 | 表项、范围、对齐和代码坐标仍需检查 |
| prologue | 架构相关前导模式 | 可省略、可出现在函数内部；命中不是证明 |
| direct call target | 解码后的直接 call/BL 目标 | 可内联、无调用入口、间接调用；字节模式扫描可能误认 |
| entry | 头部/装载映射的入口 | 一般只提供一个入口，不是完整函数清单 |

x86 的 E8 可以出现在其他指令立即数中，所以从任意字节看到 E8，再算一个落在代码节的目标，并不足以确认调用边。arm64 固定四字节扫描也要考虑代码节内数据。合并多个方法会增加覆盖，也可能把误报带进并集；排除一种启发式不意味着剩余方法没有误报。

用同一构建、相同布局且有明确来源的入口集合 T 作参考，检测集合 F 去重后：

$$precision=\frac{|F\cap T|}{|F|},\qquad recall=\frac{|F\cap T|}{|T|}.$$

空分母需要约定或报不适用。本项目约定 F 为空时 precision=0，T 为空时 recall=1；这个数值约定不证明检测器具有真实覆盖能力。

本库只读固定样本的表和原指令字，核得：

| 固定 O2 样本 | starts 表 | 代码内直接 BL 目标 | 序言命中 |
|---|---:|---:|---:|
| tally | 6 | 5 | 1 |
| meter | 6 | 4 | 1 |

tally 的直接调用法 recall 为 5/6，meter 则为 4/6；不能把前一个样本的计数当通用规则。meter 的 clamp 仍有独立函数起点，但不在所核代码的直接 BL 目标集合内。表、目标与序言各自描述不同证据。

报告误报与漏报的具体地址，比只报两个比例更有用。若真值来自另一个优化级、另一个链接基址或一份不完整符号表，先修正对齐与范围，再谈 precision/recall。

## 7. 第六阶段：报告、字节图和构建差分

JSON 报告先带 schema、文件大小与摘要，再保存 Header、区域、符号、链接、字符串、起点及各自状态。验证分三个层次：字段/类型和版本，数值/范围与索引，跨字段的引用与计数一致性。一个浅层 validate 返回空列表，不能替代后两层。

字节图是一种粗粒度投影。文件长 N、分 K 个 cell，第 i 格范围为 [⌊iN/K⌋,⌊(i+1)N/K⌋)。用 min(K,N) 可保证非空文件的每格至少一字节；空文件单独处理。区域标签可以取最大重叠节，其次段、未映射；并保留重叠长度，不能把整格都解释为这个节。

例如 N=50264、K=128：

| 格 | 文件范围 | 解释 |
|---|---|---|
| 0 | [0,392) | 位于首节前，显示头部 |
| 3 | [1178,1570) | 与 1512 开始的 __text 只重叠 58 字节，仍可因最大重叠被着成代码色 |
| 127 | [49871,50264) | 覆盖文件末尾的部分 __LINKEDIT |

K 格应该无缝且无重复地覆盖 [0,N)。图的明暗可表达 H，但不能用颜色替代原范围和字节证据。

HTML 将文件名、节名、符号、字符串等输入按输出上下文转义，并避免把目标内容当 HTML、脚本或 CSS 执行。参考程序对多数目标文本做了 escape，但部分自生成的 file.size/sha256 直接插入；自产整数和摘要有明确类型，接受外来报告时则还需重新校验和转义，不能照称“任意报告所有字段都安全”。

差分的匹配键决定它看得见什么：

| 比较内容 | 合适的身份与口径 | 简化集合差分会漏什么 |
|---|---|---|
| section | 文件格式、原节索引/稳定映射、segment+name、大小及内容摘要 | 同名多节、大小不变但内容或熵改变 |
| symbol | 表、绑定、节身份、名字及地址/偏移 | 同名符号覆盖、只移动未改名、ET_REL 坐标混淆 |
| import/export | 库、名字/ordinal、槽位/目标、forwarder | 名字相同但换库或换地址 |
| string | 编码、内容、跨度、出现位置 | 去重后丢掉的重复文本与位置变化 |
| 整个文件 | 重新计算的完整摘要 | 只信外来报告中的 sha256 |

固定 tally 的 O0→O2 代码节从848缩到768，__unwind_info从104到96；这能指引后续检查。全部差分列表为空，却未核完整摘要时，不能宣称字节相同；文本或区域变化本身也不等行为变化，继续用[差分与等价边界](06-差分重建与符号执行.md)的方法调查。

## 8. 按六阶段实现与自检

每一阶段先使用小而明确的样本，再加入畸形输入和第二个自有程序。不要只围绕固定 tally 的位置写常量。

1. 头部：给出支持矩阵、完整头表范围、具体错误位置；修改表偏移或 cmdsize，应在使用该表之前失败。
2. 区域：分别核文件与内存长度、零填充、重叠归属、权限来源；用全零、均匀字节和已知短串检查熵。
3. 符号：以原索引对照记录；构造越界名字、缺 NUL、COFF 辅助记录、同名节及未支持的反修饰输入。
4. 链接：把引用字段、表索引、目标和槽位串成关系；加入页内但越过 segment、无终止 descriptor、ordinal-only/别名导出等情形。
5. 起点：分方法列地址、真值来源、误报与漏报；加入函数内部模式与优化内联，检验并集的局限。
6. 报告：核 schema 与跨字段，验证字节图分区，处理目标文本，解释差分键；读写与发布失败应保留具体状态。

可先用本库已有小程序或自己的样本构建对象文件、未剥离可执行文件及对应剥离副本，记录编译器与参数；当前练习不依赖作者原始二进制的固定摘要。换构建后重新建立预期值，不把不同产物硬对齐到上表地址。

最后回答三个问题：高熵是否证明加密？参考答案是否定的；还需内容与用途证据。全部方法并集是否真值？不是，需各方法的误报与覆盖。91个测试方法存在、作者演示通过，是否代表本库运行通过或自己完成项目？不是，方法数、作者观察、本库静核与个人实践分别记录。
