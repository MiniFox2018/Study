# Docker沙箱与Agent工作台

先修：[核心生命周期](01-核心模型与生命周期.md)、[数据与网络](03-数据-网络-仓库.md)、[AI容器与硬件边界](09-AI容器与硬件运行边界.md)。本章解决的问题是：让Agent能使用文件、命令和服务，同时知道它到底在哪里运行、能影响哪里、怎样判断任务完成。

贯穿案例是“让Agent检查一个小代码仓库，提出修改并返回可审阅产物”。模型回答、工具运行、隔离措施、文件产物与人审决定必须分别有证据，不能因为界面显示completed就合并成一个成功。

**第一次读法**：先读1–8节，能为一次任务填出执行位置、权限、产物与失败证据；Kit构建与能力组合再读9–13；模型/MCP接线读14；有效Agent配置、预算、工具门与声明环境读15–18。重复评测与未完成分母回到[评测第33节](../../LLM%20工程实践/06-评测与实验管理.md)，不要求初读同时配置全部组件。

## 1. 先分清四个角色

| 角色 | 负责什么 | 不单独保证什么 |
|---|---|---|
| Docker容器/Engine | 镜像、进程、网络、卷与运行时资源 | 任意Agent工具必在这个容器里；镜像固定一切外部状态 |
| Docker Sandboxes的sbx | 创建/管理沙箱，连接daemon、microVM、工作区、代理及能力配置 | 模型理解了任务，或获准做任何外部动作 |
| Docker Agent运行框架 | 读取Agent配置，管理模型、工具、会话和委派 | 单凭框架名自动隔离宿主、建立有效批准或保证效果正确 |
| 模型后端 | 处理模型请求，例如宿主DMR或远端模型服务 | 请求内的文件/命令已执行，或模型输出已经验收 |

普通Linux容器共享其Linux宿主内核。macOS的Docker Desktop通常先有Linux虚拟机承载容器；这与“每个沙箱有独立guest内核和私有Engine”是不同层次。microVM增加了内核边界，guest中有root/sudo也不直接等于宿主root；真正边界仍取决于VMM及明确开放的文件、网络和宿主服务。

`docker-agent`独立二进制与`docker agent`插件可能不是同一版本；命令都叫agent不意味着行为相同。来源固定案例中独立版为1.149.0，Desktop内插件为1.144.0，旧插件资料还有1.32.4；这些是作者2026-10-08的版本证据，不是本章推荐的当前安装组合。

`sbx run docker-agent`与`docker-agent run --sandbox`也有不同引导路径和模板来源。后者先在宿主处理配置，再进入沙箱；要分别核宿主引导器和VM内运行器。来源的一次`--sandbox`运行因挂载文件系统上的SQLite只读错误1032，在模型调用前退出；另在guest临时目录成功回答是另一组条件，不能改称原路径端到端通过。

## 2. 把执行位置画在资源账本上

不必先画复杂架构图，先给每个对象写位置：

| 对象 | 常见位置 | 检查时问什么 |
|---|---|---|
| 原Git仓库、宿主配置与凭据存储 | 宿主 | 是否会被CLI引导器、hooks或host MCP直接读写？ |
| sandboxd与控制socket | 宿主 | 谁可调用？操作是否影响其它沙箱？ |
| Agent进程、guest文件与私有Engine | microVM/guest | 当前用户、工作目录、模型配置和实际Docker context是什么？ |
| 工作区挂载或私有clone | 跨边界/guest | 读写模式、可见范围、未跟踪文件和同步方向是什么？ |
| 出口代理、凭据替换、MCP网关 | 依部署可在宿主/托管端 | 它们在哪里执行策略，谁拿真实凭据？ |
| 模型与外部工具服务 | 宿主、容器、远端均可能 | 从实际调用者能否连接，有何权限、留存与费用？ |

同一个`docker ps`会查询当前配置选中的Engine；不能因为在终端里运行docker，就认定查的是宿主或guest。相同的绝对文件路径，在宿主、共享挂载、guest私有文件系统里也可能是不同对象。

例如宿主DMR监听12434，guest调用模型必须能经实际网络路径到达它。`host.docker.internal`这类名字、允许该地址的策略、服务自身监听和认证是不同检查。模型列表显示一个default，只表明配置选择；来源doctor在DMR不可达时仍能列default，说明“列出模型”不等于“可生成”。

## 3. 生命周期：创建、停止和删除的对象不同

下面是来源sbx0.47.0的教学语义；具体参数在实际使用版本中重新核对，本文没有执行这些操作。

| 动作 | 主要作用 | 容易漏掉的条件 |
|---|---|---|
| run | 按路径/配置创建或连接，并进入交互运行 | 可能隐式创建；默认工作区与create不一定相同 |
| create | 创建沙箱而不进入交互 | 不给工作区路径时可没有宿主挂载；创建时能力/端口等与每次连接环境不同 |
| exec | 在既有沙箱内运行程序 | 可能唤醒停止的VM，不是纯读取元数据 |
| stop | 停止运行并保留相应本地状态 | 不是撤销代码改动、网络写入或费用 |
| rm | 删除指定沙箱及受其管理的状态 | 宿主工作区、外部动作或先前取回的Git引用不一定被撤销 |
| template save/load | 保存/载入可复用的运行文件系统产物 | 不等于完整VM备份或所有挂载/Engine数据/运行进程迁移 |

例：Agent已把宿主共享文件`result.txt`改错，随后stop/rm通常不会使原文件自动恢复。恢复应依版本控制或备份，外部系统副作用另行对账。两个不同沙箱如果共享同一宿主工作区，文件并发冲突仍然存在。

诊断或settings读取也可能触发daemon启动；帮助文本的收集也可能尝试网络。源码中函数名叫“doctor”“check”或“help”不是零I/O/零副作用证明。首次学习先理解观察范围，再选择当前确需的诊断。

清理按明确拥有的对象身份进行。来源capture脚本有全局prune行为，不能因为README说“只清本项目”就默认安全；检查目标范围、共享状态和唯一数据。广泛reset、全局prune或清凭据不是一般学习笔记里的默认修复步骤。

## 4. 工作区有三种不同选择

### 4.1 直接读写挂载

优点是Agent立刻看到真实代码、修改可直接在宿主审阅；代价是权限也真实生效。它可能改源码、`.git`、CI配置、依赖脚本或其它可见文件。一次Git diff不能说明没读过秘密、没触发外部请求或没修改非Git管理内容。

### 4.2 只读挂载

能防止沿这条挂载写回，但不防读取或通过允许的出口披露内容；也不限制另一个host MCP拥有的文件权限。要保护secret，首先减少可见范围，不能只把整个含`.env`的目录改为只读就结束。

### 4.3 私有clone或无宿主挂载

私有clone让Agent在guest文件系统修改，产物取回后再审阅；mountless适合不需原仓库的独立工作。来源clone还将宿主源目录只读暴露于`/run/sandbox/source`，所以未跟踪敏感文件仍可能被读到。宿主CLI为建立取回路径还会改Git remote/refspec等配置，不能笼统称宿主完全没有变化。

取回commit只证明拿到了一个Git产物；仍须检查差异、来源、依赖、生成脚本和验证结果。后续在宿主执行构建或hooks是另一条信任边界。

**实践判断**：检查代码时只需某个子目录，应选择满足任务的最小可见输入；要让模型提出补丁而不直接改真实仓库，可用私有工作副本再审阅合并。若必须直接改共享目录，先说明哪些路径可改、怎样防并发覆盖和怎样恢复。

## 5. 网络、端口与秘密不是一把总开关

### 5.1 域名允许不等于数据使用获准

网络控制可以限制目标域名、端口和协议，更细能力还可能限制HTTP方法/路径。允许访问某个API，不代表任何正文或任意操作都已获准；向允许域名POST敏感内容仍可能泄露。

规则有平台/组织、全局、VM或kit等不同作用范围。应记录当前有效规则、来源与版本，再解释一次允许/拒绝；不要用“deny永远覆盖任何allow”一句话代替具体合并语义。来源存在hostname、CIDR、协议、组织授权上限等特殊条件，简化模型不能充当实际authorizer。

静态policy check表示给定参数的规则判断，不等于真实DNS、TLS、认证和应用请求成功。代理CONNECT200仅表示隧道建立；目标HTTP403与工具退出0可以同时发生，例如调用方没有把HTTP错误转成非零退出。检查传输、应用状态与任务结果三层。

### 5.2 端口是另一条入口

guest服务监听、宿主端口映射和访问者认证分别核。回环绑定减少外部暴露，却不等于服务有身份验证；同机其它进程仍可能访问。来源默认tcp4与显式双栈tcp不同，云端公开URL又是另一入口；不要把本地端口实验的结果推广成云端访问策略。

### 5.3 真实凭据可留在外部，能力仍能被滥用

代理凭据方案可以让guest持占位值，实际请求到指定目标时由外部代理替换。它减少直接把密钥放入VM的需要；但Agent若能触发真实API，仍可能产生读写与费用。密钥未进入VM，不等于没有获得使用该密钥的能力。

来源自定义秘密的替换依代理路径与目标绑定，普通环境变量、磁盘文件、透明隧道和显式header配置不能混为同一机制。host secret import是显式读取；`-e KEY`一类明文环境传递也不是自动的secret管理。保密、认证、授权与目标绑定分别解释，不能用“安全注入”四字替代。

SSH agent转发通常不是复制私钥，但能请求签名认证；共享skills、剪贴板或远程控制也会打开额外数据/执行通道。它们不是主文件挂载权限能够统一约束的对象。

## 6. MCP的执行位置比名字更重要

同为MCP，服务器可能在guest容器、宿主stdio子进程或远端。若宿主进程有读写文件或调用服务的权限，VM文件系统隔离不能自动限制它。工具声明“只读”是提示，不代替真实实现和权限检查，详见[MCP核心章节](../../Agentic%20Design%20Patterns/01-核心章节/10-模型上下文协议-MCP.md)。

来源至少区分sbx的宿主网关、Docker MCP Toolkit网关和托管网关，它们的设置、身份、工具目录与生命周期不必共享。注册一个server、允许某VM看见、动态load和成功调用是四个步骤；目录里“有工具”不能直接当本实例已经可用。

多Agent委派也不扩大授权。同步transfer、handoff和后台任务可能有不同上下文/工具集合；后台任务不可交互确认时需要明确拒绝/停止策略。外部harness还可能执行自己的权限模型，不能只靠一层“继承权限”标签推导全部后端一致。

## 7. 看回放记录时，先找证据来自哪一层

| 证据 | 可以支持 | 不能直接支持 |
|---|---|---|
| help/schema | 某固定版本声明的参数、字段、部分默认 | 真实loader一定采用默认，服务可用，动作已执行 |
| 诊断成功 | 这次检查覆盖的安装/平台/连接条件 | 所有隔离门、模型质量与业务正确性 |
| 录制HTTP/SSE | 作者那次请求、工具提议、返回与终态 | 本机现在运行成功或所有版本相同 |
| 规范化快照相同 | 指定遮罩与比较规则下结果相同 | 原始字节、顺序、摘要/签名或效果都相同 |
| 本地fixture/模拟模型 | 接线、解析和有限失败路径 | 真实模型表现、权限没有旁路或真实云调用成功 |

本次完整解析6份gzip的37,970个SSE JSON帧，并静读31组交互的有效请求、工具、输出、usage与终态。逐token模型草稿只做数量/hash登记，明确作为无独立长期价值的推测内容排除，没有当作专业事实或指令。

几个可直接学习的反例：

1. 列目录只回文件名，模型就声称文件有1行；后来read_file才给了真实内容。后一次核实不使第一次猜测变成有证据的回答。
2. 后台Agent调用被拒后模型仍反复提出，说明提出工具调用不等任务已运行；末轮只有提议时，不能补造完成回执。
3. reviewer按提示输出APPROVED，只是模型格式行为，不是有效人类批准或已验证的安全结论。
4. API的pong请求有finish/done/usage；两个标题请求虽HTTP200，却没有正文及完整终态，不能记为成功标题生成。
5. 源`--sandbox`因SQLite错误在模型前失败；另一目录的成功是条件变化后的另一条实验路径。

来源capture程序还会遮罩路径、时间、费用、digest或排序某些并行事件；比较时必须说明变换范围。manifest被解析成另一种JSON表示后，可读其语义字段，却不能用新字节声称原始摘要/签名已验证。失败后外层进程仍exit0、检查模式因前提缺失skip，也都可能发生。

## 8. 用一份小审阅结果开始学习

不需要先租云资源或启动整个工具栈。对一个计划或已有转录，先填下表：

| 项目 | 应写出的内容 |
|---|---|
| 任务 | 输入、允许修改范围、目标产物与判据 |
| 身份/位置 | 调用者、运行器、模型、工具分别在哪，使用什么凭据 |
| 能力 | 可读/写路径、出口、端口、host MCP、SSH、共享skills |
| 版本 | CLI/插件/guest模板/kit/schema及实际解析资产标识 |
| 过程 | 准入、工具提议、实际调用、拒绝/未知、重试与总预算 |
| 结果 | 原始回执、规范化范围、产物、语义验收及未验证部分 |
| 恢复 | 需要保留什么，停止/删除会影响哪些具体对象，外部效果如何对账 |

参考练习：一次轨迹只有“请求HTTP200、模型输出APPROVED、没有工具回执”。合格答案应标传输返回、模型文本、实际动作未知，不能认定补丁已保存、权限已通过或已部署。再给出直接挂载/只读/私有clone三种选择，说明各自写回和数据读取的区别。

实际开始运行时，再为所选一条最小路线制定可执行验证：先核固定配置与可见输入，再确认真实工具位置，最后对产物/失败路径留证据。已有预算、缓存、幂等和恢复方法沿[推理与服务化](../../LLM%20工程实践/03-推理与服务化.md)、[异常处理](../../Agentic%20Design%20Patterns/01-核心章节/12-异常处理和恢复.md)学习，不在这里重复维护一套框架实现。

## 9. Kit把软件内容和“向宿主申请什么”放在一起

镜像config已经描述入口、参数、用户、环境和工作目录。Kit在同一OCI镜像的manifest annotation中再声明依赖、参数和宿主能力，避免镜像更新了、旁边的权限文件却没更新。固定manifest digest可以绑定这份声明和所引用的内容；可变tag、外部服务和运行时绑定仍要另管。

本节讨论来源保存的**实验性v3规范快照**：主分支`4be7f4d…`与预发布`v3.0.0-m.8`。它是设计合同，不是本机sbx能力清单。schema字符串`"3"`、capability的`@1/@2`、前端镜像版本、Kit自己的版本是四个不同维度；相同schema号也不证明旧严格解码器认识后来增加的字段。来源中的`:3`浮动tag说明和作者捕获还有差异，需要复现时固定实际解析出的digest。

### 9.1 三个名称不要混用

- **workload**提供完整根文件系统和启动配置，一次最终运行组合恰有一个。
- **mixin**提供叠加内容或纯声明，可以有多个；它的入口配置不取代workload入口。
- **set**是编写时把若干已发布Kit合成一件产物的方式。发布后kind变成workload或mixin，并保留组成Kit的digest记录；不能把set当第三种运行时根文件系统。

声明可配同名Dockerfile、显式`dockerfile`路径、内嵌`build`、Dockerfile注释描述或`kits`集合。内容配方不能同时有多个来源。纯声明mixin仍有保存描述信息的layer；workload不能没有内容。set引用已发布资产，不能依靠作者电脑上的相对目录才能重建。

**典型选择**：给已有Agent加一套工具，用mixin；分享固定团队环境，用发布后的set；需要单独升级工具，就保留独立Kit并用组合锁记录它们。合成set后升级其中一件，需要重新发布整个set。

### 9.2 两类“能力”回答不同问题

| 声明 | 回答的问题 | 失败例子 |
|---|---|---|
| `provides` | 这个Kit声称提供哪些有名字的软件能力 | 两件Kit都提供同一个规范化名称，即便版本不同也冲突 |
| `requires` | 当前已选组合必须满足什么 | 要求node在指定范围，组合里没有提供者；不会自动到注册表搜一个 |
| `integrates` | 如果某提供者在场，应与哪些版本兼容 | 缺席可以，在场但不满足版本则失败 |
| `conflicts` | 哪些名字不能同时在场 | 已选组合确实提供了被排斥的名字 |
| `capabilities` | 希望宿主提供哪些资源、权限或执行行为 | 必需类型不支持，或所需凭据没有绑定 |

例如`provides: ["tool@2.0"]`是Kit之间的匹配；`com.docker.sandbox/credential@1`是向宿主请求某类合同。前者的短名归入`com.docker.kit/`，与`com.example/tool`不同。显示名称、作者文字、`source`诊断字段不能充当发布者身份。

解析器在**已选封闭集合**上检查依赖、冲突和单一提供者，按依赖图使提供者先于使用者组合，不能靠交换命令行顺序解决冲突。`node >= 20.0, < 21.0`中的多个约束是AND；无版本提供者只满足无版本要求。此快照的版本比较是逐段数值/字典比较，不能套用任意包管理器的SemVer规则。

来源还从workload包数据库派生`deb/`、`apk/`条目，只取已安装且各平台一致的可表达版本；这是受限清单，不是完整SBOM或漏洞结论。省去发行版修订和丢弃某些预发布条目后，不能用它代替发行版安全补丁判断，也不要把Kit自身版本冒充所含bash版本。

## 10. 从声明到真正执行，中间必须有有效配置和选择

### 10.1 三份配置的含义

1. **编写态**含配方、构建参数和占位符。
2. **发布态**已解析构建参数，内容文件被放入镜像并改为镜像内路径；签名覆盖发布产物。
3. **有效态**在某次创建时，结合创建参数和最终容器环境，展开需要的值，再校验、选择和合并。这一份才描述实际实施的能力。

不能只批准一个带`${{ kit.args.host }}`的字符串，而不看它最终变成哪个host。新版本字节没变，创建参数改变也可能扩大权限。

参数默认不自动进入容器：声明`env`才导出，声明`buildArg`才传给构建，二者互斥。`required`与默认值、`enum`与`pattern`也有互斥关系。正则匹配整个值；未声明参数、未提供必需值、展开后两个map key撞在一起应报错。

参数替换发生在解码后的结构，不能把用户值直接拼进YAML文本。整值参数可在可无损往返时转成数字等类型；`8080`与`007`、`1.0`的处理可能不同。`${{ kit.env.HOME }}`则始终是**最终容器环境的字符串**：镜像默认值、参数导出、运行时覆盖依次生效，显式空值算存在。它不读取宿主环境、不执行shell，也不递归展开新插入的模板。路径展开后仍须满足绝对路径、规范形式和冲突检查。

`$HOME`、`${HOME}`和Kit自己的`${{ ... }}`是不同替换阶段。若生命周期命令显式使用`sh -c`，后续shell仍会解释自己的语法；“结构化替换防止破坏YAML”不等于“任何命令模板都免疫shell注入”。

### 10.2 optional是可降级，不是可忽略错误

必需能力不能满足，就在启动前拒绝；optional不能满足时跳过并记录。拼错字段、错误类型、非法参数仍需校验，不能因为该项将被跳过就允许畸形声明通过。

group用于耦合一个功能的多项请求。例如“一个卷＋初始化该卷的hook”：所有成员接受才选择整组；optional组缺一项就全跳过，必需组缺一项就拒绝。成员不能自己再标optional，也不能嵌套组。

**选择原子性不等于事务回滚**。全部选择与冲突检查应先完成，才应用文件和hooks；已接受hook执行失败，是执行失败，不能事后改记为“optional正常跳过”。它也不自动撤销hook已经做过的事。restart沿用已存选择；recreate重新判断，二者不是同一实验。

组名可以重复，不能靠显示名关联授权。记录原Kit、原字段位置、成员决定、跳过原因与最终有效权限；诊断`source`只是追溯信息，真正信任仍绑定所消费的资产。

### 10.3 权限比较要识别“删了一条限制”

新版本比较的是规范化的有效授权集合，不是YAML行数。新增出口、凭据、端口、共享路径、签名目的地，或把skills从只读升为可写，都扩大权限；**删除deny也扩大权限**。

例：旧配置允许`api.example.com`但拒绝DELETE，新配置仅删掉DELETE deny。diff看起来只有删除，实际可做的事更多。反过来，改显示名称不扩大权限。规范将资源限额、guest内部生命周期/上下文/会话启动行为列为非跨边界授权；这不免除组织预算、收费、业务操作批准，也不意味着这些内容天然可信。

## 11. 按功能理解20类能力合同

下表是前述固定主分支的学习索引，字段与实施支持仍需按使用版本核对；后文给出关键组合与反例。

| 合同 | 核心作用与边界 |
|---|---|
| network-policy@1 | install/runtime分阶段出口allow/deny，未允许默认拒绝，deny优先 |
| network-policy@2 | 在host基础上增加HTTP方法/路径限制；同一描述不能同时声明@1和@2 |
| credential@1 | 按service与阶段绑定宿主凭据；代理代替、环境值与OAuth透传是不同呈现方式 |
| ssh-agent@1 | 转发身份列举及签名能力，私钥留在外部；可限制签名命名空间、登录目的地与阶段 |
| volume@1 | guest存储；块卷跨restart保留，tmpfs停止即丢；recreate/删除保留范围另核 |
| host-mount@1 | 运行器分配的宿主共享目录，同Kit身份可跨沙箱共享；Kit不能指定任意宿主路径 |
| port@1 | 发布容器端口/传输协议，宿主端由运行器分配，建议回环临时端口 |
| usb-device@1 | 按vendor/product或class申请设备，二者互斥；并非所有平台都能提供 |
| resources@1 | CPU、内存、GPU请求/限制；GPU选择器与精确实施由运行器定义 |
| privileged@1 | 整个组合的特权模式，不能只理解为某一个mixin私有权限 |
| kit-registry@1 | 访问运行器的Kit镜像存储端点，不能顺带开放整个宿主镜像库 |
| lifecycle@1 | guest内部install/startup hooks、启动文件与交互参数尾部 |
| long-running@1 | 最后客户端断开后仍运行；不保证故障重启、无限可用或不收费 |
| agent-context@1 | 将Kit上下文索引放到Agent能发现的位置，保留已有用户内容 |
| agent-skills@1 | Agent读取skills的目标目录与宿主共享上限；未声明mode默认只读 |
| agent-skill@1 | 镜像自带的一项Skill目录；注册本身不执行附带脚本 |
| agent-sessions@1 | 无终端的prompt/list/resume/continue调用合同，不授予新外部权限 |
| agent-interactive-sessions@1 | 带终端的会话操作，另有newSession和sessionPicker，空列表有独立含义 |
| git-identity@1 | 提供Git作者name/email用于归属，不是认证、签名或用户审阅证明 |
| sbx@1 | 运行器按镜像用户/工作目录和bash环境启动Agent的约定，不是额外网络授权 |

无config类型不能随手补`config: {}`或null。类型未知时，规范库能保留扩展载荷，不代表当前运行器支持它：必需未知类型拒绝，optional未知类型跳过并记录。编辑器schema通过与运行器准入通过也不同；来源总schema引用20份单独capability schema，这些依赖未完整随该手册保存，不能宣称只用总文件就完成全部字段验证。

### 11.1 host允许和HTTP请求允许是两层

@1允许host通常代表该连接范围，不限制业务方法。@2可写“只允许某host的GET/HEAD和`/repos/**`”；有paths就必须明确methods，`ANY`不能再和GET并列，空methods/paths也不能偷换为任意。

下面是**依据固定规范编写的声明示例**，只展示策略，不是已构建/已运行的环境；example.com为说明域名：

```yaml
schemaVersion: "3"
kind: mixin
capabilities:
  - type: com.docker.sandbox/network-policy@2
    config:
      runtime:
        allow:
          - hosts: [api.example.com]
            methods: [GET, HEAD]
            paths: [/repos/**]
        deny:
          - hosts: [api.example.com]
            methods: [DELETE]
```

此快照的有界allow须写字面host。只有受限HTTP授权时，不可检查的方法/路径或非HTTP流量应拒绝，不能退化成“隧道已连接就全放行”；边界拒绝用403反馈，但单看远端403仍不足以辨别是哪一层拒绝。

组合中allow取并集。若另一个Kit直接允许整个`api.example.com`，原先GET路径限制不能限制邻居的授权；需要强制禁用DELETE，就保留deny。凭据注入域名还须在相同阶段的允许host中，注入规则本身不授予网络访问。

### 11.2 volume与host-mount解决不同问题

volume的跨restart保留，不能用stop/start试验来证明：普通可写层也可能保留。要证明卷机制，应在可写层被真正替换的recreate前后比较。tmpfs属于临时数据，不应放唯一成果。

host-mount要求运行器按可信Kit身份和guest路径定位宿主目录，同Kit不同沙箱可并发读写；并发一致性、文件锁和事务由应用解决。跨tag/digest升级复用存储，不等于任意同名Kit有权继承。显示名称和作者自填source不是存储身份凭据。

两个Kit请求同一个存储路径，或volume与host-mount请求同一路径，不能静默合并。宿主共享目录在最后一个沙箱移除后仍可能保留；删除沙箱与删除共享数据是两件事。目录mode是创建权限，不是内容版本/并发隔离协议。

### 11.3 Skills需要同时看“随镜像携带”和“宿主共享”

agent-skill指向镜像内完整目录，根部应有普通`SKILL.md`，保留其脚本、相对引用与执行权限。它的有效目录名决定冲突，UI显示名不决定；与目标已有同名Skill冲突时不覆盖。注册不能为了“检查一下”执行里面的脚本。

agent-skills声明发现目录。宿主共享与镜像自带是独立来源：宿主store缺失、空或关闭，不应让自带Skill凭空消失。共享的实际权限是**宿主上限与合并后Kit请求取较窄者**：宿主只读、Kit要求可写，仍只读；宿主可写、Kit只读，也只读；双方都可写才可写。

同一组合中两个Kit对同一个skills路径声明不同mode，规范把请求合并为较宽者，再受宿主上限约束；这应显示为权限扩大。不能以“我的mixin只读”推断同沙箱其它进程也被隔离。共享store可写会影响以后别的沙箱，和只修改当前guest文件不同。

### 11.4 凭据、Git归属与SSH签名分开

credential按(service, phase)区分，重复所有者可能冲突。代理管理时容器可见占位值；inject-only可连占位变量都没有；OAuth的passthrough则可能把真实令牌送入容器，必须单列。install-only凭据在入口启动前撤销，不能只隐藏初始env却仍让后续请求继续借用。

SSH私钥留在外部不妨碍Agent借助socket签名。此快照`unrestricted`默认true；有界声明需显式false，并列出签名命名空间或认证目的地。`sign: [git]`可以只允许Git提交/标签签名；它不是远程登录能力。受限登录还要验证session binding、目的地主机key与用户名，信任的host key来自沙箱外部，不能信任guest自己递交的“这是GitHub”。网络出口仍另行控制。

git-identity只物化name/email，不导入宿主credential helper、aliases、includes、hooks或签名程序，也不共享原配置文件。署名、认证成功、Verified签名、用户批准、代码正确性分别需要证据。

## 12. 生命周期和会话参数容易在哪些地方出错

Kit lifecycle位于**guest内部**，和环境文件`sbxenv.yaml`的宿主`initialize`不是同一信任平面。install在create时一次，startup每次启动都跑且应幂等；后台hook不自动保证最后客户端断开后继续运行，需要long-running合同。install授权应在主入口前结束。

hook环境按声明的变量与平台基线构成，不应复制宿主整个env。字符串command会经shell，argv列表按参数执行。files在入口前写入，`overwrite`默认true：要保留卷内用户设置，应明确是否只在不存在时初始化，避免每次启动覆盖；不同贡献写同一文件路径应报错。

Agent上下文是给Agent读的内容，不能变成运行器自己的可信指令。把正文复制进镜像还不够，要确认发现入口指向它；多个工具上下文可渐进索引，避免全部塞进常驻提示。不同Agent harness发现路径不一定相同，不能靠“文件叫AGENTS.md”推定必定加载；已有用户内容应保留。

会话参数尾部追加到launch argv，`list`则是完整命令。Prompt与SessionID是原始argv元素替换，不应再次拼shell字符串。在此快照中，无终端agent-sessions与交互版本对空列表的语义不同：交互`continue: []`表示支持、仅用launch argv；省略表示不支持。`newSession`省略时继承lifecycle交互启动；显式声明时须与lifecycle的interactive一致，不能在序列化时把空数组丢掉。

sbx合同还要求按镜像用户解析uid/gid/home，以bash读取`BASH_ENV`，而不是假定所有镜像都是同一uid或都会读交互rc文件。镜像中“有一个可执行文件占着/bin/bash”只能静态证明文件形态，不能证明其行为确实是bash；制品检查和实际行为检查仍要分开。

## 13. 怎样验证Kit，而不制造一个“永远通过”的实验

**制品符合性**看最终发布的manifest/config/layers、描述、内容与字段；**运行器符合性**看其声称支持的能力是否按合同执行。前者通过不替后者担保。`inspect`只读信息，也不是validate；一次本地build成功不能证明导出器/注册表没丢annotation。

多平台image index可能不带描述annotation，消费者需按合同回看平台manifest。来源捕获中docker driver与docker-container driver的annotation保留不同，且作者有把JSON字符串解析成对象的规范化：这可以学习字段关系，不能据此验证原字节签名或摘要。显示`built-by`只是自述构建器，不等于签名的构建溯源。

运行器测试应明确其支持的类型并测试不支持的必需能力是否拒绝。规范测试适配器区分0成功、2主动拒绝和其它非零故障：找不到fixture、daemon崩溃不能伪装成“策略正确拒绝”。这套退出码是该适配器合同，不是所有CLI通用规则。

可信试验需要能推翻结论：

- 存储：recreate确实丢掉普通可写层，再观察声明卷；不要只stop/start。
- 长期运行：真实断开最后客户端，等过正常空闲期，用不唤醒VM的状态查询观察；不断exec检查会改变被测条件。
- skills只读：用隔离测试store，让宿主确实提供可写，再验证Kit只读上限；总把宿主设只读无法区分是哪层生效。
- 凭据：使用已知测试值才能检查泄漏与代理替换，不使用真实账号秘密作为教学fixture。
- 组选择：保存原始选择记录；读取结果时重新计算会掩盖restart错误地重选的问题。

测试覆盖也有边界。该快照明确豁免了若干尚不可观察义务：Git身份源是否在任意guest路径留下可读副本，以及拒绝/选择前是否曾应用效果再回滚。测试最后状态通过，不能证明这些中间行为没发生。规范、检查覆盖、实际结果和仍未观察事项应四栏分记。

来源还有内部口径差异：总规范对资源/会话声明合并强调相同才接受，而个别capability页存在更宽松或优先规则；不能擅自替运行器选一个“合理默认”。遇到这类冲突，应固定规范与实现版本并核实际loader；本章未运行其运行器，也未读未收录的Go实现，不作已解决断言。

参考判断题：一个mixin新增可写共享skills、删掉DELETE deny，tag没变；是否需要重新审阅？**需要**，有效权限扩大且tag可变。optional组的hook被接受后失败，能否记为正常跳过？**不能**，那是执行失败。TCK全部已覆盖项目通过，能否写“无宿主数据泄漏”？**不能**，需要同时说明豁免、未支持类型、测试输入与实际观察范围。

## 14. 模型后端、MCP配置组与迁移怎样接入工作台

### 14.1 模型管理、推理后端与调用地址

Docker Model Runner管理模型资产并连接推理引擎，可以有Desktop/Engine集成，也有独立服务形态；“用Docker模型”不意味着模型一定在当前Agent的容器内。CLI、推理daemon、权重存储、llama.cpp/vLLM等引擎与GPU驱动是不同对象，先把位置填入第2节账本。

工作站上可达的localhost，在应用容器里只代表容器自己。宿主回环服务、Desktop提供的内部名字、Engine网桥地址与Compose注入URL不是通用替代值；应从实际调用进程测试所配置地址。管理API的模型列表、推理API的chat/embeddings、metrics与控制配置端点也不能混成一个路径。

最小验证依次是：客户端与daemon版本/连接 → 模型资产存在及标识 → 选定引擎加载 → 单次请求有完整响应 → 所需流式/工具/embeddings行为 → 并发和资源边界。某个chat请求成功不能推导其余兼容接口、字段或模型工具能力成立。来源`enable_thinking:false`与实际reasoning帧不一致，说明要观察后端是否真正采用参数。

固定来源的README既有独立daemon用法，也有启动临时服务后关闭的开发包装器描述；其端口示例包括12434、开发8080、冲突规避13434，不能任选一个当默认。构建target、CPU/CUDA/ROCm、架构、wheel和驱动基线分别核，不照搬文档中的旧版本组合；其中一次“升级vLLM”示例的构建版本与产物tag不一致，tag本身不证明内含版本。

模型缓存/卷能减少重复下载，不代表会话、secret或全部推理状态持久化。metrics是观测点而非任务验收；启用详细prompt日志可能保留用户内容。来源中的卸载/删除、安装源替换与purge步骤不作为排错默认动作：先找实际客户端/服务路径和错误层，再选择最小变更。Compose模型绑定和外部provider的完整机制统一放在[Compose章节第15节](04-Compose与多容器应用.md)，避免本章重复维护另一套语法。

**API格式兼容与安全边界。** DMR在不同入口呈现chat completions、messages、Ollama以及原生模型管理接口，不能只替换host就认为所有路径/参数/流式行为等价。来源REST表与示例对Anthropic路径有两种写法，OpenCode示例还与通用base URL不同；本次作者捕获未覆盖每个别名，不把它们一并标为已验证。先确认客户端自动追加的路径、完整namespace/model ID、所选引擎与必要能力，再用完整响应核接线。

[DMR官方网络说明](https://docs.docker.com/ai/model-runner/#networking)2026-10-18仍注明API没有认证。SDK为通过本地参数检查而填`not-needed`之类占位key，不会给服务增加鉴权；Web界面有登录，也不保护可被直接访问的后端。浏览器CORS限制哪些origin可读响应，不限制任意其它程序调用，不替代网络边界或身份验证。连接信息应同时记录调用者、监听地址、入口权限、代理和是否存在绕过入口。

**冷启动、上下文与显存。** pull只把资产存到本地，不等于引擎已加载；模型已加载也不等于单次输入/输出预算能容纳。inspect中的训练/模型最大窗口与当前运行配置不同，运行窗口加大不自动提高模型在长上下文上的质量。首请求要加载，热请求、排队与并发批处理有不同延迟，不能只报一个“启动快”。

资源估算用[硬件与KV缓存合同](09-AI容器与硬件运行边界.md)计算权重、KV、运行workspace与其它常驻开销。来源“每千tokens增加100–500MB”只是粗略范围，不能替所有架构、精度和并发预算。例：16GiB可用容量，权重8GiB、KV6GiB、其余workspace3GiB，合计17GiB就不能据“权重仅8GiB”宣布可运行。量化影响权重与质量，不保证KV也按同比例缩小。

线程数、prefill batch、GPU层卸载、tensor parallel与调度并发分别控制不同环节；增大某一项可能增加内存或争用。GGUF/Safetensors/DDUF描述资产封装与引擎支持，文件格式本身不保证质量、吞吐或任意硬件兼容。此版本DMR的vLLM/Diffusers平台限制，不是上游框架所有版本的永久限制；来源README与文档还存在ARM/WSL和版本表口径差异，不复制固定选型表。

**给界面、流水线和排错各留独立验收。** Open WebUI部署前先定用户范围、监听接口、鉴权、后端可达性与聊天数据卷；来源快速示例同时用了浮动main镜像、未限定宿主IP的端口和关闭Web认证，不能作为多人部署模板。预拉模型任务挂宿主Docker socket会增加控制面权限；docker:cli镜像是否包含model插件也要独立确认，挂socket不自动安装插件。depends_on等待setup成功，只证明该任务退出，不证明推理模型Ready。

来源CI示例将生成超时124当成功、用curl退出0和文本含hello验API、清理失败后仍继续，不能作为完整生成/回收验收。更可靠的判据应分别保存：传输结果、HTTP状态、JSON结构、请求model与本次输出、流终态、超时/错误及真实资源清理状态；不要让错误消息里碰巧含hello也过关。模型ID等workflow输入通过受控数据通道传给脚本并校验，不直接拼入shell代码。

调试可查看请求/响应、token、模型/引擎和耗时，但完整prompt与聊天数据可能进入本地日志/卷或UI记录；产品遥测是否上传与本地留存不是一回事。先用已知、可公开的小输入验证，再按失败层排查地址/协议、模型身份、实际加载、容量和应用处理，不通过清空全部模型或卸载整套Docker来代替诊断。本轮未部署Open WebUI、修改CORS/监听、拉权重或运行CI。

### 14.2 MCP profile、catalog与工具白名单

Docker MCP Gateway的配置也分层：catalog描述可发现的服务器来源；profile把所选服务器、配置及工具allowlist组织成一组；gateway按具体profile启动/路由；client配置决定客户端连哪一组。更新catalog不等于原会话已经刷新工具，连接客户端也不等于所有工具已成功调用。

服务器来源可以是catalog引用、OCI镜像、公共注册表条目或本地文件。来源类型仅描述获取入口，不能替代发布者身份、digest、工具位置和权限审查；同名工具应连同server/profile确认。stdio适合进程连接，HTTP流式连接适合独立服务；共享网关带来的配置一致性，也意味着变更可能影响多个客户端。

一种可审阅工作流是：先列出任务需要的工具 → 固定服务器来源 → 在独立profile配置必要字段与凭据 → 仅暴露所需工具 → 确认客户端实际连接的profile → 用无外部副作用的真实输入验接线，再单独验证有写入效果的业务操作。工具清单、schema、调用返回与业务产物分别记录；不要用`tools count`代替调用成功率。

profile导出/推送到OCI方便复用，但导出的描述不等于私密凭据也按预期安全迁移；secret/OAuth另有生命周期，旧文档中的临时export尤其需要按实际内容判断。客户端连接命令可能修改本地配置；独立CLI的feature flag、配置目录覆盖和Desktop Toolkit开关也不同。设置一个绕过Desktop检查的环境变量，不自动提供缺失daemon/socket或隔离能力。

来源MCP README中的容器化、“最小权限”“安全处理”是产品描述，实际还需检查挂载、Engine socket、stdio宿主执行和可达服务。Compose服务的`use_api_socket`可以让服务操作宿主Engine；不能因为服务本身在容器里，就把这个门画成guest私有Engine。

### 14.3 旧命令迁移与云模式只保留可复用的判断

来源并存旧`docker sandbox`、旧`docker agent`插件与新sbx/独立docker-agent帮助。迁移应按概念对照：沙箱创建/运行、网络策略、模板、secret、会话、分享与服务暴露，逐项核新版本参数和默认。不要对旧命令做全局字符串替换；例如旧`save`与新`template save`、旧network proxy与新policy并不是只改前缀。

Desktop发布说明、插件登记名、旧help与真正执行的二进制可能不同；发布表里的显示版本和链接tag也可能不一致。先核实际CLI/服务/模板资产，不能从一个发布标题或残留插件入口推导功能。宿主扩展、控制socket与guest引擎还在不同信任平面，不因都出现在Desktop界面就共享同一隔离边界。

旧Agent的run可以已经有sandbox/record/fake，不能把新版本的改进说成旧版完全没有这些能力；反过来，旧帮助未列认证、预算、chat服务等选项，也不能推断新文档的能力可回用旧插件。别名里还可能保存旧模型、yolo或隐藏工具结果等参数；升级二进制后要核有效配置，而不是只看安装名称。

目录仍叫cagent不证明仍是旧运行器；来源发布记录实际包含旧runtime状态目录迁移，因此“完全不会自动迁移”也不成立。先辨识数据/配置/缓存的实际位置并备份需要的内容，再按当前官方迁移合同处理。全局reset、强制prune、删除旧目录会影响其它状态，不能用它们代替确认。

云模式改变执行位置、账户、配额、TTL和资源保留策略，不是本地命令无成本搬家。移动文件系统产物通常不搬运行进程、宿主挂载、secret和全部本地规则；目标还要重新绑定权限。临时云卷、停止状态、公开端口与快照并发语义由版本定义，名称相同不保证与本地相同。固定来源的价格/赠金/限额均不作当前承诺，本次没有创建云资源或调用付费服务。

### 14.4 动态发现、会话工具与账号边界

catalog可以限制可发现服务器集合，profile决定持久配置；Dynamic MCP再允许当前会话搜索、添加、配置、执行和移除服务器。**搜索管理工具本身也是能力**：只审阅初始工具清单，却允许随时添加任意服务器，不能保持原先固定的权限面。来源动态加入仅属于当前session，不自动写回profile；下一次会话的工具集可能不同，应记录实际会话与变更。

code mode把多工具编排装进一个可调用工具，减少交互轮次，但外部读写权限仍由所调用的工具决定。JS在隔离环境执行，不会把“可发GitHub issue、可改数据库”的工具自动变成只读，也不提供跨服务事务。来源该功能明确实验性，不把示意流程当可靠通用实现。

[Docker Profiles官方页](https://docs.docker.com/ai/mcp-catalog-and-toolkit/profiles/)2026-10-18仍明确：**OAuth凭据跨profile共享**。不同profile的服务器/配置集合可以不同，不能据此保证不同业务账号隔离。切换前核实际授权主体、服务与granted scopes；导出不含凭据，也不意味着同机其它profile没有复用既有授权。删除服务器、容器、镜像、profile、OAuth授权是不同对象，不能用删一个替代撤销全部访问。

客户端显示enabled只证明配置层状态，connected也不证明目标工具调用与业务效果。验证至少走“实际工具身份/输入 → 回执 → 对目标对象的独立读取”；不要让模型输出的“已完成”自己充当写入证据。来源十余种客户端UI/命令只是各版本连接入口，统一维护这一验证方法，旧菜单、旧模型和启动耗时数字不复制成永久教程。

来源E2B示例表达的是“远程sandbox → 带token网关 → 多个业务工具 → 外部对象”的可复用结构，不是本机sbx部署的同义词。其SDK写法、真实账号费用及预期成功输出未在本轮执行；固定sleep不是Ready探针，timeout=0可能无界，异常路径缺finally会遗留云资源，只捕获异常打印又可能让外层exit0。正确实践要给创建/初始化/请求/清理独立时限，失败也保对象ID与清理回执，写操作另需授权和幂等。API token拼进命令参数还可能进入进程/历史/日志，不应原样成为练习模板。

目录中的签名、SBOM与扫描提供来源/清单证据，不能证明工具语义无恶意或零漏洞；FAQ本身说明检查是best effort。容器在本地也可能访问外部API或模型服务，所以“local server”不能直接推导完全离线与数据不出本机。旧固定CPU/内存限制不是全部版本与远程服务器的统一配额保证。

参考练习：两个profile分别叫personal/work，但同一OAuth服务账号仍共享，能否据profile名字承诺工作资料不会写入个人账号？**不能**，需验证实际授权绑定与目标对象。新会话找不到上次动态添加的工具，先查session与profile持久范围，而非立即重装或放宽权限。

## 15. Agent配置要读成一份执行合同

本节依据固定Docker Agent1.149.0的v16配置schema与作者帮助转录，解释字段如何共同影响执行；没有运行框架。schema、默认配置、用户设置、CLI参数、已恢复会话与外部harness可能共同决定最终行为，不能只看仓库中的一份YAML。

### 15.1 用配置对象串起一次任务

| 对象 | 一次代码审阅任务中的作用 | 容易错在哪里 |
|---|---|---|
| agents | 谁审阅、读什么指令、可用哪些工具、何时委派 | 工具在另一Agent上并不自动属于当前Agent；外部harness另有行为 |
| models/providers | 命名模型、API协议、地址、凭据变量和默认参数 | model别名、provider名称与远端模型ID混淆；凭据存在不证明服务健康 |
| mcps/rag/toolsets | 可复用工具定义与实际暴露的工具 | 复用减少重复配置，不等于所有Agent都获准使用 |
| commands/skills | 命名提示、发现与子会话能力 | 一条slash command可能切换Agent、展开命令或打开URL，不只是静态文本 |
| runtime/permissions | 作者默认运行方式与工具批准规则 | 用户/CLI优先项、恢复会话及宿主能力改变最终结果 |
| budget/budgets | 整次run与命名共享预算 | 给每个子Agent复制一个相同数值，不等于所有子Agent共用一个上限 |
| hooks/evaluators/routing | 在明确事件处改写、判断、记录或路由 | 观察事件不能代替阻断门，概率评估不是用户批准 |
| flavors | 按顺序叠加配置补丁 | 数组替换、null删除或扩展运算使有效配置超出基础文件 |

schema要求顶层agents非空，但不少语义依赖另由loader检查。旧`safer`字段曾被接受却无效，较新v16已拒绝；退回旧schema号不能恢复真实安全检查，须按实际运行器的有效权限模式迁移。编辑器不报错，不能说明模型、工具引用、参数互斥、依赖和网络都可用。读取本地instruction_file还要核相对配置目录、禁止越界和与inline instruction互斥；打包到OCI时的内联形式不同，不能把本地可读路径直接送给远端。

在此版本，flavor的对象递归合并、标量和数组替换、null删除；扩展的`+`追加、`-`删除另有合同。未知flavor可能被忽略，因此拼错名称可能使预期限制根本没生效。验收看最终配置，并保留原配置、补丁顺序和CLI覆盖；打印canonical配置可能包含已展开敏感值，审阅输出需控制范围。

### 15.2 选到模型、回退成功和完成任务是三件事

first_available按“凭据已配置”选首个候选，不发一次真实生成来证明健康；本地候选不需key，也可能没有daemon、没加载模型或资源不足。运行时fallback是在失败后尝试其它模型，与加载时选择不同。重试模型调用不应暗中重复已经成功的外部写入；工具副作用需要幂等ID和回执。

max_tokens是一次输出预算，context_size是上下文容量；thinking/task预算、框架累计tokens与按时间计的run预算又不同。某个字段可配置，不代表后端实际采用。附件能力override也只是告诉框架怎样发请求；声明支持image/PDF不会让纯文本模型变成视觉模型，缺省导致附件被丢弃也不能写成“模型读过图”。

自定义base_url在此版本模型路径会隐含绕过模型gateway；evaluator配置又有不同bypass规则。不能用同一套地址/鉴权推断所有子调用经过同一个审计与限额点。摘要、标题、重排、工具后处理和外部harness调用都要计入实际数据与费用路径；本章不固定旧型号、价格或厂商能力表。

### 15.3 预算中的零值与时间含义必须明确

此固定schema的run预算零值通常表示无限；max_iterations的零值也可能不设限，而max_consecutive_tool_calls的零值取默认5。这些字段不能按“0就是禁用”统一解释。重复调用检测针对连续相同调用，不代替任务总预算或语义进展判据。

顶层run预算由内部子会话共享；多个Agent引用同名named budget时共用一个池，多池同时约束时任一个耗尽即停止。把上限复制到N个独立池，最坏总量可能变成N倍。模型供应商task_budget是否实施、服务端serve路径是否转发、外部harness是否计入，都要另核。

max_cost只累计运行器能定价的响应，未知模型缺价格应标未知，不能当免费；cost override是估价配置，不是供应商账单。max_tokens用于累计run用量，不随上下文压缩归零；发布记录还专门修复缓存token、摘要与评估器计账，不能把缓存命中当零用量，具体字段归并按实际版本核。max_time按工作turn时长累计，在turn边界检查，不能硬中断正在执行的模型/工具；总预算与单次调用timeout需要一起设。

**例**：两子任务共享1000 tokens池，已用600与300时只剩100；不能再给每个任务各1000。若成本字段未知，即使仪表盘显示0美元，也不能证明没有付费调用。取消与预算停止后，真实外部动作还要按回执确认，不能把“停止循环”写成“撤销效果”。

### 15.4 缓存与压缩改变什么证据

该框架response cache可按问题文本复用旧答案，还能忽略大小写/裁掉首尾空白。它不天然绑定租户、权限、历史、文档版本、有效指令和模型配置。两个用户问“我的token多久过期”，问题相同但权限/制度不同，不能共享答案；缓存命中也不证明本轮重新检索或执行了工具。需要这些维度时扩充键或关闭此层，统一见[RAG权限与缓存](../../LLM%20工程实践/12-文本检索与RAG文档工程.md)。

压缩摘要是派生信息，不可替代原始回执。保留工件路径、输入摘要、版本、操作ID、未解决错误与下一步，而不是把所有细节留给模型记忆。工具结果中间截断会保头尾却丢中段；字符数除4只是token估计，中文/代码/多模态不能按它得到精确容量。短摘要模型自己的窗口也可能约束何时触发压缩。

## 16. 权限规则、hooks与工具进程各自在哪层生效

### 16.1 按工具名过滤不等于操作系统隔离

此版本Agent/Toolset的readonly依赖工具annotations中的只读提示筛选工具。它可以减少暴露，但不能证明实现无副作用；错标工具、另一个子Agent、shell/host MCP或外部harness仍要分别约束。filesystem的allow_list空或省略，在该schema里表示进程可达范围，不能误当“一个目录都不许读”。有白名单还要核真实路径、符号链接与其它工具的独立通道。

fetch域名过滤与Kit网络策略匹配规则不同：前者裸example.com可以包含子域，而Kit规范的通配符又有自己的范围。SSRF防护涉及实际DNS解析后地址检查、重定向、直连/代理路径和私有IP开关，不能只检查输入URL的文字。给内部服务开allow_private_ips是额外能力，不是修复所有网络错误的默认开关。

MCP命令/remote/ref、自动安装、工作目录、环境、OAuth和监督生命周期各自有配置。startup_timeout限制连接初始化，call_timeout限制一次工具调用，重连重试/嵌套交互也可能计入调用预算。**此快照Lifecycle.required的说明明确“尚未实施”**：不能仅设required=true就承诺缺关键工具时一定拒绝启动。strict/resilient/best-effort描述意图，还要看真实错误与最终Ready。

### 16.2 先改写参数，再做不能被普通allow跳过的检查

固定schema描述的关键次序是：tool_input_transform改参数 → tool_guard判定 → 普通权限/安全模式链 → 对应pre_tool_use/确认 → 执行 → response transform → 记录和后续消费。具体实现仍须按版本核验；它不是任意Agent框架通用事件表。

transform用于修改，不应偷带授权；guard并发判断取更严格结果，deny拒绝、ask要求交互、allow只是允许继续后续链。guard失败应拒绝。普通pre_tool_use可在确定性allow后才发生，关键检查需明确是否前置；仅在post_tool_use记录“拒绝”已不能撤回动作。

hook的事件合同也不同：观察性事件输出可能被忽略；有的错误按warn/ignore继续，有的必须fail closed。成功调用返回0而输出畸形JSON，不能当有效准入判断。prompt_file_guard/skill_content_guard检查加载内容的门，与给Agent增加instruction不同；资料里的指令、模型判断和真人批准仍是不同对象。

内置redact_secrets在参数、发给模型的消息和工具结果三个阶段处理识别到的秘密，减少传播；但检测只覆盖其规则，不保护未命中模式、已发出的外部请求或所有hook日志。改写过的输出用于解释结果时，保留“发生了哪些变换”，不能用脱敏结果反推原始完整字节。

### 16.3 评估器要分开“判断”和“采取动作”

evaluator可输出boolean/choice/score，policy再把结果映射为allow/ask/deny或限定Agent路由。概率阈值不等于已校准的正确率；需要代表性例子检查误拒、误放、未映射结果、超时和畸形分布。工具guard的provider失败应阻断；路由的不确定结果可能走明确default_agent，而取消/预算耗尽不应继续路由。这些失败策略不能互相套用。

before_agent_run可以在模型选择与response cache之前路由；after_agent_complete只在真正成功完成的事件后运行，错误、取消或预算停止不触发。路由图需限定目标并防环；force_handoff与hook路由的冲突条件另查。缓存命中也可能触发“成功完成”，因此这个事件不证明本轮模型真的运行，更不证明所有业务操作完成。

## 17. 用命令帮助检查几个容易越过边界的动作

- **debug tool**：此版本直接执行工具，没有模型turn；帮助明确普通审批检查被绕过，默认只运行部分输入/结果变换及post hooks，`--no-hook`还可跳过这些。它适合有意识的调用调试，绝不是纯读取schema或“安全dry run”。
- **sandbox deny**：在此Agent CLI里是从持久allowlist删除host，不是增加一条强制deny；自动gateway/安装host或配置其它贡献仍可能允许。不同CLI同名deny不能混用。
- **share push --encrypt**：帮助明确原YAML仍明文发布，只额外嵌入加密副本；不能用它发布写有密钥的Agent配置。签名/MAC验证与解密分别有key类型约束，Ed25519不用于加密。
- **board移动卡片**：会向目标列Agent发送该列提示，并可能启动tmux/worktree里的任务。把卡移到Push列不是普通无副作用的UI分类，列名Done也不是独立验收。
- **sessions diff**：比较工具调用序列并停在第一个分歧，不比较所有自然语言、工具回执与外部效果。同一调用读到不同内容，或同参数写入失败/成功，仍可能有相同调用序列。

评测与回放也要核完整任务分母：相同工具名字F1不检查次序/参数，错误计数不包含所有质量失败，配置repeat=k不保证已完成k次。重复稳定性、成本异常与未完成反例统一见[评测第33节](../../LLM%20工程实践/06-评测与实验管理.md)，避免从一次绿表推质量。

共享plan的并发维护则可以学习一个正面模式：读取内容与version → 修改 → 带expected-version写回；版本冲突时重新读并融合，不能默认force覆盖。create是只创建、update不隐式创建，status改变也是写入并提升版本。list中不可读文件应是warning而不是“缺失”，export的原子替换又与并发版本检查不同。原子文件写不防基于旧内容覆盖另一人修改。

**自测**：工具输出“APPROVED”、工作流进入Done、debug调用exit0，哪项独立证明用户已同意部署？**都不能**。需要与具体动作、输入版本、可信主体和实际回执绑定的批准与结果；先前题目的模型reviewer不能自我赋予这个角色。

## 18. 声明环境：计划批准的是哪些真实效果

`sbxenv.yaml`把Agent、工作区、kits、变量、秘密、绑定、端口、MCP和生命周期放到一份环境文件。它与Kit描述不同：**环境文件的lifecycle在宿主以当前用户权限执行**，Kit lifecycle在guest执行。这里按来源sbx0.47.0帮助解释，不提供默认自动批准或真实安装命令。

### 18.1 先确定文件、路径和环境身份

显式相对workspace/kit路径以声明它的环境文件目录为锚，projectDir和fileDir也有区别。多文件按顺序合并，标量后者覆盖，而ports、mcp.servers等列表会连接，重复项可能出现；这与Agent flavor数组替换的规则不同。没有PATH时的home默认层、项目隐藏旧文件是否读取，又是独立的版本行为。

同一套创建/执行/删除应使用相同有序文件、目标端点、账号和name。改变默认Agent可改变派生沙箱名；这时删除“当前环境”未必会找到旧名字，不能把未显示的旧资源当已删除。状态存放在宿主环境记录中，删除项目YAML不等于清理它创建的资源。

### 18.2 读计划时区分资源与每次动作

| 计划标记 | 应理解为 | 需要补问的条件 |
|---|---|---|
| + | 新增声明或资源 | 创建到哪个账号/宿主位置，谁拥有，怎样回收？ |
| ~ | 修改属性 | 新旧有效值是什么，是否扩大权限？ |
| - | 销毁资源 | 是否是本环境拥有的对象，是否含唯一数据？ |
| > | 再运行命令 | 命令文本相同，但脚本、工作目录或依赖是否变了？ |
| ! | 不再由该环境声明/跟踪 | 是解除跟踪还是实际删除，外部对象还在不在？ |

例如workspace没改，而initialize仍要在本次run执行，计划不能以“没有资源diff”为由省掉这项宿主执行。来源initialize在create/run甚至仅重新连接时也会跑，postCreate有创建时机，preRemove失败通常只是warning；不能靠preRemove脚本假定一定完成备份后才删除。

只显示计划不执行、不批准、不登记已应用状态。实际apply还要区分先前“批准但未应用”与“已经应用”；端口/kit/凭据的某些改变需下次创建才生效，重新连接旧Agent进程也不会改变其已有env。计划接受、进程配置更新、资源创建完成和业务验证仍须分开。

默认每次含宿主命令的调用都应重新展示该调用的效果，因为同一命令背后的文件会变化。rememberHostCommands或auto-approve改变的是批准策略，不能证明命令内容可信。环境文件在挂载里是否只读也有限制：它所在目录可被重命名时，单文件只读不总能保护路径身份；动态secret helper及其依赖/配置应在Agent不可写的位置，不能只核helper主文件。

### 18.3 凭据绑定、快照与不确定恢复

动态secret的command在宿主运行，ref需要实际已认证的解析器；它不是guest里读一个变量。snapshot把批准后解析的一次值保存为静态值，不会自动刷新。计划用摘要代替字面secret只减少明文暴露，不把短/低熵secret的哈希变成无信息；预览、resolver stderr、日志、argv和已复制到磁盘的凭据仍分别检查。

沙箱级secret与全局credential bindings具有不同生命周期。环境删除一般清其创建的沙箱secret，默认保留可能共享的全局绑定；删除绑定要确认其它环境的依赖。registry宿主拉取凭据与允许guest借用的服务凭据也分开，不能因为一次私有镜像pull成功就认定Agent获准登录该注册表。

云端创建/secret上传被中断时，服务可能已接受但客户端未得到确认。来源提供按同一环境身份重试和journal恢复的合同；不能直接删除journal再新建一轮，从而遗留重复资源/秘密。先核原请求、目标账号和资源状态，未知就保留恢复材料并记录未知。本地资源原子写与云API幂等是不同层次。

移动环境时，镜像文件里的真实凭据可能随文件系统一起走；“sbx管理的secret不迁移”不等于“所有secret都不会迁移”。移动成功也未必意味着源端已停止：来源帮助明确云端停止请求可能被拒或尚未完成，而move仅警告。目标新ID、源保留、端口新绑定和策略重建要分别验。

### 18.4 几个固定帮助中不能简化的语义

- `policy check network`即使接收完整URL，也只取host/port评估网络授权，不核HTTP方法/路径；不能用它证明Kit的L7 DELETE限制已实施。
- sbx本地允许hostname的判定不再用其解析IP的CIDR规则覆盖；hostname、IP、TCP/UDP和规则scope都需列出。allow默认TCP，deny默认TCP+UDP；不能把一个成功TCP试验当UDP已受控。
- MCP注册的SSRF检查在该版本是**警告后继续**，不是默认阻断；OAuth元数据也有独立检查。不要把Agent工具HTTP客户端的默认拒私有IP机制套到注册器上。
- OAuth advertised、requested、granted scopes不同。no-scope可能省略参数并使用服务器默认授权，并非“权限为空”；resource指标的override还可能在某些托管路径只登记、不实际发送。要查实际授权主体、resource和granted集合。
- 云rm可能接受请求后仍在删除，CLI等待到上限退出0不能证明已不存在；云stop也先返回请求接受。应按对象ID查询终态，不能再用会隐式启动VM的exec观察“是否停止”。
- 云卷在此快照是退出时快照、并发最后退出者覆盖；这不是持续共享文件系统或数据库多写者一致性。两次独立更新不能靠同卷名自动合并。
- 共享Skills的已有文件修改可能沿只读链接立即可见，新增条目要下一次启动才链接，删除可能马上使链接失效。只读只限制写入，不固定读取内容版本。

对照[sbx0.47.0发布说明](https://github.com/docker/sbx-releases/releases/tag/v0.47.0)后，还需保留三个实施边界：该版long-running只在本地可提供，云端和kit add路径对必需请求拒绝、对optional请求跳过；一次TCP策略修复没有覆盖相关UDP多hostname情形；升级不会自动删除旧云策略中已保存的宽泛CIDR允许项。它们说明合同、修复范围与存量状态必须分别核验，不能因版本号更新就推定全部策略收紧。

TLS检查不完整时拒绝继续、压缩资产同时限制声明大小/解压体积/条目数、撤销凭据后再验证运行中proxy能力，是这些发布记录中仍可复用的工程方法。具体阈值、平台和修复状态依使用版本核，不把历史漏洞清单当当前运行器的全部攻击面。

Kit发布的签名、来源证明和执行准入也要分层：来源旧pack/push/pull描述schema1/2的打包布局，不能当v3构建命令。签名验证至少绑定接受的key/证书主体与issuer、制品digest和证明subject；无签名SLSA记录只是自述。透明日志、时间戳与私有签名各有条件，关闭某项验证不能继续沿用原先完整的信任结论。固定manifest与运行器审批都通过，也仍要验实际工具效果。

来源帮助中的builder history子命令收集还因宿主socket权限失败，只有启动错误而没有真正帮助正文。这里保留“帮助也可能启动daemon、缺正文不能补造参数”的学习结论，不把这些失败日志当完整子命令参考。

参考练习：旧环境文件加了一个同名port，再运行说“已批准”，为何服务没变？依次查合并列表是否重复、是否只是approved而未apply、改变是否要求recreate、运行的是哪个旧进程、最后核监听与实际请求；不能直接重置全部沙箱。迁移显示success但云源仍running时，标目标已创建/源停止未确认，继续按源ID对账，不能声称迁移清理闭环。
