# Docker沙箱与Agent工作台

先修：[核心生命周期](01-核心模型与生命周期.md)、[数据与网络](03-数据-网络-仓库.md)、[AI容器与硬件边界](09-AI容器与硬件运行边界.md)。本章解决的问题是：让Agent能使用文件、命令和服务，同时知道它到底在哪里运行、能影响哪里、怎样判断任务完成。

贯穿案例是“让Agent检查一个小代码仓库，提出修改并返回可审阅产物”。模型回答、工具运行、隔离措施、文件产物与人审决定必须分别有证据，不能因为界面显示completed就合并成一个成功。

## 1. 先分清四个角色

| 角色 | 负责什么 | 不单独保证什么 |
|---|---|---|
| Docker容器/Engine | 镜像、进程、网络、卷与运行时资源 | 任意Agent工具必在这个容器里；镜像固定一切外部状态 |
| Docker Sandboxes的sbx | 创建/管理沙箱，连接daemon、microVM、工作区、代理及能力配置 | 模型理解了任务，或获准做任何外部动作 |
| Docker Agent运行框架 | 读取Agent配置，管理模型、工具、会话和委派 | 单凭框架名自动隔离宿主、建立有效批准或保证效果正确 |
| 模型后端 | 处理模型请求，例如宿主DMR或远端模型服务 | 请求内的文件/命令已执行，或模型输出已经验收 |

普通Linux容器共享其Linux宿主内核。macOS的Docker Desktop通常先有Linux虚拟机承载容器；这与“每个沙箱有独立guest内核和私有Engine”是不同层次。microVM增加了内核边界，guest中有root/sudo也不直接等于宿主root；真正边界仍取决于VMM及明确开放的文件、网络和宿主服务。

`docker-agent`独立二进制与`docker agent`插件可能不是同一版本；命令都叫agent不意味着行为相同。来源固定案例中独立版为1.149.0，Desktop内插件为1.144.0，旧插件资料还有1.32.4；这些是作者2026-10-08的版本证据，不是本章推荐的当前安装组合。

`sbx run docker-agent`与`docker-agent run --sandbox`也有不同引导路径和模板来源。后者先在宿主处理配置，再进入沙箱；要分别核宿主引导器和VM内运行器。来源的一次`--sandbox`运行因挂载文件系统上的SQLite只读错误1032，在模型调用前退出；另在guest临时目录成功回答是另一组条件，不能改称原路径端到端通过。

## 2. 把执行位置画在资源账本上

不必先画复杂架构图，先给每个对象写位置：

| 对象 | 常见位置 | 检查时问什么 |
|---|---|---|
| 原Git仓库、宿主配置与凭据存储 | 宿主 | 是否会被CLI引导器、hooks或host MCP直接读写？ |
| sandboxd与控制socket | 宿主 | 谁可调用？操作是否影响其它沙箱？ |
| Agent进程、guest文件与私有Engine | microVM/guest | 当前用户、工作目录、模型配置和实际Docker context是什么？ |
| 工作区挂载或私有clone | 跨边界/guest | 读写模式、可见范围、未跟踪文件和同步方向是什么？ |
| 出口代理、凭据替换、MCP网关 | 依部署可在宿主/托管端 | 它们在哪里执行策略，谁拿真实凭据？ |
| 模型与外部工具服务 | 宿主、容器、远端均可能 | 从实际调用者能否连接，有何权限、留存与费用？ |

同一个`docker ps`会查询当前配置选中的Engine；不能因为在终端里运行docker，就认定查的是宿主或guest。相同的绝对文件路径，在宿主、共享挂载、guest私有文件系统里也可能是不同对象。

例如宿主DMR监听12434，guest调用模型必须能经实际网络路径到达它。`host.docker.internal`这类名字、允许该地址的策略、服务自身监听和认证是不同检查。模型列表显示一个default，只表明配置选择；来源doctor在DMR不可达时仍能列default，说明“列出模型”不等于“可生成”。

## 3. 生命周期：创建、停止和删除的对象不同

下面是来源sbx0.47.0的教学语义；具体参数在实际使用版本中重新核对，本文没有执行这些操作。

| 动作 | 主要作用 | 容易漏掉的条件 |
|---|---|---|
| run | 按路径/配置创建或连接，并进入交互运行 | 可能隐式创建；默认工作区与create不一定相同 |
| create | 创建沙箱而不进入交互 | 不给工作区路径时可没有宿主挂载；创建时能力/端口等与每次连接环境不同 |
| exec | 在既有沙箱内运行程序 | 可能唤醒停止的VM，不是纯读取元数据 |
| stop | 停止运行并保留相应本地状态 | 不是撤销代码改动、网络写入或费用 |
| rm | 删除指定沙箱及受其管理的状态 | 宿主工作区、外部动作或先前取回的Git引用不一定被撤销 |
| template save/load | 保存/载入可复用的运行文件系统产物 | 不等于完整VM备份或所有挂载/Engine数据/运行进程迁移 |

例：Agent已把宿主共享文件`result.txt`改错，随后stop/rm通常不会使原文件自动恢复。恢复应依版本控制或备份，外部系统副作用另行对账。两个不同沙箱如果共享同一宿主工作区，文件并发冲突仍然存在。

诊断或settings读取也可能触发daemon启动；帮助文本的收集也可能尝试网络。源码中函数名叫“doctor”“check”或“help”不是零I/O/零副作用证明。首次学习先理解观察范围，再选择当前确需的诊断。

清理按明确拥有的对象身份进行。来源capture脚本有全局prune行为，不能因为README说“只清本项目”就默认安全；检查目标范围、共享状态和唯一数据。广泛reset、全局prune或清凭据不是一般学习笔记里的默认修复步骤。

## 4. 工作区有三种不同选择

### 4.1 直接读写挂载

优点是Agent立刻看到真实代码、修改可直接在宿主审阅；代价是权限也真实生效。它可能改源码、`.git`、CI配置、依赖脚本或其它可见文件。一次Git diff不能说明没读过秘密、没触发外部请求或没修改非Git管理内容。

### 4.2 只读挂载

能防止沿这条挂载写回，但不防读取或通过允许的出口披露内容；也不限制另一个host MCP拥有的文件权限。要保护secret，首先减少可见范围，不能只把整个含`.env`的目录改为只读就结束。

### 4.3 私有clone或无宿主挂载

私有clone让Agent在guest文件系统修改，产物取回后再审阅；mountless适合不需原仓库的独立工作。来源clone还将宿主源目录只读暴露于`/run/sandbox/source`，所以未跟踪敏感文件仍可能被读到。宿主CLI为建立取回路径还会改Git remote/refspec等配置，不能笼统称宿主完全没有变化。

取回commit只证明拿到了一个Git产物；仍须检查差异、来源、依赖、生成脚本和验证结果。后续在宿主执行构建或hooks是另一条信任边界。

**实践判断**：检查代码时只需某个子目录，应选择满足任务的最小可见输入；要让模型提出补丁而不直接改真实仓库，可用私有工作副本再审阅合并。若必须直接改共享目录，先说明哪些路径可改、怎样防并发覆盖和怎样恢复。

## 5. 网络、端口与秘密不是一把总开关

### 5.1 域名允许不等于数据使用获准

网络控制可以限制目标域名、端口和协议，更细能力还可能限制HTTP方法/路径。允许访问某个API，不代表任何正文或任意操作都已获准；向允许域名POST敏感内容仍可能泄露。

规则有平台/组织、全局、VM或kit等不同作用范围。应记录当前有效规则、来源与版本，再解释一次允许/拒绝；不要用“deny永远覆盖任何allow”一句话代替具体合并语义。来源存在hostname、CIDR、协议、组织授权上限等特殊条件，简化模型不能充当实际authorizer。

静态policy check表示给定参数的规则判断，不等于真实DNS、TLS、认证和应用请求成功。代理CONNECT200仅表示隧道建立；目标HTTP403与工具退出0可以同时发生，例如调用方没有把HTTP错误转成非零退出。检查传输、应用状态与任务结果三层。

### 5.2 端口是另一条入口

guest服务监听、宿主端口映射和访问者认证分别核。回环绑定减少外部暴露，却不等于服务有身份验证；同机其它进程仍可能访问。来源默认tcp4与显式双栈tcp不同，云端公开URL又是另一入口；不要把本地端口实验的结果推广成云端访问策略。

### 5.3 真实凭据可留在外部，能力仍能被滥用

代理凭据方案可以让guest持占位值，实际请求到指定目标时由外部代理替换。它减少直接把密钥放入VM的需要；但Agent若能触发真实API，仍可能产生读写与费用。密钥未进入VM，不等于没有获得使用该密钥的能力。

来源自定义秘密的替换依代理路径与目标绑定，普通环境变量、磁盘文件、透明隧道和显式header配置不能混为同一机制。host secret import是显式读取；`-e KEY`一类明文环境传递也不是自动的secret管理。保密、认证、授权与目标绑定分别解释，不能用“安全注入”四字替代。

SSH agent转发通常不是复制私钥，但能请求签名认证；共享skills、剪贴板或远程控制也会打开额外数据/执行通道。它们不是主文件挂载权限能够统一约束的对象。

## 6. MCP的执行位置比名字更重要

同为MCP，服务器可能在guest容器、宿主stdio子进程或远端。若宿主进程有读写文件或调用服务的权限，VM文件系统隔离不能自动限制它。工具声明“只读”是提示，不代替真实实现和权限检查，详见[MCP核心章节](../../Agentic%20Design%20Patterns/01-核心章节/10-模型上下文协议-MCP.md)。

来源至少区分sbx的宿主网关、Docker MCP Toolkit网关和托管网关，它们的设置、身份、工具目录与生命周期不必共享。注册一个server、允许某VM看见、动态load和成功调用是四个步骤；目录里“有工具”不能直接当本实例已经可用。

多Agent委派也不扩大授权。同步transfer、handoff和后台任务可能有不同上下文/工具集合；后台任务不可交互确认时需要明确拒绝/停止策略。外部harness还可能执行自己的权限模型，不能只靠一层“继承权限”标签推导全部后端一致。

## 7. 看回放记录时，先找证据来自哪一层

| 证据 | 可以支持 | 不能直接支持 |
|---|---|---|
| help/schema | 某固定版本声明的参数、字段、部分默认 | 真实loader一定采用默认，服务可用，动作已执行 |
| 诊断成功 | 这次检查覆盖的安装/平台/连接条件 | 所有隔离门、模型质量与业务正确性 |
| 录制HTTP/SSE | 作者那次请求、工具提议、返回与终态 | 本机现在运行成功或所有版本相同 |
| 规范化快照相同 | 指定遮罩与比较规则下结果相同 | 原始字节、顺序、摘要/签名或效果都相同 |
| 本地fixture/模拟模型 | 接线、解析和有限失败路径 | 真实模型表现、权限没有旁路或真实云调用成功 |

本次完整解析6份gzip的37,970个SSE JSON帧，并静读31组交互的有效请求、工具、输出、usage与终态。逐token模型草稿只做数量/hash登记，明确作为无独立长期价值的推测内容排除，没有当作专业事实或指令。

几个可直接学习的反例：

1. 列目录只回文件名，模型就声称文件有1行；后来read_file才给了真实内容。后一次核实不使第一次猜测变成有证据的回答。
2. 后台Agent调用被拒后模型仍反复提出，说明提出工具调用不等任务已运行；末轮只有提议时，不能补造完成回执。
3. reviewer按提示输出APPROVED，只是模型格式行为，不是有效人类批准或已验证的安全结论。
4. API的pong请求有finish/done/usage；两个标题请求虽HTTP200，却没有正文及完整终态，不能记为成功标题生成。
5. 源`--sandbox`因SQLite错误在模型前失败；另一目录的成功是条件变化后的另一条实验路径。

来源capture程序还会遮罩路径、时间、费用、digest或排序某些并行事件；比较时必须说明变换范围。manifest被解析成另一种JSON表示后，可读其语义字段，却不能用新字节声称原始摘要/签名已验证。失败后外层进程仍exit0、检查模式因前提缺失skip，也都可能发生。

## 8. 用一份小审阅结果开始学习

不需要先租云资源或启动整个工具栈。对一个计划或已有转录，先填下表：

| 项目 | 应写出的内容 |
|---|---|
| 任务 | 输入、允许修改范围、目标产物与判据 |
| 身份/位置 | 调用者、运行器、模型、工具分别在哪，使用什么凭据 |
| 能力 | 可读/写路径、出口、端口、host MCP、SSH、共享skills |
| 版本 | CLI/插件/guest模板/kit/schema及实际解析资产标识 |
| 过程 | 准入、工具提议、实际调用、拒绝/未知、重试与总预算 |
| 结果 | 原始回执、规范化范围、产物、语义验收及未验证部分 |
| 恢复 | 需要保留什么，停止/删除会影响哪些具体对象，外部效果如何对账 |

参考练习：一次轨迹只有“请求HTTP200、模型输出APPROVED、没有工具回执”。合格答案应标传输返回、模型文本、实际动作未知，不能认定补丁已保存、权限已通过或已部署。再给出直接挂载/只读/私有clone三种选择，说明各自写回和数据读取的区别。

实际开始运行时，再为所选一条最小路线制定可执行验证：先核固定配置与可见输入，再确认真实工具位置，最后对产物/失败路径留证据。已有预算、缓存、幂等和恢复方法沿[推理与服务化](../../LLM%20工程实践/03-推理与服务化.md)、[异常处理](../../Agentic%20Design%20Patterns/01-核心章节/12-异常处理和恢复.md)学习，不在这里重复维护一套框架实现。
