# 07｜安全、可观测性与故障诊断

## 1. 容器安全的本质

容器共享宿主机内核，因此安全必须按“纵深防御”设计。

```text
可信镜像
→ 最小权限
→ namespace
→ cgroup
→ capabilities
→ seccomp
→ AppArmor/SELinux
→ network/storage policy
→ runtime monitoring
→ supply-chain verification
```

任一层都不是绝对边界。

## 2. 最大的高风险入口：Docker daemon

Docker daemon 可以：

- 挂载主机目录；
- 启动 privileged 容器；
- 访问设备；
- 修改网络；
- 运行 root 进程。

因此：

- `docker.sock` 不应随意暴露；
- 不应把 socket 挂进不受信任容器；
- `docker` 用户组接近 root 权限；
- 远程 API 必须做认证、TLS 和访问控制；
- 共享环境优先考虑 Rootless 或平台级隔离。

## 3. Namespace 不是完整安全边界

namespace 隔离的是视图，但容器仍共享：

- kernel；
- 部分内核攻击面；
- 物理资源；
- 某些设备和 host interface。

运行恶意/不受信任代码时，应考虑更强边界，例如 VM、Kata、gVisor 等。

## 4. Capability

Linux root 权限被拆为多种 capability。

安全原则：

```text
默认能力
→ 尽量 drop
→ 只 add 必须能力
```

不要为了“先跑起来”直接使用 `--privileged`。

## 5. seccomp

seccomp 限制可调用的系统调用集合。

作用：

- 缩小内核攻击面；
- 阻止应用不需要的高风险 syscall。

自定义 profile 前需要理解应用行为，过度收紧会导致难排查故障。

## 6. AppArmor / SELinux

它们提供 Mandatory Access Control，可以进一步限制：

- 文件；
- socket；
- capability；
- 进程行为。

与 namespace/capability 组合，形成多层安全边界。

## 7. 镜像供应链安全

镜像安全不仅是“扫 CVE”。

完整链路：

```text
source
→ dependency lock
→ build
→ SBOM
→ vulnerability scan
→ provenance
→ sign
→ registry policy
→ deploy verification
```

关注：

- 基础镜像是否可信；
- 依赖是否锁定；
- 构建器是否可信；
- secret 是否进入层；
- SBOM 是否完整；
- 签名是否验证；
- 部署是否固定 digest。

## 8. 漏洞扫描

扫描结果需要结合：

- 是否可达；
- 是否运行时加载；
- 是否有修复版本；
- exploitability；
- 业务暴露面。

不要把“漏洞数量”直接当作风险排序。

## 9. 日志

容器日志首先要遵循：

- 应用写 stdout/stderr；
- 不依赖容器内部本地日志文件；
- 日志平台统一采集、解析、索引、保留；
- 明确 rotation 与存储成本。

日志回答“发生了什么”，但无法独立解释系统整体状态和跨服务因果。

## 10. Metrics

核心容器指标：

- CPU usage / throttling；
- memory working set；
- RSS / cache；
- OOM；
- network bytes/errors；
- disk I/O；
- restart count；
- latency / error rate / throughput。

Prometheus 适合时序指标采集；Grafana 负责展示。关键是建立：

```text
signal
→ alert
→ owner
→ runbook
→ response
→ postmortem
```

没有闭环的告警只是噪音。

## 11. ELK / 日志平台

典型链路：

```text
container logs
→ agent / shipper
→ processing
→ Elasticsearch
→ Kibana
```

选择日志平台时关注：

- 吞吐；
- retention；
- 查询模式；
- 索引成本；
- 多租户；
- 结构化日志；
- 数据合规。

## 12. 实时诊断

### `docker stats`

快速观察：

- CPU；
- memory；
- network；
- block I/O；
- PIDs。

适合局部定位，不替代长期监控。

### `docker inspect`

检查：

- mount；
- network；
- state；
- env；
- health；
- resource limit。

### `docker logs`

先确认主进程到底输出了什么。

### `docker exec`

进入容器做最小化诊断。生产镜像可能没有完整 shell/诊断工具，此时可使用临时 debug 容器或平台调试能力。

## 13. OOM 排障

内存故障常见链路：

```text
工作集增长
→ 接近 memory limit
→ reclaim / pressure
→ OOM kill
→ container restart
```

排查顺序：

1. 是否 OOMKilled；
2. limit 是多少；
3. working set 是否持续增长；
4. 是否内存泄漏；
5. cache 是否被误判；
6. 进程是否有语言运行时 heap limit；
7. 上游流量是否异常；
8. 是否应该扩容而不是单纯提高 limit。

## 14. 性能优化

优先顺序：

1. 先测量；
2. 找瓶颈；
3. 区分 CPU / memory / I/O / network；
4. 优化应用；
5. 再调容器资源。

常见问题：

- CPU throttling；
- 内存限制过低；
- bind mount I/O 慢；
- 日志过量；
- 镜像过大导致冷启动慢；
- 跨网络服务链太长；
- 数据库连接池无上限。

## 16. 把“启动失败”拆成可核对证据

复用 01 的 `study-web`，只读取其状态：

```bash
docker ps -a --filter name=study-web
docker inspect study-web --format '状态={{.State.Status}} 退出码={{.State.ExitCode}} OOM={{.State.OOMKilled}}'
docker logs --tail 50 study-web
docker stats --no-stream study-web
```

容器已删除时 inspect 报不存在是预期，需要先按 01 重新建自己的练习对象。退出码 137 常与 SIGKILL 有关，但不能单凭它认定 OOM；结合 OOMKilled、事件、主机日志和资源变化。

自测：Docker HEALTHCHECK 变为 unhealthy 会自动重启吗？答：普通 Docker Engine 不会仅因为 unhealthy 自动重启；restart policy 主要响应进程退出，额外编排/自动恢复策略需要单独配置。调试输出可能包含配置和敏感环境变量，分享前只摘取必要字段。
