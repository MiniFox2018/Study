# 11｜Agent沙箱策略与审计

> 学习顺序：先读[Docker沙箱与Agent工作台](./10-Docker沙箱与Agent工作台.md)的执行位置、工作区和Kit合同，再读本章。目标是能解释一次请求为何被允许、批准是否仍有效，以及日志能证明到哪一步。
>
> 依据第一来源固定提交`1a8c4fd…`保存的Docker文档，原获取日2026-10-08；2026-10-18整理并对照官方关键页。以下组织治理主要针对**本地沙箱**；云网络采用另一配置体系。组织治理、审计的账号/授权与收费前提须按实际服务核，不能由一份YAML推定已开通。

## 1. 先确定策略在哪一层生效

假设Agent要读项目、调用工单MCP并请求代码托管API。至少有四个不同问题：能否挂载项目目录、能否连API、能否调用MCP工具、外部账号能否完成该业务。允许其中一个不替代其它三个。

| 控制面 | 判断对象 | 典型生效点 |
|---|---|---|
| 文件系统 | 宿主workspace路径及read/write | 创建沙箱、建立挂载时 |
| 网络 | 目标host/IP、端口、协议，必要时HTTP方法与路径 | 后续连接或可检查的HTTP请求 |
| MCP注册 | 注册名、解析后的服务器身份/类型 | 增加注册时 |
| MCP使用 | 工具、资源、prompt、网关元工具 | 经过治理网关的调用时 |
| 外部系统 | 账号、仓库/租户、具体对象与业务权限 | 服务端实际操作时 |

修改文件系统规则不会自动撤掉现有挂载；禁止新注册也不会自动停止已加载MCP。要撤销已有能力，找实际使用面的控制点，再验证生效。策略同步成功、规则已保存和业务请求被阻止，是三个不同观察。

组织规则涵盖组织范围与用户所属团队范围。一个用户可能同时命中多份策略。组织治理启用后，普通local/Kit allow不再扩权，相关deny仍能收紧；无组织治理时再按本地与Kit规则判断。显示一条inactive allow，不能说明它当时实际放行。

## 2. 用具体请求检查规则组合

### 2.1 允许集合、明确拒绝和默认拒绝

有效策略中的allow一般累加，任一明确deny可阻止请求。组织层deny不能被团队层allow或本地批准重新打开。没有匹配allow的默认拒绝，与明确deny应分记：前者在某些本地模式会生成批准请求，后者不会靠批准越过。

例：团队允许`api.example.com`，组织拒绝同host的DELETE `/records/**`。GET `/records/7`可能允许，DELETE `/records/7`仍拒绝。若组织直接拒绝整个host，补一条GET路径allow也不能恢复。不要只数allow有几条，应拿**同一协议、host、端口、方法、路径**做判断。

来源的Open/Balanced/Locked Down是初始化基线。Locked Down没有基线allow，不等于存在覆盖全部Kit授权的明确deny。Kit仍可贡献允许项；需要禁止某目的地就检查有效deny。Balanced也可能包含广泛通配域，不能据名称推断只允许少数模型API。

### 2.2 目标匹配要保留层级

`example.com`不包括子域；`*.example.com`只匹配一层；`**.example.com`覆盖更深层。根域与子域通常需要分别列出。域名无端口可能允许多个端口，带`:443`才限制到该端口。HTTP方法、IPv4/IPv6、TCP/UDP的覆盖范围都应单列。

HTTP规则可以在只允许某些方法/路径时提供访问，也可从已有host allow中扣除部分请求。路径`/repos`只匹配本身；`/repos/*`与`/repos/**`对目录深度不同。不能把query参数当路径规则的一部分。

本地CLI对HTTP路径的规范形式有限制，包括百分号编码、重复斜杠、点段等；组织UI与CLI在方法集合、目标类型和可写路径数上也不同。读取UI空选择时，要查它表示“全部可选方法”还是空集合；不能照搬Kit规范中空数组非法的解释。

只有经过可检查HTTP代理的请求，才有方法/路径的授权证据。纯SSH等非HTTP流量没有这些字段；host级检查通过也不证明DELETE被正确阻止。来源的`policy check network`只检查host/port，策略流量摘要也不能代替完整L7审计。

### 2.3 文件系统规则检查的是挂载路径

可写workspace要同时满足read与write，只有write规则并不够；只读挂载只需read。`/data/*`不等于`/data/**`，`~`的展开与`$HOME`等环境变量展开也不是一回事。跨macOS/Linux/Windows/WSL路径，应按实际路径格式分别匹配。

规则允许挂载不等于目录内容适合暴露。只读仓库内的未跟踪文件、被gitignore忽略的`.env`仍可能可读。目录项若是指向其它位置同一inode的硬链接，按路径授权不等于阻止通过该入口读写同一文件；不要把“符号链接不跟随到外部”推广到硬链接。

收紧规则后，已有挂载可能继续使用直到重建。记录旧沙箱ID、挂载路径、读写模式和规则同步时刻，不能仅凭管理端规则已经更新就称撤权完成。

## 3. 两种批准具有不同的持续时间

| 问题 | 网络目的地批准 | MCP会话内确认 |
|---|---|---|
| 起始请求 | 先被阻止，不等人答复 | 请求等待客户端确认和重新授权判断 |
| 批准后的范围 | 保存为该沙箱后续请求可用的规则 | 针对本次授权请求，不建立持久网络规则 |
| 绑定对象 | 具体host/port；命中HTTP规则时含具体方法/路径 | 已评估请求的摘要与会话 |
| 能否越过deny | 不能 | 不能越过匹配的forbid |
| 是否证明管理员审阅 | 不能 | 不能，仅同一客户端协议内确认 |

例如批准`api.example.com:443`不会批准另一沙箱，也不覆盖8443；策略中一个通配域可分别触发各具体子域批准。批准GET `/v1/data`也不能自动批准POST同一路径。

多个组织策略同时允许同一请求时，只要有匹配的批准要求，另一个普通allow不会把它消除。批准保存后，后来新增批准要求也不必然撤销已有grant；真正撤销要移除grant或加有效deny并复核。

网络批准后的首次失败请求不会自动重发。应先判断原请求是否确实未送达及能否安全重试；不要把“现在允许访问”当原业务已经成功。dismiss一般只是暂不处理，可能没有终结事件，下次请求还会出现。

MCP的`@requireApproval`是准确的产品注解名。拼成`@requireConsent`并不会获得同样行为。普通permit与带批准permit同时匹配时，批准要求仍优先；forbid则直接拒绝。客户端不支持elicitation、转发失败或再次评估不允许，都应拒绝；不能自动改成无批准执行。

来源还明确：自主MCP客户端可以程序化回答协议内elicitation。要实现管理员与执行者分离，需要另有独立身份、批准通道和不可绕过的服务端限制。网关弹过提示不能单独证明这些条件成立。

## 4. MCP策略从服务器身份走到具体动作

### 4.1 注册许可与使用许可各写一份

注册名由使用者选择，不是服务器的固有身份。对远端服务，匹配预期注册名与解析后的identityURL；否则相同名称可能换到另一个端点，同一端点也可能有多个别名。

使用阶段至少分开invokeTool、readResource、getPrompt；动态发现/附加服务器、code-mode和OAuth授权helper是网关元工具，属于invokePrimordial。只禁某服务器的工具，不自动禁止它的资源、prompt或独立授权helper。

撤销一台已注册服务器时，需要覆盖已存在的别名和使用动作；仅禁止register不会删掉旧记录。若Agent能从guest直接连接同一远端MCP，它不经过治理网关，还需网络策略限制。主机stdio服务器则在VM之外运行，必须另按宿主进程权限审阅。

### 4.2 不要信任工具自述来证明没有副作用

readOnly、destructive、idempotent、openWorld等来自服务端注解/目录元数据，属于提示信息。缺失值的保守默认并不能防止服务器错误自述。业务只读还应由实际服务账号、接口权限、目标范围与测试证据约束。

工具匹配使用裸name，不含显示前缀。只匹配`move_file`可能覆盖多个服务器的同名工具，应把服务器身份一起限定。resource URI与prompt名是不同属性。Cedar字符串like按整串匹配，`*`是通配，`?`为字面；args集合的contains不能当字符串子串操作。

这些是Docker定义的MCP策略面，不是所有MCP服务器通用标准。在该实现中，用户/团队由策略scope提供，不能假设自行写principal.role就会生效；注册阶段也没有调用阶段的request_time。

### 4.3 缺参数时不能让限制悄悄失效

以下为**自行编写的策略结构示意，未提交给任何策略服务或执行器**。假设read_ticket只应读当前项目的工单：

```text
默认：没有满足条件的permit，就拒绝。
允许条件：服务器身份符合预期；action=invokeTool；
          工具name=read_ticket；参数是对象；project字段存在；
          project等于本次获准项目。
明确拒绝：所有写工具以及不允许的服务器。
批准：即使同意一次确认，也不能越过上述明确拒绝。
```

Docker的context.args只呈现可支持的JSON对象参数；畸形或其它形状可能没有这个字段。条件须先检查context has args，再检查需要的字段。只写“金额>500就forbid”，同时又宽泛permit全部工具，缺失amount时forbid可能不匹配，造成漏挡。用明确的有效输入permit范围，并对未知输入拒绝；策略通过不替代工具参数类型、金额单位、对象归属的服务端验证。

展示列表也不等于允许使用。来源列出的listTools/listResources/subscribeResource在schema存在，但并非全部被Cedar门控。工具仍可出现在列表、调用时才拒绝。一次列表看不到工具也不能证明其它路径均不可调用。

## 5. 用审计区分“评估”“执行”和“业务结果”

审计记录至少需要知道谁、何时、哪个策略版本/模式、什么动作、哪个资源、何种判断。来源schema以category区分管理、评估、执行，用action_type区分network_egress、http_request、filesystem_mount、tool_invocation等。**ALLOW是授权判断，不能直接写成业务成功**；还需实际执行记录与服务端结果。

例如网络ALLOW后收到TLS错误，说明授权可能允许但传输失败。工具调用获准后退出码非零，说明不应归为策略拒绝。评估只记录一条连接，也不代表其中每个HTTP方法均被允许。保留原始事件ID与层级，避免把不同失败合并成“Agent坏了”。

`enforcement_mode=audit`表示记录判断但不强制执行；off表示治理未启用，并不等于字段缺失。来源另有若干批准事件不带该字段，缺失不能一律填off。模式、事件类别和schema版本一起解释。

网络批准可以用approval_request_id把“需批准”与“批准grant”相连；MCP批准并不保证有同一组关联字段。不能为方便统计伪造统一join键。批准记录若最终decision为DENY，还可能是grant应用失败，不能因它有approval对象就算成功。

日志不含prompt/参数值，不意味着没有敏感信息。用户名、邮箱、主机名、工单URI、项目目录、资源路径仍可能暴露身份与业务。必要的关联键可与对外展示的脱敏字段分开；摘要也不能替代对访问权和保留周期的管理。

### 5.1 本地JSONL、云投递与云沙箱不是同一件事

来源组织审计有许可证、登录和有效组织策略等前提；普通个人沙箱没有日志不能推断“没有访问”。Docker Cloud投递只是把相应审计记录送到云，不自动增加云沙箱的事件覆盖。

本地由daemon写入记录，而非每个CLI进程。写入中的.tmp在轮转/正常关闭时原子改名成.jsonl；收集器只取完整文件，需考虑轮转延迟。不要为“实时”直接把未完成文件当完整批次，也不能把尚未轮转的空目录当零事件证明。原子改名只说明文件发布边界，不自动证明跨采集器恰好一次投递。

去重可按audit_event_id，对账daemon会话与文件序号；schema_version变化时更新字段映射。来源声明本地完整日志不自动删，保留和磁盘清理由采集者负责。云搜索保留、归档保留与CSV导出的条数/下载有效期又是独立约束；一次下载不是整段历史完整归档。

托管搜索、CSV、SIEM要求相应cloud delivery，只有本地投递不会自动开启它们。SIEM连接验证只说明某次端点可达/凭据接受，不证明后续无丢失、无重复或过滤正确。记录投递模式、启用时刻、采集延迟、断连窗口与补发核验。缩短云保留配置也不能推定立刻抹去曾按更长期限保留的旧记录。

## 6. 生效时机与故障定位

先确定账号/组织/团队是否正确、治理是否启用，再看最后同步时刻、规则状态与实际资源。多组织治理无法确定时，来源采用fail closed，不能靠加local allow解开。来源的组织同步间隔仅是该版文档行为，不是服务等级保证。

| 看见的现象 | 下一步应分辨什么 |
|---|---|
| local allow已保存但仍拒绝 | 是否因组织治理而inactive，是否有deny，是否需要批准 |
| host级检查Allowed，DELETE仍失败 | 是否存在L7限制，是否在可检查代理路径 |
| 注册被禁止，旧工具仍列出 | 是否只改register；列表是否本来不门控；使用规则是否涵盖别名 |
| 文件规则已收紧，旧进程仍能写 | 旧挂载是否仍在，是否需要有保存成果的重建 |
| 无审计结果 | 账号/许可/治理/投递、时间窗口、轮转与筛选是否满足 |
| 有DENY记录但动作仍发生 | 是否audit模式、事件是否另一请求、是否存在直接连接或宿主旁路 |

`policy reset`不是只刷新规则：来源会清本地规则与已批准grant、重启daemon并停止相关沙箱。完整reset还可能删数据。优先保存诊断与身份、查同步和有效规则，再判断是否需要有明确范围的恢复；不能将来源排错页的破坏性命令机械加入教程。

登录组织限制依赖端点管理配置：只在管理后台写组织规则，却允许终端改用个人账号，可能没有约束到目标执行者。测试用用户偏好与真正受管理配置的优先级不同。Linux配置的普通文件、属主与不可组写检查，是配置来源可信性条件；文件语法解析成功不证明终端已有效执行。缺失allowedOrgs还可能表示限制未启用，应独立验证。

## 7. 一次最小推演与参考答案

练习：工单服务器注册为tickets和tickets-old；团队允许读取、组织禁止写，网络要求批准。Agent在tickets-old调用一个自述readOnly的close_ticket，并从guest另建直连。管理员只禁止新register，随后看见一条APPROVAL_ALLOW。

判断步骤：

1. 检查两个别名的实际endpoint与使用规则；禁止新register不封闭旧入口。
2. readOnly自述与close_ticket实际副作用不一致，不能凭注解放行；使用端和服务端账号都应限制写操作。
3. 查APPROVAL_ALLOW属于网络还是MCP、grant范围和最终decision/mode；它不证明工单已读，更不证明关闭获准。
4. 直连不经过治理网关，应按网络规则、服务端账号权限和真实请求另核。
5. 只有策略评估、批准绑定、实际执行及工单状态均能对账，才可描述该次结果。当前推演没有运行服务器，也没有产生真实批准或业务操作。
