# AI 容器与硬件运行边界

先修：[镜像与构建](./02-镜像-Dockerfile-构建.md)、[数据与网络](./03-数据-网络-仓库.md)、[Compose](./04-Compose与多容器应用.md)。本章把已有概念用于AI开发、训练与服务，重点是模型/数据持久化与主机硬件边界。

## 1. 容器固定了什么

镜像包含文件系统中的程序、库及配置，不能固定主机内核、CPU指令、GPU驱动、挂载输入、网络服务、时间和所有随机行为。同一个digest也可能在不同硬件上得到有差异的数值结果；tag可被更新，多架构manifest还可能为不同平台选择不同镜像。

原教程图“每条Dockerfile指令都加层、每个主机完全相同”是过度简化：RUN/COPY等可创建文件系统层，ENV/CMD等主要影响配置元数据；相同镜像提供更可控用户空间，不是运行结果绝对一致保证。

Docker Engine 的Linux容器使用Linux内核；macOS Docker Desktop通常通过Linux虚拟机运行，不直接共享macOS内核。

## 2. 三种镜像角色

| 角色 | 保留内容 | 生命周期 | 常见误区 |
|---|---|---|---|
| 开发工作台 | 编辑/Notebook/调试及任务依赖 | 可交互迭代 | 把大工具栈直接变生产镜像 |
| 训练任务 | 训练入口、依赖和恢复逻辑 | 批处理、有产物 | checkpoint只写容器临时层 |
| 推理服务 | 必要运行库、模型加载、健康/服务入口 | 长驻服务 | 只看能import而不验输出和延迟 |

选择基础镜像：轻量Python适合CPU工具；预装框架镜像减少安装步骤；CUDA runtime镜像用于已有可运行产物；需要nvcc编译扩展时才考虑devel镜像。大小、启动速度和兼容性要测量，源站旧版CUDA/PyTorch组合不作为当前默认安装方案。

## 3. 一个完全自包含的CPU构建练习

新建独立练习目录，文件 `check.py`：

```python
import json
from pathlib import Path

result = {"结果": sum(range(10)), "模式": "CPU标准库练习"}
assert result["结果"] == 45
out = Path("/outputs")
out.mkdir(exist_ok=True)
(out / "result.json").write_text(json.dumps(result, ensure_ascii=False), encoding="utf-8")
print(result)
```

文件 `Dockerfile`：

```dockerfile
FROM python:3.12-slim
ENV PYTHONUNBUFFERED=1
WORKDIR /app
COPY check.py /app/check.py
CMD ["python", "/app/check.py"]
```

3.12是此练习兼容基线，不声称最新版本。生产应核对基础镜像支持、安全更新与digest，不照此小程序把root作为所有服务默认身份。

```bash
mkdir -p outputs
docker build -t study-ai-lab .
docker run --rm -v "$PWD/outputs:/outputs" study-ai-lab
cat outputs/result.json
```

预期结果45；删除容器后主机outputs中的文件仍在。命令需要daemon可达、镜像可下载和路径可挂载；CLI存在不代表能运行。本次仅静态检查Dockerfile结构及宿主Python逻辑，没有启动Docker daemon或宣称容器实跑。

## 4. 数据与模型为什么分开挂载

代码可随镜像或开发bind mount，输入数据/模型挂载为只读，输出挂到独立位置：

```text
/data（输入） → 训练/推理程序 → /outputs（结果）
/models（固定revision资产） → 程序
```

没有显式挂载时，普通容器停止不会自动删除全部文件，但容器移除/重建可能丢失可写层内容；`--rm` 会在退出后移除容器。命名卷与bind mount生命周期不同，先检查真实挂载，不能把“停止”和“删除”混为一谈。

挂载会遮蔽镜像对应目录的已有内容。开发挂整个项目目录便于迭代，生产则明确最小资产与权限。模型位置、框架缓存环境变量与实际加载路径要一致，避免挂了/models仍向另一缓存目录重复下载。

## 5. NVIDIA 与 Apple 的路径不同

Linux主机使用NVIDIA容器时，一般需要受支持GPU、主机驱动、容器集成工具与兼容的框架构建；容器内CUDA toolkit不能替代主机驱动。要看当前官方兼容矩阵，不能只对比两个字符串是否相等。

Docker Desktop 的普通 `--gpus` Linux容器透传按官方文档走Windows WSL2/NVIDIA条件；不能把它原样用于macOS原生MPS。其他Docker产品的模型加速路径是另一能力，不能因此推断任意Linux CUDA容器能访问Apple GPU。

在Apple Silicon上强制构建amd64镜像会引入仿真成本，不会生成NVIDIA GPU。优先选择与工作负载一致的平台路径；需要MPS/MLX时按原生框架支持执行，而不是反复安装CUDA。

硬件检测、容量与计时见[跨硬件部署](../../LLM%20工程实践/09-跨硬件部署.md)。

## 6. 多服务组合要验证两类地址

Compose默认网络中容器可用服务名如 `vector-store:6333` 通信；浏览器/主机通过发布到本机的端口访问，两者不是同一网络命名空间。

组合Notebook与向量服务时分别记录：Notebook环境与kernel、向量服务版本、持久卷、认证、端口、实际调用依赖。原教程调用qdrant-client却未把它列入依赖，不能从容器已启动推断Python客户端可导入。

本地开发服务优先只发布回环地址，保留Jupyter token/密码等认证。向量服务的tag、健康API及client兼容性使用前查官方文档；不为了“完整吸收”保留固定旧tag和未经验证的GPU Compose。

## 7. 从构建到结果的五步验收

1. `docker version` 区分client/server，确认daemon。
2. 构建时检查平台、层缓存、锁定依赖和实际镜像标识。
3. 启动后检查进程、日志、退出码或健康状态。
4. 从调用方验证容器间连接和正确认证，不能只在主机curl通过。
5. 比较结果、输入版本、持久文件、资源和失败路径，再称为任务完成。

修改依赖后重建镜像；层缓存不会自动发现外部包索引中“同一个latest”内容变化。删除卷、批量prune前先确认是否有唯一实验数据，源站的清理命令不直接作为默认操作。

## 8. 练习与答案

执行CPU例子并检查主机结果 → 修改程序输出字段再重建 → 比较缓存命中 → 从挂载路径取结果 → 在自己实际需要时再设计训练或推理镜像。无daemon时只能做静态练习，记录边界。

自查：相同镜像启动，模型输出为什么仍可能不同？答案：硬件、内核、驱动、输入、外部服务、随机性等没有由镜像独立固定。

自查：`docker compose down -v` 会比普通down影响更多什么？答案：可能删除项目命名卷及数据，必须核对该卷生命周期。

## Agent工作台的进一步边界

容器镜像、microVM沙箱、Agent运行框架和模型后端分别管理不同对象。需要让Agent处理代码与工具时，沿[Docker沙箱与Agent工作台](10-Docker沙箱与Agent工作台.md)核实际运行位置、挂载、网络/秘密与host MCP，而不从“在Docker里”推断全部工具与数据都已隔离；原CPU容器练习继续由本章维护。


## 9. 并置训练的共享内存与健康门禁

这部分是理解容量账和失败证据的案例，不是让当前Mac运行NVIDIA容器。作者环境是一个GB10、128GB CPU/GPU共享物理池，Ray报告可用节点121.69GB；不能把该GPU、镜像架构或热参数当所有机器的默认。

### 先计算驻留，再看实测峰值

mixed-precision Adam常见粗略状态账为每参数约16B：低精度权重/梯度、主权重与两矩；具体优化器、分片和主权重策略会变化。按假定总参数量0.6B约9.6GB、1.7B约27.2GB、4B约64GB（应从config/权重核真实参数，不只读模型名称），还没加激活、引擎另一份权重、KV、CUDA图和传输缓冲，不能把它叫总峰值或足够容量证明。

手册实际1.7B只跑4步/256token回答；没有验证1.7B按1024token原配方。4B在两次试验被Ray以节点115.86/121.69GB和119.18/121.69GB停止，降低引擎fraction0.4→0.2未避免；这只是此配置的结果，不能推出所有4B或所有统一内存机器都训不了。

统一物理池中的host offload可以让出GPU分配，但状态仍占节点物理内存，且可能有复制/重映射/页驻留与带宽成本。不能直接说“offload到CPU等于释放整机内存”或“共享内存所以没有任何数据搬运”。Ray进程RSS列表也不穷尽GPU分配和共享页；未列出的75GB归因GPU只是作者解释，缺乏逐项测量，不能简单把各RSS相加当唯一内存账。

Ray节点内存保护与CUDA分配失败是不同故障层。先读哪层报错，再减模型、并发、回答长度、缓存或激活；提高阈值只推迟保护，不创造容量。小引擎fraction也不是越低越安全：作者0.02仅留3082个KV token，首rollout385.5s；0.25留211813token约60.7s。它同时改变容量和排队/换入条件，不能只看启动未OOM。

### 停止条件必须同时覆盖致命错误、进度与依赖可见性

作者一次引擎启动失败后63分钟仍有200533条503；运行进程存在不等有进展。其看门狗按每30秒观察过去60秒、错误数>100连续若干有效观察触发停止。健康16回答试验也有22357条短促503，独立重建30种观察起点得到6-check误停17/30，10-check为0/30、持续错误模型273～302s触发。这只校同一错误轨迹，不能承诺生产无误报/5分钟内一定停止。

每次观测窗口重叠50%，不是十份独立证据；source脚本读日志失败不重置strike，docker stop失败仍exit1，所以“连续检查”和“已停容器”都需明确语义。还要单独核目标容器ID、停止确认、看门狗退出原因和自身健康。源脚本正常结束exit0、触发停止exit1、无法观察/参数错exit2；外层脚本需区分它们，不能统一叫训练失败。

503单指标还会漏掉其他挂死：作者缺reward模块的测试近两小时无rollout，只有44条503，看门狗没停。较完整门禁应同时监控引擎健康、首步/后续进度期限、致命异常、资源压力、总预算和观测链可用性，停止后保留未知效果与诊断记录。

热守卫按作者机器的84℃暂停、至少45秒后≤74℃恢复，或到120秒强制恢复，并只挑匹配镜像的第一个容器。它不是普遍热安全策略，也不能替代硬件散热/温控保护；读温度失败、多GPU选择、可变tag、停止目标、异常退出与resume确认都需另设计。这里不复制可直接操作真实容器的自动暂停脚本。
