# 05｜底层实现与容器生态

## 1. Docker 的组件关系

现代 Docker 不应被理解成一个单一二进制。

典型链路：

```text
docker CLI
   ↓ API
dockerd
   ↓
containerd
   ↓
runc
   ↓
Linux kernel
```

- **docker CLI**：用户入口；
- **dockerd**：镜像、网络、卷、API 等高层管理；
- **containerd**：容器生命周期与镜像运行时管理；
- **runc**：按 OCI Runtime Spec 创建和运行具体容器；
- **kernel**：真正提供 namespace、cgroup、filesystem、network 等能力。

理解这条链路后，才不会把 Docker 与“容器技术本身”混为一谈。

## 2. Namespace：隔离“看到什么”

常见 namespace：

| 类型 | 隔离对象 |
|---|---|
| PID | 进程视图 |
| NET | 网络栈 |
| MNT | 挂载点与文件系统 |
| UTS | hostname/domain |
| IPC | 进程间通信 |
| USER | UID/GID |
| cgroup namespace | cgroup 视图 |

容器隔离不是“创建一台新机器”，而是让一个进程看到被限制的系统视图。

## 3. cgroup：限制“能用多少”

cgroup 负责资源控制与统计：

- CPU；
- memory；
- PIDs；
- I/O；
- 其他控制器。

生产中必须显式思考资源边界，否则一个容器可把整台主机拖垮。

典型原则：

- 为关键服务设置 memory limit；
- 为 burst 服务设置合理 CPU 限制；
- 观察 OOMKilled；
- 避免把 limit 设置得低于应用稳定运行所需；
- 区分限制与实际工作集；Kubernetes 的 request 是调度/资源分配依据，不是普通 Docker run 的通用参数。

现代 Linux 主要向 cgroup v2 收敛，设计和排障时应优先以统一层级模型理解。

## 4. Union / Overlay 文件系统

容器镜像利用联合文件系统把多个只读层叠加成统一视图。

```text
container writable layer
------------------------
app layer
dependency layer
base OS layer
```

修改旧层文件时会触发 Copy-on-Write。

这解释了：

- 为什么镜像可以共享基础层；
- 为什么“后面删除文件”不一定缩小镜像；
- 为什么大型可写工作负载不应放在容器层；
- 为什么多阶段构建能有效减小最终镜像。

Linux 常见 OverlayFS，但 Docker 可能通过经典存储驱动或 containerd snapshotter 使用它；不能把所有当前安装都等同为 overlay2。用 `docker info` 核对实际后端，再分析对应数据目录。知识重点是“分层 + CoW”。

## 5. OCI 标准

OCI 把容器生态的关键格式标准化：

- Image Spec；
- Runtime Spec；
- Distribution Spec 等。

意义是：

```text
镜像格式
≠ Docker 专有格式
容器运行时
≠ 只能使用 Docker
```

Docker、containerd、Podman、CRI-O、Kubernetes 等可以围绕共同标准协作。

## 6. containerd 的位置

containerd 是通用高层容器运行时，承担：

- 镜像管理；
- 容器生命周期；
- snapshot；
- task 管理；
- 与低层 OCI runtime 对接。

Kubernetes 不需要 Docker Engine 才能运行容器，它通过 CRI 对接 containerd / CRI-O 等运行时。

这是理解“Docker 与 Kubernetes 已解耦”的关键。

## 7. Rootless

Rootless 模式把 daemon / 容器尽量放到普通用户权限边界内。

价值：

- 降低 daemon 被攻破后的主机影响；
- 避免把普通用户加入高权限 `docker` 组；
- 更适合共享开发机和受控平台。

限制可能包括：

- 某些网络模式；
- 低端口；
- cgroup 能力；
- 特权操作。

不能把 Rootless 理解为“绝对安全”，仍要做镜像、能力、系统调用和挂载控制。

## 8. Podman

Podman 与 Docker CLI 心智模型接近，但强调：

- daemonless；
- rootless；
- OCI；
- pod 概念。

适合需要更弱 daemon 中心化、偏 Linux 原生工作流的环境。

迁移时应逐项验证：

- Compose 兼容；
- volume；
- network；
- socket/API；
- build 行为；
- CI 集成。

## 9. Buildah

Buildah 专注镜像构建，可：

- 按 Dockerfile 构建；
- 脚本式构建；
- 直接操作镜像层和容器 rootfs。

它适合需要更细粒度构建控制的 Linux/OCI 工作流。

## 10. Skopeo

Skopeo 专注“镜像搬运与检查”，无需先运行容器。

典型能力：

- inspect remote image；
- registry 间复制；
- 查看 manifest；
- 删除远端镜像；
- 签名相关操作。

适合 Registry 运维和供应链流水线。

## 11. 安全容器运行时

### Kata Containers

通过轻量虚拟机提供更强隔离：

```text
container UX
+
VM-level boundary
```

适合多租户、不受信任工作负载和高隔离需求。

### gVisor

通过用户态内核/系统调用拦截降低容器直接暴露宿主内核的攻击面。

两者都在性能、兼容性与隔离之间做权衡。

## 12. WebAssembly 与容器

Wasm 的优势包括：

- 启动快；
- 体积小；
- sandbox；
- 跨平台字节码。

它与传统 OCI 容器不是简单替代关系。适合：

- 边缘计算；
- 插件；
- serverless；
- 高密度短任务；
- 受控执行环境。

容器仍更适合完整 Linux 用户空间和复杂系统依赖。

## 13. 基础操作系统镜像选择

长期原则是“**小而够用**”。

### BusyBox

极小工具集合，适合诊断和最简 shell 环境。

### Alpine

体积小，但基于 musl libc。需要验证：

- 二进制兼容；
- Python/Node 原生扩展；
- glibc 假设；
- DNS / locale / debugging 行为。

不要只为了几 MB 强行迁移。

### Debian / Ubuntu

生态完整、兼容性高，适合通用服务和依赖复杂项目。

### RHEL 系 / Fedora 系

适合企业生态和需要 RPM 工具链的场景。

镜像选择优先级：

```text
兼容性
→ 安全维护
→ 可重现
→ 可调试性
→ 体积
```

“最小镜像”不是唯一目标。


## 14. LXC / LXD 与 systemd-nspawn

Linux 容器生态不只包含 OCI 应用容器。

### LXC / LXD

LXC 更偏向“system container”模型：在共享 Linux 内核的前提下运行更完整的发行版用户空间，使用体验更接近轻量虚拟机。

理解区别：

```text
Docker / OCI 应用容器
→ 通常围绕单个应用与不可变镜像

LXC / LXD system container
→ 更像长期运行的一套 Linux 用户空间
```

它适合实验环境、系统级隔离和需要完整 init/多服务用户空间的场景，但隔离边界仍不是硬件虚拟机。

### systemd-nspawn

systemd-nspawn 可以直接运行一个 Linux OS 目录树或镜像，提供 namespace 等隔离，并与 systemd 工具链集成。

适合：

- 测试发行版 rootfs；
- systemd 原生实验；
- 轻量系统容器；
- 构建/调试隔离环境。

它不是通用生产编排器，也不替代 Kubernetes。知识重点是：容器是一组 Linux kernel 隔离机制，不等于 Docker 产品本身。

来源补充：USTC LUG Linux 101 Docs Ch08 supplement。

## 15. 只读观察：限制、镜像与内核各在哪一层

在已有运行中的练习容器上，将 `study-web` 换成真实名称：

```bash
docker info
docker inspect study-web --format '内存限制={{.HostConfig.Memory}} 字节，进程ID={{.State.Pid}}'
docker exec study-web uname -r
```

Memory 为 0 表示没有通过该字段设置显式内存上限，并不表示容器可无限用内存；外层虚拟机/父 cgroup/主机仍有限制。Desktop 显示的 PID 属于 Linux 虚拟机视角，不能直接拿它去匹配 macOS 的进程列表。

自测：非 root 容器和 Rootless Docker 相同吗？答：不同。前者约束容器进程用户，后者还让 daemon 等在非 root 权限下运行，控制的层级不同。
