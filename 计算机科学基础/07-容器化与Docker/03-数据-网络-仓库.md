# 03｜数据、网络与镜像仓库

## 1. 容器为什么必须显式设计数据层

容器本身应尽量无状态。数据是否能持久存在，取决于它写到哪里。

三种主要挂载方式：

| 方式 | 生命周期 | 主要用途 |
|---|---|---|
| Volume | Docker/平台管理 | 数据库、持久化应用数据 |
| Bind Mount | 绑定宿主机路径 | 开发代码、明确宿主机文件 |
| tmpfs | 内存 | 临时敏感数据、高速临时文件 |

## 2. Volume

Volume 与容器生命周期解耦。

适合：

- 数据库；
- 需要备份/恢复的数据；
- 多个容器共享的数据；
- 不希望依赖宿主机固定目录结构的部署。

运维时需要明确：

- 创建与归属；
- 备份；
- 恢复；
- 清理；
- 权限；
- 容量监控。

普通删除容器通常不删除命名卷，但显式删除卷/Compose down -v 会影响数据，匿名卷重建时也未必自动复用。挂载路径必须与镜像实际数据路径一致；保留卷还不等于已有备份。

## 3. Bind Mount

Bind Mount 把宿主机路径直接暴露给容器。

适合：

- 本地开发源码；
- 配置文件；
- 与宿主工具共享输出。

风险：

- 容器可能修改宿主文件；
- 主机目录结构成为部署耦合；
- UID/GID 与权限容易产生问题；
- 跨平台路径和 I/O 行为不同。

不需要写入时使用只读挂载。

## 4. tmpfs

tmpfs 主要使用内存，但 Linux 可能把页面换出到 swap，因此不能承诺敏感数据绝不落盘。它的生命周期短暂，不等于具备独立加密或保密保证。

适合：

- session / 临时缓存；
- 短生命周期敏感信息；
- 不需要持久化的高频临时文件。

代价是内存占用，且容器停止后数据消失。

## 5. Docker 网络心智模型

最重要的是区分：

- 容器自己的 network namespace；
- Docker 创建的虚拟网络；
- 服务名/DNS；
- 主机端口映射；
- 外部网络。

默认 bridge 网络提供基础 NAT 和隔离；自定义 bridge 网络通常更适合多容器应用，因为能获得稳定的服务名解析和更清晰的隔离边界。

## 6. 常见网络模式

### bridge

默认且通用。容器拥有独立网络空间，通过虚拟网桥连接。

### host

Linux Engine 中容器使用宿主机网络命名空间；Docker Desktop 的 host 网络是需启用的功能，其 TCP/UDP 层行为与 Linux 原生共享网络栈有差异，不能假设容器能直接绑定 macOS 所有网卡地址。

优点是少一层网络转换；缺点是端口隔离消失、可移植性降低。

### none

没有常规外部网络，适合完全离线或自己配置网络栈的场景。

### macvlan / ipvlan

使容器更像局域网中的独立主机。适合传统网络集成，但交换机、安全策略和平台支持要求更高。

### overlay

跨主机虚拟网络，常见于集群编排。

## 7. DNS 与服务发现

在用户自定义网络中，应优先通过**服务名**访问其他容器，而不是固定 IP。

```text
web → db:5432
api → redis:6379
```

原因：容器 IP 是运行时细节，可随重建变化。

## 8. 端口映射

`EXPOSE 80` 不会自动把端口开放给宿主机。

```bash
docker run -p 127.0.0.1:8080:80 app
```

需要明确：

- 监听地址；
- 宿主端口；
- 容器端口；
- TCP/UDP；
- 是否真的要对公网开放。

生产环境避免无意绑定 `0.0.0.0`。

## 9. 网络隔离

一个常见三层结构：

```text
Internet
   ↓
frontend network
   ↓
web / gateway
   ↓
backend network
   ↓
api / db / redis
```

数据库不应因为“方便”而直接映射到公网。通过网络分区把“谁能连谁”编码进基础设施。

## 10. Registry / Repository / Tag

层级关系：

```text
Registry
└── Repository: myapp
    ├── :1.2.0
    ├── :1.2.1
    └── :latest
```

镜像完整引用：

```text
registry.example.com/team/myapp:1.2.3
```

生产更可靠的引用：

```text
registry.example.com/team/myapp@sha256:...
```

## 11. Registry 的基本工作流

```text
build
→ tag
→ authenticate
→ push
→ scan/sign
→ deploy side pull
→ verify digest
→ run
```

企业镜像仓库通常还承担：

- RBAC；
- 漏洞扫描；
- 生命周期策略；
- 审计；
- 镜像签名；
- 多租户；
- 代理缓存。

Harbor 是典型容器专用方案；Nexus 更偏通用制品仓库。云环境也可直接使用云厂商托管 Registry。

## 12. 镜像来源安全

优先：

1. 官方镜像；
2. 可信组织；
3. 自建可审计镜像。

第三方镜像至少检查：

- Dockerfile / 源码；
- 最近维护状态；
- 架构支持；
- 漏洞；
- 是否固定 digest；
- 是否携带异常入口脚本；
- 是否包含不必要权限。

## 13. 镜像签名与扫描

现代供应链通常组合：

- 漏洞扫描：Docker Scout、Trivy 等；
- SBOM：记录软件物料；
- 签名：Sigstore/Cosign、Notation 等；
- provenance：记录构建来源和构建过程。

旧的 Docker Content Trust 不应作为新项目默认方案。

## 14. 镜像加速与代理的原则

镜像加速站点高度时效，不在知识库固定具体站点。

长期规则：

- 云内服务器优先使用云平台内部 Registry / cache；
- 团队可自建 pull-through cache；
- 代理要区分 daemon、CLI、build 和容器内应用四个层次；
- 第三方公共镜像站必须评估可信度与缓存策略。

## 15. 小实验：容器消失后命名卷仍在

前提：已有 Docker daemon 和可拉取的 busybox 镜像；确认 `study-volume-lab` 未被其他任务使用。

```bash
docker volume create study-volume-lab
docker run --rm --mount type=volume,src=study-volume-lab,dst=/data busybox:stable sh -c 'printf "保存成功\n" > /data/message.txt'
docker run --rm --mount type=volume,src=study-volume-lab,dst=/data,readonly busybox:stable cat /data/message.txt
```

第二个全新容器输出 `保存成功`；两个容器都使用 `--rm`，数据仍由命名卷保留。练习结束后先 inspect 确认卷归属，再决定是否删除自己的测试卷。

自测：bind mount 的“宿主路径”由哪台机器解释？答：由 Docker daemon 所在主机，不一定是发出命令的 CLI 客户端；远程 daemon 无法直接读取你的本机项目目录。Docker Desktop 另有主机文件共享机制。
