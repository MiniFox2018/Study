# 后续如何检查和记录更新

每次修改后在仓库根目录运行：

```bash
python3 tools/check_knowledge.py
```

只需要 Python 3.9 或更高版本及标准库。需要完整机器结果时：

```bash
python3 tools/check_knowledge.py --json /tmp/study-check.json
```

工具输出中文提示并返回退出码：0 表示所覆盖的结构检查通过，非 0 表示存在错误。

## 工具能检查什么

- 主库一级标题、代码围栏、常见损坏公式分隔符和控制字符。
- Markdown 内联链接、引用式链接目标、HTML 图片/链接属性的本地文件存在性。
- 主库指向 Markdown 标题的常见 GitHub 锚点；复杂内嵌格式仍应看实际渲染。
- Notebook 的 JSON、基本结构及所需单元 ID；已登记的上游空 Notebook 会明确提示。
- SVG 是否是可解析的 XML，捕获未转义符号与无效实体。
- 全部来源保全文件与记录中的 SHA-256 是否一致，新增文件是否登记。

工具不联网，不证明外链永远可达，不检查每条数学结论，也不会执行教材代码。专业审阅、公式渲染和有条件的实验运行仍需分别完成。

## 修改正文时

读前后文，确保术语、条件和符号一致。若结论来自简化假设，要把假设与例子写在附近。新示例应说明是完整程序还是片段、必要环境和预期结果；实际运行过再写“已验证”。

公式在 GitHub 使用 `$...$` 行内形式或独占行的 `$$` 块，避免字符串脚本把 `\frac`、`\beta`、`\theta` 当作转义控制字符。批量写入时用原始字符串或明确转义，写完重新读取并渲染检查。

## 修改来源材料时

先保留上游仓库、提交、原路径与 Blob 标识；检查实际 diff，记录是链接调整、数据路径修复还是正文修订。只有理解变化后，才能更新[来源完整性记录](./来源完整性.json)的本地 SHA-256，不能为了消除报错直接重算整个清单。

## 中文记录模板

```text
日期：
修改位置：
原问题：
修改结果：
验证：官方文档核对 / 手算 / 运行环境与结果 / 仅结构检查
学习影响：需要回看哪些章节，还是只修复排版与链接
尚未覆盖：
```

提交说明示例：`修正文档：补齐概率条件与统计练习答案`。PR 标题、说明、面向读者的待办与后续更新提示使用中文；既有历史提交不改写。
